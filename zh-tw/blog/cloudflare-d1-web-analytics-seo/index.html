為靜態部落格補上統計與 SEO：Cloudflare Web Analytics + D1 實戰

記錄 Astro 靜態部落格串接 Cloudflare Web Analytics、Pages Functions 與 D1 的完整過程，並系統補齊 Canonical、Open Graph、JSON-LD、Sitemap 與自動化 SEO 檢查。

部落格遷移到 Astro 與 Cloudflare Pages 之後，頁面已經夠輕量，也能完整靜態部署。但一個長期寫作的網站還需要回答另外兩個問題：文章是否真的有人看，以及搜尋引擎能否正確理解這些內容。

一開始我考慮過在專案裡嵌入記憶體資料庫。這個方案對一般伺服器程式或許能當作暫時的快取，卻不適合靜態網站與無伺服器執行環境：靜態檔案本身沒有常駐行程，Pages Functions 的執行個體也可能隨時建立與回收，記憶體中的計數既無法持久化，也無法在多個執行個體之間共享。

最後我採用 Cloudflare Web Analytics + Pages Functions + D1：Web Analytics 負責網站層級的流量趨勢，D1 負責文章閱讀量與自訂點擊事件；同時把 SEO 中繼資料、結構化資料與建置檢查補齊。這篇文章記錄完整的設計、實作、上線與排錯過程。

如果想先了解部落格的選型、雙倉庫發布與網域遷移，可以閱讀上一篇：從零重寫個人部落格：Astro + React + MDX + Cloudflare Pages。

最終架構

這套統計並沒有把部落格改成動態網站。文章、首頁、封存與標籤仍由 Astro 建置成靜態 HTML，只有 /api/analytics 交給 Pages Functions 處理。

flowchart LR
  A[造訪 lucaslz.com] --> B[Cloudflare CDN]
  B --> C[Astro 靜態頁面]
  B --> D[Web Analytics]
  C --> E[前端統計腳本]
  E --> F[/api/analytics<br/>Pages Functions]
  F --> G[(Cloudflare D1)]
  H[GitHub Actions] --> I[建置與 SEO 檢查]
  I --> B

兩套統計各自解決不同問題：

頁面造訪、訪客趨勢是可記錄頁面瀏覽
來源、國家與效能指標是不採集

Web Analytics 用來觀察全站，D1 用來回答與內容和互動有關的具體問題。它們不是重複建設，而是互補。

為什麼不使用記憶體資料庫

Cloudflare Pages 的主體仍然是靜態檔案。即使加入 Pages Functions，請求也執行在按需建立的 Worker 隔離環境中，不能假設某個 JavaScript 變數會一直存在。

如果這樣記錄閱讀量：

let views = 0;

export function onRequest() {
  views += 1;
  return Response.json({ views });
}

它會遇到三個根本問題：

  1. 執行個體重啟後資料歸零。
  2. 多個執行個體各自維護一份計數。
  3. 新部署也會遺失原本的狀態。

LocalStorage 只能保存在訪客自己的瀏覽器裡，也無法形成全站彙總。因此，需要一個真正的持久化儲存。D1 是 Cloudflare 託管的 SQLite 資料庫，可以直接綁定到 Pages Functions，部署結構最簡單。

用每日彙總控制寫入量

統計系統很容易走向「每次造訪就存一筆明細」的設計，但個人部落格通常不需要保存訪客層級的日誌。我更關心某天某篇文章有多少次瀏覽、某個入口被點擊多少次。

因此資料表結構採用每日彙總：

CREATE TABLE IF NOT EXISTS event_daily (
  event TEXT NOT NULL,
  path TEXT NOT NULL,
  target TEXT NOT NULL DEFAULT '',
  stat_date TEXT NOT NULL,
  count INTEGER NOT NULL DEFAULT 0 CHECK (count >= 0),
  updated_at TEXT NOT NULL DEFAULT (datetime('now')),
  PRIMARY KEY (event, path, target, stat_date)
) WITHOUT ROWID;

CREATE INDEX IF NOT EXISTS idx_event_daily_date
  ON event_daily (stat_date, event);

複合主鍵由 event + path + target + stat_date 組成。同一天同一種事件只更新一列，不保存 IP、User-Agent、完整 Referer 或使用者身分。

這種設計的好處是：

  • 資料量隨「頁面 × 事件 × 天數」成長，而不是隨造訪次數成長。
  • 查詢文章累計閱讀量只需要對每日計數加總。
  • 不需要維護訪客輪廓，隱私界線更清楚。
  • 即使流量增加，儲存與查詢成本也比較可控。

目前允許的事件包括：

page_view
article_click
article_impression
tag_click
search_click
nav_click
toc_click
cta_click
outbound_click

Pages Functions 統計介面

在專案根目錄加入 functions/api/analytics.js 後，Cloudflare Pages 會把它對應為：

GET  /api/analytics?event=page_view&path=/article
POST /api/analytics

GET 用來讀取某篇文章的累計閱讀量。POST 接收事件並使用 Upsert 更新當天計數：

await env.BLOG_ANALYTICS.prepare(
  `INSERT INTO event_daily
     (event, path, target, stat_date, count, updated_at)
   VALUES (?1, ?2, ?3, ?4, 1, datetime('now'))
   ON CONFLICT (event, path, target, stat_date)
   DO UPDATE SET
     count = count + 1,
     updated_at = datetime('now')`,
)
  .bind(event, path, target, statDate)
  .run();

介面還做了幾項必要的限制：

  • 只接受白名單中的事件。
  • 統一清除路徑尾端斜線與查詢參數。
  • 請求主體上限為 2 KB。
  • POST 只接受同源請求。
  • 外部連結只保存網域與路徑，不保存查詢參數。
  • 所有回應都設定 Cache-Control: no-store。

這些限制不能阻止所有惡意流量，但能避免介面變成任意字串收集器，也能降低把敏感查詢參數寫入資料庫的風險。

前端如何記錄與展示

頁面載入後，統計元件會向 /api/analytics 寫入一次 page_view。介面在完成寫入後直接回傳累計值，文章頁再顯示「幾次閱讀」。

const response = await fetch("/api/analytics", {
  method: "POST",
  headers: { "content-type": "application/json" },
  body: JSON.stringify({
    event: "page_view",
    path: window.location.pathname,
  }),
  credentials: "same-origin",
});

const data = await response.json();
showPageViews(data.total);

為了避免一次工作階段內重新整理頁面就不斷增加計數，前端使用 sessionStorage 對 page_view 與曝光事件去重。這裡的閱讀量不是嚴格的獨立訪客人數，而是一個輕量、可解釋的工作階段層級閱讀計數。

點擊類事件使用 navigator.sendBeacon() 傳送。訪客點擊連結並立即離開目前頁面時，Beacon 比一般非同步請求更適合完成最後一次小資料上報。

所有埋點透過 HTML 的 data-* 屬性宣告，元件不需要直接依賴統計實作：

<a
  href={postHref}
  data-analytics-event="article_click"
  data-analytics-target={postHref}
>
  阅读文章
</a>

在 Cloudflare 建立並綁定 D1

程式碼完成後，還要在 Cloudflare 儀表板設定真正的資料庫。

1. 建立資料庫

進入：

Storage & databases
→ D1 SQL Database
→ Create database

資料庫名稱使用：

lucaslz-blog-analytics

建立完成後進入 D1 Console，執行專案中的 migrations/0001_analytics.sql，確認資料表與索引建立成功。

2. 綁定 Pages Functions

進入：

Workers & Pages
→ lucaslz-blog
→ Settings
→ Bindings
→ Add

選擇 D1 database，變數名稱填寫：

BLOG_ANALYTICS

再選擇剛建立的 lucaslz-blog-analytics 資料庫並儲存。變數名稱必須與程式碼中的 env.BLOG_ANALYTICS 完全一致。

3. 重新部署

這裡有一個容易忽略的細節：新綁定只對之後的部署生效。儲存綁定後，既有的 Deployment 不會自動取得新環境。

綁定完成但沒有重新部署時，介面回傳：

HTTP/2 503

{"enabled":false}

觸發一次 GitHub Actions 部署後，Pages Functions 才能讀取 D1 Binding。可以提交正常異動，也可以在沒有檔案變更時建立一次空提交：

git commit --allow-empty -m "chore: redeploy with D1 analytics"
git push origin main

啟用 Cloudflare Web Analytics

D1 不適合重新實作一整套訪客來源、地理分布、裝置與效能分析。Cloudflare Web Analytics 已經提供這些網站層級指標，而且不需要為每個訪客建立用戶端識別。

在 Cloudflare Dashboard 中進入：

Analytics
→ Web Analytics
→ Add a site

輸入 lucaslz.com。由於網域已經屬於目前的 Cloudflare 帳號，可以選擇 Automatic setup，不需要手動把 Beacon 程式碼寫入 Astro Layout。

完成後儀表板會顯示：

Web Analytics are now set up

資料不會立即出現在儀表板中，首次啟用後需要等待 Cloudflare 收集與處理造訪資料。官方文件可參考：Cloudflare Web Analytics。

系統補齊 SEO

統計只能告訴我內容是否被造訪，SEO 則決定搜尋引擎與社群平台如何理解、收錄與顯示頁面。這次沒有只增加幾個 <meta> 標籤，而是統一由 BaseLayout 產生頁面語意。

基礎中繼資料

每個頁面現在都包含：

  • 唯一的 <title> 與 description。
  • 指向 https://lucaslz.com 的絕對 Canonical。
  • robots 索引指令。
  • zh-CN 與 x-default hreflang。
  • RSS 與 Web App Manifest 連結。
  • Open Graph 與 Twitter Card。
  • 1200 × 630 的絕對分享圖片網址。

Canonical 使用目前路徑與固定的正式網域產生，避免 pages.dev 預覽網址被當成另一份內容：

const canonical = new URL(Astro.url.pathname, Astro.site ?? SITE.url);

JSON-LD 結構化資料

一般頁面輸出 Person 與 WebSite。文章頁額外輸出：

  • BlogPosting
  • BreadcrumbList
  • 發布時間與更新時間
  • 作者、標籤、關鍵字與字數
  • 主頁面與分享圖片

JSON-LD 由物件序列化產生，而不是手寫 JSON 字串；序列化後再跳脫 <，避免文章內容破壞 script 邊界。

Sitemap、RSS 與 robots.txt

Astro 在建置階段產生 Sitemap，文章集合同時產生 RSS。robots.txt 指向正式 Sitemap。這樣新增 Markdown 文章時，就不需要再手動維護 URL 清單。

把 SEO 變成建置門檻

SEO 最怕「這次修好了，下次新增頁面又漏掉」。因此我加入 scripts/check-seo.mjs，在 dist/ 中逐個掃描 HTML，並檢查：

  • 頁面標題與 description。
  • Canonical 是否使用正式網域。
  • robots 指令。
  • 絕對 Open Graph 圖片。
  • 頁面是否只有一個 H1。
  • JSON-LD 是否為有效 JSON。
  • 文章頁是否具有 BlogPosting 與 BreadcrumbList。

統計介面也有獨立測試，涵蓋正常寫入、讀取、無效事件、跨域請求與 OPTIONS 回應。

GitHub Actions 中的發布順序變為：

Astro check
→ Astro build
→ 站内链接检查
→ SEO 检查
→ Analytics 接口测试
→ 同步 GitHub Pages 镜像
→ 部署 Cloudflare Pages

只要其中一項失敗，正式部署就不會繼續。

上線驗證

部署完成後，先讀取一個還沒有資料的頁面：

curl \
  "https://lucaslz.com/api/analytics?event=page_view&path=/howtostudy"

介面正常時回傳：

{
  "event": "page_view",
  "path": "/howtostudy",
  "total": 0
}

再開啟文章或傳送一次同源 POST，回應狀態應為 201：

{
  "ok": true,
  "event": "page_view",
  "path": "/howtostudy",
  "total": 1
}

重新整理文章頁後，標題下方會顯示：

7 分钟阅读 · 1 次阅读

最後在 D1 Console 中檢查彙總結果：

SELECT
  event,
  path,
  target,
  SUM(count) AS total
FROM event_daily
GROUP BY event, path, target
ORDER BY total DESC;

常見問題

介面回傳 503

{"enabled":false} 表示 Function 已經上線，但目前這個 Deployment 沒有取得 BLOG_ANALYTICS。檢查正式環境的 Binding，並在儲存後重新部署。

介面回傳 500

通常是資料庫已經綁定，但遷移尚未執行，導致 event_daily 資料表不存在。進入 D1 Console 執行遷移，再查看 Function 日誌確認 SQL 錯誤。

頁面沒有顯示閱讀量

依序檢查：

  1. 目前網域是否為 lucaslz.com、www.lucaslz.com 或 pages.dev。
  2. GET 介面是否回傳 200 與數值型態的 total。
  3. 文章頁是否存在 data-page-views 元素。
  4. 瀏覽器主控台是否有 CSP、網路或腳本錯誤。

閱讀量與 Web Analytics 不完全一致

這是預期結果。D1 的 page_view 在同一瀏覽器工作階段內去重，Web Analytics 有自己的訪客、機器人過濾與資料處理規則。兩者定義不同，不應該強求數字完全相等。

隱私與成本界線

這套實作刻意不儲存：

  • IP 位址
  • User-Agent
  • Cookie 識別碼
  • 使用者帳號
  • 完整 Referer
  • URL 查詢參數

D1 中只有事件、正規化路徑、目標、日期與次數。Web Analytics 與自訂事件的職責分開後，也不需要把第三方重量級分析 SDK 放進每個頁面。

D1 的免費額度與具體限制可能調整，應該以 Cloudflare D1 定價文件 為準。相比記錄每次造訪的明細，每日彙總可以顯著減少列數與讀取範圍，也更適合個人部落格。

最終結果

這次改造後，部落格仍然保持靜態優先：

Astro 静态内容
  ├─ Cloudflare Web Analytics：全站趋势与性能
  ├─ Pages Functions：轻量统计 API
  ├─ D1：文章阅读量与自定义事件
  └─ SEO：元数据、结构化数据与自动检查

最重要的不是多了一個造訪數字，而是建立了一套可以長期維護的回饋閉環：搜尋引擎能更準確地理解文章，我可以看到哪些內容真正被閱讀，建置流程則保證後續新頁面不會輕易遺失 SEO 基準。

對靜態個人部落格來說，這已經涵蓋絕大多數實際需求，同時沒有引入常駐伺服器、記憶體資料庫或複雜的使用者追蹤系統。
