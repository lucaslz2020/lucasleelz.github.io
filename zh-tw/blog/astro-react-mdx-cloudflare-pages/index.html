從零重寫個人部落格：Astro + React + MDX + Cloudflare Pages

從技術選型、行動端設計到雙存放庫發布、GitHub Actions、Cloudflare Pages 與阿里雲 DNS，記錄一次完整的個人部落格重構與上線過程。

用了幾年的部落格已經可以正常運作，但它越來越不像一個讓我願意持續寫作的地方：頁面偏文件站，行動端體驗一般，原始碼、建置產物與部署平台之間的關係也不夠清楚。

這次我沒有繼續修補舊專案，而是從零重寫了一套部落格。最終方案是 Astro + React + MDX，原始碼放在私有 GitHub 存放庫中，由 GitHub Actions 建置後同時發布到 GitHub Pages 鏡像存放庫和 Cloudflare Pages，lucaslz.com 由 Cloudflare 代管 DNS，並作為正式入口。

這篇文章記錄了完整的技術選型、專案結構、自動部署、DNS 切換與故障排查過程。

最終目標

重寫前先確定約束，避免在框架之間反覆搖擺：

  • 部落格首先要好看，而不是像 API 文件。
  • 預設同時適用於手機、平板與桌面端。
  • 文章使用 Markdown 或 MDX 管理。
  • 繼續使用 React，但不為純靜態內容引入完整的伺服器端框架。
  • 原始碼存放庫保持私有，建置後的靜態檔案可以公開。
  • 推送 main 後自動建置、檢查並部署。
  • 不維護伺服器，盡量使用免費的靜態代管與 CDN。
  • lucaslz.com 始終是唯一正式網址。

最終的發布鏈路如下：

  A[私有源码仓库<br/>lucaslz-blog] -->|push main| B[GitHub Actions]
  B --> C[pnpm install --frozen-lockfile]
  C --> D[Astro build]

為什麼選擇 Astro + React + MDX

Astro 負責靜態內容

部落格的核心是文章。文章不需要在瀏覽器裡重新執行一遍 React 才能顯示，因此靜態產生比完整用戶端渲染更合適。

Astro 在建置階段把內容產生為 HTML，預設不會把不必要的 JavaScript 送到瀏覽器。它的 Content Collections 可以驗證文章 frontmatter，動態路由可以統一產生文章頁，RSS、Sitemap、SEO 元資料也能在建置時完成。

對這個專案而言，建置結果就是一個 dist/ 目錄，不依賴 Node.js 伺服器，因此既能部署到 Cloudflare Pages，也能同步到 GitHub Pages。

React 只負責互動

保留 React，不等於讓整個部落格變成 SPA。目前專案只在需要互動的區域使用 React Island：

  • 站內搜尋
  • 深色模式切換
  • 行動端導覽

Mermaid 圖表由獨立的按需載入腳本處理，只有圖表接近可視區域時才下載渲染器。文章內文、首頁卡片、彙整與標籤頁都由 Astro 直接輸出 HTML。這樣既保留 React 的開發體驗，也控制了用戶端腳本的大小。

MDX 負責表達能力

一般文章繼續使用 Markdown；需要元件或複雜互動時再使用 MDX。兩者由同一個內容集合管理，不必為了少數進階文章犧牲整個網站的簡潔性。

專案的主要相依套件包括：

{
  "dependencies": {
    "astro": "7.1.6",
    "@astrojs/mdx": "7.0.5",
    "@astrojs/react": "6.0.2",
    "react": "19.2.8",
    "react-dom": "19.2.8"
  }
}

如果是純靜態 Astro 專案，部署到 Pages 時不需要安裝 @astrojs/cloudflare 轉接器；只有使用 Cloudflare 伺服器端執行環境或 SSR 時才需要對應的轉接器。

內容模型與專案結構

部落格內容放在 src/content/blog/，檔案路徑直接決定最終 URL。例如：

src/content/blog/
├── blog/
│   └── astro-react-mdx-cloudflare-pages.md
├── css/
├── foundation/
├── java/
└── react/

文章 frontmatter 透過 Zod 驗證，避免日期、標籤或草稿狀態寫錯後仍然進入正式環境：

const blog = defineCollection({
  loader: glob({
    base: "./src/content/blog",
    pattern: "**/*.{md,mdx}",
  }),
  schema: z.object({
    title: z.string(),
    description: z.string(),
    date: z.coerce.date(),
    author: z.string().default("lucaslz"),
    tags: z.array(z.string()).default([]),
    featured: z.boolean().default(false),
    draft: z.boolean().default(false),
  }),
});

發布文章只需要新增一個 Markdown 檔案。首頁、彙整、標籤、搜尋索引、RSS 與 Sitemap 都會在建置時自動更新。

行動端不是最後才補

這次重寫從一開始就按小螢幕版面設計，而不是先完成桌面版再硬塞進小螢幕：

  • 所有頁面都設定正確的 viewport。
  • 主要斷點圍繞內容寬度，而不是特定手機型號。
  • 文章字級與間距使用 clamp() 保持連續縮放。
  • 點擊目標不小於常見的行動端可觸控尺寸。
  • 桌面導覽在小螢幕切換為抽屜式選單。
  • 程式碼區塊可以水平捲動，不會撐破文章容器。
  • 表格、圖片、Mermaid 圖與長 URL 都有溢出保護。
  • 同時支援淺色與深色系統主題。

靜態頁面並不等於簡單頁面。行動端體驗更多取決於版面、字體、觸控區域與資源大小，而不是使用哪個 JavaScript 框架。

為什麼使用兩個 GitHub 存放庫

原始碼存放庫 lucaslz-blog 是私有存放庫，包含文章原始檔、Astro 設定與 GitHub Actions 工作流程。另一個存放庫 lucasleelz.github.io 只存放建置後的靜態檔案。

這樣拆分有三個好處：

  1. 寫作過程與工程設定保持私有。
  2. GitHub Pages 存放庫仍然可以作為公開、可回滾的靜態鏡像。
  3. Cloudflare Pages 與 GitHub Pages 使用同一份 dist/，不會出現兩套建置邏輯。

建置產物不是原始碼，因此不要在原始碼存放庫中手動維護 dist/。它應該由 CI 每次重新產生。

GitHub Actions 自動發布

工作流程只監聽 main。每次推送依序執行安裝、型別檢查、靜態建置、站內連結檢查與發布。

以下是核心結構的簡化版本：

name: Build and publish site

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  deployments: write

concurrency:
  group: publish-production
  cancel-in-progress: false

jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout source
        uses: actions/checkout@v6

      - name: Setup pnpm
        uses: pnpm/action-setup@v4

      - name: Setup Node
        uses: actions/setup-node@v6
        with:
          node-version: 24
          cache: pnpm

      - name: Install dependencies
        run: pnpm install --frozen-lockfile

      - name: Build site
        run: pnpm run build

      - name: Check internal links
        run: pnpm run check:links

同步 GitHub Pages 鏡像

原始碼存放庫透過專用 Deploy Key 取得靜態存放庫的寫入權限。工作流程取出目標存放庫後，使用 rsync --delete 讓目標分支與這次的 dist/ 完全一致：

- name: Checkout Pages repository
  uses: actions/checkout@v6
  with:
    repository: lucaslz2020/lucasleelz.github.io
    ref: master
    ssh-key: ${{ secrets.PAGES_DEPLOY_KEY }}
    path: publish

- name: Copy static files
  run: rsync -a --delete --exclude=.git dist/ publish/

- name: Publish generated site
  working-directory: publish
  run: |
    git config user.name "github-actions[bot]"
    git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
    git add --all
    if git diff --cached --quiet; then
      exit 0
    fi
    git commit -m "deploy: ${GITHUB_SHA}"
    git push origin HEAD:master

這裡要確認目標存放庫實際使用的是 main 還是 master。分支名稱寫錯時，建置會成功，但發布步驟會失敗。

發布到 Cloudflare Pages

Cloudflare Pages 專案採用 Direct Upload，由 GitHub Actions 完成自訂建置後上傳 dist/。Cloudflare 官方文件也採用這種方式來整合自訂 CI 平台。

- name: Deploy to Cloudflare Pages
  uses: cloudflare/wrangler-action@v3
  with:
    apiToken: ${{ secrets.CLOUDFLARE_API_TOKEN }}
    accountId: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
    command: >-
      pages deploy dist
      --project-name=lucaslz-blog
      --branch=main
    gitHubToken: ${{ secrets.GITHUB_TOKEN }}

正式工作流程中，我會進一步把第三方 Action 固定到完整 commit SHA，並在註解中保留對應版本，降低上游標籤被意外修改所帶來的供應鏈風險。

憑證採用最小權限

自動部署需要兩個方向的寫入權限，但不應該重複使用個人 SSH 金鑰或全域管理員 Token。

GitHub Pages Deploy Key

  • 單獨產生一組 SSH 金鑰。
  • 公開金鑰只加入靜態發布存放庫，並開啟寫入權限。
  • 私密金鑰以 PAGES_DEPLOY_KEY Secret 形式存放在原始碼存放庫。
  • 確認部署正常後，刪除本機的暫時私密金鑰副本。

Cloudflare API Token

  • 建立自訂 API Token，而不是使用 Global API Key。
  • 只授予目標帳號的 Cloudflare Pages 寫入權限。
  • Token 存放在 CLOUDFLARE_API_TOKEN。
  • Account ID 存放在 CLOUDFLARE_ACCOUNT_ID。
  • 不要在終端機輸出、建置日誌、截圖或文章中顯示 Token 原文。

如果 Token 曾出現在日誌或工具輸出中，不要只刪除日誌：應立即撤銷舊 Token、產生新 Token 並覆寫 GitHub Secret。

GitHub 也建議憑證只授予完成任務所需的最小權限，優先使用 Deploy Key、GitHub App 或專用服務身分，而不是長期重複使用個人憑證。參考：GitHub Actions Secrets。

從 Vercel 切換到 Cloudflare Pages

遷移時最容易出問題的不是建置，而是操作順序。

我的網域最初仍有一筆根網域 A 記錄指向 Vercel。刪除 Vercel 專案後，造訪網域出現：

404: NOT_FOUND
Code: DEPLOYMENT_NOT_FOUND

這個錯誤不代表 Cloudflare Pages 部署失敗，而是 DNS 仍把造訪請求送到已經被刪除的 Vercel Deployment。

更穩妥的順序是：

  1. 先建立並驗證 Cloudflare Pages 的 pages.dev 位址。
  2. 在 Cloudflare 中新增正式網域，檢查自動掃描到的 DNS 記錄。
  3. 確認沒有遺漏 MX、SPF、DKIM、DMARC 等郵件記錄。
  4. 在網域註冊商處把權威名稱伺服器切換到 Cloudflare。
  5. 等待 Cloudflare Zone 啟用。
  6. 在 Pages 專案的 Custom domains 中綁定根網域。
  7. 確認 HTTPS 與主要頁面都正常後，再清理舊平台設定。

這個網域沒有郵件記錄，因此切換相對簡單。如果網域同時承載信箱、API 或其他子網域，就必須先完整遷移 DNS，不能只關注部落格的 A/CNAME 記錄。

在阿里雲修改名稱伺服器

網域註冊商是阿里雲，原權威名稱伺服器是 HiChina。Cloudflare 為 Zone 分配兩條名稱伺服器後，在阿里雲網域主控台進入：

域名详情 → DNS 管理 → DNS 修改 → 修改 DNS 服务器

填入 Cloudflare 分配的兩條名稱伺服器，完成簡訊驗證並儲存。

名稱伺服器切換屬於影響層面很大的網路設定。送出前至少確認：

  • Cloudflare Zone 中現有的記錄是否完整。
  • DNSSEC 是否處於相容狀態；必要時先關閉舊服務商的 DNSSEC，啟用後再由 Cloudflare 開啟。
  • 網域沒有依賴未遷移的信箱、介面或驗證記錄。
  • 舊 DNS 的 TTL 是否會導致快取持續較長時間。

Cloudflare 主控台可能會在一段時間內顯示 Initializing 或 Verifying。不要因為狀態沒有立即變成 Active 就反覆刪除與重建記錄，先從公用 DNS 與 HTTPS 兩個角度驗證真實結果。

綁定根網域

Zone 啟用後，在 Cloudflare Dashboard 中進入：

Workers & Pages
→ lucaslz-blog
→ Custom domains
→ Set up a custom domain

輸入 lucaslz.com。Cloudflare 會把舊的根網域記錄替換為指向 lucaslz-blog.pages.dev 的記錄，並處理根網域的 CNAME Flattening、代理與憑證簽發。

最終狀態應顯示：

lucaslz.com  Active
SSL enabled

GitHub Pages 鏡像存放庫不再保留 CNAME 檔案，避免兩個代管平台同時宣告同一個正式網域。

上線後的驗證清單

不能只看主控台裡的綠色狀態。發布完成後至少檢查以下內容：

# 权威名称服务器
dig NS lucaslz.com

# HTTPS、跳转与响应头
curl -I -L https://lucaslz.com/

# 关键页面
curl -I -L https://lucaslz.com/archive/
curl -I -L https://lucaslz.com/tags/

# RSS 与 Sitemap
curl -I https://lucaslz.com/rss.xml
curl -I https://lucaslz.com/sitemap-index.xml

瀏覽器中還需要驗證：

  • 首頁、文章頁、彙整與標籤頁。
  • 手機寬度下的導覽、搜尋與程式碼區塊。
  • 淺色與深色主題。
  • 404 頁面。
  • Canonical、Open Graph、RSS 與 Sitemap 位址。
  • 頁尾是否顯示正確的部署平台。

這次發布後，首頁、彙整與文章路由都回傳 200，回應標頭中的 server 為 cloudflare，Cloudflare Pages 主控台顯示 Active · SSL enabled。

幾個值得保留的經驗

先打通暫用網域，再動正式 DNS

pages.dev 是最好的隔離驗證入口。只要暫用網域尚未通過建置、連結與頁面檢查，就不應該切換正式網域。

原始碼部署與靜態產物發布是兩回事

私有原始碼存放庫負責寫作與建置，公開 Pages 存放庫只負責保存產物。兩者用 GitHub Actions 串接，比手動複製 dist/ 更穩定，也更容易稽核。

刪除舊平台前先確認 DNS

舊專案已刪除而 DNS 還沒切換，會立刻看到平台 404。正式環境的遷移應先準備新環境，再切換流量，最後清理舊環境。

Secret 外洩後的正確動作是輪換

「介面上看不到了」不等於「憑證安全了」。一旦憑證可能被讀取，就應撤銷、重建、更新 Secret，並清除不再需要的本機副本。

CI 必須包含建置以外的檢查

靜態建置成功不代表網站可用。型別檢查、內容 Schema、站內連結檢查與線上 smoke test 應共同構成發布門檻。

最終結果

新的部落格沒有執行中的應用程式伺服器，也沒有執行階段資料庫。日常發布流程只剩下：

写 Markdown / MDX
→ 本地预览
→ git push main
→ GitHub Actions 构建与检查
→ 同步 GitHub Pages 镜像
→ 部署 Cloudflare Pages
→ lucaslz.com 自动更新

Astro 負責把內容變成盡可能輕量的靜態頁面，React 只處理真正需要的互動，GitHub Actions 負責可重複的發布流程，Cloudflare Pages 負責 CDN、HTTPS 與正式網域。

對個人技術部落格來說，這套結構夠簡單，也保留了長期演進的空間。更重要的是，它把維護部署環境的時間，重新還給了寫作本身。
