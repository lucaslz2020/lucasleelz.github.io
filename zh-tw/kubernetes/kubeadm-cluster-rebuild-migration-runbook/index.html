Kubernetes 重建式遷移 Runbook：把臨場救火變成階段驗收

一份可執行的 kubeadm 叢集重建遷移手冊，涵蓋凍結基線、備份還原、節點初始化、網路、資料、Nacos、業務驗收、停止條件與回滾。

本文中的節點、地址、網域、環境名稱與容量資料皆為脫敏範例。Secret、資料庫備份、Token 與內部倉庫資訊不屬於可發布內容。

系列導覽：Kubernetes 重建遷移教學系列。本篇負責遷移日的執行、停止條件與回滾。

上一篇文章復盤了重建式遷移中遇到的問題。這篇不再按照事故時間線敘述，而是把經驗收斂成一份可以逐階段執行的 Runbook。

「一步到位」並不等於用一個指令啟動所有節點與業務。它真正的意思是：在遷移窗口內只執行經過驗證的版本化資產，不再臨時修改 YAML、Nacos、Service IP、節點污點或防火牆。

總原則：上一階段失敗就停止

flowchart LR
  A["凍結設計"] --> B["備份與還原演練"]
  B --> C["作業系統基線"]
  C --> D["高可用控制平面"]
  D --> E["CNI 與基礎設施"]
  E --> F["零複本預部署"]
  F --> G["資料還原"]
  G --> H["Nacos 與平台依賴"]
  H --> I["業務分批啟動"]
  I --> J["真實業務驗收"]
  J --> K["入口切換"]

每個箭頭都是硬性門檻。失敗時只能：

  1. 回滾目前批次。
  2. 在 Git 中修正來源設定。
  3. 重新 dry-run 與評審。
  4. 從失敗階段重新執行。

不要用 kubectl edit、臨時 patch、固定 sleep 或重啟 Pod 來掩蓋設定錯誤。

階段 0：凍結不可變基線

建立第一個控制平面之前，先凍結：

  • Kubernetes、kubeadm、kubelet、kubectl 版本。
  • 作業系統與 containerd 版本。
  • 控制平面節點與 API VIP。
  • Pod CIDR、Service CIDR、叢集 DNS 網域。
  • CNI、Ingress、StorageClass 與 metrics-server 方案。
  • Nacos 版本與叢集模式。
  • 映像來源與 digest。
  • 節點池、標籤、污點與 toleration。

三類網路必須有清楚的邊界：

網路用途是否寫入應用程式設定
節點網段虛擬機器、節點與少量外部依賴僅確有必要時
Pod CIDRCNI 分配的 Pod IP禁止
Service CIDRClusterIP僅限相容白名單

應用程式內部預設使用：

<service>.<namespace>.svc.cluster.local:<port>

階段 1：準備所有輸入

執行前必須具備：

  • 伺服器、虛擬機器、磁碟與節點池清單。
  • 舊主機名稱到新主機名稱的對應。
  • etcd snapshot 與 Kubernetes 資源封存。
  • 資料庫、訊息系統與檔案儲存的備份。
  • Nacos namespace、group、dataId、內容與校驗值。
  • 映像與 digest 清單。
  • Service DNS 取代表與固定 ClusterIP 白名單。
  • 網域、憑證、Ingress 與外層入口的對應。
  • 回滾負責人、停止條件與還原指令。

任何輸入缺失，都不應重裝仍承載資料的舊節點。

階段 2：完成還原演練

備份矩陣可以依下列方式建立：

服務備份驗收
etcdsnapshot隔離 restore，API 物件可讀
MySQL全量備份、使用者授權、binlog關鍵資料表、列數、應用程式帳號查詢
PostgreSQLdump/base backup、角色、WALschema、擴充、應用程式查詢
MongoDBdump/snapshot、認證庫collection、索引、業務查詢
RedisRDB/AOF、設定PING、關鍵 key、TTL 抽樣
Kafkatopic、partition、offsetbroker、ISR、consumer group
RabbitMQdefinitions、vhost、使用者exchange、queue、binding
NFS/hostPath檔案或儲存快照檔案數、容量、checksum 抽樣

只有「備份檔案存在」不算完成，還原演練才是門檻。

階段 3：所有設定先在 Git 中改完

遷移前完成以下靜態治理：

  • 內部 URL 改為 Service DNS。
  • Pod IP 引用歸零。
  • 固定 ClusterIP 只保留白名單。
  • Kafka advertised listener 個別評審，不做字串替換。
  • Deployment 的資源、探針、排程、DNS 與優雅停機統一。
  • 匯出物件移除唯讀欄位與舊管理平台中繼資料。
  • Deployment、StatefulSet 初始複本為 0。
  • CronJob 初始 suspend=true。

常用靜態掃描：

rg -n '<pod-cidr-pattern>' config/ manifests/
rg -n '<service-cidr-pattern>' config/ manifests/
rg -n 'node[0-9]+' manifests/

掃描結果不能直接批量替換，每個命中都需要歸類為 Service、節點、外部依賴或歷史垃圾設定。

階段 4：統一節點基線

重裝後每台節點執行同一個腳本：

swapoff -a
modprobe overlay
modprobe br_netfilter
sysctl --system
systemctl enable --now containerd
systemctl enable kubelet

逐節點驗收：

hostnamectl
ip address
ip route
timedatectl
swapon --show
systemctl is-active containerd
crictl info

firewalld 規則必須在 kubeadm 之前完成。所有節點都需要允許 Pod CIDR 轉發；hostNetwork 服務則依實際連接埠增加最小範圍規則。

階段 5：建立控制平面

順序固定為：

  1. 初始化第一個 control-plane。
  2. 部署 kube-vip 並驗證 API VIP。
  3. 加入其餘 control-plane。
  4. 檢查 etcd 成員。
  5. 測試 VIP Leader 漂移。
  6. 產生並受控保存 worker join 指令。

控制平面驗收項目：

  • API VIP 持續可達。
  • 三個控制平面節點 Ready。
  • etcd 三個成員健康。
  • kubeconfig 指向 VIP，而非單台主機。
  • 憑證 SAN 包含實際存取地址。

階段 6：安裝網路與基礎設施

安裝 CNI 後，先驗證跨節點 Pod IP、CoreDNS、Service ClusterIP 與外部 DNS。

再依序安裝：

  1. 預設儲存類別。
  2. metrics-server。
  3. Ingress Controller。
  4. 日誌與監控。

每個節點池至少執行一次 PVC smoke test；kubectl top nodes 與 kubectl top pods -A 都回傳資料後，指標系統才算可用。

階段 7：標籤、污點與零複本預部署

節點加入後立即設定目標標籤與污點，避免未標記節點參與排程。

多複本狀態服務使用 required Pod Anti-Affinity：

podAntiAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
    - topologyKey: kubernetes.io/hostname
      labelSelector:
        matchLabels:
          app: zookeeper

資源預部署後的硬性檢查：

  • PVC 已 Bound 或有明確的還原計畫。
  • Service selector 與 Pod label 完全匹配。
  • 固定 ClusterIP 無衝突。
  • 所有映像都可拉取。
  • 不存在舊主機名稱。
  • 停用環境複本保持為 0。

階段 8：資料還原

固定順序：

存储
→ 基础数据库与消息组件
→ Kafka
→ PostgreSQL 与辅助服务
→ Nacos 数据库
→ Nacos

每個服務都必須從同節點 Pod、跨節點 Pod、Service DNS 三個入口驗證。只看 Pod Ready 無法發現 kube-proxy、firewalld 或 DNS 問題。

階段 9：Nacos 叢集驗收

Nacos 三個 Pod 需要兩類 Service：

Service類型用途
nacos-hsHeadless成員穩定 DNS 與叢集互連
nacos-csClusterIP用戶端統一入口

三層驗收：

  1. 三個成員都是健康狀態。
  2. 三個節點的運行模式開關一致。
  3. 測試用戶端註冊後，三個節點都能查到同一個實例。

完成後再匯入 Nacos 設定，逐筆回讀 namespace、group、dataId 與校驗值。

階段 10：平台依賴與業務分批啟動

先啟動鑑權、字典、檔案、工作流等平台依賴，再啟動 OAuth、Gateway 與 DevOps。第一個鑑權服務應成為硬性門檻：

  • Deployment Ready。
  • Service 有 Endpoint。
  • 三個 Nacos 節點實例一致。
  • OAuth 能透過 Service DNS 呼叫。
  • 無效登入回傳正確的業務錯誤，而不是「無可用實例」。

業務一次只啟動一個命名空間。該批次全部通過後再繼續下一批。

階段 11：Ingress 與真實業務驗收

先繞過外部入口，直接請求 Ingress：

curl --resolve app.example.com:443:<ingress-address> \
  https://app.example.com/

叢集內成功後，再設定路由器、NLB 或代理層的 Host/SNI 轉發。叢集內 200、公網失敗時，不要修改 Kubernetes 業務資源。

真實驗收至少涵蓋：

  • 正常登入、失敗登入與 Token 刷新。
  • 權限、檔案、Session。
  • 資料庫讀寫。
  • Kafka/RabbitMQ 生產與消費。
  • WebSocket。
  • CI/CD 上傳發布。

自動停止條件

遇到以下情況立即停止：

  • etcd 或資料庫備份無法還原。
  • 網路 CIDR 衝突。
  • API VIP 漂移失敗。
  • CNI 或 kube-proxy 未全量就緒。
  • 資料校驗不一致。
  • Nacos 三節點實例不一致。
  • 核心鑑權鏈路不可用。
  • 出現不可接受的資料寫入錯誤。
  • 公網故障需要修改業務 Pod 才能繞過。

Go / No-Go 清單

  • 伺服器與節點池清單無重複、無遺漏。
  • 版本、網路與映像已凍結。
  • etcd 與資料庫已完成還原演練。
  • 檔案儲存已備份。
  • Nacos 設定已匯出、DNS 化並回讀。
  • 固定 ClusterIP 白名單已評審。
  • 標籤、污點與 toleration 已成對校驗。
  • 防火牆初始化腳本已驗證。
  • Nacos 兩類 Service 清單完整。
  • 網域、憑證與入口對應已準備。
  • 所有資源可零複本預部署。
  • 真實驗收請求與預期結果已準備。
  • 回滾入口、負責人與停止條件已確認。

完成的定義

遷移完成必須同時滿足：

全部节点 Ready
+ 基础组件健康
+ 数据恢复并通过应用查询
+ Nacos 三节点一致
+ Service DNS 与 Endpoint 正常
+ 活跃业务全部 Ready
+ 登录与核心业务成功
+ 公网入口成功
+ 配置和脚本已进入 Git
+ 旧集群经过观察窗口后下线

Runbook 的真正價值不是讓操作更「機械」，而是把依賴個人記憶的臨場決策，轉化為可以審查、暫停、回滾與重現的工程流程。
