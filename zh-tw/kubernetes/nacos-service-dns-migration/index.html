把 Nacos 裡的固定 Service IP 改成 Kubernetes DNS：一次配置治理實戰

記錄如何盤點數百份 Nacos 設定，將 Kubernetes ClusterIP 安全遷移為 Service DNS，並區分 Redis、Kafka、外部依賴與已刪除服務。

文中的 namespace、服務名稱、網域、位址與設定數量均已去識別化或泛化。真實設定備份可能包含密碼和 Token，絕不能進入部落格或 Git 存放庫。

系列導覽：Kubernetes 重建遷移教學系列。本文假設 Nacos 叢集已搭建完成並通過驗收。

Kubernetes 叢集遷移後，最隱蔽的一類故障不是 Pod 起不來，而是 Nacos 設定裡還保存著舊叢集的 Service ClusterIP。

典型現象包括：

Load balancer does not have available server
Unable to connect to Redis
No route to host
connect timed out

舊 IP 在新叢集中可能不存在，也可能剛好被另一個 Service 占用。後者比直接逾時更危險，因為請求會被轉送到錯誤的服務。

因此，這次治理的目標不是「把 IP 換成新 IP」，而是盡可能改成穩定的 Kubernetes Service DNS。

下面先完整走一遍操作流程，再解釋為什麼有些位址不能自動替換。

第 1 步：建立隔離的工作目錄

mkdir -p nacos-dns-migration/{backup,inventory,candidates,reports}
cd nacos-dns-migration

git init
printf 'backup/\n*.zip\n*.token\n.env\n' > .gitignore

原始 Nacos 匯出檔可能包含密碼、Token 和資料庫位址，只能放在 backup/，並應使用加密儲存。Git 中只保留去識別化後的規則、腳本與報告範本。

建立一份變更清單：

namespace,group,data_id,old_value,target_service,target_port,action,owner,status
app-test,DEFAULT_GROUP,global.properties,<old-address>,redis-service,6379,replace,team-a,pending

所有發布動作都要能追溯到這一行。

第 2 步：匯出 Nacos 設定

最穩妥的方式是使用 Nacos 控制台按 namespace 匯出設定壓縮檔，並記錄匯出時間、操作人與檔案校驗值：

sha256sum backup/<namespace>-configs.zip \
  > backup/<namespace>-configs.zip.sha256

如果使用 OpenAPI 自動匯出，API 路徑、鑑權與相容性必須按目前 Nacos Server 版本核對。Nacos 3.2 起移除了部分舊 HTTP API，不能拿舊腳本直接操作新叢集。

解壓到暫存目錄後，先做唯讀掃描：

mkdir -p backup/unpacked
unzip -q backup/<namespace>-configs.zip -d backup/unpacked

rg -n --glob '*.{properties,yaml,yml,json,xml}' \
  '([0-9]{1,3}\.){3}[0-9]{1,3}' backup/unpacked \
  > reports/ip-references.txt

不要在掃描結果裡印出整行 Secret。正式腳本應對 password、secret、token 等鍵的值進行遮罩。

第 3 步：匯出新舊叢集 Service 清單

分別使用明確的 kubeconfig 匯出，不要依賴目前的 context：

kubectl --kubeconfig <old-kubeconfig> get service -A -o json \
  > inventory/old-services.json

kubectl --kubeconfig <new-kubeconfig> get service -A -o json \
  > inventory/new-services.json

轉換成便於審閱的 TSV：

jq -r '
  .items[]
  | select(.spec.clusterIP != "None")
  | [
      .metadata.namespace,
      .metadata.name,
      .spec.clusterIP,
      (.spec.ports | map((.port|tostring) + ":" + (.targetPort|tostring)) | join(","))
    ]
  | @tsv
' inventory/old-services.json > inventory/old-services.tsv

jq -r '
  .items[]
  | select(.spec.clusterIP != "None")
  | [
      .metadata.namespace,
      .metadata.name,
      .spec.clusterIP,
      (.spec.ports | map((.port|tostring) + ":" + (.targetPort|tostring)) | join(","))
    ]
  | @tsv
' inventory/new-services.json > inventory/new-services.tsv

現在可以依舊 IP 反查 Service：

rg -F '<old-service-ip>' inventory/old-services.tsv

預期得到：

app-test    rbac-api    <old-service-ip>    8082:8082

目標 DNS 就是：

rbac-api.app-test.svc.cluster.local

第 4 步：逐條確認目標 Service 與連接埠

先檢查新叢集是否存在同名 Service：

kubectl --kubeconfig <new-kubeconfig> -n app-test \
  get service rbac-api -o yaml

kubectl --kubeconfig <new-kubeconfig> -n app-test \
  get endpointslice \
  -l kubernetes.io/service-name=rbac-api -o wide

只有同時滿足下列條件，才能進入自動候選：

  • 舊 IP 能唯一反查到一個 Service。
  • 新叢集存在語意相同的 Service。
  • 設定連接埠對應新 Service 的 port，不是誤拿 targetPort。
  • EndpointSlice 至少有一個 Ready 位址。
  • 負責人確認該依賴仍然存在。

其餘條目全部標成 manual-review，不能讓腳本猜。

第 5 步：產生候選檔，不直接發布

複製一份原始設定：

cp backup/unpacked/global.properties \
  candidates/global.properties

把：

rbac.api.url=http://<old-service-ip>:8082

改為：

rbac.api.url=http://rbac-api.app-test.svc.cluster.local:8082

然後審閱差異：

diff -u backup/unpacked/global.properties \
  candidates/global.properties \
  | tee reports/global.properties.diff

審閱時逐行確認：

  • 只修改主機部分，協定、連接埠、路徑與參數都未遺失。
  • 沒有把外部依賴改成叢集 DNS。
  • 沒有把 Kafka broker 位址合併成一般 Service。
  • 沒有新增不存在的 Service 名稱。

第 6 步：在業務 Pod 中提早驗證 DNS

正式發布前，從真實呼叫方 Pod 測試目標位址：

kubectl -n <caller-namespace> exec <caller-pod> -- \
  getent hosts rbac-api.app-test.svc.cluster.local

kubectl -n <caller-namespace> exec <caller-pod> -- \
  nc -vz rbac-api.app-test.svc.cluster.local 8082

這一步失敗時，修改 Nacos 沒有意義。先修復 Service、Endpoint、NetworkPolicy、CNI 或 kube-proxy。

第 7 步：逐個 Data ID 發布

第一次治理建議透過 Nacos 控制台操作：

  1. 進入正確的 namespace。
  2. 搜尋精確的 Data ID 與 Group。
  3. 開啟歷史版本，確認能夠回滾。
  4. 貼上候選內容，檢視控制台顯示的 diff。
  5. 只發布一個 Data ID。
  6. 立即回讀並下載一次，比對校驗值。

若使用自動化 API，腳本必須實作：鑑權、逾時、發布前備份、發布後回讀、內容校驗與單一 Data ID 回滾。不要用一個迴圈無條件覆寫整個 namespace。

第 8 步：只滾動受影響的用戶端

先確認設定是否支援動態刷新。不能動態刷新的應用再執行滾動重啟：

kubectl -n <caller-namespace> rollout restart deployment/<caller-app>
kubectl -n <caller-namespace> rollout status deployment/<caller-app> --timeout=10m

檢視最近日誌：

kubectl -n <caller-namespace> logs deployment/<caller-app> --since=10m \
  | grep -Ei 'nacos|refused|timed out|no route|available server'

不要因為修改了一份共用的 global.properties 就同時重啟所有命名空間。依依賴關係分批執行，前一批通過真實業務驗收後再繼續。

第 9 步：執行真實請求並搜尋舊位址

除了健康檢查，還應完成登入、查詢、快取讀寫或內部 RPC 等真實請求。然後在設定與執行日誌中搜尋舊位址：

rg -n -F '<old-service-ip>' candidates reports

kubectl -n <caller-namespace> logs deployment/<caller-app> --since=30m \
  | grep -F '<old-service-ip>'

候選設定與新日誌中都不應再出現舊 Service IP。

第 10 步：依 Data ID 回滾

如果業務驗收失敗：

  1. 停止繼續發布其他 Data ID。
  2. 使用 Nacos 歷史版本還原剛才修改的內容。
  3. 回讀確認還原成功。
  4. 滾動剛才受影響的用戶端。
  5. 保存故障日誌與失敗請求。

不要匯入整個舊 namespace 壓縮檔，否則會覆寫遷移期間其他團隊已發布的正常設定。

為什麼固定 ClusterIP 會成為遷移負債

ClusterIP 的生命週期屬於 Service 物件。刪除並重建 Service 後，如果沒有明確指定 clusterIP，位址可能改變。

下面這種設定把應用與某一次叢集狀態綁在一起：

rbac.api.url=http://10.x.y.z:8082
spring.data.redis.host=10.x.y.z

更穩定的寫法是：

rbac.api.url=http://rbac-api.app-test.svc.cluster.local:8082
spring.data.redis.host=redis-service.app-test.svc.cluster.local

只要 Service 名稱與 namespace 保持不變，Pod、Endpoint 與 ClusterIP 的變化都不會影響呼叫方。

先建立來源，而不是直接替換

對每個 Nacos 設定參照，需要同時收集四類資料：

  1. 舊叢集 Service 名稱、namespace、ClusterIP 與連接埠。
  2. 新叢集 Service 名稱、namespace、ClusterIP 與連接埠。
  3. 正式環境或其他同構環境中的穩定設定。
  4. 目前 Deployment、StatefulSet 與 Endpoint 的實際存在狀態。

隨後為每個位址建立分類：

類型處理方式
目前存在的 Kubernetes Service改為完整 Service DNS，並核對連接埠
已刪除或未遷移的 Service不自動替換，先確認要還原還是移除路由
Pod IP禁止保留，找到對應的 Service
Kafka broker 位址單獨設計 listener，不做一般 DNS 替換
節點上的 hostNetwork 服務評估能否改為 Service；不行時登記例外
外部資料庫、簡訊、專網系統保留原有外部位址

這一步決定了治理是否安全。正規表達式只能找到位址，無法判斷位址的所有權。

為什麼不能把所有 IP 都替換掉

已刪除服務

如果一個舊位址指向已經不存在的 Service，把它改成：

missing-service.app-test.svc.cluster.local

只會把連線逾時變成 DNS 解析失敗。正確選擇只有兩個：還原目標 Service，或刪除不再使用的設定與路由。

Kafka advertised listener

Kafka 用戶端不是只連一個入口。Bootstrap Server 會回傳 broker 的 advertised address，用戶端隨後直連具體的 broker。

因此，原本依 broker 暴露的 NodePort 或節點位址，不能簡單改成一個一般 ClusterIP。需要先設計：

  • 內外部 listener。
  • 每個 broker 的 Service。
  • advertised listener。
  • DNS、NodePort 或負載平衡入口。

Kafka 位址治理應作為獨立專案執行。

外部依賴

簡訊、雲端資料庫、合作方介面與專網系統並不屬於 Kubernetes。只因為它們也是 IP，並不代表應該改成 svc.cluster.local。

設定發布必須可回滾

每次修改前保存：

  • namespace。
  • group。
  • dataId。
  • 原始內容。
  • MD5 或其他校驗值。

發布流程：

flowchart LR
  A["匯出設定"] --> B["識別 IP 和 URL"]
  B --> C["關聯 Service 與連接埠"]
  C --> D["產生候選變更"]
  D --> E["人工審閱例外"]
  E --> F["逐 dataId 發布"]
  F --> G["回讀並比對校驗值"]
  G --> H["滾動用戶端並驗證"]

不要一次覆寫整個 namespace，也不要把備份檔提交到 Git。回滾應精確到單一 dataId，而不是用舊匯出包覆寫之後產生的其他正常變更。

連接埠必須與 Service 一起校驗

DNS 正確不代表設定正確。常見問題是服務名稱已改，連接埠卻仍來自舊環境。

可以把參照解析成：

namespace / service / configured-port

再與 Kubernetes Service 的 port、targetPort 與實際 Endpoint 比對。最終要求：

  • DNS 能解析。
  • Service 存在。
  • 設定連接埠與 Service port 一致。
  • Endpoint 不為空。
  • 目標 Pod 真實監聽對應連接埠。

Redis 設定需要相容不同 Spring Boot 版本

不同服務可能分別讀取：

spring.data.redis.host
spring.redis.host
gateway.oauth2.redis.host
platform.redis.host

如果系統正在跨 Spring Boot 版本升級，可以先以新屬性為來源，並為舊服務保留暫時別名：

spring.data.redis.host=redis-service.app-test.svc.cluster.local
spring.data.redis.port=6379

spring.redis.host=${spring.data.redis.host}
spring.redis.port=${spring.data.redis.port}
spring.redis.password=${spring.data.redis.password}
spring.redis.database=${spring.data.redis.database}

相容別名需要註明移除條件，避免永久維護兩套設定。

如果舊應用已經回退到 localhost:6379，或補充 Lettuce pool 參數後出現 commons-pool2 類別缺失，可繼續閱讀Boot 2/3 Redis 設定回退故障復盤。

驗證不能停在 Nacos 頁面

設定發布後依五層驗證：

1. 設定回讀

確認 namespace、group、dataId、內容與 MD5 和發布結果一致。

2. DNS 解析

從真實業務 Pod 中執行：

getent hosts redis-service.app-test.svc.cluster.local

3. Service 與 Endpoint

kubectl -n app-test get svc redis-service
kubectl -n app-test get endpointslice -l kubernetes.io/service-name=redis-service

4. 網路連線

從呼叫方 Pod 存取 Service DNS 與連接埠。若 Endpoint 可達而 Service 不可達，排查請求來源節點的 kube-proxy；若 Pod IP 跨節點不可達，排查 CNI 與 firewalld。

5. 真實業務請求

重啟或刷新對應用戶端後，執行登入、快取、訊息或內部 API 請求。日誌中不應繼續出現舊位址。

Nacos 服務發現與設定中心要分開看

Nacos 同時承擔設定中心與服務發現，兩個問題經常被混在一起：

  • 設定中心決定 Redis、資料庫、內部 API 等 URL。
  • 服務發現決定某個服務是否有健康實例。

當閘道提示「沒有可用服務」時，應檢查 Nacos instance list；當應用連線到舊 ClusterIP 時，應檢查設定內容。只重啟 Pod 可能讓現象短暫改變，卻不會修復錯誤的來源設定。

自動化稽核建議

持續治理可以包含這些檢查：

1. 扫描所有 IPv4、URL 和主机名
2. 判断是否属于 Pod CIDR、Service CIDR 或节点网段
3. 将 Service IP 反查到 namespace/service
4. 校验配置端口和 Service port
5. 标记不存在的 Service DNS
6. 生成例外清单，而不是自动覆盖

新增設定可以在 CI 中設定規則：

  • 禁止寫入 Pod CIDR。
  • 預設禁止寫入 Service CIDR。
  • 允許完整 Service DNS。
  • 固定 ClusterIP 必須參照白名單紀錄。
  • Secret 與設定匯出不得進入存放庫。

最終經驗

這次治理最重要的結果不是替換了多少位址，而是建立了明確邊界：

  1. Kubernetes 內部依賴優先使用 Service DNS。
  2. 已刪除服務不能靠虛構的 DNS 修復。
  3. Kafka、hostNetwork 與外部系統必須單獨分類。
  4. 每次 Nacos 修改都要備份、逐項發布、回讀與真實請求驗證。

固定 IP 並不總是錯誤，但它必須是有負責人、有原因、有移除計畫的明確相容項目，而不是沒人知道來源的歷史字串。

位址遷移穩定後，可繼續依Spring Boot 3 Nacos 全域設定基線治理 Redis、Redisson、RabbitMQ、Hikari、Tomcat 與設定覆蓋關係。
