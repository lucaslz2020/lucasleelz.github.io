Spring Boot 3 的 Nacos 完整生產基線：Redis、RabbitMQ、Hikari 與探針

給出一套可落地的 Spring Boot 3 Nacos 分層設定，重點治理 Redis 連線數、RabbitMQ 併發與預取、資料庫連線池、Tomcat、優雅停機與 Actuator。

{ }

本文來自一次多服務連線數與容器記憶體治理。地址、帳號、命名空間與業務名稱均已泛化。設定值是保守起點，必須依資料庫、Redis、RabbitMQ 容量與業務壓測結果調整。

當幾十個 Spring Boot 服務共同讀取一份 global.properties 時，任何「順手最佳化」都會被複本數放大：

每 Pod 多 8 个 Redis 空闲连接
× 60 个 Pod
= 480 个额外连接

RabbitMQ 也一樣。幾十個 @RabbitListener、多個消費者執行緒與較大的 prefetch 相乘後，既增加 Channel 與執行緒，也讓大量未確認訊息留在 JVM Heap。

因此，一份「完整 Nacos 設定」不能只是把可用參數全部填上。它應該明確說明：

  • 哪些是所有 Spring Boot 3 服務共享的安全基線。
  • 哪些只能放在應用層級 dataId。
  • 哪些敏感值必須來自 Kubernetes Secret。
  • 哪些舊 Boot 服務需要暫時性相容層。
  • 每個連線池上限如何與 Pod 數量一起核算。

建議的設定分層

flowchart TD
  A["Kubernetes Secret / 環境變數"] --> D["最終 Environment"]
  B["global.properties<br/>Boot 3 保守基線"] --> D
  C["application.properties<br/>應用例外"] --> D
  E["Deployment 環境變數<br/>強制執行基線"] --> D
  D --> F["Spring Boot 屬性綁定"]

建議邊界：

層存放內容範例
Secret密碼、Token、憑證Redis、RabbitMQ、資料庫密碼
global dataId同版本、同語義的保守參數timeout、探針、預設併發
app dataId業務特有容量與相容項目pool、批次任務、Boot 2 別名
Deployment與容器直接相關且必須強制的項目JVM、HOME、診斷開關

請勿在四層中重複維護同一個 key。Spring 的屬性來源有優先順序；Deployment 環境變數一旦覆蓋 Nacos，控制台發布成功也不代表執行環境中的值已經改變。

一份可審閱的 Spring Boot 3 全域範本

下面使用佔位符，不包含生產密碼。先把它當作候選基線，而不是一次全部發布。

# ------------------------------------------------------------
# Web 与反向代理
# ------------------------------------------------------------
server.forward-headers-strategy=framework
server.shutdown=graceful
spring.lifecycle.timeout-per-shutdown-phase=30s

# 仅适用于 Servlet / Tomcat 服务；WebFlux 服务会忽略这些项
server.tomcat.threads.max=100
server.tomcat.threads.min-spare=10
server.tomcat.accept-count=100
server.tomcat.max-connections=2000
server.tomcat.connection-timeout=10s

# ------------------------------------------------------------
# Actuator 与 Kubernetes 探针
# ------------------------------------------------------------
management.endpoint.health.probes.enabled=true
management.health.livenessstate.enabled=true
management.health.readinessstate.enabled=true
management.endpoint.health.show-details=never
management.endpoints.web.exposure.include=health,info,prometheus,serviceregistry

# ------------------------------------------------------------
# HikariCP：只对使用 Spring 默认 Hikari DataSource 的服务生效
# ------------------------------------------------------------
spring.datasource.hikari.maximum-pool-size=10
spring.datasource.hikari.minimum-idle=2
spring.datasource.hikari.connection-timeout=3000
spring.datasource.hikari.validation-timeout=1000
spring.datasource.hikari.idle-timeout=600000
spring.datasource.hikari.max-lifetime=1800000
spring.datasource.hikari.keepalive-time=120000

# ------------------------------------------------------------
# Spring Data Redis / Lettuce
# 地址不是 Secret，密码从环境变量读取
# ------------------------------------------------------------
spring.data.redis.host=redis-service.app.svc.cluster.local
spring.data.redis.port=6379
spring.data.redis.database=0
spring.data.redis.password=${REDIS_PASSWORD:}
spring.data.redis.connect-timeout=3s
spring.data.redis.timeout=3s
spring.data.redis.client-type=lettuce
spring.data.redis.lettuce.shutdown-timeout=100ms

# 默认不启用连接池，避免 commons-pool2 出现在 classpath 后
# 每个 Pod 自动建立一批空闲连接
spring.data.redis.lettuce.pool.enabled=false

# ------------------------------------------------------------
# RabbitMQ
# ------------------------------------------------------------
spring.rabbitmq.addresses=rabbitmq.app.svc.cluster.local:5672
spring.rabbitmq.username=${RABBITMQ_USERNAME}
spring.rabbitmq.password=${RABBITMQ_PASSWORD}
spring.rabbitmq.virtual-host=/
spring.rabbitmq.connection-timeout=5s
spring.rabbitmq.requested-heartbeat=30s

spring.rabbitmq.cache.connection.mode=channel
spring.rabbitmq.cache.channel.size=25
spring.rabbitmq.cache.channel.checkout-timeout=2s

spring.rabbitmq.listener.type=simple
spring.rabbitmq.listener.simple.concurrency=1
spring.rabbitmq.listener.simple.max-concurrency=3
spring.rabbitmq.listener.simple.prefetch=10
spring.rabbitmq.listener.simple.acknowledge-mode=auto
spring.rabbitmq.listener.simple.auto-startup=true

# ------------------------------------------------------------
# 文件上传：限制请求在内存和临时盘中的放大
# ------------------------------------------------------------
spring.servlet.multipart.max-file-size=100MB
spring.servlet.multipart.max-request-size=110MB
spring.servlet.multipart.file-size-threshold=2MB

先修正棄用屬性

範本已使用 server.forward-headers-strategy，不再保留 server.use-forward-headers。NATIVE、FRAMEWORK、NONE 的選擇取決於實際代理鏈，不能無條件信任公網傳入的 X-Forwarded-*。

舊 key 的遷移報告與 spring-boot-properties-migrator 的移除條件統一整理在 Spring Boot 3 容器啟動異常復盤，本篇只維護最終生產設定。

Redis：連線少不代表連線池越小越好

Spring Data Redis 使用 Lettuce 時，一般指令可以複用共享的 native connection。連線池並非所有服務都預設需要。

Spring Boot 3.1 屬性說明指出，Lettuce pool 在 commons-pool2 存在時可以自動啟用。因此只要某個 starter 後來引入該依賴，連線行為就可能變化。

本次治理將全域預設設為：

spring.data.redis.lettuce.pool.enabled=false

只有滿足下列條件的應用才在自己的 dataId 中啟用 pool：

  • 使用阻塞式 Redis 指令。
  • 使用交易或需要獨佔連線的呼叫。
  • 已透過指標證明共享連線存在爭用。
  • classpath 明確包含相容版本的 commons-pool2。

應用層級候選：

spring.data.redis.lettuce.pool.enabled=true
spring.data.redis.lettuce.pool.max-active=8
spring.data.redis.lettuce.pool.max-idle=4
spring.data.redis.lettuce.pool.min-idle=0
spring.data.redis.lettuce.pool.max-wait=2s
spring.data.redis.lettuce.pool.time-between-eviction-runs=60s

min-idle=0 避免每個 Pod 在沒有業務流量時也強制保留一批閒置連線。是否需要調高，由 Redis connected_clients、指令延遲與 pool 等待指標決定。

別忘了 Redisson 是另一套用戶端

spring.data.redis.* 不會自動限制程式碼中單獨建立的 RedissonClient。如果服務同時使用 Spring Data Redis 與 Redisson，連線總數是兩套用戶端的總和。

需要額外盤點：

  • Redisson 是單節點、主從、哨兵還是叢集模式。
  • connectionPoolSize 與 connectionMinimumIdleSize。
  • subscription connection pool。
  • threads 與 nettyThreads。
  • 每個 Pod 實際建立了幾個 RedissonClient。

連線預算應按用戶端分別計算：

总连接上界
≈ Pod 数
× 每 Pod 的 Lettuce 连接
+ Pod 数
× 每 Pod 的 Redisson 普通连接
+ subscription 连接
+ Redis 运维与监控连接

多個業務模組各自 new RedissonClient，比 pool 參數偏大更危險。優先確保同一個應用上下文只建立一組受管理的用戶端。

RabbitMQ：全域限制的是每個 Listener 容器

Spring Boot RabbitMQ 屬性說明中：

  • concurrency 是最小的 listener invoker 執行緒數。
  • max-concurrency 是自動擴充上限。
  • prefetch 是每個消費者允許的最大未確認訊息數。

因此：

concurrency=1
max-concurrency=3
prefetch=10

不是「整個服務最多三條訊息」，而是每個 Listener 容器最多三個消費者，每個消費者最多十條未確認訊息。

若一個應用有 40 個 Listener，理論上限可能達到：

40 × 3 × 10 = 1200 条未确认消息

真實數量還受佇列流量與容器擴充策略影響，但這個乘法足以解釋為什麼 Listener 多的服務 Heap 會突然升高。

不建議在全域基線中直接修改：

spring.rabbitmq.listener.simple.default-requeue-rejected
spring.rabbitmq.listener.simple.retry.enabled
spring.rabbitmq.publisher-confirm-type

它們會改變訊息可靠性語意，必須由業務結合 DLQ、冪等與重試策略決定，不能當作純效能最佳化。

Hikari：先算資料庫能承受多少連線

maximum-pool-size=10 只有在總量合理的前提下才成立：

数据库业务连接上界
= 所有服务的 Pod 数 × 各自 maximumPoolSize
+ 任务、管理、迁移和运维连接

例如 50 個服務、每個 2 個 Pod、每池 20 個連線，理論上已經達到 2000 個連線。資料庫不一定因為每個池都「只有 20」就能承受。

建議步驟：

  1. 按資料庫實例彙總所有呼叫方與複本數。
  2. 記錄高峰的 active、idle、pending 與 acquire time。
  3. 一般服務先使用較小的池。
  4. 為高併發或長交易服務做應用層級例外。
  5. 保留資料庫維運與故障切換餘量。

如果專案使用 dynamic-datasource、Druid 或手動建立多個 DataSource，spring.datasource.hikari.* 可能只作用於預設資料來源。必須檢查最終 Bean，而不是只看 Nacos key。

Tomcat 執行緒與資料庫連線不是一對一

server.tomcat.threads.max=100 不代表應該給 Hikari 100 個連線。大量請求可能命中快取、驗證失敗或執行非資料庫邏輯；反過來，一個請求也可能並行存取多個資料來源。

容量關係應透過指標驗證：

HTTP active threads
→ 数据库 active / pending
→ 下游 P95/P99
→ CPU 与 GC

WebFlux/Netty 服務不會使用 Tomcat 執行緒設定，應在應用層級 dataId 刪除不適用的項目，並單獨管理 event loop、連線池與 Direct Buffer。

Actuator 暴露範圍必須配合網路邊界

全域設定中暴露 health、prometheus 與 serviceregistry 是為了探針、監控與優雅卸載流量。但 serviceregistry 能改變註冊狀態，不應直接暴露到公網。

至少要做到：

  • Management 連接埠只允許叢集內部存取。
  • Ingress 不轉發管理路徑，或透過認證與 NetworkPolicy 限制存取。
  • health detail 不洩漏地址、帳號或異常堆疊。
  • Prometheus 透過明確的 ServiceMonitor 或受控抓取存取。

如果無法保證邊界，就不要為了 preStop 方便而全域暴露管理端點。

Boot 2 服務不要直接繼承這份全域 Redis 設定

Spring Boot 2 使用 spring.redis.*，Spring Boot 3 使用 spring.data.redis.*。仍未升級的服務只在自己的 dataId 中新增相容別名，不要把舊前綴重新塞回 Boot 3 全域基線。

相容設定、localhost:6379 的證據鏈與 commons-pool2 陷阱統一整理在 Boot 2/3 Redis 設定回退 localhost，本篇不再重複。

Nacos 發布順序

全域 dataId 的變更會影響大量用戶端，建議：

  1. 匯出並儲存原始設定、namespace、group、dataId 與校驗值。
  2. 對所有 key 建立 Boot 版本與元件適用矩陣。
  3. 從 global 中刪除明顯屬於單一應用的參數。
  4. 選一個一般服務，用應用層級臨時覆蓋來測試候選值。
  5. 滾動一個 Pod，驗證真實的 Redis、RabbitMQ 與資料庫路徑。
  6. 觀察連線數、執行緒、Heap、訊息積壓與延遲。
  7. 再發布 global，並分批滾動服務。
  8. 回讀 Nacos，掃描新 Pod 的有效設定與近期日誌。

不要同時修改：

  • Redis pool。
  • RabbitMQ 併發。
  • Hikari 上限。
  • JVM Heap。
  • 探針閾值。

否則記憶體用量下降或吞吐量退化後，無法判斷是哪個參數造成的。

驗收指標

元件必看指標風險訊號
Redisconnected_clients、指令延遲、逾時連線下降但 pool 等待上升
Redisson每 Pod 的用戶端與連線數多實例重複建立
RabbitMQready、unacked、consumer、channel積壓持續增長
Hikariactive、idle、pending、acquirepending 非零且延遲升高
Tomcatactive、queue、reject執行緒長期打滿
JVMHeap used/committed、GC、RSSFull GC 或 OOM 增加
KubernetesReady、Restart、rollout舊 ReplicaSet 無法退出

至少經歷過一個真實業務高峰，再決定是否繼續縮減。

完成定義

  • global.properties 只包含適用於 Boot 3 且語意通用的參數。
  • Secret 不以明文存放在 Nacos。
  • Redis 預設不因 classpath 變化而自動擴大連線池。
  • Redisson 與 Spring Data Redis 分別計入連線預算。
  • RabbitMQ 併發與 prefetch 已按 Listener 數量核算。
  • 資料庫連線總上限低於實例容量，並保留故障切換的餘量。
  • Servlet 與 WebFlux 設定不再混為一談。
  • Deployment 環境變數與 Nacos 不得互相覆蓋、形成雙重事實來源。
  • Boot 2 相容項目只放在應用層級 dataId，並訂有移除期限。

最終結論

全域設定的目標不是讓所有服務參數完全相同，而是提供最小、安全、可預測的預設行為。

Redis 連線數、RabbitMQ 未確認訊息與資料庫連線池都會隨 Pod 數與業務元件數放大。把它們放進 Nacos 之前，必須先做乘法；把參數發布到 Nacos 之後，還要確認沒有被 Deployment 環境變數覆蓋。

真正完整的設定不是 key 最多，而是每個 key 都有適用版本、容量依據、覆蓋關係、監控指標與回滾邊界。
