Kubernetes 滾動發布如何做到業務無感：探針、優雅停機與 PDB 實戰

說明 startup、readiness、liveness 探針及其時間計算，結合 Spring Boot 優雅停機、Deployment 策略、preStop 與 PDB 設計可驗證的滾動發布。

滾動發布期間出現少量 Connection refused、Connect timed out，不應該簡單歸類為「正常」。它通常代表新 Pod 太早接流量、舊 Pod 太快退出、應用沒有優雅停機，或是服務實際上只有一個可用複本。

一次 Pod 替換發生了什麼

sequenceDiagram
  participant D as Deployment
  participant N as New Pod
  participant S as Service
  participant O as Old Pod
  D->>N: 建立新 Pod
  N->>N: startupProbe
  N->>N: readinessProbe
  N->>S: Ready 後加入 EndpointSlice
  D->>O: 請求終止舊 Pod
  O->>S: readiness 變為 false
  O->>O: preStop 與優雅停機
  O-->>D: 在 grace period 內退出

無感發布依賴整個順序，而不是某一個 YAML 參數。

三種探針各司其職

Kubernetes 官方說明：設定 startupProbe 後，在它成功之前不會執行 readiness 和 liveness。Liveness、Readiness 和 Startup Probes 是設計探針的基線。

startupProbe：應用是否完成初始化

適合 Spring 上下文、資料庫遷移、快取預熱較慢的服務：

startupProbe:
  httpGet:
    path: /actuator/health/readiness
    port: management
  periodSeconds: 10
  timeoutSeconds: 5
  failureThreshold: 30

最大啟動容忍時間大約是：

initialDelaySeconds + periodSeconds × failureThreshold

上例約為 300 秒。timeoutSeconds 是單次探測逾時，不應再簡單乘進總時間。

readinessProbe：此刻能不能接請求

readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: management
  periodSeconds: 10
  timeoutSeconds: 5
  failureThreshold: 3
  successThreshold: 1

readiness 失敗不會重啟容器，只會把 Pod 從 Service Endpoint 中移除。資料庫連線池耗盡、必要依賴不可用時，可以讓 readiness 失敗，但要避免把一個可降級依賴錯誤地設為全域 NotReady。

livenessProbe：行程是否已經無法自癒

livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: management
  periodSeconds: 10
  timeoutSeconds: 5
  failureThreshold: 12

10/5/12 表示每 10 秒發起一次探測，單次最多等 5 秒，連續 12 次失敗後重啟容器。粗略的故障窗口約 120 秒，不是 60 秒。

不要讓 liveness 深度訪問資料庫、Redis、Nacos 或外部 HTTP。依賴阻塞時重啟所有 Pod，可能把局部故障放大成重啟風暴。

先讓 Spring Boot 正確優雅停機

server.shutdown=graceful
spring.lifecycle.timeout-per-shutdown-phase=30s

應用收到 SIGTERM 後應：

  1. 停止接收新請求。
  2. 等待正在處理的請求完成。
  3. 停止訊息監聽器和排程任務。
  4. 提交或回滾交易。
  5. 關閉連線池並退出。

透過日誌驗證，而不是只相信設定：

kubectl -n <namespace> delete pod <test-pod>
kubectl -n <namespace> logs <test-pod> -f

terminationGracePeriodSeconds 是總預算

spec:
  terminationGracePeriodSeconds: 120

它涵蓋 preStop、應用優雅停機和容器退出的總時間。超過預算後，kubelet 會強制終止行程。

設定為 120 秒不代表每次刪除都必須等待 120 秒；行程提前退出，Pod 會立即結束。

如果應用最壞請求需要 45 秒，preStop 等待 10 秒，停止訊息監聽器需要 20 秒，60 秒的總預算就可能過短。

preStop 用來排空，不是掩蓋慢啟動

最簡單的做法：

lifecycle:
  preStop:
    exec:
      command: ["sh", "-c", "sleep 10"]

這給 Endpoint 傳播和上游連線池一點排空時間，但這 10 秒也屬於 grace period。

更成熟的應用可以在 preStop hook 中主動：

  • 將 readiness 設為 false。
  • 停止從 Kafka/RabbitMQ 拉取新訊息。
  • 等待目前任務完成。

不要用 180 秒固定 sleep 取代正確的應用生命週期。

Deployment 策略決定同時有幾個可用 Pod

spec:
  replicas: 2
  minReadySeconds: 15
  progressDeadlineSeconds: 600
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0

含義：

  • 發布時允許暫時多建立一個 Pod。
  • 在新 Pod 沒有 Ready 之前，不允許減少現有可用複本。
  • 新 Pod Ready 後還要穩定 15 秒才算可用。

前提是節點池能容納 surge Pod。資源已滿時，新 Pod 會 Pending，發布會停止但舊服務仍可繼續。

單複本即使使用 maxUnavailable: 0，也無法抵禦節點故障；某些使用 ReadWriteOnce 本地磁碟區的應用還無法同時啟動新舊 Pod。

PDB 不是 Deployment 滾動策略

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: app-api
spec:
  minAvailable: 1
  selector:
    matchLabels:
      app.kubernetes.io/name: app-api

PDB 主要約束使用 Eviction API 的自願中斷，例如 kubectl drain。Kubernetes 官方明確指出，Deployment 和 StatefulSet 自身的滾動升級不受 PDB 限制；滾動升級由工作負載策略控制。Disruptions

因此同時需要：

  • Deployment 的 maxSurge/maxUnavailable。
  • PDB 保護節點維護。
  • 反親和或 topology spread 防止複本同節點。

一份完整範本

apiVersion: apps/v1
kind: Deployment
metadata:
  name: app-api
spec:
  replicas: 2
  minReadySeconds: 15
  progressDeadlineSeconds: 600
  strategy:
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }
  template:
    spec:
      terminationGracePeriodSeconds: 120
      containers:
        - name: app
          image: <image-registry>/app-api:<version>@sha256:<digest>
          ports:
            - { name: management, containerPort: 8081 }
          lifecycle:
            preStop:
              exec: { command: ["sh", "-c", "sleep 10"] }
          startupProbe:
            httpGet: { path: /actuator/health/readiness, port: management }
            periodSeconds: 10
            timeoutSeconds: 5
            failureThreshold: 30
          readinessProbe:
            httpGet: { path: /actuator/health/readiness, port: management }
            periodSeconds: 10
            timeoutSeconds: 5
            failureThreshold: 3
          livenessProbe:
            httpGet: { path: /actuator/health/liveness, port: management }
            periodSeconds: 10
            timeoutSeconds: 5
            failureThreshold: 12

參數不能無腦複製。應使用應用真實啟動分位數、請求耗時、訊息處理耗時和依賴恢復時間計算。

如果數十個服務都要複用這套發布結構，應繼續閱讀統一 Spring Boot Deployment 範本：它只保留一份範本源碼，用參數表達資源分檔、節點池和舊應用相容例外。

發布前容量檢查

kubectl -n <namespace> get deployment app-api -o wide
kubectl describe node <target-node> | sed -n '/Allocated resources:/,$p'
kubectl get events -A --field-selector reason=FailedScheduling

發布需要額外一個 Pod 的 requests。不要用目前 kubectl top 的低使用率取代排程容量。

如何驗證是否真正無感

在獨立終端持續發送請求：

while true; do
  curl -fsS -o /dev/null -w '%{http_code} %{time_total}\n' \
    https://app.example.com/<business-read-api>
  sleep 0.2
done

開始滾動：

kubectl -n <namespace> set image deployment/app-api \
  app=<image-registry>/app-api:<new-version>@sha256:<new-digest>

kubectl -n <namespace> rollout status deployment/app-api --timeout=15m
kubectl -n <namespace> get pod -l app.kubernetes.io/name=app-api -w

同時觀察：

kubectl -n <namespace> get endpointslice \
  -l kubernetes.io/service-name=app-api -w

kubectl -n <namespace> logs deployment/app-api --since=15m \
  | grep -Ei 'timeout|refused|shutdown|killed|oom'

驗收不只看 HTTP 200，還要看錯誤率、P95/P99、訊息積壓、資料庫連線和執行緒池。

常見錯誤

現象根因修復方向
新 Pod Ready 後立即報錯readiness 太淺，依賴尚未初始化將真正必要的初始化納入 readiness
舊 Pod 仍有請求卻退出grace period 太短或沒有優雅停機延長預算並驗證 SIGTERM
所有 Pod 同時重啟liveness 深度依賴共享中介軟體liveness 只判斷行程自癒能力
新 Pod 一直 Pending沒有 surge 容量釋放或增加節點容量
有 PDB 仍在發布中斷PDB 不控制 Deployment rollout設定滾動策略和複本數

完成定義

  • 至少兩個可用複本分布在不同節點。
  • startup、readiness、liveness 各自只承擔一個職責。
  • 應用接收 SIGTERM 後能在 grace period 內退出。
  • maxUnavailable: 0，且節點有 surge 容量。
  • PDB 能阻止不安全的節點 drain。
  • 連續業務請求在發布期間無 5xx、拒絕連線和異常逾時。
  • 發布失敗時能使用 kubectl rollout undo 還原上一 Revision。

無感發布不是把三個探針都調大，而是讓流量進入、流量排空和行程生命週期嚴格對齊。
