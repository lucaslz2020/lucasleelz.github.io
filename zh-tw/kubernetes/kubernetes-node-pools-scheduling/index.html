Kubernetes 節點池如何規劃：標籤、污點、親和性與反親和實戰

從伺服器清單開始，逐步劃分入口、平台、業務、資料、監控、共享與預留節點池，並用標籤、污點、容忍與親和性落實排程策略。

節點池不是雲端廠商才有的概念。即使所有節點都來自本地虛擬化平台，也應該用標籤、污點和親和性把不同故障域分開。

系列導覽：Kubernetes 重建遷移教學系列。本篇在基礎元件驗收通過後執行。

這篇文章從一份節點清單開始，把規劃真正落實到 Kubernetes 排程規則中。

第 1 步：先按職責分池

一個通用的起點是：

節點池典型工作負載是否建議獨佔
control-planeAPI Server、etcd是
ingressIngress Controller、四層入口是
platformNacos、DevOps、核心平台視容量而定
app-*各業務環境建議用於生產
dataMySQL、Redis、Kafka、RabbitMQ、ZooKeeper是
observabilityPrometheus、日誌、追蹤建議
shared小型無狀態服務否
reserve故障和滾動升級預留不部署常規業務

先為每個節點分配一個主池，不要讓同一台機器同時出現在兩個獨佔池。

第 2 步：把規劃寫成 CSV 並驗證

hostname,pool,cpu,memory_gib,disk_type,failure_domain
worker-a,app-test,8,32,ssd,host-a
worker-b,app-test,8,32,ssd,host-b
worker-c,app-test,8,32,ssd,host-c

檢查重複：

cut -d, -f1 inventory/node-pools.csv | tail -n +2 | sort | uniq -d

檢查每個池的節點數：

cut -d, -f2 inventory/node-pools.csv | tail -n +2 | sort | uniq -c

高可用三複本要同時考慮 Kubernetes 節點和虛擬化宿主機。三個 Pod 落在三台虛擬機器，但若三台虛擬機器位於同一台實體宿主機，仍是單點。

第 3 步：先加入描述性標籤

標籤描述「節點是什麼」，不會產生排他效果：

kubectl label node worker-a workload.yj/pool=app-test
kubectl label node worker-a topology.yj/failure-domain=host-a
kubectl label node worker-a hardware.yj/disk=ssd

批次完成後檢查：

kubectl get nodes -L workload.yj/pool,topology.yj/failure-domain,hardware.yj/disk

自訂標籤應使用自己的 DNS 前綴，避免與 Kubernetes 保留標籤衝突。

第 4 步：再決定哪些池需要污點

污點表示「預設不允許誰進來」。對獨佔資料池可以加入：

kubectl taint node data-a workload.yj/pool=data:NoSchedule
kubectl taint node data-b workload.yj/pool=data:NoSchedule
kubectl taint node data-c workload.yj/pool=data:NoSchedule

檢查：

kubectl describe node data-a | sed -n '/Taints:/,/Unschedulable:/p'

不要先幫幾十個節點加污點，再回頭修改 Deployment。正確順序是：

准备应用 toleration 和 nodeAffinity
→ server-side dry-run
→ 给第一台节点加污点
→ 验证调度
→ 批量推广

第 5 步：應用同時宣告容忍與目標節點

只設定 toleration 代表「允許進入」，並不保證一定會進入資料池。應同時使用 nodeAffinity：

spec:
  template:
    spec:
      tolerations:
        - key: workload.yj/pool
          operator: Equal
          value: data
          effect: NoSchedule
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
              - matchExpressions:
                  - key: workload.yj/pool
                    operator: In
                    values: [data]

先做 dry-run：

kubectl apply --server-side --dry-run=server -f workload.yaml

第 6 步：讓有狀態複本分散

Kafka、RabbitMQ、ZooKeeper、MySQL 複本不能落在同一節點。使用 Pod 反親和：

affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app.kubernetes.io/name: zookeeper
        topologyKey: kubernetes.io/hostname

如果還要跨虛擬化宿主機，可再使用自訂故障域標籤：

topologyKey: topology.yj/failure-domain

節點不足時，required 會讓 Pod 維持 Pending。這比把三個複本擠到同一個節點更誠實；應擴充節點或調整容量規劃，而不是默默降級故障域。

第 7 步：為滾動升級保留容量

假設某個業務有兩個 Pod，每個 request 為 2 核 6 GiB。滾動升級使用預設 maxSurge: 25% 時，至少需要暫時容納第三個 Pod。

可用資源要按 request 計算，而不是按實際瞬時使用量：

kubectl describe node <node> | sed -n '/Allocated resources:/,$p'
kubectl top node <node>

兩者用途不同：

  • describe 的 Allocated resources 是排程器已經承諾的 request/limit。
  • top 是目前實際使用量。

低優先權業務不應長期佔用預留池，否則故障遷移和滾動發布都會卡住。

第 8 步：驗證排程結果

部署後執行：

kubectl get pods -A -o custom-columns='NS:.metadata.namespace,POD:.metadata.name,NODE:.spec.nodeName' \
  | sort

kubectl get pods -n <namespace> -l app.kubernetes.io/name=<app> -o wide
kubectl get events -A --field-selector reason=FailedScheduling --sort-by=.lastTimestamp

重點檢查：

  • 獨佔池是否混入無關 Pod。
  • 三複本是否落在不同節點和故障域。
  • DaemonSet 是否因缺少 toleration 而無法排程到帶污點的節點。
  • 預留節點是否仍為閒置。
  • 小規格節點是否承載了不適合的重型服務。

實戰復盤：0/69 nodes are available 應該怎麼讀

一次雙複本服務發布時，事件持續回報：

0/69 nodes are available:
several nodes had untolerated taint,
some nodes didn't match Pod's node affinity/selector,
some nodes had insufficient memory

這不表示 69 台機器全部記憶體不足。排程器會依序過濾：

flowchart LR
  A["69 個節點"] --> B["Taint / Toleration"]
  B --> C["nodeSelector / nodeAffinity"]
  C --> D["CPU / Memory request"]
  D --> E["Topology spread / anti-affinity"]
  E --> F["可排程節點"]

應先把 Pod 的約束完整輸出：

kubectl -n <namespace> get pod <pending-pod> -o jsonpath='
nodeSelector={.spec.nodeSelector}{"\n"}
affinity={.spec.affinity}{"\n"}
tolerations={.spec.tolerations}{"\n"}
requests={.spec.containers[*].resources.requests}{"\n"}
spread={.spec.topologySpreadConstraints}{"\n"}'

再逐層檢查候選節點：

kubectl get node --show-labels
kubectl describe node <candidate-node>
kubectl get events -n <namespace> \
  --field-selector reason=FailedScheduling \
  --sort-by=.lastTimestamp

為什麼兩個 Pod 實際只用 2G，第三個仍提示記憶體不足

排程器看的不是「兩個既有 Pod 目前合計用了多少」，而是新 Pod 的 memory request 與節點剩餘可用的 allocatable：

可调度
⇔ node allocatable
  - 已调度 Pod requests
  ≥ incoming Pod request

如果每個 Pod 的 request 為 3.5 GiB，即使兩個既有實例目前各用約 1 GiB，新 revision 的 surge Pod 仍須完整申請 3.5 GiB。

這也是資源治理後來把一般服務、倉儲服務和重型服務分級的原因：request 應涵蓋穩定狀態與可解釋的峰值，但不能用一個過大的通用值佔滿所有專屬節點。

為什麼看起來有空節點，Pod 仍然無法使用

「節點沒有業務 Pod」不等於「這個 Pod 可以排程進去」。它可能：

  • 帶有目前 Pod 不容忍的 NoSchedule 污點。
  • 缺少 required nodeSelector 標籤。
  • 不屬於 topology spread 的 eligible domain。
  • 已被其他 Pod 的 request 預留。
  • 是故障或滾動升級預留節點。

因此不能只憑節點清單推論「還有 9 台伺服器閒置」。先把污點、標籤和 allocated requests 一併統計。

火山引擎為什麼把手動刪除的標籤和污點寫回來

託管節點池的設定是控制面的期望狀態。若節點池中仍宣告：

app-type=<dedicated-service>
taint app-type=<dedicated-service>:NoSchedule

只執行：

kubectl label node <node> app-type-
kubectl taint node <node> app-type-

可能只是暫時改變 Kubernetes Node 物件。節點池控制器再次同步時會還原這些欄位。

火山引擎 VKE 節點池文件明確說明，節點池中新增或修改標籤、污點，會自動更新新建節點和既有節點。

要把專屬節點永久遷入公共池，應：

  1. 先確認該節點不再承擔獨佔業務和特殊硬體職責。
  2. 在 VKE 節點池設定中刪除或修改目標標籤、污點。
  3. 等控制器完成同步。
  4. 再檢查 Kubernetes Node 物件。
  5. 遷移一個低風險 Pod 驗證公共池排程。
  6. 確認重啟、調整容量或節點替換後，設定仍不會還原。

如果原節點池的所有成員都必須共用同一組設定，單一機器不應繼續留在該節點池；需要將它遷移到公共節點池，或新建一個沒有專屬污點的節點池。

實戰復盤：兩個複本為什麼仍在同一節點

只有 preferred node affinity 或 ScheduleAnyway 時，排程器可能會為了更佳的資源評分，把兩個複本放在同一台機器。這是合法行為，但無法抵抗單節點故障。

在 Kubernetes 1.30 的 Deployment 中，可以按目前 ReplicaSet revision 強制分散：

topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: DoNotSchedule
    matchLabelKeys:
      - pod-template-hash
    labelSelector:
      matchLabels:
        app: <application>
        version: <version>

matchLabelKeys: [pod-template-hash] 讓新舊 ReplicaSet 分開計算。這樣在 maxUnavailable: 0、maxSurge: 1 的滾動發布中，舊 revision 不會因為參與 skew 計算而阻塞新 revision。

Kubernetes topology spread 文件也把 pod-template-hash 作為 Deployment revision 的典型場景。

強制分散前必須保證：

  • 至少兩個節點同時符合 nodeSelector/affinity。
  • 兩個節點都能被 Pod 的 toleration 接受。
  • 每個節點都能容納一個複本的 request。
  • 發布期間有容納 surge Pod 的空間。

如果只有一個合格節點，DoNotSchedule 會讓第二個 Pod 維持 Pending。這是故障域約束下的正常結果，不應透過刪除 spread 規則悄悄恢復同機部署。

如何安全撤銷

刪除污點：

kubectl taint node data-a workload.yj/pool=data:NoSchedule-

刪除標籤：

kubectl label node data-a workload.yj/pool-

撤銷前先修改工作負載，避免它仍要求一個已經不存在的標籤。

完成定義

  • 每個節點只有一個明確的主池。
  • 獨佔池同時設定標籤和污點。
  • 工作負載同時設定 toleration 與 nodeAffinity。
  • 有狀態三複本跨節點，關鍵服務還要跨實體故障域。
  • 滾動升級時至少能容納一個 surge Pod。
  • 監控、CNI、CSI 等 DaemonSet 已驗證能容忍必要污點。
  • 預留節點沒有被常規業務長期佔用。
  • 託管節點池與 Kubernetes Node 上的標籤、污點保持一致。
  • FailedScheduling 已按污點、親和性、request 和 spread 分層解釋。
  • 雙複本使用 revision-aware topology spread 強制跨節點。
