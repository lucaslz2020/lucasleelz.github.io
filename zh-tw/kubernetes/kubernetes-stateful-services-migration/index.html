ENGINEERING NOTE · 2026年7月4日

Kubernetes 叢集重建時，MySQL、Redis、Kafka、RabbitMQ 和 Zookeeper 怎麼遷移

依 RPO、備份還原、零複本預部署和逐層驗收遷移常見資料服務，避免只複製 PVC、只啟動空庫或把三個複本排程到同一節點。

系列導覽：Kubernetes 重建遷移教學系列。所有資料庫名稱、帳號、節點和儲存位址均為佔位符。

有狀態服務遷移最危險的迷思是：Pod 為 Running，就代表資料已經遷移完成。實際上，一個全新的空資料庫同樣可以 Running，甚至健康檢查全部通過。

先定義每個服務的資料邊界

建立清單：

服務權威資料可接受遺失量 RPO可容許停機時間 RTO還原工具驗證負責人
MySQL業務資料表、帳號、binlog<rpo><rto>實體/邏輯備份DBA
RedisSession、快取或業務資料<rpo><rto>RDB/AOF應用團隊
KafkaTopic、訊息、offset<rpo><rto>複製/同步工具訊息團隊
RabbitMQdefinitions、訊息、使用者<rpo><rto>definitions + 資料方案訊息團隊
Zookeeperznodes、ACL、交易日誌<rpo><rto>snapshot/log平台團隊

快取 Redis 和業務主資料 Redis 的遷移標準完全不同。沒有 RPO/RTO，就無法決定要複製、停寫匯出還是重新產生。

總體遷移順序

flowchart LR
  A["盘点数据和依赖"] --> B["恢复演练"]
  B --> C["新集群零副本预部署"]
  C --> D["全量备份与恢复"]
  D --> E["停止写入"]
  E --> F["增量追平"]
  F --> G["服务端验证"]
  G --> H["客户端切换"]
  H --> I["观察与回滚窗口"]

不要等到遷移當天才第一次嘗試備份還原。

第 1 步：盤點真實儲存位置

kubectl get statefulset -A -o wide
kubectl get pvc,pv -A
kubectl get storageclass
kubectl get pod -A -o custom-columns='NS:.metadata.namespace,POD:.metadata.name,NODE:.spec.nodeName'

對每個 PVC 記錄：

  • StorageClass 和回收策略。
  • 底層 Volume、NFS 目錄或本機路徑。
  • Pod 與 Volume 的 nodeAffinity。
  • 檔案擁有者 UID/GID。
  • 目前資料量和成長速度。
  • 快照、備份與還原耗時。

Kubernetes StatefulSet 提供穩定的身分識別與持久 Volume 綁定，但不會自動把舊叢集的資料複製到新叢集。StatefulSets 也明確說明，縮容或刪除 StatefulSet 預設不會刪除關聯 Volume，這是資料安全設計，不是完整備份。

第 2 步：先部署零複本物件

在新叢集預先建立：

  • Namespace、Service、Headless Service。
  • Secret 和 ConfigMap。
  • StorageClass、PV、PVC。
  • StatefulSet，但複本數為 0。
  • NetworkPolicy、ServiceMonitor 和警示。
kubectl apply --server-side --dry-run=server -f manifests/data-services/
kubectl apply -f manifests/data-services/
kubectl -n <namespace> scale statefulset/<service> --replicas=0

這樣可以提前發現 API、儲存、排程和 Secret 的問題，又不會啟動一個空服務接受連線。

第 3 步：MySQL 遷移

邏輯備份範例

mysqldump --single-transaction --routines --triggers --events \
  --set-gtid-purged=OFF \
  -h <old-mysql-host> -u <backup-user> -p \
  --databases <database-list> \
  > backup/mysql-full.sql

sha256sum backup/mysql-full.sql > backup/mysql-full.sql.sha256

大型資料庫應評估實體備份、複製或專業遷移工具。MySQL 官方將邏輯/實體、全量/增量以及基於 binlog 的時間點還原視為不同策略，不能只保存一份 SQL 就宣稱可還原。MySQL Backup and Recovery

還原到隔離執行個體並驗證：

mysql -h <restore-host> -u <restore-user> -p < backup/mysql-full.sql

至少比較：

SELECT COUNT(*) FROM <critical-table>;
SHOW INDEX FROM <critical-table>;
SHOW GRANTS FOR '<application-user>'@'%';
SELECT @@character_set_server, @@collation_server, @@sql_mode;

正式切換時停止寫入、記錄 binlog/GTID 位置、追平增量，再切換應用程式連線。空資料庫能連線不算成功。

第 4 步：Redis 遷移

先判斷 Redis 的用途：

  • 可丟棄的快取。
  • Session 儲存。
  • 分散式鎖。
  • 業務主資料。

查看持久化狀態：

redis-cli -h <old-redis-host> INFO persistence
redis-cli -h <old-redis-host> INFO keyspace
redis-cli -h <old-redis-host> CONFIG GET appendonly
redis-cli -h <old-redis-host> CONFIG GET dir

RDB 是時間點快照，AOF 記錄寫入操作；兩者同時啟用時，Redis 重啟會優先使用較完整的 AOF。遷移前先依 Redis Persistence 確認對應版本的檔案結構，尤其注意 Redis 7 之後的多檔案 AOF。

還原後驗證：

redis-cli -h <new-redis-service> PING
redis-cli -h <new-redis-service> INFO keyspace
redis-cli -h <new-redis-service> DBSIZE

然後從真實應用程式 Pod 存取 Service DNS。PING 成功只證明 Redis 行程可用，不證明 key、TTL、資料庫編號和序列化格式正確。

第 5 步：Kafka 遷移

Kafka 不能只把某個 broker 的資料目錄複製到三台新節點就算完成。需要盤點：

Topic 与 partition
replication factor
min.insync.replicas
consumer group offsets
ACL
broker.id 或 node.id
listener / advertised.listener

遷移策略通常是：

  1. 在新叢集建立結構相同的 Topic。
  2. 使用經過驗證的跨叢集複製工具持續同步。
  3. 驗證生產與消費。
  4. 短暫停寫或接受已定義的 RPO。
  5. 追平 lag，先切換生產者，再切換消費者。

Kubernetes 內部 listener 可以使用穩定 DNS，但用戶端最終會直連 broker 回傳的 advertised address。不能把三個 broker 簡單替換成一個普通 ClusterIP。

驗證：

kafka-topics.sh --bootstrap-server <new-bootstrap> --describe
kafka-consumer-groups.sh --bootstrap-server <new-bootstrap> --all-groups --describe

再發送帶唯一 ID 的訊息，確認目標消費端只處理一次或具備冪等能力。

第 6 步：RabbitMQ 遷移

分別保護：

  • 使用者、角色、vhost、policy、exchange、queue、binding。
  • 尚未消費的持久訊息。
  • TLS 與 Erlang cookie 等叢集機密資料。

先匯出 definitions：

rabbitmqctl export_definitions /backup/definitions.json

definitions 不包含佇列中的訊息。若必須保留訊息，應依佇列類型、版本和拓撲選擇官方支援的複製、備份或停機遷移方案。

還原後檢查：

rabbitmq-diagnostics check_running
rabbitmq-diagnostics check_local_alarms
rabbitmqctl list_vhosts
rabbitmqctl list_queues name durable messages_ready messages_unacknowledged

最後用測試 exchange/queue 完成一次生產與消費。

第 7 步：Zookeeper 遷移

盤點：

  • dataDir、snapshot 和 transaction log。
  • myid 與成員清單。
  • ACL 和業務根路徑。
  • 目前 Leader/Follower 狀態。

三個複本必須分散到不同節點和實體故障域：

podAntiAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchLabels:
          app.kubernetes.io/name: zookeeper
      topologyKey: kubernetes.io/hostname

還原時不要讓多個節點使用相同 myid。啟動後檢查成員角色、znode 和 ACL，再讓 Kafka 等依賴接入。

遷移完成後如果 ZooKeeper Pod 長期接近記憶體 request，不要直接判斷是洩漏；可以按 ZooKeeper 固定堆與 Kubernetes 資源縮減 繼續檢查 Xms/Xmx、mntr、資源預留和 PVC。

第 8 步：按依賴順序啟動

PVC 与存储
→ MySQL / Redis
→ Zookeeper
→ Kafka / RabbitMQ
→ Nacos
→ 平台依赖
→ 业务服务

每啟動一個服務，先驗證 Endpoint：

kubectl -n <namespace> get pod,service,endpointslice -o wide
kubectl -n <namespace> get events --sort-by=.lastTimestamp

第 9 步：切換用戶端

設定優先使用 Service DNS：

spring.datasource.url=jdbc:mysql://mysql.<namespace>.svc.cluster.local:3306/<database>
spring.data.redis.host=redis.<namespace>.svc.cluster.local
spring.kafka.bootstrap-servers=<kafka-bootstrap-dns>:9092
spring.rabbitmq.host=rabbitmq.<namespace>.svc.cluster.local

Kafka broker advertised listener、跨叢集資料庫和外部消費者必須單獨設計，不能機械式套用。

第 10 步：真實業務驗收

至少包含：

  • MySQL 真實應用程式帳號讀寫和交易。
  • Redis Session、TTL 和鎖。
  • Kafka 生產、消費、offset 與 lag。
  • RabbitMQ 發布、確認、消費和積壓。
  • Zookeeper 節點讀取、寫入和 ACL。
  • 刪除或重建一個非關鍵複本後的還原。

回滾邊界

把入口切回舊叢集的做法，只適用於新環境尚未產生權威寫入的階段。一旦新叢集接受寫入，就必須提前設計：

  • 反向增量同步。
  • 雙寫一致性與去重。
  • 寫入凍結點。
  • 資料衝突處理。

沒有這些機制，就不能把「改回 DNS」描述為完整回滾。

完成定義

  • 每個服務都有經驗證的 RPO、RTO 和還原步驟。
  • 備份在隔離環境成功還原，不只是檔案存在。
  • 資料量、關鍵 row/key、權限、索引、Topic、佇列和 ACL 與基線一致。
  • 三個複本跨節點並盡量跨實體故障域。
  • 應用程式透過 Service DNS 存取依賴。
  • 真實讀寫、訊息生產消費和故障重建通過。
  • 舊環境和備份在觀察期結束前保留唯讀。

資料服務遷移的完成標準不是所有 StatefulSet Ready，而是業務能證明資料完整、持續寫入且仍可回滾。
