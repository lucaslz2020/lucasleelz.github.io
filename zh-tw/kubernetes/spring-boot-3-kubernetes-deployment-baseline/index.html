50 個 Spring Boot 服務如何統一成一份 Kubernetes Deployment 範本

復盤一次多服務 Deployment 治理：合併重複範本，統一滾動發布、探針、JVM、快取目錄、安全上下文、訊息並發、資源分檔與跨節點策略。

本文來自一批 Spring Boot 服務在託管 Kubernetes 上的 Deployment 治理。服務名稱、映像、命名空間與容量已泛化。系列導覽：Kubernetes 重建遷移教學系列。

最初的問題看起來彼此無關：

  • 兩個 Pod 經常落在同一節點上。
  • 部分服務滾動發布時長期 Pending。
  • Nacos 啟動時無法建立 /root/nacos。
  • 檔案上傳元件因為 mkdir failed 讓 Spring Context 啟動失敗。
  • 某些服務常駐 3–4 GiB，另一些只有 1 GiB。
  • 倉儲類服務擁有大量 RabbitMQ Listener，在途訊息把 Heap 推高。
  • 有的 Deployment 還在載入 JProfiler，有的已經關閉。
  • 五份「幾乎相同」的 Java Deployment 越改越不一致。

如果逐個為每個服務的 YAML 打補丁，很快又會發生設定漂移。最終方案不是把五個服務合併成一個 Deployment，而是：

一份参数化模板
→ 渲染出多个相互独立的 Deployment
→ 结构和安全基线一致
→ 只让资源、端口、节点池等数据存在差异

「合併 Deployment」到底合併什麼

一個 Deployment 只能描述一種 Pod 範本。不同服務仍然需要獨立的：

  • Deployment 名稱。
  • 映像與版本。
  • Service 與連接埠。
  • 複本數。
  • 回滾邊界。
  • 擴縮容與發布節奏。

真正應合併的是重複的範本原始碼：

旧结构
common Deployment
finance Deployment
finance-rest Deployment
system-setting Deployment
repair-check Deployment

新结构
一份 Java Deployment 模板
+ app.name / app.port / app.replicas / resourceClass / nodePool 等参数

這樣修改探針或安全上下文時只改一個地方，同時仍會產生多個 Kubernetes Deployment。

基線整體結構

flowchart TD
  A["參數化 Java Deployment"] --> B["滾動發布與可用性"]
  A --> C["排程與故障域"]
  A --> D["容器安全與可寫目錄"]
  A --> E["JVM 與診斷"]
  A --> F["RabbitMQ 在途量"]
  A --> G["資源分檔"]
  B --> H["渲染後的獨立 Deployment"]
  C --> H
  D --> H
  E --> H
  F --> H
  G --> H

這六個部分應該一起評審。只最佳化 JVM，卻讓探針在 GC 時誤殺 Pod；只強制跨節點，卻沒有給滾動發布預留第三個 Pod 的 request，都會產生新的事故。

第 1 層：讓滾動發布有明確完成條件

spec:
  replicas: <replicas>
  revisionHistoryLimit: 5
  progressDeadlineSeconds: 600
  minReadySeconds: 20
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1

各自含義如下：

  • maxUnavailable: 0：新 Pod 穩定前不主動減少舊複本。
  • maxSurge: 1：發布期間最多增加一個臨時複本。
  • minReadySeconds: 20：剛變成 Ready 不等於已經穩定。
  • progressDeadlineSeconds：發布卡住後讓控制器明確回報失敗。
  • revisionHistoryLimit：保留有限回滾版本，避免 ReplicaSet 無限成長。

這套策略要求節點池能暫時容納一個 surge Pod。排程器依 request 預留，不依 kubectl top 的瞬時用量計算。

探針、preStop、優雅停機與 PDB 已在 Kubernetes 無感滾動發布 中提供完整範本。本篇不再重複，只定義統一範本的選擇規則：

  • Spring Boot 3 Servlet 服務使用 Actuator liveness/readiness。
  • 尚未暴露 Availability 的 Netty、閘道與 WebSocket 服務暫時使用 TCP 探針。
  • 相容例外必須在範本條件中可見，並有遷移期限。
  • liveness 不得存取資料庫、Redis、RabbitMQ 或遠端 HTTP。

第 2 層：安全收緊後必須明確提供可寫目錄

安全基線：

spec:
  automountServiceAccountToken: false
  enableServiceLinks: false
  securityContext:
    seccompProfile:
      type: RuntimeDefault

containers:
  - name: application
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop: [ALL]

第三方 SDK 仍可能根據 HOME 或 user.home 寫入 Nacos failover、上傳斷點與暫存檔。範本為它們提供有上限的可寫 emptyDir：

volumeMounts:
  - name: tmp-volume
    mountPath: /tmp

env:
  - name: HOME
    value: /tmp
  - name: JDK_JAVA_OPTIONS
    value: >-
      -Duser.home=/tmp
      -DJM.SNAPSHOT.PATH=/tmp
      -DJM.LOG.PATH=/data/java/logs/nacos

volumes:
  - name: tmp-volume
    emptyDir:
      sizeLimit: 2Gi

emptyDir.sizeLimit 防止暫存檔無限佔用節點的 ephemeral storage。真正需要跨 Pod 保存的資料仍應使用 PVC 或物件儲存，不能因為路徑可寫就把 emptyDir 當持久磁碟。

目錄事故、異常鏈與 Nacos 路徑請見 Spring Boot 3 容器啟動異常復盤，這裡不再重複堆疊分析。

第 3 層：執行期參數引用既有基線

範本只負責執行經過驗證的執行期基線；參數依據放在對應專題：

範本內容規則詳細說明
JDK 17 Heap、G1、Metaspace、Dump一般服務使用百分比堆；不全域啟用週期 GCJDK 17 記憶體最佳化
JProfiler檔案可預置，native agent 預設關閉JDK 17 記憶體最佳化
MALLOC_ARENA_MAX=4僅用於已驗證的 glibc 映像JDK 17 記憶體最佳化
RabbitMQ 1/3/10全域統一消費者並發與 prefetchNacos 全域設定基線
Redis、Hikari、Tomcat在 Nacos 分層治理，不在 YAML 複製Nacos 全域設定基線

如此一來，每個參數只在一篇文章中維護單一說明。Deployment 範本引用結論，不複製完整調校過程。

第 4 層：同一範本，資源仍然要分檔

統一範本不等於所有服務使用相同容量。可以保留少量可稽核的資源類別：

類型CPU requestMemory requestMemory limit適用範圍
standard250m1536Mi4Gi一般 API
medium500m2Gi4Gi採購、倉儲等
heavy500m4Gi5Gi財務或批次處理

每個例外都要附上證據，例如穩態 P95、峰值、GC、執行緒數與滾動發布所需的臨時容量。不要讓 if app.name == ... 無限成長；當例外變多時，應改為明確的 resourceClass 參數。

第 5 層：多複本必須跨節點，但不要鎖死滾動發布

在 Kubernetes 1.30 中，可以依目前 ReplicaSet revision 強制分散：

topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: DoNotSchedule
    matchLabelKeys:
      - pod-template-hash
    labelSelector:
      matchLabels:
        app: <application>
        version: <version>

Kubernetes topology spread 文件 明確給出使用 pod-template-hash 區分 Deployment revision 的方式。

沒有 matchLabelKeys 時，新舊 ReplicaSet 可能一起參與 skew 計算。在 maxUnavailable: 0 的發布中，舊 Pod 尚未退出，新 Pod 又被嚴格 spread 阻擋，發布可能形成死鎖。

DoNotSchedule 會保證兩個同 revision 複本不落在同一主機，但前提是目標節點池至少有兩個合格節點，而且 request 有容量。如果業務更看重「盡快啟動」而非強制故障域，應明確選擇 ScheduleAnyway，不能模糊地說「盡量分散」。

範本發布順序

一份範本影響幾十個服務，發布順序必須比一般應用更保守：

  1. 渲染範本，儲存目標 Deployment 的完整 YAML。
  2. 執行 schema 檢查與 server-side dry-run。
  3. 選擇一個一般雙複本服務試點。
  4. 等新 ReplicaSet 全部 Ready，並維持 Ready 超過 minReadySeconds。
  5. 驗證 Nacos、Redis、RabbitMQ、資料庫與實際介面。
  6. 檢查複本節點分布、GC 日誌、RSS 與連線數。
  7. 再處理一個重型服務與一個需相容舊版 Boot 的服務。
  8. 分批推廣，不同時重啟幾十個用戶端。

驗證指令：

kubectl apply --server-side --dry-run=server -f rendered.yaml
kubectl -n <namespace> rollout status deployment/<name> --timeout=10m
kubectl -n <namespace> get pod -l app=<name> -o wide
kubectl -n <namespace> get rs -l app=<name>
kubectl -n <namespace> describe pod <new-pod>

滾動重啟只會依叢集中目前的 Deployment spec 重建 Pod。Git 儲存庫裡的範本已經修改，並不代表線上 spec 已經更新；必須先執行渲染與發布流程。

完成定義

  • 所有 Java 服務由同一範本渲染，但仍是獨立 Deployment。
  • 通用範本不包含未經普遍驗證的週期 GC 與診斷 agent。
  • startup、readiness、liveness 的職責不同。
  • Nacos、上傳與暫存檔寫入受控可寫磁碟區。
  • RabbitMQ 並發與 prefetch 有全域保守上限與業務例外。
  • requests 依據實際 P95/峰值，並為 surge Pod 預留容量。
  • 雙複本依 revision 強制跨節點。
  • 安全上下文、SIGTERM、Heap Dump 與日誌路徑均已驗證。
  • 每個應用例外都有原因、負責人與移除條件。

最終結論

統一 Deployment 的價值不是減少幾份 YAML，而是把幾十個服務共享的執行契約收斂到一個地方：

如何启动
+ 如何被探测
+ 如何退出
+ 可以写哪里
+ 最多使用多少资源
+ 消息同时在途多少
+ 副本如何跨故障域

結構統一之後，差異才會變得可見。資源佔用高的服務可以繼續使用較高檔位，舊閘道可以暫時使用 TCP 探針，但這些都必須是明確資料，而不是散落在五份 Deployment 中逐漸漂移的複製貼上。
