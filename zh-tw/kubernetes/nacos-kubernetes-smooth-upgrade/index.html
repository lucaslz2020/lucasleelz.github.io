Nacos 如何平滑升級：Kubernetes 三節點滾動升級與回滾教學

從版本相容性、資料庫 schema、設定備份和客戶端盤點開始，逐節點升級 Kubernetes 中的三節點 Nacos，並驗證註冊、設定與回滾路徑。

Nacos 平滑升級不是把 StatefulSet 映像標籤改成新版本，然後等三個 Pod 自動重啟。真正需要保護的是三件事：資料庫 schema、服務註冊的連續性、設定讀取的連續性。

系列導覽：Kubernetes 重建遷移教學系列。升級前應先完成 Nacos 叢集基線與客戶端版本盤點。

本文假設目前是三節點 StatefulSet、使用外部 MySQL、應用程式透過一般 Service 連線，節點之間透過 Headless Service 通訊。

升級前先回答四個問題

在工單或變更紀錄中寫清楚：

  1. 目前的 Server 版本和目標 Server 版本是什麼？
  2. 所有應用程式的 Nacos Client 主版本是什麼？
  3. 目標版本是否修改資料表結構、連接埠、環境變數和探針路徑？
  4. 回滾舊映像時，新的 schema 是否仍與舊版本相容？

官方升級手冊目前的說明是：從 2.0.x 及以上升級到 3.2.x，需要比對目標版本的資料庫 schema；3.2.x Server 相容 2.x 和 3.x Client，而 1.x Client 已不再相容。這個結論會隨版本改變，執行前必須重新查閱官方升級手冊。

第 1 步：導出版本與客戶端清單

保存目前的映像與 Pod：

kubectl -n nacos-system get statefulset nacos \
  -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}' \
  | tee reports/nacos-current-image.txt

kubectl -n nacos-system get pods -o wide \
  | tee reports/nacos-pods-before.txt

客戶端版本不能靠猜。可以從 Maven 依賴樹、Gradle dependencies、建置產物清單或映像 SBOM 中彙整：

mvn dependency:tree -Dincludes=com.alibaba.nacos:nacos-client

把結果整理成 CSV：

namespace,workload,client_version,owner,verified
app-test,order-api,<client-version>,team-a,false

只要還有官方不支援的 Client 主版本，升級就應暫停。

第 2 步：備份設定、資料庫與 Kubernetes 資源

備份 StatefulSet、Service、ConfigMap 和 Secret 的資源定義：

kubectl -n nacos-system get statefulset,service,configmap -o yaml \
  > backup/nacos-kubernetes.yaml

umask 077
kubectl -n nacos-system get secret nacos-secret -o yaml \
  > backup/nacos-secret.yaml

資料庫使用一致性備份工具執行。以 MySQL 邏輯備份為例：

mysqldump --single-transaction --routines --triggers \
  -h <mysql-host> -u <backup-user> -p \
  <nacos-database> > backup/nacos-before-upgrade.sql

sha256sum backup/nacos-before-upgrade.sql > backup/nacos-before-upgrade.sha256

設定資料也應透過 Nacos 匯出功能產生獨立的歸檔。資料庫備份和設定匯出至少要在隔離環境還原一次。

第 3 步：比較資料庫 schema

從目前版本和目標版本的發行套件中分別取出 mysql-schema.sql：

diff -u current/mysql-schema.sql target/mysql-schema.sql \
  | tee reports/nacos-schema.diff

不要直接執行目標版本的完整建表腳本。先取出增量 DDL，在資料庫副本演練：

恢复生产备份到临时库
→ 执行增量 DDL
→ 启动一个目标版本 Nacos
→ 验证配置读取和服务注册
→ 记录耗时与锁表影响

如果變更不可逆，回滾方案不能只寫「改回舊映像」，還必須包含資料庫還原或向後相容的證明。

第 4 步：比較設定、連接埠與探針

匯出目前的 StatefulSet：

kubectl -n nacos-system get statefulset nacos -o yaml \
  > reports/nacos-statefulset-before.yaml

逐項對照目標映像的文件：

  • 環境變數是否改名。
  • 8848、9848、9849、7848、8080 等連接埠的用途是否改變。
  • HTTP API 與控制台路徑是否改變。
  • 健康檢查路徑是否仍然有效。
  • JDK 和資源需求是否改變。

Nacos 3.0 起控制台與主連接埠分離，代理層不能沿用舊版本的假設。gRPC 連接埠經過代理時要使用 TCP 轉發，不能當作一般 HTTP 處理。參考部署手冊概覽。

第 5 步：在影子環境完成升級演練

從正式環境備份還原一個隔離資料庫，建立單獨的命名空間：

kubectl create namespace nacos-upgrade-lab

把 Service 名稱、資料庫位址和 Secret 全部改為實驗值，啟動與正式環境相同的舊版本。先證明舊版本能讀取備份資料，再升級到目標版本。

至少驗證：

  • 登入與權限。
  • 命名空間、Data ID、Group 數量。
  • 設定發布、回讀和歷史版本。
  • 臨時應用程式註冊、發現和註銷。
  • 重啟任一個 Nacos Pod 後叢集恢復。

影子環境失敗時，不要到正式環境「再試一次」。

第 6 步：設定逐節點滾動策略

StatefulSet 預設從最大序號向前滾動。為了先升級一個節點觀察，可以暫時設定 partition：

kubectl -n nacos-system patch statefulset nacos --type merge -p '
{
  "spec": {
    "updateStrategy": {
      "type": "RollingUpdate",
      "rollingUpdate": {"partition": 2}
    }
  }
}'

然後只更新 Pod 範本中的映像：

kubectl -n nacos-system set image statefulset/nacos \
  nacos=<image-registry>/nacos-server:<target-version>@sha256:<target-digest>

此時只應更新 nacos-2：

kubectl -n nacos-system get pods -w

第 7 步：觀察第一個新版本節點

不要看到 Ready 就立刻繼續。至少觀察一個完整的業務高峰時段，檢查：

kubectl -n nacos-system logs nacos-2 --since=30m \
  | grep -Ei 'error|exception|raft|grpc|database'

kubectl -n nacos-system get endpointslice \
  -l kubernetes.io/service-name=nacos-client -o wide

同時執行連續探測：

while true; do
  date
  curl -fsS 'http://<internal-nacos-address>/nacos/v1/console/health/readiness'
  sleep 5
done

應用端檢查設定監聽、註冊續約、呼叫錯誤率和登入流程。若出現實例清單突然為空、gRPC 連線失敗或設定監聽中斷，立即停止。

第 8 步：逐步放開剩餘節點

第一個節點穩定後，把 partition 改為 1：

kubectl -n nacos-system patch statefulset nacos --type merge -p '
{"spec":{"updateStrategy":{"rollingUpdate":{"partition":1}}}}'

等待 nacos-1 Ready，重複完整驗證。最後把 partition 改為 0：

kubectl -n nacos-system patch statefulset nacos --type merge -p '
{"spec":{"updateStrategy":{"rollingUpdate":{"partition":0}}}}'

kubectl -n nacos-system rollout status statefulset/nacos --timeout=20m

三台節點之間至少留出明確的觀察時間，不要用一個命令同時刪除三個 Pod。

第 9 步：做一次真實故障演練

選擇一個非 Leader 或已確認可安全重建的 Pod：

kubectl -n nacos-system delete pod nacos-2
kubectl -n nacos-system wait --for=condition=Ready pod/nacos-2 --timeout=10m

刪除期間持續發起設定讀取和服務呼叫。目標不是零日誌，而是客戶端能夠重新連線，業務請求不出現持續失敗。

回滾方法

如果新舊版本允許混部、資料庫變更向後相容，可維持 partition 不動，先在故障節點恢復舊映像：

kubectl -n nacos-system set image statefulset/nacos \
  nacos=<image-registry>/nacos-server:<old-version>@sha256:<old-digest>

如果資料庫 schema 不向後相容：

  1. 停止所有 Nacos 寫入和設定發布。
  2. 將 Nacos StatefulSet 縮容為零。
  3. 還原升級前的資料庫。
  4. 還原舊版 Kubernetes 清單和 Secret。
  5. 啟動舊版本，驗證設定與實例。

這個流程會造成中斷，因此不可逆的 DDL 必須在維護時段執行。

完成定義

  • 三個 Pod 都執行目標映像 digest。
  • 資料庫 schema 與目標版本一致，並保存執行紀錄。
  • 設定、服務實例、使用者和權限數量與升級前基線一致。
  • 所有關鍵客戶端版本都在相容矩陣內。
  • 刪除一個 Pod 時，設定讀取和服務呼叫仍可繼續。
  • 觀察期間沒有持續的註冊失敗、gRPC 斷線或資料庫異常。
  • 備份、舊映像和回滾清單在觀察期結束前不得刪除。
