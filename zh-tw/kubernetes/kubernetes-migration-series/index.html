Kubernetes 重建遷移教學系列：從零搭建到業務切換

一套按照實際執行順序整理的 Kubernetes 教學，涵蓋叢集、網路、排程、滾動發布、Deployment 與 Nacos 基線、中介軟體、JVM 最佳化和故障復盤。

#Kubernetes #kubeadm #Rocky Linux #Nacos #Nexus #遷移

這組文章來自一次完整的叢集重建，但不是按照故障發生時間寫的流水帳，而是重新整理成可以從頭執行的教學。

所有內部位址、網域、節點、命名空間、帳號和容量都已脫敏。命令中的 <...> 是必須替換的變數，不能直接複製到正式環境。

建議閱讀順序

第一階段：先取得一個健康的空叢集

  1. 從零搭建 Kubernetes：準備 Rocky Linux 和 containerd，使用 kubeadm 建立三節點控制平面，設定 kube-vip 與 Calico。
  2. 理解三類網路位址：分清 Node、Pod、Service CIDR 與 DNS，避免位址重疊和固定 IP 依賴。
  3. 安裝基礎元件：部署 metrics-server、動態儲存和 NGINX Ingress，並用測試工作負載驗收。
  4. 規劃節點池：用標籤、污點、容忍和親和性劃分入口、業務、資料、監控和預留節點。
  5. 設計無感滾動發布：正確設定三類探針、優雅停機、Deployment 策略與 PDB。

第二階段：建立平台依賴

  1. 搭建 Nacos 三節點叢集：理解 Headless Service 與一般 Service，設定資料庫、鑑權、探針和反親和。
  2. 把固定 Service IP 改成 DNS：盤點 Nacos 設定，逐條替換、回讀、重啟和驗證。
  3. 把 Nacos 服務發現遷移到 Service DNS：保留設定中心，逐條遷移 Feign、Gateway 和內部 HTTP 呼叫鏈。
  4. 平滑升級 Nacos：備份設定與資料庫，驗證版本相容性，逐節點滾動升級並規劃回滾。
  5. 排查 Service 與註冊失敗：依 DNS、Service、Endpoint、Pod、CNI 和 kube-proxy 逐層定位。

第三階段：遷移業務和製品庫

  1. 遷移有狀態服務：分別處理 MySQL、Redis、Kafka、RabbitMQ 和 Zookeeper 的備份、還原與切換。
  2. 業務遷移 Runbook：資源零複本落地、資料還原、分批啟動、真實業務驗收、入口切換和回滾。
  3. 在 Kubernetes 部署 Nexus 3：先把新的製品庫穩定跑起來。
  4. 從 Nexus 2 平滑遷移到 Nexus 3：Upgrade Wizard、H2 升級、PostgreSQL 遷移和 VIP 切換。
  5. 治理 Nexus CE 用量：區分元件、請求與 Blob 空間，安全清理代理快取和過期製品。

第四階段：執行期最佳化與事故復盤

  1. 分析多服務 Pod 重啟風暴：從終止狀態和 previous logs 定位慢依賴、連線池與探針放大效應。
  2. 統一多服務 Spring Boot 3 Deployment 範本：合併重複範本，用參數表達資源和相容例外，並統一安全、執行期與跨節點契約。
  3. 建立 Spring Boot 3 Nacos 全域設定基線：治理 Redis、Redisson、RabbitMQ、Hikari、Tomcat、Actuator 和設定覆寫關係。
  4. 復盤 Boot 2/3 Redis 設定回退 localhost：解釋 Nacos 屬性前綴、延遲建連、應用層級相容別名與 commons-pool2 依賴陷阱。
  5. 最佳化 JDK 17 與 G1 容器記憶體：從 3–4GiB 與同版本 Pod 記憶體差異出發，治理堆、執行緒、訊息預取、glibc arena 與診斷工具。
  6. 縮減 ZooKeeper 在 Kubernetes 中的記憶體：用真實 JVM 參數、mntr 與快照建立容量模型，分階段降低 Heap 和資源請求，並處理 emptyDir 風險。
  7. 最佳化 JDK 25 與 ZGC 容器記憶體：分解 Heap、Native Memory 和 cgroup 工作集，驗證 Soft Max 與記憶體歸還。
  8. 復盤 Spring Boot 3 容器啟動相容問題：依檔案系統、棄用屬性、classpath 和業務程式碼分層解決目錄、日誌與空驅動異常。
  9. 復盤 Spring Boot 3.1.7 → 3.5.13 升級：定位編譯通過後才暴露的 Batch Job 重名、執行緒池注入和 MongoDB 健康檢查問題。
  10. 規劃 Spring Boot 3.5.13 → 4.1 遷移：只梳理 Boot 4 新增的 Cloud Alibaba、Config Data、Web 容器、Jackson 與資料存取邊界。

為什麼不寫成一篇

叢集安裝、應用程式遷移和 Nacos 治理的失敗邊界完全不同。把它們放在一篇文章裡，容易出現三個問題：

  • 讀者不知道目前命令應該在哪台機器、哪個叢集執行。
  • 故障處理被埋在長文中，無法作為獨立手冊重複使用。
  • 某個元件升級後，整篇文章都需要重新驗證。

拆分後，每篇文章都遵循相同結構：

目标 → 前置条件 → 文件准备 → 逐步执行 → 预期结果 → 故障判断 → 回滚 → 完成定义

實驗環境約定

範例統一使用以下佔位符：

佔位符含義
<api-vip>Kubernetes API 虛擬位址
<pod-cidr>Pod 位址段
<service-cidr>Service 位址段
<node-ip>節點管理位址
<image-registry>已審核的映像倉庫
<storage-server>儲存伺服器位址或 DNS
<nacos-domain>Nacos 存取網域

如果需要在實驗環境使用範例 IP，應使用 RFC 5737 文件用位址段；文章不會出現真實內網位址。

每個階段的停止條件

遇到以下任何一種情況，不要繼續下一篇：

  • etcd 或資料備份沒有完成還原驗證。
  • 節點不是全部 Ready，或跨節點 Pod 網路不通。
  • ClusterIP、DNS、PVC、Ingress 任一項冒煙測試失敗。
  • Nacos 三節點狀態不一致，或服務實例清單為空。
  • 新舊入口沒有可執行的回滾方案。

教學的目標不是「命令執行完了」，而是每一步都留下可驗證的證據，並且能安全回到上一個穩定狀態。
