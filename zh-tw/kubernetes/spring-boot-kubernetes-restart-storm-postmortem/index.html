ENGINEERING NOTE · 2026年7月19日

多個 Spring Boot Pod 同時重啟，真的是 Kubernetes 或 Nacos 故障嗎

復盤一次多服務 Pod 重啟：從 Last State、Exit Code、Events 和 previous logs 排除節點故障，最終定位阻塞依賴、連線池等待與 liveness 放大效應。

#Kubernetes #Spring Boot #故障復盤 #Feign #Probe
{ }

本文來自一次真實事故，但服務名稱、Pod、節點、時間、介面、容量與組織資訊均已泛化。系列導覽：Kubernetes 重建遷移教學系列。

現象很像平台故障：多項 Spring Boot 服務在相近時間重啟，日誌裡同時出現 Nacos gRPC 重連、JDBC 取得連線失敗、Feign 逾時與探針失敗。

如果只截取其中一行，很容易得出三個不同結論：

  • Kubernetes 節點故障。
  • Nacos 升級導致全站異常。
  • JDK 或記憶體問題。

最終證據顯示，節點與中介軟體沒有同步重啟；多個業務執行緒被慢依賴和資料庫連線等待佔住，liveness 又把「暫時無法及時回應」判成「行程永久失活」，從而放大成重啟風暴。

事故判斷鏈路

flowchart LR
  A["多個 Pod 重啟"] --> B["Last State / Exit Code"]
  B --> C["Events 與探針"]
  C --> D["previous logs"]
  D --> E["節點分布"]
  E --> F["共同依賴"]
  F --> G["執行緒與連線池阻塞"]
  G --> H["程式碼逾時與降級修復"]

第 1 步：不要先看目前日誌

Pod 已經重啟後，kubectl logs 預設看到的是新容器。先收集：

kubectl -n <namespace> get pod <pod> -o jsonpath='
restartCount={.status.containerStatuses[0].restartCount}{"\n"}
reason={.status.containerStatuses[0].lastState.terminated.reason}{"\n"}
exitCode={.status.containerStatuses[0].lastState.terminated.exitCode}{"\n"}
startedAt={.status.containerStatuses[0].lastState.terminated.startedAt}{"\n"}
finishedAt={.status.containerStatuses[0].lastState.terminated.finishedAt}{"\n"}'

kubectl -n <namespace> logs <pod> --previous --timestamps \
  > reports/<pod>-previous.log

--previous 是事故證據，不應等 Pod 再重啟一次才想起來保存。

第 2 步：理解 Exit 137 與 143

Exit Code常見訊號不能直接證明什麼
137SIGKILL，可能是 OOM 或 grace period 後強制終止不能僅憑 137 就斷言 JVM 堆積溢位
143SIGTERM，常見於探針重啟、滾動或人工刪除不能僅憑 143 就斷言正常發布

繼續看 reason：

kubectl -n <namespace> describe pod <pod>
kubectl -n <namespace> get events --sort-by=.lastTimestamp

如果是 OOMKilled，再檢查容器 limit、JVM Native Memory 與節點壓力。如果事件持續出現 Liveness probe failed，就要解釋探針為什麼逾時。

第 3 步：比較 Pod 是否集中在同一節點

kubectl get pods -A -o custom-columns='NS:.metadata.namespace,POD:.metadata.name,NODE:.spec.nodeName,RESTARTS:.status.containerStatuses[0].restartCount' \
  | sort

如果故障 Pod 分散在多台 Ready 節點，而同節點其他工作負載正常，單一節點 kubelet、containerd、磁碟或網路故障的可能性下降。

同時檢查節點：

kubectl get nodes
kubectl describe node <node> | sed -n '/Conditions:/,/Addresses:/p'
kubectl get events -A --field-selector involvedObject.kind=Node --sort-by=.lastTimestamp

第 4 步：建立時間線，而不是搜尋一個關鍵字

將所有 previous logs 的關鍵事件依時間排序：

rg -n -i 'liveness|readiness|timeout|refused|connection|pool|nacos|shutdown|killed' reports/

這次事件呈現的順序是：

遠端介面回應持續變慢
→ Feign 呼叫佔住業務執行緒
→ 資料庫連線池等待增加
→ 健康端點無法在 timeout 內回傳
→ liveness 連續失敗
→ kubelet 發送 SIGTERM
→ 部分行程未在 grace period 內退出
→ 容器被重啟

日誌中同時存在 Nacos 重連，但時間線顯示 Nacos StatefulSet 的滾動發生在更早的維護窗口，不能把相鄰日誌自動當成同一個根因。

第 5 步：區分「共同出現」與「共同根因」

建立對照表：

元件是否重啟是否健康與故障同一時間
Kubernetes Node否Ready否
Nacos無同步重啟三節點可用否
Redis否PING 正常否
訊息中介軟體否成員正常否
多個業務 Pod是liveness 逾時是

這張表排除了「所有底層元件同時崩潰」的敘述，把範圍收斂到業務共用依賴與探針設計。

第 6 步：找到沒有邊界的遠端呼叫

問題呼叫是一個非核心附件查詢。它位於主業務查詢內部，但沒有獨立的短逾時；下游變慢後，請求長時間佔住執行緒。

為單一 Feign Client 設定邊界：

spring:
  cloud:
    openfeign:
      client:
        config:
          attachment-api:
            connectTimeout: 3000
            readTimeout: 5000
            loggerLevel: basic

Spring Cloud OpenFeign 支援依 client 設定 URL、連線與讀取參數，具體屬性應依專案的 Release Train 對照官方文件。

只對冪等請求做有限重試。下游已經變慢時，無限制重試會把一次壅塞放大成更多並發。

第 7 步：讓可選依賴真正可降級

附件不是付款、訂單或報表主資料。目標行為應是：

附件查詢成功 → 回傳附件
附件逾時 → 記錄帶業務鍵的警示，回傳空附件
主業務資料 → 正常回傳

偽程式碼：

try {
    return attachmentClient.findByBusinessKey(businessKey);
} catch (RetryableException ex) {
    log.warn("attachment lookup degraded, businessKey={}", businessKey, ex);
    return List.of();
}

降級不能吞掉核心資料寫入失敗，也不能把所有例外都當成「沒有附件」。應只捕捉明確的遠端連線/逾時例外，並為降級計數警示。

第 8 步：檢查連線池與執行緒池

遠端呼叫阻塞可能導致：

  • Web 請求執行緒耗盡。
  • Spring Batch 分割區執行緒等待。
  • Druid/Hikari 取得連線逾時。
  • 健康端點與業務共用資源時一起逾時。

需要同時監控：

HTTP active threads
Feign latency/error
JDBC active/pending connections
Kafka/Rabbit listener lag
GC pause
readiness/liveness latency

看到 CannotCreateTransactionException 不代表資料庫一定當機。若底層是 InterruptedException，可能是 Pod 正在終止時執行緒被中斷。

第 9 步：調寬探針只能暫時止血

暫時將 liveness 調整為更寬容的時間窗口，可以避免依賴短暫抖動立即殺掉行程：

livenessProbe:
  periodSeconds: 10
  timeoutSeconds: 5
  failureThreshold: 12

但這只是把重啟窗口延後到約 120 秒。若執行緒永久阻塞，行程仍會重啟；若沒有程式碼逾時，流量仍會持續排隊。

正確順序是：

暫時降低重啟爆炸半徑
→ 為依賴設定逾時與隔離
→ 實作業務降級
→ 驗證執行緒與連線池恢復
→ 再依資料校準探針

第 10 步：驗證修復

在測試環境人為讓附件服務延遲超過 read timeout：

主業務介面在規定時間內回傳
附件欄位進入明確降級結果
Feign 逾時指標增加
Web 執行緒不持續累積
資料庫連線池等待恢復
liveness 始終成功
Pod restartCount 不增加

部署後觀察：

kubectl -n <namespace> get pods -w
kubectl -n <namespace> logs deployment/<app> --since=30m \
  | grep -Ei 'attachment lookup degraded|liveness|timeout|shutdown'
kubectl top pod -n <namespace>

如何辨識 Nacos 滾動升級日誌

Nacos Client 出現：

RST_STREAM closed stream
HTTP/2 error code: CANCEL
reconnect

先比較：

kubectl -n <nacos-namespace> get pod -o wide
kubectl -n <nacos-namespace> get controllerrevision
kubectl -n <nacos-namespace> rollout history statefulset/nacos

若日誌與 Nacos Pod 逐個替換嚴格對應，隨後用戶端自動重連且實例恢復，這更像是升級過程中的連線切換。只有時間、實例狀態與業務失敗一致，才能判斷為事故根因。

最終根因與改進

根因

  • 可選遠端依賴沒有獨立的短逾時。
  • 慢呼叫佔用業務執行緒並誘發連線池等待。
  • liveness 健康檢查對暫時資源壅塞過於敏感。

放大因素

  • 多項服務使用相同探針範本。
  • 日誌中同時存在 Nacos 重連，干擾了初始判斷。
  • previous logs 沒有第一時間集中保存。

改進

  • 每個外部依賴明確逾時、重試、隔離與降級。
  • liveness 只檢查行程是否能自癒，readiness 表達承接流量的能力。
  • 統一採集 Last State、Events 與 previous logs。
  • 發布與中介軟體升級建立時間線與 Revision 記錄。

結論

多個 Pod 同時重啟是現象，不是根因。最可靠的排查方式是：

終止狀態 → 事件 → 前一容器日誌 → 節點分布 → 共用依賴 → 執行緒/連線池 → 探針放大效應

平台層通常負責最後一次「殺掉行程」，但真正讓行程無法及時回應的原因，可能藏在一條沒有逾時邊界的普通業務呼叫裡。
