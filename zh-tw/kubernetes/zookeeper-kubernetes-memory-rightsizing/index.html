ZooKeeper 每個 Pod 接近 2G：從固定 Heap 到 Kubernetes 資源縮減

透過 JVM 參數、mntr、快照與 Kubernetes requests 拆解 ZooKeeper Pod 記憶體偏高的原因，並提供分階段縮減、監控、滾動驗證與持久化遷移方案。

本文來自一個三節點 ZooKeeper 叢集的資源治理案例。命名空間、節點、業務名稱與容量都已泛化；參數只能作為同量級負載的起點，不能直接複製到正式環境。系列導覽：Kubernetes 重建遷移教學系列。

一個三節點 ZooKeeper 叢集長期以來呈現以下資源狀態：

指標節點 A節點 B節點 C
Pod 記憶體約 1.8 GiB約 1.8 GiB約 1.4 GiB
CPU約 10m約 9m約 11m
memory request2 GiB2 GiB2 GiB
memory limit3 GiB3 GiB3 GiB
重啟次數000

乍看很像記憶體洩漏：CPU 很低，三個 Pod 卻佔用接近 5 GiB。但繼續檢查後發現，業務資料只有約 1.2 MiB，連線數與 watch 數也很低。

真正的問題不是 ZooKeeper 存了幾 GiB 資料，而是 JVM 被設定為固定 2 GiB Heap，Chart 又透過資源預設為每個 Pod 申請 2 GiB 記憶體。

先建立判斷鏈路

重點在於先釐清「Heap 上限大」「Heap 已提交」與「業務存活物件多」這三者；單憑 kubectl top 無法分辨。

第 1 步：讀取執行中的真實 JVM 參數

不要只看 Helm values。先檢查容器內的 Java 程式：

kubectl -n infra exec zookeeper-0 -- \
  sh -c 'tr "\0" " " < /proc/1/cmdline'

這次看到的關鍵片段是：

-Xmx1000m -Xmx2048m -Xms2048m

重複的 -Xmx 不會相加，HotSpot 通常採用最後出現的值。因此有效設定是：

Xms = 2048 MiB
Xmx = 2048 MiB

前一個 -Xmx1000m 來自映像腳本的預設值，後一個 -Xmx2048m 與 -Xms2048m 來自 Chart 的 heapSize。這代表：

  • 預設值沒有真正限制住 Heap。
  • Heap 從啟動時便以固定的 2 GiB 大小提交。
  • 三節點的理論固定 Heap 預算已達 6 GiB。

重複參數本身不是 3 GiB Heap，也不是洩漏的證據，但會讓只檢查環境變數的人得出錯誤結論。

第 2 步：區分 RSS、Committed Heap 與 Live Data

ZooKeeper Pod 的記憶體可以大致拆解為：

Pod working set
≈ JVM committed heap
+ Metaspace / Code Cache / GC structures
+ thread stacks / direct buffers / native libraries
+ process working-set file pages

Xms=2g 不代表程式在啟動瞬間就佔滿 2 GiB RSS；JVM 會在執行與 GC 過程中逐步觸及已提交的頁面。即使存活物件很少，作業系統看到的工作集也可能長期接近固定 Heap 大小。

因此，下面兩個判斷都不成立：

Pod RSS 接近 2 GiB，所以 ZooKeeper 一定存了 2 GiB 数据
数据只有 1 MiB，所以 Pod RSS 应该只有几十 MiB

業務資料規模是決定 Heap 需求的重要輸入，但不能直接等同於 Pod 的總記憶體。

第 3 步：用 mntr 判斷真實負載

ZooKeeper 的四字命令必須在伺服器端白名單中放行。啟用前應評估安全邊界，避免把管理介面暴露到不可信網路。ZooKeeper 管理指南已經建議新系統優先使用 AdminServer；這裡保留 mntr，是為了配合現有叢集的收集方式。

在允許 mntr 的環境中，可以執行：

kubectl -n infra exec zookeeper-0 -- \
  sh -c 'printf "mntr\n" | nc 127.0.0.1 2181'

重點收集：

zk_server_state
zk_znode_count
zk_approximate_data_size
zk_num_alive_connections
zk_outstanding_requests
zk_avg_latency
zk_max_latency
zk_watch_count
zk_ephemerals_count
zk_open_file_descriptor_count
zk_max_file_descriptor_count

本次脫敏後的資料量級是：

指標觀測值解釋
znode 數約 22,000規模較小
approximate data size約 1.2 MiB業務資料遠小於固定 Heap
全域 Session約 40用戶端壓力低
單節點存活連線10–20連線壓力低
watch 數10–20沒有 watch 風暴
outstanding requests0沒有請求排隊
平均延遲低於 1 ms目前效能餘量充足
單一快照約 3 MiB與資料量級一致

這些證據比較支持「Heap 設定過大」，而非「業務物件正在無限增長」。

第 4 步：檢查事務日誌與快照

繼續檢查 ZooKeeper 資料目錄：

kubectl -n infra exec zookeeper-0 -- \
  sh -c 'du -sh /bitnami/zookeeper/data /bitnami/zookeeper/logs 2>/dev/null'

事務日誌可能使用預先分配的檔案。即使日誌檔有幾十 MiB，也不代表其中每個位元組都是有效業務資料，更不能直接當作 Heap 大小的依據。

同時確認：

  • snapCount。
  • autopurge.snapRetainCount。
  • autopurge.purgeInterval。
  • 資料目錄是否位於 PVC。
  • 三個節點的快照與事務日誌是否持續增長。

本次自動清理已啟用，快照也很小，因此沒有證據支持立刻調整 snapCount 或清理頻率。效能最佳化只應調整有證據支持的參數。

第 5 步：把 Chart 資源預設改成明確預算

目前設定類似：

heapSize: 2048

resourcesPreset: large
resources: {}

resourcesPreset 適合快速部署，但不適合長期容量治理。它隱藏了實際的 request 與 limit，也很難表達「CPU 很低、記憶體仍須保留 JVM 餘量」這種真實模型。Bitnami ZooKeeper Chart同樣建議正式環境的工作負載依實際情境調整 resources。

不要在沒有監控的情況下直接從 2 GiB Heap 砍到 512 MiB。更穩妥的是兩階段縮減。

第一階段：先降到 1536 MiB

heapSize: 1536

resourcesPreset: none
resources:
  requests:
    cpu: 250m
    memory: 1792Mi
    ephemeral-storage: 256Mi
  limits:
    cpu: 1500m
    memory: 2560Mi
    ephemeral-storage: 1Gi

這一階段保留約 1 GiB 的容器層級餘量，用來容納 JVM 非 Heap、執行緒、直接記憶體、共享函式庫與工作集波動。

第二階段：穩定後再評估 1024 MiB

如果至少跨過一個完整業務尖峰，且 GC、延遲、連線與選舉都穩定，可以繼續評估：

heapSize: 1024

resourcesPreset: none
resources:
  requests:
    cpu: 250m
    memory: 1280Mi
    ephemeral-storage: 256Mi
  limits:
    cpu: 1500m
    memory: 2Gi
    ephemeral-storage: 1Gi

三個複本在第一階段的 memory request 合計為 5.25 GiB；進入第二階段後，合計為 3.75 GiB。CPU request 則從原本的 3 核降到 750m。實際節省應以排程器看到的 request 為準，而非瞬間的 kubectl top 讀數。

為什麼 Heap 不能頂到容器 limit

即使 ZooKeeper 的主要資料在 Java Heap 中，也必須給這些區域留空間：

  • Metaspace 與 Compressed Class Space。
  • JIT Code Cache。
  • GC remembered set 與其他原生結構。
  • NIO Direct Buffer。
  • 執行緒堆疊。
  • JNI 與壓縮函式庫。
  • 檔案頁面與程式執行期。

如果設定：

Xmx = container memory limit

JVM Heap 還沒 OOM，容器就可能先被 cgroup 殺掉。為 1 GiB 的 Heap 配置 2 GiB 的 limit 不是浪費，而是先建立可驗證的安全邊界；觀察穩定後，再決定是否繼續壓縮。

第 6 步：縮減前先補上可觀測性

如果原本的設定關閉了 metrics，資源縮減後只能靠 kubectl top 猜測，風險很高。建議先開啟 ZooKeeper metrics exporter，並至少監控：

  • Pod working set 與 RSS。
  • JVM heap used、committed、max。
  • GC pause、次數與分配速率。
  • zk_outstanding_requests。
  • avg/max latency。
  • 存活連線、watch、znode、ephemeral 數。
  • leader 變化與選舉時間。
  • 容器重啟、OOMKilled 與探針失敗。

警示不應只使用「記憶體超過 80%」這個條件。組合式判斷更有意義：

heap 持续高位
+ GC 频率升高
+ 请求延迟或 outstanding requests 增长

固定 Heap 的情境下，RSS 長期偏高本來就可能是預期行為。

第 7 步：依 ZooKeeper 法定人數滾動

三節點叢集必須始終保持至少兩個健康成員。建議流程：

  1. 備份 values、ZooKeeper 設定與關鍵資料。
  2. 確認三個成員的角色、連線與法定人數正常。
  3. 一次只更新一個 follower。
  4. 等待該 Pod 進入 Ready 狀態，並透過 ruok、stat、mntr 驗證。
  5. 觀察同步、延遲、GC 與連線恢復。
  6. 更新另一個 follower。
  7. 最後處理 leader，或先確認 leader 已安全遷移。
  8. 跨過真實尖峰後再進入第二階段。

每一步都應等待 StatefulSet 就緒：

kubectl -n infra rollout status statefulset/zookeeper --timeout=15m
kubectl -n infra get pod -l app.kubernetes.io/name=zookeeper -o wide

發生下列任一情況時，應停止繼續滾動：

  • 成員無法加入 quorum。
  • 選舉頻繁發生。
  • GC 暫停明顯上升。
  • outstanding requests 持續不為零且持續增長。
  • 業務端 Session 大量重建或逾時。

比記憶體更大的風險：資料目錄使用 emptyDir

本次檢查還發現，StatefulSet 沒有 volumeClaimTemplates，持久化開關也已關閉，資料目錄實際上使用 emptyDir。Bitnami Chart 的參數說明也明確指出：persistence.enabled=false 時會使用 emptyDir。

這代表：

  • 容器重啟但 Pod 未重建時，目錄可能還在。
  • Pod 被重新排程、刪除或節點故障時，本機快照與事務日誌會遺失。
  • 單一節點可以從其他成員重新同步，但不代表三個節點同時遺失資料後仍能恢復。

三複本不是持久化的替代品。複本解決執行期可用性，PVC 與備份解決可恢復性。

比起把高頻事務日誌放在共用 NFS 上，ZooKeeper 更適合使用低延遲的區塊儲存，例如 SSD StorageClass。一個保守起點是每個 Pod 10 GiB PVC，再依事務量與保留策略調整：

persistence:
  enabled: true
  storageClass: ssd
  size: 10Gi

但這裡不能直接做一般滾動更新。StatefulSet 的 volumeClaimTemplates 涉及不可變欄位，通常需要單獨設計遷移：

  1. 建立並驗證備份。
  2. 確認現有 ensemble 健康。
  3. 準備帶有 PVC 的新 StatefulSet，或依 Chart 的升級要求重建。
  4. 一次遷移一個成員並等待重新同步。
  5. 驗證快照、事務日誌與故障恢復。
  6. 保留明確的回滾窗口。

記憶體縮減與儲存遷移應該拆成兩次變更；否則出問題時，無法快速判斷究竟是 JVM 容量還是資料目錄所導致。

不應該順手修改的參數

目前的證據沒有指向下列參數，因此不應為了「最佳化」而一併修改：

  • maxClientCnxns：目前連線數遠未達到限制。
  • snapCount：目前快照與事務壓力不高。
  • 自動清理週期：現有磁碟增長正常。
  • Tick、Session timeout：沒有 Session 抖動證據。
  • 複本數：三節點是正式環境中最小且常見的 quorum。

一次只改變一個容量變數，才能在指標變化後判斷因果關係。

完成定義

ZooKeeper 記憶體最佳化完成，至少要滿足：

  • JVM 命令列中不存在無法解釋的重複 Heap 參數。
  • Heap、request 與 limit 形成明確的三層預算。
  • 三個成員在滾動期間始終保持 quorum。
  • 至少經過一個業務尖峰，沒有明顯 GC 或延遲退化。
  • znode、Session、watch、連線與請求積壓均有監控。
  • OOMKilled、頻繁選舉與 Session 重建須有警示。
  • emptyDir 風險已有獨立的 SSD PVC 遷移計畫與還原演練。

最終結論

ZooKeeper Pod 接近 2 GiB 不等於記憶體洩漏。固定 Xms=Xmx=2g、Chart 的大規格資源預設，加上逐步觸及 JVM 已提交的頁面，足以在很小的資料量下形成穩定的高工作集。

正確做法不是看到 CPU 低就一次把記憶體砍半，而是先讀取真實命令列，用 mntr 與快照證明負載規模，明確定義 requests/limits，再透過 1536 MiB 到 1024 MiB 的兩階段滾動驗證釋放資源。

而檢查中暴露出的 emptyDir 才是更值得優先列入風險清單的問題：資源過度配置浪費容量，沒有持久化則可能在故障時失去恢復的基礎。
