ENGINEERING NOTE · 2026年6月21日

從 Nacos 服務發現遷移到 Kubernetes Service DNS：逐條呼叫鏈平滑切換

保留 Nacos 設定中心，逐步將 Feign、Gateway 和內部 HTTP 呼叫從註冊中心實例發現遷移到 Kubernetes Service DNS，並設計灰度、驗證與回滾。

系列導覽：Kubernetes 重建遷移教學系列。服務名稱、命名空間和網域皆為通用範例。

把 Nacos 設定中的固定 ClusterIP 改成 Service DNS，只解決「設定位址不穩定」的問題。如果 Feign、Gateway 和 RestTemplate 仍透過 Nacos 取得實例清單，註冊中心故障仍可能讓所有內部呼叫提示「沒有可用服務」。

本文討論下一階段：保留 Nacos 設定中心，逐條呼叫鏈把服務發現交給 Kubernetes Service。

先拆開 Nacos 的兩個職責

flowchart LR
  A["應用程式"] --> B["Nacos 設定中心"]
  A --> C["Nacos 服務發現"]
  C --> D["Pod 實例清單"]
  E["目標架構"] --> F["Nacos 繼續提供設定"]
  E --> G["Service DNS 提供服務入口"]
  G --> H["EndpointSlice 中的 Ready Pod"]

遷移服務發現不等於同時移除 Nacos 設定中心。把兩個變更綁在同一個窗口，會讓設定載入、實例註冊和呼叫路由同時變化，回滾邊界非常差。

什麼時候適合使用 Service DNS

適合：

  • 呼叫方和被呼叫方位於同一個 Kubernetes 叢集。
  • 服務已經有穩定的 Service 名稱和命名空間。
  • Service selector、readiness 和 EndpointSlice 可靠。
  • 不依賴 Nacos metadata 做複雜權重、區域或版本路由。

需要謹慎：

  • 跨叢集、跨機房或 Kubernetes 外部實例。
  • 同一服務需要依租戶、版本或標籤選擇實例。
  • 用戶端需要感知每個實例做特殊負載平衡。
  • 長連線協定或每實例固定位址，例如部分 Kafka listener。

Kubernetes Service 的目標就是讓用戶端不需要追蹤易變的 Pod 實例，並透過 EndpointSlice 持續維護後端。Kubernetes Service

第 1 步：盤點所有服務發現入口

在程式碼和設定倉庫掃描：

rg -n '@FeignClient|lb://|LoadBalancerClient|DiscoveryClient|NacosDiscovery|spring.cloud.nacos.discovery' .

整理成表格：

caller,client_type,service_id,target_namespace,criticality,owner,status
gateway,Gateway,rbac-api,app-test,critical,team-a,pending
order-api,Feign,inventory-api,app-test,normal,team-b,pending

不要一開始掃描到多少就改多少。先選一個唯讀、低風險、容易驗證的呼叫鏈。

第 2 步：證明目標 Service 實際可用

kubectl -n app-test get service rbac-api -o yaml
kubectl -n app-test get endpointslice \
  -l kubernetes.io/service-name=rbac-api -o wide
kubectl -n app-test get pod -l app.kubernetes.io/name=rbac-api -o wide

要求：

  • selector 精確匹配目標 Pod。
  • EndpointSlice 只包含 Ready Pod。
  • port 和 targetPort 正確。
  • 至少兩個複本時分散在不同節點。

從呼叫方 Pod 測試：

kubectl -n gateway exec <gateway-pod> -- \
  getent hosts rbac-api.app-test.svc.cluster.local

kubectl -n gateway exec <gateway-pod> -- \
  curl -fsS http://rbac-api.app-test.svc.cluster.local:8082/<health-path>

這一步不通過時，不要修改 Feign 或 Gateway。

第 3 步：先遷移一個 Feign Client

原本只使用服務名稱：

@FeignClient(name = "inventory-api")
public interface InventoryClient {
    @GetMapping("/v1/inventory/{id}")
    InventoryDTO find(@PathVariable String id);
}

Spring Cloud OpenFeign 支援從設定中提供固定 URL 給 Feign Client；提供 URL 後，請求不再透過 LoadBalancer 依服務名稱發現實例。目前版本的具體設定鍵應以專案所用 Release Train 的官方 OpenFeign 文件為準。

spring:
  cloud:
    openfeign:
      client:
        config:
          inventory-api:
            url: http://inventory-api.app-test.svc.cluster.local:8090
            connectTimeout: 3000
            readTimeout: 5000

Kubernetes Service 本身負責把連線轉發到 Ready Endpoint，因此這裡不需要用戶端再從 Nacos 取得 Pod IP。

第 4 步：為切換保留開關

在 Nacos 設定或 ConfigMap 中保留兩組值：

clients.inventory-api.discovery-mode=nacos
clients.inventory-api.kubernetes-url=http://inventory-api.app-test.svc.cluster.local:8090

應用程式依明確開關選擇，而不是發現 DNS 失敗後悄悄回退到 Nacos。隱式雙路徑會造成：

  • 同一次故障中不同實例走不同鏈路。
  • 指標難以判斷哪個入口生效。
  • Nacos 問題被自動回退掩蓋。

回滾只需要還原開關並滾動呼叫方。

第 5 步：灰度一個呼叫方 Pod

建立 canary Deployment，複本為 1，只修改它的設定：

kubectl -n <caller-namespace> apply -f caller-canary.yaml
kubectl -n <caller-namespace> rollout status deployment/<caller>-canary --timeout=10m

透過臨時 Service、Header 或內部直連把測試請求送給 canary。觀察：

kubectl -n <caller-namespace> logs deployment/<caller>-canary --since=15m \
  | grep -Ei 'inventory-api|available server|timeout|refused'

同時驗證目標 Service Endpoint 變化時 canary 能繼續呼叫：

kubectl -n app-test rollout restart deployment/inventory-api
kubectl -n app-test rollout status deployment/inventory-api --timeout=10m

第 6 步：遷移 Gateway 路由

原路由：

uri: lb://rbac-api

候選路由：

uri: http://rbac-api.app-test.svc.cluster.local:8082

先複製一條測試 Path 或測試 Host，不要直接替換全部正式路由。驗證：

  • Path rewrite。
  • Authorization Header。
  • Cookie 和 CORS。
  • 逾時和回應內容。
  • 目標 Pod 滾動時的連線連續性。

如果 Gateway 仍報 Load balancer does not have available server，表示實際生效的 route 仍是 lb://，或設定沒有刷新。

第 7 步：遷移一般 HTTP Client

把基礎 URL 放在設定中：

clients.file-storage.base-url=http://file-storage.app-test.svc.cluster.local:8686

用戶端必須同時設定：

  • connect timeout。
  • read timeout。
  • 連線池和並發上限。
  • 只對冪等請求設定有限重試。
  • 可選依賴的明確降級。

Service DNS 解決發現問題，不會自動解決慢依賴和執行緒堆積。

第 8 步：擴大到完整 Deployment

灰度穩定後：

kubectl -n <caller-namespace> set env deployment/<caller> \
  DISCOVERY_MODE=kubernetes

kubectl -n <caller-namespace> rollout status deployment/<caller> --timeout=10m

檢查全部 Pod 的設定來源和日誌，避免只有新 Pod 生效。

第 9 步：停止這個服務的 Nacos 註冊

只有所有呼叫方都切換後，才考慮關閉目標服務的 Nacos discovery 註冊：

spring:
  cloud:
    nacos:
      discovery:
        register-enabled: false

屬性名稱會隨 Spring Cloud Alibaba 版本變化，必須依專案依賴核對。關閉前從程式碼倉庫和 Nacos 訂閱關係確認沒有遺漏呼叫方。

Nacos Config 仍可繼續運作；不要誤刪 spring.config.import 或設定 namespace。

第 10 步：模擬 Nacos 服務發現不可用

在隔離環境驗證：

  1. 呼叫方已經載入完成設定。
  2. 暫時阻斷它對 Nacos Naming 連接埠的連線。
  3. 持續請求已經遷移的呼叫鏈。
  4. 重啟目標業務 Pod，觀察 EndpointSlice 更新。

預期：已遷移的呼叫鏈仍可透過 Service DNS 呼叫；需要動態設定的功能是否受影響，要單獨記錄。

回滾

停止扩大范围
→ 恢复 discovery-mode=nacos
→ 滚动调用方
→ 检查 Nacos 中目标服务实例
→ 验证 lb:// 调用

如果已經關閉目標服務註冊，應先還原註冊並確認實例健康，再切回呼叫方。

完成定義

  • 已遷移的呼叫鏈不再建立 Nacos LoadBalancer Client。
  • Feign/Gateway 生效 URL 為 Service DNS。
  • 目標 Pod 滾動時請求沒有持續失敗。
  • Nacos Naming 暫時不可用時，已遷移鏈路仍能運作。
  • Nacos Config 載入與動態刷新仍正常。
  • 所有呼叫方遷移完成後才關閉目標服務註冊。
  • 每條呼叫鏈都有獨立的回滾開關和驗證記錄。

正確的遷移單位不是「整個 Nacos」，而是一條可驗證、可回滾的服務呼叫鏈。
