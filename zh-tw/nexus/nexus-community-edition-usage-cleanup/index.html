ENGINEERING NOTE · 2026年7月18日

Nexus Repository Community Edition 用量限制與儲存清理實戰

解釋元件數、請求量、Blob 空間與 maven-public 的區別，逐步盤點 hosted 與 proxy 倉庫、設定 Cleanup Policy、壓縮 Blob Store，並驗證 CE 用量回落。

本文使用通用的倉庫名稱、網域與容量。刪除 hosted 製品可能無法復原，所有指令都應先在測試環境驗證，並完成備份。

Nexus 頁面顯示「實例正在接近使用限制」時，不是磁碟空間警示，也不是 Kubernetes 不允許執行社群版。

截至本文核對時，Sonatype 官方 Usage Center 說明，Community Edition 的限制為：總元件數 40,000，或每日請求數 100,000；超過任一限制後不能新增元件，降回限制以內才恢復。指標變更最多需要約一小時反映。Usage Center

這些規則屬於產品版本與授權政策，執行前應再次查看官方頁面。

先分清四個容易混淆的概念

概念含義是否等於 CE 用量
ComponentNexus 管理的邏輯元件／版本是，影響元件數
AssetPOM、JAR、校驗檔等具體檔案不等同於元件數
Blob Store 空間檔案實際佔用的磁碟不等同於元件數
Request用戶端下載、查詢、上傳請求影響每日請求量

maven-public 通常只是一個 Maven Group 倉庫名稱，不代表「Public 版本」或另一種 Nexus 授權。

Hosted、Proxy、Group 的清理風險不同

hosted

保存企業自行發布的 Release 與 Snapshot。刪除可能永久失去建置產物，必須先確認：

  • 是否仍被正式環境、歷史分支或回滾使用。
  • 原始碼能否重建出完全相同的二進位檔。
  • 是否滿足稽核與保留期限。
  • 是否已有離線備份。

proxy

保存上游倉庫的快取。上游仍存在且網路可靠時，快取通常可以重新下載，因此更適合優先治理。

但上游元件可能已被刪除或變更，或因網路不可達而無法重新取得。不能把所有 proxy cache 都視為沒有價值。

group

Group 本身聚合其他倉庫，一般不是直接儲存製品的清理對象。應清理它所包含的 hosted／proxy 成員。

第 1 步：備份資料庫與 Blob Store

Nexus 使用 PostgreSQL 時，備份必須涵蓋：

PostgreSQL 数据库
全部 Blob Store
/nexus-data 中的配置和密钥
Kubernetes Secret 与清单

資料庫與 Blob 的時間點要協調。只備份資料庫，還原後會出現中繼資料指向不存在的檔案；只備份 Blob，也無法重建完整的倉庫狀態。

pg_dump -Fc -h <postgres-host> -U <backup-user> <nexus-database> \
  -f backup/nexus-before-cleanup.dump

sha256sum backup/nexus-before-cleanup.dump \
  > backup/nexus-before-cleanup.dump.sha256

Blob Store 應依底層儲存能力建立唯讀快照或一致性備份。不要在 Nexus 正在大量寫入時直接打包目錄。

第 2 步：記錄清理前基線

在 Usage Center 截圖或匯出：

  • Total Components。
  • Daily Requests。
  • 指標更新時間。

記錄倉庫與 Blob：

curl --fail --silent --show-error \
  --netrc-file <secure-netrc> \
  https://repo.example.com/nexus/service/rest/v1/repositories \
  > reports/repositories-before.json

curl --fail --silent --show-error \
  --netrc-file <secure-netrc> \
  https://repo.example.com/nexus/service/rest/v1/blobstores \
  > reports/blobstores-before.json

不要把含憑證的指令、.netrc 或 API 回應中的內部資訊提交到公開倉庫。

第 3 步：依倉庫類型盤點

建立表格：

repository,format,type,owner,retention_days,upstream_recoverable,cleanup_policy
maven-releases,maven2,hosted,release-team,365,false,manual-review
maven-snapshots,maven2,hosted,dev-team,30,true,snapshot-retention
maven-central,maven2,proxy,platform-team,60,true,proxy-cache

優先順序通常是：

失效 proxy cache
→ 过期 Snapshot
→ 无引用的临时 hosted 制品
→ Release 人工审计

第 4 步：分頁匯出元件，避免只看 UI

Nexus Components API 使用 continuation token 分頁，單頁結果不能代表倉庫總量。

請求結構：

curl --fail --silent --show-error \
  --netrc-file <secure-netrc> \
  'https://repo.example.com/nexus/service/rest/v1/components?repository=<repository>'

自動化指令碼應：

  1. 儲存 items。
  2. 讀取 continuationToken。
  3. token 非空時繼續請求。
  4. 只輸出脫敏後的 group/name/version/lastModified。
  5. 產生候選清單，不直接 DELETE。

第 5 步：先找消費者，再決定刪除

搜尋：

  • Maven POM、Gradle 與 npm lockfile。
  • Jenkinsfile 與流水線參數。
  • Kubernetes 映像與啟動指令碼。
  • Git tag、Release 與維護分支。
  • 正式環境回滾清單。

Release 製品沒有被目前主幹引用，不代表歷史版本不需要。

候選清單至少經過製品負責人與維運雙人確認。

第 6 步：為 Proxy 設定 Cleanup Policy

在 Nexus 管理介面建立 Cleanup Policy，依目標版本支援的條件設定：

  • Last downloaded before。
  • Last blob updated before。
  • Release type 或格式相關條件。
  • 名稱正規表達式，只限制明確命名空間。

先關聯一個低風險的 proxy 倉庫，等待任務執行並抽樣驗證。不要第一天就關聯所有倉庫。

第 7 步：治理 Snapshot

Snapshot 常見規則：

保留最近 N 个版本
保留最近 N 天
保留仍被活跃分支引用的版本
Release 不套用 Snapshot 规则

刪除前用一個隔離的 Maven 專案，驗證最新與歷史 Snapshot 的下載路徑。清理後驗證仍在保留範圍內的版本。

第 8 步：依正確順序執行任務

不同 Nexus 版本的任務名稱可能不同，原則順序是：

执行 Cleanup Policy
→ 等待逻辑删除完成
→ 删除不再引用的 Blob
→ Compact Blob Store
→ 等待数据库与 Usage Center 指标更新

Compact Blob Store 主要回收磁碟空間，不等於立即降低元件數。不要因為磁碟沒有立刻變小，就再次大量刪除。

執行任務時記錄：

  • Task ID、開始與結束時間。
  • 刪除候選數量。
  • Task 日誌與錯誤。
  • Blob 空間變化。
  • Usage Center 更新時間。

第 9 步：驗證代理快取能否重新拉取

清理 proxy cache 後，從空的 Maven 本機倉庫下載一個允許刪除的元件：

mvn -Dmaven.repo.local=<temporary-empty-directory> \
  dependency:get \
  -Dartifact=<group>:<artifact>:<version>

同時觀察 Nexus request log 與 proxy remote 狀態。上游不可用時，應在擴大清理前停止。

第 10 步：驗證 Hosted 倉庫

至少完成：

  • 下載保留的歷史 Release。
  • 下載最新 Snapshot。
  • 上傳新的測試 Snapshot。
  • 使用 CI 帳號發布與讀取。
  • 使用匿名／一般帳號驗證權限沒有改變。

如果已超過 CE 限制，新增元件可能仍被阻止，需等待指標確認回落；官方說明 Usage Center 可能最多延遲約一小時。

每日請求數超限怎麼辦

清理元件不能直接降低請求量，應分析：

  • CI 是否每次都強制更新全部依賴。
  • 是否有錯誤重試或健康檢查高頻存取倉庫。
  • 開發機建置是否繞過本機快取。
  • 同一個元件是否被大量重複下載。
  • 代理、映像與建置快取策略是否合理。

不要為了減少請求，就對 Release 回應過長且不可撤銷的錯誤快取標頭。

為什麼不應該修改原始碼繞過限制

  • 限制可能同時存在於 UI、伺服端寫入路徑與授權狀態。
  • 修改建置會失去官方升級與安全修補路徑。
  • 資料庫結構與任務行為無法獲得支援。
  • 下一次升級可能直接破壞私有修改。
  • 授權條款不是前端數字可以改變的。

正確的選擇是降低真實用量、調整架構，或購買符合規模的版本。

什麼時候考慮 Pro

  • 正常業務元件數量長期超過 CE 限制。
  • 每日請求量來自合理的 CI/CD，而不是錯誤流量。
  • 製品保留期受稽核要求約束，不能繼續刪除。
  • 需要官方 HA、支援或企業能力。
  • 清理成本已經高於授權與維運收益。

完成定義

  • 資料庫與 Blob Store 完成一致性備份與還原驗證。
  • 每個倉庫都有所有者、類型與保留策略。
  • Proxy、Snapshot、Release 使用不同的清理規則。
  • 刪除候選均有引用掃描與人工審核。
  • Cleanup 與 Blob Compact 任務順序正確且日誌完整。
  • Maven 下載、發布與 CI 建置通過。
  • Usage Center 在指標刷新後回到安全範圍。
  • 清理規則納入定期稽核，而不是接近限制時臨時刪除。

Nexus 容量治理的目標，不是讓頁面數字暫時變小，而是讓製品生命週期、快取、稽核與還原能力長期可控。
