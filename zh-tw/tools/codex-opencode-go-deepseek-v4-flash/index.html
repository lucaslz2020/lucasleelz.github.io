ENGINEERING NOTE · 2026年8月6日

在 Codex 中串接 OpenCode Go 的 DeepSeek V4 Flash：Responses API、模型目錄與 Profile 切換

按真實時間線復盤將 DeepSeek V4 Flash 透過 OpenCode Go Responses API 串接到 Codex 的完整過程，包括協定驗證、代理誤判、無明文金鑰認證、模型目錄、雙 Profile 切換、exec 相容性修正與檔案修改實測。

目標很明確：保留 Codex 原本的 OpenAI 登入，同時把 OpenCode Go 提供的 DeepSeek V4 Flash 串接到 Codex；預設使用 DeepSeek，需要時用一條指令切回 OpenAI。

最後實作了三個入口：

# 默认：DeepSeek V4 Flash
codex

# 显式选择 DeepSeek
codex -p deepseek

# 切回 OpenAI
codex -p openai

實際過程不是簡單改一個模型名稱。這裡同時涉及 Responses API 相容性、Provider 認證、模型元資料、Codex 自訂工具，以及 Profile 的設定覆寫順序。更麻煩的是，有些設定可以通過靜態檢查，卻只會在第一次真實請求時暴露協定差異。

需求、約束與驗收標準

開始修改前，我把目標拆成一組可以驗證的條件：

  • 沿用 OpenCode Go 中已經設定好的 deepseek-v4-flash，不再另外申請和複製一份憑證。
  • Codex 直接呼叫 Responses API，不長期執行本機協定代理。
  • DeepSeek 維持預設，OpenAI 登入與模型仍然可用。
  • 跨 Provider 切換不能只改模型名稱，必須同時切換認證與模型目錄。
  • 目前工作階段的設定可以追溯，修改前要保留原始的 config.toml。
  • 不把 API Key 輸出到終端機日誌、文章、Git 或截圖。
  • 不能只透過 curl；還要透過 Codex 原生對話與真實檔案修改。
  • 出現不相容時，保留完整錯誤並定位到請求協定，而不是靠重試掩蓋。

最終驗收標準是：

驗收項通過條件
原始 API/v1/responses 回傳 HTTP 200 和 completed
Codex 設定doctor 無 warning、無 failure
模型目錄能解析 100 萬上下文、high/max 與正確工具模式
DeepSeek Profile啟動資訊顯示 opencode-go + deepseek-v4-flash
OpenAI Profile啟動資訊顯示 openai + gpt-5.6-luna
生成能力兩個 Profile 分別回傳約定的精確文字
Agent 工具DeepSeek 能透過 apply_patch 建立並寫入指定內容
憑證安全Codex 設定不包含 API Key，相關檔案權限限制為目前使用者

完整排查時間線

這次串接經歷了幾次方向修正。依發生順序記錄如下：

階段操作結果或判斷
1確認 OpenCode Go 已儲存 DeepSeek 憑證不重複儲存明文 Key
2根據舊資料判斷只支援 Chat Completions結論過時，方向錯誤
3暫時安裝協定相容代理尚未啟用，等待介面能力確認
4閱讀 DeepSeek 建立 Response 文件確認新介面已支援 Responses API
5直連 OpenCode Go /v1/responsesHTTP 200，回傳 OK
6解除安裝未使用的代理減少一層執行與憑證鏈路
7設定 Codex 自訂 Provider 與執行時期認證Provider 可達，Key 未寫入設定
8使用未知模型的 fallback 元資料執行原生 Codex 回傳 OK，但有模型元資料警告
9加入自訂模型目錄警告消失，但首次真實請求被 exec 工具拒絕
10將 tool_mode 從 code_mode_only 改為標準模式DeepSeek 原生請求恢復成功

這條時間線有一個反直覺的點：沒有模型目錄時請求可以成功，補上看似更完整的模型目錄後反而失敗。 根因不是模型品質，而是模型目錄改變了 Codex 傳送給上游的工具宣告。

最終架構

  B -->|預設或 -p deepseek| C[DeepSeek Profile]
  B -->|-p openai| D[OpenAI Profile]

設定分為四個檔案：

~/.codex/
├── config.toml
├── deepseek.config.toml
├── openai.config.toml
└── model-catalogs/

config.toml 儲存預設值與 Provider 定義；兩個 Profile 只覆寫模型、Provider、上下文視窗與模型目錄。API Key 不寫進這些檔案，而是在執行時期從 OpenCode 已儲存的認證檔讀取。

先驗證 Responses API，不要從舊資料推斷

一開始我根據舊的搜尋結果誤以為 DeepSeek 端點只支援 Chat Completions，並準備增加一層協定代理。隨後在 DeepSeek 建立 Response 文件 中確認了 Responses API，再對 OpenCode Go 的實際端點做最小請求驗證：

curl --request POST \
  --url https://opencode.ai/zen/go/v1/responses \
  --header "Authorization: Bearer ${OPENCODE_GO_API_KEY}" \
  --header "Content-Type: application/json" \
  --data '{
    "model": "deepseek-v4-flash",
    "input": "Reply exactly OK.",
    "max_output_tokens": 16
  }'

去識別化後的關鍵結果如下：

{
  "object": "response",
  "status": "completed",
  "model": "deepseek-v4-flash",
  "output_text": "OK",
  "error": null
}

介面回傳 HTTP 200，回應狀態為 completed，模型為 deepseek-v4-flash，文字結果為 OK。這代表不需要額外的協定代理，可以讓 Codex 直接使用 wire_api = "responses"。

文件、模型服務與閘道是三層能力

這裡不能只問「DeepSeek 是否支援 Responses API」，因為實際請求會經過三層：

  1. DeepSeek 模型與介面定義是否支援 Response 物件。
  2. OpenCode Go 是否暴露相容的 /v1/responses 路由。
  3. OpenCode Go 是否完整接受 Codex 附帶的工具 schema 與串流事件。

最小文字請求只能證明前兩層以及第三層的基礎部分。Codex 還會傳送開發者指令、工具、推理參數與串流設定，所以後面仍需要原生端到端測試。

這一步很重要：搜尋索引、舊文件與第三方說明都可能落後，最終應以目標端點的真實契約與最小請求結果為準。先前暫時安裝、但尚未投入使用的代理隨後被解除安裝，避免留下重複鏈路。

測試時不要把真實 API Key 寫進文章、腳本或 shell 歷史。上面的環境變數只用來說明請求結構。

第一條彎路：為什麼代理裝了又解除安裝

最初的判斷來自舊的 DeepSeek API 印象：如果上游只有 /chat/completions，而目前的 Codex 自訂 Provider 只接受 wire_api = "responses"，中間就需要一個轉換層。

因此當時的備援鏈路是：

flowchart LR
  A[Codex Responses] --> B[本機相容代理]
  B --> C[Chat Completions]
  C --> D[DeepSeek]

代理套件已經暫時安裝，但沒有啟動服務，也沒有寫入 Codex 路由。看到 DeepSeek 的新文件後，我沒有繼續完成代理設定，而是先驗證直連。直連通過後立即解除安裝代理。

這不是單純清理一個 npm 套件。多保留一層代理會引入：

  • 第二處 API Key 或憑證讀取邏輯。
  • 獨立行程、連接埠、健康檢查與開機啟動。
  • 兩套逾時、串流轉送、重試與錯誤格式。
  • 工具 schema、推理欄位與 Response 事件的轉換風險。
  • 故障時難以判斷問題來自 Codex、代理、OpenCode Go 還是模型。

只有當直連協定確實缺失，或者必須做統一稽核、限流與路由時，代理才值得長期存在。

設定前先盤點本機狀態

直接覆寫 config.toml 之前，先確認目前版本、預設模型、登入狀態與已儲存的 OpenCode 憑證。本文當時使用：

Codex CLI: 0.145.0
原默认模型: gpt-5.6-luna
原推理强度: high
OpenAI 登录: 已存在
OpenCode Go 凭证: 已存在

版本檢查：

codex --version

憑證存在性檢查只回傳布林結果，不印出內容：

jq -e \
  '.["opencode-go"].key | type == "string" and length > 0' \
  ~/.local/share/opencode/auth.json >/dev/null

再檢查檔案權限：

ls -l ~/.codex/config.toml ~/.local/share/opencode/auth.json

如果權限允許同機其他使用者讀取，應先修正權限，再繼續串接。不要為了確認 Key 是否存在，直接執行會把它印到終端機的 jq -r。

設定 OpenCode Go Provider

先備份目前設定：

cp ~/.codex/config.toml ~/.codex/config.toml.before-opencode-go

在 ~/.codex/config.toml 中設定預設模型：

model = "deepseek-v4-flash"
model_provider = "opencode-go"
model_context_window = 1000000
model_catalog_json = "/Users/you/.codex/model-catalogs/opencode-go.json"
model_reasoning_effort = "high"

[model_providers.opencode-go]
name = "OpenCode Go"
base_url = "https://opencode.ai/zen/go/v1"
wire_api = "responses"
request_max_retries = 4
stream_max_retries = 5
stream_idle_timeout_ms = 300000

base_url 到 /v1 為止，Codex 會根據 wire_api 請求 /responses。不要把完整的 /responses 再寫進 base_url。

這裡明確設定 100 萬上下文，但實際可用視窗仍受模型、Provider 與閘道策略共同約束。超長任務上線前應單獨做邊界測試，不能只依賴本機元資料。

每個欄位解決什麼問題

設定項作用
model傳送給上游的模型識別
model_provider選擇哪一組 Base URL、認證與重試策略
model_context_window給 Codex 的上下文預算提示
model_catalog_json提供模型名稱、推理檔位、工具模式與其他能力元資料
wire_api指定 Provider 使用 Responses 協定
request_max_retries一般 HTTP 請求的最大重試次數
stream_max_retries串流回應中斷後的恢復次數
stream_idle_timeout_ms串流長時間沒有事件時的逾時

model 與 model_provider 必須成對理解。把模型改成 DeepSeek、卻仍保留 model_provider = "openai"，請求不會自動發現 OpenCode Go；反過來，在 OpenCode Go Provider 下選擇只有 OpenAI 提供的模型名稱也會失敗。

為什麼沒有使用環境變數直接複製 Key

Codex Provider 也可以讀取指定的環境變數，但這需要保證每個啟動 Codex 的終端機、IDE 或桌面行程都繼承同一個變數。目前憑證已經由 OpenCode 管理，所以讓認證指令按需求讀取現有檔案，更符合「單一憑證來源」。

如果團隊用統一的 Secret Manager 注入環境變數，則應優先使用團隊的標準做法；本文的 jq 方案適合已經使用 OpenCode 本機認證儲存的個人開發機。

/models 能回傳，不代表 Codex 能使用

設定 Provider 後，Codex 會嘗試重新整理模型清單。OpenCode Go 的 /models 當時回傳 OpenAI 風格結構：

{
  "object": "list",
  "data": [{ "id": "deepseek-v4-flash", "object": "model" }]
}

目前 Codex 的模型管理邏輯在這條自訂重新整理鏈路中預期的是包含 models 欄位的目錄結構，因此記錄了類似的錯誤：

failed to decode models response:
missing field `models`

這不代表 /responses 不可用。實際上，最小 Response 與 Codex 的 fallback 元資料請求都已經成功。失敗的是「自動重新整理模型目錄」這條輔助鏈路。

處理方式不是修改閘道回應，也不是忽略所有日誌，而是提供本機 model_catalog_json：

文本生成链路: Codex -> /responses -> 成功
模型发现链路: Codex -> /models -> schema 不匹配
替代方案:     Codex -> 本地 model_catalog_json

這樣可以把模型執行與模型發現解耦，同時明確由本機設定維護 DeepSeek 的能力宣告。

用執行時期認證避免複製明文金鑰

OpenCode 已經在本機認證檔中儲存憑證，沒有必要再把同一個 Key 複製到 config.toml。Codex 的自訂 Provider 支援透過指令取得認證資訊：

[model_providers.opencode-go.auth]
command = "/usr/bin/jq"
args = [
  "-r",
  ".[\"opencode-go\"].key",
  "/Users/you/.local/share/opencode/auth.json",
]
timeout_ms = 5000
refresh_interval_ms = 300000

注意：args 由 Codex 直接傳給指令，不一定經過 shell，因此不要假設 ~ 會自動展開。macOS 應寫實際的絕對路徑，Linux 則通常是 /home/用户名/...。

這種做法有幾個好處：

  • Codex 設定中沒有第二份明文 Key。
  • OpenCode 更新憑證後，Codex 可以依重新整理週期重新讀取。
  • 設定檔更適合備份與審查。

認證檔與 Codex 設定都應限制為目前使用者可讀，例如權限 600。任何診斷輸出也不應印出 Key。

為什麼需要自訂模型目錄

只設定模型名稱時，Codex 可以使用 fallback 元資料啟動，但會提示：

Model metadata for `deepseek-v4-flash` not found.
Defaulting to fallback metadata; this can degrade performance and cause issues.

有趣的是，這個 fallback 模式首先通過了原生 Codex 測試：啟動資訊顯示 deepseek-v4-flash + opencode-go，並回傳 OK。因此可以先得到兩個結論：

  • Provider、認證與 Responses 路由本身是通的。
  • 後續失敗如果只發生在自訂目錄啟用後，應優先比較模型元資料，而不是重新懷疑 API Key。

最小 JSON 為什麼失敗

我先嘗試手動寫一個只有名稱、上下文與推理檔位的目錄。Codex 解析時直接拒絕：

failed to parse model_catalog_json:
missing field `base_instructions`

這代表 model_catalog_json 不是給模型選擇器使用的簡易清單。它還包含 Codex 執行時所需的基本指令、訊息範本、截斷策略與工具能力。

手動撰寫幾十個隨版本變化的欄位很容易製造新的相容問題，所以最終改為從目前的 models_cache.json 複製一條結構完整的記錄，再明確縮小 DeepSeek 的能力。

為了讓 Codex 認識模型名稱、上下文視窗與推理檔位，可以根據目前 Codex 的模型快取產生一份自訂目錄。以下指令以既有模型條目為結構範本，只取代與 DeepSeek 相關的能力欄位：

mkdir -p ~/.codex/model-catalogs

jq '{
  models: [
    (.models[] | select(.slug == "gpt-5.6-luna")
      | .slug = "deepseek-v4-flash"
      | .display_name = "DeepSeek V4 Flash (OpenCode Go)"
      | .description = "通过 OpenCode Go 使用的 DeepSeek V4 Flash"
      | .context_window = 1000000
      | .max_context_window = 1000000
      | .effective_context_window_percent = 95
      | .default_reasoning_level = "high"
      | .supported_reasoning_levels = [
          {"effort": "high", "description": "适合日常编程与复杂任务"},
          {"effort": "max", "description": "为最困难任务提供最大推理强度"}
        ]
      | .tool_mode = null
      | .input_modalities = ["text"]
      | .supports_image_detail_original = false
      | .supports_search_tool = false
      | .use_responses_lite = false)
  ]
}' ~/.codex/models_cache.json > ~/.codex/model-catalogs/opencode-go.json

chmod 600 ~/.codex/model-catalogs/opencode-go.json

這裡不是隨便拼一個最小 JSON。模型目錄的 schema 會隨 Codex 版本演進，直接重複使用目前安裝版本快取中的完整條目，可以保留該版本要求的基本指令與必填欄位。本次設定以 Codex 0.145.0 驗證；升級後應重新執行解析與端到端測試。

產生後先限制權限並檢查關鍵欄位，不需要印出長篇的基本指令：

chmod 600 ~/.codex/model-catalogs/opencode-go.json

jq '.models[] | {
  slug,
  display_name,
  context_window,
  max_context_window,
  default_reasoning_level,
  tool_mode,
  input_modalities
}' ~/.codex/model-catalogs/opencode-go.json

預期關鍵值：

{
  "slug": "deepseek-v4-flash",
  "display_name": "DeepSeek V4 Flash (OpenCode Go)",
  "context_window": 1000000,
  "max_context_window": 1000000,
  "default_reasoning_level": "high",
  "tool_mode": null,
  "input_modalities": ["text"]
}

最隱蔽的問題：模型目錄會改變工具協定

第一次產生目錄時，我完整繼承了 OpenAI 模型的能力宣告，其中包括：

{
  "tool_mode": "code_mode_only",
  "shell_type": "shell_command",
  "apply_patch_tool_type": "freeform"
}

模型目錄可以正常解析，codex doctor 也沒有回報錯誤，但真實呼叫失敗：

Unsupported custom tool: 'exec'. Only 'apply_patch' is supported.

原因是 tool_mode = "code_mode_only" 不只是一種 UI 標籤。它會讓 Codex 在 Responses 請求中宣告 exec 自訂工具，而當時的 OpenCode Go 上游只接受 apply_patch 這類自訂工具。

把 DeepSeek 條目的工具模式改為標準模式：

{
  "tool_mode": null
}

隨後同一個原生 Codex 請求成功回傳 DEEPSEEK_OK。

為什麼關閉 features.unified_exec 仍然失敗

排查時還試過一次指令列覆寫：

codex exec \
  -p deepseek \
  -c features.unified_exec=false \
  -s read-only \
  --ephemeral \
  "Reply exactly DEEPSEEK_OK. Do not use tools."

請求仍然回報同一個 Unsupported custom tool: 'exec'。這代表問題不只是全域 feature flag；模型條目中的 tool_mode = "code_mode_only" 仍在決定執行時期工具協定。

真正有效的對照實驗是：其他設定保持不變，只把模型目錄中的 tool_mode 改為 null。修改前失敗，修改後成功，因果關係才夠清晰。

用真實檔案修改證明 Agent 工具可用

精確回覆只能證明模型能產生文字。為了確認 Codex 不是「能聊天但不能改程式碼」，我在獨立的暫時目錄執行了一個最小的寫檔任務：

codex exec \
  -p deepseek \
  -C /private/tmp/codex-deepseek-agent-test \
  -s workspace-write \
  --ephemeral \
  --skip-git-repo-check \
  "Use apply_patch to create result.txt containing exactly DEEPSEEK_TOOL_OK followed by a newline. Then stop."

執行資訊確認：

model: deepseek-v4-flash
provider: opencode-go
sandbox: workspace-write
reasoning effort: high

模型隨後發起 apply_patch，Codex 顯示：

apply patch
patch: completed

--- /dev/null
+++ b/result.txt
@@ -0,0 +1 @@
+DEEPSEEK_TOOL_OK

44 45 45 50 53 45 45 4b 5f 54 4f 4f 4c 5f 4f 4b 0a

測試後刪除檔案與暫時目錄，沒有把測試產物留在正式儲存庫。

這個問題說明：

  • 支援 Responses API，不等於支援所有 Codex 擴充工具。
  • 模型目錄不是純展示資料，它可能改變請求結構。
  • doctor 與 JSON 解析成功只代表靜態設定成立，不能取代真實請求。
  • 從另一個模型複製元資料後，必須逐項核對工具、圖片、搜尋與推理能力。

如果閘道未來加入對 exec 的原生支援，可以重新評估工具模式；不要在沒有協定測試的情況下預先宣告能力。

用 Profile 快速切換 Provider

Codex 互動工作階段中的 /model 適合切換目前 Provider 下的模型與推理強度，但 OpenAI 與 OpenCode Go 是兩個不同的 Provider。只改模型名稱可能把請求送到錯誤的服務，因此應使用 Codex Profile 同時覆寫模型、Provider 與模型目錄。

目前 Codex 使用獨立的 Profile 檔案：

$CODEX_HOME/deepseek.config.toml
$CODEX_HOME/openai.config.toml

不要繼續使用舊式寫法：

profile = "deepseek"

[profiles.deepseek]
model = "deepseek-v4-flash"

從 Codex 0.134.0 起，--profile 不再從主設定中的 [profiles.<name>] 讀取，而是載入同目錄下的 <name>.config.toml。

DeepSeek Profile，檔名為 ~/.codex/deepseek.config.toml：

model = "deepseek-v4-flash"
model_provider = "opencode-go"
model_context_window = 1000000
model_catalog_json = "/Users/you/.codex/model-catalogs/opencode-go.json"
model_reasoning_effort = "high"
plan_mode_reasoning_effort = "max"

OpenAI Profile，檔名為 ~/.codex/openai.config.toml：

model = "gpt-5.6-luna"
model_provider = "openai"
model_context_window = 272000
model_catalog_json = "/Users/you/.codex/models_cache.json"
model_reasoning_effort = "high"
plan_mode_reasoning_effort = "xhigh"

請依自己的系統替換 /Users/you。模型上下文與推理檔位也應以目前的模型目錄為準，不要永久照抄本文的數值。

啟動時切換：

codex -p deepseek
codex -p openai

非互動任務同樣支援：

codex exec -p deepseek "检查当前代码"
codex exec -p openai "检查当前代码"

Profile 在新工作階段啟動時載入。已經在執行的工作階段不能靠修改磁碟設定無損更換底層 Provider；完成目前任務後再啟動新工作階段更安全。

設定覆寫順序

Profile 不是完全獨立的設定，它疊加在使用者主設定之上。與本文相關的優先順序可以簡化為：

用户 ~/.codex/config.toml
  < 启动时选择的 Profile
  < 项目 .codex/config.toml
  < CLI 专用参数或 -c/--config 覆盖

這代表：

  • deepseek.config.toml 不需要重複 Provider 的 Base URL 與認證定義，它可以繼承主設定。
  • 專案內如果固定了 model_provider，可能覆寫個人 Profile，需要用 /status 或啟動資訊確認。
  • 暫時診斷適合用 -c，驗證完成後再決定是否永久保留。

/model、--model 和 --profile 的邊界

方式是否新工作階段適合場景
/model否目前 Provider 內切模型或推理強度
codex -m <model>是單次覆寫模型名稱
codex -p <profile>是同時切換模型、Provider、目錄與策略
codex -c key=value是暫時排查任意設定項

跨 Provider 時優先使用 Profile，因為 -m 不會自動選擇另一組認證與 Base URL。

如果每天頻繁切換，可以在個人 shell 設定中增加可選別名：

alias cdx-ds='codex -p deepseek'
alias cdx-openai='codex -p openai'

別名只是縮短啟動指令，不會改變 Codex 設定的語意。桌面版模型選擇器與 CLI Profile 也不是同一種能力；本文驗證的是本機 Codex CLI。

驗證不能只跑一層

最終依五層驗證。每層排除的問題不同，不能互相取代。

第一層：原始 Responses 請求

確認 OpenCode Go 端點能夠接受 deepseek-v4-flash，並回傳 completed。這一層排除 URL、認證、模型名稱與基礎協定問題。

第二層：模型目錄解析

codex debug models

輸出應包含：

deepseek-v4-flash
DeepSeek V4 Flash (OpenCode Go)
context_window: 1000000
default_reasoning_level: high
tool_mode: null

目前版本的 codex debug models 不支援 --profile；Profile 只適用於執行時期指令與部分子指令。需要確認 Profile 是否真的生效時，應查看 codex exec 的啟動資訊或執行最小請求。

排查時曾執行：

codex -p deepseek debug models | jq ...

Codex 已明確回報錯誤 --profile only applies to runtime commands，但因為 shell 預設回傳管線最後一個 jq 的退出碼，整條指令表面上顯示 exit=0。自動化腳本應啟用 pipefail，否則可能把前半段失敗誤判為成功：

set -o pipefail

第三層：Codex 健康檢查

codex doctor --summary --no-color

本次結果為：

17 ok · 1 idle · 1 notes · 0 warn · 0 fail

它確認設定可以載入、Provider 不需要 OpenAI 認證、目標 HTTP 端點可達，但仍無法發現工具協定不符。

第四層：兩個 Profile 的真實請求

用唯讀沙盒與暫時性工作階段做最小端到端測試：

codex exec -p deepseek \
  -s read-only \
  --ephemeral \
  "Reply exactly DEEPSEEK_OK. Do not use tools."

codex exec -p openai \
  -s read-only \
  --ephemeral \
  "Reply exactly OPENAI_OK. Do not use tools."

最後分別回傳：

DEEPSEEK_OK
OPENAI_OK

啟動資訊也應分別顯示：

model: deepseek-v4-flash
provider: opencode-go

以及：

model: gpt-5.6-luna
provider: openai

這一步同時驗證了 Profile 覆寫順序、認證、模型目錄、Provider 路由與 Responses 請求。

第五層：Agent 檔案工具

使用 workspace-write 沙盒在隔離目錄執行真實的 apply_patch，再檢查檔案長度與最後一個換行位元組。它驗證的不是文字生成，而是：

  • 模型能夠選擇 Codex 提供的工具。
  • OpenCode Go 接受該工具宣告。
  • Codex 能執行並回傳修補結果。
  • 目標檔案內容符合精確要求。

只有第五層通過，才可以說這條鏈路具備最小編碼 Agent 能力。更複雜的 shell、平行工具、MCP、圖片與 Web 搜尋仍要分別驗證，不能從一次 apply_patch 推論出全部能力。

常見誤區

把模型切換等同於 Provider 切換

/model 或 --model 主要覆寫模型名稱。跨服務切換時，還必須同步切換 model_provider、認證方式與模型目錄。Profile 是更可靠的原子設定單位。

直接把 API Key 寫進 config.toml

這會增加備份、截圖、日誌與誤提交時的洩漏面。優先使用 bearer_token_env_var 或 Provider 的執行時期認證指令，並收緊憑證檔權限。

只看 doctor，不跑真實請求

健康檢查可以發現設定解析與連通性問題，卻不一定觸發模型閘道對工具 schema 的完整驗證。至少執行一次真實的唯讀、暫時性工作階段。

盲目複製官方模型元資料

上下文視窗、工具模式、圖片輸入、Web 搜尋與推理檔位都可能影響執行時期行為。複製只能作為產生 schema 的起點，不代表能力完全等同。

為已經支援的協定保留額外代理

如果目標端點已直接支援 Responses API，額外代理只會增加日誌、憑證、重試與故障定位層級。先驗證直連，再決定是否真的需要轉換層。

故障診斷矩陣

遇到問題時，先依錯誤所在的層級定位，不要同時修改 URL、Key、模型目錄與 Profile。

現象優先檢查不要先做什麼
/responses 回傳 401Key 是否有效、Authorization 格式重寫模型目錄
/responses 回傳 404base_url、/v1 與閘道實際路由增加重試次數
模型不存在model 字串與 OpenCode Go 目前模型清單切換 tool_mode
missing field models/models 與 Codex 目錄 schema判斷文字生成端點也不可用
Model metadata ... not foundmodel_catalog_json 路徑與 slug把 Key 寫進設定
missing field base_instructions自訂模型目錄是否使用完整 schema繼續手動撰寫更多猜測欄位
Unsupported custom tool: exectool_mode 與上游自訂工具支援反覆重新整理 Key
--profile only applies to runtime commands子指令是否支援 Profile根據管線最後一個退出碼宣稱成功
Profile 啟動後仍是另一個模型專案設定與 CLI 參數是否覆寫個人 Profile直接刪除所有 Codex 設定
doctor 通過但真實請求失敗請求 body、工具 schema、模型參數把 doctor 當成端到端測試

建議使用單一變數實驗：每次只調整一個欄位，並保留修改前後的完整錯誤。像這次的 tool_mode 問題，如果同時修改 feature flag、模型目錄與 Provider，很難建立可靠的因果關係。

從零重現的操作清單

如果要在另一台開發機重新設定，可以依下面的順序執行。

1. 確認版本與憑證

codex --version
jq -e \
  '.["opencode-go"].key | type == "string" and length > 0' \
  ~/.local/share/opencode/auth.json >/dev/null

2. 備份設定

cp ~/.codex/config.toml ~/.codex/config.toml.before-opencode-go

3. 用原始請求驗證 /responses

只傳送短文字，不附加工具。確認 HTTP 狀態、status、model 與 output_text。

4. 加入 Provider 與執行時期認證

先只設定 model_provider、base_url、wire_api 與認證，保留最少變數。

5. 用 fallback 元資料做第一次 Codex 請求

如果請求成功但出現模型元資料 warning，代表執行鏈路已經建立，再單獨處理目錄。

6. 從目前模型快取生成本機目錄

複製完整記錄，縮小上下文、輸入模態、搜尋與工具能力，並確保 tool_mode = null。

7. 分別建立兩個 Profile

DeepSeek Profile 指向 OpenCode Go；OpenAI Profile 指向 OpenAI 與原生模型快取。

8. 依序做靜態與真實驗證

codex debug models
codex doctor --summary --no-color
codex exec -p deepseek -s read-only --ephemeral "Reply exactly DEEPSEEK_OK."
codex exec -p openai -s read-only --ephemeral "Reply exactly OPENAI_OK."

9. 在隔離目錄驗證 apply_patch

不要把第一次工具測試直接放進重要儲存庫。確認檔案內容後清理暫時目錄。

10. 記錄版本並保留回滾點

Codex、閘道與模型能力都會變化。把測試日期、Codex 版本、模型 slug 與已驗證工具寫入文件；升級後重新執行相同的檢查。

目前已驗證與尚未推論的邊界

截至 2026-08-06，本次設定已經真實驗證：

  • OpenCode Go /v1/responses 的非串流最小請求。
  • Codex 原生 Responses 呼叫。
  • high 推理檔位的精確文字回應。
  • DeepSeek 與 OpenAI 兩個 CLI Profile。
  • DeepSeek 選擇並執行 apply_patch。
  • Codex 健康檢查、模型目錄解析與 Provider 連通性。

本文沒有把以下能力視為已經證明：

  • 100 萬上下文的極限輸入與自動壓縮邊界。
  • 圖片輸入、原始圖片細節與多模態輸出。
  • Web Search、MCP、Browser、Computer Use 等擴充工具。
  • exec 自訂工具與統一 PTY 執行協定。
  • 長時間 SSE 中斷恢復、平行工具呼叫與限流退避。
  • Codex 桌面版或雲端工作階段的自訂 Provider 切換。

這種邊界宣告不是保守措辭，而是避免把「API 能回傳一句話」誤寫成「所有 Codex 能力都與 OpenAI Provider 等同」。

回滾方式

如果需要完全還原先前的 Codex 預設設定：

cp ~/.codex/config.toml.before-opencode-go ~/.codex/config.toml

Profile 檔案是獨立覆寫層，不影響備份內容。不再需要時可以先移出 ~/.codex，確認 Codex 正常啟動後再刪除。

結論

這次串接真正困難的部分，不是把 model 改成 deepseek-v4-flash，而是確認整條鏈路的能力邊界：

  1. DeepSeek 與 OpenCode Go 端點確實接受 Responses API。
  2. Codex Provider 使用執行時期認證，不複製明文憑證。
  3. 自訂模型目錄補齊上下文與推理檔位。
  4. tool_mode 必須符合閘道支援的自訂工具協定。
  5. Profile 同時切換模型、Provider 與目錄。
  6. 原始 API、靜態診斷與原生 Codex 請求必須分別驗證。
  7. 真實 apply_patch 成功後，才證明最小編碼 Agent 鏈路成立。

最大的經驗不是某一段 TOML，而是排查順序：先驗證最小協定，再串接 Codex；先用 fallback 元資料證明主鏈路，再補模型目錄；靜態檢查之後，一定要執行真實工具任務。 這樣每一步只有一個主要變數，失敗時才能快速回到正確的層級。
