ENGINEERING NOTE · 2026年7月25日

JDK 17 服務從 3–4G 到可控：Spring Boot 容器記憶體最佳化實戰

從 Kubernetes、cgroup、JVM Heap 與 Native Memory 四層拆解 Spring Boot 記憶體，逐步調整 G1、堆上限、Metaspace、執行緒、訊息預取、glibc arena、JProfiler 與探針。

2026年7月25日 更新於 2026年8月6日 21 分鐘閱讀

{ }

本文來自一批 JDK 17 服務的容器記憶體治理。服務名稱、叢集、節點與業務資料均已泛化；範例參數是排查的起點，不是所有應用程式都能直接複製的標準答案。

有一段時間，我們對 Java 服務記憶體的處理方式相當粗糙：容器容易重啟，就把 -Xmx 和 Kubernetes memory limit 一起調大。結果是普通 Spring Boot 服務穩定占用 3–4 GiB，較重的服務接近 5 GiB，少數實例最後還是被殺掉。

實際排查後，我們發現這些現象至少包含兩類完全不同的問題：

  • 一個實例 -Xmx4g，實際堆使用約 3.5 GiB；執行一次堆檢查後，存活物件降到約 1.9 GiB，但 RSS 沒有立即下降。
  • 另一個實例堆只用約 280 MiB，Java 行程 RSS 卻超過 1.2 GiB，同時存在兩百多個執行緒與常駐的 native profiler。

前者主要是堆與物件分配壓力，後者主要是非堆、執行緒與 native 記憶體。只看 kubectl top，兩者都會被誤判為「Java 堆太大」。

第 0 步：先確認比較對象與證據窗口

如果問題是「同一服務的兩個 Pod 記憶體為什麼相差數倍」，第一步不是進入 JVM，而是確認它們是否真的來自同一份部署範本。

kubectl -n <namespace> get pod <pod-a> \
  -o jsonpath='{.metadata.ownerReferences[0].name}{"\n"}'

kubectl -n <namespace> get pod <pod-b> \
  -o jsonpath='{.metadata.ownerReferences[0].name}{"\n"}'

kubectl -n <namespace> get rs <replicaset> -o yaml

Pod 名稱中相同的 ReplicaSet hash 通常代表它們共用同一份 PodTemplateSpec，包括：

  • 映像與啟動指令。
  • JVM 參數與環境變數。
  • ConfigMap、Secret 與掛載。
  • requests、limits、探針與排程規則。

如果屬於同一個 ReplicaSet，就不應再把「兩個 Pod 的 JVM 參數不同」當成首要假設，應該轉向流量、快取、批次處理、連線池、執行緒數與 native 分配。

也要確認歷史證據是否還在。舊 Pod、舊 ReplicaSet 與 previous logs 可能已被滾動發布清理，Prometheus 的留存窗口也可能短於 Pod 離線時間。可以先查詢目標時間段：

max by (pod) (
  max_over_time(
    container_memory_working_set_bytes{
      namespace="<namespace>",
      pod=~"<application>-<revision>-.+",
      container!="",
      image!=""
    }[24h]
  )
)

如果目標時段沒有指標與日誌，應明確記錄：

可以排除模板差异，但现有证据不足以证明旧 Pod 的具体根因。

不要用新 Pod 的一張快照替舊 Pod 編造結論。此時正確做法是補齊下一次重現所需的 NMT、GC 日誌與監控，而不是直接宣布「記憶體洩漏」。

先建立正確的記憶體模型

flowchart TD
  A["Pod memory working set"] --> B["Java Heap"]
  A --> C["Metaspace 與 Class Space"]
  A --> D["執行緒堆疊"]
  A --> E["Direct / Mapped Buffer"]
  A --> F["JIT Code Cache 與 GC 結構"]
  A --> G["JNI、Profiler、glibc arena"]
  A --> H["共享函式庫與部分檔案頁"]

-Xmx 只限制 Java Heap。下面這個等式通常不成立：

容器内存 = Xmx

更接近實際的關係是：

容器内存 ≈ Heap committed + JVM native + 线程栈 + 第三方 native + 工作集中的文件页

因此，容器 limit 與 -Xmx 之間必須留出明確餘量。

第 1 步：確認到底是不是 OOM

先看退出原因，不要看到 Restart 就直接調堆：

kubectl -n <namespace> get pod <pod> \
  -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason}{"\n"}{.status.containerStatuses[0].lastState.terminated.exitCode}{"\n"}'

kubectl -n <namespace> describe pod <pod>
kubectl -n <namespace> logs <pod> --previous --tail=300

常見情況：

證據更可能的方向
OOMKilled、Exit Code 137容器超過 cgroup limit，或節點發生記憶體壓力
Java 日誌出現 OutOfMemoryError: Java heap spaceJava Heap 不足或物件無法釋放
Metaspace類別載入、動態代理或 Metaspace 上限問題
Exit Code 143通常是收到 SIGTERM，不等於 OOM
探針連續失敗後重啟應用程式阻塞、依賴逾時或 GC 停頓被探針放大

核心 OOMKill 可能來得太快，JVM 未必有機會產生 Heap Dump。所以沒有 Heap Dump，不能反推「不是記憶體問題」。

第 2 步：同時測量 Pod、行程與 JVM

Kubernetes 側：

kubectl top pod -n <namespace> <pod> --containers

kubectl -n <namespace> get pod <pod> \
  -o jsonpath='{.spec.containers[0].resources}{"\n"}'

容器側：

kubectl -n <namespace> exec <pod> -- sh -c '
  grep -E "VmRSS|VmSize|Threads" /proc/1/status
  test -f /sys/fs/cgroup/memory.current && cat /sys/fs/cgroup/memory.current
  test -f /sys/fs/cgroup/memory.stat && \
    grep -E "^(anon|file|kernel|sock) " /sys/fs/cgroup/memory.stat
'

JVM 側：

kubectl -n <namespace> exec <pod> -- jcmd 1 VM.version
kubectl -n <namespace> exec <pod> -- jcmd 1 VM.command_line
kubectl -n <namespace> exec <pod> -- jcmd 1 VM.flags
kubectl -n <namespace> exec <pod> -- jcmd 1 GC.heap_info

必須把採樣時間寫下來。啟動一分鐘、業務高峰與閒置一小時的資料不能直接橫向比較。

第 3 步：用 NMT 拆分 JVM Native Memory

啟動時增加：

-XX:NativeMemoryTracking=summary

注意它必須位於 -jar 之前：

java \
  -XX:NativeMemoryTracking=summary \
  -jar /app/application.jar

下面這種寫法不會生效，因為參數已經變成應用程式參數：

java -jar /app/application.jar -XX:NativeMemoryTracking=summary

啟動後建立基線並比較：

jcmd 1 VM.native_memory summary scale=MB
jcmd 1 VM.native_memory baseline

# 运行一段代表性业务流量后
jcmd 1 VM.native_memory summary.diff scale=MB

重點查看：

  • Java Heap
  • Class
  • Thread
  • Code
  • GC
  • Compiler
  • Internal

NMT 預設關閉，summary 和 detail 都有額外開銷；Oracle 文件給出的開銷參考約為 5%–10%。它也無法涵蓋所有第三方 native 分配，因此 NMT 總計小於 RSS 並不奇怪。Native Memory Tracking

第 4 步：取消「Xmx 等於容器上限」的設定

最危險的設定類似這樣：

容器 limit: 4Gi
-Xmx4g

Heap 一旦接近 4 GiB，Metaspace、執行緒堆疊、Direct Buffer、GC 資料結構與 native 函式庫就沒有空間了。最後更可能得到的是 cgroup OOMKill，而不是可分析的 Java Heap OOM。

本輪治理將普通 JDK 17 服務調整為按容器記憶體計算堆上限：

-Xms768m
-XX:MaxRAMPercentage=65.0
-XX:+UseG1GC

例如容器 limit 為 3 GiB 時，最大堆目標約為 1.95 GiB，剩餘約 1.05 GiB 給非堆與 native 記憶體。65% 只是經過目前服務驗證的起點；執行緒多、Netty Direct Buffer 多或 native 依賴重的服務還要繼續降低。

不要同時設定兩組互相競爭的上限：

-Xmx2g
-XX:MaxRAMPercentage=65.0

當明確的 -Xmx 存在時，百分比不再是你以為的主要控制手段。最終參數應使用 jcmd 1 VM.flags 驗證，而不是只看 YAML。

JDK 17 提供容器感知與百分比堆參數，準確含義可以在 JDK 17 java 命令文件 中核對。

第 5 步：保留 G1，但不要用 Full GC 美化監控

JDK 17 的服務繼續使用 G1：

-XX:+UseG1GC

一次現場排查中，Heap used 從約 3.5 GiB 降到約 1.9 GiB，但 RSS 沒有立刻跟著下降。這說明：

  1. 存活物件確實減少了。
  2. JVM 或分配器仍可能保留已提交的記憶體頁。
  3. 「GC 後 Heap used 下降」與「容器立刻歸還同等 RSS」不是同一件事。

同一個 ReplicaSet 的兩個 Pod，為什麼一個 1.8G、一個 1.2G

另一次排查中，兩個複本來自同一個 ReplicaSet，映像、JVM 參數、設定與 limit 完全一致：

指標Pod APod B
Pod working set約 1.86 GiB約 1.24 GiB
G1 committed Heap約 1.5 GiB約 768 MiB
當時 Heap used約 514 MiB約 212 MiB
重啟 / OOM00

GC 日誌顯示 Pod A 在業務高峰經歷了一輪較高的分配，G1 因此擴大 committed Heap。後續 mixed GC 逐步把存活物件降到約 442 MiB，繼續閒置後 Old 區進一步下降，Heap 也收縮回接近 Xms=768M；容器記憶體最終回落到約 1.27 GiB。

現場沒有看到：

  • OOMKilled。
  • Full GC 風暴。
  • Humongous Region 持續增長。
  • 重啟次數增加。
  • Old 區只增不減。

因此，這組證據更符合「短時分配抬高 committed Heap，G1 延遲收縮」，而不是記憶體洩漏。

正確的同窗採集方式：

kubectl top pod <pod-a> <pod-b> -n <namespace>

kubectl exec -n <namespace> <pod-a> -- jcmd 1 GC.heap_info
kubectl exec -n <namespace> <pod-b> -- jcmd 1 GC.heap_info

kubectl exec -n <namespace> <pod-a> -- \
  jcmd 1 VM.native_memory summary scale=MB
kubectl exec -n <namespace> <pod-b> -- \
  jcmd 1 VM.native_memory summary scale=MB

還要對齊同一時刻的 GC 日誌。只比較兩個 kubectl top 數字，無法知道差異來自 live objects、committed Heap 還是 native memory。

不要為了讓曲線下降就定時執行 System.gc()，也不要把很短的 G1PeriodicGCInterval 全域加給所有服務。週期 GC 會消耗 CPU，掩蓋真實的物件分配問題；只有明確驗證應用程式存在長時間閒置窗口時，才值得單獨評估。

如果 Git 中的最新 Deployment 已經刪除週期 GC，但執行中的 jcmd 1 VM.flags 仍看得到它，代表線上 Pod 還來自舊 spec。kubectl rollout restart 只按目前叢集 spec 重建，不會自動讀取 Git；必須先執行範本渲染與發布。

Oracle 對 G1 的首要建議仍是盡量使用預設策略，只設定合適的最大堆，再根據 GC 日誌調整。Garbage-First Garbage Collector Tuning

第 6 步：給 Metaspace 上限，但不要拍腦袋壓得過低

目前範本的起點：

-XX:MetaspaceSize=256m
-XX:MaxMetaspaceSize=512m

這樣能防止異常類別載入無限擠占容器記憶體，但 MaxMetaspaceSize 太小會直接產生：

java.lang.OutOfMemoryError: Metaspace

調整前後應比較：

jcmd 1 VM.native_memory summary scale=MB
jcmd 1 GC.class_histogram

如果類別數量持續增長，先查動態代理、指令碼引擎、熱部署 ClassLoader 與重複產生的類別，不要只繼續提高上限。

第 7 步：關閉常駐 Profiler

診斷工具本身也會占記憶體。過去範本預設載入 JProfiler native agent，即使沒有人在連線，agent、採樣結構與額外事件仍然常駐在行程中。

改成預設關閉：

env:
  - name: JPROFILER_ENABLED
    value: "false"

啟動指令碼只在排查時追加：

set -- java

if [ "${JPROFILER_ENABLED:-false}" = "true" ]; then
  set -- "$@" \
    -agentpath:/opt/jprofiler/bin/linux-x64/libjprofilerti.so=port=8849,nowait
fi

分析結束後把開關恢復為 false 並滾動發布。Profiler 應該是一種短時診斷能力，不應成為每個生產 Pod 的預設組成部分。

第 8 步：處理執行緒堆疊與訊息堆積

一次輕量服務的現場資料是：Heap used 約 280 MiB，RSS 約 1.2 GiB，執行緒數超過 200。此時繼續縮小 Heap 收益很有限，應先查執行緒來源：

jcmd 1 Thread.print > /tmp/threads.txt
grep '^"' /tmp/threads.txt | wc -l

重點盤點：

  • Web 容器工作執行緒。
  • 資料庫連線池維護執行緒。
  • Kafka、RabbitMQ 與 Nacos 用戶端執行緒。
  • XXL-JOB、定時任務與自建執行緒池。
  • ForkJoinPool 與非同步執行器。

不建議先全域設定很小的 -Xss。深層呼叫、複雜表達式或大堆疊幀可能因此觸發 StackOverflowError。更穩妥的順序是：

  1. 刪除重複的執行緒池。
  2. 根據容器 CPU 限制執行緒池最大值。
  3. 收斂訊息消費並發與預取。
  4. 最後再壓測 -Xss。

訊息消費服務可以從保守設定開始：

env:
  - name: SPRING_RABBITMQ_LISTENER_SIMPLE_CONCURRENCY
    value: "1"
  - name: SPRING_RABBITMQ_LISTENER_SIMPLE_MAX_CONCURRENCY
    value: "3"
  - name: SPRING_RABBITMQ_LISTENER_SIMPLE_PREFETCH
    value: "10"

這不是單純節省執行緒。prefetch 太大時，大量尚未確認的訊息及其業務物件會同時留在 Heap 中。修改後必須驗證消費延遲與積壓，不能只看記憶體下降。

第 9 步：限制 glibc arena

在 Linux glibc 環境中，多執行緒 native 分配可能產生多個 malloc arena。業務物件釋放後，閒置的 arena 不一定立即歸還給作業系統，表現為 Heap 已下降、RSS 仍偏高。

目前使用的保守起點：

env:
  - name: MALLOC_ARENA_MAX
    value: "4"

它不是 JVM 參數，也不保證對 Alpine/musl 或其他分配器有效。值太小可能增加多執行緒分配的鎖競爭，因此要同時看：

  • CPU 使用率。
  • 請求 P95/P99。
  • native 分配熱點。
  • RSS 是否真的改善。

第 10 步：讓下一次 OOM 留下證據

建議保留：

-XX:+HeapDumpOnOutOfMemoryError
-XX:+ExitOnOutOfMemoryError
-XX:HeapDumpPath=/data/dumps/<app>/<pod>/heap.hprof
-Xlog:gc*,safepoint:file=/data/logs/gc-%t.log:time,uptime,level,tags:filecount=10,filesize=20M

Heap Dump 路徑必須：

  • 可寫。
  • 有足夠空間。
  • 每個 Pod 唯一，避免複本互相覆寫。
  • 有清理與下載流程，避免把共用磁碟寫滿。

GC 日誌回答「什麼時候回收、回收前後多少、暫停多久」；Heap Dump 回答「哪些物件占用堆」。兩者不能互相取代。

第 11 步：Kubernetes 資源與 JVM 參數一起計算

一個普通服務的範例起點：

resources:
  requests:
    cpu: 250m
    memory: 1536Mi
  limits:
    memory: 3Gi

搭配：

-Xms768m
-XX:MaxRAMPercentage=65.0

計算時要回答三個問題：

  1. 穩態 P95 記憶體是多少，request 能否涵蓋正常運行？
  2. 啟動與批次峰值是多少，limit 是否保留安全餘量？
  3. 最大堆之外，Thread、Class、Code、GC、Direct 與 native 共需要多少？

重型服務不能套用普通服務的 request/limit。它們應單獨建立基線，並考慮滾動發布時新舊 Pod 同時存在的節點容量。

第 12 步：探針不要把短時壅塞變成重啟風暴

記憶體或依賴壓力升高時，健康檢查介面也可能變慢。如果 liveness 只允許幾十秒，Kubernetes 會在應用程式最忙時不斷重啟它，形成：

启动分配高峰 → 探针超时 → 重启 → 再次启动分配高峰

可以從下面的職責拆分開始：

startupProbe:
  httpGet:
    path: /actuator/health/liveness
    port: http
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 30

readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: http
  periodSeconds: 5
  timeoutSeconds: 3
  failureThreshold: 2

livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: http
  periodSeconds: 10
  timeoutSeconds: 5
  failureThreshold: 12
  • startup 負責給慢啟動足夠的窗口。
  • readiness 先快速摘除流量。
  • liveness 只處理真正無法復原的行程狀態。

放寬探針不能修復記憶體洩漏，但能避免一次短時 GC、資料庫抖動或依賴逾時被放大成叢集級重啟。

一份可複用的 JDK 17 啟動基線

#!/bin/sh
set -eu

DUMP_DIR="/data/dumps/${APP_NAME}/${HOSTNAME}"
mkdir -p "$DUMP_DIR" /data/logs

set -- java \
  -XX:+UseContainerSupport \
  -Xms768m \
  -XX:MaxRAMPercentage=65.0 \
  -XX:+UseG1GC \
  -XX:MetaspaceSize=256m \
  -XX:MaxMetaspaceSize=512m \
  -XX:+HeapDumpOnOutOfMemoryError \
  -XX:+ExitOnOutOfMemoryError \
  -XX:HeapDumpPath="$DUMP_DIR/heap.hprof" \
  -Xlog:gc*,safepoint:file=/data/logs/gc-%t.log:time,uptime,level,tags:filecount=10,filesize=20M

if [ "${NMT_ENABLED:-false}" = "true" ]; then
  set -- "$@" -XX:NativeMemoryTracking=summary
fi

if [ "${JPROFILER_ENABLED:-false}" = "true" ]; then
  set -- "$@" \
    -agentpath:/opt/jprofiler/bin/linux-x64/libjprofilerti.so=port=8849,nowait
fi

set -- "$@" -jar /app/application.jar
exec "$@"

上線後必須驗證真實指令：

jcmd 1 VM.command_line
jcmd 1 VM.flags
jcmd 1 GC.heap_info

推薦的分階段上線順序

不要一次修改十幾個參數，否則記憶體下降後也不知道是誰起作用。

階段 A：只增加觀測

  • 記錄 Pod working set、RSS、Heap、執行緒數。
  • 增加輪轉 GC 日誌。
  • 在一個複本上短時啟用 NMT。

階段 B：移除診斷常駐開銷

  • 預設關閉 JProfiler。
  • 對 glibc 映像試行 MALLOC_ARENA_MAX=4。
  • 比較 CPU 與延遲，確認沒有明顯回退。

階段 C：重算堆與容器餘量

  • 從固定 -Xmx4g 改為經過計算的百分比或更小的明確 -Xmx。
  • 保留至少 30%–35% 給非堆與 native。
  • 分普通服務與重型服務兩套基線。

階段 D：治理執行緒與訊息在途量

  • 收斂執行緒池。
  • 降低訊息並發與 prefetch。
  • 驗證積壓、吞吐量與業務延遲。

階段 E：校準資源與探針

  • 依穩態與峰值調整 request/limit。
  • 確保滾動發布時節點能容納臨時複本。
  • readiness 快速摘流量，liveness 避免誤殺。

至少要跨過一個真實業務高峰再下結論。記憶體從 4 GiB 降到 1.5 GiB，如果代價是頻繁 Full GC 或訊息積壓，並不是成功的優化。

最終結論

這輪 JDK 17 治理真正有效的不是某一個「神奇參數」，而是把以下邊界同時收緊：

  1. Heap 不再吃滿容器，給 native 記憶體留出明確空間。
  2. G1 保持簡單，先解決物件分配，而不是定時強制 GC。
  3. JProfiler 改為按需啟用。
  4. 用 NMT、RSS 與 cgroup 資料區分 Heap 與 Native。
  5. 收斂執行緒、訊息並發與 prefetch。
  6. 限制 glibc arena，並用延遲與 CPU 驗證副作用。
  7. 保留 GC 日誌、Heap Dump 與退出原因，讓下次故障可以復盤。
  8. 用合理探針避免短時壅塞演變成重啟風暴。

從「所有服務都給 4G」轉向「每類服務都有可解釋的記憶體預算」，才是這次最佳化最重要的結果。
