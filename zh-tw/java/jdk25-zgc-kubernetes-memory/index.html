Spring Boot 升級 JDK 25 後記憶體從 3.5G 降到 900M：ZGC 實戰分析

說明 Kubernetes 看到的 Java 容器記憶體包含哪些內容，並逐步使用 ZGC、SoftMaxHeapSize、ZUncommitDelay 與 Native Memory Tracking 分析與最佳化 Spring Boot 服務。

2026年7月26日 10 分鐘閱讀

{ }

本文來自一次真實的最佳化案例。服務名稱、映像、節點、容量與業務資料均已泛化。參數只能作為分析方法，不能直接複製到所有 Java 服務。

某個 Spring Boot 服務升級到 JDK 25 後，剛啟動時 Kubernetes 看到約 3.5 GiB，穩定後逐步下降到不足 1 GiB。這個現象不是「JVM 把業務資料清空了」，也不能只用「ZGC 比 G1 更省記憶體」來解釋。

關鍵是先弄清楚 kubectl top 看到的是什麼，以及 JVM 的「已使用堆、已提交堆、行程常駐記憶體、容器工作集」為什麼不相等。

Java 容器記憶體由什麼組成

flowchart TD
  A["Container Memory"] --> B["Java Heap"]
  A --> C["Metaspace / Compressed Class Space"]
  A --> D["Thread Stacks"]
  A --> E["Direct / Mapped Buffers"]
  A --> F["JIT Code Cache"]
  A --> G["GC Native Structures"]
  A --> H["Shared Libraries / Page Cache"]

-Xmx 只限制 Java Heap 的上限，不涵蓋其他區域。一個以 -Xmx2g 啟動的行程，容器記憶體超過 2 GiB 完全正常。

第 1 步：確認 Pod 裡到底是哪個 JDK

不要用基礎映像名稱猜測供應商：

kubectl -n <namespace> exec <pod> -- java -version

kubectl -n <namespace> exec <pod> -- \
  java -XshowSettings:properties -version 2>&1 \
  | grep -E 'java.vendor|java.version|java.home|java.vm.name'

OpenJDK 是實作與生態；Oracle JDK、Eclipse Temurin、Amazon Corretto、Microsoft Build of OpenJDK 等是不同發行版本。選擇時注意：

  • 安全更新週期。
  • 容器與 CPU 架構支援。
  • 供應商支援與授權。
  • 是否通過專案的完整回歸測試。

換成 Oracle JDK 不會自動解決應用程式的記憶體問題。

第 2 步：確認所有 JVM 參數來源

kubectl -n <namespace> exec <pod> -- sh -c '
  printf "JAVA_TOOL_OPTIONS=%s\n" "$JAVA_TOOL_OPTIONS"
  printf "JDK_JAVA_OPTIONS=%s\n" "$JDK_JAVA_OPTIONS"
  printf "JAVA_OPTS=%s\n" "$JAVA_OPTS"
'

再查看行程：

kubectl -n <namespace> exec <pod> -- jcmd 1 VM.command_line
kubectl -n <namespace> exec <pod> -- jcmd 1 VM.flags

Picked up JAVA_TOOL_OPTIONS 和 Picked up JDK_JAVA_OPTIONS 表示參數是由環境注入的。若同一個 Deployment 同時定義兩者，要確認沒有重複或衝突。

全域範本尤其危險：某個只有新 JDK 支援的參數，注入仍在執行舊 JDK 的服務後，會直接出現：

Unrecognized option
Could not create the Java Virtual Machine

第 3 步：分別檢視 Kubernetes 與 JVM

Kubernetes 側：

kubectl top pod -n <namespace> <pod> --containers
kubectl -n <namespace> get pod <pod> \
  -o jsonpath='{.spec.containers[0].resources}{"\n"}'

容器內：

kubectl -n <namespace> exec <pod> -- sh -c '
  grep -E "VmRSS|VmSize|Threads" /proc/1/status
  test -f /sys/fs/cgroup/memory.current && cat /sys/fs/cgroup/memory.current
'

JVM 側：

kubectl -n <namespace> exec <pod> -- jcmd 1 GC.heap_info
kubectl -n <namespace> exec <pod> -- jcmd 1 VM.native_memory summary

Native Memory Tracking 需要啟動參數：

-XX:NativeMemoryTracking=summary

NMT 有額外開銷，適合用於診斷與基線觀測；是否長期啟用應經過壓測。

第 4 步：理解 SoftMaxHeapSize

範例：

-Xmx2g
-XX:SoftMaxHeapSize=1g

Oracle JDK 25 的 ZGC 文件說明，Soft Max 是 GC 的軟性目標，不是硬上限。ZGC 會盡量把堆維持在 1 GiB 附近，但在壓力下仍可暫時成長到 -Xmx2g。The Z Garbage Collector

因此它適合表達：

平时尽量少占内存
高峰允许使用预留上限

不能用它取代容器的 memory limit，也不能保證 RSS 一定小於 1 GiB。

第 5 步：理解 ZUncommitDelay

-XX:ZUncommitDelay=120

表示 ZGC 發現堆記憶體長期閒置後，相關記憶體頁至少空閒約 120 秒才有機會歸還作業系統。JDK 25 的預設值是 300 秒。

設為 30 秒可能讓監控數字下降更快，但負載頻繁波動時也可能反覆 commit/uncommit。建議先觀察業務波峰間隔：

負載型態初始建議
長時間低負載，偶發高峰120–300 秒
持續穩定高負載維持預設，收益有限
每分鐘快速波動避免設定過短，先壓測

「歸還更快」不一定代表「吞吐更好」。

第 6 步：一份可驗證的 ZGC 起點

-XX:+UseZGC
-Xms512m
-Xmx2g
-XX:SoftMaxHeapSize=1g
-XX:ZUncommitDelay=120
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/data/java/dumps

容器資源範例：

resources:
  requests:
    cpu: "1"
    memory: 1536Mi
  limits:
    cpu: "2"
    memory: 3Gi

必須為非堆記憶體預留餘量。當 JVM 堆上限、Direct Memory、執行緒堆疊、Metaspace 與 native 函式庫的總和逼近容器 limit 時，程序會被核心 OOMKilled，JVM 未必有機會產生 Heap Dump。

第 7 步：解釋為什麼先高後低

啟動階段會發生：

  • 載入大量 Class 與 Bean。
  • JIT 編譯熱點程式碼。
  • 建立資料庫、Nacos、Kafka 等客戶端的緩衝區。
  • 解析設定、掃描註解、建立執行緒。
  • 堆為了啟動吞吐暫時擴張。

啟動完成後：

  • 短命物件被回收。
  • ZGC 根據 Soft Max 調整堆目標。
  • 空閒頁面超過 ZUncommitDelay 後逐步歸還 OS。

因此從 3.5 GiB 降到 900 MiB，可能包含堆收縮，也可能包含檔案頁面與容器工作集的變化。只有同時觀察 NMT、Heap 與 cgroup，才能拆解出真正的原因。

第 8 步：為什麼本機仍然是 3.5G

逐項比較：

JDK 发行版和准确版本
GC 参数
JAVA_TOOL_OPTIONS / JDK_JAVA_OPTIONS
容器 limit
激活的 Spring Profile
是否连接真实 Nacos / Kafka / 数据库
线程数和连接池
流量及定时任务
观测时间点

在本機直接執行可能沒有 cgroup limit，JVM 會看到更大的主機記憶體；IDE 也可能覆寫 VM Options。先執行：

jcmd <pid> VM.command_line
jcmd <pid> VM.flags
jcmd <pid> GC.heap_info

不要比較「本機啟動一分鐘」和「線上穩定一小時」的數字。

第 9 步：處理 JDK 25 警告

Unsafe terminally deprecated

通常來自 Netty、gRPC、Nacos Client 等相依套件呼叫 sun.misc.Unsafe。處理順序：

  1. 用依賴樹找到確切的 jar。
  2. 查詢上游是否已有相容版本。
  3. 先升級依賴並做回歸。
  4. 不要自行屏蔽所有警告。

restricted native access

--enable-native-access=ALL-UNNAMED

只有在執行時期確認支援該參數、依賴確實需要、且安全審查接受時才加入。不能放進面向混合 JDK 版本的全域 Deployment 範本。

add-opens / add-exports

這類參數是相容舊版反射或內部 API 的過渡措施。每一項都應記錄「哪個依賴需要它、升級到什麼版本後可以刪除」。

第 10 步：壓測與驗收

至少對比兩組相同流量的設定：

基线：原 JDK + 原 GC
候选：JDK 25 + ZGC 参数

採集：

  • 啟動耗時與 Ready 時間。
  • P50/P95/P99 延遲。
  • 吞吐與錯誤率。
  • Heap used/committed。
  • RSS、cgroup memory、Direct Memory。
  • GC pause、allocation rate。
  • CPU 與上下文切換。
  • 一次完整的批次處理或業務高峰。

觀察至少要涵蓋一個真實負載週期，不能只看啟動後的十分鐘。

如何判斷 900M 是否健康

900 MiB 不是天然的好消息。還要確認：

  • 沒有因頻繁 GC 導致 CPU 上升。
  • P99 沒有變差。
  • Heap 在高峰時有足夠餘量。
  • Direct Buffer、執行緒與 Metaspace 沒有持續增長。
  • 沒有 OOMKilled 或容器 memory pressure。
  • 批次處理與訊息消費吞吐正常。

完成定義

  • 執行時期 JDK、供應商與 JVM 參數可重複確認。
  • kubectl top、cgroup、Heap、NMT 四層資料能夠對應。
  • Soft Max 與 Xmx 的關係已在高峰驗證。
  • ZUncommitDelay 涵蓋真實負載週期，且不產生明顯抖動。
  • 容器 limit 為非堆預留足夠空間。
  • 所有相容參數都有來源與移除條件。
  • 最佳化後延遲、吞吐與穩定性不退化。

ZGC 的價值不是讓行程「越用越少」，而是在延遲目標允許的範圍內，更主動地適應負載，並歸還長期不使用的堆記憶體。
