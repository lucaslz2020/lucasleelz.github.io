Spring Boot 從 3.1.7 升級到 3.5.13：三個編譯通過後才暴露的問題

復盤一次 Spring Boot 3.1.7 到 3.5.13、Java 17 到 Java 25 的升級，定位 Spring Batch Job 重名、TaskExecutor 注入歧義與 MongoDB 4.2 健康檢查不相容。

2026年8月1日 12 分鐘閱讀

{ }

本文來自一次真實升級。服務名稱、專案座標、Pod、節點、映像、命名空間與組織資訊均已去敏或泛化。本文聚焦升級排查方法，請勿未經驗證就將設定或修復程式碼複製到其他服務。

最近將兩個 Spring Boot 服務從 3.1.7 升級到 3.5.13，同時把執行時期從 Java 17 切換到 Java 25。Maven 編譯與打包均能通過，但部署到測試 Kubernetes 叢集後，兩個服務先後出現啟動失敗、完整健康檢查異常。

這次升級最值得記錄的地方在於：問題都不在業務程式碼的語法層面，而在框架預設行為發生變化。以下按實際排查順序整理。

本文負責復盤已經完成的 3.1.7 → 3.5.13 升級。下一篇從 Spring Boot 3.5.13 升級到 4.1只討論下一階段新增的相容邊界，不再重複本文的通用啟動、健康檢查與中介軟體驗收流程。

先建立升級判斷鏈

flowchart LR
  A["升級 Spring Boot 與 JDK"] --> B["以目標 JDK 編譯與打包"]
  B --> C["新 Pod 啟動日誌"]
  C --> D["完整 /actuator/health"]
  D --> E["中介軟體指令與協定驗證"]
  E --> F["滾動發布與 Endpoint 切換"]

升級失敗時，不能從「報錯日誌裡看見了哪個元件」直接跳到根因。先區分故障發生在 Bean 建立、框架初始化、健康檢查，還是業務請求，再為每一層補充獨立證據。

升級範圍與驗收邊界

父 POM 的 Spring Boot 版本從 3.1.7 升級到 3.5.13，JDK 從 17 升級到 25。

升級前先確認兩件事：

  1. CI、容器基礎映像與本機 Maven 使用的是同一代 JDK；
  2. 不能只以「編譯通過」為驗收標準，至少要驗證應用程式啟動、完整 Actuator 健康檢查與關鍵中介軟體連線。

本次三個問題都屬於第二類：它們不阻擋編譯，卻會在新複本啟動或實際探測時暴露。

問題一：Spring Batch 的 Job 名稱重複，應用程式無法啟動

現象：新複本在註冊 Job 時失敗

其中一個服務啟動時拋出類似異常：

DuplicateJobException: A job configuration with this name [initPriceJob] was already registered

程式碼中兩個不同的 @Bean 方法分別宣告了 Job，但其中一個 JobBuilder 的內部名稱仍然是 initPriceJob。

@Bean
public Job productionInitPriceJob(...) {
    return new JobBuilder("initPriceJob", jobRepository)
        // ...
        .build();
}

證據與根因：Bean 名稱並不等於 Batch Job 名稱

Spring Batch 升級後，預設設定會在容器初始化階段收集所有 Job Bean 並註冊到 JobRegistry。因此，過去未被立即暴露的「內部 Job 名稱重複」問題，在新版本啟動階段變成了確定性失敗。

這裡要區分兩個名稱：

  • Spring Bean 名稱：例如 productionInitPriceJob；
  • Spring Batch Job 名稱：new JobBuilder("...") 中傳入的名稱。

真正參與 JobRegistry 去重的是後者。

修復：讓 JobBuilder 名稱唯一

讓 JobBuilder 內部名稱與業務 Job 保持唯一：

return new JobBuilder("productionInitPriceJob", jobRepository)
    // ...
    .build();

驗證與經驗

升級 Spring Batch 時，建議對所有 new JobBuilder(...) 做一次全域掃描，檢查字串名稱是否重複，而不是只檢查 @Bean 方法名稱。

問題二：TaskExecutor 從「按名稱注入」變成「兩個候選 Bean」

現象：兩個候選 Bean 導致注入失敗

另一個服務啟動失敗：

Parameter 0 of ... required a single bean, but 2 were found:
 - applicationTaskExecutor
 - taskScheduler

原始程式碼是欄位注入：

@Autowired
private TaskExecutor taskExecutor;

服務同時啟用了非同步與定時任務。升級後，容器中既存在 applicationTaskExecutor，也存在 taskScheduler；兩者都可以匹配 TaskExecutor，Spring 無法再猜測應該注入哪一個。

證據與根因：過去的隱式名稱匹配不再成立

在舊版自動設定中，預設非同步執行器還相容地暴露為 taskExecutor。當欄位名稱恰好與這個別名一致時，Spring 可以利用名稱匹配完成注入。

新版自動設定保留了 applicationTaskExecutor，但不再以同樣方式提供 taskExecutor 別名；同時啟用排程後，taskScheduler 也成為 TaskExecutor 的候選，原本依賴欄位名稱的隱式行為隨之失效。

修復：把執行緒池的選擇寫進程式碼

明確依賴的是應用程式的非同步執行緒池：

@Autowired
@Qualifier("applicationTaskExecutor")
private TaskExecutor taskExecutor;

如果專案中存在多個相同類型的注入點，要全部搜尋，例如：

rg 'TaskExecutor taskExecutor' src/main/java

驗證與經驗

不要讓業務程式碼依賴 Spring Boot 自動設定 Bean 的歷史別名。對於執行緒池、資料來源、快取管理器這類常見的多實例類型，應使用 @Qualifier，或改成建構子注入並在參數上標註限定名稱。

問題三：MongoDB 看似「連不上」，實際是健康檢查指令不相容

現象：MongoDB 看似「連不上」

應用程式啟動後，日誌持續出現：

MongoDB health check failed
Command failed with error 59 (CommandNotFound):
no such command: 'hello'

第一個反應很容易是 DNS、Service、帳號密碼或網路策略問題。但在叢集內驗證後發現：

db.adminCommand({ ping: 1 });
// { "ok" : 1 }

db.adminCommand({ isMaster: 1 });
// { "ismaster" : true, ..., "ok" : 1 }

db.adminCommand({ hello: 1 });
// no such command: 'hello'

測試環境的 MongoDB 是 4.2.8；Mongo Java Driver 本身已經成功建立連線。失敗發生在完整 /actuator/health 呼叫預設 MongoHealthIndicator 時。

證據與根因：失敗的是 Actuator 指令，不是 TCP 連線

Spring Boot 3.1 的 Mongo 健康檢查執行的是：

mongoTemplate.executeCommand("{ isMaster: 1 }");

Spring Boot 3.5 改為：

mongoTemplate.executeCommand("{ hello: 1 }");

MongoDB 4.2 不認識 hello 指令，所以健康檢查為 DOWN。這裡的重點是：健康檢查失敗不等於應用程式無法建立 Mongo 連線。先用 ping、驅動程式連線日誌與業務讀寫驗證，才能判斷是協定、驗證還是網路問題。

修復：保留真實檢查，覆寫不相容的預設指令

不建議為了讓健康檢查變綠，直接關閉 Mongo 健康檢查：

management.health.mongo.enabled=false

這樣會失去真實的 Mongo 可用性訊號。

本次採用的是保留健康檢查語意、覆寫預設貢獻者的方式：以相同 Bean 名稱提供一個相容 MongoDB 4.2 的檢查實作。

@Configuration(proxyBeanMethods = false)
public class MongoHealthConfiguration {

    @Bean(name = "mongoHealthContributor")
    public HealthIndicator mongoHealthContributor(MongoTemplate mongoTemplate) {
        return new AbstractHealthIndicator("MongoDB health check failed") {
            @Override
            protected void doHealthCheck(Health.Builder builder) throws Exception {
                Document result = mongoTemplate.executeCommand("{ isMaster: 1 }");
                builder.up().withDetail("maxWireVersion", result.getInteger("maxWireVersion"));
            }
        };
    }
}

Spring Boot 的自動設定發現名為 mongoHealthContributor 的 Bean 後會退讓。最終 /actuator/health 仍會真實檢查 Mongo，且能相容本機 4.2 實例。

驗證與經驗

升級框架時，Actuator 也屬於執行時期相容面。特別是資料庫、訊息佇列、註冊中心的健康檢查指令，可能比應用程式業務程式碼更早碰到舊伺服器端的相容性問題。

長期方案仍然是規劃 MongoDB 伺服器端升級；應用程式側的相容實作適合在測試環境或遷移過渡期使用。

第 4 步：把驗證寫成升級驗收清單

僅執行 mvn package 不足以證明升級成功。對於 Spring Boot 大版本或跨多個小版本的升級，建議按下面順序驗收：

  1. 使用目標 JDK 執行編譯與打包；
  2. 在本機或測試環境啟動新複本，確認沒有 Bean 注入、自動設定或 Job 註冊異常；
  3. 請求完整 /actuator/health，不要只看 Kubernetes 的 liveness/readiness；
  4. 核驗 DB、Redis、RabbitMQ、MongoDB、Nacos 等關鍵元件均為 UP；
  5. 對 Job 名稱、執行緒池注入、序列化設定與中介軟體協定指令做針對性回歸；
  6. 滾動發布後確認新 Pod Ready、Endpoint 已切換、舊 Pod 正常退出。

總結：把原本隱含的框架契約顯式化

這次從 Spring Boot 3.1.7 到 3.5.13 的升級，沒有遇到傳統意義上的 API 編譯錯誤，卻暴露了三類更隱晦的問題：

類型根因修復原則
Spring Batch新版啟動時嚴格註冊全部 Job，暴露內部名稱重複保證 JobBuilder 名稱全域唯一
非同步執行緒池自動設定 Bean 別名變化，出現多個 TaskExecutor 候選顯式 @Qualifier，不依賴欄位名稱匹配
Mongo 健康檢查預設指令從 isMaster 改為 hello，舊版 Mongo 不支援覆寫健康檢查並保留真實連通性檢測

框架升級的核心不是「把版本號改上去」，而是辨識並驗證那些原先依賴預設行為、卻從未被顯式寫進業務程式碼的契約。

如果升級後的問題出現在容器目錄、廢棄屬性、commons-logging、Nacos Logback 或選用 JDBC 驅動程式，統一參見Spring Boot 3 容器啟動異常復盤。
