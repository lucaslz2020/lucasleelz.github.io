ENGINEERING NOTE · 2026年8月2日

從 Spring Boot 3.5.13 升級到 4.1：先分清已完成事項與真正的風險

以 JDK 25、Nacos 3.1.2 與標準資料存取為基線，梳理 Spring Boot 3.5.13 升級到 4.1 的依賴邊界、實施順序與驗收清單。

lucaslz作者
2026年8月2日 12 分鐘閱讀
#Java #Spring Boot #Spring Cloud #Nacos #Kubernetes
{ }

Spring Boot 4.1 不是一次普通的依賴升級。它以 Spring Framework 7、Jakarta EE 11 與 Servlet 6.1 為基礎，周邊的 Spring Cloud、Nacos Client、Web 容器、JSON、資料存取與自研 starter 都會一起跨大版本。

升級評估最容易犯的錯誤，是把已經解決的問題重新列為風險。本文記錄一次實際升級前的梳理方法：起點已經是 Spring Boot 3.5.13、JDK 25、Nacos Server 3.1.2，歷史的客製查詢擴充也已經移除。於是評估的重點不再是 Boot 3.1 或 Nacos 2 的歷史相容，而是 3.5 到 4.1 之間真正的斷點。

上一篇Spring Boot 從 3.1.7 升級到 3.5.13已經給出編譯、Pod 啟動、完整 Actuator 健康檢查與中介軟體驗證方法。本文只保留 Boot 4 新增的相容風險，避免把同一份通用清單再寫一遍。

本文討論的是升級路線與驗證邊界，不代表把版本號改為 4.1 後即可直接上線。

脫敏說明：文中不包含專案名稱、服務名稱、儲存庫路徑、網域、叢集資訊、命名空間、Data ID、帳號或真實業務資料；所有設定片段皆為佔位範例。

先固定基線

先在變更單中寫清楚目前的狀態，避免後續討論混入過期資訊：

項目目前狀態本次是否需要處理
Spring Boot3.5.13升級到 4.1
JDK25保持，不需要回退
Nacos Server3.1.2保持，不遷移資料庫、不重建設定
查詢條件擴充歷史客製能力已移除不需要移植舊擴充
複雜查詢已改為明確的 SQL保持 Repository 邊界並回歸結果

Nacos Server 已升級到 3.1.2，只代表伺服器、資料庫與設定資料可以繼續使用；它不能自動證明某個 Spring Cloud Alibaba Client 已相容 Spring Boot 4.1。Server 與 Client 是兩條獨立的相容鏈。

第一個硬邊界：Spring Cloud Alibaba 對 4.1 的支援

Spring Cloud 官方已經說明，2025.1.2 開始支援 Spring Boot 4.1.x。因此 Boot 4.1 的 Spring Cloud 目標版本應是：

<spring-cloud.version>2025.1.2</spring-cloud.version>

但 Spring Cloud Alibaba 的官方相容表目前寫的是：

Spring Cloud Alibaba 2025.1.0.0
Spring Cloud 2025.1.0
Spring Boot 4.0.0

並將該分支描述為適配 Spring Boot 4.0.x。4.0.x 不是 4.1.x 的泛稱，不能據此宣稱 2025.1.0.0 已獲得 Boot 4.1 的官方支援。

這不等於組合一定無法執行，而是要區分兩種結論：

  • 官方支援：相容矩陣明確列出對應版本。
  • 本機驗證可用：透過依賴收斂、啟動、註冊、設定讀取與業務回歸得到的專案結論。

在 Alibaba 發布明確的 Boot 4.1 適配版本前，若要直接推進 Boot 4.1，應把下面的組合當作驗證對象，而不是預設為生產承諾：

Spring Boot 4.1.x
Spring Cloud 2025.1.2
Spring Cloud Alibaba 2025.1.x
Nacos Server 3.1.2

官方依據：Spring Cloud 版本相容表、Spring Cloud Alibaba 2025.x 版本說明。

Nacos 不遷移資料，但應用程式的設定載入方式要遷移

Spring Cloud Alibaba 2025.x 不再支援 Spring Cloud Bootstrap。應用程式若仍依賴：

bootstrap.yml
spring.cloud.bootstrap.enabled

就要改為 Spring Boot Config Data 方式，例如：

spring:
  config:
    import:
      - optional:nacos:<data-id>?group=<group>

具體 Data ID 是否拆分、Group、Namespace、使用者名稱與位址，依目標環境定義即可，且不應寫入公開文件；改變的是「應用程式在啟動階段如何讀取設定」，不是 Nacos 中儲存的資料格式。

遷移完必須驗證兩個方向：

  1. 啟動時能載入必填設定，例如 Feign URL、資料來源、Redis、訊息佇列位址。
  2. 執行中的設定重新整理、服務註冊與執行個體探索仍正常。

Boot 4 本身帶來的主要變化

1. Undertow 不能再作為嵌入式容器

Boot 4 的 Servlet 6.1 基線與 Undertow 不相容，官方已移除 Undertow starter 與嵌入式 Undertow 支援。若最終依賴樹使用 Undertow，需要切換到 Tomcat 11 或 Jetty 12，並刪除 server.undertow.* 設定。

不要僅憑一份共用設定就認定所有服務都需要改容器；應先確認每個服務的最終依賴樹與實際啟動日誌。

2. Boot 模組與 starter 重新拆分

Boot 4 將許多大型 jar 拆成更細的模組。自研 starter、直接依賴 Boot 內部類別、手寫自動設定的模組，尤其容易在編譯期暴露問題。

首輪可使用 spring-boot-starter-classic 與 spring-boot-starter-test-classic 取得接近 Boot 3 的完整 classpath，先恢復編譯、啟動與測試；穩定後再依實際功能替換成精確的 starter。不要讓同一個自研 starter 同時承諾 Boot 3 與 Boot 4 的二進位相容，應建立獨立的 Boot 4 版本線。

3. Jackson 3 是方向，不應與框架升級綁在一起冒險

Boot 4 預設偏向 Jackson 3，而 Jackson 3 的座標與部分套件名稱發生變化。對已有大量 ObjectMapper、訊息序列化、日期格式化、匯入匯出邏輯的系統，首輪應優先保持 Jackson 2 的相容行為：

spring:
  jackson:
    use-jackson2-defaults: true

必要時使用 Boot 提供的暫時性 Jackson 2 模組。待 HTTP 回應、Kafka/Rabbit 訊息與匯出檔案全部回歸通過後，再單獨規劃 Jackson 3 遷移。否則一次異常很難區分是 Boot、Jackson 還是業務序列化造成的。

4. 資料存取元件必須依 Boot 4 重新確認

已移除的歷史查詢擴充不再是風險，但以下元件仍需確認版本：

  • Hibernate 7：實體映射、方言、JPA Criteria、原生 SQL、JSON 與日期欄位。
  • 動態資料來源：dynamic-datasource-spring-boot3-starter 不能直接假定相容 Boot 4。
  • MyBatis-Plus：分頁、攔截器、多資料來源交易與 SQL 日誌。
  • Redis、Kafka、Rabbit：用戶端、序列化、監聽器、重試與訊息標頭。

每一項都應採用「升級依賴後執行測試」的方式確認，而不是只看 Maven 能否下載 jar。

5. 安全、測試與維運也會跟著升級

Boot 4 同時帶來 Spring Security 7、Spring Kafka 4、Spring AMQP 4、Spring Batch 6 等大版本升級。需要重點驗證：

  • 登入、Token、權限註解、Feign 呼叫身分。
  • 訊息消費、反序列化、重試與冪等。
  • @SpringBootTest 下的 Web 測試；需要時明確加入 @AutoConfigureMockMvc。
  • Actuator 健康檢查。Boot 4 預設啟用 liveness/readiness 分組，Kubernetes 探針、Prometheus 抓取與優雅停機都要重新確認。

在 3.5 驗收基線上的實施順序

建立 4.1-SNAPSHOT 分支
        ↓
确认 Cloud / Alibaba Client 精确版本
        ↓
迁 Nacos Config Data，处理父工程自研 starter
        ↓
父工程全量编译与测试
        ↓
升级一个试点服务并在本地连接 Nacos 3.1.2
        ↓
test Kubernetes 发布与业务回归
        ↓
逐服务推广

建議先選一個業務邊界清楚、測試較完整的服務作為試點，而不是一次升級所有服務。父工程新版本使用獨立的 Maven 版本，例如 4.1-SNAPSHOT，避免覆蓋仍在執行的 3.5.13-SNAPSHOT。

Boot 4 試點的增量驗收清單

下面只列相對上一篇新增的檢查項。目標 JDK 編譯、Pod 啟動、完整 /actuator/health、資料庫與訊息中介軟體連通性等通用驗收仍然必須執行，但不在這裡重複展開。

啟動與基礎設施

  • Spring Cloud 已使用支援 Boot 4.1 的 2025.1.2+，依賴樹中沒有舊版 Release Train。
  • Spring Cloud Alibaba Client 的精確版本有相容矩陣或試點驗證證據，不能只用 Nacos Server 版本代替。
  • Nacos 設定已改為 Config Data，啟動鏈路不再依賴 Spring Cloud Bootstrap。
  • 實際 Web 容器是 Tomcat 11 或 Jetty 12，依賴樹與設定中沒有殘留 Undertow。
  • spring-boot-starter-classic 只作為過渡；拆分 starter 與屬性遷移完成後應移除。

業務與資料

  • Hibernate 7、MyBatis-Plus 與動態資料來源分別完成分頁、交易、原生 SQL 與多資料來源回歸。
  • Spring Batch 6 的 Job 註冊、中繼資料表、重啟與分割執行語意通過驗證。
  • Spring Kafka 4、Spring AMQP 4 的訊息標頭、序列化、重試、死信與冪等行為沒有變化。
  • Jackson 3 與暫時性 Jackson 2 相容路徑只能選擇一條作為生產基線，並完成 HTTP、訊息與匯入匯出回歸。

介面契約

  • 前端核心頁面請求與錯誤提示。
  • 日期、金額、列舉、null 欄位、分頁結構。
  • HTTP API 與訊息 JSON 的反序列化相容。

結論

從 Spring Boot 3.5.13 升到 4.1，Nacos 3.1.2 與已移除的歷史查詢擴充不再是阻礙。真正需要優先確認的是 Spring Cloud Alibaba Client 是否對 Boot 4.1 有明確支援；隨後依 Nacos 設定載入、Boot 模組化與 Web 容器、資料存取、Jackson 與自研 starter 的順序推進。

先建立「本機與 test 環境驗證可用」的證據，再把它升級為生產標準，才是這類跨大版本升級可控的做法。Boot 官方遷移指南可作為逐項排查清單：Spring Boot 4.0 Migration Guide。
