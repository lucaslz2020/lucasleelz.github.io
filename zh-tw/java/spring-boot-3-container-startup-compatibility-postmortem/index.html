ENGINEERING NOTE · 2026年8月8日

Spring Boot 3 容器啟動異常復盤：目錄、廢棄屬性、日誌橋與選用驅動

從 UnsatisfiedDependencyException 追到 mkdir failed，並系統處理 Nacos 快取目錄、server.use-forward-headers、commons-logging、nacos-logback.xml 與空 Class.forName。

lucaslz作者
2026年8月8日 13 分鐘閱讀
#Spring Boot #Java #Nacos #Kubernetes #故障復盤
{ }

本文來自 Spring Boot 3 服務的一次滾動發布。類別名稱、服務名稱、路徑與業務設定均已泛化。系列導覽：Kubernetes 重建遷移教學系列。

統一的 Deployment 發布後，啟動日誌同時出現五類訊息：

UnsatisfiedDependencyException ... Factory method threw: mkdir failed

failed to create cache dir: /root/nacos/naming/.../failover

server.use-forward-headers is no longer supported

please remove commons-logging.jar from classpath

Could not initialize Logback Nacos logging from classpath:nacos-logback.xml

java.lang.ClassNotFoundException:
  at java.lang.Class.forName(...)

把它們都歸因於「Deployment 改壞了」並不準確；把它們都當成無害 warning 也很危險。真實情況橫跨四層：

層典型問題是否可能阻止啟動
檔案系統SDK 無法建立快取或斷點檔案是
設定遷移舊屬性由 migrator 暫時對應通常否
classpath日誌橋重複、Logback 版本不相容視元件而定
業務程式碼空字串傳給 Class.forName是或形成隱患

正確的排查順序

flowchart TD
  A["Spring Boot 啟動失敗"] --> B["從例外最底層往上讀"]
  B --> C{"最深層 Cause 是什麼"}
  C --> D["IOException / mkdir"]
  C --> E["NoClassDefFound / ClassNotFound"]
  C --> F["Properties migration"]
  C --> G["Logging warning"]
  D --> H["檢查 UID、HOME、掛載與權限"]
  E --> I["檢查有效設定與依賴樹"]
  F --> J["替換設定 key"]
  G --> K["清理日誌橋或增加 adapter"]

UnsatisfiedDependencyException 往往只是最外層的包裝：Controller 依賴 Service，Service 依賴 FileManager，而 FileManager 在建構時建立目錄失敗，才導致 Controller 無法注入。

不要一看到堆疊頂端出現哪個 Bean，就先改哪個 Bean。

事故一：UnsatisfiedDependencyException 的根因是 mkdir

外層日誌：

Error creating bean with name 'voucherController'
Unsatisfied dependency expressed through constructor parameter 0

繼續往下：

Error creating bean with name 'fileManager'
Factory method 'fileManager' threw exception with message: mkdir failed

最底層：

Caused by: java.io.IOException: mkdir failed
  at ...FileRecorder.<init>(...)

這說明：

  • Spring DI 本身沒有壞。
  • Controller 與 Service 建構子不是首要問題。
  • 第三方檔案 SDK 在 Bean 初始化階段建立斷點紀錄目錄失敗。

先以相同映像與 security context 進入容器檢查：

id
printf 'HOME=%s\n' "$HOME"
java -XshowSettings:properties -version 2>&1 | grep 'user.home'
mount
ls -ld /root /tmp /data/java/logs
touch /tmp/write-test

容器即使以 root UID 執行，也不代表任何路徑都可寫；唯讀根檔案系統、磁碟區權限、掛載覆蓋與 SDK 選擇的預設路徑，都會影響最終結果。

事故二：Nacos 為什麼突然寫入 /root/nacos

Nacos Client 會保存 naming failover、snapshot 或日誌。路徑計算可能依賴：

  • HOME。
  • Java user.home。
  • Nacos 自己的 JM.SNAPSHOT.PATH。
  • JM.LOG.PATH。

舊 Deployment 剛好允許寫入 /root，所以問題一直被隱藏。安全基線收緊或映像使用者改變後，啟動執行緒開始回報：

failed to create cache dir: /root/nacos/naming/<namespace>/failover

修復方式是給用戶端一個明確、受控、可寫的目錄：

volumeMounts:
  - name: tmp-volume
    mountPath: /tmp

env:
  - name: HOME
    value: /tmp
  - name: JDK_JAVA_OPTIONS
    value: >-
      -Duser.home=/tmp
      -DJM.SNAPSHOT.PATH=/tmp
      -DJM.LOG.PATH=/data/java/logs/nacos

volumes:
  - name: tmp-volume
    emptyDir:
      sizeLimit: 2Gi

啟動指令碼先建立目錄，失敗時直接退出：

mkdir -p /tmp/nacos /data/java/logs/nacos
test -w /tmp
test -w /data/java/logs/nacos

不要為了修一個快取目錄問題，就恢復所有 capability 或讓整個根檔案系統變成可寫。

還要區分嚴重程度：

  • Nacos failover 備份失敗時，主註冊流程有時仍能運作，但災難復原能力會下降。
  • 檔案 SDK 在 Bean 建構期間 mkdir failed，會直接導致 Spring Context 啟動失敗。

即使日誌等級都是 ERROR，也不代表影響相同；必須結合例外發生的生命週期階段判斷。

事故三：server.use-forward-headers 是遷移提示

日誌：

The use of configuration keys that are no longer supported was found:
server.use-forward-headers
Reason: Replaced to support additional strategies.

升級期間如果引入 spring-boot-properties-migrator，應用程式可能仍能啟動，因為 migrator 會暫時對應舊 key。但應該盡快替換：

# 删除
server.use-forward-headers=true

# 根据代理链选择
server.forward-headers-strategy=framework

FRAMEWORK、NATIVE 與 NONE 的差異見 Spring Boot 反向代理指南。

Spring Boot 升級指南明確說明，properties migrator 只用來發現並暫時遷移重新命名的屬性，升級完成後應刪除該依賴。

所以處理順序如下：

  1. 在 Nacos 中搜尋舊 key 的所有 namespace、group 與 dataId。
  2. 用新 key 替換。
  3. 滾動服務並確認不再出現遷移報告。
  4. 從 parent 或應用程式移除 properties migrator。

不要靠關閉遷移日誌來「解決」設定問題。

事故四：commons-logging 與 spring-jcl 同時存在

警告：

Standard Commons Logging discovery in action with spring-jcl:
please remove commons-logging.jar from classpath

Spring Framework 使用 spring-jcl 作為 Commons Logging bridge。如果 classpath 上又出現傳統的：

commons-logging:commons-logging

就可能發生日誌實作發現順序衝突。

先定位引入鏈：

mvn dependency:tree \
  -Dverbose \
  -Dincludes=commons-logging:commons-logging

不要在幾十個業務儲存庫裡逐個排除。如果依賴來自統一的 Nacos config/discovery starter，應在其直接依賴邊界排除：

<dependency>
  <groupId>com.alibaba.cloud</groupId>
  <artifactId>spring-cloud-starter-alibaba-nacos-config</artifactId>
  <exclusions>
    <exclusion>
      <groupId>commons-logging</groupId>
      <artifactId>commons-logging</artifactId>
    </exclusion>
  </exclusions>
</dependency>

discovery starter 若有獨立依賴，也要在對應邊界排除。Maven exclusion 只對指定的依賴路徑生效；另一個 SDK 仍可能再次引入同一個 JAR。

治理後重新檢查：

mvn dependency:tree \
  -Dincludes=commons-logging:commons-logging

jar tf application.jar \
  | grep 'BOOT-INF/lib/commons-logging'

如果組織內要求長期禁止它，可以在 parent 新增 Maven Enforcer 的 bannedDependencies 規則；但應先處理已知的傳遞鏈，避免一次升級同時阻斷所有儲存庫。

事故五：Nacos 無法載入 nacos-logback.xml

警告：

Load Logback Configuration of Nacos fail,
message: Could not initialize Logback Nacos logging
from classpath:nacos-logback.xml

這不是「缺少一個 XML 檔案」這麼簡單。Spring Boot 3 使用 Logback 1.4，而部分 Nacos Client 2.2.x 的日誌初始化方式與其不相容。

Nacos 官方 FAQ提供的相容對應關係是：

Nacos Clientlogback-adapter
2.2.1–2.3.x1.0.x
2.4.0 及以後1.1.x

對於 Nacos Client 2.2.1，可以在統一依賴管理中鎖定：

<properties>
  <nacos-logback-adapter.version>1.0.1</nacos-logback-adapter.version>
</properties>

<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>com.alibaba.nacos</groupId>
      <artifactId>logback-adapter</artifactId>
      <version>${nacos-logback-adapter.version}</version>
    </dependency>
  </dependencies>
</dependencyManagement>

但 dependencyManagement 只管理版本，不會自動把 JAR 放進應用程式。真正使用 Nacos 的共用 starter 還要宣告：

<dependency>
  <groupId>com.alibaba.nacos</groupId>
  <artifactId>logback-adapter</artifactId>
</dependency>

最後用可執行 JAR 驗證，而不是只看 parent：

jar tf application.jar \
  | grep -E 'nacos-client|logback-adapter|logback-classic'

不要自行把舊的 nacos-logback.xml 複製到每個應用程式。這樣會把版本相容責任分散到業務儲存庫，並在下次 Nacos 升級時再次漂移。

事故六：沒有 message 的 ClassNotFoundException

另一個服務啟動時出現：

java.lang.ClassNotFoundException:
  at java.lang.Class.forName0(...)
  at java.lang.Class.forName(...)
  at ...JDBCUtil.initialize(...)

例外冒號後沒有類別名稱，這是重要線索。程式碼實際執行了：

Class.forName(driver);

但這些選用設定是空字串：

sales.driver=
sales.url=

Class.forName("") 會拋出幾乎沒有業務資訊的 ClassNotFoundException。

如果這組同步資料來源是選用功能，初始化邏輯應該先判斷「功能是否啟用」：

@PostConstruct
void initialize() {
    if (!StringUtils.hasText(url)) {
        log.info("未配置 sales.url，同步功能已禁用");
        return;
    }

    if (!StringUtils.hasText(driver)) {
        throw new IllegalStateException(
            "已配置 sales.url，但缺少 sales.driver"
        );
    }

    try {
        Class.forName(driver);
    } catch (ClassNotFoundException ex) {
        throw new IllegalStateException(
            "无法加载同步数据库驱动: " + driver,
            ex
        );
    }
}

更理想的做法是使用條件式組態：

@ConditionalOnProperty(
    prefix = "sales",
    name = "url"
)

讓未設定的選用功能根本不建立 Bean。不要用空字串來表示「已啟用，但暫時還不知道驅動」。

另外，Class.forName 所在的方法曾被命名為 getServletPort，但它實際載入 JDBC 驅動。錯誤的命名會讓堆疊追蹤誤導排障方向，應一併修正。

如何判斷該改 Deployment、Nacos、parent 還是業務程式碼

證據修改位置
同一映像在舊 security context 可寫，在新 context 不可寫Deployment 與掛載
key 被 properties migrator 對應Nacos / 應用程式設定
多個應用程式都透過同一 starter 引入舊 JARparent 或共用 starter
只有一個選用模組把空值傳給反射 API業務程式碼
Adapter 與用戶端版本不匹配dependency management + starter

不要因為日誌出現在 Kubernetes 裡，就預設所有問題都該透過 YAML 修復。

滾動驗證清單

  1. 建置後檢查最終 JAR 的依賴，不只檢查 IDE dependency view。
  2. 渲染 Deployment，確認 HOME、user.home、掛載與 UID。
  3. 先滾動一個複本。
  4. 等新 ReplicaSet Ready，確認舊 Pod 仍能作為備援。
  5. 檢查啟動日誌中的五類關鍵字。
  6. 觸發 Nacos 註冊、Redis、檔案上傳與選用 JDBC 的實際呼叫路徑。
  7. 再滾動其餘複本。
kubectl -n <namespace> logs <new-pod> --since=20m \
  | grep -Ei \
  'mkdir failed|/root/nacos|use-forward-headers|commons-logging|nacos-logback|ClassNotFound'

完成定義

  • Spring 例外已追到最底層 Cause，而不是停在 Bean 名稱。
  • 所有需要寫入的用戶端目錄都有受控掛載與大小限制。
  • Nacos 不再嘗試寫入 /root/nacos。
  • Nacos、上傳 SDK 與日誌目錄都完成真實寫入驗證。
  • server.use-forward-headers 已從所有 Nacos dataId 刪除。
  • 最終 JAR 不包含傳統的 commons-logging.jar。
  • Nacos Client 與 logback-adapter 版本匹配。
  • 選用 JDBC 功能在未設定時不載入驅動。
  • 新舊 ReplicaSet 切換完成，沒有舊 Pod 長期作為備援。

最終結論

這輪啟動事故背後沒有一個統一的「神奇設定」；它真正提供的，是一條穩定的判斷路徑：

先读最深 Cause
→ 判断文件系统、配置、classpath 还是业务代码
→ 在最接近根因的公共边界修复
→ 检查最终 JAR 和最终 Pod，而不是源码与模板

安全基線暴露了過去依賴 /root 可寫的隱含假設；Spring Boot 3 暴露了舊屬性與日誌堆疊的版本邊界；空的 Class.forName 則暴露了業務程式碼沒有正確表達「選用功能」。

把這些問題分別修在 Deployment、Nacos、共用 starter 與業務程式碼中，才不會為了消除一條日誌，就對整個叢集放寬權限或引入新的 classpath 衝突。
