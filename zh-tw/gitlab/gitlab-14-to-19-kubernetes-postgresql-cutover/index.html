GitLab 14 升級到 19 實戰復盤（一）：遷移架構、升級路線與停服規劃

從一臺運行多年的 GitLab CE 14.9.3 開始，復盤如何先同版本遷入 Kubernetes，再按官方停靠點升級至 GitLab 19.2.1。

lucaslz作者
2026年8月8日 更新於 2026年8月10日 9 分鐘閱讀
#GitLab #Kubernetes #PostgreSQL #DevOps #遷移
{ }

本文來自一次真實生產遷移。IP、域名、節點名、項目名、倉庫數量、用戶數量、鏡像倉庫、備份文件名和校驗值均已脫敏或泛化；Secret、密碼和內部地址只使用佔位符。

升級停靠點和 PostgreSQL 支持矩陣會繼續變化。執行前必須重新核對 GitLab 官方升級路徑 與 安裝要求。本文記錄的是一次可復盤的過程，不是可以永久照抄的版本清單。

這不是一篇“把 GitLab 14 直接換成 GitLab 19 鏡像”的教程。真實遷移中，我們先把一臺 Omnibus GitLab 14.9.3 原樣恢復到 Kubernetes，再完成二十多個版本停靠點，最後凍結舊實例、同步最終倉庫增量、保留原來的 HTTP/SSH 入口。

系列共三篇：

  1. 本篇講遷移設計、同版本恢復和升級節奏。
  2. 第二篇：升級停靠點、後臺遷移與 PostgreSQL 17 講最容易卡住的版本與數據庫問題。
  3. 第三篇：Kubernetes 增量切流、保留 IP 與回滾 講真正決定能否上線的最後一公里。

遷移前的真實約束

起點是一臺運行多年的 GitLab CE 14.9.3。Git 倉庫、內置 PostgreSQL、Redis、配置和日誌都在一臺虛擬機中；開發機、Jenkins 和歷史倉庫地址已經依賴原來的域名、服務 IP 和 SSH 入口。

目標不是為了“容器化”而容器化，而是同時完成四件事：

  • 升級到 GitLab CE 19.2.1。
  • 改為 Kubernetes 中的單副本 StatefulSet。
  • 使用集群內獨立 PostgreSQL，最終到 PostgreSQL 17。
  • 儘量不改開發者和 CI 的 Git 地址，並保留可執行回滾點。

這四件事相互制約。Pod Ready 只能說明進程通過探針，不能說明數據庫遷移、後臺遷移、倉庫對象、加密數據和最終增量都安全。

為什麼沒有直接跨版本

繼續運行 14.x 不只是“版本舊”。安全更新會停止，Runner、瀏覽器和集成組件的兼容範圍持續前移，舊操作系統和數據庫也會一起進入維護末期。

但 GitLab 的升級也不能只看容器標籤。大版本之間有 schema 變化、加密配置變化和 Batched Background Migration（批量後臺遷移）。直接把 14.9 的數據放進 19.x，常見結果是遷移類缺失、表結構不匹配、數據庫版本不受支持，或歷史加密數據無法解密。

我們採用的實際路徑如下。每個數字都是在目標 minor 的最新 patch 上停留並驗收後，才進入下一站：

14.9.3 → 14.9.5 → 14.10.5 → 15.0.5 → 15.4.6 → 15.11.13
→ 16.0.10 → 16.1.8 → 16.2.11 → 16.3.9 → 16.7.10 → 16.11.10
→ 17.3.7 → 17.5.5 → 17.8.7 → 17.11.7
→ 18.2.8 → 18.5.7 → 18.8.11 → 18.11.9 → 19.2.1

其中有些停靠點是否需要經過，取決於實例規模、Web 節點數量及特定表的數據量。本次確認相關條件不觸發後跳過了不適用的站點；這不是通用結論。每次升級都應把源版本、目標版本和實例條件重新輸入 Upgrade Path 工具，再逐條閱讀 Upgrade Notes。

先固定基線，後面每站都拿它驗收

遷移剛開始時，我們沒有立刻創建 Pod，而是先把“以後如何證明數據沒有丟”寫成一組可重複執行的檢查。至少記錄：GitLab 版本、核心對象計數、關鍵倉庫 refs、各類附件佔用、PostgreSQL 版本與擴展、服務狀態以及兩類遷移狀態。

gitlab-rake gitlab:env:info
gitlab-rake gitlab:check SANITIZE=true

gitlab-rails runner '
puts({
  users: User.count,
  groups: Group.count,
  projects: Project.count,
  merge_requests: MergeRequest.count,
  builds: Ci::Build.count
}.inspect)
'

現場經驗是：gitlab:check 很有價值，但它不是數據一致性證明。它發現配置、權限和服務異常；倉庫是否完整仍要比 refs、做 git fsck，並在最後做真實 clone、push 和 Jenkins 拉取測試。

備份要拆開理解

第一次演練就暴露了一個常見誤區：GitLab 應用備份不是全部恢復能力。gitlab-secrets.json 保存 CI/CD 變量、2FA 等加密數據的解密能力；SSH Host Key 關係到客戶端是否會看到主機指紋改變。

每個關鍵大版本前，我們至少保留以下內容，並記錄文件大小和 SHA-256：

  1. GitLab 應用備份。
  2. PostgreSQL 獨立 dump。
  3. /etc/gitlab 配置歸檔與 gitlab-secrets.json。
  4. SSH Host Key。
  5. StatefulSet、Service、PV、PVC、Secret、ConfigMap 清單。
umask 077
gitlab-backup create
gitlab-ctl backup-etc
tar -C /etc -czf /backup/ssh-host-keys.tar.gz ssh
sha256sum /backup/* > /backup/SHA256SUMS

恢復演練必須使用同一個 GitLab 版本。14.x 的備份先恢復到 14.x，確認服務和數據正常後才能開始升級；不能拿舊備份直接餵給 19.x 容器。外部 PostgreSQL dump 也要注意 pg_dump 客戶端主版本不能低於服務端，必要時在 PostgreSQL Pod 或匹配版本的臨時工具容器中執行。

平臺遷移與版本升級必須拆開

這次最重要的控制點，是先把 GitLab 14.9.3 同版本恢復進 Kubernetes。若一邊換運行平臺、一邊跨五個大版本，任何異常都無法快速判斷是 PV、權限、網絡、數據庫連接還是 GitLab 升級本身造成的。

我們使用單副本 StatefulSet，本地 PersistentVolume 採用 Retain：即使誤刪 PVC 或 StatefulSet，宿主機數據目錄也不會被回收。GitLab 是有狀態服務，先把數據歸屬和節點綁定設計清楚，再談版本升級。

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: gitlab
spec:
  replicas: 1
  updateStrategy:
    type: OnDelete
  template:
    spec:
      nodeSelector:
        app-type: gitlab
      terminationGracePeriodSeconds: 300

OnDelete 是刻意選擇。修改鏡像後不會自動滾動；運維人員必須在當前站點的後臺遷移、備份和驗證全部完成後，才顯式刪除 Pod 進入下一版本。

每一站都執行同一套閘門

實際執行時，我們把每個停靠點固化為同一個節奏：檢查前一站遷移、創建回滾備份、同步並預拉取下一鏡像、修改 StatefulSet、顯式刪除 Pod、觀察日誌、檢查遷移、執行服務與倉庫驗證。

kubectl -n <namespace> set image statefulset/gitlab \
  gitlab=<registry>/gitlab-ce:<next-version>

kubectl -n <namespace> delete pod gitlab-0
kubectl -n <namespace> wait --for=condition=Ready \
  pod/gitlab-0 --timeout=30m

kubectl -n <namespace> exec gitlab-0 -- \
  gitlab-rake gitlab:check SANITIZE=true

首次啟動數分鐘沒有 Ready 並不等於卡死。我們同時看 Pod 事件、reconfigure、數據庫鎖、Sidekiq、Gitaly 和磁盤 IO，避免因為一次 wait 超時就併發啟動 Rails Runner 或完整 checksum，反而把存儲壓力放大。

完成平臺遷移和升級節奏設計後，真正危險的部分才開始出現：後臺遷移狀態在 GitLab 17 改變，歷史分區數據會阻塞任務，而 PostgreSQL 必須跟著 GitLab 分階段升級。
