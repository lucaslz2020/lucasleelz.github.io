Migrating from Nacos Service Discovery to Kubernetes Service DNS: Smooth Cutover One Call Chain at a Time

Keep the Nacos config center and progressively move Feign, Gateway, and internal HTTP calls from registry-based instance discovery to Kubernetes Service DNS, with canary, verification, and rollback designed in.

lucaslzAuthor
June 21, 2026 7 min read
#Nacos #Kubernetes #Service DNS #Feign #Gateway

Swapping the fixed ClusterIP in Nacos config for Service DNS only fixes the “unstable configuration address” problem. If Feign, Gateway, and RestTemplate still fetch instance lists from Nacos, a registry outage can still make every internal call fail with “no available servers.”

This article covers the next phase: keeping the Nacos config center and handing service discovery over to Kubernetes Service one call chain at a time.

Separate Nacos’s Two Responsibilities First

flowchart LR
  A["Application"] --> B["Nacos Config Center"]
  A --> C["Nacos Service Discovery"]
  C --> D["Pod Instance List"]
  E["Target Architecture"] --> F["Nacos Keeps Providing Config"]
  E --> G["Service DNS Provides the Service Entry"]
  G --> H["Ready Pods in EndpointSlice"]

Migrating service discovery doesn’t mean also removing the Nacos config center. Bundling both changes into a single window makes config loading, instance registration, and call routing all change at once, leaving very poor rollback boundaries.

When Service DNS Is a Good Fit

Suitable when:

  • The caller and callee are in the same Kubernetes cluster.
  • The service already has a stable Service name and namespace.
  • The Service selector, readiness, and EndpointSlice are reliable.
  • You don’t rely on Nacos metadata for complex weight, zone, or version routing.

Be careful when:

  • Instances are cross-cluster, cross-datacenter, or outside Kubernetes.
  • The same service needs to select instances by tenant, version, or label.
  • Clients need per-instance awareness for special load balancing.
  • Long-lived connection protocols or per-instance fixed addresses are in play, such as some Kafka listeners.

A Kubernetes Service exists precisely so clients don’t have to track churning Pod instances; it keeps its backends current through EndpointSlice. Kubernetes Service

Step 1: Inventory All Service Discovery Entry Points

Scan the code and config repositories:

rg -n '@FeignClient|lb://|LoadBalancerClient|DiscoveryClient|NacosDiscovery|spring.cloud.nacos.discovery' .

Organize the results into a table:

caller,client_type,service_id,target_namespace,criticality,owner,status
gateway,Gateway,rbac-api,app-test,critical,team-a,pending
order-api,Feign,inventory-api,app-test,normal,team-b,pending

Don’t change everything you scan in one go. Start with a single call chain that is read-only, low-risk, and easy to verify.

Step 2: Prove the Target Service Actually Works

kubectl -n app-test get service rbac-api -o yaml
kubectl -n app-test get endpointslice \
  -l kubernetes.io/service-name=rbac-api -o wide
kubectl -n app-test get pod -l app.kubernetes.io/name=rbac-api -o wide

Requirements:

  • The selector matches the target Pods exactly.
  • EndpointSlice contains only Ready Pods.
  • port and targetPort are correct.
  • With at least two replicas, Pods are spread across different nodes.

Test from a caller Pod:

kubectl -n gateway exec <gateway-pod> -- \
  getent hosts rbac-api.app-test.svc.cluster.local

kubectl -n gateway exec <gateway-pod> -- \
  curl -fsS http://rbac-api.app-test.svc.cluster.local:8082/<health-path>

If this step doesn’t pass, don’t touch Feign or Gateway yet.

Step 3: Migrate One Feign Client First

Originally, only the service name was used:

@FeignClient(name = "inventory-api")
public interface InventoryClient {
    @GetMapping("/v1/inventory/{id}")
    InventoryDTO find(@PathVariable String id);
}

Spring Cloud OpenFeign lets you configure a fixed URL for a Feign Client; once a URL is set, requests no longer go through LoadBalancer to discover instances by service name. The exact config keys for your current version depend on the Release Train your project uses — follow the official OpenFeign documentation.

spring:
  cloud:
    openfeign:
      client:
        config:
          inventory-api:
            url: http://inventory-api.app-test.svc.cluster.local:8090
            connectTimeout: 3000
            readTimeout: 5000

The Kubernetes Service itself forwards connections to Ready Endpoints, so the client no longer needs to fetch Pod IPs from Nacos in this setup.

Step 4: Keep a Switch for the Cutover

Keep both values in Nacos config or a ConfigMap:

clients.inventory-api.discovery-mode=nacos
clients.inventory-api.kubernetes-url=http://inventory-api.app-test.svc.cluster.local:8090

The application chooses based on an explicit switch instead of silently falling back to Nacos after a DNS failure. An implicit dual-path setup causes:

  • Different instances taking different paths during the same incident.
  • Metrics that make it hard to tell which entry point is in effect.
  • Nacos problems being masked by automatic fallback.

Rolling back only requires restoring the switch and rolling the callers.

Step 5: Canary a Caller Pod

Create a canary Deployment with one replica and change only its config:

kubectl -n <caller-namespace> apply -f caller-canary.yaml
kubectl -n <caller-namespace> rollout status deployment/<caller>-canary --timeout=10m

Send test requests to the canary through a temporary Service, a Header, or direct internal access. Watch:

kubectl -n <caller-namespace> logs deployment/<caller>-canary --since=15m \
  | grep -Ei 'inventory-api|available server|timeout|refused'

Also verify the canary keeps calling successfully when the target Service’s Endpoints change:

kubectl -n app-test rollout restart deployment/inventory-api
kubectl -n app-test rollout status deployment/inventory-api --timeout=10m

Step 6: Migrate Gateway Routes

Original route:

uri: lb://rbac-api

Candidate route:

uri: http://rbac-api.app-test.svc.cluster.local:8082

First duplicate a test Path or test Host instead of replacing all production routes at once. Verify:

  • Path rewrite.
  • Authorization Header.
  • Cookie and CORS.
  • Timeout and response body.
  • Connection continuity while target Pods roll.

If the Gateway still reports Load balancer does not have available server, the route actually in effect is still lb://, or the config hasn’t been refreshed.

Step 7: Migrate Plain HTTP Clients

Put the base URL in config:

clients.file-storage.base-url=http://file-storage.app-test.svc.cluster.local:8686

The client must also set:

  • connect timeout.
  • read timeout.
  • Connection pool and concurrency limits.
  • Finite retries on idempotent requests only.
  • Explicit degradation for optional dependencies.

Service DNS solves the discovery problem; it won’t automatically fix slow dependencies or thread pileup.

Step 8: Roll Out to the Full Deployment

Once the canary is stable:

kubectl -n <caller-namespace> set env deployment/<caller> \
  DISCOVERY_MODE=kubernetes

kubectl -n <caller-namespace> rollout status deployment/<caller> --timeout=10m

Check the config source and logs on every Pod so the change isn’t only effective on new Pods.

Step 9: Stop Nacos Registration for This Service

Only consider disabling the target service’s Nacos discovery registration after every caller has switched over:

spring:
  cloud:
    nacos:
      discovery:
        register-enabled: false

The property name changes with the Spring Cloud Alibaba version, so verify it against your project’s dependencies. Before disabling, confirm from the code repository and Nacos subscription relationships that no caller was missed.

Nacos Config can keep working; don’t accidentally remove spring.config.import or the config namespace.

Step 10: Simulate Nacos Service Discovery Being Unavailable

Verify in an isolated environment:

  1. The caller has finished loading its config.
  2. Temporarily block its access to the Nacos Naming port.
  3. Keep sending requests to the migrated call chain.
  4. Restart the target business Pod and observe EndpointSlice updates.

Expected: migrated call chains still work through Service DNS. Whether features that depend on dynamic config are affected should be tracked separately.

Rollback

停止扩大范围
→ 恢复 discovery-mode=nacos
→ 滚动调用方
→ 检查 Nacos 中目标服务实例
→ 验证 lb:// 调用

If the target service’s registration was already disabled, restore registration and confirm the instances are healthy before switching callers back.

Definition of Done

  • Migrated call chains no longer create a Nacos LoadBalancer Client.
  • The effective Feign/Gateway URL is Service DNS.
  • Requests see no sustained failures while target Pods roll.
  • Migrated call chains still work when Nacos Naming is temporarily unavailable.
  • Nacos Config loading and dynamic refresh still work normally.
  • The target service’s registration is disabled only after all callers have migrated.
  • Every call chain has an independent rollback switch and verification record.

The right migration unit is not “the whole Nacos,” but a service call chain that is verifiable and can be rolled back.
