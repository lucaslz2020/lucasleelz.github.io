How to Smoothly Upgrade Nacos: Rolling Upgrade and Rollback on Kubernetes

Upgrade a three-node Nacos on Kubernetes node by node: check versions, schema, config backups, and client inventory; verify registration, config, and rollback.

lucaslzAuthor
June 27, 2026 7 min read
#Nacos #Kubernetes #Rolling Upgrade #MySQL #Rollback
{ }

A smooth Nacos upgrade is not just changing the StatefulSet image tag to a new version and waiting for the three Pods to restart automatically. What really needs protecting is threefold: the database schema, service registration continuity, and configuration read continuity.

Series: Kubernetes Rebuild Migration Series. Complete the Nacos cluster baseline and client version inventory before upgrading.

This article assumes a three-node StatefulSet backed by an external MySQL, with applications connecting through a regular Service and the Nacos nodes communicating through a Headless Service.

Answer Four Questions Before Upgrading

Document the answers clearly in the ticket or change record:

  1. What are the current and target Server versions?
  2. What is the Nacos Client major version used by every application?
  3. Does the target version modify the database schema, ports, environment variables, or probe paths?
  4. If you roll back to the old image, is the new schema still compatible with the old version?

The official upgrade guide currently states that upgrading from 2.0.x or later to 3.2.x requires comparing the target version’s database schema; a 3.2.x Server is compatible with 2.x and 3.x Clients, while 1.x Clients are no longer supported. This can change between releases, so re-check the official upgrade guide before you start.

Step 1: Export the Version and Client Inventory

Save the current image and Pods:

kubectl -n nacos-system get statefulset nacos \
  -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}' \
  | tee reports/nacos-current-image.txt

kubectl -n nacos-system get pods -o wide \
  | tee reports/nacos-pods-before.txt

Don’t guess client versions. Gather them from the Maven dependency tree, Gradle dependencies, build artifact manifest, or image SBOM:

mvn dependency:tree -Dincludes=com.alibaba.nacos:nacos-client

Organize the results into a CSV:

namespace,workload,client_version,owner,verified
app-test,order-api,<client-version>,team-a,false

If any client is still on an officially unsupported major version, pause the upgrade.

Step 2: Back Up Configuration, the Database, and Kubernetes Resources

Back up the resource definitions for the StatefulSet, Service, ConfigMap, and Secret:

kubectl -n nacos-system get statefulset,service,configmap -o yaml \
  > backup/nacos-kubernetes.yaml

umask 077
kubectl -n nacos-system get secret nacos-secret -o yaml \
  > backup/nacos-secret.yaml

Take a consistent backup of the database. Using a MySQL logical backup as an example:

mysqldump --single-transaction --routines --triggers \
  -h <mysql-host> -u <backup-user> -p \
  <nacos-database> > backup/nacos-before-upgrade.sql

sha256sum backup/nacos-before-upgrade.sql > backup/nacos-before-upgrade.sha256

Also generate a separate archive of configuration data using the Nacos export feature. Restore both the database backup and the configuration export at least once in an isolated environment.

Step 3: Compare the Database Schemas

Extract mysql-schema.sql from the current and target release packages:

diff -u current/mysql-schema.sql target/mysql-schema.sql \
  | tee reports/nacos-schema.diff

Don’t run the target version’s full schema script directly. Extract the incremental DDL and rehearse it on a database copy:

恢复生产备份到临时库
→ 执行增量 DDL
→ 启动一个目标版本 Nacos
→ 验证配置读取和服务注册
→ 记录耗时与锁表影响

If the change isn’t reversible, the rollback plan can’t just say “switch back to the old image”; it must also include database recovery or proof of backward compatibility.

Step 4: Compare Configuration, Ports, and Probes

Export the current StatefulSet:

kubectl -n nacos-system get statefulset nacos -o yaml \
  > reports/nacos-statefulset-before.yaml

Check each item against the target image’s documentation:

  • Whether any environment variables were renamed.
  • Whether the purpose of ports such as 8848, 9848, 9849, 7848, and 8080 changed.
  • Whether the HTTP API and console paths changed.
  • Whether the health check path still works.
  • Whether the JDK and resource requirements changed.

Since Nacos 3.0, the console is separated from the main port, so the proxy layer can’t keep relying on assumptions from older versions. gRPC ports that go through a proxy must use TCP forwarding, not ordinary HTTP handling. See the deployment overview.

Step 5: Rehearse the Upgrade in a Shadow Environment

Restore an isolated database from a production backup and create a dedicated namespace:

kubectl create namespace nacos-upgrade-lab

Change the Service name, database address, and Secret to lab values, and start the same old version as production. First prove the old version can read the backup data, then upgrade to the target version.

At minimum, verify:

  • Login and permissions.
  • Namespace, Data ID, and Group counts.
  • Publishing configurations, reading them back, and checking history.
  • Temporary application registration, discovery, and deregistration.
  • Cluster recovery after restarting any Nacos Pod.

If the shadow environment fails, don’t just try again in production.

Step 6: Set Up a Node-by-Node Rolling Strategy

By default, a StatefulSet rolls out updates starting from the largest ordinal. To upgrade and observe one node first, you can temporarily set partition:

kubectl -n nacos-system patch statefulset nacos --type merge -p '
{
  "spec": {
    "updateStrategy": {
      "type": "RollingUpdate",
      "rollingUpdate": {"partition": 2}
    }
  }
}'

Then update only the image in the Pod template:

kubectl -n nacos-system set image statefulset/nacos \
  nacos=<image-registry>/nacos-server:<target-version>@sha256:<target-digest>

Only nacos-2 should update at this point:

kubectl -n nacos-system get pods -w

Step 7: Observe the First Node on the New Version

Don’t continue the moment the Pod shows Ready. Watch through at least one full peak-traffic window and check:

kubectl -n nacos-system logs nacos-2 --since=30m \
  | grep -Ei 'error|exception|raft|grpc|database'

kubectl -n nacos-system get endpointslice \
  -l kubernetes.io/service-name=nacos-client -o wide

Meanwhile, run continuous probes:

while true; do
  date
  curl -fsS 'http://<internal-nacos-address>/nacos/v1/console/health/readiness'
  sleep 5
done

On the application side, check configuration listening, registration renewal, call error rates, and the login flow. Stop immediately if the instance list suddenly becomes empty, gRPC connections fail, or configuration listening is interrupted.

Step 8: Roll Out the Remaining Nodes Gradually

Once the first node is stable, set partition to 1:

kubectl -n nacos-system patch statefulset nacos --type merge -p '
{"spec":{"updateStrategy":{"rollingUpdate":{"partition":1}}}}'

Wait for nacos-1 to become Ready, then repeat the full verification. Finally, set partition to 0:

kubectl -n nacos-system patch statefulset nacos --type merge -p '
{"spec":{"updateStrategy":{"rollingUpdate":{"partition":0}}}}'

kubectl -n nacos-system rollout status statefulset/nacos --timeout=20m

Leave a clear observation window between the three nodes; don’t delete all three Pods in a single command.

Step 9: Run a Real Failure Drill

Pick a Pod that isn’t the Leader or has been confirmed safe to rebuild:

kubectl -n nacos-system delete pod nacos-2
kubectl -n nacos-system wait --for=condition=Ready pod/nacos-2 --timeout=10m

Keep issuing configuration reads and service calls while the Pod is being deleted. The goal isn’t zero logs; it’s that clients can reconnect and business requests don’t fail persistently.

Rollback Method

If the old and new versions can coexist and the database changes are backward compatible, leave partition unchanged and restore the old image on the failed node first:

kubectl -n nacos-system set image statefulset/nacos \
  nacos=<image-registry>/nacos-server:<old-version>@sha256:<old-digest>

If the database schema isn’t backward compatible:

  1. Stop all Nacos writes and configuration publishing.
  2. Scale the Nacos StatefulSet down to zero.
  3. Restore the pre-upgrade database.
  4. Restore the old Kubernetes manifests and Secret.
  5. Start the old version and verify configuration and instances.

This process causes downtime, so irreversible DDL must run in a maintenance window.

Definition of Done

  • All three Pods are running the target image digest.
  • The database schema matches the target version, and the execution records are saved.
  • Configuration, service instances, users, and permission counts match the pre-upgrade baseline.
  • All critical client versions are within the compatibility matrix.
  • Configuration reads and service calls keep working while a Pod is deleted.
  • No persistent registration failures, gRPC disconnects, or database anomalies during the observation period.
  • Backups, the old image, and the rollback checklist must not be deleted before the observation period ends.
