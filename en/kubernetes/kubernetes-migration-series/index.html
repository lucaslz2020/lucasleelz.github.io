Kubernetes Rebuild Migration Series: From Scratch to Production Cutover

Kubernetes tutorials in execution order: clusters, networking, scheduling, rolling releases, Deployment & Nacos baselines, middleware, JVM tuning, postmortems.

lucaslzAuthor
May 24, 2026 5 min read
#Kubernetes #kubeadm #Rocky Linux #Nacos #Nexus #Migration
{ }

This series grew out of a complete cluster rebuild. Rather than a chronological failure log, it was reorganized into tutorials you can follow from scratch.

All internal addresses, domains, nodes, namespaces, accounts, and capacities have been sanitized. The <...> placeholders in commands are variables you must replace; never copy these commands into production as-is.

Recommended Reading Order

Phase 1: Start with a Healthy Empty Cluster

  1. Set Up Kubernetes from Scratch: prepare Rocky Linux and containerd, create a three-node control plane with kubeadm, and configure kube-vip and Calico.
  2. Understand the Three Types of Network Addresses: learn the difference between Node, Pod, and Service CIDRs and DNS to avoid address overlap and fixed-IP dependencies.
  3. Install Core Add-ons: deploy metrics-server, dynamic storage, and NGINX Ingress, then validate them with a test workload.
  4. Plan Node Pools: use labels, taints, tolerations, and affinity to divide nodes into ingress, business, data, monitoring, and reserved pools.
  5. Design Zero-Downtime Rolling Releases: configure the three probe types, graceful shutdown, Deployment strategy, and PDB correctly.

Phase 2: Build Platform Dependencies

  1. Set Up a Three-Node Nacos Cluster: understand Headless Services versus regular Services, and configure the database, authentication, probes, and anti-affinity.
  2. Replace Fixed Service IPs with DNS: inventory the Nacos configuration, then replace, read back, restart, and verify each entry.
  3. Migrate Nacos Service Discovery to Service DNS: keep the config center and migrate Feign, Gateway, and internal HTTP call chains one by one.
  4. Upgrade Nacos Smoothly: back up configuration and the database, verify version compatibility, run the rolling upgrade node by node, and plan the rollback.
  5. Troubleshoot Service and Registration Failures: locate the problem layer by layer across DNS, Service, Endpoint, Pod, CNI, and kube-proxy.

Phase 3: Migrate Workloads and the Artifact Repository

  1. Migrate Stateful Services: handle backup, restore, and switchover for MySQL, Redis, Kafka, RabbitMQ, and ZooKeeper separately.
  2. Workload Migration Runbook: deploy resources with zero replicas, restore data, start in batches, verify with real business traffic, switch the ingress, and roll back.
  3. Deploy Nexus 3 on Kubernetes: first get the new artifact repository running stably.
  4. Migrate Smoothly from Nexus 2 to Nexus 3: Upgrade Wizard, H2 upgrade, PostgreSQL migration, and VIP switchover.
  5. Govern Nexus CE Usage: distinguish component, request, and Blob space, and safely clean up proxy caches and stale artifacts.

Phase 4: Runtime Optimization and Incident Postmortems

  1. Analyze the Multi-Service Pod Restart Storm: use termination status and previous logs to pinpoint slow dependencies, connection pools, and probe amplification effects.
  2. Standardize a Multi-Service Spring Boot 3 Deployment Template: merge duplicate templates, parameterize resources and compatibility exceptions, and unify security, runtime, and cross-node contracts.
  3. Establish a Spring Boot 3 Nacos Global Configuration Baseline: manage Redis, Redisson, RabbitMQ, Hikari, Tomcat, Actuator, and configuration override relationships.
  4. Postmortem: Boot 2/3 Redis Configuration Falling Back to localhost: explain Nacos property prefixes, lazy connection establishment, application-level compatibility aliases, and the commons-pool2 dependency trap.
  5. Optimize JDK 17 and G1 Container Memory: use the 3–4GiB memory differences between same-version Pods as the starting point, then manage heap, threads, message prefetch, glibc arenas, and diagnostic tools.
  6. Rightsize ZooKeeper Memory on Kubernetes: build a capacity model from real JVM parameters, mntr, and snapshots, lower Heap and resource requests in stages, and handle emptyDir risks.
  7. Optimize JDK 25 and ZGC Container Memory: break down Heap, Native Memory, and the cgroup working set, and verify Soft Max and memory return.
  8. Postmortem: Spring Boot 3 Container Startup Compatibility: work through filesystem, deprecated properties, classpath, and business code layer by layer to resolve directory, logging, and empty-driver exceptions.
  9. Postmortem: Spring Boot 3.1.7 → 3.5.13 Upgrade: pin down the Batch Job name collisions, thread pool injection, and MongoDB health check issues that only surface once compilation succeeds.
  10. Plan the Spring Boot 3.5.13 → 4.1 Migration: map out just the new boundaries Boot 4 introduces for Cloud Alibaba, Config Data, Web containers, Jackson, and data access.

Why Not a Single Article

Cluster installation, application migration, and Nacos governance fail along completely different boundaries. Putting them in one article causes three problems:

  • Readers cannot tell which machine or which cluster a command should run on.
  • Troubleshooting gets buried in a long article and cannot be reused as a standalone manual.
  • After any component upgrade, the entire article needs to be revalidated.

After the split, each article follows the same structure:

目标 → 前置条件 → 文件准备 → 逐步执行 → 预期结果 → 故障判断 → 回滚 → 完成定义

Lab Environment Conventions

All examples use the following placeholders:

PlaceholderMeaning
<api-vip>Kubernetes API virtual address
<pod-cidr>Pod address range
<service-cidr>Service address range
<node-ip>Node management address
<image-registry>Approved image registry
<storage-server>Storage server address or DNS
<nacos-domain>Nacos access domain

If you need example IPs in a lab environment, use the documentation address ranges defined in RFC 5737; this article never shows real internal network addresses.

Stop Conditions for Each Phase

Do not move on to the next article if any of the following applies:

  • etcd or data backups have not completed restore verification.
  • Not all nodes are Ready, or cross-node Pod networking is broken.
  • Any one of ClusterIP, DNS, PVC, or Ingress fails a smoke test.
  • The three Nacos nodes are in inconsistent states, or the service instance list is empty.
  • There is no executable rollback plan for the old and new ingress.

The goal of this tutorial is not just to run every command to completion; it is to leave verifiable evidence at every step and always be able to return safely to the previous stable state.
