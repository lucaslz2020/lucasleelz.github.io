Spring Boot Pods Restarted Together — Was It Really Kubernetes or Nacos?

Restart-storm postmortem: rule out node failure via Last State, Exit Code, Events, previous logs; find blocked dependencies, pool waits, liveness amplification.

lucaslzAuthor
July 19, 2026 8 min read
#Kubernetes #Spring Boot #Postmortem #Feign #Probe
{ }

This article is based on a real incident, but service names, Pods, nodes, times, APIs, capacity, and organization details have all been generalized. Series navigation: Kubernetes Rebuild Migration Series.

The symptoms looked like a platform failure: multiple Spring Boot services restarted around the same time, with the logs simultaneously showing Nacos gRPC reconnects, JDBC connection acquisition failures, Feign timeouts, and probe failures.

Pick any single log line and you could easily reach three different conclusions:

  • A Kubernetes node failed.
  • A Nacos upgrade broke the entire site.
  • A JDK or memory problem.

The final evidence showed that the nodes and middleware had not restarted in sync. Business threads were held up by a slow dependency and database connection waits, while liveness read “temporarily unable to respond in time” as “the process is permanently dead”, amplifying the problem into a restart storm.

Incident Investigation Flow

flowchart LR
  A["Multiple Pods restarted"] --> B["Last State / Exit Code"]
  B --> C["Events and probes"]
  C --> D["previous logs"]
  D --> E["Node distribution"]
  E --> F["Shared dependency"]
  F --> G["Threads and connection pool blocked"]
  G --> H["Code timeout and degradation fix"]

Step 1: Don’t Start with the Current Logs

Once a Pod has restarted, kubectl logs shows the new container by default. Start by collecting:

kubectl -n <namespace> get pod <pod> -o jsonpath='
restartCount={.status.containerStatuses[0].restartCount}{"\n"}
reason={.status.containerStatuses[0].lastState.terminated.reason}{"\n"}
exitCode={.status.containerStatuses[0].lastState.terminated.exitCode}{"\n"}
startedAt={.status.containerStatuses[0].lastState.terminated.startedAt}{"\n"}
finishedAt={.status.containerStatuses[0].lastState.terminated.finishedAt}{"\n"}'

kubectl -n <namespace> logs <pod> --previous --timestamps \
  > reports/<pod>-previous.log

--previous is incident evidence — don’t wait until the Pod restarts again to think about saving it.

Step 2: Understanding Exit 137 and 143

Exit CodeCommon signalWhat it cannot prove by itself
137SIGKILL, possibly OOM or a force-kill after the grace periodCannot assert a JVM heap overflow from 137 alone
143SIGTERM, common with probe restarts, rollouts, or manual deletionCannot assert a normal release from 143 alone

Continue with reason:

kubectl -n <namespace> describe pod <pod>
kubectl -n <namespace> get events --sort-by=.lastTimestamp

If it’s OOMKilled, check the container limits, JVM Native Memory, and node pressure. If Liveness probe failed events keep appearing, investigate why the probe is timing out.

Step 3: Compare Whether the Pods Are Concentrated on the Same Node

kubectl get pods -A -o custom-columns='NS:.metadata.namespace,POD:.metadata.name,NODE:.spec.nodeName,RESTARTS:.status.containerStatuses[0].restartCount' \
  | sort

If the failing Pods are scattered across multiple Ready nodes while other workloads on those nodes stay healthy, a single-node failure (kubelet, containerd, disk, or network) becomes less likely.

Also check the nodes:

kubectl get nodes
kubectl describe node <node> | sed -n '/Conditions:/,/Addresses:/p'
kubectl get events -A --field-selector involvedObject.kind=Node --sort-by=.lastTimestamp

Step 4: Build a Timeline Instead of Searching for a Keyword

Sort the key events from all previous logs by time:

rg -n -i 'liveness|readiness|timeout|refused|connection|pool|nacos|shutdown|killed' reports/

This incident unfolded in this order:

Remote API responses keep slowing down
→ Feign calls hold up business threads
→ Database connection pool waits increase
→ Health endpoint can't return within the timeout
→ Liveness fails repeatedly
→ kubelet sends SIGTERM
→ Some processes don't exit within the grace period
→ Containers are restarted

Nacos reconnects were also in the logs, but the timeline showed the Nacos StatefulSet rollout happened in an earlier maintenance window, so you can’t automatically assume adjacent log lines share the same root cause.

Step 5: Distinguish “Co-occurrence” from “Shared Root Cause”

Build a comparison table:

ComponentRestarted?Healthy?At the same time as the incident
Kubernetes NodeNoReadyNo
NacosNo, separate rolloutThree nodes availableNo
RedisNoPING OKNo
Message middlewareNoMembers healthyNo
Multiple business PodsYesliveness timed outYes

The table rules out the “all underlying components crashed at once” narrative and narrows the scope to shared business dependencies and probe design.

Step 6: Find the Remote Call Without a Boundary

The problematic call was a non-core attachment query. It was nested inside the main business query but had no dedicated short timeout, so when the downstream slowed down, requests held threads for a long time.

Set a boundary for a single Feign client:

spring:
  cloud:
    openfeign:
      client:
        config:
          attachment-api:
            connectTimeout: 3000
            readTimeout: 5000
            loggerLevel: basic

Spring Cloud OpenFeign supports per-client URL, connect, and read settings. Check the exact properties against your project’s Release Train in the official documentation.

Only retry idempotent requests, and keep retries bounded. When the downstream is already slow, unlimited retries turn one bout of congestion into even more concurrent load.

Step 7: Make Optional Dependencies Truly Degradable

Attachments are not payment, order, or report master data. The desired behavior is:

Attachment query succeeds → return attachments
Attachment times out → log an alert with the business key, return no attachments
Main business data → return normally

Pseudo-code:

try {
    return attachmentClient.findByBusinessKey(businessKey);
} catch (RetryableException ex) {
    log.warn("attachment lookup degraded, businessKey={}", businessKey, ex);
    return List.of();
}

Degradation must not swallow core data write failures, and it must not treat every exception as “no attachment”. Catch only explicit remote connection/timeout exceptions, and alert on the degradation count.

Step 8: Check Connection Pools and Thread Pools

Remote call blocking can cause:

  • Web request threads to be exhausted.
  • Spring Batch partition threads to wait.
  • Druid/Hikari connection acquisition timeouts.
  • The health endpoint to time out alongside business requests because they share resources.

Monitor all of these at the same time:

HTTP active threads
Feign latency/error
JDBC active/pending connections
Kafka/Rabbit listener lag
GC pause
readiness/liveness latency

Seeing CannotCreateTransactionException doesn’t mean the database is down. If the underlying cause is InterruptedException, the thread may have been interrupted while the Pod was terminating.

Step 9: Widening the Probe Is Only a Temporary Stopgap

Temporarily making liveness more tolerant can keep short dependency jitter from killing the process immediately:

livenessProbe:
  periodSeconds: 10
  timeoutSeconds: 5
  failureThreshold: 12

But this only pushes the restart window out to roughly 120 seconds. If threads are permanently blocked, the process will still restart; without code timeouts, traffic keeps queueing.

The correct order is:

Temporarily shrink the restart blast radius
→ Set timeouts and isolation on dependencies
→ Implement business degradation
→ Verify threads and connection pools recover
→ Calibrate probes against the data

Step 10: Verify the Fix

In the test environment, deliberately make the attachment service delay exceed the read timeout:

Main business API returns within the required time
Attachment fields clearly reflect the degraded result
Feign timeout metrics increase
Web threads don't keep accumulating
Database connection pool waits recover
Liveness always succeeds
Pod restartCount doesn't increase

After deployment, observe:

kubectl -n <namespace> get pods -w
kubectl -n <namespace> logs deployment/<app> --since=30m \
  | grep -Ei 'attachment lookup degraded|liveness|timeout|shutdown'
kubectl top pod -n <namespace>

How to Recognize Nacos Rolling Upgrade Logs

When the Nacos Client shows:

RST_STREAM closed stream
HTTP/2 error code: CANCEL
reconnect

First compare:

kubectl -n <nacos-namespace> get pod -o wide
kubectl -n <nacos-namespace> get controllerrevision
kubectl -n <nacos-namespace> rollout history statefulset/nacos

If the log lines correspond strictly to Nacos Pods being replaced one by one, and clients then reconnect automatically with instances recovering, this is more like connection switching during an upgrade. Only when the timing, instance state, and business failures all line up can it be judged as the root cause of the incident.

Root Cause and Improvements

Root Cause

  • The optional remote dependency had no dedicated short timeout.
  • Slow calls occupied business threads and triggered connection-pool waits.
  • The liveness health check was too sensitive to temporary resource congestion.

Amplifying Factors

  • Multiple services shared the same probe template.
  • Nacos reconnects in the logs muddied the initial diagnosis.
  • previous logs weren’t collected and saved centrally from the start.

Improvements

  • Give every external dependency explicit timeouts, retries, isolation, and degradation.
  • Liveness should only check whether the process can self-heal; readiness should reflect the ability to accept traffic.
  • Centralize collection of Last State, Events, and previous logs.
  • Maintain timelines and Revision records for releases and middleware upgrades.

Conclusion

Multiple Pods restarting at the same time is a symptom, not the root cause. The most reliable investigation path is:

Termination state → events → previous container logs → node distribution → shared dependencies → threads/connection pools → probe amplification

The platform layer is usually the one delivering the final “kill the process”, but the real reason the process couldn’t respond in time may lie in an ordinary business call with no timeout boundary.
