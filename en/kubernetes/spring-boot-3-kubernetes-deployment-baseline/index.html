How 50 Spring Boot Services Were Unified into a Single Kubernetes Deployment Template

A retrospective on multi-service Deployment governance: consolidating duplicate templates to unify rolling releases, probes, JVM settings, cache directories, security contexts, message concurrency, resource classes, and cross-node scheduling policy.

lucaslzAuthor
August 9, 2026 9 min read
#Kubernetes #Spring Boot #Deployment #Rolling Release #Configuration Governance
{ }

This article is based on Deployment governance work for a set of Spring Boot services running on managed Kubernetes. Service names, images, namespaces, and capacities have been generalized. Series navigation: Kubernetes Rebuild Migration Tutorial Series.

The initial problems looked unrelated:

  • Two Pods often landed on the same node.
  • Some services stayed Pending for a long time during rolling releases.
  • Nacos could not create /root/nacos at startup.
  • The file upload component caused Spring Context startup to fail with mkdir failed.
  • Some services consistently used 3–4 GiB; others only 1 GiB.
  • Warehousing services ran many RabbitMQ listeners, and in-flight messages kept pushing up the heap.
  • Some Deployments still had JProfiler loaded; others had it disabled.
  • Five “almost identical” Java Deployments kept drifting further apart.

Patching each service’s YAML individually would quickly reintroduce configuration drift. The final solution was not to merge five workloads into one Deployment, but to:

一份参数化模板
→ 渲染出多个相互独立的 Deployment
→ 结构和安全基线一致
→ 只让资源、端口、节点池等数据存在差异

What “Merging Deployments” Actually Merges

A Deployment can only describe one kind of Pod template. Different services still need their own:

  • Deployment name.
  • Image and version.
  • Service and port.
  • Replica count.
  • Rollback limits.
  • Scaling and release cadence.

What should actually be merged is the duplicated template source:

旧结构
common Deployment
finance Deployment
finance-rest Deployment
system-setting Deployment
repair-check Deployment

新结构
一份 Java Deployment 模板
+ app.name / app.port / app.replicas / resourceClass / nodePool 等参数

That way, changing probes or the security context touches only one place while still generating multiple Kubernetes Deployments.

Baseline Structure Overview

flowchart TD
  A["Parameterized Java Deployment"] --> B["Rolling release and availability"]
  A --> C["Scheduling and failure domains"]
  A --> D["Container security and writable directories"]
  A --> E["JVM and diagnostics"]
  A --> F["RabbitMQ in-flight volume"]
  A --> G["Resource classes"]
  B --> H["Rendered independent Deployments"]
  C --> H
  D --> H
  E --> H
  F --> H
  G --> H

The six parts should be reviewed together. Tuning only the JVM while letting probes kill Pods during GC, or forcing cross-node placement without reserving request capacity for the third Pod during rollouts, will create new incidents.

Layer 1: Give Rollouts an Explicit Completion Condition

spec:
  replicas: <replicas>
  revisionHistoryLimit: 5
  progressDeadlineSeconds: 600
  minReadySeconds: 20
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1

What each one means:

  • maxUnavailable: 0: do not actively remove old replicas before new Pods are stable.
  • maxSurge: 1: add at most one temporary replica during the rollout.
  • minReadySeconds: 20: becoming Ready does not mean the Pod is stable yet.
  • progressDeadlineSeconds: the controller explicitly reports failure once the rollout gets stuck.
  • revisionHistoryLimit: keeps a bounded set of rollback revisions so ReplicaSets do not grow without limit.

This strategy requires the node pool to be able to temporarily accommodate a surge Pod. The scheduler reserves based on requests, not on the instantaneous usage reported by kubectl top.

Complete templates for probes, preStop, graceful shutdown, and PDB are already provided in Kubernetes seamless rolling rollout. This article will not repeat them; it only defines the selection rules for the unified template:

  • Spring Boot 3 Servlet services use Actuator liveness/readiness.
  • Netty, gateway, and WebSocket services that do not yet expose Availability use TCP probes for now.
  • Compatibility exceptions must be visible in the template conditions and carry a migration deadline.
  • liveness must not touch databases, Redis, RabbitMQ, or remote HTTP.

Layer 2: Security Hardening Requires Explicit Writable Directories

Security baseline:

spec:
  automountServiceAccountToken: false
  enableServiceLinks: false
  securityContext:
    seccompProfile:
      type: RuntimeDefault

containers:
  - name: application
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop: [ALL]

Third-party SDKs may still write Nacos failover data, upload resume checkpoints, and temp files based on HOME or user.home. The template gives them a bounded writable emptyDir:

volumeMounts:
  - name: tmp-volume
    mountPath: /tmp

env:
  - name: HOME
    value: /tmp
  - name: JDK_JAVA_OPTIONS
    value: >-
      -Duser.home=/tmp
      -DJM.SNAPSHOT.PATH=/tmp
      -DJM.LOG.PATH=/data/java/logs/nacos

volumes:
  - name: tmp-volume
    emptyDir:
      sizeLimit: 2Gi

emptyDir.sizeLimit stops temp files from consuming node ephemeral storage without bound. Data that really needs to survive across Pods should still use PVC or object storage; a writable path does not turn emptyDir into persistent storage.

For the directory incidents, the exception chain, and the Nacos paths, see Spring Boot 3 container startup failure postmortem; this article will not repeat the stack analysis.

Each parameter’s rationale is maintained in exactly one article. The Deployment template references those conclusions instead of copying the full tuning process.

Layer 4: One Template, Tiered Resources

A unified template does not mean every service gets the same capacity. Keep a small set of auditable resource classes:

TypeCPU requestMemory requestMemory limitScope
standard250m1536Mi4GiRegular APIs
medium500m2Gi4GiProcurement, warehousing, etc.
heavy500m4Gi5GiFinance or batch processing

Every exception needs evidence, such as steady-state P95, peaks, GC, thread counts, and the temporary capacity required for rolling releases. Do not let if app.name == ... grow without limit; when exceptions multiply, switch to an explicit resourceClass parameter.

Layer 5: Spread Multi-Replica Workloads Across Nodes Without Deadlocking Rollouts

On Kubernetes 1.30, you can enforce spreading based on the current ReplicaSet revision:

topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: DoNotSchedule
    matchLabelKeys:
      - pod-template-hash
    labelSelector:
      matchLabels:
        app: <application>
        version: <version>

The Kubernetes topology spread documentation explicitly shows how pod-template-hash distinguishes Deployment revisions.

Without matchLabelKeys, the old and new ReplicaSets may both participate in the skew calculation. In a maxUnavailable: 0 rollout, old Pods are still running while new Pods are blocked by strict spread, so the rollout can deadlock.

DoNotSchedule guarantees that two replicas of the same revision never land on the same host, as long as the target node pool has at least two eligible nodes and enough request capacity. If “start as fast as possible” matters more than enforcing failure domains, choose ScheduleAnyway explicitly instead of vaguely saying “spread as much as possible.”

Template Release Order

One template affects dozens of services, so the release order must be more conservative than for an ordinary application:

  1. Render the template and save the complete YAML of the target Deployment.
  2. Run schema checks and a server-side dry-run.
  3. Pilot with one ordinary two-replica service.
  4. Wait until the new ReplicaSet is fully Ready and has passed minReadySeconds.
  5. Verify Nacos, Redis, RabbitMQ, the database, and real endpoints.
  6. Check replica node distribution, GC logs, RSS, and connection counts.
  7. Then take on one heavy service and one service with legacy Boot compatibility.
  8. Roll out in batches; do not restart dozens of clients at the same time.

Verification commands:

kubectl apply --server-side --dry-run=server -f rendered.yaml
kubectl -n <namespace> rollout status deployment/<name> --timeout=10m
kubectl -n <namespace> get pod -l app=<name> -o wide
kubectl -n <namespace> get rs -l app=<name>
kubectl -n <namespace> describe pod <new-pod>

A rolling restart only rebuilds Pods according to the current Deployment spec in the cluster. A modified template in the Git repository does not mean the live spec has been updated; you must run the render and release pipeline first.

Definition of Done

  • All Java services are rendered from the same template but remain independent Deployments.
  • The common template does not include periodic GC or diagnostic agents that are not universally validated.
  • startup, readiness, and liveness each have distinct responsibilities.
  • Nacos, uploads, and temp file writes are confined to controlled writable volumes.
  • RabbitMQ concurrency and prefetch have globally conservative ceilings with business exceptions.
  • requests are based on actual P95/peaks and reserve capacity for surge Pods.
  • Two-replica workloads are forced to spread across nodes by revision.
  • Security context, SIGTERM, heap dumps, and log paths are validated.
  • Every application exception has a reason, an owner, and removal conditions.

Final Conclusion

The value of a unified Deployment is not saving a few YAML files, but converging the runtime contract shared by dozens of services into one place:

如何启动
+ 如何被探测
+ 如何退出
+ 可以写哪里
+ 最多使用多少资源
+ 消息同时在途多少
+ 副本如何跨故障域

Once the structure is unified, differences become visible. Heavy-resource services can keep using higher tiers, and legacy gateways can temporarily keep TCP probes — but all of these must be explicit parameters, not copy-paste that drifts across five Deployments.
