Kubernetes v1.36.3 from Scratch: A kubeadm Tutorial on Rocky Linux

Build a kubeadm high-availability cluster: network planning, Rocky Linux initialization, kube-vip, Calico, metrics, storage, Ingress, and acceptance.

lucaslzAuthor
May 30, 2026 19 min read
#Kubernetes #kubeadm #Rocky Linux #Calico #Nacos #Migration
{ }

This article is a retrospective of a real migration. Node names, addresses, domains, namespaces, business counts, and internal repository details have been redacted or generalized; the examples cannot be used directly in production.

Series navigation: Kubernetes Rebuild Migration Series. This article covers building a healthy empty cluster from scratch.

Instead of running multiple kubeadm upgrade commands in sequence on the old control plane, this upgrade created a brand-new Kubernetes v1.36.3 cluster and then migrated nodes, data, middleware, configuration, and workloads in stages.

This article does more than present conclusions. It follows the actual execution order, from creating a working directory all the way to the workload switchover. You can copy the commands into your own ops repository and replace every <...> placeholder.

The main reason for choosing a rebuild over an in-place upgrade was that the old environment had accumulated problems: an aging OS, nodes with unclear purposes, fixed Service IPs, legacy namespaces, inconsistent network rules, and scattered stateful services. Upgrading only the control plane would have carried all of those problems unchanged into the new version.

In the end, the hardest part of the migration was not getting Pods to show Running, but making the whole chain below work end to end:

节点
→ CNI / kube-proxy
→ PVC 与真实数据
→ Pod Ready
→ Service Endpoint
→ Service DNS / 服务注册
→ Gateway / Ingress
→ 登录与真实业务请求
→ 外部入口

Migration Goals and the Final Architecture

The final cluster uses:

  • Rocky Linux 10.2.
  • Kubernetes v1.36.3.
  • containerd with systemd cgroup.
  • A three-node control plane and etcd.
  • kube-vip for the virtual API address.
  • Calico for the Pod network.
  • NGINX Ingress with three replicas.
  • NFS dynamic storage and a small number of local PersistentVolumes.
  • metrics-server for node and Pod metrics.
  • A three-node Nacos cluster.
  • Node pools divided by business, data, ingress, monitoring, shared, and reserved purposes.

The network plan was frozen before the control plane was created. The Pod CIDR, Service CIDR, and node network must not overlap, and applications must not confuse the three address types.

flowchart LR
  A["Old cluster and virtualization platform inventory"] --> B["etcd, resource, and data backup"]
  B --> C["Bulk Rocky Linux reinstall"]
  C --> D["HA control plane creation"]
  D --> E["Calico, Ingress, storage, metrics"]
  E --> F["Zero-replica pre-deployment"]
  F --> G["Data service recovery"]
  G --> H["Nacos and Service DNS governance"]
  H --> I["Batch workload startup"]
  I --> J["Real requests and ingress switchover"]

Before You Start: Set Up a Versioned Working Directory

Don’t scatter downloaded files, backups, temporary patches, and final manifests across the download folder on the ops machine. Create a dedicated directory first:

mkdir -p cluster-migration/{inventory,backup,images,manifests,scripts,reports}
cd cluster-migration

git init
printf 'backup/\n*.key\n*.kubeconfig\n.env\n' > .gitignore

The recommended structure is:

cluster-migration/
├── inventory/       # 节点、服务、存储和域名清单
├── backup/          # 不进入 Git 的备份及校验值
├── images/          # 镜像和 digest 清单
├── manifests/       # kubeadm、CNI、存储和业务清单
├── scripts/         # 可重复执行的初始化与验证脚本
└── reports/         # 每个阶段的验收结果

Then create a .env that is never committed to Git:

cat > .env <<'EOF'
K8S_VERSION=v1.36.3
API_VIP=<api-vip>
POD_CIDR=<pod-cidr>
SERVICE_CIDR=<service-cidr>
CONTROL_PLANE_1=<control-plane-1>
CONTROL_PLANE_2=<control-plane-2>
CONTROL_PLANE_3=<control-plane-3>
EOF

chmod 600 .env

This article doesn’t use real addresses. For public documentation, use the dedicated documentation networks such as 192.0.2.0/24 or 198.51.100.0/24; in real execution, replace them with your own plan.

Step 1: Turn the Server Inventory into Verifiable Data

Don’t maintain only a free-form Excel spreadsheet. At minimum, export a CSV as well:

hostname,ip,role,pool,cpu,memory_gib,disk_gib,local_data
cp-a,<node-ip>,control-plane,control-plane,8,32,100,false
worker-a,<node-ip>,worker,app-dev,8,32,100,false
data-a,<node-ip>,worker,data,16,64,500,true

First check for duplicate IPs or hostnames:

cut -d, -f1 inventory/nodes.csv | tail -n +2 | sort | uniq -d
cut -d, -f2 inventory/nodes.csv | tail -n +2 | sort | uniq -d

Neither command should output anything. Then check the number of node pools:

cut -d, -f4 inventory/nodes.csv | tail -n +2 | sort | uniq -c

This step is simple, but it catches problems early, such as a node listed in two business pools or a reserved node mistakenly treated as a data node.

Step 2: Export Resources from the Old Cluster

First confirm that you’re operating on the old cluster:

kubectl config current-context
kubectl cluster-info
kubectl get nodes -o wide

Then export namespaced and cluster-scoped resources separately. In production, use a reviewed script to export each resource type; the commands below only show the structure:

kubectl get deploy,statefulset,daemonset,job,cronjob -A -o yaml \
  > backup/workloads.yaml

kubectl get svc,ingress,configmap,pvc -A -o yaml \
  > backup/application-resources.yaml

kubectl get pv,storageclass,clusterrole,clusterrolebinding,crd -o yaml \
  > backup/cluster-resources.yaml

Secrets must be handled separately:

umask 077
kubectl get secret -A -o yaml > backup/secrets.yaml

backup/secrets.yaml must never be committed to Git, sent over chat apps, or distributed through ordinary file sharing. After the export, compute checksums for the backups:

sha256sum backup/*.yaml > backup/SHA256SUMS

Also save the replica counts, because the new cluster will start all workloads at zero replicas:

kubectl get deployment,statefulset -A \
  -o custom-columns='KIND:.kind,NAMESPACE:.metadata.namespace,NAME:.metadata.name,REPLICAS:.spec.replicas' \
  > inventory/workload-replicas.txt

Step 3: Create and Verify an etcd Snapshot

On a control plane node, find the etcd certificates and endpoint, then run:

ETCDCTL_API=3 etcdctl snapshot save /backup/etcd-snapshot.db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=<etcd-ca> \
  --cert=<etcd-client-cert> \
  --key=<etcd-client-key>

ETCDCTL_API=3 etcdctl snapshot status /backup/etcd-snapshot.db \
  --write-out=table

Copy the snapshot to separate storage and run a restore on an isolated host:

etcdutl snapshot restore /backup/etcd-snapshot.db \
  --data-dir /var/lib/etcd-restore-test

If the restore directory can be created and the member information can be read, the snapshot has demonstrated at least basic recoverability. A formal drill should also start an isolated etcd and API server to verify the objects.

Step 4: Build a Unified Node Initialization Script

Don’t type commands by hand on each machine. Create scripts/prepare-node.sh; at minimum, the script should:

#!/usr/bin/env bash
set -euo pipefail

swapoff -a
sed -ri '/\sswap\s/s/^#?/#/' /etc/fstab

cat >/etc/modules-load.d/kubernetes.conf <<'EOF'
overlay
br_netfilter
EOF

modprobe overlay
modprobe br_netfilter

cat >/etc/sysctl.d/99-kubernetes.conf <<'EOF'
net.bridge.bridge-nf-call-iptables=1
net.bridge.bridge-nf-call-ip6tables=1
net.ipv4.ip_forward=1
EOF

sysctl --system
systemctl enable --now containerd
systemctl enable kubelet

After the containerd configuration is generated, verify it:

containerd config dump | grep -E 'SystemdCgroup|sandbox_image'
crictl info

SystemdCgroup=true is expected, and the pause image should come from a repository you have verified is pullable.

Step 5: Complete Firewall Setup Before Joining the Cluster

Allow the planned Pod CIDR on every node:

firewall-cmd --permanent --zone=trusted --add-source=<pod-cidr>
firewall-cmd --reload
firewall-cmd --zone=trusted --query-source=<pod-cidr>

The last command must output yes. Then write the result to the report:

hostname
firewall-cmd --zone=trusted --list-sources

Don’t simply disable firewalld long term. Disabling the firewall may make the network recover quickly, but it removes an auditable security boundary.

Step 6: Generate the kubeadm Configuration and Pre-Pull Images

Create manifests/kubeadm.yaml:

apiVersion: kubeadm.k8s.io/v1beta4
kind: ClusterConfiguration
kubernetesVersion: v1.36.3
controlPlaneEndpoint: <api-vip>:6443
imageRepository: <kubernetes-image-mirror>
networking:
  dnsDomain: cluster.local
  podSubnet: <pod-cidr>
  serviceSubnet: <service-cidr>
apiServer:
  certSANs:
    - <api-vip>
    - <api-dns-name>
    - <control-plane-1-ip>
    - <control-plane-2-ip>
    - <control-plane-3-ip>

Pre-pull the images on the three control plane nodes:

kubeadm config images list --config manifests/kubeadm.yaml
kubeadm config images pull --config manifests/kubeadm.yaml

If this fails, resolve the image registry, DNS, and certificate issues first; do not proceed to kubeadm init.

Step 7: Initialize the First Control Plane Node

On the first control plane node, run:

sudo kubeadm init --config manifests/kubeadm.yaml --upload-certs \
  | tee reports/kubeadm-init.log

After initialization succeeds, save the two kubeadm join commands from the output. They are for control plane and worker nodes respectively and contain short-lived tokens; never commit them to Git.

Configure kubeconfig for the current admin:

mkdir -p "$HOME/.kube"
sudo install -m 600 /etc/kubernetes/admin.conf "$HOME/.kube/config"
sudo chown "$(id -u):$(id -g)" "$HOME/.kube/config"

kubectl get nodes
kubectl get pods -A

At this point the first node is usually NotReady, and CoreDNS may be Pending. That’s because the CNI isn’t installed yet; don’t mistake it for a kubeadm failure.

Step 8: Deploy the HA Virtual Address for the API

A three-node control plane must not have clients pinned to a single node. This article uses kube-vip in static Pod mode to provide <api-vip>.

Generate the manifest on the first control plane node. The image version must be pinned and the image scanned before the migration:

export VIP=<api-vip>
export INTERFACE=<node-interface>
export KVVERSION=<approved-kube-vip-version>

sudo ctr image pull <kube-vip-image>:${KVVERSION}
sudo ctr run --rm --net-host <kube-vip-image>:${KVVERSION} vip /kube-vip manifest pod \
  --interface "$INTERFACE" \
  --address "$VIP" \
  --controlplane \
  --services \
  --arp \
  --leaderElection \
  | sudo tee /etc/kubernetes/manifests/kube-vip.yaml >/dev/null

Check the virtual address and the API:

ip address show dev <node-interface>
curl --cacert /etc/kubernetes/pki/ca.crt https://<api-vip>:6443/readyz

/readyz should return ok. If there’s no VIP, check the kubelet logs and the static Pod first:

sudo crictl ps -a --name kube-vip
sudo journalctl -u kubelet -n 100 --no-pager

Step 9: Install Calico and Get Nodes Truly Ready

Save the reviewed, version-pinned Calico manifest to manifests/calico.yaml. Before installing, confirm that its address pool exactly matches the <pod-cidr> in kubeadm:

grep -n '<pod-cidr>' manifests/calico.yaml
kubectl apply -f manifests/calico.yaml
kubectl -n kube-system rollout status daemonset/calico-node --timeout=10m
kubectl get nodes

All nodes should gradually enter Ready, and CoreDNS should enter Running. Then run a DNS test:

kubectl run dns-check --image=<approved-busybox-image> --restart=Never \
  --command -- nslookup kubernetes.default.svc.cluster.local
kubectl logs dns-check
kubectl delete pod dns-check

Seeing the Calico Pods running isn’t enough. At minimum, create two test Pods on different nodes that reach each other’s Pod IP and a ClusterIP Service, proving that cross-node routing and Service forwarding both work.

Step 10: Join the Remaining Control Plane and Worker Nodes

Join the other two control plane nodes first, then the worker nodes. The control plane command looks like:

sudo kubeadm join <api-vip>:6443 \
  --token <bootstrap-token> \
  --discovery-token-ca-cert-hash sha256:<ca-hash> \
  --control-plane \
  --certificate-key <certificate-key>

Worker nodes omit the last two flags:

sudo kubeadm join <api-vip>:6443 \
  --token <bootstrap-token> \
  --discovery-token-ca-cert-hash sha256:<ca-hash>

If a token expires, regenerate it on an existing control plane node:

kubeadm token create --print-join-command
sudo kubeadm init phase upload-certs --upload-certs

After everything has joined, check that the control plane and etcd static Pods are evenly distributed:

kubectl get nodes -o wide
kubectl -n kube-system get pods -o wide | grep -E 'kube-apiserver|etcd'
kubectl get --raw='/readyz?verbose'

Step 11: Install Metrics, Storage, and Ingress

Install the core add-ons in a fixed order:

metrics-server → StorageClass → 动态制备器 → Ingress Controller

Verify each component with a small acceptance check as you go; don’t run kubectl apply -f manifests/ all at once:

kubectl apply -f manifests/metrics-server.yaml
kubectl -n kube-system rollout status deployment/metrics-server --timeout=5m
kubectl top nodes

kubectl apply -f manifests/storage/
kubectl get storageclass

kubectl apply -f manifests/ingress-nginx/
kubectl -n ingress-nginx rollout status deployment/ingress-nginx-controller --timeout=10m

Storage must be tested with reads and writes on a temporary PVC, and Ingress must be tested with Host-based routing on a temporary domain. The full manifests live in the “Core Add-ons” article of this series — don’t move on to the business migration just because Pods are Running.

Step 12: Complete Cluster-Level Acceptance

Create reports/cluster-baseline.txt and record the output of the following commands:

kubectl get nodes -o wide
kubectl get pods -A -o wide
kubectl get storageclass
kubectl top nodes
kubectl get ingressclass
kubectl get --raw='/readyz?verbose'

At this point, the new empty cluster is complete. The series then continues by topic:

  • Core add-ons: step-by-step deployment and acceptance of Calico, metrics-server, Ingress, and NFS.
  • Node scheduling: labels, taints, affinity, and anti-affinity for data services.
  • Business migration: zero-replica pre-deployment, data recovery, phased rollout, ingress switchover, and rollback.
  • Nacos: three-node cluster setup, Service DNS governance, and smooth upgrades.

Retrospective: Why the First Step Was Inventory, Not Installation

Before migrating, build an inventory of servers and workloads. For each node, record at least:

  • The virtualization host and VM identifiers.
  • IP, hostname, CPU, memory, and disk.
  • Whether it hosts local disks, databases, Ingress, proxies, or the control plane.
  • The mapping from old hostnames to new hostnames.
  • The target node pool, labels, taints, and tolerations.

For the old cluster, export separately:

  • Deployments, StatefulSets, DaemonSets, CronJobs.
  • Services, Ingresses, Endpoints, ConfigMaps, Secrets.
  • PVCs, PVs, StorageClasses, and local directories.
  • RBAC, CRDs, and cluster-level resources.
  • Current replica counts of each workload and the CronJob suspend state.

Saving YAML alone isn’t enough. What’s easiest to lose during recovery is “runtime state” and “where the data actually lives.” So replica counts, node affinity, storage locations, and data verification must be recorded separately.

Backups Must Prove They Can Be Restored

Before reinstalling nodes, make three kinds of backups:

  1. An etcd snapshot.
  2. A full archive of Kubernetes resources.
  3. Data backups for databases, message systems, NFS, and hostPath data.

Minimum verification includes:

etcdctl snapshot status /backup/etcd-snapshot.db --write-out=table
tar -tzf /backup/kubernetes-resources.tgz | head
sha256sum /backup/* > /backup/SHA256SUMS

A truly reliable approach is to run an etcd restore in an isolated environment and restore a sample of the databases. A normal snapshot status only proves the file is readable; it does not prove the restore process is complete.

The OS Baseline Comes Before kubeadm

All nodes are prepared with the same versioned initialization script:

swapoff -a
modprobe overlay
modprobe br_netfilter
sysctl --system

systemctl enable --now containerd
systemctl enable kubelet

containerd consistently uses:

SystemdCgroup = true

Also enable bridged traffic and IPv4 forwarding:

net.bridge.bridge-nf-call-iptables=1
net.bridge.bridge-nf-call-ip6tables=1
net.ipv4.ip_forward=1

The most typical network failure this time came from firewalld: the Pod IP returned by Nacos was healthy, but cross-node clients hit No route to host when accessing it. The cause was not Nacos; the nodes simply didn’t trust the Calico Pod CIDR.

The correct approach is to add <pod-cidr> to the trusted zone permanently before kubeadm, and after Calico is installed, run a one-off DaemonSet to recalibrate every node. Don’t wait until workloads start to add rules node by node.

For data services that still use hostNetwork, separately verify whether the target node’s ports allow traffic after Pod SNAT. The long-term approach should be to reduce hostNetwork and expose services through the normal Pod network and Services.

Control Plane and Core Add-ons

The HA control plane uses three nodes. Once the version, API VIP, Pod CIDR, Service CIDR, and DNS domain in the kubeadm configuration are frozen, they should not be changed during the business migration.

apiVersion: kubeadm.k8s.io/v1beta4
kind: ClusterConfiguration
kubernetesVersion: v1.36.3
controlPlaneEndpoint: <api-vip>:6443
networking:
  dnsDomain: cluster.local
  podSubnet: <pod-cidr>
  serviceSubnet: <service-cidr>

After the control plane is complete, install in order:

  1. Calico.
  2. The NFS provisioner.
  3. metrics-server.
  4. NGINX Ingress.
  5. Logging, monitoring, and other required system components.

The kubectl on the ops machine should stay within the officially supported version skew of the API server. The Kubernetes documentation states that kubectl supports only one minor version above or below kube-apiserver. See Version Skew Policy.

Node Pools Are About Failure Boundaries, Not Tidiness

Nodes are divided into control plane, ingress, platform base services, business, data, monitoring, shared, and reserved pools. The scheduling strategy uses all of the following together:

  • nodeSelector to target a specific pool.
  • Taints to keep unauthorized workloads off dedicated pools.
  • Tolerations to let matching workloads schedule.
  • required Pod Anti-Affinity to spread replicas of Kafka, ZooKeeper, Nacos, and similar services.

A common mistake is adding labels without taints. Then workloads that “target a node pool” look fine, but other Pods without a nodeSelector still land on dedicated nodes. Another mistake is adding taints first and tolerations later, which leaves large numbers of Pods Pending.

Labels, taints, and tolerations must be generated as matching pairs in Git and dry-run in advance.

Land Resources First, Keep Replicas at Zero

Old objects can’t be imported as-is. Remove:

  • uid
  • resourceVersion
  • managedFields
  • creationTimestamp
  • status
  • Auto-generated ServiceAccount tokens
  • Helm release Secrets
  • Labels and resources from the old cluster management platform

Create Services, Ingresses, ConfigMaps, Secrets, PVCs, and so on first; set Deployments and StatefulSets to zero replicas initially; suspend CronJobs.

This step surfaces problems early:

  • YAML that is incompatible with the new API.
  • Fixed ClusterIP conflicts.
  • PVCs that cannot bind.
  • Missing images or missing pull credentials.
  • Service selectors that don’t match Pod labels.
  • Incomplete node labels and toleration configuration.

Stateful Services Must Be Restored Layer by Layer

The startup order is fixed:

存储与 PVC
→ MySQL / MongoDB / Redis / RabbitMQ / Zookeeper
→ Kafka
→ PostgreSQL 与辅助服务
→ Nacos
→ 平台依赖
→ 业务服务

A database can’t be considered migrated just because “an empty database with the same name was created.” At minimum, verify tables, permissions, key row counts, indexes, and queries with real application accounts.

Redis troubleshooting is also layered:

redis-cli PING
→ Pod Endpoint
→ ClusterIP
→ Service DNS
→ 真实应用接口

If the Endpoint is healthy but the ClusterIP fails, check kube-proxy on the source node first; restarting the business Pod or changing Nacos won’t fix the Service forwarding table.

Nacos: A Running Process Doesn’t Mean a Usable Registry

Nacos runs as three StatefulSet Pods. The Headless Service gives each member stable DNS, and the regular ClusterIP Service gives clients a single entry point.

nacos-0.nacos-hs.platform.svc.cluster.local
nacos-1.nacos-hs.platform.svc.cluster.local
nacos-2.nacos-hs.platform.svc.cluster.local

nacos-cs.platform.svc.cluster.local:8848

During the migration, Nacos logs showed successful startup, but clients still couldn’t register. The root cause turned out to be an incompatibility between the run-mode switch and gRPC registration. After the fix, acceptance was done in three layers:

  1. All three Pods are Ready, and all three members are healthy.
  2. All three nodes have the same run mode.
  3. The same test client is visible in the instance lists on all three nodes.

Only after all three layers pass should you continue starting OAuth, gateways, and business services.

Migrating from Fixed IPs to Service DNS

Many internal services in the old configuration used ClusterIPs:

rbac.api.url=http://<cluster-ip>:8082
spring.data.redis.host=<cluster-ip>

After the migration:

rbac.api.url=http://rbac-api.app-test.svc.cluster.local:8082
spring.data.redis.host=redis-service.app-test.svc.cluster.local

But don’t use a regex to replace every IP with DNS:

  • Deleted Services have no replacement target.
  • Kafka advertised listeners need to be designed separately.
  • External databases, SMS, and private network addresses are not Kubernetes Services.
  • A few Jenkins or ingress dependencies may temporarily keep fixed ClusterIPs, but they must be whitelisted and recorded in Git.

Pod Running Is Only the Starting Point of Acceptance

Start workloads namespace by namespace, in batches. For each batch, check at least:

kubectl -n <namespace> get deployment,statefulset,pod
kubectl -n <namespace> get svc,endpointslice
kubectl -n <namespace> get event --sort-by=.lastTimestamp

Then run real requests:

  • Login and token refresh.
  • Users, roles, and permissions.
  • Redis sessions.
  • File upload and download.
  • RabbitMQ and Kafka produce/consume.
  • Database reads and writes.
  • WebSocket connection setup.
  • CI/CD release interfaces.

An unauthenticated endpoint returning “not logged in” only proves the path from the ingress to the business service is reachable; it can’t replace post-login business verification.

Rollback Must Be Designed Before the Migration

Rollback has four layers:

  1. Ingress rollback: restore the old routing, VIP, or DNS.
  2. Object rollback: restore Services, Ingresses, RBAC, and PVC/PV from the resource archive.
  3. Configuration rollback: roll back precisely by Nacos namespace, group, and dataId.
  4. Data rollback: restore from database backups, binlog/WAL, and storage snapshots.

Once the new environment starts accepting writes, rollback is no longer just switching the ingress. You must define how incremental data is handled to avoid double writes or data regression between the old and new environments.

Final Thoughts

The value of a rebuild-style upgrade is not just getting a new-version cluster; it also cleans up the implicit dependencies the old system had accumulated: fixed IPs, undocumented node purposes, backups that couldn’t be restored, messy taints, dead routes, and untraceable manual configuration.

Only four principles are truly reusable:

  1. Freeze all designs before the switchover.
  2. Prove all stateful data can be restored before reinstalling.
  3. Every stage has an acceptance gate that can’t be skipped.
  4. Define completion by real business requests, not by Pod status.
