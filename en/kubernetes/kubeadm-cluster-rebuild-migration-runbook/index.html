Kubernetes Rebuild Migration Runbook: From Firefighting to Phase-Gated Acceptance

A kubeadm cluster rebuild migration runbook: baseline freeze, backup/restore, node setup, networking, data, Nacos, business acceptance, stop/rollback rules.

lucaslzAuthor
July 5, 2026 10 min read
#Kubernetes #Runbook #kubeadm #Disaster Recovery #DevOps
{ }

All node names, addresses, domains, environment names, and capacity figures in this article are anonymized examples. Secrets, database backups, tokens, and internal repository information are not publishable content.

Series navigation: Kubernetes Rebuild Migration Tutorial Series. This post covers migration-day execution, stop conditions, and rollback.

The previous post reviewed the problems encountered during the rebuild migration. Rather than rehashing the incident timeline, this post distills those lessons into a runbook that can be executed phase by phase.

“All at once” does not mean one command starts every node and workload. It means that during the migration window, only verified, versioned artifacts are executed — no ad-hoc changes to YAML, Nacos, Service IPs, node taints, or firewalls.

General principle: stop when a phase fails

flowchart LR
  A["Freeze design"] --> B["Backup and restore drill"]
  B --> C["OS baseline"]
  C --> D["HA control plane"]
  D --> E["CNI and infrastructure"]
  E --> F["Zero-replica pre-deployment"]
  F --> G["Data recovery"]
  G --> H["Nacos and platform dependencies"]
  H --> I["Business batch startup"]
  I --> J["Real business acceptance"]
  J --> K["Ingress switchover"]

Every arrow is a hard gate. When a phase fails, the only options are:

  1. Roll back the current batch.
  2. Fix the source configuration in Git.
  3. Re-run the dry-run and review.
  4. Restart from the failed phase.

Do not use kubectl edit, ad-hoc patches, fixed sleeps, or Pod restarts to paper over configuration errors.

Phase 0: Freeze the immutable baseline

Before creating the first control plane, freeze:

  • Kubernetes, kubeadm, kubelet, and kubectl versions.
  • OS and containerd versions.
  • Control plane nodes and the API VIP.
  • Pod CIDR, Service CIDR, and cluster DNS domain.
  • CNI, Ingress, StorageClass, and metrics-server choices.
  • Nacos version and cluster mode.
  • Image sources and digests.
  • Node pools, labels, taints, and tolerations.

The three network types must have clear boundaries:

NetworkPurposeWritten into app config?
Node networkVMs, nodes, and a few external dependenciesOnly when truly necessary
Pod CIDRPod IPs allocated by CNINever
Service CIDRClusterIPOnly in the compatibility allowlist

Applications use the following internally by default:

<service>.<namespace>.svc.cluster.local:<port>

Phase 1: Prepare all inputs

Before execution, the following must be in place:

  • An inventory of servers, VMs, disks, and node pools.
  • A mapping from old hostnames to new hostnames.
  • An etcd snapshot and an archive of Kubernetes resources.
  • Backups of databases, messaging systems, and file storage.
  • Nacos namespaces, groups, dataIds, contents, and checksums.
  • An inventory of images and digests.
  • A Service DNS replacement table and a fixed ClusterIP allowlist.
  • Mappings for domains, certificates, Ingress, and the external entry point.
  • Rollback owners, stop conditions, and recovery commands.

If any input is missing, do not reinstall an old node that still holds data.

Phase 2: Complete the restore drill

The backup matrix can be built as follows:

ServiceBackupAcceptance
etcdsnapshotIsolated restore; API objects readable
MySQLFull backup, user grants, binlogKey tables, row counts, app-account queries
PostgreSQLdump/base backup, roles, WALSchema, extensions, application queries
MongoDBdump/snapshot, auth databaseCollections, indexes, business queries
RedisRDB/AOF, configPING, key spot checks, TTL sampling
KafkaTopics, partitions, offsetsBrokers, ISR, consumer groups
RabbitMQDefinitions, vhosts, usersExchanges, queues, bindings
NFS/hostPathFile or storage snapshotsFile counts, capacity, checksum sampling

“The backup file exists” alone is not completion. The restore drill is the real gate.

Phase 3: Make all configuration changes in Git first

Before the migration, complete the following static governance:

  • Internal URLs switched to Service DNS.
  • Pod IP references eliminated.
  • Fixed ClusterIPs kept only on the allowlist.
  • Kafka advertised listeners reviewed individually, never string-replaced.
  • Deployment resources, probes, scheduling, DNS, and graceful shutdown standardized.
  • Read-only fields and old management-platform metadata removed from exported objects.
  • Deployments and StatefulSets start with 0 replicas.
  • CronJobs start with suspend=true.

Common static scans:

rg -n '<pod-cidr-pattern>' config/ manifests/
rg -n '<service-cidr-pattern>' config/ manifests/
rg -n 'node[0-9]+' manifests/

Scan results must not be bulk-replaced. Each hit must be classified as a Service, a node, an external dependency, or leftover junk configuration.

Phase 4: Standardize the node baseline

After reinstalling, run the same script on every node:

swapoff -a
modprobe overlay
modprobe br_netfilter
sysctl --system
systemctl enable --now containerd
systemctl enable kubelet

Verify node by node:

hostnamectl
ip address
ip route
timedatectl
swapon --show
systemctl is-active containerd
crictl info

firewalld rules must be in place before kubeadm runs. Every node must allow forwarding of the Pod CIDR; for hostNetwork services, add minimal rules scoped to the actual ports.

Phase 5: Create the control plane

The order is fixed:

  1. Initialize the first control plane.
  2. Deploy kube-vip and verify the API VIP.
  3. Join the remaining control planes.
  4. Check the etcd members.
  5. Test VIP leader failover.
  6. Generate the worker join commands and store them safely.

Control plane acceptance items:

  • The API VIP is continuously reachable.
  • All three control plane nodes are Ready.
  • All three etcd members are healthy.
  • kubeconfig points at the VIP, not a single host.
  • The certificate SAN includes the real access addresses.

Phase 6: Install networking and infrastructure

After installing the CNI, first verify cross-node Pod IPs, CoreDNS, Service ClusterIPs, and external DNS.

Then install, in order:

  1. The default StorageClass.
  2. metrics-server.
  3. The Ingress Controller.
  4. Logging and monitoring.

Run a PVC smoke test at least once per node pool; the metrics stack is only considered usable once both kubectl top nodes and kubectl top pods -A return data.

Phase 7: Labels, taints, and zero-replica pre-deployment

Set the target labels and taints immediately after a node joins, so unmarked nodes do not participate in scheduling.

Use required Pod anti-affinity for multi-replica stateful services:

podAntiAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
    - topologyKey: kubernetes.io/hostname
      labelSelector:
        matchLabels:
          app: zookeeper

Hard checks after resource pre-deployment:

  • PVCs are Bound or have an explicit recovery plan.
  • Service selectors exactly match Pod labels.
  • Fixed ClusterIPs do not conflict.
  • Every image can be pulled.
  • No old hostnames remain.
  • Disabled environments stay at 0 replicas.

Phase 8: Data recovery

Fixed order:

存储
→ 基础数据库与消息组件
→ Kafka
→ PostgreSQL 与辅助服务
→ Nacos 数据库
→ Nacos

Every service must be verified from three entry points: a Pod on the same node, a Pod on another node, and Service DNS. Looking only at Pod Ready cannot reveal kube-proxy, firewalld, or DNS problems.

Phase 9: Nacos cluster acceptance

The three Nacos Pods need two kinds of Service:

ServiceTypePurpose
nacos-hsHeadlessStable member DNS and cluster interconnect
nacos-csClusterIPUnified client entry point

Three-layer acceptance:

  1. All three members are healthy.
  2. The run-mode setting is identical across all three nodes.
  3. After a test client registers, all three nodes can query the same instance.

Only then import the Nacos configuration, and read back every namespace, group, dataId, and checksum one by one.

Phase 10: Platform dependencies and staged business startup

Start platform dependencies first — auth, dictionaries, files, workflows — then OAuth, Gateway, and DevOps. The first auth service must be a hard gate:

  • Deployment Ready.
  • The Service has Endpoints.
  • Instances are consistent across the three Nacos nodes.
  • OAuth is reachable via Service DNS.
  • An invalid login returns a clear business error, not “no available instances”.

Start only one business namespace at a time. Move on to the next batch only after the current one fully passes.

Phase 11: Ingress and real business acceptance

First bypass the external entry point and call the Ingress directly:

curl --resolve app.example.com:443:<ingress-address> \
  https://app.example.com/

Once it succeeds inside the cluster, configure Host/SNI forwarding on the router, NLB, or proxy layer. If it returns 200 in the cluster but fails on the public network, do not modify Kubernetes workload resources.

Real acceptance must cover at least:

  • Successful login, failed login, and Token refresh.
  • Permissions, files, and Session.
  • Database reads and writes.
  • Kafka/RabbitMQ produce and consume.
  • WebSocket.
  • CI/CD upload and release.

Automatic stop conditions

Stop immediately if any of the following happens:

  • The etcd or database backup cannot be restored.
  • Network CIDRs conflict.
  • API VIP failover fails.
  • CNI or kube-proxy is not fully ready.
  • Data checks are inconsistent.
  • Nacos instances are inconsistent across the three nodes.
  • The core auth chain is unavailable.
  • Unacceptable data write errors occur.
  • A public-network failure would require modifying business Pods to work around it.

Go / No-Go checklist

  • The server and node pool inventory has no duplicates or gaps.
  • Versions, networking, and images are frozen.
  • etcd and database restore drills are done.
  • File storage is backed up.
  • Nacos configuration is exported, converted to DNS, and read back.
  • The fixed ClusterIP allowlist is reviewed.
  • Labels, taints, and tolerations are validated in pairs.
  • The firewall initialization script is verified.
  • The inventory of both Nacos Service types is complete.
  • Domains, certificates, and entry mappings are prepared.
  • All resources can be pre-deployed with zero replicas.
  • Real acceptance requests and expected results are prepared.
  • Rollback entry points, owners, and stop conditions are confirmed.

Definition of done

The migration is complete only when all of the following hold:

全部节点 Ready
+ 基础组件健康
+ 数据恢复并通过应用查询
+ Nacos 三节点一致
+ Service DNS 与 Endpoint 正常
+ 活跃业务全部 Ready
+ 登录与核心业务成功
+ 公网入口成功
+ 配置和脚本已进入 Git
+ 旧集群经过观察窗口后下线

The real value of a runbook is not making operations more “mechanical”; it is turning on-the-spot decisions that relied on personal memory into an engineering process that can be reviewed, paused, rolled back, and reproduced.
