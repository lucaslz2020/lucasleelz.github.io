How to Troubleshoot Kubernetes Service Access Failures: The Full Path from DNS to kube-proxy

For Connection refused, No route to host, timeouts, and Nacos reporting no available instances, isolate the fault layer by layer across DNS, Service, Endpoint, Pod, CNI, kube-proxy, and the firewall.

lucaslzAuthor
June 28, 2026 6 min read
#Kubernetes #Service #kube-proxy #Calico #Troubleshooting
{ }

One of the easiest problems to misdiagnose during a business migration is assuming that because the application logs mention Nacos, Redis, or Feign, the fault must be in Nacos, Redis, or the code. In practice, the failure is often in Service forwarding or cross-node networking.

Series navigation: Kubernetes Rebuild Migration Tutorial Series. This post also works as a standalone troubleshooting manual for the migration period and daily on-call duty.

This article lays out a fixed troubleshooting path. When something fails, work through it top to bottom instead of restarting every Pod up front.

Narrow Down by Error Type First

ErrorTypical meaning
UnknownHostExceptionThe DNS name doesn’t exist, or CoreDNS is unavailable
Connection refusedThe packet reached the target host, but no port is listening or traffic is forwarded to the wrong port
Connect timed outRouting, firewall, NetworkPolicy, or the target isn’t responding
No route to hostCross-node routing, firewall, or the CNI address range is unreachable
Load balancer does not have available serverThe registry has no healthy instances, or the client didn’t subscribe correctly
HTTP 404The request reached an HTTP service, but the Host, Path, or Gateway route doesn’t match

Errors are clues, not conclusions.

Layer 1: Confirm What Address the Client Is Actually Using

Enter the failing Pod and inspect its environment variables and the configuration actually in effect:

kubectl -n <namespace> exec <client-pod> -- env \
  | grep -Ei 'nacos|redis|gateway|service'

If the configuration comes from Nacos, also read back the matching Data ID. Don’t rely only on what’s in Git: at runtime the settings may be overridden by environment variables, startup arguments, or remote configuration.

Layer 2: Verify DNS

kubectl -n <namespace> exec <client-pod> -- \
  getent hosts <service>.<namespace>.svc.cluster.local

If the image has no debugging tools, start a temporary diagnostic Pod:

kubectl -n <namespace> run net-debug --rm -it --restart=Never \
  --image=<approved-network-tool-image> -- sh

If DNS fails, check:

kubectl -n kube-system get deployment,pod -l k8s-app=kube-dns -o wide
kubectl -n kube-system logs deployment/coredns --tail=200
kubectl -n <namespace> get networkpolicy

Layer 3: Inspect the Service Definition

kubectl -n <target-namespace> get service <service> -o yaml

Verify that:

  • The selector matches the labels of the target Pods.
  • port is the port clients use to access the Service.
  • targetPort points to the port the container actually listens on, or to the correct named port.
  • No stale ClusterIP from the old cluster is in use.

Compare the labels right away:

kubectl -n <target-namespace> get pods --show-labels
kubectl -n <target-namespace> get pods -l '<service-selector>' -o wide

Layer 4: Check EndpointSlices

kubectl -n <target-namespace> get endpointslice \
  -l kubernetes.io/service-name=<service> -o yaml

If there are no addresses, the selector usually doesn’t match, or the Pods aren’t Ready. If addresses exist but conditions.ready: false, check the readiness probe.

Note a Ready Pod’s IP and port; later you’ll test both direct Pod access and access through the Service.

Layer 5: Connect Directly to the Pod IP

From the client Pod, run:

kubectl -n <namespace> exec <client-pod> -- \
  nc -vz <target-pod-ip> <target-port>

How to read the results:

  • Pod IP unreachable: focus on CNI, node routing, the firewall, and NetworkPolicy.
  • Pod IP reachable but ClusterIP unreachable: focus on kube-proxy or the Service rules.
  • Both reachable: continue with the application protocol, authentication, Gateway, or Nacos registration data.

Layer 6: Repeat the Test on Different Nodes

A Service failure can be limited to a single node. List the node running the client:

kubectl -n <namespace> get pod <client-pod> -o wide

Start temporary Pods on the failing node and on a healthy node, and access the same ClusterIP from both. If only one node fails, the problem is already narrowed down to that node’s kube-proxy, CNI, iptables/nftables, or firewall.

Layer 7: Check kube-proxy

kubectl -n kube-system get pods -l k8s-app=kube-proxy -o wide
kubectl -n kube-system logs <kube-proxy-pod-on-bad-node> --tail=200

Compare the ConfigMap against the running mode:

kubectl -n kube-system get configmap kube-proxy -o yaml

Restart kube-proxy only on the failing node:

kubectl -n kube-system delete pod <kube-proxy-pod-on-bad-node>
kubectl -n kube-system get pod -l k8s-app=kube-proxy -o wide -w

Deleting a DaemonSet Pod lets the controller recreate it automatically. Don’t delete kube-proxy on every node at once without evidence.

Layer 8: Check Node Routing and the Firewall

Log in to the failing node:

ip route
sudo firewall-cmd --get-active-zones
sudo firewall-cmd --zone=trusted --list-sources
sudo sysctl net.ipv4.ip_forward

The Pod CIDR must be routed correctly or included in a trusted zone, and net.ipv4.ip_forward should be 1.

For Calico environments, continue with:

kubectl -n kube-system get pod -l k8s-app=calico-node -o wide
kubectl -n kube-system logs <calico-pod-on-bad-node> -c calico-node --tail=200

Layer 9: Check Nacos and the Application Last

If the network layers are all healthy but the client still reports no available services, check the following in Nacos:

  • The namespace, group, and cluster match.
  • The service name’s case and prefix match.
  • The instance IP isn’t still an old-cluster Pod IP.
  • The instance’s health and ephemeral status.
  • The client hasn’t enabled an incorrect dual-write or compatibility mode.

Accessing the dependency’s health address from inside the target application Pod is more meaningful than checking from an operations machine.

Use a Controlled Comparison to Avoid Misdiagnosis

The most effective troubleshooting table is:

Test locationPod IPClusterIPService DNSResult
Pod on failing node<pod-ip><service-ip><service-fqdn>Record
Pod on healthy node<pod-ip><service-ip><service-fqdn>Record
Target Pod locallylocalhostN/AN/ARecord

This table quickly separates application port issues, cross-node CNI issues, and Service forwarding issues.

Acceptance Check After the Fix

kubectl -n <namespace> exec <client-pod> -- \
  curl -fsS http://<service>.<target-namespace>.svc.cluster.local:<port>/<health-path>

kubectl -n <namespace> logs <client-pod> --since=10m \
  | grep -Ei 'refused|timed out|no route|available server'

Then run one real business request. Network commands recovering is only the first layer of evidence; you must ultimately verify the real chain—Gateway, login, queries, or message consumption.

The Final Principle

DNS → Service → EndpointSlice → Pod 端口 → 跨节点网络 → kube-proxy → 防火墙 → 注册中心 → 业务

Working through the layers in a fixed order pays off because each step rules out an entire layer. Restarting every Pod may make the symptoms disappear temporarily, but it neither proves the root cause nor prevents the failure from recurring after the next node drift.
