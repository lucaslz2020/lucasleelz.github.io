Moving Fixed Service IPs in Nacos to Kubernetes DNS: A Practical Guide

How to inventory hundreds of Nacos configs, safely migrate ClusterIPs to Service DNS, and treat Redis, Kafka, external, and deleted services separately.

lucaslzAuthor
June 20, 2026 12 min read
#Nacos #Kubernetes #Service DNS #Redis #Configuration Governance
{ }

The namespaces, service names, domains, addresses, and config counts in this article have been anonymized or generalized. Real configuration backups may contain passwords and tokens, and must never end up in a blog post or Git repository.

Series navigation: Kubernetes Rebuild Migration Series. This article assumes the Nacos cluster has already been deployed and passed acceptance.

After a Kubernetes cluster migration, the most insidious class of failure isn’t Pods failing to start — it’s Service ClusterIPs from the old cluster still sitting in Nacos configs.

Typical symptoms include:

Load balancer does not have available server
Unable to connect to Redis
No route to host
connect timed out

The old IP may not exist in the new cluster at all, or it may happen to be assigned to another Service. The latter is more dangerous than a plain timeout because requests get forwarded to the wrong service.

So the goal of this pass isn’t to swap one IP for another, but to move to stable Kubernetes Service DNS wherever possible.

Below is the full procedure, followed by an explanation of why some addresses cannot be automatically replaced.

Step 1: Create an Isolated Working Directory

mkdir -p nacos-dns-migration/{backup,inventory,candidates,reports}
cd nacos-dns-migration

git init
printf 'backup/\n*.zip\n*.token\n.env\n' > .gitignore

Original Nacos exports may contain passwords, tokens, and database addresses, so keep them only under backup/ and use encrypted storage. Git should contain only the sanitized rules, scripts, and report templates.

Create a change manifest:

namespace,group,data_id,old_value,target_service,target_port,action,owner,status
app-test,DEFAULT_GROUP,global.properties,<old-address>,redis-service,6379,replace,team-a,pending

Every publish action must be traceable to a row in this manifest.

Step 2: Export Nacos Configurations

The safest approach is to export a config archive per namespace from the Nacos console, recording the export time, the operator, and the file checksum:

sha256sum backup/<namespace>-configs.zip \
  > backup/<namespace>-configs.zip.sha256

If you export automatically via the OpenAPI, verify the API paths, authentication, and compatibility against the current Nacos Server version. Nacos 3.2 removed some legacy HTTP APIs, so old scripts can’t be run directly against the new cluster.

After extracting to a temporary directory, run a read-only scan first:

mkdir -p backup/unpacked
unzip -q backup/<namespace>-configs.zip -d backup/unpacked

rg -n --glob '*.{properties,yaml,yml,json,xml}' \
  '([0-9]{1,3}\.){3}[0-9]{1,3}' backup/unpacked \
  > reports/ip-references.txt

Don’t print full lines containing secrets in the scan output. A real script should mask the values of keys such as password, secret, and token.

Step 3: Export Service Inventories for Both Clusters

Export using explicit kubeconfigs; don’t rely on the current context:

kubectl --kubeconfig <old-kubeconfig> get service -A -o json \
  > inventory/old-services.json

kubectl --kubeconfig <new-kubeconfig> get service -A -o json \
  > inventory/new-services.json

Convert to TSV for easier review:

jq -r '
  .items[]
  | select(.spec.clusterIP != "None")
  | [
      .metadata.namespace,
      .metadata.name,
      .spec.clusterIP,
      (.spec.ports | map((.port|tostring) + ":" + (.targetPort|tostring)) | join(","))
    ]
  | @tsv
' inventory/old-services.json > inventory/old-services.tsv

jq -r '
  .items[]
  | select(.spec.clusterIP != "None")
  | [
      .metadata.namespace,
      .metadata.name,
      .spec.clusterIP,
      (.spec.ports | map((.port|tostring) + ":" + (.targetPort|tostring)) | join(","))
    ]
  | @tsv
' inventory/new-services.json > inventory/new-services.tsv

Now you can look up a Service by its old IP:

rg -F '<old-service-ip>' inventory/old-services.tsv

Expected output:

app-test    rbac-api    <old-service-ip>    8082:8082

The target DNS is:

rbac-api.app-test.svc.cluster.local

Step 4: Confirm the Target Service and Port One by One

First check whether a Service with the same name exists in the new cluster:

kubectl --kubeconfig <new-kubeconfig> -n app-test \
  get service rbac-api -o yaml

kubectl --kubeconfig <new-kubeconfig> -n app-test \
  get endpointslice \
  -l kubernetes.io/service-name=rbac-api -o wide

An entry qualifies for the automatic candidate list only when all of the following hold:

  • The old IP resolves to exactly one Service.
  • A semantically equivalent Service exists in the new cluster.
  • The configured port matches the new Service’s port, not a mistakenly used targetPort.
  • The EndpointSlice has at least one Ready address.
  • The owner confirms the dependency still exists.

Everything else is marked manual-review; the script must not guess.

Step 5: Generate Candidate Files Without Publishing Directly

Copy an original config:

cp backup/unpacked/global.properties \
  candidates/global.properties

Change:

rbac.api.url=http://<old-service-ip>:8082

to:

rbac.api.url=http://rbac-api.app-test.svc.cluster.local:8082

Then review the diff:

diff -u backup/unpacked/global.properties \
  candidates/global.properties \
  | tee reports/global.properties.diff

Confirm each line during review:

  • Only the host part changed; the protocol, port, path, and parameters are intact.
  • No external dependency was rewritten to cluster DNS.
  • No Kafka broker address was collapsed into a plain Service.
  • No nonexistent Service name was introduced.

Step 6: Verify DNS Early from a Business Pod

Before the production publish, test the target address from a real caller Pod:

kubectl -n <caller-namespace> exec <caller-pod> -- \
  getent hosts rbac-api.app-test.svc.cluster.local

kubectl -n <caller-namespace> exec <caller-pod> -- \
  nc -vz rbac-api.app-test.svc.cluster.local 8082

If this step fails, editing Nacos is pointless. Fix the Service, Endpoint, NetworkPolicy, CNI, or kube-proxy first.

Step 7: Publish One Data ID at a Time

For the first governance pass, it’s recommended to operate through the Nacos console:

  1. Enter the correct namespace.
  2. Search for the exact Data ID and Group.
  3. Open the history to confirm rollback is available.
  4. Paste the candidate content and review the diff in the console.
  5. Publish only one Data ID.
  6. Read it back immediately and download it once, comparing checksums.

If you use an automated API, the script must implement authentication, timeouts, pre-publish backup, post-publish read-back, content verification, and single-Data-ID rollback. Don’t run a loop that unconditionally overwrites an entire namespace.

Step 8: Roll Only the Affected Clients

First confirm whether the config supports dynamic refresh. For apps that can’t refresh dynamically, do a rolling restart:

kubectl -n <caller-namespace> rollout restart deployment/<caller-app>
kubectl -n <caller-namespace> rollout status deployment/<caller-app> --timeout=10m

Check recent logs:

kubectl -n <caller-namespace> logs deployment/<caller-app> --since=10m \
  | grep -Ei 'nacos|refused|timed out|no route|available server'

Don’t restart every namespace at once just because one shared global.properties changed. Roll out in batches along dependency chains, and continue only after the previous batch passes real business acceptance.

Step 9: Run Real Requests and Search for Old Addresses

In addition to health checks, complete real requests such as logins, queries, cache reads/writes, or internal RPC. Then search the configs and runtime logs for the old address:

rg -n -F '<old-service-ip>' candidates reports

kubectl -n <caller-namespace> logs deployment/<caller-app> --since=30m \
  | grep -F '<old-service-ip>'

Neither the candidate configs nor new logs should contain the old Service IP anymore.

Step 10: Roll Back per Data ID

If business acceptance fails:

  1. Stop publishing other Data IDs.
  2. Restore the changed content from Nacos history.
  3. Read back to confirm the restore succeeded.
  4. Roll the clients that were just affected.
  5. Keep the failure logs and failed requests.

Don’t import the entire old namespace archive — it would overwrite normal configs that other teams published during the migration.

Why Fixed ClusterIPs Become Migration Debt

The ClusterIP lifecycle belongs to the Service object. After a Service is deleted and recreated without an explicit clusterIP, the address may change.

A config like this binds the application to a particular cluster state:

rbac.api.url=http://10.x.y.z:8082
spring.data.redis.host=10.x.y.z

A more stable form is:

rbac.api.url=http://rbac-api.app-test.svc.cluster.local:8082
spring.data.redis.host=redis-service.app-test.svc.cluster.local

As long as the Service name and namespace stay the same, changes to Pods, Endpoints, and ClusterIPs don’t affect callers.

Build the Source of Truth Before Replacing

For every Nacos config reference, collect four kinds of data:

  1. The old cluster’s Service name, namespace, ClusterIP, and port.
  2. The new cluster’s Service name, namespace, ClusterIP, and port.
  3. Stable config from production or other homogeneous environments.
  4. Whether the Deployment, StatefulSet, and Endpoint actually exist right now.

Then classify every address:

TypeHandling
Kubernetes Service that still existsChange to full Service DNS and verify the port
Deleted or unmigrated ServiceDon’t auto-replace; first decide whether to restore or remove the route
Pod IPNever keep it; find the corresponding Service
Kafka broker addressDesign a dedicated listener; don’t do a plain DNS replacement
hostNetwork service on a nodeEvaluate whether it can become a Service; register an exception if not
External database, SMS, private network systemsKeep the original external address

This step determines whether the governance is safe. Regular expressions can only find addresses; they can’t determine address ownership.

Why You Can’t Replace Every IP

Deleted Services

If an old address points to a Service that no longer exists, changing it to:

missing-service.app-test.svc.cluster.local

only turns a connection timeout into a DNS resolution failure. There are exactly two correct choices: restore the target Service, or remove the config and route that are no longer used.

Kafka Advertised Listeners

A Kafka client doesn’t just connect to a single entry point. The bootstrap server returns the brokers’ advertised addresses, and the client then connects directly to those brokers.

So a NodePort or node address originally exposed per broker can’t simply be turned into a plain ClusterIP. You need to design first:

  • Internal and external listeners.
  • A per-broker Service.
  • Advertised listeners.
  • DNS, NodePort, or load balancer entry points.

Handle Kafka address governance as a separate project.

External Dependencies

SMS, cloud databases, partner APIs, and private network systems aren’t part of Kubernetes. Just because they’re IPs too doesn’t mean they should be rewritten as svc.cluster.local.

Config Publishing Must Support Rollback

Before every change, save:

  • namespace.
  • group.
  • dataId.
  • original content.
  • MD5 or another checksum.

Publish flow:

flowchart LR
  A["Export configs"] --> B["Identify IPs and URLs"]
  B --> C["Map Services and ports"]
  C --> D["Generate candidate changes"]
  D --> E["Manually review exceptions"]
  E --> F["Publish per dataId"]
  F --> G["Read back and compare checksums"]
  G --> H["Roll clients and verify"]

Don’t overwrite an entire namespace at once, and don’t commit backup files to Git. Rollback should be scoped to a single dataId, rather than using an old export archive to overwrite other legitimate changes made since.

Validate Ports Together with the Service

Correct DNS doesn’t mean correct config. A common problem is that the service name was updated but the port still comes from the old environment.

Resolve each reference to:

namespace / service / configured-port

Then compare against the Kubernetes Service’s port, targetPort, and actual Endpoints. Final requirements:

  • DNS resolves.
  • The Service exists.
  • The configured port matches the Service port.
  • Endpoints aren’t empty.
  • The target Pod actually listens on that port.

Redis Config Needs to Accommodate Different Spring Boot Versions

Different services may read:

spring.data.redis.host
spring.redis.host
gateway.oauth2.redis.host
platform.redis.host

If the system is in the middle of a Spring Boot version upgrade, use the new properties as the source and keep temporary aliases for older services:

spring.data.redis.host=redis-service.app-test.svc.cluster.local
spring.data.redis.port=6379

spring.redis.host=${spring.data.redis.host}
spring.redis.port=${spring.data.redis.port}
spring.redis.password=${spring.data.redis.password}
spring.redis.database=${spring.data.redis.database}

Compatibility aliases need documented removal conditions, so you don’t maintain two config sets forever.

If an old application has already fallen back to localhost:6379, or you see missing commons-pool2 classes after adding Lettuce pool parameters, see the Boot 2/3 Redis Config Fallback Postmortem.

Verification Doesn’t Stop at the Nacos Page

After publishing, verify in five layers:

1. Config Read-Back

Confirm that namespace, group, dataId, content, and MD5 match what was published.

2. DNS Resolution

From a real business Pod:

getent hosts redis-service.app-test.svc.cluster.local

3. Service and Endpoint

kubectl -n app-test get svc redis-service
kubectl -n app-test get endpointslice -l kubernetes.io/service-name=redis-service

4. Network Connectivity

Access the Service DNS and port from the caller Pod. If Endpoints are reachable but the Service isn’t, investigate kube-proxy on the request source node; if Pod IPs aren’t reachable across nodes, check the CNI and firewalld.

5. Real Business Requests

After restarting or refreshing the affected clients, run login, cache, messaging, or internal API requests. Old addresses shouldn’t keep appearing in the logs.

Separate Nacos Service Discovery from the Config Center

Nacos serves as both config center and service discovery, and the two problems are often conflated:

  • The config center determines the URLs for Redis, databases, internal APIs, and so on.
  • Service discovery decides whether a service has healthy instances.

When a gateway reports “no available services,” check the Nacos instance list; when an application connects to an old ClusterIP, check the config content. Restarting a Pod may briefly mask the symptoms, but it won’t fix the wrong source config.

Suggestions for Automated Auditing

Ongoing governance can include these checks:

1. 扫描所有 IPv4、URL 和主机名
2. 判断是否属于 Pod CIDR、Service CIDR 或节点网段
3. 将 Service IP 反查到 namespace/service
4. 校验配置端口和 Service port
5. 标记不存在的 Service DNS
6. 生成例外清单，而不是自动覆盖

For new configs, set up rules in CI:

  • No writes to the Pod CIDR.
  • No writes to the Service CIDR by default.
  • Full Service DNS is allowed.
  • Fixed ClusterIPs must reference a whitelist entry.
  • Secrets and config exports must never enter the repository.

Final Takeaways

The most important outcome of this pass isn’t how many addresses were replaced, but the clear boundaries it established:

  1. Prefer Service DNS for Kubernetes-internal dependencies.
  2. Deleted services can’t be fixed with invented DNS.
  3. Kafka, hostNetwork, and external systems must be classified separately.
  4. Every Nacos change needs a backup, item-by-item publishing, read-back, and verification with real requests.

A fixed IP isn’t always wrong, but it must be an explicit compatibility item with an owner, a reason, and a removal plan — not a legacy string whose origin nobody knows.

Once the address migration is stable, move on to the Spring Boot 3 Nacos Global Config Baseline to govern Redis, Redisson, RabbitMQ, Hikari, Tomcat, and config override relationships.
