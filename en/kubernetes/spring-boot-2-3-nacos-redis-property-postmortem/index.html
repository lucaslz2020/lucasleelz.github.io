Mixed Spring Boot 2/3 Cluster: Why Nacos Redis Config Falls Back to localhost

Why Spring Boot 2 in Kubernetes ignored Boot 3's Redis config: prefixes, Nacos dataIds, lazy connections, rolling releases, and commons-pool2.

lucaslzAuthor
August 8, 2026 9 min read
#Spring Boot #Nacos #Redis #Kubernetes #Postmortem
{ }

This post recounts a real troubleshooting session in a mixed Spring Boot 2/3 cluster. Service names, cluster, addresses, and business data have been generalized. Series navigation: Kubernetes Rebuild Migration Series.

After a global rollout of Redis connection-pool tuning, most Spring Boot 3 services ran fine, but a few gateways and WebSocket services kept reporting:

Unable to connect to localhost:6379

Redis was clearly deployed behind a Kubernetes Service, and Nacos held the correct address. What made it so misleading: some old services started successfully and only failed later, while others failed to start outright once connection-pool parameters were added, because commons-pool2 was missing.

In the end, this wasn’t a Redis, Service DNS, or network failure, but three issues compounding:

  1. Spring Boot 2 and 3 use different Redis property prefixes.
  2. A Redis client may not actually connect until the first request that uses it.
  3. Configuring connection-pool parameters changes the auto-configuration branch, and without the dependency it can actually prevent the application from starting.

Trace the Incident Chain First

flowchart LR
  A["Global config switched to spring.data.redis"] --> B["Boot 3 binds normally"]
  A --> C["Boot 2 ignores the new prefix"]
  C --> D["Keeps default localhost:6379"]
  D --> E["Connects only on first Redis access"]
  E --> F["Failure surfaces once business traffic runs"]
  C --> G["Pool parameters added blindly"]
  G --> H["commons-pool2 missing"]
  H --> I["New Pod fails to start"]

This chain explains how “the config is in Nacos”, “the Pod is Ready”, and “Redis is actually reachable” can all be true at the same time while the application still accesses localhost:6379.

Root Cause 1: Boot 2 and Boot 3 Do Not Share the Same Prefix

A common Spring Boot 2 configuration:

spring.redis.host=redis-service.app.svc.cluster.local
spring.redis.port=6379
spring.redis.database=0
spring.redis.timeout=3s

Spring Boot 3 uses:

spring.data.redis.host=redis-service.app.svc.cluster.local
spring.data.redis.port=6379
spring.data.redis.database=0
spring.data.redis.timeout=3s

Spring Boot’s official property lists confirm this version boundary directly: Boot 2.7 uses spring.redis.*, and Boot 3.5 uses spring.data.redis.*. Both default to host localhost and port 6379.

spring.redis.host and spring.data.redis.host are not the same property, and relaxed binding does not swap them automatically. When an old application receives the latter, it may not report an “unknown property”; instead, it may keep using the client defaults:

host = localhost
port = 6379

So localhost:6379 in the logs is very valuable evidence: it usually means the application never bound to the expected address, not that the cluster resolved the Redis domain to the local machine.

Root Cause 2: Successful Startup Does Not Mean the Redis Configuration Is Correct

Many services don’t access Redis immediately during Spring context initialization. For example:

  • Session is only read after a user logs in.
  • Online status is only written after a WebSocket connection is established.
  • A distributed lock is only acquired when a scheduled job fires.
  • A low-frequency endpoint is the only path that touches the cache.

Such services may pass startup, readiness, and even liveness probes, then fail only when a real request triggers a connection:

RedisConnectionFailureException
Unable to connect to localhost:6379

So “the new Pod is Ready” only proves the current probes passed; it does not prove that every lazily initialized external dependency is available.

Step 1: Build a Version and Configuration Matrix First

Don’t guess the Spring Boot version from the repository name. Confirm it from the build file, startup logs, or the executable JAR:

unzip -l app.jar | grep 'BOOT-INF/lib/spring-boot-[0-9]'

Then build a minimal matrix:

ServiceBoot versionRedis prefixConnects at startupHas commons-pool2
service-a3.xspring.data.redisNoYes
service-b2.3.xspring.redisNoNo
service-c2.7.xspring.redisYesYes

This table is far more reliable than changing the global config once and watching which services error out. In particular, treat services that haven’t accessed Redis yet as potential risks, not as healthy.

Step 2: Rule Out DNS, Service, and Redis Itself

Verify from inside a real business Pod that has the problem:

getent hosts redis-service.app.svc.cluster.local
nc -vz redis-service.app.svc.cluster.local 6379

Then confirm the Service and Endpoints from the cluster side:

kubectl -n app get svc redis-service
kubectl -n app get endpointslice \
  -l kubernetes.io/service-name=redis-service

If the name resolves, the port is reachable, and Endpoints are non-empty, yet the reported failing address is explicitly localhost:6379, the investigation should focus on property binding and configuration precedence.

Step 3: Confirm the Actual Source of the Properties in Nacos

The fact that a key can be found in Nacos doesn’t mean the application actually ends up using it. At minimum, confirm:

  • The namespace is correct.
  • The group is correct.
  • The dataId is loaded by the current application.
  • The precedence of shared, extension, and application dataIds.
  • Whether environment variables or command-line arguments override Nacos.
  • Whether the client really refreshed after publishing.

Record this chain in the change ticket:

application -> namespace -> group -> dataId -> key -> expected value

Also read back the freshly published configuration and compare the content or checksum; don’t rely only on the “publish succeeded” notice in the console.

Minimal-Risk Fix: Add Compatibility Aliases to the Old Application’s dataId

If the global configuration has been unified for Spring Boot 3, add only the following to the application-level dataId of services still on Boot 2:

spring.redis.host=${spring.data.redis.host}
spring.redis.port=${spring.data.redis.port}
spring.redis.database=${spring.data.redis.database}
spring.redis.timeout=${spring.data.redis.timeout}

This has three benefits:

  1. The Redis address is still maintained by one set of Boot 3 global properties.
  2. The compatibility scope covers only old applications, so deprecated keys don’t linger across every Boot 3 service.
  3. After an application is upgraded, the temporary aliases can be removed per dataId.

Don’t permanently put both prefixes into the global configuration just to “support all versions.” That widens the configuration surface and keeps Boot 3 applications triggering property-migration or deprecation warnings.

If the password comes from a Secret or a separate dataId, reference the existing value too; don’t copy plaintext into the compatibility configuration.

A Second Incident That’s Easy to Stumble Into: Connection Pool Parameters Activate a New Code Path

During troubleshooting it’s tempting to add:

spring.redis.lettuce.pool.max-active=16
spring.redis.lettuce.pool.max-idle=8
spring.redis.lettuce.pool.min-idle=2
spring.redis.lettuce.pool.max-wait=2s

But connection pool configuration is not a dependency-free performance parameter. For old applications without Apache Commons Pool 2, it can switch auto-configuration to the pooling branch and fail at startup:

NoClassDefFoundError:
org/apache/commons/pool2/impl/GenericObjectPoolConfig

Spring Boot’s property documentation also explicitly ties pool availability to commons-pool2; so don’t treat the pool keys as a purely numeric optimization on the Nacos side.

If the business genuinely needs a Lettuce connection pool, add the dependency explicitly in code first and verify the build:

<dependency>
  <groupId>org.apache.commons</groupId>
  <artifactId>commons-pool2</artifactId>
</dependency>

To contain the incident, the safer approach is:

  1. Only fill in host, port, database, and timeout.
  2. Don’t enable pool parameters whose dependencies haven’t been verified.
  3. Treat connection pool tuning as a separate code change with its own capacity test.

A configuration change doesn’t just change values; it can also change how Spring Boot’s conditional auto-configuration resolves. This must be part of the review checklist.

Why the Rolling Release Didn’t Take the Old Services Down With It

Under the Deployment’s default rolling strategy, when a new Pod fails to start, the old Pods usually stay and keep serving. That’s good, but it can easily create a false impression:

Deployment 有可用副本 ≠ 新版本发布成功

After the rollout, check all of the following:

kubectl -n app rollout status deployment/<deployment> --timeout=10m
kubectl -n app get pod -l app=<application> -o wide
kubectl -n app get rs -l app=<application>
kubectl -n app logs <new-pod> --since=20m

If the old ReplicaSet still has replicas and the new ReplicaSet’s Pods keep restarting, the business may be temporarily available, but the rollout has already failed.

Recommended Rolling Fix Order

  1. Back up the original content and checksum of the target dataId.
  2. Pick one low-risk Boot 2 service and add the four compatibility keys first.
  3. Read back Nacos and confirm the namespace, group, dataId, and content.
  4. Roll the Deployment and wait until the new ReplicaSet is fully Ready.
  5. Trigger a real Redis read/write path, not just a health endpoint.
  6. Search the new Pod logs for localhost:6379, connection exceptions, and missing classes.
  7. After verification passes, handle the remaining old services one by one using the version matrix.

Suggested log check:

kubectl -n app logs deployment/<deployment> --since=30m \
  | grep -Ei 'localhost:6379|RedisConnection|commons.pool2|GenericObjectPool'

Also check the Boot 2 services that previously looked fine; they may simply not have triggered any Redis access yet.

Definition of Done

This fix cannot be called done just because the Pod has stopped restarting. The completion criteria include at least:

  • Every service that uses Redis has its Spring Boot version confirmed.
  • Every Boot 2 service has an explainable application-level compatibility configuration.
  • New Pods all come from the target ReplicaSet and are Ready.
  • Real business paths that touch Redis read and write successfully.
  • localhost:6379 no longer appears in current or recent logs.
  • Services without a configured pool don’t accidentally load the pooling branch.
  • Every compatibility alias has an upgrade and removal condition.

Final Conclusion

The most important lesson from this incident isn’t “memorize two Redis prefixes.” It’s that configuration-center governance has to be designed together with the client version.

A global configuration can unify connection addresses, but you can’t assume different Spring Boot major versions have identical binding rules. A Ready Pod proves the process can serve for now, but it says nothing about connections established lazily. An ordinary-looking connection pool parameter can also change the auto-configuration path and introduce a new runtime dependency.

The more robust governance approach: build a version matrix first, use the new property set as the single source of truth, add minimal compatibility in old application dataIds, verify through real business paths, and remove the compatibility layer item by item as upgrades complete.
