Pod CIDR, Service CIDR, and Node Subnets in Kubernetes, Explained

Tracing real packet paths explains Node IP, Pod IP, Service ClusterIP, and DNS—plus address planning, overlap checks, migration, and verification.

lucaslzAuthor
May 31, 2026 7 min read
#Kubernetes #Networking #CIDR #Service #Calico
{ }

Series navigation: Kubernetes Rebuild Migration Tutorial Series. All addresses in this post use <...> placeholders and contain no real network information.

Seeing multiple IP ranges in the same Kubernetes cluster is not a sign of messy networking. Nodes, Pods, and Services each have distinct responsibilities. The real question is whether the ranges overlap, whether component configuration is consistent, and whether applications incorrectly depend on a temporary IP.

First, Trace Where a Request Goes

At least four kinds of addresses are involved:

AddressAssigned byBound directly to a processPrimary purpose
Node IPPhysical network, virtualization platform, or cloud providerYesNode management and cross-node hosting
Pod IPCNI, e.g., CalicoYesPod-to-Pod communication
Service ClusterIPkube-apiserverNoStable virtual entry point and traffic forwarding
External entry IPLB, VIP, Ingress, or routerDepends on implementationAccess from outside the cluster

The official Kubernetes networking model requires Nodes, Pods, and Services to use non-overlapping address ranges. A Service is only a logical entry point; its backends are kept up to date via EndpointSlice. Cluster Networking and Service define this in full.

Node IP: the machine a packet must eventually reach

kubectl get nodes -o wide
kubectl get node <node> -o jsonpath='{.status.addresses}'

The Node IP comes from the existing underlying network. Calico, kubelet, the API server, storage mounts, and operational SSH may all use it.

Record the following during planning:

  • The node management address range.
  • The default gateway and MTU.
  • The failure domain of physical machines or virtualization hosts.
  • The Pod address range allowed by the firewall.
  • Whether the VPN, office network, or dedicated lines overlap.

Don’t fold Node IPs into the Pod CIDR for the sake of “unification” — they live on different network layers.

Pod CIDR: Addresses the CNI Assigns to Workloads

In kubeadm, the Pod CIDR is usually written as:

networking:
  podSubnet: <pod-cidr>

Calico must use the same address pool:

kubectl get ippools.crd.projectcalico.org -o wide
kubectl get pod -A -o wide

Every ordinary Pod gets a Pod IP. The IP can change when the Pod is recreated, so:

  • Never write a Pod IP into Nacos configuration.
  • Never let clients save a Pod IP.
  • Discover backends through a Service or Headless Service.

When cross-node Pod IPs can’t reach each other, check CNI routes, encapsulation mode, MTU, and firewalld first, rather than editing Service DNS.

Service CIDR: a Virtual Address Pool with no NIC

In kubeadm, the Service CIDR is usually written as:

networking:
  serviceSubnet: <service-cidr>

Unlike a Node IP, a ClusterIP does not appear on any NIC. kube-proxy’s iptables, IPVS, or the CNI’s eBPF data plane forwards it to an Endpoint.

kubectl get service -A -o wide
kubectl get endpointslice -A

The Service CIDR should only be used inside the cluster. Applications should use DNS:

<service>.<namespace>.svc.cluster.local

instead of:

<cluster-ip>

The ClusterIP can change when a Service is deleted and recreated, but the DNS name stays valid as long as the Service name and namespace are unchanged.

CoreDNS Does Not Create a Fourth Business Network

CoreDNS watches the Kubernetes API and generates DNS records for Services and Pods. For an ordinary ClusterIP Service, DNS resolves to the ClusterIP; for a Headless Service, it returns the backend Pod IPs.

kubectl run dns-check --rm -it --restart=Never \
  --image=<approved-dns-image> -- \
  nslookup <service>.<namespace>.svc.cluster.local

A working DNS lookup only proves that the name resolves; it doesn’t mean:

  • The Service selector is correct.
  • Endpoints are non-empty.
  • The target port is listening.
  • kube-proxy’s forwarding tables are correct.

So keep checking:

kubectl -n <namespace> get service <service> -o yaml
kubectl -n <namespace> get endpointslice \
  -l kubernetes.io/service-name=<service> -o wide

Why You Can’t Merge the Three Address Ranges into One

If the Node, Pod, and Service ranges overlap, a single destination address can simultaneously be interpreted as:

  • A server on the local L2 network.
  • A remote Pod that must be handed to Calico.
  • A virtual Service that must be handed to kube-proxy.

Routing precedence can then send traffic to the wrong interface. Common symptoms include:

No route to host
connect timed out
某些节点能访问，某些节点不能访问
访问一个 Service 却命中另一台真实主机

“Unify” should mean unified planning and unified configuration, not squeezing every purpose into a single CIDR.

Step 1: Collect All Networks Before Migration

Create network-plan.csv:

type,cidr,owner,purpose,changeable
node,<node-cidr>,network-team,node-management,false
pod,<pod-cidr>,kubernetes-team,calico,true
service,<service-cidr>,kubernetes-team,clusterip,true
vpn,<vpn-cidr>,network-team,remote-access,false

Also collect:

kubectl -n kube-system get configmap kubeadm-config -o yaml
kubectl get service -A -o json
kubectl get pod -A -o wide
ip route

Step 2: Check for Overlap

Use an IPAM or CIDR tool approved by the team:

Pod CIDR ∩ Service CIDR = 空集
Pod CIDR ∩ Node CIDR = 空集
Service CIDR ∩ Node CIDR = 空集
三者 ∩ VPN/办公网/专线 = 空集

Also leave headroom for future growth. Don’t size by the current Pod count alone; rolling releases, Jobs, DaemonSets, and failovers all temporarily consume extra addresses.

Step 3: Freeze into Versioned Configuration

At minimum, pin down:

manifests/kubeadm.yaml
manifests/calico.yaml
inventory/network-plan.csv
scripts/network-smoke.sh

Changing the Pod CIDR or Service CIDR after the control plane is created is usually not a routine configuration change — it’s a network migration. Don’t try to “unify things as you go” while your applications are starting up.

Step 4: Run a Four-Layer Smoke Test

Pod to Pod

kubectl exec <source-pod> -- ping -c 3 <target-pod-ip>

Pod to ClusterIP

kubectl exec <source-pod> -- nc -vz <service-ip> <service-port>

Pod to Service DNS

kubectl exec <source-pod> -- \
  nc -vz <service>.<namespace>.svc.cluster.local <service-port>

Outside the Cluster to Ingress

curl --resolve app.example.com:443:<ingress-address> \
  https://app.example.com/<health-path>

Run test Pods on different nodes; otherwise, a kube-proxy or firewall failure on a single node will go undetected.

Step 5: Remove Address Dependencies from Configuration

Handle each address found using these rules:

Address foundHow to handle
Pod IPMust switch to a Service
ClusterIPPrefer switching to Service DNS
Node IP + NodePortConfirm whether it is a required external entry point
Kafka broker addressHandle the advertised listener separately
External database or dedicated lineKeep it and register the owner

Don’t blindly replace every IPv4 string with .svc.cluster.local.

Definition of Done

  • Node, Pod, Service, VPN, and office network address ranges do not overlap.
  • kubeadm and CNI use the same Pod CIDR.
  • Every node has correct Pod routes and firewall rules.
  • Cross-node Pod, ClusterIP, Service DNS, and Ingress smoke tests pass.
  • Kubernetes-internal applications no longer depend on Pod IPs.
  • Fixed ClusterIPs are allowed only when listed in a reviewed compatibility whitelist.

Having multiple IP ranges in one cluster is a normal design. What should actually be unified is the network plan, the configuration source, and the verification approach.
