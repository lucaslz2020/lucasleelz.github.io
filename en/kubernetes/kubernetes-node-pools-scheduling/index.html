Planning Kubernetes Node Pools: Labels, Taints, Affinity, and Anti-Affinity in Practice

Divide nodes into ingress, platform, app, data, monitoring, shared, and reserve pools, and enforce scheduling with labels, taints, tolerations, and affinity.

lucaslzAuthor
June 7, 2026 Updated August 6, 2026 9 min read
#Kubernetes #Scheduling #Node Pools #Taint #Affinity
{ }

Node pools are not a concept exclusive to cloud providers. Even if every node runs on an on-premises virtualization platform, use labels, taints, and affinity to keep failure domains separate.

Series navigation: Kubernetes Rebuild Migration Tutorial Series. This post assumes the base components have already passed acceptance.

This article starts with a node inventory and turns the plan into concrete Kubernetes scheduling rules.

Step 1: Group Nodes by Responsibility First

A common starting point is:

Node poolTypical workloadsDedicated?
control-planeAPI Server, etcdYes
ingressIngress Controller, layer-4 ingressYes
platformNacos, DevOps, core platformDepends on capacity
app-*Per-environment workloadsRecommended for production
dataMySQL, Redis, Kafka, RabbitMQ, ZooKeeperYes
observabilityPrometheus, logging, tracingRecommended
sharedSmall stateless servicesNo
reserveReserved for failures and rolling upgradesNo regular workloads

Assign each node one primary pool first, and don’t let the same machine appear in two dedicated pools at once.

Step 2: Turn the Plan into a CSV and Validate It

hostname,pool,cpu,memory_gib,disk_type,failure_domain
worker-a,app-test,8,32,ssd,host-a
worker-b,app-test,8,32,ssd,host-b
worker-c,app-test,8,32,ssd,host-c

Check for duplicates:

cut -d, -f1 inventory/node-pools.csv | tail -n +2 | sort | uniq -d

Check the node count for each pool:

cut -d, -f2 inventory/node-pools.csv | tail -n +2 | sort | uniq -c

When planning three-replica high availability, consider both layers: the Kubernetes nodes and the virtualization hosts. Three Pods can land on three VMs, but if those VMs sit on the same physical host, it is still a single point of failure.

Step 3: Add Descriptive Labels First

Labels describe what a node is; they don’t enforce exclusivity:

kubectl label node worker-a workload.yj/pool=app-test
kubectl label node worker-a topology.yj/failure-domain=host-a
kubectl label node worker-a hardware.yj/disk=ssd

After applying them in batches, verify:

kubectl get nodes -L workload.yj/pool,topology.yj/failure-domain,hardware.yj/disk

Use your own DNS prefix for custom labels so they don’t conflict with Kubernetes reserved labels.

Step 4: Then Decide Which Pools Need Taints

A taint states who is not allowed by default. For a dedicated data pool, add:

kubectl taint node data-a workload.yj/pool=data:NoSchedule
kubectl taint node data-b workload.yj/pool=data:NoSchedule
kubectl taint node data-c workload.yj/pool=data:NoSchedule

Verify:

kubectl describe node data-a | sed -n '/Taints:/,/Unschedulable:/p'

Don’t taint dozens of nodes first and then go back and modify Deployments. The correct order is:

准备应用 toleration 和 nodeAffinity
→ server-side dry-run
→ 给第一台节点加污点
→ 验证调度
→ 批量推广

Step 5: Workloads Declare Both Toleration and the Target Node

Configuring only a toleration means “allowed in,” but it doesn’t guarantee the Pod lands in the data pool. Use nodeAffinity together with it:

spec:
  template:
    spec:
      tolerations:
        - key: workload.yj/pool
          operator: Equal
          value: data
          effect: NoSchedule
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
              - matchExpressions:
                  - key: workload.yj/pool
                    operator: In
                    values: [data]

Run a dry-run first:

kubectl apply --server-side --dry-run=server -f workload.yaml

Step 6: Spread Stateful Replicas

Kafka, RabbitMQ, ZooKeeper, and MySQL replicas must not land on the same node. Use Pod anti-affinity:

affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app.kubernetes.io/name: zookeeper
        topologyKey: kubernetes.io/hostname

To spread across virtualization hosts too, use the custom failure-domain label:

topologyKey: topology.yj/failure-domain

When nodes are insufficient, required keeps the Pod Pending. That is more honest than squeezing three replicas onto one node; add more nodes or adjust the capacity plan instead of quietly settling for a weaker failure domain.

Step 7: Reserve Capacity for Rolling Upgrades

Suppose a workload has two Pods, each with a request of 2 cores and 6 GiB. With the default maxSurge: 25%, a rolling upgrade must be able to temporarily fit a third Pod.

Calculate available capacity from requests, not from actual instantaneous usage:

kubectl describe node <node> | sed -n '/Allocated resources:/,$p'
kubectl top node <node>

The two commands serve different purposes:

  • describe’s Allocated resources are the requests/limits the scheduler has already committed.
  • top shows current actual usage.

Don’t keep the reserve pool permanently filled with low-priority workloads, or both failure migration and rolling releases will stall.

Step 8: Verify Scheduling Results

After deploying, run:

kubectl get pods -A -o custom-columns='NS:.metadata.namespace,POD:.metadata.name,NODE:.spec.nodeName' \
  | sort

kubectl get pods -n <namespace> -l app.kubernetes.io/name=<app> -o wide
kubectl get events -A --field-selector reason=FailedScheduling --sort-by=.lastTimestamp

Key checks:

  • Whether unrelated Pods slipped into dedicated pools.
  • Whether three replicas land on different nodes and failure domains.
  • Whether DaemonSets are missing tolerations for taints.
  • Whether reserve nodes are still idle.
  • Whether small nodes are carrying heavy services they shouldn’t.

Postmortem: How to Read 0/69 nodes are available

During a rollout of a two-replica service, events kept reporting:

0/69 nodes are available:
several nodes had untolerated taint,
some nodes didn't match Pod's node affinity/selector,
some nodes had insufficient memory

This doesn’t mean all 69 machines are low on memory. The scheduler filters in sequence:

flowchart LR
  A["69 nodes"] --> B["Taint / Toleration"]
  B --> C["nodeSelector / nodeAffinity"]
  C --> D["CPU / Memory request"]
  D --> E["Topology spread / anti-affinity"]
  E --> F["Schedulable nodes"]

Print the Pod’s complete constraints first:

kubectl -n <namespace> get pod <pending-pod> -o jsonpath='
nodeSelector={.spec.nodeSelector}{"\n"}
affinity={.spec.affinity}{"\n"}
tolerations={.spec.tolerations}{"\n"}
requests={.spec.containers[*].resources.requests}{"\n"}
spread={.spec.topologySpreadConstraints}{"\n"}'

Then inspect candidate nodes layer by layer:

kubectl get node --show-labels
kubectl describe node <candidate-node>
kubectl get events -n <namespace> \
  --field-selector reason=FailedScheduling \
  --sort-by=.lastTimestamp

Why the Third Pod Still Reports Insufficient Memory When Two Pods Actually Use Only 2G

The scheduler doesn’t look at how much the two existing Pods are currently using in total; instead, it compares the new Pod’s memory request with the node’s remaining allocatable capacity:

可调度
⇔ node allocatable
  - 已调度 Pod requests
  ≥ incoming Pod request

If each Pod’s request is 3.5 GiB, even when the two existing instances currently use about 1 GiB each, the new revision’s surge Pod still requests the full 3.5 GiB.

This is also why resource governance later grouped services into ordinary, warehousing, and heavy tiers: requests should cover steady-state load and explainable peaks, but one oversized generic value shouldn’t fill every dedicated node.

Why a Pod Still Can’t Use a Node That Looks Idle

“The node has no workload Pods” doesn’t mean “this Pod can be scheduled there.” It might:

  • Carry a NoSchedule taint the current Pod doesn’t tolerate.
  • Lack the required nodeSelector labels.
  • Not belong to an eligible domain for topology spread.
  • Already have capacity reserved by other Pods’ requests.
  • Be reserved for failures or rolling upgrades.

So don’t conclude that nine servers are still idle based on the node list alone. Tally taints, labels, and allocated requests together first.

Why Volcano Engine Writes Back Manually Deleted Labels and Taints

For a managed node pool, the configuration is the desired state on the control plane. If the pool still declares:

app-type=<dedicated-service>
taint app-type=<dedicated-service>:NoSchedule

Running only:

kubectl label node <node> app-type-
kubectl taint node <node> app-type-

may change the Kubernetes Node object only temporarily. The node pool controller restores these fields on its next reconciliation.

Volcano Engine VKE node pool documentation explicitly states that labels and taints added or modified in the node pool are automatically applied to both new and existing nodes.

To permanently move a dedicated node into the shared pool:

  1. First confirm the node no longer handles dedicated workloads or special hardware duties.
  2. Delete or modify the target labels and taints in the VKE node pool configuration.
  3. Wait for the controller to finish reconciling.
  4. Then check the Kubernetes Node object.
  5. Migrate one low-risk Pod to verify shared-pool scheduling.
  6. Confirm the configuration doesn’t come back after restarts, scaling, or node replacement.

If all members of the original node pool must share the same configuration, a single machine shouldn’t stay in that pool; migrate it to the shared node pool, or create a new node pool without the dedicated taint.

Postmortem: Why Two Replicas Are Still on the Same Node

With only preferred node affinity or ScheduleAnyway, the scheduler may place two replicas on the same machine to improve its resource score. This is legitimate behavior, but it can’t survive a single-node failure.

In a Kubernetes 1.30 Deployment, you can force spreading based on the current ReplicaSet revision:

topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: DoNotSchedule
    matchLabelKeys:
      - pod-template-hash
    labelSelector:
      matchLabels:
        app: <application>
        version: <version>

matchLabelKeys: [pod-template-hash] makes the old and new ReplicaSets compute skew separately. That way, in a rolling release with maxUnavailable: 0 and maxSurge: 1, the old revision doesn’t block the new revision by participating in the skew calculation.

Kubernetes topology spread documentation also cites pod-template-hash as the canonical example of spreading by Deployment revision.

Before forcing spread, make sure:

  • At least two nodes match the nodeSelector/affinity at the same time.
  • Both nodes are accepted by the Pod’s tolerations.
  • Each node can fit one replica’s request.
  • There’s room for the surge Pod during the release.

If only one node qualifies, DoNotSchedule keeps the second Pod Pending. That’s the normal result of a failure-domain constraint; don’t silently restore same-node placement by removing the spread rule.

How to Undo Safely

Remove a taint:

kubectl taint node data-a workload.yj/pool=data:NoSchedule-

Remove a label:

kubectl label node data-a workload.yj/pool-

Update the workload before removing the label, so it stops depending on a label that will no longer exist.

Definition of Done

  • Every node has exactly one clearly defined primary pool.
  • Dedicated pools have both labels and taints configured.
  • Workload manifests configure both toleration and nodeAffinity.
  • Stateful three-replica workloads spread across nodes, and critical services across physical failure domains.
  • Rolling upgrades can always accommodate at least one surge Pod.
  • DaemonSets such as monitoring, CNI, and CSI are verified to tolerate the required taints.
  • Reserve nodes aren’t occupied long-term by regular workloads.
  • Labels and taints on the managed node pool stay consistent with the Kubernetes Node objects.
  • FailedScheduling is explained layer by layer across taints, affinity, requests, and spread.
  • Two-replica workloads use revision-aware topology spread to force cross-node placement.
