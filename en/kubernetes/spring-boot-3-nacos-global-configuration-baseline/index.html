A Complete Spring Boot 3 Nacos Production Baseline: Redis, RabbitMQ, Hikari, and Probes

Practical layered Spring Boot 3 Nacos configuration: Redis connections, RabbitMQ concurrency and prefetch, database pools, Tomcat, graceful shutdown, Actuator.

lucaslzAuthor
August 9, 2026 11 min read
#Spring Boot #Nacos #Redis #RabbitMQ #Configuration Governance
{ }

This article draws on a governance pass across multiple services focused on connection counts and container memory. Addresses, accounts, namespaces, and service names have been generalized. The configuration values are a conservative starting point; adjust them based on database, Redis, and RabbitMQ capacity and business load testing.

When dozens of Spring Boot services read the same global.properties, any “convenient tweak” is amplified by the replica count:

每 Pod 多 8 个 Redis 空闲连接
× 60 个 Pod
= 480 个额外连接

The same applies to RabbitMQ. Dozens of @RabbitListeners, multiple consumer threads, and a large prefetch compound the effect — more Channels and threads, and more unacknowledged messages sitting in the JVM heap.

So a “complete Nacos configuration” isn’t just filling in every available parameter. It should spell out:

  • Which settings are a safe baseline shared by all Spring Boot 3 services.
  • Which settings belong only in application-level dataIds.
  • Which sensitive values must come from Kubernetes Secrets.
  • Which legacy Boot services need a temporary compatibility layer.
  • How each connection pool ceiling is accounted for alongside the number of Pods.

Recommended configuration layering

Suggested boundaries:

LayerWhat it storesExample
SecretPasswords, tokens, certificatesRedis, RabbitMQ, database passwords
global dataIdConservative parameters for the same version and semanticstimeouts, probes, default concurrency
app dataIdBusiness-specific capacity and compatibility itemspool, batch jobs, Boot 2 aliases
DeploymentContainer-related items that must be enforcedJVM, HOME, diagnostic switches

Don’t maintain the same key in more than one layer. Spring property sources follow a precedence order: once a Deployment environment variable overrides Nacos, a successful publish in the console doesn’t mean the runtime value has changed.

An auditable Spring Boot 3 global template

The template below uses placeholders and contains no production passwords. Treat it as a candidate baseline rather than rolling it out wholesale.

# ------------------------------------------------------------
# Web 与反向代理
# ------------------------------------------------------------
server.forward-headers-strategy=framework
server.shutdown=graceful
spring.lifecycle.timeout-per-shutdown-phase=30s

# 仅适用于 Servlet / Tomcat 服务；WebFlux 服务会忽略这些项
server.tomcat.threads.max=100
server.tomcat.threads.min-spare=10
server.tomcat.accept-count=100
server.tomcat.max-connections=2000
server.tomcat.connection-timeout=10s

# ------------------------------------------------------------
# Actuator 与 Kubernetes 探针
# ------------------------------------------------------------
management.endpoint.health.probes.enabled=true
management.health.livenessstate.enabled=true
management.health.readinessstate.enabled=true
management.endpoint.health.show-details=never
management.endpoints.web.exposure.include=health,info,prometheus,serviceregistry

# ------------------------------------------------------------
# HikariCP：只对使用 Spring 默认 Hikari DataSource 的服务生效
# ------------------------------------------------------------
spring.datasource.hikari.maximum-pool-size=10
spring.datasource.hikari.minimum-idle=2
spring.datasource.hikari.connection-timeout=3000
spring.datasource.hikari.validation-timeout=1000
spring.datasource.hikari.idle-timeout=600000
spring.datasource.hikari.max-lifetime=1800000
spring.datasource.hikari.keepalive-time=120000

# ------------------------------------------------------------
# Spring Data Redis / Lettuce
# 地址不是 Secret，密码从环境变量读取
# ------------------------------------------------------------
spring.data.redis.host=redis-service.app.svc.cluster.local
spring.data.redis.port=6379
spring.data.redis.database=0
spring.data.redis.password=${REDIS_PASSWORD:}
spring.data.redis.connect-timeout=3s
spring.data.redis.timeout=3s
spring.data.redis.client-type=lettuce
spring.data.redis.lettuce.shutdown-timeout=100ms

# 默认不启用连接池，避免 commons-pool2 出现在 classpath 后
# 每个 Pod 自动建立一批空闲连接
spring.data.redis.lettuce.pool.enabled=false

# ------------------------------------------------------------
# RabbitMQ
# ------------------------------------------------------------
spring.rabbitmq.addresses=rabbitmq.app.svc.cluster.local:5672
spring.rabbitmq.username=${RABBITMQ_USERNAME}
spring.rabbitmq.password=${RABBITMQ_PASSWORD}
spring.rabbitmq.virtual-host=/
spring.rabbitmq.connection-timeout=5s
spring.rabbitmq.requested-heartbeat=30s

spring.rabbitmq.cache.connection.mode=channel
spring.rabbitmq.cache.channel.size=25
spring.rabbitmq.cache.channel.checkout-timeout=2s

spring.rabbitmq.listener.type=simple
spring.rabbitmq.listener.simple.concurrency=1
spring.rabbitmq.listener.simple.max-concurrency=3
spring.rabbitmq.listener.simple.prefetch=10
spring.rabbitmq.listener.simple.acknowledge-mode=auto
spring.rabbitmq.listener.simple.auto-startup=true

# ------------------------------------------------------------
# 文件上传：限制请求在内存和临时盘中的放大
# ------------------------------------------------------------
spring.servlet.multipart.max-file-size=100MB
spring.servlet.multipart.max-request-size=110MB
spring.servlet.multipart.file-size-threshold=2MB

Fix deprecated properties first

The template already uses server.forward-headers-strategy and drops server.use-forward-headers. The choice between NATIVE, FRAMEWORK, and NONE depends on the actual proxy chain; you can’t unconditionally trust X-Forwarded-* headers from the public internet.

The migration report for old keys and the exit criteria for spring-boot-properties-migrator live in Spring Boot 3 Container Startup Postmortem; this article only covers the final production configuration.

Redis: fewer connections doesn’t mean a smaller pool is always better

When Spring Data Redis uses Lettuce, ordinary commands can reuse the shared native connection. Not every service needs a connection pool by default.

The Spring Boot 3.1 property documentation notes that the Lettuce pool can be enabled automatically when commons-pool2 is present. So if any starter later brings in that dependency, connection behavior can change.

This round of governance sets the global default to:

spring.data.redis.lettuce.pool.enabled=false

Only applications meeting all of the following conditions enable the pool in their own dataId:

  • They use blocking Redis commands.
  • They use transactions or calls that need an exclusive connection.
  • Metrics already show contention on the shared connection.
  • The classpath explicitly contains a compatible version of commons-pool2.

Application-level candidates:

spring.data.redis.lettuce.pool.enabled=true
spring.data.redis.lettuce.pool.max-active=8
spring.data.redis.lettuce.pool.max-idle=4
spring.data.redis.lettuce.pool.min-idle=0
spring.data.redis.lettuce.pool.max-wait=2s
spring.data.redis.lettuce.pool.time-between-eviction-runs=60s

min-idle=0 keeps each Pod from holding a batch of idle connections when there’s no business load. Whether to raise it depends on Redis connected_clients, command latency, and pool-wait metrics.

Don’t forget Redisson is a separate client

spring.data.redis.* doesn’t automatically limit a RedissonClient created separately in code. If a service uses both Spring Data Redis and Redisson, the total connection count is the sum of both clients.

You’ll also need to inventory:

  • Single-node, master–slave, sentinel, or cluster mode for Redisson.
  • connectionPoolSize and connectionMinimumIdleSize.
  • The subscription connection pool.
  • threads and nettyThreads.
  • How many RedissonClients each Pod actually creates.

Calculate each client’s connection budget separately:

总连接上界
≈ Pod 数
× 每 Pod 的 Lettuce 连接
+ Pod 数
× 每 Pod 的 Redisson 普通连接
+ subscription 连接
+ Redis 运维与监控连接

Multiple business modules each calling new RedissonClient is more dangerous than slightly oversized pool parameters. Make sure each application context creates only one set of managed clients.

RabbitMQ: the global limit applies per listener container

In the Spring Boot RabbitMQ property documentation:

  • concurrency is the minimum number of listener invoker threads.
  • max-concurrency is the automatic scaling ceiling.
  • prefetch is the maximum number of unacknowledged messages allowed per consumer.

So:

concurrency=1
max-concurrency=3
prefetch=10

doesn’t mean “at most three messages per service.” It means at most three consumers per listener container and at most ten unacknowledged messages per consumer.

If an application has 40 listeners, the theoretical ceiling can reach:

40 × 3 × 10 = 1200 条未确认消息

The real number is also affected by queue traffic and container scaling policy, but this multiplication alone explains why services with many listeners see sudden heap growth.

Don’t modify these directly in the global baseline:

spring.rabbitmq.listener.simple.default-requeue-rejected
spring.rabbitmq.listener.simple.retry.enabled
spring.rabbitmq.publisher-confirm-type

They change message-reliability semantics, so they must be decided together with DLQ, idempotency, and retry strategies — not treated as pure performance tuning.

Hikari: first calculate how many connections the database can take

maximum-pool-size=10 only makes sense once the total connection count is accounted for:

数据库业务连接上界
= 所有服务的 Pod 数 × 各自 maximumPoolSize
+ 任务、管理、迁移和运维连接

For example, 50 services with 2 Pods each and 20 connections per pool already reach 2,000 connections in theory. The database isn’t necessarily able to handle it just because every pool is “only 20”.

Recommended steps:

  1. Aggregate all callers and replica counts per database instance.
  2. Record peak active, idle, pending, and acquire time.
  3. Start ordinary services with smaller pools.
  4. Create application-level exceptions for high-concurrency or long-transaction services.
  5. Keep headroom for database operations and failover.

If a project uses dynamic-datasource, Druid, or manually creates multiple DataSources, spring.datasource.hikari.* may only apply to the default DataSource. Inspect the final beans, not just the Nacos key.

Tomcat threads and database connections aren’t one-to-one

server.tomcat.threads.max=100 doesn’t mean Hikari should be configured with 100 connections either. Many requests may hit the cache, fail validation, or run non-database logic; conversely, one request may access multiple DataSources in parallel.

Validate the capacity relationship with metrics:

HTTP active threads
→ 数据库 active / pending
→ 下游 P95/P99
→ CPU 与 GC

WebFlux/Netty services don’t use the Tomcat thread configuration. Remove those inapplicable keys from their application-level dataId and manage the event loop, connection pools, and Direct Buffers separately.

Actuator exposure must match the network boundary

The global configuration exposes health, prometheus, and serviceregistry for probes, monitoring, and graceful traffic draining. But serviceregistry can change registration state and shouldn’t be exposed directly to the public internet.

At minimum:

  • The management port is only reachable from inside the cluster.
  • Ingress doesn’t forward management paths, or access is restricted by authentication and NetworkPolicy.
  • Health details don’t leak addresses, accounts, or exception stacks.
  • Prometheus is accessed through an explicit ServiceMonitor or controlled scraping.

If the boundary can’t be guaranteed, don’t expose management endpoints globally just for preStop convenience.

Boot 2 services shouldn’t inherit this global Redis configuration directly

Spring Boot 2 uses spring.redis.*; Spring Boot 3 uses spring.data.redis.*. Services that haven’t upgraded should add compatibility aliases only in their own dataId, not push the old prefix back into the Boot 3 global baseline.

The compatibility configuration, the evidence chain for localhost:6379, and the commons-pool2 pitfalls are covered in Boot 2/3 Redis Configuration Falling Back to localhost; this article won’t repeat them.

Nacos publish order

Changes to a global dataId affect many clients. Recommended order:

  1. Export and save the original configuration, namespace, group, dataId, and checksum.
  2. Build a Boot-version and component applicability matrix for every key.
  3. Remove parameters that clearly belong to a single application from the global dataId.
  4. Pick an ordinary service and test candidate values using a temporary application-level override.
  5. Roll one Pod and verify the real Redis, RabbitMQ, and database paths.
  6. Watch connections, threads, heap, message backlog, and latency.
  7. Then publish the global dataId and roll services in batches.
  8. Read back from Nacos and check the new Pods’ effective configuration and recent logs.

Don’t change all of these at once:

  • Redis pool.
  • RabbitMQ concurrency.
  • Hikari ceiling.
  • JVM heap.
  • Probe thresholds.

Otherwise, when memory drops or throughput degrades, you can’t tell which parameter caused it.

Acceptance metrics

ComponentMetrics to watchRisk signals
Redisconnected_clients, command latency, timeoutsConnections drop while pool waits rise
Redissonclients and connections per PodMultiple instances created repeatedly
RabbitMQready, unacked, consumer, channelBacklog keeps growing
Hikariactive, idle, pending, acquirepending non-zero with rising latency
Tomcatactive, queue, rejectThreads saturated for a long time
JVMHeap used/committed, GC, RSSMore Full GC or OOM
KubernetesReady, Restart, rolloutOld ReplicaSets can’t exit

Get through at least one real business peak before deciding to shrink further.

Definition of done

  • global.properties contains only Boot 3 parameters with common semantics.
  • Secrets are not stored in plain text in Nacos.
  • By default, Redis connection pools don’t expand automatically with classpath changes.
  • Redisson and Spring Data Redis are counted separately in the connection budget.
  • RabbitMQ concurrency and prefetch are accounted for by listener count.
  • The total database connection ceiling is below instance capacity, with failover headroom.
  • Servlet and WebFlux configurations are no longer mixed together.
  • Deployment environment variables and Nacos must not form two sources of truth that override each other.
  • Boot 2 compatibility items live only in application-level dataIds, with a removal deadline.

Final conclusion

The goal of a global configuration isn’t to make every service’s parameters identical; it’s to provide minimal, safe, predictable default behavior.

Redis connection counts, RabbitMQ unacknowledged messages, and database connection pools all scale with Pod count and the number of business components. Do the multiplication before putting them into Nacos; after publishing to Nacos, double-check that no Deployment environment variable overrides them.

A truly complete configuration isn’t the one with the most keys — it’s one where every key has an applicable version, a capacity rationale, an override relationship, monitoring metrics, and a rollback boundary.
