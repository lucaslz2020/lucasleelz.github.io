How to Migrate MySQL, Redis, Kafka, RabbitMQ, and Zookeeper During a Kubernetes Cluster Rebuild

Migrate common data services with RPO, backup and restore, zero-replica pre-deployment, and layered acceptance; avoid copying only PVCs, starting an empty database, or scheduling all three replicas onto the same node.

The most dangerous misconception in stateful service migration is: the Pod is Running, so the data migration is complete. In reality, a brand-new empty database can also be Running and even pass every health check.

Define the Data Boundary for Each Service

Build an inventory:

ServiceSource of truthAcceptable data loss (RPO)Max downtime (RTO)Recovery toolVerification owner
MySQLBusiness tables, accounts, binlog<rpo><rto>Physical/logical backupDBA
RedisSession, cache, or business data<rpo><rto>RDB/AOFApplication team
KafkaTopics, messages, offsets<rpo><rto>Replication/sync toolsMessaging team
RabbitMQdefinitions, messages, users<rpo><rto>definitions + data planMessaging team
Zookeeperznodes, ACLs, transaction logs<rpo><rto>snapshot/logPlatform team

A cache Redis and a primary-data Redis have completely different migration standards. Without RPO/RTO, you cannot choose between replication, stop-writes-and-export, and regeneration.

Overall Migration Sequence

flowchart LR
  A["盘点数据和依赖"] --> B["恢复演练"]
  B --> C["新集群零副本预部署"]
  C --> D["全量备份与恢复"]
  D --> E["停止写入"]
  E --> F["增量追平"]
  F --> G["服务端验证"]
  G --> H["客户端切换"]
  H --> I["观察与回滚窗口"]

Do not attempt backup and restore for the first time on the same day as the migration.

Step 1: Inventory the Real Storage Locations

kubectl get statefulset -A -o wide
kubectl get pvc,pv -A
kubectl get storageclass
kubectl get pod -A -o custom-columns='NS:.metadata.namespace,POD:.metadata.name,NODE:.spec.nodeName'

For each PVC, record:

  • StorageClass and reclaim policy.
  • Underlying volume, NFS directory, or local path.
  • Pod-to-volume nodeAffinity.
  • File owner UID/GID.
  • Current data size and growth rate.
  • Snapshot, backup, and restore duration.

Kubernetes StatefulSet provides stable identity and persistent volume binding, but it does not automatically copy data from the old cluster to the new one. The StatefulSets documentation also states that scaling down or deleting a StatefulSet does not delete its associated volumes by default. That is a data-safety design, not a complete backup.

Step 2: Deploy Zero-Replica Objects First

Pre-create in the new cluster:

  • Namespace, Service, and Headless Service.
  • Secret and ConfigMap.
  • StorageClass, PV, and PVC.
  • StatefulSet, with replicas set to 0.
  • NetworkPolicy, ServiceMonitor, and alerts.
kubectl apply --server-side --dry-run=server -f manifests/data-services/
kubectl apply -f manifests/data-services/
kubectl -n <namespace> scale statefulset/<service> --replicas=0

This surfaces API, storage, scheduling, and Secret issues early without starting an empty service that accepts connections.

Step 3: MySQL Migration

Logical Backup Example

mysqldump --single-transaction --routines --triggers --events \
  --set-gtid-purged=OFF \
  -h <old-mysql-host> -u <backup-user> -p \
  --databases <database-list> \
  > backup/mysql-full.sql

sha256sum backup/mysql-full.sql > backup/mysql-full.sql.sha256

For large databases, evaluate physical backup, replication, or a professional migration tool. MySQL’s official documentation treats logical/physical backup, full/incremental, and binlog-based point-in-time recovery as distinct strategies; saving a single SQL file does not prove recoverability. MySQL Backup and Recovery

Restore to an isolated instance and verify:

mysql -h <restore-host> -u <restore-user> -p < backup/mysql-full.sql

At minimum, compare:

SELECT COUNT(*) FROM <critical-table>;
SHOW INDEX FROM <critical-table>;
SHOW GRANTS FOR '<application-user>'@'%';
SELECT @@character_set_server, @@collation_server, @@sql_mode;

During the real cutover, stop writes, record the binlog/GTID position, catch up the incremental changes, and only then switch application connections. An empty database accepting connections is not success.

Step 4: Redis Migration

First determine what Redis is:

  • A disposable cache.
  • Session storage.
  • Distributed locks.
  • Primary business data.

Check persistence status:

redis-cli -h <old-redis-host> INFO persistence
redis-cli -h <old-redis-host> INFO keyspace
redis-cli -h <old-redis-host> CONFIG GET appendonly
redis-cli -h <old-redis-host> CONFIG GET dir

RDB is a point-in-time snapshot; AOF records write operations. When both are enabled, Redis prefers the more complete AOF at startup. Before migrating, confirm the file layout for your version against Redis Persistence, especially the multi-file AOF in Redis 7 and later.

After restore, verify:

redis-cli -h <new-redis-service> PING
redis-cli -h <new-redis-service> INFO keyspace
redis-cli -h <new-redis-service> DBSIZE

Then access the Service DNS from a real application Pod. A successful PING only proves the Redis process is available; it does not prove that keys, TTLs, database numbers, and serialization formats are correct.

Step 5: Kafka Migration

Kafka migration is not done by copying one broker’s data directory to three new nodes. You need to inventory:

Topic 与 partition
replication factor
min.insync.replicas
consumer group offsets
ACL
broker.id 或 node.id
listener / advertised.listener

The typical migration strategy is:

  1. Create isomorphic topics in the new cluster.
  2. Keep syncing with a proven cross-cluster replication tool.
  3. Verify produce and consume.
  4. Briefly stop writes or accept the defined RPO.
  5. Catch up lag, switch producers, then consumers.

Internal Kubernetes listeners can use stable DNS, but clients ultimately connect to the advertised address returned by the broker. You cannot simply replace three brokers with one ordinary ClusterIP.

Verify:

kafka-topics.sh --bootstrap-server <new-bootstrap> --describe
kafka-consumer-groups.sh --bootstrap-server <new-bootstrap> --all-groups --describe

Then send a message with a unique ID and confirm the target consumer processes it exactly once or is idempotent.

Step 6: RabbitMQ Migration

Protect each of these separately:

  • Users, roles, vhosts, policies, exchanges, queues, and bindings.
  • Persistent messages that have not been consumed yet.
  • Cluster materials such as TLS and the Erlang cookie.

First export definitions:

rabbitmqctl export_definitions /backup/definitions.json

definitions does not include queued messages. If messages must be kept, choose an officially supported replication, backup, or downtime migration plan based on queue type, version, and topology.

Check after restore:

rabbitmq-diagnostics check_running
rabbitmq-diagnostics check_local_alarms
rabbitmqctl list_vhosts
rabbitmqctl list_queues name durable messages_ready messages_unacknowledged

Finally, complete one produce-and-consume round trip with a test exchange/queue.

Step 7: Zookeeper Migration

Inventory:

  • dataDir, snapshots, and transaction logs.
  • myid and the member list.
  • ACLs and business root paths.
  • Current Leader/Follower status.

The three replicas must be spread across different nodes and physical failure domains:

podAntiAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchLabels:
          app.kubernetes.io/name: zookeeper
      topologyKey: kubernetes.io/hostname

During restore, do not let multiple nodes use the same myid. After startup, check member roles, znodes, and ACLs before allowing dependencies such as Kafka to connect.

If a ZooKeeper Pod stays close to its memory request for a long time after the migration, do not immediately conclude it is a leak. Follow ZooKeeper Fixed Heap and Kubernetes Resource Rightsizing to check Xms/Xmx, mntr, resource reservations, and PVC.

Step 8: Start in Dependency Order

PVC 与存储
→ MySQL / Redis
→ Zookeeper
→ Kafka / RabbitMQ
→ Nacos
→ 平台依赖
→ 业务服务

After starting each service, verify the Endpoint first:

kubectl -n <namespace> get pod,service,endpointslice -o wide
kubectl -n <namespace> get events --sort-by=.lastTimestamp

Step 9: Switch Clients

Prefer Service DNS in configuration:

spring.datasource.url=jdbc:mysql://mysql.<namespace>.svc.cluster.local:3306/<database>
spring.data.redis.host=redis.<namespace>.svc.cluster.local
spring.kafka.bootstrap-servers=<kafka-bootstrap-dns>:9092
spring.rabbitmq.host=rabbitmq.<namespace>.svc.cluster.local

Kafka broker advertised listeners, cross-cluster databases, and external consumers must be designed individually; do not apply the same pattern mechanically.

Step 10: Real Business Acceptance

At minimum, cover:

  • MySQL real reads/writes with application accounts and transactions.
  • Redis Session, TTL, and locks.
  • Kafka produce, consume, offsets, and lag.
  • RabbitMQ publish, ack, consume, and backlog.
  • Zookeeper node reads, writes, and ACLs.
  • Recovery after deleting or recreating one non-critical replica.

Rollback Boundary

Switching the entry point back to the old cluster only works while the new environment has not yet produced authoritative writes. Once the new cluster accepts writes, you must design in advance:

  • Reverse incremental sync.
  • Dual-write consistency and deduplication.
  • A write freeze point.
  • Data conflict handling.

Without these mechanisms, “point DNS back” is not a complete rollback.

Definition of Done

  • Every service has a verified RPO, RTO, and recovery procedure.
  • Backups restore successfully in an isolated environment, not merely because the files exist.
  • Data volume, critical rows/keys, permissions, indexes, topics, queues, and ACLs match the baseline.
  • Three replicas span different nodes and, where possible, different physical failure domains.
  • Applications reach dependencies through Service DNS.
  • Real reads/writes, message produce/consume, and failure rebuilds all pass.
  • The old environment and backups remain read-only until the observation window ends.

The completion standard for data service migration is not that every StatefulSet is Ready, but that the business can prove data integrity, continuous writes, and a working rollback path.
