ZooKeeper Pods Near 2G Each: From Fixed Heap to Kubernetes Resource Rightsizing

Diagnose ZooKeeper's high memory footprint with JVM parameters, mntr, snapshots, and Kubernetes requests, then walk through phased downsizing, monitoring, rolling verification, and a persistence migration plan.

lucaslzAuthor
August 9, 2026 12 min read
#Zookeeper #Kubernetes #JVM #Performance Tuning #Observability
{ }

This post comes from resource-governance work on a three-node ZooKeeper cluster. Namespaces, nodes, service names, and capacities have been generalized; the parameter values are only a starting point for workloads of similar scale and shouldn’t be copied into production as-is. Series navigation: Kubernetes Rebuild & Migration Tutorial Series.

A three-node ZooKeeper cluster has long shown the following resource state:

MetricNode ANode BNode C
Pod memory~1.8 GiB~1.8 GiB~1.4 GiB
CPU~10m~9m~11m
memory request2 GiB2 GiB2 GiB
memory limit3 GiB3 GiB3 GiB
Restarts000

At first glance this looks like a memory leak: CPU is very low, yet the three Pods are consuming nearly 5 GiB combined. Digging deeper, however, shows only about 1.2 MiB of business data, with connection and watch counts also low.

The real problem isn’t that ZooKeeper stores several GiB of data. The JVM is configured with a fixed 2 GiB heap, and the Chart’s resource preset requests 2 GiB of memory for every Pod.

First, Build the Diagnostic Chain

flowchart TD
  A["kubectl top: Pod near 2G"] --> B["Read the real Java command line"]
  B --> C["Confirm Xms / Xmx and duplicate flags"]
  C --> D["Collect mntr, stat, snapshots, and disk"]
  D --> E{"Are live data and connection pressure high?"}
  E -- "High" --> F["Remodel around peak capacity"]
  E -- "Low" --> G["Shrink Heap and requests in phases"]
  G --> H["Roll Pod by Pod and watch GC / latency"]
  H --> I["Then handle the emptyDir persistence risk"]

The key here is to first distinguish “a large heap upper bound”, “a committed heap”, and “many live business objects”. kubectl top alone cannot tell them apart.

Step 1: Read the Real JVM Arguments of a Running Process

Don’t rely only on the Helm values. Check the Java process inside the container first:

kubectl -n infra exec zookeeper-0 -- \
  sh -c 'tr "\0" " " < /proc/1/cmdline'

The key fragment this time was:

-Xmx1000m -Xmx2048m -Xms2048m

Duplicate -Xmx flags don’t add up; HotSpot generally uses the last occurrence. So the effective configuration is:

Xms = 2048 MiB
Xmx = 2048 MiB

The earlier -Xmx1000m comes from the image script’s default, while the later -Xmx2048m and -Xms2048m come from the Chart’s heapSize. This tells us:

  • The default never actually constrained the heap.
  • The heap is allowed to commit a fixed 2 GiB from startup.
  • The theoretical fixed-heap budget across the three nodes is already 6 GiB.

The duplicate flags themselves aren’t a 3 GiB heap or evidence of a leak, but they will mislead anyone who only checks environment variables.

Step 2: Distinguish RSS, Committed Heap, and Live Data

The memory of a ZooKeeper Pod can be roughly understood as:

Pod working set
≈ JVM committed heap
+ Metaspace / Code Cache / GC structures
+ thread stacks / direct buffers / native libraries
+ process working-set file pages

Xms=2g doesn’t mean the process immediately occupies 2 GiB of RSS at startup, but the JVM gradually touches committed pages as it runs and garbage-collects. Even with very few live objects, the working set the OS sees can stay close to the fixed heap size for a long time.

So neither of these conclusions holds:

Pod RSS 接近 2 GiB，所以 ZooKeeper 一定存了 2 GiB 数据
数据只有 1 MiB，所以 Pod RSS 应该只有几十 MiB

Business data size is an important input to heap sizing, but it doesn’t directly determine total Pod memory.

Step 3: Use mntr to Judge Real Load

ZooKeeper’s four-letter words must be allowed in the server-side whitelist. Evaluate the security boundary before enabling them so you don’t expose the admin interface to untrusted networks. The ZooKeeper admin guide already recommends AdminServer for new systems; mntr is kept here only to mirror the existing cluster’s collection approach.

In an environment where mntr is allowed, you can run:

kubectl -n infra exec zookeeper-0 -- \
  sh -c 'printf "mntr\n" | nc 127.0.0.1 2181'

Collect at least:

zk_server_state
zk_znode_count
zk_approximate_data_size
zk_num_alive_connections
zk_outstanding_requests
zk_avg_latency
zk_max_latency
zk_watch_count
zk_ephemerals_count
zk_open_file_descriptor_count
zk_max_file_descriptor_count

This time, the sanitized measurements were on the order of:

MetricObserved valueInterpretation
znode count~22,000Small scale
approximate data size~1.2 MiBBusiness data is far smaller than the fixed heap
Global sessions~40Low client pressure
Alive connections per node10–20Low connection pressure
watch count10–20No watch storm
outstanding requests0Nothing is queued
Avg latency<1 msPlenty of performance headroom
Single snapshot~3 MiBConsistent with the data scale

These observations point to “an oversized heap” rather than “business objects growing without bound”.

Step 4: Inspect Transaction Logs and Snapshots

Next, check the ZooKeeper data directory:

kubectl -n infra exec zookeeper-0 -- \
  sh -c 'du -sh /bitnami/zookeeper/data /bitnami/zookeeper/logs 2>/dev/null'

Transaction logs may use preallocated files. Log files in the tens of MiB don’t mean every byte is valid business data, nor can they be used directly to size the heap.

Also confirm:

  • snapCount.
  • autopurge.snapRetainCount.
  • autopurge.purgeInterval.
  • Whether the data directory is on a PVC.
  • Whether snapshots and transaction logs on all three nodes keep growing.

Auto-purge was already enabled and the snapshots are small, so there’s no evidence to support changing snapCount or the purge frequency right now. Performance tuning should only touch parameters the evidence points to.

Step 5: Replace the Chart’s Resource Preset with an Explicit Budget

The current configuration looks like:

heapSize: 2048

resourcesPreset: large
resources: {}

resourcesPreset is fine for quick deployment, but not for long-term capacity governance. It hides the actual request and limit, and it can’t express a realistic model such as “low CPU, but memory needs JVM headroom”. The Bitnami ZooKeeper Chart likewise recommends scenario-tuned resources for production workloads.

Don’t cut the heap from 2 GiB to 512 MiB in one shot without monitoring. A two-phase shrink is safer.

Phase 1: Drop to 1536 MiB First

heapSize: 1536

resourcesPreset: none
resources:
  requests:
    cpu: 250m
    memory: 1792Mi
    ephemeral-storage: 256Mi
  limits:
    cpu: 1500m
    memory: 2560Mi
    ephemeral-storage: 1Gi

This phase keeps roughly 1 GiB of container-level headroom to cover JVM non-heap memory, threads, direct memory, shared libraries, and working-set fluctuation.

Phase 2: Evaluate 1024 MiB After It Stabilizes

If at least one full business peak has passed and GC, latency, connections, and elections are all stable, you can keep evaluating:

heapSize: 1024

resourcesPreset: none
resources:
  requests:
    cpu: 250m
    memory: 1280Mi
    ephemeral-storage: 256Mi
  limits:
    cpu: 1500m
    memory: 2Gi
    ephemeral-storage: 1Gi

In phase 1, the memory requests of the three replicas total 5.25 GiB; after moving to phase 2, they total 3.75 GiB. CPU requests drop from the original 3 cores to 750m. Actual savings should be judged by the requests the scheduler sees, not by an instantaneous kubectl top reading.

Why the Heap Shouldn’t Sit at the Container Limit

Even though most of ZooKeeper’s data lives in the Java heap, room must be left for these areas:

  • Metaspace and Compressed Class Space.
  • JIT Code Cache.
  • GC remembered set and other native structures.
  • NIO Direct Buffer.
  • Thread stacks.
  • JNI and compression libraries.
  • File pages and process runtime.

If you set:

Xmx = container memory limit

the container can be killed by cgroup before the JVM heap even OOMs. Giving a 1 GiB heap a 2 GiB limit isn’t waste: it first establishes a verifiable safety boundary, and once you’ve observed stability you can decide whether to compress further.

Step 6: Add Observability Before Shrinking

If the original configuration disabled metrics, shrinking would leave you guessing through kubectl top, which is risky. Turn on the ZooKeeper metrics exporter first and at least monitor:

  • Pod working set and RSS.
  • JVM heap used, committed, max.
  • GC pause duration, count, and allocation rate.
  • zk_outstanding_requests.
  • avg/max latency.
  • Alive connections, watch, znode, and ephemeral counts.
  • Leader changes and election time.
  • Container restarts, OOMKilled, and probe failures.

Alerts shouldn’t rely only on “memory above 80%”. A composite signal is more meaningful:

heap 持续高位
+ GC 频率升高
+ 请求延迟或 outstanding requests 增长

With a fixed heap, a persistently high RSS may simply be expected behavior.

Step 7: Roll by ZooKeeper Quorum

A three-node cluster must always keep at least two healthy members. Recommended workflow:

  1. Back up the values, ZooKeeper configuration, and critical data.
  2. Confirm roles, connections, and quorum across the three members.
  3. Update only one follower at a time.
  4. Wait for that Pod to become Ready, and verify with ruok, stat, and mntr.
  5. Observe sync, latency, GC, and connection recovery.
  6. Update another follower.
  7. Handle the leader last, or confirm the leader has migrated safely first.
  8. Move to phase 2 only after a real peak has passed.

Wait for the StatefulSet to be ready at every step:

kubectl -n infra rollout status statefulset/zookeeper --timeout=15m
kubectl -n infra get pod -l app.kubernetes.io/name=zookeeper -o wide

Stop the rollout if any of the following happens:

  • A member can’t join the quorum.
  • Elections happen frequently.
  • GC pauses rise noticeably.
  • outstanding requests stay non-zero and keep growing.
  • Business sessions are rebuilt in large numbers or time out.

A Bigger Risk Than Memory: the Data Directory Uses emptyDir

The inspection also found that the StatefulSet has no volumeClaimTemplates and persistence is disabled, so the data directory actually sits on emptyDir. The Bitnami Chart’s parameter documentation states it explicitly: persistence.enabled=false uses emptyDir.

This means:

  • If the container restarts without the Pod being recreated, the directory may survive.
  • When the Pod is rescheduled, deleted, or its node fails, local snapshots and transaction logs are lost.
  • A single node can resync from other members, but that doesn’t mean the cluster can still recover after all three lose data at the same time.

Three replicas are not a substitute for persistence. Replicas handle runtime availability; PVCs and backups handle recoverability.

Low-latency block storage, such as an SSD StorageClass, suits ZooKeeper better than putting high-frequency transaction logs on shared NFS. A conservative starting point is a 10 GiB PVC per Pod, adjusted by transaction volume and retention policy:

persistence:
  enabled: true
  storageClass: ssd
  size: 10Gi

But you can’t just run a normal rolling update here. volumeClaimTemplates in a StatefulSet involves immutable fields and usually requires a dedicated migration design:

  1. Create and verify backups.
  2. Confirm the existing ensemble is healthy.
  3. Prepare a new StatefulSet with PVCs, or rebuild according to the Chart’s upgrade requirements.
  4. Migrate one member at a time and wait for resync.
  5. Verify snapshots, transaction logs, and failure recovery.
  6. Keep a clear rollback window.

Memory shrinking and storage migration should be two separate changes; otherwise, when something goes wrong you can’t quickly tell whether the JVM capacity or the data directory is to blame.

Parameters You Shouldn’t Change Along the Way

The current evidence doesn’t point to these parameters, so don’t change them just for the sake of “optimization”:

  • maxClientCnxns: the current connection count is far below the limit.
  • snapCount: current snapshot and transaction pressure is low.
  • Auto-purge period: existing disk growth is normal.
  • Tick and session timeout: no evidence of session churn.
  • Replica count: three nodes is the minimum common production quorum.

Only by changing one explainable capacity variable at a time can you attribute metric changes to a cause.

Definition of Done

ZooKeeper memory optimization counts as complete only when all of the following hold:

  • No unexplained duplicate heap flags in the JVM command line.
  • Heap, request, and limit form a clear three-layer budget.
  • The three members keep quorum throughout the rollout.
  • At least one business peak passes without obvious GC or latency regression.
  • znode, Session, watch, connection, and request backlog are all monitored.
  • OOMKilled, frequent elections, and Session rebuilds have alerts.
  • The emptyDir risk is covered by a standalone SSD PVC migration plan and a recovery drill.

Final Conclusion

A ZooKeeper Pod near 2 GiB is not a memory leak. A fixed Xms=Xmx=2g, the Chart’s large resource preset, and committed JVM pages that get gradually touched are enough to produce a stable high working set even with very little data.

The right approach isn’t to cut memory in half in one shot just because CPU is low. Read the real command line first, prove the load scale with mntr and snapshots, declare requests/limits explicitly, then release resources through the two-phase 1536 MiB → 1024 MiB rolling verification.

The emptyDir discovered during the inspection deserves a higher place on the risk list: over-provisioning wastes capacity, but without persistence you may lose the foundation for recovery when a failure strikes.
