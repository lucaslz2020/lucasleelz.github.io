Migrating Smoothly from Nexus Repository 2 to Nexus 3: Kubernetes, PostgreSQL, and VIP Switchover

A complete record of the Nexus2-to-Nexus3 migration path: the official upgrade wizard, H2 version upgrade, PostgreSQL data migration, Kubernetes StatefulSet, legacy path compatibility, and VIP rollback.

lucaslzAuthor
July 12, 2026 10 min read
#Nexus #Kubernetes #PostgreSQL #Maven #DevOps
{ }

This article is based on a real migration. Servers, addresses, domains, repository counts, component counts, and enterprise configurations have been sanitized. The example Secret and passwords are placeholders.

Series navigation: Kubernetes Rebuild Migration Tutorial Series. It is recommended to complete “Deploying Nexus Repository 3 on Kubernetes from Scratch” first.

A Nexus Repository 2 instance that has been running for years is usually relied on heavily by Maven, Jenkins, development machines, and release scripts. The hard part is not starting Nexus3, but migrating without losing artifacts, breaking permissions, or forcing clients to change too much.

The ultimate goals of this migration are:

  • Move Nexus2’s repositories, users, roles, and configuration into Nexus3.
  • Run Nexus3 on Kubernetes as a single-replica StatefulSet.
  • Use a dedicated persistent volume for the Blob Store.
  • Migrate metadata from H2 to PostgreSQL.
  • Keep the original domain, VIP, port, and /nexus context path.
  • Keep legacy Maven URLs working during the transition period.
  • Fail back to Nexus2 quickly if the migration fails.

Sonatype ended maintenance of Nexus Repository 2 on June 30, 2025. The product no longer receives new features or bug fixes, and Sonatype recommends migrating to Nexus3 as soon as possible. See Nexus Repository 2 Version Status.

Final Migration Path

flowchart LR
  A["Nexus2 final version<br/>old server"] -->|"official Upgrade"| B["Nexus3 interim version<br/>H2 / Kubernetes"]
  B -->|"in-place version upgrade"| C["Nexus3 target version<br/>H2 / Kubernetes"]
  C -->|"Database Migrator"| D["Nexus3 target version<br/>PostgreSQL / Kubernetes"]
  E["Maven / Jenkins"] --> F["original domain or VIP"]
  F --> D
  D --> G["Blob Store PV"]
  D --> H["PostgreSQL"]

The key design decision is to split the migration into two phases:

  1. Nexus2 → Nexus3, still running on H2.
  2. After Nexus3 reaches the target version, migrate H2 → PostgreSQL.

Do not combine repository conversion, version upgrade, database migration, and traffic switchover into a single step.

Why Nexus2’s Data Directory Cannot Be Mounted Directly into Nexus3

Nexus3 redesigned component metadata and the Blob Store. Nexus2’s working directory is not a data volume that Nexus3 can read directly.

The correct path is:

  • Upgrade Nexus2 to the final officially supported version.
  • Use the Nexus2 Upgrade Agent and the Nexus3 Upgrade Capability.
  • Migrate repository content and server configuration.
  • Run Finalize after synchronization completes.

The official procedure is documented in Upgrade from Nexus Repository 2. Check the interim and target versions against the official upgrade matrix at the time of execution; do not treat one successful combination as a permanent rule.

Pay special attention to Nexus2’s legacy paths:

/nexus/content/repositories/releases/
/nexus/content/groups/public/

Nexus3’s modern paths are usually:

/nexus/repository/releases/
/nexus/repository/public/

If clients cannot all be updated at once, add explicit rewrites at the outer proxy and set a removal date for the legacy paths.

Full Backup of Nexus2

At minimum, keep:

  1. The Nexus2 program directory.
  2. The Nexus2 working directory.
  3. Repository storage and checksum records.

After freezing writes, take a filesystem backup:

systemctl stop nexus

tar -C /opt -czf /backup/nexus2-program.tar.gz nexus-2
tar -C /data -czf /backup/nexus2-work.tar.gz sonatype-work
sha256sum /backup/nexus2-*.tar.gz > /backup/SHA256SUMS

Copying directories while the service is running can produce backups where metadata and artifacts are inconsistent.

Storage Design in Kubernetes

The Blob Store is read and written frequently. This migration uses a dedicated local PV with the following settings:

apiVersion: v1
kind: PersistentVolume
metadata:
  name: nexus-data
spec:
  capacity:
    storage: <capacity>
  accessModes: [ReadWriteOnce]
  persistentVolumeReclaimPolicy: Retain
  storageClassName: nexus-local
  local:
    path: /data/nexus
  nodeAffinity:
    required:
      nodeSelectorTerms:
        - matchExpressions:
            - key: kubernetes.io/hostname
              operator: In
              values: [repo-node]

Retain matters: if you accidentally delete the StatefulSet or PVC, historical artifacts must not be destroyed as a result.

A local PV pins the Pod to a specific node, so it is not a high-availability solution. For the single-replica Community Edition, the trade-off is lower storage complexity in exchange for a clearer failure boundary.

Keep the Context Path and Health Checks

To minimize client changes, keep using /nexus:

application-port=8081
application-host=0.0.0.0
nexus-context-path=/nexus
nexus.datastore.enabled=true

The probes use the status endpoint instead of the homepage HTML:

startupProbe:
  httpGet:
    path: /nexus/service/rest/v1/status
    port: http
  failureThreshold: 60
  periodSeconds: 10
  timeoutSeconds: 5

The first upgrade and index rebuild can take several minutes. connection refused only means the process is not listening on the port yet; the real cause is in nexus.log.

The Correct Nexus2 → Nexus3 Sequence

Start with Nexus3 on H2:

  1. Create the Upgrade Agent / Upgrade Capability.
  2. Establish the connection and run pre-checks.
  3. Migrate repository content.
  4. Migrate server configuration.
  5. Wait for the sync queue to reach zero.
  6. Freeze Nexus2 uploads.
  7. Run Finalize and Done.

Before Finalize, at least verify the latest Hosted version, Proxy fetching, Group ordering, anonymous access, and a real Maven build.

The Upgrade Wizard is not a two-way sync system. Once the migration starts, stop modifying Nexus2’s users, roles, and repository structure.

Upgrade H2 First, Then Migrate to PostgreSQL

After the Nexus2 migration, upgrade Nexus3 to the target version while still on H2. Before upgrading, back up both H2 and the Blob Store so the two come from the same recovery point.

After starting the new version, wait for the internal schema, upgrade, browse, and search tasks to finish. A Ready Pod does not mean the upgrade tasks are complete; do not restart the instance repeatedly while they are running.

Prepare PostgreSQL

CREATE ROLE nexus LOGIN PASSWORD '<random-password>';
CREATE DATABASE nexus OWNER nexus;

\connect nexus

CREATE SCHEMA nexus AUTHORIZATION nexus;
GRANT USAGE, CREATE ON SCHEMA nexus TO nexus;
ALTER ROLE nexus SET search_path TO nexus;

The password is stored only in a Kubernetes Secret:

kubectl -n repository create secret generic nexus-db \
  --from-literal=username=nexus \
  --from-literal=password="$(openssl rand -base64 36)"

Base64 is encoding, not encryption. Neither the Secret’s plaintext nor command output may end up in Git or CI logs.

Use the Database Migrator

The migrator version must match the Nexus target version, and its SHA256 must be verified. See Migrating to a New Database for the official instructions.

sha256sum nexus-db-migrator-<version>.jar

Starting with Nexus Repository 3.93.0, self-hosted deployments require at least Java 25; confirm the runtime requirements before running the migrator. See 2026 Release Notes.

Stop Nexus completely before migrating:

kubectl -n repository scale statefulset/nexus --replicas=0
kubectl -n repository wait --for=delete pod/nexus-0 --timeout=180s

If the password contains characters like +, &, %, ?, or #, encode them before writing the JDBC URL, and never print the full URL.

A migration Job reporting Complete is not the only criterion; also check the final summary for skipped or failed records. After a failure, do not rerun against a schema that already has data — locate the cause first and restore a clean target.

After the migration, run the following while Nexus is still stopped:

VACUUM (FULL, ANALYZE);

Connect to PostgreSQL and Start the Final Version

env:
  - name: NEXUS_DATASTORE_NEXUS_JDBCURL
    value: jdbc:postgresql://postgresql.repository.svc.cluster.local:5432/nexus?currentSchema=nexus
  - name: NEXUS_DATASTORE_NEXUS_USERNAME
    value: nexus
  - name: NEXUS_DATASTORE_NEXUS_PASSWORD
    valueFrom:
      secretKeyRef:
        name: nexus-db
        key: password

After startup, wait for the Browse/Search rebuild tasks to finish, then verify search, download, and upload.

Five-Layer Acceptance

  1. Pod and logs: Ready, stable across restarts, no database or Blob errors.
  2. Status endpoint: /nexus/service/rest/v1/status returns normally.
  3. Repositories: verify Hosted, Proxy, and Group individually.
  4. Real build: run a Maven build covering POM, metadata, checksum, and authentication.
  5. Upload: verify a Hosted upload with a temporary version and clean it up.

Opening the admin page in a browser cannot prove that the Maven build chain works.

Seamless VIP Switchover and Rollback

When many legacy clients depend on a fixed address, keep the old address as a VIP and point it at the new node.

Before switching, all of the following must be true:

  • The old Nexus2 is stopped.
  • The old node no longer holds the VIP.
  • The new Nexus3 has been verified via its internal address.
  • Downloads, uploads, and builds pass again after the VIP is added.

At no point may two machines hold the same IP; otherwise you will get ARP flapping and requests landing on random machines.

Rollback order: freeze new uploads, remove the VIP from the new node, confirm the network has converged, start the old Nexus2, and restore the old entry point. Once the new environment accepts writes, rollback must also reconcile data differences between the two sides.

Community Edition Usage Governance

As of this article’s publication, Nexus Repository Community Edition is limited to 40,000 components or 100,000 requests per day. When the limit is exceeded, new components cannot be added, and metrics updates may be delayed by about an hour. See Usage Center.

Governance principles:

  • Prioritize cleaning up Proxy caches that have been unused for a long time.
  • Use separate retention policies for Hosted releases, snapshots, and internal third-party artifacts.
  • Back up PostgreSQL before cleanup.
  • Soft-delete first, then compact the Blob Store after the observation period.
  • Do not treat cleanup as failed just because the page has not refreshed in a short time.

A Proxy can refetch from upstream, but a Hosted repository is often the enterprise’s only source; the two cannot share the same cleanup policy.

Common Pitfalls

  • Migrating the database on the wrong version.
  • Running the Migrator while Nexus is still running.
  • Granting privileges on the database but not on the schema.
  • Not encoding the JDBC password.
  • Restarting right after the Job reports Complete and ignoring index tasks.
  • Backing up only the database, not the Blob Store.
  • Verifying only the admin page.
  • Destroying the old server and recovery points too early.

Summary

Upgrading from Nexus2 to Nexus3 is not about “swapping the image”; it is about controlling four boundaries:

  1. Content and metadata are converted through a supported path.
  2. Version upgrade and database migration are completed in phases.
  3. The database, Blob Store, and client access paths are verified together.
  4. Every irreversible step has an independent recovery point before it.

Stick to backing up first, migrating in phases, verifying layer by layer, and switching traffic last. That way, downtime stays concentrated in the final freeze, database migration, and entry-point switchover windows, rather than leaving the whole project unusable for an extended period.
