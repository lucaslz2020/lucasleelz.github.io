Deploying Nexus Repository 3 on Kubernetes from Scratch: PostgreSQL, PVC, and Ingress

Deploy a persistent, backup-friendly, upgradeable Nexus Repository 3 on Kubernetes, step by step from namespace to Ingress.

lucaslzAuthor
July 11, 2026 8 min read
#Nexus #Kubernetes #PostgreSQL #StatefulSet #Maven
{ }

This article covers only a fresh Nexus Repository 3 deployment; Nexus 2 data migration is out of scope. Getting a clean Nexus 3 up and stable first makes troubleshooting much easier when you move on to the migration tutorial.

Series navigation: Kubernetes Rebuild Migration Series. This article is a prerequisite tutorial for the Nexus migration.

The examples use a single-instance StatefulSet, an external PostgreSQL database, and persistent volumes. High-availability multi-instance deployments involve licensing and the official HA architecture; you cannot simply change replicas from 1 to 3.

Final Architecture

flowchart LR
  A["Maven / npm / Docker clients"] --> B["Ingress or internal VIP"]
  B --> C["nexus Service"]
  C --> D["Nexus StatefulSet single instance"]
  D --> E["PVC /nexus-data"]
  D --> F["PostgreSQL"]
  G["Backup job"] --> E
  G --> F

The official Nexus container keeps configuration, logs, and artifact data in /nexus-data and runs the container process as UID 200. This directory must be persistent and writable. See the official container image documentation.

Step 1: Pin the Version, Capacity, and Context Path

Freeze these values first:

NEXUS_VERSION=<approved-version>
NEXUS_IMAGE=<image-registry>/sonatype/nexus3:${NEXUS_VERSION}
NEXUS_HOST=repo.example.com
NEXUS_CONTEXT=/nexus

Do not use latest. After syncing the image to an internal registry, record the digest:

crane digest "$NEXUS_IMAGE"

Plan capacity with at least the following in mind:

  • Total size of current hosted artifacts.
  • The proxy cache upper limit and cleanup policy.
  • Temporary space for the database, logs, and tasks.
  • The backup retention period.
  • Expected growth over the next one to two years.

Step 2: Create the Namespace and PostgreSQL Database

kubectl create namespace repository-system

PostgreSQL is best provided by a dedicated database platform that also handles backups. Create a dedicated account and database:

CREATE ROLE nexus LOGIN PASSWORD '<generated-password>';
CREATE DATABASE nexus OWNER nexus ENCODING 'UTF8';

Verify that the Nexus node can reach the database:

kubectl -n repository-system run pg-check --rm -it --restart=Never \
  --image=<approved-postgres-client-image> -- \
  psql 'postgresql://nexus:<password>@<postgres-host>:5432/nexus' \
  -c 'select current_database(), current_user;'

Keep the password out of shell history. In production, use interactive input, temporary environment variables, or a secret management system.

Step 3: Create the Database Secret

kubectl -n repository-system create secret generic nexus-database \
  --from-literal=jdbc-url='jdbc:postgresql://<postgres-host>:5432/nexus' \
  --from-literal=username='nexus' \
  --from-literal=password='<generated-password>'

Nexus officially supports configuring PostgreSQL via environment variables, JVM parameters, or a properties file, but mixing approaches is not recommended. In a container environment, environment variables are the clearest choice. See Installing Nexus Repository with PostgreSQL.

Step 4: Create the PVC

Save as 00-storage.yaml:

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: nexus-data
  namespace: repository-system
spec:
  storageClassName: <storage-class>
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: <planned-size>

Apply it and confirm the binding:

kubectl apply -f 00-storage.yaml
kubectl -n repository-system get pvc nexus-data -w

The PVC must show Bound. For a static local volume, also add nodeAffinity to the Nexus Pod and document node-failure recovery in the Runbook.

Step 5: Create the Service

Save as 01-service.yaml:

apiVersion: v1
kind: Service
metadata:
  name: nexus
  namespace: repository-system
spec:
  selector:
    app.kubernetes.io/name: nexus
  ports:
    - name: http
      port: 8081
      targetPort: http
kubectl apply -f 01-service.yaml

If you later assign a dedicated port for a Docker hosted/group repository, add it explicitly to both the Service and the container ports, and keep it separate from the management port.

Step 6: Create the StatefulSet

Save as 02-statefulset.yaml:

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: nexus
  namespace: repository-system
spec:
  serviceName: nexus
  replicas: 1
  selector:
    matchLabels:
      app.kubernetes.io/name: nexus
  template:
    metadata:
      labels:
        app.kubernetes.io/name: nexus
    spec:
      terminationGracePeriodSeconds: 120
      securityContext:
        fsGroup: 200
        fsGroupChangePolicy: OnRootMismatch
      containers:
        - name: nexus
          image: <image-registry>/sonatype/nexus3:<approved-version>@sha256:<digest>
          ports:
            - { name: http, containerPort: 8081 }
          env:
            - { name: NEXUS_CONTEXT, value: /nexus }
            - name: NEXUS_DATASTORE_NEXUS_JDBCURL
              valueFrom:
                { secretKeyRef: { name: nexus-database, key: jdbc-url } }
            - name: NEXUS_DATASTORE_NEXUS_USERNAME
              valueFrom:
                { secretKeyRef: { name: nexus-database, key: username } }
            - name: NEXUS_DATASTORE_NEXUS_PASSWORD
              valueFrom:
                { secretKeyRef: { name: nexus-database, key: password } }
            - name: INSTALL4J_ADD_VM_PARAMS
              value: >-
                -Xms2g -Xmx2g -XX:MaxDirectMemorySize=2g
                -Djava.util.prefs.userRoot=/nexus-data/javaprefs
          resources:
            requests: { cpu: "2", memory: 4Gi }
            limits: { cpu: "4", memory: 6Gi }
          startupProbe:
            httpGet: { path: /nexus/service/rest/v1/status, port: http }
            periodSeconds: 10
            timeoutSeconds: 5
            failureThreshold: 60
          readinessProbe:
            httpGet: { path: /nexus/service/rest/v1/status, port: http }
            periodSeconds: 10
            timeoutSeconds: 5
            failureThreshold: 6
          livenessProbe:
            httpGet: { path: /nexus/service/rest/v1/status, port: http }
            periodSeconds: 30
            timeoutSeconds: 5
            failureThreshold: 6
          volumeMounts:
            - { name: data, mountPath: /nexus-data }
      volumes:
        - name: data
          persistentVolumeClaim: { claimName: nexus-data }

The resource requests are only a starting point; tune them after load testing based on index size, concurrent request volume, and the official system requirements. Do not set the JVM heap directly to the container memory limit.

Validate before applying:

kubectl apply --server-side --dry-run=server -f 02-statefulset.yaml
kubectl apply -f 02-statefulset.yaml
kubectl -n repository-system rollout status statefulset/nexus --timeout=20m

The first startup can take several minutes. startupProbe should cover database initialization and plugin loading; the readiness probe should not admit traffic too early.

Step 7: Troubleshoot Startup Failures

kubectl -n repository-system get pod nexus-0 -o wide
kubectl -n repository-system describe pod nexus-0
kubectl -n repository-system logs nexus-0 --tail=300
kubectl -n repository-system get endpointslice \
  -l kubernetes.io/service-name=nexus -o wide

Common causes:

  • The PVC is not bound, or the directory is not writable by UID 200.
  • The PostgreSQL address, account, or TLS parameters are wrong.
  • The probe path does not include the /nexus context.
  • The container has too little memory and gets OOMKilled.
  • The database schema was initialized by an incompatible version.

connection refused means the port is not listening yet. During first startup, read the application logs instead of deleting the Pod repeatedly.

Step 8: Retrieve the Initial Admin Password

kubectl -n repository-system exec nexus-0 -- \
  sh -c 'test -f /nexus-data/admin.password && cat /nexus-data/admin.password'

After the first login:

  1. Change the admin password immediately and store it in a password manager.
  2. Create a personal admin account instead of sharing admin.
  3. Decide whether to allow anonymous downloads based on your security requirements.
  4. Configure email, auditing, and cleanup tasks.
  5. Confirm that Nexus has deleted or invalidated the admin.password file.

Never copy the initial password into wikis, Git, or chat logs.

Step 9: Create the Ingress

Save as 03-ingress.yaml:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: nexus
  namespace: repository-system
  annotations:
    nginx.ingress.kubernetes.io/proxy-body-size: "0"
    nginx.ingress.kubernetes.io/proxy-read-timeout: "600"
    nginx.ingress.kubernetes.io/proxy-send-timeout: "600"
spec:
  ingressClassName: nginx
  tls:
    - hosts: [repo.example.com]
      secretName: repo-example-com-tls
  rules:
    - host: repo.example.com
      http:
        paths:
          - path: /nexus
            pathType: Prefix
            backend:
              service:
                name: nexus
                port: { number: 8081 }

Before changing public DNS, test with --resolve:

curl -kfsS --resolve repo.example.com:443:<ingress-address> \
  https://repo.example.com/nexus/service/rest/v1/status

It should report that Nexus is available. Before uploading large artifacts, verify that the Ingress, load balancer, and CDN have no request body size limits.

Step 10: Create Maven Repositories and Validate

Create in the UI:

  • maven-releases: hosted, with Version policy set to Release.
  • maven-snapshots: hosted, with Version policy set to Snapshot.
  • maven-central: proxy, pointing at Maven Central.
  • maven-public: group, containing all of the above.

Client repository URL:

<repository>
  <id>nexus-public</id>
  <url>https://repo.example.com/nexus/repository/maven-public/</url>
</repository>

Deployment URL:

<distributionManagement>
  <repository>
    <id>nexus-releases</id>
    <url>https://repo.example.com/nexus/repository/maven-releases/</url>
  </repository>
  <snapshotRepository>
    <id>nexus-snapshots</id>
    <url>https://repo.example.com/nexus/repository/maven-snapshots/</url>
  </snapshotRepository>
</distributionManagement>

Put credentials in the user-level settings.xml or in CI secrets — never in the project POM.

Use a temporary Maven project to verify:

mvn -U dependency:get -Dartifact=<group>:<artifact>:<version>
mvn deploy

Step 11: Configure Backup and Cleanup Tasks

Backups must cover all of the following:

  • Consistent PostgreSQL backups.
  • Blobs, configuration, and key material under /nexus-data.
  • Kubernetes manifests and references in the secret management system.

The database and blob snapshots must be taken at coordinated points in time, otherwise metadata and files can become inconsistent. Proxy caches can have cleanup policies, but deleting hosted artifacts requires retention and audit rules.

Definition of Done

  • The StatefulSet recovers normally with the same PVC after a rebuild.
  • Restore drills have been completed for both PostgreSQL and /nexus-data.
  • The Service, Ingress, TLS, and context path are consistent.
  • Maven downloads, Release deploys, and Snapshot deploys all succeed.
  • The initial admin password has been rotated, and CI uses a dedicated least-privilege account.
  • The image version and digest are pinned, and the upgrade and rollback procedure is documented.

After the clean deployment is complete and stable, move on to migrating data from Nexus 2 to Nexus 3. Do not combine “setting up the new platform” and “importing historical data” into a single irreversible operation.
