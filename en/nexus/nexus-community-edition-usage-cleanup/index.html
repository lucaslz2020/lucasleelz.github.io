Nexus Repository Community Edition: Usage Limits and Storage Cleanup in Practice

Understand the differences between component count, request volume, Blob space, and maven-public; then inventory hosted and proxy repositories, configure Cleanup Policy, compact the Blob Store, and verify that CE usage drops back down.

lucaslzAuthor
July 18, 2026 8 min read
#Nexus #Community Edition #Cleanup Policy #Blob Store #Maven
{ }

This article uses generic repository names, domains, and capacities. Deleting hosted artifacts may be irreversible, so test every command in a test environment and complete backups first.

When the Nexus UI says the instance is “approaching its usage limit”, that’s not a disk space warning, and it doesn’t mean Kubernetes is refusing to run the Community Edition.

As of this writing, Sonatype’s official Usage Center states that the Community Edition is limited to 40,000 total components or 100,000 requests per day. Once either limit is exceeded, no new components can be added until usage drops back below the limit. Metric changes can take up to about an hour to be reflected. Usage Center

These rules are part of the product edition and licensing policy, so review the official page again before acting.

First, distinguish four easily confused concepts

ConceptMeaningDoes it count toward CE usage?
ComponentA logical component/version managed by NexusYes — affects the component count
AssetConcrete files such as POM, JAR, and checksum filesNot equivalent to the component count
Blob Store spaceDisk space actually occupied by filesNot equivalent to the component count
RequestClient download, search, and upload requestsAffects the daily request count

maven-public is usually just a Maven group repository name; it doesn’t mean a “public edition” or a different Nexus license.

Hosted, proxy, and group repositories carry different cleanup risks

hosted

Stores the Releases and Snapshots your organization publishes itself. Deleting them can permanently lose build artifacts, so confirm first:

  • Whether production, historical branches, or rollbacks still use them.
  • Whether the source code can rebuild a byte-identical binary.
  • Whether audit and retention requirements are satisfied.
  • Whether offline backups exist.

proxy

Stores caches of upstream repositories. When the upstream still exists and the network is reliable, caches can usually be re-downloaded, so proxy repositories are the better first target for governance.

However, upstream components may already be deleted or changed, or unreachable due to network problems. Don’t treat every proxy cache as worthless.

group

A group aggregates other repositories and is generally not a direct storage target for cleanup. Clean up the hosted/proxy members it contains instead.

Step 1: Back up the database and Blob Store

When Nexus uses PostgreSQL, the backup must cover:

PostgreSQL 数据库
全部 Blob Store
/nexus-data 中的配置和密钥
Kubernetes Secret 与清单

The database and Blob backup time points must be coordinated. If you back up only the database, restoration leaves metadata pointing at files that don’t exist; if you back up only the Blobs, you can’t rebuild the complete repository state either.

pg_dump -Fc -h <postgres-host> -U <backup-user> <nexus-database> \
  -f backup/nexus-before-cleanup.dump

sha256sum backup/nexus-before-cleanup.dump \
  > backup/nexus-before-cleanup.dump.sha256

Create a read-only snapshot or consistent backup of the Blob Store using the underlying storage capabilities. Don’t just tar the directory directly while Nexus is writing heavily.

Step 2: Record the pre-cleanup baseline

Screenshot or export from the Usage Center:

  • Total Components.
  • Daily Requests.
  • Metric update time.

Record repositories and Blobs:

curl --fail --silent --show-error \
  --netrc-file <secure-netrc> \
  https://repo.example.com/nexus/service/rest/v1/repositories \
  > reports/repositories-before.json

curl --fail --silent --show-error \
  --netrc-file <secure-netrc> \
  https://repo.example.com/nexus/service/rest/v1/blobstores \
  > reports/blobstores-before.json

Don’t commit commands with credentials, .netrc files, or internal information from API responses to a public repository.

Step 3: Take inventory by repository type

Create a table:

repository,format,type,owner,retention_days,upstream_recoverable,cleanup_policy
maven-releases,maven2,hosted,release-team,365,false,manual-review
maven-snapshots,maven2,hosted,dev-team,30,true,snapshot-retention
maven-central,maven2,proxy,platform-team,60,true,proxy-cache

The usual priority is:

失效 proxy cache
→ 过期 Snapshot
→ 无引用的临时 hosted 制品
→ Release 人工审计

Step 4: Paginate component exports instead of relying on the UI

The Nexus Components API paginates with a continuation token; a single page of results doesn’t represent the repository total.

Request structure:

curl --fail --silent --show-error \
  --netrc-file <secure-netrc> \
  'https://repo.example.com/nexus/service/rest/v1/components?repository=<repository>'

An automation script should:

  1. Save items.
  2. Read continuationToken.
  3. Keep requesting while the token is non-empty.
  4. Output only sanitized group/name/version/lastModified.
  5. Generate candidates without calling DELETE directly.

Step 5: Find consumers before deciding what to delete

Search:

  • Maven POMs, Gradle builds, and npm lockfiles.
  • Jenkinsfiles and pipeline parameters.
  • Kubernetes images and startup scripts.
  • Git tags, Releases, and maintenance branches.
  • Production rollback checklists.

A Release artifact not referenced by the current mainline doesn’t mean historical versions aren’t needed.

Have the candidate list confirmed by at least two people: the artifact owner and operations.

Step 6: Configure Cleanup Policy for proxy repositories

Create a Cleanup Policy in the Nexus admin UI and set the criteria supported by the target version:

  • Last downloaded before.
  • Last blob updated before.
  • Release type or format-related criteria.
  • Name regex, restricted to explicit namespaces.

Start by attaching it to one low-risk proxy repository, wait for the task to run, and validate with samples. Don’t attach every repository on the first day.

Step 7: Govern Snapshots

Common Snapshot rules:

保留最近 N 个版本
保留最近 N 天
保留仍被活跃分支引用的版本
Release 不套用 Snapshot 规则

Before deleting, use an isolated Maven project to verify the download paths for the latest and historical Snapshots. After cleanup, verify the versions still within the retention scope.

Step 8: Run tasks in the correct order

Task names vary between Nexus versions; the general order is:

执行 Cleanup Policy
→ 等待逻辑删除完成
→ 删除不再引用的 Blob
→ Compact Blob Store
→ 等待数据库与 Usage Center 指标更新

Compact Blob Store mainly reclaims disk space; it doesn’t immediately reduce the component count. Don’t run another bulk delete just because the disk hasn’t shrunk right away.

Record while tasks run:

  • Task ID, start and end time.
  • Number of deletion candidates.
  • Task logs and errors.
  • Blob space changes.
  • Usage Center update time.

Step 9: Verify proxy caches can be re-fetched

After cleaning proxy caches, download a component eligible for deletion into an empty local Maven repository:

mvn -Dmaven.repo.local=<temporary-empty-directory> \
  dependency:get \
  -Dartifact=<group>:<artifact>:<version>

Also watch the Nexus request log and proxy remote status. If the upstream is unavailable, stop before expanding the cleanup.

Step 10: Verify hosted repositories

At minimum:

  • Download a retained historical Release.
  • Download the latest Snapshot.
  • Upload a new test Snapshot.
  • Publish and read with the CI account.
  • Verify permissions are unchanged with anonymous/regular accounts.

If the CE limit has already been exceeded, adding components may still be blocked; wait for the metrics to confirm usage has dropped. Sonatype notes that the Usage Center can lag by up to about an hour.

What to do when daily requests exceed the limit

Cleaning up components doesn’t directly reduce request volume. Analyze instead:

  • Whether CI forces updates of all dependencies on every run.
  • Whether error retries or health checks hit the repository frequently.
  • Whether developer builds bypass local caches.
  • Whether the same component is downloaded repeatedly at scale.
  • Whether proxy, mirror, and build cache policies are reasonable.

Don’t return overly long, irreversible error cache headers for Releases just to reduce request counts.

Why you shouldn’t modify the source code to bypass the limits

  • Limits may exist simultaneously in the UI, the server-side write path, and license status.
  • Modified builds lose the official upgrade and security patch path.
  • Database structure and task behavior become unsupported.
  • The next upgrade may directly break private modifications.
  • License terms can’t be changed by a frontend number.

The right choice is to reduce real usage, adjust the architecture, or purchase a version that matches your scale.

When to consider Pro

  • The number of legitimate business components exceeds the CE limit long-term.
  • Daily request volume comes from reasonable CI/CD rather than error traffic.
  • Artifact retention is constrained by audit requirements and can’t be cut further.
  • You need official HA, support, or enterprise capabilities.
  • Cleanup costs already exceed the value of a license and operational effort.

Definition of done

  • Database and Blob Store complete consistent backup and restore verification.
  • Every repository has an owner, type, and retention policy.
  • Proxy, Snapshot, and Release use different cleanup rules.
  • Every deletion candidate has reference scanning and human approval.
  • Cleanup and Blob Compact tasks run in the correct order with complete logs.
  • Maven download, publishing, and CI builds pass.
  • Usage Center returns to a safe range after metrics refresh.
  • Cleanup rules enter regular audits instead of ad-hoc deletions near the limit.

The goal of Nexus capacity governance isn’t to make the page numbers temporarily smaller; it’s to keep the artifact lifecycle, cache, audit, and recovery capabilities under control long-term.
