Nexus3 Kubernetes Migration Runbook: H2, PostgreSQL, Probes, and Seamless Cutover

An executable Kubernetes runbook for the Nexus2-to-Nexus3 migration, covering resource creation, the Upgrade Wizard, H2 upgrade, Database Migrator, verification, and VIP rollback.

#Nexus #Kubernetes #Runbook #PostgreSQL #StatefulSet

This article keeps only the generic execution logic. Addresses, nodes, domains, capacities, and Secrets are placeholders; before executing, re-confirm everything against the official version matrix and your own recovery drill results.

Series navigation: Kubernetes Rebuild Migration Tutorial Series. This article covers item-by-item execution and acceptance during the formal migration window.

The previous article explained the overall Nexus2 → Nexus3 → PostgreSQL design. This one condenses the migration into an executable checklist that focuses on one question: when can each step proceed.

Fixed Design

Freeze the following decisions before migration:

  • Nexus2 has been upgraded to the final officially supported version.
  • Nexus3 uses a verified interim version to receive the Upgrade Wizard data.
  • Nexus3 upgrades to the final target version while running on H2.
  • Database Migrator strictly matches the target version.
  • The Java versions for Nexus and the migrator meet the target version requirements.
  • Blob Store uses a dedicated persistent volume with the Retain reclaim policy.
  • PostgreSQL uses a dedicated database, role, and schema.
  • The /nexus context path stays unchanged.
  • The old domain or VIP is switched only after final verification.

Required Order

Nexus2 最终版与完整备份
→ Nexus3 中转版 H2
→ Upgrade Wizard + Finalize
→ Nexus3 目标版 H2
→ H2 备份与 Blob Store 恢复点
→ 停止 Nexus
→ Database Migrator
→ PostgreSQL VACUUM
→ Nexus3 目标版 PostgreSQL
→ Browse/Search 完成
→ 真实构建与上传
→ VIP/域名切换

Do not migrate to PostgreSQL early on the interim version, and do not let Nexus run while the database migration is in progress.

1. Create Kubernetes Base Resources

Create first:

  1. StorageClass, PV, PVC.
  2. Non-sensitive ConfigMap.
  3. Nexus Service.
  4. PostgreSQL database and schema initialization Job.
  5. Database Secret.

Create the Secret with a command instead of writing plaintext YAML:

kubectl -n repository create secret generic nexus-db \
  --from-literal=username=nexus \
  --from-literal=password="$(openssl rand -base64 36)"

Storage acceptance:

  • PVC Bound.
  • PV is Retain.
  • Target node directory has enough capacity.
  • Nexus container UID/GID has write permission.
  • Blob Store and database temp-file space are assessed separately.

2. Start the Interim Nexus3 with H2

kubectl -n repository apply -f nexus3-migration.yaml
kubectl -n repository rollout status statefulset/nexus --timeout=15m

curl -fsS \
  http://<migration-address>:8081/nexus/service/rest/v1/status

Use the status endpoint for the startup probe, and allow enough time for the first upgrade:

startupProbe:
  httpGet:
    path: /nexus/service/rest/v1/status
    port: http
  periodSeconds: 10
  timeoutSeconds: 5
  failureThreshold: 60

If the probe reports connection refused, check nexus.log first; do not keep increasing the wait time indefinitely.

3. Run the Nexus2 Upgrade Wizard

  1. Back up the Nexus2 program and working directory.
  2. Create the Upgrade Agent on Nexus2.
  3. Create the Upgrade Capability on Nexus3.
  4. Migrate repository content.
  5. Migrate server configuration.
  6. Wait for the sync queue to reach zero.
  7. Freeze uploads and stop Nexus2.
  8. Run Finalize and Done.

Confirm the following before Finalize:

  • Latest Hosted artifacts exist.
  • Proxy can re-pull.
  • Group members and their order are correct.
  • Users, roles, and anonymous access are correct.
  • Both the modern URLs and the legacy URLs that must remain compatible are available.
  • At least one real Maven build passes.

4. Upgrade to the Target Version, Still on H2

First create an official H2 backup, record its SHA256, and back up the Blob Store:

sha256sum /backup/nexus-h2-* /backup/nexus-blob-* > /backup/SHA256SUMS

Then upgrade the StatefulSet image. After startup, wait for all internal schema and upgrade tasks to finish, and regenerate the H2 restore point.

Do not restart the Pod while internal tasks are running.

5. Prepare PostgreSQL

CREATE ROLE nexus LOGIN PASSWORD '<random-password>';
CREATE DATABASE nexus OWNER nexus;

\connect nexus

CREATE SCHEMA nexus AUTHORIZATION nexus;
GRANT USAGE, CREATE ON SCHEMA nexus TO nexus;
ALTER ROLE nexus SET search_path TO nexus;

Verify that the application role can:

  • Connect to the database.
  • Create and drop temporary tables in the target schema.
  • Use the expected search_path.

Granting only database-level privileges, without USAGE and CREATE on the schema, still makes the migrator fail.

6. Run the Database Migrator

Download the migrator matching the Nexus target version and verify it:

curl -fLO https://download.sonatype.com/nexus/nxrm3-migrator/nexus-db-migrator-<version>.jar
curl -fLO https://download.sonatype.com/nexus/nxrm3-migrator/nexus-db-migrator-<version>.jar.sha256

test "$(sha256sum nexus-db-migrator-<version>.jar | awk '{print $1}')" = \
  "$(cat nexus-db-migrator-<version>.jar.sha256)"

Stop Nexus completely:

kubectl -n repository scale statefulset/nexus --replicas=0
kubectl -n repository wait --for=delete pod/nexus-0 --timeout=180s

The migrator reads the controlled Secret. If the password contains URL-reserved characters, URL-encode it first, and never print the JDBC URL to logs.

Continue conditions:

  • Job status is Complete.
  • The migration summary shows 0 skipped.
  • No failed, constraint, schema permission, or authentication errors.
  • PostgreSQL table, component, asset, and Blob reference counts match the summary.

If migration fails, do not re-run directly against the existing target schema. Find the root cause first, then restore or rebuild a clearly empty schema.

7. Clean Up PostgreSQL and Start the Final Version

While Nexus is still stopped:

VACUUM (FULL, ANALYZE);

Then point the final StatefulSet at PostgreSQL:

env:
  - name: NEXUS_DATASTORE_NEXUS_JDBCURL
    value: jdbc:postgresql://postgresql.repository.svc.cluster.local:5432/nexus?currentSchema=nexus
  - name: NEXUS_DATASTORE_NEXUS_USERNAME
    value: nexus
  - name: NEXUS_DATASTORE_NEXUS_PASSWORD
    valueFrom:
      secretKeyRef:
        name: nexus-db
        key: password

After startup, wait for:

  • Rebuild repository browse
  • Rebuild repository search

Do not restart the instance or switch traffic before these one-time tasks complete.

8. Verification Matrix

Runtime

  • Pod Ready, Restart not growing.
  • Status endpoint is healthy.
  • Logs show no database, Blob, or index errors.
  • Nexus and Java versions match the plan.

Repositories

  • Hosted releases download.
  • Hosted snapshots download.
  • Third-party downloads.
  • Proxy hit and miss both succeed.
  • Group resolves by member order.
  • Search finds known components.

Permissions

  • Users, roles, and Realm are healthy.
  • Anonymous downloads behave as expected.
  • Hosted upload permissions are correct.

Clients

  • Maven runs a full build with real settings.
  • Jenkins downloads dependencies.
  • Upload and clean up with a temporary version.
  • Legacy /content/ URLs that must be kept are verified or rewritten.

9. Ingress Switchover

Before switching:

  • Old Nexus2 is stopped.
  • Old nodes no longer hold the VIP.
  • New Nexus3 has been verified through the internal address.
  • Backup and rollback commands still work.

Immediately after the switch, verify status, downloads, uploads, and a real build. At no point may two machines hold the same VIP.

Rollback:

  1. Freeze uploads on the new Nexus3.
  2. Remove the VIP from the new node.
  3. Confirm ARP and routes have converged.
  4. Start the old Nexus2.
  5. Restore the old ingress.

10. Finalize Credentials and Backups

  • Delete Secrets used only during the migration window.
  • If a password may have reached the logs, rotate the PostgreSQL role and the Kubernetes Secret.
  • Both passwords must be updated at the same time.
  • Keep Nexus2, both H2 restore points, the PostgreSQL backup, and the Blob Store backup.
  • Release the old server only after a period of stable observation and successful recovery drills.

Maintaining Community Edition Component Counts

Set separate policies for Proxy and Hosted:

  • Proxy: remove cached components that have been unused for a long time.
  • Hosted: retain per release and compliance requirements.
  • Take a PostgreSQL backup before cleanup.
  • Soft-delete first, then run Compact Blob Store after a period of observation.

Usage Center may refresh with a delay, and historical peaks will not drop immediately. Do not repeatedly run cleanup just because the page still shows the old counts for a while.

Definition of Done

迁移器无跳过
+ PostgreSQL 数据与 Blob 引用一致
+ Browse/Search 完成
+ 仓库和权限正确
+ Maven/Jenkins 下载上传通过
+ 入口切换成功
+ 回滚和备份仍可用

A good runbook is not about having as many commands as possible; it makes every irreversible step have a clear input, a continue condition, and a rollback boundary.
