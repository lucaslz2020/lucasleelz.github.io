Wiring DeepSeek V4 Flash from OpenCode Go into Codex: Responses API, Model Catalog, and Profile Switching

A real-timeline retrospective of wiring DeepSeek V4 Flash into Codex through the OpenCode Go Responses API, covering protocol validation, a mistaken proxy detour, plaintext-free runtime authentication, the model catalog, dual-Profile switching, the exec compatibility fix, and verified file edits.

The goal was clear: keep Codex’s existing OpenAI login while wiring the DeepSeek V4 Flash served by OpenCode Go into Codex; use DeepSeek by default, and switch back to OpenAI with a single command when needed.

In the end, three entry points work:

# 默认：DeepSeek V4 Flash
codex

# 显式选择 DeepSeek
codex -p deepseek

# 切回 OpenAI
codex -p openai

The actual process was not a simple model-name change. It touched Responses API compatibility, provider authentication, model metadata, Codex’s custom tools, and the order in which Profile settings override each other. Worse, some settings pass static checks but only expose protocol differences on the first real request.

Requirements, Constraints, and Acceptance Criteria

Before making changes, I split the goal into a set of verifiable conditions:

  • Reuse the deepseek-v4-flash already configured in OpenCode Go instead of requesting and copying another set of credentials.
  • Have Codex call the Responses API directly, without running a local protocol proxy long-term.
  • Keep DeepSeek as the default while keeping the OpenAI login and model available.
  • Switching providers must not change only the model name; it must switch authentication and the model catalog together.
  • Keep the session configuration traceable; preserve the original config.toml before changes.
  • Never print the API Key to terminal logs, articles, Git, or screenshots.
  • Validate not just with curl, but also through native Codex conversations and real file edits.
  • When something is incompatible, keep the full error and locate it in the request protocol instead of masking it with retries.

The final acceptance criteria were:

Acceptance itemPass condition
Raw API/v1/responses returns HTTP 200 and completed
Codex configdoctor reports no warnings and no failures
Model catalogResolves 1,000,000 context, high/max, and the correct tool mode
DeepSeek ProfileStartup info shows opencode-go + deepseek-v4-flash
OpenAI ProfileStartup info shows openai + gpt-5.6-luna
GenerationEach Profile returns the agreed exact text
Agent toolsDeepSeek can create and write the specified content via apply_patch
Credential safetyThe Codex config contains no API Key, and related files are restricted to the current user

Full Troubleshooting Timeline

The integration went through several direction changes. In chronological order:

StageActionResult or assessment

One point in this timeline is counterintuitive: requests succeed without a model catalog, but fail after adding one that looks more complete. The root cause was not model quality; the catalog changed the tool declarations Codex sends upstream.

Final Architecture

flowchart LR
  A[Codex CLI] --> B{Startup arguments}
  B -->|default or -p deepseek| C[DeepSeek Profile]
  B -->|-p openai| D[OpenAI Profile]
  C --> E[OpenCode Go Provider]
  E --> F[deepseek-v4-flash]
  D --> G[OpenAI Provider]
  G --> H[gpt-5.6-luna]

The configuration is split across four files:

~/.codex/
├── config.toml
├── deepseek.config.toml
├── openai.config.toml
└── model-catalogs/
    └── opencode-go.json

config.toml holds the defaults and provider definitions; the two Profiles only override the model, provider, context window, and model catalog. No API Key is written into these files; at runtime it is read from the credential file OpenCode already stores.

Validate the Responses API First — Don’t Infer from Old Sources

At first, older search results led me to believe the DeepSeek endpoint only supported Chat Completions, so I prepared to add a protocol proxy. I then confirmed the Responses API in the DeepSeek Create Response documentation and ran a minimal request against OpenCode Go’s actual endpoint:

curl --request POST \
  --url https://opencode.ai/zen/go/v1/responses \
  --header "Authorization: Bearer ${OPENCODE_GO_API_KEY}" \
  --header "Content-Type: application/json" \
  --data '{
    "model": "deepseek-v4-flash",
    "input": "Reply exactly OK.",
    "max_output_tokens": 16
  }'

The key results, with sensitive values redacted:

{
  "object": "response",
  "status": "completed",
  "model": "deepseek-v4-flash",
  "output_text": "OK",
  "error": null
}

The endpoint returned HTTP 200, status completed, model deepseek-v4-flash, and text OK. This meant no extra protocol proxy was needed, and Codex could use wire_api = "responses" directly.

Docs, Model Service, and Gateway Are Three Layers

It’s not enough to ask “does DeepSeek support the Responses API?”, because a real request crosses three layers:

  1. Whether the DeepSeek model and its interface definition support the Response object.
  2. Whether OpenCode Go exposes a compatible /v1/responses route.
  3. Whether OpenCode Go fully accepts the tool schemas and streaming events Codex sends along.

A minimal text request only proves the first two layers plus the basics of the third. Codex also sends developer instructions, tools, reasoning parameters, and streaming configuration, so native end-to-end testing is still required later.

This step matters: search indexes, old documentation, and third-party write-ups can lag behind, so the target endpoint’s real contract and a minimal request result should be the final authority. The temporarily installed proxy, which was never used, was removed afterwards to avoid leaving a duplicate path.

Don’t write a real API Key into articles, scripts, or shell history while testing. The environment variable above is only there to illustrate the request structure.

First Detour: Why the Proxy Was Installed and Then Removed

The initial judgment came from an outdated impression of the DeepSeek API: if the upstream only offered /chat/completions while the current Codex custom provider only accepts wire_api = "responses", a translation layer would be needed in between.

The backup path at that time was:

flowchart LR
  A[Codex Responses] --> B[Local compatibility proxy]
  B --> C[Chat Completions]
  C --> D[DeepSeek]

The proxy package was installed temporarily, but no service was started and nothing was wired into Codex routing. Once I saw DeepSeek’s new documentation, I did not finish the proxy configuration; instead, I verified the direct connection first. After it passed, I uninstalled the proxy immediately.

This wasn’t just cleaning up an npm package. Keeping an extra proxy layer would introduce:

  • A second place that reads an API Key or credentials.
  • A separate process, port, health check, and startup routine.
  • Two sets of timeouts, streaming forwarding, retries, and error formats.
  • Conversion risk for tool schemas, reasoning fields, and Response events.
  • Unclear fault attribution when something breaks: Codex, the proxy, OpenCode Go, or the model.

A proxy is only worth keeping long-term when direct protocol support is genuinely missing, or when unified auditing, rate limiting, and routing are required.

Inventory Local State Before Configuring

Before overwriting config.toml, I confirmed the current version, default model, login state, and stored OpenCode credentials. At the time of writing:

Codex CLI: 0.145.0
原默认模型: gpt-5.6-luna
原推理强度: high
OpenAI 登录: 已存在
OpenCode Go 凭证: 已存在

Version check:

codex --version

The credential existence check only returns a boolean result and never prints contents:

jq -e \
  '.["opencode-go"].key | type == "string" and length > 0' \
  ~/.local/share/opencode/auth.json >/dev/null

Then check file permissions:

ls -l ~/.codex/config.toml ~/.local/share/opencode/auth.json

If other users on the machine can read these files, fix the permissions before continuing. Don’t run a jq -r that prints the key to the terminal just to confirm it exists.

Configure the OpenCode Go Provider

First, back up the current configuration:

cp ~/.codex/config.toml ~/.codex/config.toml.before-opencode-go

Set the default model in ~/.codex/config.toml:

model = "deepseek-v4-flash"
model_provider = "opencode-go"
model_context_window = 1000000
model_catalog_json = "/Users/you/.codex/model-catalogs/opencode-go.json"
model_reasoning_effort = "high"

[model_providers.opencode-go]
name = "OpenCode Go"
base_url = "https://opencode.ai/zen/go/v1"
wire_api = "responses"
request_max_retries = 4
stream_max_retries = 5
stream_idle_timeout_ms = 300000

base_url ends at /v1; Codex appends /responses based on wire_api. Don’t put the full /responses path into base_url.

The 1,000,000-token context is set explicitly here, but the actually usable window is still jointly constrained by the model, provider, and gateway policy. Boundary-test very long tasks separately before going to production; don’t rely on local metadata alone.

What Each Field Does

SettingPurpose
modelThe model identifier sent upstream
model_providerSelects the Base URL, authentication, and retry strategy group
model_context_windowContext budget hint for Codex
model_catalog_jsonModel name, reasoning levels, tool mode, and other capability metadata
wire_apiTells the provider to use the Responses protocol
request_max_retriesMaximum retries for regular HTTP requests
stream_max_retriesRecovery attempts after a streamed response is interrupted
stream_idle_timeout_msTimeout when a stream has no events for too long

model and model_provider must be understood as a pair. Changing the model to DeepSeek while keeping model_provider = "openai" will not auto-discover OpenCode Go; conversely, selecting a model name only OpenAI provides under the OpenCode Go provider will also fail.

Why Not Just Copy the Key via an Environment Variable

A Codex provider can also read a specified environment variable, but every terminal, IDE, or desktop process that starts Codex would need to inherit the same variable. Since the credential is already managed by OpenCode, having the auth command read the existing file on demand better matches a “single source of credentials” model.

If a team injects environment variables through a unified secret manager, use the team’s standard approach instead; the jq approach in this article suits a personal dev machine that already uses OpenCode’s local credential store.

/models Responding Doesn’t Mean Codex Can Consume It

After configuring the provider, Codex tries to refresh its model list. OpenCode Go’s /models returned an OpenAI-style structure at the time:

{
  "object": "list",
  "data": [{ "id": "deepseek-v4-flash", "object": "model" }]
}

The current Codex model manager expects a catalog structure with a models field on this custom refresh path, so it logged something like:

failed to decode models response:
missing field `models`

That doesn’t mean /responses is unavailable. In fact, both the minimal Response and Codex’s fallback metadata request had already succeeded. What failed was the auxiliary “auto-refresh model catalog” path.

The fix wasn’t to modify the gateway response or ignore logs, but to provide a local model_catalog_json:

文本生成链路: Codex -> /responses -> 成功
模型发现链路: Codex -> /models -> schema 不匹配
替代方案:     Codex -> 本地 model_catalog_json

This decouples model execution from model discovery, while making it explicit that the local config maintains DeepSeek’s capability declarations.

Use Runtime Authentication to Avoid Copying a Plaintext Key

OpenCode already saves credentials in a local auth file, so there’s no reason to copy the same key into config.toml. Codex custom providers support fetching auth info through a command:

[model_providers.opencode-go.auth]
command = "/usr/bin/jq"
args = [
  "-r",
  ".[\"opencode-go\"].key",
  "/Users/you/.local/share/opencode/auth.json",
]
timeout_ms = 5000
refresh_interval_ms = 300000

Note: args is passed to the command directly by Codex and doesn’t necessarily go through a shell, so don’t assume ~ will be expanded. On macOS, use the actual absolute path; on Linux it’s usually /home/username/....

This approach has a few benefits:

  • No second plaintext key in the Codex config.
  • When OpenCode updates the credential, Codex re-reads it on the refresh interval.
  • The config file is safer to back up and review.

Both the auth file and the Codex config should be readable only by the current user, e.g. permissions 600. Diagnostic output should never print the key either.

Why a Custom Model Catalog Is Needed

With only a model name, Codex can start with fallback metadata, but it warns:

Model metadata for `deepseek-v4-flash` not found.
Defaulting to fallback metadata; this can degrade performance and cause issues.

Interestingly, this fallback mode passed native Codex testing first: startup showed deepseek-v4-flash + opencode-go and returned OK. That yields two conclusions:

  • The provider, authentication, and Responses routing work.
  • If a later failure only appears after the custom catalog is enabled, compare the model metadata first instead of questioning the API Key again.

Why the Minimal JSON Failed

I first tried hand-writing a catalog with only the name, context, and reasoning level. Codex rejected it during parsing:

failed to parse model_catalog_json:
missing field `base_instructions`

So model_catalog_json isn’t a lightweight manifest for a model picker. It also carries the base instructions, message templates, truncation policy, and tool capabilities Codex needs at runtime.

Hand-writing dozens of version-dependent fields creates new compatibility problems, so I ended up cloning a structurally complete record from the current models_cache.json and explicitly narrowing DeepSeek’s capabilities.

To let Codex recognize the model name, context window, and reasoning levels, generate a custom catalog based on the current Codex model cache. The command below uses an existing model entry as the structural template and only replaces the DeepSeek-relevant capability fields:

mkdir -p ~/.codex/model-catalogs

jq '{
  models: [
    (.models[] | select(.slug == "gpt-5.6-luna")
      | .slug = "deepseek-v4-flash"
      | .display_name = "DeepSeek V4 Flash (OpenCode Go)"
      | .description = "通过 OpenCode Go 使用的 DeepSeek V4 Flash"
      | .context_window = 1000000
      | .max_context_window = 1000000
      | .effective_context_window_percent = 95
      | .default_reasoning_level = "high"
      | .supported_reasoning_levels = [
          {"effort": "high", "description": "适合日常编程与复杂任务"},
          {"effort": "max", "description": "为最困难任务提供最大推理强度"}
        ]
      | .tool_mode = null
      | .input_modalities = ["text"]
      | .supports_image_detail_original = false
      | .supports_search_tool = false
      | .use_responses_lite = false)
  ]
}' ~/.codex/models_cache.json > ~/.codex/model-catalogs/opencode-go.json

chmod 600 ~/.codex/model-catalogs/opencode-go.json

This isn’t a random minimal JSON. The model catalog schema evolves with Codex versions, so reusing a complete entry from the currently installed version’s cache preserves the base instructions and required fields for that version. This setup was verified against Codex 0.145.0; re-run parsing and end-to-end tests after upgrading.

After generation, restrict permissions and check the key fields without printing the long base instructions:

chmod 600 ~/.codex/model-catalogs/opencode-go.json

jq '.models[] | {
  slug,
  display_name,
  context_window,
  max_context_window,
  default_reasoning_level,
  tool_mode,
  input_modalities
}' ~/.codex/model-catalogs/opencode-go.json

Expected key values:

{
  "slug": "deepseek-v4-flash",
  "display_name": "DeepSeek V4 Flash (OpenCode Go)",
  "context_window": 1000000,
  "max_context_window": 1000000,
  "default_reasoning_level": "high",
  "tool_mode": null,
  "input_modalities": ["text"]
}

The Most Subtle Problem: the Model Catalog Changes the Tool Protocol

The first time I generated the catalog, I inherited OpenAI’s full capability declarations, including:

{
  "tool_mode": "code_mode_only",
  "shell_type": "shell_command",
  "apply_patch_tool_type": "freeform"
}

The catalog parsed fine and codex doctor reported no errors, but real calls failed:

Unsupported custom tool: 'exec'. Only 'apply_patch' is supported.

The reason is that tool_mode = "code_mode_only" isn’t just a UI label. It makes Codex declare the exec custom tool in Responses requests, while the OpenCode Go upstream at the time only accepted custom tools like apply_patch.

Changing the DeepSeek entry’s tool mode to standard:

{
  "tool_mode": null
}

The same native Codex request then succeeded, returning DEEPSEEK_OK.

Why Disabling features.unified_exec Still Failed

During troubleshooting I also tried a command-line override:

codex exec \
  -p deepseek \
  -c features.unified_exec=false \
  -s read-only \
  --ephemeral \
  "Reply exactly DEEPSEEK_OK. Do not use tools."

The request still reported the same Unsupported custom tool: 'exec'. That means the problem wasn’t just a global feature flag; the tool_mode = "code_mode_only" in the model entry still decided the runtime tool protocol.

The effective controlled experiment was: keep everything else the same and only change tool_mode to null in the model catalog. It failed before the change and succeeded after, which makes the causality clear enough.

Prove the Agent Tools Work with Real File Edits

An exact reply only proves the model can generate text. To confirm Codex isn’t “able to chat but not to change code”, I ran a minimal file-writing task in a separate temp directory:

codex exec \
  -p deepseek \
  -C /private/tmp/codex-deepseek-agent-test \
  -s workspace-write \
  --ephemeral \
  --skip-git-repo-check \
  "Use apply_patch to create result.txt containing exactly DEEPSEEK_TOOL_OK followed by a newline. Then stop."

The run info confirmed:

model: deepseek-v4-flash
provider: opencode-go
sandbox: workspace-write
reasoning effort: high

The model then issued an apply_patch, and Codex showed:

apply patch
patch: completed

--- /dev/null
+++ b/result.txt
@@ -0,0 +1 @@
+DEEPSEEK_TOOL_OK

The byte-level check confirmed 17 bytes, with the last byte being 0a:

44 45 45 50 53 45 45 4b 5f 54 4f 4f 4c 5f 4f 4b 0a
D  E  E  P  S  E  E  K  _  T  O  O  L  _  O  K  \n

After the test, I deleted the file and the temp directory, leaving no test artifacts in the business repository.

The takeaways:

  • Supporting the Responses API doesn’t mean supporting every Codex extension tool.
  • The model catalog isn’t display-only data; it can change the request structure.
  • A clean doctor and successful JSON parsing only mean the static config is valid; they don’t replace real requests.
  • After copying metadata from another model, check tools, images, search, and reasoning capabilities item by item.

If the gateway adds native exec support in the future, the tool mode can be revisited; don’t declare capabilities ahead of protocol testing.

Switch Providers Quickly with Profiles

In an interactive Codex session, /model is good for switching the model and reasoning effort within the current provider, but OpenAI and OpenCode Go are two different providers. Changing only the model name could send requests to the wrong service, so use Codex Profiles to override the model, provider, and model catalog together.

Current Codex uses separate Profile files:

$CODEX_HOME/deepseek.config.toml
$CODEX_HOME/openai.config.toml

Don’t keep using the legacy style:

profile = "deepseek"

[profiles.deepseek]
model = "deepseek-v4-flash"

Since Codex 0.134.0, --profile no longer reads from [profiles.<name>] in the main config; it loads <name>.config.toml in the same directory.

DeepSeek Profile, file name ~/.codex/deepseek.config.toml:

model = "deepseek-v4-flash"
model_provider = "opencode-go"
model_context_window = 1000000
model_catalog_json = "/Users/you/.codex/model-catalogs/opencode-go.json"
model_reasoning_effort = "high"
plan_mode_reasoning_effort = "max"

OpenAI Profile, file name ~/.codex/openai.config.toml:

model = "gpt-5.6-luna"
model_provider = "openai"
model_context_window = 272000
model_catalog_json = "/Users/you/.codex/models_cache.json"
model_reasoning_effort = "high"
plan_mode_reasoning_effort = "xhigh"

Replace /Users/you for your own system. Context window and reasoning levels should follow your current model catalog; don’t permanently copy the values in this article.

Switch at startup:

codex -p deepseek
codex -p openai

Non-interactive tasks support the same:

codex exec -p deepseek "检查当前代码"
codex exec -p openai "检查当前代码"

Profiles load when a new session starts. A running session can’t swap its underlying provider losslessly by editing disk config; finish the current task, then start a new session — that’s safer.

Configuration Override Order

A Profile isn’t a fully independent config; it layers on top of the user’s main config. The priority relevant to this article simplifies to:

用户 ~/.codex/config.toml
  < 启动时选择的 Profile
  < 项目 .codex/config.toml
  < CLI 专用参数或 -c/--config 覆盖

This means:

  • deepseek.config.toml doesn’t need to repeat the provider’s Base URL and auth definitions; it inherits them from the main config.
  • If a project pins model_provider, it can override the personal Profile; confirm with /status or the startup info.
  • -c is good for temporary diagnostics; decide whether to persist after verification.

The Boundaries of /model, —model, and —profile

MethodNew sessionBest for
/modelNoSwitching model or reasoning effort within the current provider
codex -m <model>YesOne-off model name override
codex -p <profile>YesSwitching model, provider, catalog, and policy together
codex -c key=valueYesTemporarily checking any config key

Prefer Profiles when crossing providers, because -m won’t automatically pick another set of credentials and Base URL.

If you switch often, add optional aliases to your personal shell config:

alias cdx-ds='codex -p deepseek'
alias cdx-openai='codex -p openai'

Aliases only shorten the startup command; they don’t change Codex config semantics. The desktop model picker and CLI Profiles are also not the same capability; this article verified the local Codex CLI.

Verification Can’t Stop at One Layer

Final verification ran at five layers. Each layer rules out different problems, and none can replace another.

Layer 1: Raw Responses Request

Confirm the OpenCode Go endpoint accepts deepseek-v4-flash and returns completed. This layer rules out URL, authentication, model name, and basic protocol issues.

Layer 2: Model Catalog Parsing

codex debug models

Output should include:

deepseek-v4-flash
DeepSeek V4 Flash (OpenCode Go)
context_window: 1000000
default_reasoning_level: high
tool_mode: null

The current codex debug models doesn’t accept --profile; Profiles only apply to runtime commands and some subcommands. To check whether a Profile actually took effect, look at codex exec startup info or run a minimal request.

During troubleshooting I ran:

codex -p deepseek debug models | jq ...

Codex clearly reported --profile only applies to runtime commands, but because the shell returns the last command in the pipeline (jq)‘s exit code by default, the whole line looked like exit=0. Automation scripts should enable pipefail, or a failed first half can be mistaken for success:

set -o pipefail

Layer 3: Codex Health Check

codex doctor --summary --no-color

This run’s result:

17 ok · 1 idle · 1 notes · 0 warn · 0 fail

It confirms the config loads, the provider doesn’t require OpenAI auth, and the target HTTP endpoint is reachable — but it still can’t detect a tool protocol mismatch.

Layer 4: Real Requests with Both Profiles

Run minimal end-to-end tests with a read-only sandbox and an ephemeral session:

codex exec -p deepseek \
  -s read-only \
  --ephemeral \
  "Reply exactly DEEPSEEK_OK. Do not use tools."

codex exec -p openai \
  -s read-only \
  --ephemeral \
  "Reply exactly OPENAI_OK. Do not use tools."

They respectively returned:

DEEPSEEK_OK
OPENAI_OK

Startup info should also show:

model: deepseek-v4-flash
provider: opencode-go

and:

model: gpt-5.6-luna
provider: openai

This step verifies Profile override order, authentication, model catalog, provider routing, and the Responses request at once.

Layer 5: Agent File Tools

Using the workspace-write sandbox, run a real apply_patch in an isolated directory, then check the file length and the final newline byte. This doesn’t verify text generation; it verifies that:

  • The model can pick the tool Codex provides.
  • OpenCode Go accepts that tool declaration.
  • Codex can execute and return the patch result.
  • The target file content meets the exact requirement.

Only when layer 5 passes can the chain be said to have minimal coding-agent capability. More complex shells, parallel tools, MCP, images, and Web Search still need separate verification; don’t extrapolate all capabilities from a single apply_patch.

Common Mistakes

Treating Model Switching as Provider Switching

/model and --model mostly override the model name. When switching across services, you must also switch model_provider, the auth method, and the model catalog. Profiles are a more reliable atomic configuration unit.

Writing the API Key Directly into config.toml

This increases the exposure surface in backups, screenshots, logs, and accidental commits. Prefer bearer_token_env_var or the provider’s runtime auth command, and tighten credential file permissions.

Only Looking at doctor Without Sending a Real Request

A health check finds config parsing and connectivity issues, but it may not trigger the model gateway’s full validation of the tool schema. Run at least one real read-only, ephemeral session.

Blindly Copying Official Model Metadata

Context window, tool mode, image input, Web Search, and reasoning levels can all affect runtime behavior. Copying is only a starting point for generating a schema, not proof of fully equivalent capabilities.

Keeping an Extra Proxy for a Protocol That’s Already Supported

If the target endpoint already supports the Responses API directly, an extra proxy only adds layers of logs, credentials, retries, and fault localization. Validate the direct connection first, then decide whether a translation layer is truly needed.

Troubleshooting Matrix

When something goes wrong, locate the error by layer first; don’t change the URL, key, model catalog, and Profile all at once.

Step-by-Step Reproduction Checklist

To set up another dev machine from scratch, follow this order.

1. Confirm Version and Credentials

codex --version
jq -e \
  '.["opencode-go"].key | type == "string" and length > 0' \
  ~/.local/share/opencode/auth.json >/dev/null

2. Back Up the Configuration

cp ~/.codex/config.toml ~/.codex/config.toml.before-opencode-go

3. Validate /responses with a Raw Request

Send only a short text without tools. Confirm the HTTP status, status, model, and output_text.

4. Add the Provider and Runtime Authentication

Configure only model_provider, base_url, wire_api, and auth first, keeping variables minimal.

5. Make the First Codex Request with Fallback Metadata

If the request succeeds with a model metadata warning, the runtime chain works; handle the catalog separately.

6. Generate a Local Catalog from the Current Model Cache

Clone a complete record, narrow context, input modalities, search, and tool capabilities, and make sure tool_mode = null.

7. Create Two Profiles

The DeepSeek Profile points to OpenCode Go; the OpenAI Profile points to OpenAI and the native model cache.

8. Run Static and Real Verification in Order

codex debug models
codex doctor --summary --no-color
codex exec -p deepseek -s read-only --ephemeral "Reply exactly DEEPSEEK_OK."
codex exec -p openai -s read-only --ephemeral "Reply exactly OPENAI_OK."

9. Verify apply_patch in an Isolated Directory

Don’t put the first tool test directly into an important repository. Verify the file content, then clean up the temp directory.

10. Record Versions and Keep a Rollback Point

Codex, gateways, and model capabilities all change. Write the test date, Codex version, model slug, and verified tools into documentation; re-run the same checks after upgrading.

Current Boundaries: Verified vs. Not Yet Extrapolated

As of 2026-08-06, this setup has been verified with real tests:

  • Non-streaming minimal requests against OpenCode Go /v1/responses.
  • Native Codex Responses calls.
  • Exact text responses at the high reasoning level.
  • Both DeepSeek and OpenAI CLI Profiles.
  • DeepSeek selecting and executing apply_patch.
  • Codex health check, model catalog parsing, and provider connectivity.

This article does not treat the following as proven:

  • Extreme 1,000,000-token inputs and automatic compression boundaries.
  • Image input, original image detail, and multimodal output.
  • Extension tools such as Web Search, MCP, Browser, and Computer Use.
  • The exec custom tool and the unified PTY execution protocol.
  • Long SSE interruption recovery, parallel tool calls, and rate-limit backoff.
  • Custom provider switching in Codex desktop or cloud sessions.

These boundary statements aren’t conservative wording; they prevent “the API can return a sentence” from being written as “all Codex capabilities are equivalent to the OpenAI Provider”.

How to Roll Back

To fully restore the previous Codex default config:

cp ~/.codex/config.toml.before-opencode-go ~/.codex/config.toml

Profile files are an independent override layer and don’t affect the backup. When no longer needed, move them out of ~/.codex first, confirm Codex starts normally, then delete them.

Conclusion

The hard part of this integration wasn’t changing model to deepseek-v4-flash; it was pinning down the capability boundaries of the whole chain:

  1. DeepSeek and the OpenCode Go endpoint genuinely accept the Responses API.
  2. The Codex provider uses runtime authentication instead of copying plaintext credentials.
  3. The custom model catalog completes the context window and reasoning levels.
  4. tool_mode must match the custom tool protocol the gateway supports.
  5. Profiles switch the model, provider, and catalog together.
  6. The raw API, static diagnostics, and native Codex requests must each be verified.
  7. Only after a real apply_patch succeeds is the minimal coding-agent chain proven.

The biggest lesson isn’t a particular TOML block; it’s the troubleshooting order: validate the minimal protocol first, then integrate Codex; prove the main chain with fallback metadata first, then add the model catalog; after static checks, always run a real tool task. That way each step has only one major variable, and failures can be traced back to the right layer quickly.
