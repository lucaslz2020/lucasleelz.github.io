Upgrading Spring Boot 3.5.13 to 4.1: What's Already Done vs. What's Really at Risk

Spring Boot 3.5.13 to 4.1: dependency boundaries, upgrade order, and acceptance checklist — JDK 25, Nacos 3.1.2, and standard data access as the baseline.

lucaslzAuthor
August 2, 2026 9 min read
#Java #Spring Boot #Spring Cloud #Nacos #Kubernetes
{ }

Spring Boot 4.1 is not an ordinary dependency upgrade. It builds on Spring Framework 7, Jakarta EE 11, and Servlet 6.1, and the surrounding ecosystem moves with it: Spring Cloud, Nacos Client, web containers, JSON, data access, and in-house starters all jump to new major versions at the same time.

The most common mistake in an upgrade assessment is re-listing already-solved problems as risks. This article documents the assessment approach used before an actual upgrade: the starting point is already Spring Boot 3.5.13, JDK 25, Nacos Server 3.1.2, and the legacy custom query extension has already been removed. The assessment therefore focuses not on historical compatibility with Boot 3.1 or Nacos 2, but on the actual breaking points between 3.5 and 4.1.

The previous article, Upgrading Spring Boot from 3.1.7 to 3.5.13, already covered compilation, Pod startup, complete Actuator health checks, and middleware verification. This article focuses only on the compatibility risks introduced by Boot 4, so it doesn’t repeat the same generic checklist.

This article discusses the upgrade path and verification boundaries — it doesn’t mean you can simply bump the version to 4.1 and go live.

Anonymization note: this article contains no project names, service names, repository paths, domains, cluster information, namespaces, Data IDs, accounts, or real business data; all configuration snippets are placeholder examples.

Pin Down the Baseline First

Record the current state in the change ticket first, so later discussions don’t end up referencing outdated information:

ItemCurrent stateNeeds handling this time
Spring Boot3.5.13Upgrade to 4.1
JDK25Keep, no rollback
Nacos Server3.1.2Keep, no database migration, no config rebuild
Legacy custom query extensionRemovedNo need to port it
Complex queriesAlready moved to explicit SQLKeep the Repository boundary and re-verify results via regression

The fact that Nacos Server has been upgraded to 3.1.2 only means the server, database, and configuration data can keep being used; it cannot automatically prove that a Spring Cloud Alibaba Client is compatible with Spring Boot 4.1. Server and Client are two independent compatibility chains.

First Hard Boundary: Spring Cloud Alibaba Support for 4.1

Spring Cloud officially states that 2025.1.2 supports Spring Boot 4.1.x. The Spring Cloud target version for Boot 4.1 should therefore be:

<spring-cloud.version>2025.1.2</spring-cloud.version>

But Spring Cloud Alibaba’s official compatibility table currently reads:

Spring Cloud Alibaba 2025.1.0.0
Spring Cloud 2025.1.0
Spring Boot 4.0.0

and describes that branch as targeting Spring Boot 4.0.x. 4.0.x is not a blanket term for 4.1.x, so you can’t use it to claim that 2025.1.0.0 officially supports Boot 4.1.

That doesn’t mean the combination won’t run; it means you need to distinguish two kinds of conclusions:

  • Official support: the compatibility matrix explicitly lists the matching versions.
  • Verified usable locally: a project-level conclusion reached through dependency convergence, startup, registration, configuration loading, and business regression.

If you want to move straight to Boot 4.1 before Alibaba ships explicit support, treat the combination below as a verification target, not a default production commitment:

Spring Boot 4.1.x
Spring Cloud 2025.1.2
Spring Cloud Alibaba 2025.1.x
Nacos Server 3.1.2

Official references: Spring Cloud version compatibility, Spring Cloud Alibaba 2025.x release notes.

Nacos Data Stays, but the Config Loading Approach Must Migrate

Spring Cloud Alibaba 2025.x no longer supports Spring Cloud Bootstrap. If the application still depends on:

bootstrap.yml
spring.cloud.bootstrap.enabled

migrate to the Spring Boot Config Data approach, for example:

spring:
  config:
    import:
      - optional:nacos:<data-id>?group=<group>

Whether to split Data IDs, plus details like Group, Namespace, username, and address, should follow the target environment’s definitions and never appear in public documentation. What changes is how the application reads configuration at startup, not the format of the data stored in Nacos.

Once the migration is complete, two things must be verified:

  1. Required configuration loads at startup, such as Feign URLs, data sources, Redis, and message queue addresses.
  2. Runtime configuration refresh, service registration, and instance discovery still work.

Main Changes Introduced by Boot 4 Itself

1. Undertow Can No Longer Be an Embedded Container

Boot 4’s Servlet 6.1 baseline is incompatible with Undertow, and the official Undertow starter and embedded Undertow support have been removed. If the final dependency tree uses Undertow, switch to Tomcat 11 or Jetty 12 and remove server.undertow.* configuration.

Don’t assume from a single shared configuration that every service needs a container change; check each service’s final dependency tree and actual startup logs first.

2. Boot Modules and Starters Have Been Split into Finer Pieces

Boot 4 splits many large jars into finer-grained modules. In-house starters, modules that directly depend on Boot internal classes, and hand-written auto-configuration are especially likely to surface problems at compile time.

In the first round, use spring-boot-starter-classic and spring-boot-starter-test-classic to get a classpath close to Boot 3 and restore compilation, startup, and tests; once things are stable, swap in more precise starters based on actual needs. Don’t let a single in-house starter claim binary compatibility with both Boot 3 and Boot 4; give it a separate Boot 4 version line.

3. Jackson 3 Is the Way Forward, but Don’t Bundle It into This Upgrade

Boot 4 leans toward Jackson 3 by default, and Jackson 3 changes its coordinates and some package names. For systems with a lot of ObjectMapper usage, message serialization, date formatting, and import/export logic, keep Jackson 2-compatible behavior in the first round:

spring:
  jackson:
    use-jackson2-defaults: true

Use Boot’s provided temporary Jackson 2 modules when necessary. Only after HTTP responses, Kafka/Rabbit messages, and exported files all pass regression should Jackson 3 migration be planned separately. Otherwise, a single anomaly is hard to attribute to Boot, Jackson, or business serialization.

4. Data Access Components Must Be Re-verified Against Boot 4

The removed legacy query extension is no longer a risk, but the following components still need version confirmation:

  • Hibernate 7: entity mapping, dialect, JPA Criteria, native SQL, JSON, and date fields.
  • Dynamic data source: dynamic-datasource-spring-boot3-starter cannot simply be assumed compatible with Boot 4.
  • MyBatis-Plus: pagination, interceptors, multi-data-source transactions, and SQL logging.
  • Redis, Kafka, Rabbit: clients, serialization, listeners, retries, and message headers.

Each item must be confirmed by upgrading the dependency and running tests — not just by Maven being able to download the jar.

5. Security, Testing, and Operations Get Upgraded Too

Boot 4 also brings major version upgrades such as Spring Security 7, Spring Kafka 4, Spring AMQP 4, and Spring Batch 6. Key verification points:

  • Login, tokens, authorization annotations, and Feign call identity.
  • Message consumption, deserialization, retries, and idempotency.
  • Web tests under @SpringBootTest; explicitly add @AutoConfigureMockMvc when needed.
  • Actuator health checks. Boot 4 enables the liveness/readiness groups by default; Kubernetes probes, Prometheus scraping, and graceful shutdown must all be rechecked.

Implementation Order on the 3.5 Acceptance Baseline

建立 4.1-SNAPSHOT 分支
        ↓
确认 Cloud / Alibaba Client 精确版本
        ↓
迁 Nacos Config Data，处理父工程自研 starter
        ↓
父工程全量编译与测试
        ↓
升级一个试点服务并在本地连接 Nacos 3.1.2
        ↓
test Kubernetes 发布与业务回归
        ↓
逐服务推广

Start with a pilot service that has clear business boundaries and fairly complete tests, rather than upgrading all services at once. Use a separate Maven version for the parent project, such as 4.1-SNAPSHOT, so the still-running 3.5.13-SNAPSHOT is not overwritten.

Incremental Acceptance Checklist for the Boot 4 Pilot

The list below only includes checks that are new compared with the previous article. General acceptance items such as target JDK compilation, Pod startup, full /actuator/health, and database and message middleware connectivity still apply but are not repeated here.

Startup and Infrastructure

  • Spring Cloud already uses 2025.1.2+, which supports Boot 4.1, and the dependency tree contains no old Release Train.
  • The exact Spring Cloud Alibaba Client version is backed by a compatibility matrix or pilot verification; the Nacos Server version alone is no substitute for that evidence.
  • Nacos configuration has been migrated to Config Data, and the startup chain no longer depends on Spring Cloud Bootstrap.
  • The actual web container is Tomcat 11 or Jetty 12, with no leftover Undertow in the dependency tree or configuration.
  • spring-boot-starter-classic is only a stopgap; remove it once the starter split and property migration are complete.

Business and Data

  • Hibernate 7, MyBatis-Plus, and the dynamic data source each complete pagination, transaction, native SQL, and multi-data-source regression.
  • Spring Batch 6 job registration, metadata tables, restarts, and partitioned execution semantics pass verification.
  • Spring Kafka 4 and Spring AMQP 4 message headers, serialization, retry, dead-letter, and idempotency behavior remain unchanged.
  • Choose exactly one — Jackson 3 or the temporary Jackson 2 compatibility path — as the production baseline, and complete HTTP, message, and import/export regression.

API Contracts

  • Core frontend page requests and error messages.
  • Dates, amounts, enums, null fields, pagination structure.
  • Deserialization compatibility for HTTP APIs and message JSON.

Conclusion

In moving from Spring Boot 3.5.13 to 4.1, Nacos 3.1.2 and the removed legacy query extension are no longer blockers. What needs priority confirmation is whether the Spring Cloud Alibaba Client explicitly supports Boot 4.1; then proceed in order through Nacos config loading, Boot modularization and web containers, data access, Jackson, and in-house starters.

Build evidence that the upgrade works in local and test environments first; only then make it the production standard. That’s how you keep a cross-major-version upgrade like this under control. Boot’s official migration guide can serve as an item-by-item checklist: Spring Boot 4.0 Migration Guide.
