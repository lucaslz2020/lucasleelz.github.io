JDK 17 Services from 3–4G to Controllable: Practical Spring Boot Container Memory Tuning

A four-layer breakdown of Spring Boot memory usage across Kubernetes, cgroup, JVM Heap, and Native Memory, with step-by-step tuning of G1, heap ceilings, Metaspace, threads, message prefetch, glibc arenas, JProfiler, and probes.

July 25, 2026 Updated August 6, 2026 17 min read
#Java #JDK 17 #G1 #Kubernetes #Spring Boot
{ }

This article draws on container memory tuning work for a batch of JDK 17 services. Service names, clusters, nodes, and business data have all been generalized; the example parameters are a starting point for investigation, not a one-size-fits-all answer.

For a while, our approach to Java service memory was crude: when a container kept restarting, we raised -Xmx and the Kubernetes memory limit together. The result was that ordinary Spring Boot services steadily used 3–4 GiB, heavy services got close to 5 GiB, and a few instances were still killed in the end.

When we actually investigated, we found these symptoms fell into at least two completely different categories:

  • One instance ran with -Xmx4g and used about 3.5 GiB of heap. After a heap inspection, live objects dropped to about 1.9 GiB, but RSS did not fall right away.
  • Another instance used only about 280 MiB of heap, yet its Java process RSS exceeded 1.2 GiB, with more than two hundred threads and a resident native profiler.

The former is mostly heap and allocation pressure; the latter is mostly non-heap memory, threads, and native memory. Looking only at kubectl top, both would be misread as “Java heap too big.”

Step 0: Confirm what you’re comparing and the evidence window

If the question is “why do two Pods of the same service differ in memory by several times,” the first step is not to dig into the JVM but to confirm whether they really come from the same deployment template.

kubectl -n <namespace> get pod <pod-a> \
  -o jsonpath='{.metadata.ownerReferences[0].name}{"\n"}'

kubectl -n <namespace> get pod <pod-b> \
  -o jsonpath='{.metadata.ownerReferences[0].name}{"\n"}'

kubectl -n <namespace> get rs <replicaset> -o yaml

An identical ReplicaSet hash in the Pod names usually means they share the same PodTemplateSpec, including:

  • Image and startup command.
  • JVM arguments and environment variables.
  • ConfigMap, Secret, and mounts.
  • requests, limits, probes, and scheduling rules.

If they belong to the same ReplicaSet, “the two Pods have different JVM arguments” should no longer be the primary hypothesis. Focus instead on traffic, caching, batch processing, connection pools, thread counts, and native allocations.

Also check whether historical evidence is still available. Old Pods, old ReplicaSets, and previous logs may already have been cleaned up by rolling releases, and the Prometheus retention window may be shorter than the time a Pod has been offline. Query the target time window first:

max by (pod) (
  max_over_time(
    container_memory_working_set_bytes{
      namespace="<namespace>",
      pod=~"<application>-<revision>-.+",
      container!="",
      image!=""
    }[24h]
  )
)

If no metrics or logs exist for the target window, record that explicitly:

可以排除模板差异，但现有证据不足以证明旧 Pod 的具体根因。

Don’t use a snapshot of a new Pod to invent a conclusion about the old one. The right move is to put NMT, GC logging, and monitoring in place so the next occurrence can be captured, not to declare a “memory leak” outright.

Build the right memory model first

flowchart TD
  A["Pod memory working set"] --> B["Java Heap"]
  A --> C["Metaspace and Class Space"]
  A --> D["Thread stacks"]
  A --> E["Direct / Mapped Buffer"]
  A --> F["JIT Code Cache and GC structures"]
  A --> G["JNI, Profiler, glibc arena"]
  A --> H["Shared libraries and partial file pages"]

-Xmx only limits the Java Heap. This equation usually does not hold:

容器内存 = Xmx

A more accurate relationship is:

容器内存 ≈ Heap committed + JVM native + 线程栈 + 第三方 native + 工作集中的文件页

So leave an explicit margin between the container limit and -Xmx.

Step 1: Confirm whether it’s actually OOM

Check the exit reason first. Don’t raise the heap the moment you see a Restart:

kubectl -n <namespace> get pod <pod> \
  -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason}{"\n"}{.status.containerStatuses[0].lastState.terminated.exitCode}{"\n"}'

kubectl -n <namespace> describe pod <pod>
kubectl -n <namespace> logs <pod> --previous --tail=300

Common cases:

EvidenceMore likely cause
OOMKilled, Exit Code 137Container exceeded the cgroup limit, or the node was under memory pressure
OutOfMemoryError: Java heap space in Java logsJava Heap is insufficient, or objects cannot be released
MetaspaceClass loading, dynamic proxies, or a Metaspace ceiling problem
Exit Code 143Usually a SIGTERM, not OOM
Restart after consecutive probe failuresThe app is blocked, a dependency timed out, or GC pauses were amplified by probes

The kernel OOM killer can strike too quickly for the JVM to get a chance to produce a Heap Dump, so its absence does not rule out a memory problem.

Step 2: Measure the Pod, the process, and the JVM at the same time

Kubernetes side:

kubectl top pod -n <namespace> <pod> --containers

kubectl -n <namespace> get pod <pod> \
  -o jsonpath='{.spec.containers[0].resources}{"\n"}'

Container side:

kubectl -n <namespace> exec <pod> -- sh -c '
  grep -E "VmRSS|VmSize|Threads" /proc/1/status
  test -f /sys/fs/cgroup/memory.current && cat /sys/fs/cgroup/memory.current
  test -f /sys/fs/cgroup/memory.stat && \
    grep -E "^(anon|file|kernel|sock) " /sys/fs/cgroup/memory.stat
'

JVM side:

kubectl -n <namespace> exec <pod> -- jcmd 1 VM.version
kubectl -n <namespace> exec <pod> -- jcmd 1 VM.command_line
kubectl -n <namespace> exec <pod> -- jcmd 1 VM.flags
kubectl -n <namespace> exec <pod> -- jcmd 1 GC.heap_info

Record the sampling time. Data from one minute after startup, a business peak, and an hour of idle time cannot be compared directly.

Step 3: Break down JVM native memory with NMT

Add it at startup:

-XX:NativeMemoryTracking=summary

Note that it must come before -jar:

java \
  -XX:NativeMemoryTracking=summary \
  -jar /app/application.jar

This form will not take effect, because the argument becomes an application argument:

java -jar /app/application.jar -XX:NativeMemoryTracking=summary

After startup, establish a baseline and compare:

jcmd 1 VM.native_memory summary scale=MB
jcmd 1 VM.native_memory baseline

# 运行一段代表性业务流量后
jcmd 1 VM.native_memory summary.diff scale=MB

Watch in particular:

  • Java Heap
  • Class
  • Thread
  • Code
  • GC
  • Compiler
  • Internal

NMT is disabled by default, and both summary and detail modes add overhead; Oracle’s documentation puts the overhead at roughly 5%–10%. NMT also cannot account for every third-party native allocation, so a total below RSS is not surprising. Native Memory Tracking

Step 4: Drop the “Xmx equals the container limit” configuration

The most dangerous setup looks like this:

容器 limit: 4Gi
-Xmx4g

Once the heap approaches 4 GiB, Metaspace, thread stacks, Direct Buffers, GC data structures, and native libraries have no room left. You are more likely to end up with a cgroup OOMKill than an analyzable Java heap OOM.

This round of tuning moved ordinary JDK 17 services to a heap ceiling calculated from container memory:

-Xms768m
-XX:MaxRAMPercentage=65.0
-XX:+UseG1GC

For example, with a 3 GiB container limit, the maximum heap target is about 1.95 GiB, leaving about 1.05 GiB for non-heap and native memory. 65% is only a starting point validated against the current services; services with many threads, heavy Netty Direct Buffers, or heavy native dependencies should lower it further.

Don’t configure two competing ceilings at the same time:

-Xmx2g
-XX:MaxRAMPercentage=65.0

When an explicit -Xmx is present, the percentage is no longer the primary control you might assume it is. Verify the final arguments with jcmd 1 VM.flags instead of just reading the YAML.

JDK 17 provides container awareness and percentage-based heap parameters; you can verify their exact meaning in the JDK 17 java command documentation.

Step 5: Keep G1, but don’t use Full GC to make the dashboards look better

JDK 17 services keep using G1:

-XX:+UseG1GC

In one live investigation, heap usage dropped from about 3.5 GiB to about 1.9 GiB, but RSS did not follow right away. That tells us:

  1. Live objects really did decrease.
  2. The JVM or the allocator may still retain committed memory pages.
  3. “Heap used dropped after GC” and “the container returned the same RSS immediately” are not the same thing.

Why two Pods from the same ReplicaSet used 1.8G vs 1.2G

In another investigation, two replicas came from the same ReplicaSet with identical images, JVM arguments, configuration, and limits:

MetricPod APod B
Pod working setabout 1.86 GiBabout 1.24 GiB
G1 committed Heapabout 1.5 GiBabout 768 MiB
Heap used at the timeabout 514 MiBabout 212 MiB
Restarts / OOM00

GC logs showed that Pod A went through a period of heavier allocation during a business peak, so G1 expanded its committed heap. Subsequent mixed GCs gradually brought live objects down to about 442 MiB; with continued idle time, the Old region shrank further and the heap contracted back toward Xms=768M. Container memory eventually fell back to about 1.27 GiB.

In the live environment, we did not see:

  • OOMKilled.
  • Full GC storms.
  • Humongous Regions growing continuously.
  • An increase in restarts.
  • The Old region only ever growing.

So this evidence fits “a short allocation burst raised the committed heap, and G1 shrank it back slowly” better than a memory leak.

The right way to collect data within the same window:

kubectl top pod <pod-a> <pod-b> -n <namespace>

kubectl exec -n <namespace> <pod-a> -- jcmd 1 GC.heap_info
kubectl exec -n <namespace> <pod-b> -- jcmd 1 GC.heap_info

kubectl exec -n <namespace> <pod-a> -- \
  jcmd 1 VM.native_memory summary scale=MB
kubectl exec -n <namespace> <pod-b> -- \
  jcmd 1 VM.native_memory summary scale=MB

Also align GC logs from the same moment. Comparing two kubectl top numbers alone cannot tell you whether the difference comes from live objects, committed heap, or native memory.

Don’t schedule System.gc() just to push the curves down, and don’t apply a very short G1PeriodicGCInterval globally to every service. Periodic GC burns CPU and masks real allocation problems; it is worth evaluating per service only after you have explicitly verified that the application has long idle windows.

If the latest Deployment in Git already removed periodic GC, but a running jcmd 1 VM.flags still shows it, the live Pod still comes from an old spec. kubectl rollout restart rebuilds from the current cluster spec; it does not read Git automatically. You must render the template and roll it out first.

Oracle’s primary advice for G1 is still to stick with the default policy as much as possible, set only an appropriate maximum heap, and tune based on GC logs. Garbage-First Garbage Collector Tuning

Step 6: Cap Metaspace, but don’t squeeze it arbitrarily low

The current template’s starting point:

-XX:MetaspaceSize=256m
-XX:MaxMetaspaceSize=512m

This keeps runaway class loading from crowding out container memory without bound, but a MaxMetaspaceSize that is too small will directly produce:

java.lang.OutOfMemoryError: Metaspace

Compare before and after the change:

jcmd 1 VM.native_memory summary scale=MB
jcmd 1 GC.class_histogram

If the class count keeps growing, look first at dynamic proxies, script engines, hot-reload ClassLoaders, and repeatedly generated classes; don’t just keep raising the ceiling.

Step 7: Turn off the resident profiler

Diagnostic tools consume memory themselves. The old template loaded the JProfiler native agent by default, so even when nobody was connected, the agent, sampling structures, and extra events stayed resident in the process.

Disable it by default:

env:
  - name: JPROFILER_ENABLED
    value: "false"

The startup script only adds it during investigations:

set -- java

if [ "${JPROFILER_ENABLED:-false}" = "true" ]; then
  set -- "$@" \
    -agentpath:/opt/jprofiler/bin/linux-x64/libjprofilerti.so=port=8849,nowait
fi

After the investigation, set the switch back to false and roll it out. A profiler should be a short-lived diagnostic capability, not a default component of every production Pod.

Step 8: Handle thread stacks and message backlog

In one live investigation, a lightweight service showed heap usage of about 280 MiB, RSS of about 1.2 GiB, and more than 200 threads. At that point, shrinking the heap further has limited payoff, so check where the threads come from first:

jcmd 1 Thread.print > /tmp/threads.txt
grep '^"' /tmp/threads.txt | wc -l

Take stock of:

  • Web container worker threads.
  • Database connection pool maintenance threads.
  • Kafka, RabbitMQ, and Nacos client threads.
  • XXL-JOB, scheduled tasks, and self-built thread pools.
  • ForkJoinPool and async executors.

Don’t set a very small -Xss globally up front. Deep call chains, complex expressions, or large stack frames can then trigger StackOverflowError. A safer order is:

  1. Remove duplicate thread pools.
  2. Cap thread pool max sizes based on container CPU.
  3. Rein in message consumption concurrency and prefetch.
  4. Load-test -Xss last.

Message consumers can start from a conservative configuration:

env:
  - name: SPRING_RABBITMQ_LISTENER_SIMPLE_CONCURRENCY
    value: "1"
  - name: SPRING_RABBITMQ_LISTENER_SIMPLE_MAX_CONCURRENCY
    value: "3"
  - name: SPRING_RABBITMQ_LISTENER_SIMPLE_PREFETCH
    value: "10"

This is not just about saving threads. When prefetch is too large, many unacknowledged messages and their business objects sit in the heap at the same time. After changing it, verify consumption latency and backlog; don’t just watch memory drop.

Step 9: Limit glibc arenas

On Linux with glibc, multi-threaded native allocation can produce multiple malloc arenas. After business objects are released, idle arenas do not necessarily return to the operating system right away, which shows up as lower heap usage with RSS still high.

The conservative starting point currently in use:

env:
  - name: MALLOC_ARENA_MAX
    value: "4"

It is not a JVM parameter, and it is not guaranteed to work with Alpine/musl or other allocators. A value that is too small can increase lock contention for multi-threaded allocation, so also watch:

  • CPU usage.
  • Request P95/P99.
  • Native allocation hotspots.
  • Whether RSS actually improves.

Step 10: Make the next OOM leave evidence

Keep these:

-XX:+HeapDumpOnOutOfMemoryError
-XX:+ExitOnOutOfMemoryError
-XX:HeapDumpPath=/data/dumps/<app>/<pod>/heap.hprof
-Xlog:gc*,safepoint:file=/data/logs/gc-%t.log:time,uptime,level,tags:filecount=10,filesize=20M

The Heap Dump path must:

  • Be writable.
  • Have enough space.
  • Be unique per Pod, so replicas don’t overwrite each other.
  • Have a cleanup and download process, so the shared volume doesn’t fill up.

GC logs answer “when collection happened, how much before and after, and how long the pauses lasted”; the Heap Dump answers “which objects occupy the heap.” Neither can replace the other.

Step 11: Calculate Kubernetes resources and JVM arguments together

An example starting point for an ordinary service:

resources:
  requests:
    cpu: 250m
    memory: 1536Mi
  limits:
    memory: 3Gi

Paired with:

-Xms768m
-XX:MaxRAMPercentage=65.0

Answer three questions when calculating:

  1. What is the steady-state P95 memory, and can the request cover normal operation?
  2. What are the startup and batch peaks, and does the limit leave a safety margin?
  3. Beyond the maximum heap, how much do Thread, Class, Code, GC, Direct, and native need in total?

Heavy services cannot simply reuse an ordinary service’s request/limit. Build a separate baseline for them, and account for node capacity while old and new Pods coexist during a rolling release.

Step 12: Don’t let probes turn short congestion into a restart storm

When memory or dependency pressure rises, the health endpoint can slow down too. If liveness only allows a few dozen seconds, Kubernetes keeps restarting the application exactly when it is busiest, creating:

启动分配高峰 → 探针超时 → 重启 → 再次启动分配高峰

A good starting point is this split of responsibilities:

startupProbe:
  httpGet:
    path: /actuator/health/liveness
    port: http
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 30

readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: http
  periodSeconds: 5
  timeoutSeconds: 3
  failureThreshold: 2

livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: http
  periodSeconds: 10
  timeoutSeconds: 5
  failureThreshold: 12
  • startup gives slow starts enough of a window.
  • readiness pulls traffic away quickly first.
  • liveness handles only process states that genuinely cannot recover.

Relaxing probes does not fix a memory leak, but it prevents a brief GC pause, a database hiccup, or a dependency timeout from being amplified into cluster-wide restarts.

A reusable JDK 17 startup baseline

#!/bin/sh
set -eu

DUMP_DIR="/data/dumps/${APP_NAME}/${HOSTNAME}"
mkdir -p "$DUMP_DIR" /data/logs

set -- java \
  -XX:+UseContainerSupport \
  -Xms768m \
  -XX:MaxRAMPercentage=65.0 \
  -XX:+UseG1GC \
  -XX:MetaspaceSize=256m \
  -XX:MaxMetaspaceSize=512m \
  -XX:+HeapDumpOnOutOfMemoryError \
  -XX:+ExitOnOutOfMemoryError \
  -XX:HeapDumpPath="$DUMP_DIR/heap.hprof" \
  -Xlog:gc*,safepoint:file=/data/logs/gc-%t.log:time,uptime,level,tags:filecount=10,filesize=20M

if [ "${NMT_ENABLED:-false}" = "true" ]; then
  set -- "$@" -XX:NativeMemoryTracking=summary
fi

if [ "${JPROFILER_ENABLED:-false}" = "true" ]; then
  set -- "$@" \
    -agentpath:/opt/jprofiler/bin/linux-x64/libjprofilerti.so=port=8849,nowait
fi

set -- "$@" -jar /app/application.jar
exec "$@"

After going live, verify the actual command line:

jcmd 1 VM.command_line
jcmd 1 VM.flags
jcmd 1 GC.heap_info

Recommended phased rollout order

Don’t change a dozen parameters at once, or you won’t know which one helped when memory drops.

Stage A: Add observability only

  • Record Pod working set, RSS, heap, and thread count.
  • Add rotating GC logs.
  • Enable NMT briefly on one replica.

Stage B: Remove resident diagnostic overhead

  • Turn off JProfiler by default.
  • Pilot MALLOC_ARENA_MAX=4 on glibc images.
  • Compare CPU and latency to confirm there is no obvious regression.

Stage C: Recalculate the heap and the container margin

  • Move from a fixed -Xmx4g to a calculated percentage or a smaller explicit -Xmx.
  • Keep at least 30%–35% for non-heap and native memory.
  • Maintain two baselines: ordinary services and heavy services.

Stage D: Govern threads and in-flight messages

  • Consolidate thread pools.
  • Lower message concurrency and prefetch.
  • Verify backlog, throughput, and business latency.

Stage E: Calibrate resources and probes

  • Adjust request/limit against steady state and peaks.
  • Make sure nodes can host extra replicas during rolling releases.
  • readiness pulls traffic quickly; liveness avoids killing healthy instances.

Only draw conclusions after the service has passed at least one real business peak. Dropping memory from 4 GiB to 1.5 GiB is not a successful optimization if the cost is frequent Full GCs or message backlog.

Final takeaways

What actually worked in this round of JDK 17 tuning was not any single “magic parameter” — it was tightening all of these boundaries at once:

  1. The heap no longer fills the container; native memory gets explicit room.
  2. Keep G1 simple: fix object allocation first instead of forcing periodic GC.
  3. JProfiler is enabled on demand.
  4. Use NMT, RSS, and cgroup data to tell Heap apart from Native.
  5. Rein in threads, message concurrency, and prefetch.
  6. Limit glibc arenas and validate the side effects with latency and CPU.
  7. Keep GC logs, Heap Dump, and exit reasons so the next incident can be reviewed.
  8. Use sensible probes so short congestion doesn’t become a restart storm.

Moving from “give every service 4G” to “an explainable memory budget for each service type” was the most important result of this optimization.
