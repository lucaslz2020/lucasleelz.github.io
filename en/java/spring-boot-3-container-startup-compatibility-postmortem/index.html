Spring Boot 3 Container Startup Postmortem: Directories, Deprecated Properties, Logging, Drivers

From UnsatisfiedDependencyException to mkdir failed: Nacos cache dir, server.use-forward-headers, commons-logging, nacos-logback.xml, empty Class.forName.

lucaslzAuthor
August 8, 2026 10 min read
#Spring Boot #Java #Nacos #Kubernetes #Postmortem
{ }

This post is based on a rolling release of a Spring Boot 3 service. Class names, service names, paths, and business configuration have been generalized. Series navigation: Kubernetes Rebuild Migration Series.

After the unified Deployment was rolled out, five types of messages appeared in the startup logs at once:

UnsatisfiedDependencyException ... Factory method threw: mkdir failed

failed to create cache dir: /root/nacos/naming/.../failover

server.use-forward-headers is no longer supported

please remove commons-logging.jar from classpath

Could not initialize Logback Nacos logging from classpath:nacos-logback.xml

java.lang.ClassNotFoundException:
  at java.lang.Class.forName(...)

Attributing all of them to “the Deployment broke it” is inaccurate; writing them all off as harmless warnings is just as dangerous. The real picture spans four layers:

LayerTypical issueCan it block startup
FilesystemSDK cannot create cache or checkpoint filesYes
Configuration migrationOld properties temporarily mapped by the migratorUsually not
classpathDuplicate logging bridge, incompatible Logback versionsDepends on the component
Business codeEmpty string passed to Class.forNameYes, or a latent risk

The right debugging order

flowchart TD
  A["Spring Boot startup failure"] --> B["Read from the deepest exception upward"]
  B --> C{"What is the deepest cause"}
  C --> D["IOException / mkdir"]
  C --> E["NoClassDefFound / ClassNotFound"]
  C --> F["Properties migration"]
  C --> G["Logging warning"]
  D --> H["Check UID, HOME, mounts, and permissions"]
  E --> I["Check the effective configuration and dependency tree"]
  F --> J["Replace the configuration key"]
  G --> K["Clean up the logging bridge or add an adapter"]

UnsatisfiedDependencyException is often just the outermost wrapper: the Controller depends on the Service, the Service depends on FileManager, and FileManager fails to create a directory during construction — which is why the Controller can’t be injected.

Don’t jump to fixing whichever Bean you see first in the stack trace.

Incident 1: The root cause of UnsatisfiedDependencyException was mkdir

Outer logs:

Error creating bean with name 'voucherController'
Unsatisfied dependency expressed through constructor parameter 0

Going further down:

Error creating bean with name 'fileManager'
Factory method 'fileManager' threw exception with message: mkdir failed

At the very bottom:

Caused by: java.io.IOException: mkdir failed
  at ...FileRecorder.<init>(...)

This shows:

  • Spring DI itself is not broken.
  • The Controller and Service constructors are not the primary problem.
  • A third-party file SDK failed to create its checkpoint-record directory during bean initialization.

Start by entering the container with the same image and security context:

id
printf 'HOME=%s\n' "$HOME"
java -XshowSettings:properties -version 2>&1 | grep 'user.home'
mount
ls -ld /root /tmp /data/java/logs
touch /tmp/write-test

Running as root UID in a container does not mean every path is writable; a read-only root filesystem, volume permissions, mount overlays, and the default paths chosen by the SDK can all change the outcome.

Incident 2: Why Nacos suddenly started writing to /root/nacos

The Nacos Client stores naming failover, snapshot, or log files. Path calculation can depend on:

  • HOME.
  • Java user.home.
  • Nacos’s own JM.SNAPSHOT.PATH.
  • JM.LOG.PATH.

The old Deployment happened to allow writing to /root, so the problem stayed hidden. After the security baseline was tightened or the image user changed, startup threads began to report:

failed to create cache dir: /root/nacos/naming/<namespace>/failover

The fix is to give the client an explicit, controlled, writable directory:

volumeMounts:
  - name: tmp-volume
    mountPath: /tmp

env:
  - name: HOME
    value: /tmp
  - name: JDK_JAVA_OPTIONS
    value: >-
      -Duser.home=/tmp
      -DJM.SNAPSHOT.PATH=/tmp
      -DJM.LOG.PATH=/data/java/logs/nacos

volumes:
  - name: tmp-volume
    emptyDir:
      sizeLimit: 2Gi

The startup script creates the directories in advance and exits on failure:

mkdir -p /tmp/nacos /data/java/logs/nacos
test -w /tmp
test -w /data/java/logs/nacos

Don’t solve one cache-directory problem by restoring all capabilities or making the entire root filesystem writable.

Also distinguish severity:

  • If the Nacos failover backup fails, the main registration flow may still work, but disaster recovery is degraded.
  • If the file SDK hits mkdir failed during bean construction, the Spring Context fails to start outright.

Just because all of these messages are logged at ERROR level doesn’t mean they have the same impact; you need to look at the lifecycle phase where the exception occurs.

Incident 3: server.use-forward-headers is a migration hint

Log:

The use of configuration keys that are no longer supported was found:
server.use-forward-headers
Reason: Replaced to support additional strategies.

If spring-boot-properties-migrator was added during the upgrade, the app may still start, because the migrator temporarily maps the old key. But you should replace the key as soon as possible:

# 删除
server.use-forward-headers=true

# 根据代理链选择
server.forward-headers-strategy=framework

The differences between FRAMEWORK, NATIVE, and NONE are described in the Spring Boot reverse proxy guide.

The Spring Boot upgrade guide states explicitly that the properties migrator is only for discovering and temporarily migrating renamed properties, and the dependency should be removed once the upgrade is complete.

So the order of operations is:

  1. Search all namespaces, groups, and dataIds in Nacos for the old key.
  2. Replace it with the new key.
  3. Roll the service and confirm the migration report no longer appears.
  4. Remove the properties migrator from the parent or the app.

Don’t “fix” the configuration by turning off migration logging.

Incident 4: commons-logging coexists with spring-jcl

Warning:

Standard Commons Logging discovery in action with spring-jcl:
please remove commons-logging.jar from classpath

Spring Framework uses spring-jcl as its Commons Logging bridge. If the traditional artifact also appears on the classpath:

commons-logging:commons-logging

the logging implementation discovery order can conflict.

First locate the chain that introduces it:

mvn dependency:tree \
  -Dverbose \
  -Dincludes=commons-logging:commons-logging

Don’t exclude it one by one across dozens of business repositories. If the dependency comes from a unified Nacos config/discovery starter, exclude it at the starter’s direct-dependency boundary:

<dependency>
  <groupId>com.alibaba.cloud</groupId>
  <artifactId>spring-cloud-starter-alibaba-nacos-config</artifactId>
  <exclusions>
    <exclusion>
      <groupId>commons-logging</groupId>
      <artifactId>commons-logging</artifactId>
    </exclusion>
  </exclusions>
</dependency>

If the discovery starter carries its own dependency, exclude it at that boundary as well. A Maven exclusion only applies to the specified dependency path; another SDK may still pull the same JAR back in.

Re-check after the cleanup:

mvn dependency:tree \
  -Dincludes=commons-logging:commons-logging

jar tf application.jar \
  | grep 'BOOT-INF/lib/commons-logging'

If the organization wants to ban it long-term, add a Maven Enforcer bannedDependencies rule in the parent — but handle the known transitive chains first so a single upgrade doesn’t block every repository at once.

Incident 5: Nacos cannot load nacos-logback.xml

Warning:

Load Logback Configuration of Nacos fail,
message: Could not initialize Logback Nacos logging
from classpath:nacos-logback.xml

This is not as simple as “a missing XML file”. Spring Boot 3 uses Logback 1.4, and some Nacos Client 2.2.x versions initialize logging in a way that is incompatible with it.

The compatibility mapping in the Nacos official FAQ is:

Nacos Clientlogback-adapter
2.2.1–2.3.x1.0.x
2.4.0 and later1.1.x

For Nacos Client 2.2.1, you can lock the version in unified dependency management:

<properties>
  <nacos-logback-adapter.version>1.0.1</nacos-logback-adapter.version>
</properties>

<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>com.alibaba.nacos</groupId>
      <artifactId>logback-adapter</artifactId>
      <version>${nacos-logback-adapter.version}</version>
    </dependency>
  </dependencies>
</dependencyManagement>

But dependencyManagement only manages versions; it does not automatically put the JAR into the app. The shared starter that actually uses Nacos also has to declare:

<dependency>
  <groupId>com.alibaba.nacos</groupId>
  <artifactId>logback-adapter</artifactId>
</dependency>

Finally, verify with the executable JAR rather than just the parent:

jar tf application.jar \
  | grep -E 'nacos-client|logback-adapter|logback-classic'

Don’t copy an old nacos-logback.xml into every app. That scatters version-compatibility responsibility across business repositories, and the versions will drift again the next time Nacos is upgraded.

Incident 6: ClassNotFoundException without a message

Another service reported this at startup:

java.lang.ClassNotFoundException:
  at java.lang.Class.forName0(...)
  at java.lang.Class.forName(...)
  at ...JDBCUtil.initialize(...)

No class name after the exception colon — that is an important clue. The code actually executes:

Class.forName(driver);

But the optional configuration contains empty strings:

sales.driver=
sales.url=

Class.forName("") throws a ClassNotFoundException that carries almost no diagnostic information.

If this synchronous data source is an optional feature, the initialization logic should first check whether the feature is enabled:

@PostConstruct
void initialize() {
    if (!StringUtils.hasText(url)) {
        log.info("未配置 sales.url，同步功能已禁用");
        return;
    }

    if (!StringUtils.hasText(driver)) {
        throw new IllegalStateException(
            "已配置 sales.url，但缺少 sales.driver"
        );
    }

    try {
        Class.forName(driver);
    } catch (ClassNotFoundException ex) {
        throw new IllegalStateException(
            "无法加载同步数据库驱动: " + driver,
            ex
        );
    }
}

An even better approach is conditional configuration:

@ConditionalOnProperty(
    prefix = "sales",
    name = "url"
)

That way, an unconfigured optional feature never creates a Bean at all. Don’t use an empty string as a stand-in for “enabled, but the driver isn’t known yet”.

Also, the method that calls Class.forName was once named getServletPort, even though it actually loads the JDBC driver. A misleading name steers stack-trace debugging in the wrong direction, so fix it in the same change.

How to decide whether to change Deployment, Nacos, the parent, or business code

EvidenceWhere to fix
Same image writable under the old security context, unwritable under the new oneDeployment and mounts
Key mapped by the properties migratorNacos / application config
Multiple apps pull the old JAR through the same starterParent or shared starter
Only one optional module passes empty values to a reflection APIBusiness code
Adapter and client versions do not matchDependency management + starter

Just because the logs show up in Kubernetes doesn’t mean every problem should be fixed through YAML.

Rolling verification checklist

  1. After building, inspect the final JAR’s dependencies, not just the IDE dependency view.
  2. Render the Deployment and confirm HOME, user.home, mounts, and UID.
  3. Roll one replica first.
  4. Wait for the new ReplicaSet to become Ready, and confirm the old Pod can still serve as a fallback.
  5. Check the startup logs for all five kinds of keywords.
  6. Exercise the real paths for Nacos registration, Redis, file upload, and optional JDBC.
  7. Roll the remaining replicas.
kubectl -n <namespace> logs <new-pod> --since=20m \
  | grep -Ei \
  'mkdir failed|/root/nacos|use-forward-headers|commons-logging|nacos-logback|ClassNotFound'

Definition of done

  • The Spring exception has been traced to the deepest cause instead of stopping at the Bean name.
  • Every client directory that needs write access has a controlled mount and size limit.
  • Nacos no longer attempts to write to /root/nacos.
  • Nacos, the upload SDK, and log directories have all passed real write verification.
  • server.use-forward-headers has been removed from all Nacos dataIds.
  • The final JAR contains no traditional commons-logging.jar.
  • The Nacos Client and logback-adapter versions match.
  • The optional JDBC feature does not load a driver when unconfigured.
  • The old and new ReplicaSets have switched over, with no old Pod serving as a long-term fallback.

Final conclusion

There was no single “magic configuration” behind these startup incidents. What these incidents really provide is a reliable decision path:

先读最深 Cause
→ 判断文件系统、配置、classpath 还是业务代码
→ 在最接近根因的公共边界修复
→ 检查最终 JAR 和最终 Pod，而不是源码与模板

The security baseline exposed a long-standing implicit assumption that /root was writable; Spring Boot 3 exposed version-boundary problems in old properties and the logging stack; the empty Class.forName exposed business code that didn’t express “optional feature” properly.

Fix each problem where it belongs — Deployment, Nacos, the shared starter, or business code. Only then can you avoid loosening cluster-wide permissions or introducing new classpath conflicts just to silence a log line.
