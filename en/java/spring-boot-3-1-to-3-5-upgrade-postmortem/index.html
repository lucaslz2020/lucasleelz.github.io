Upgrading Spring Boot from 3.1.7 to 3.5.13: Three Problems That Only Surfaced After a Clean Compile

A postmortem of the upgrade from Spring Boot 3.1.7 to 3.5.13 and Java 17 to 25, covering a duplicate Spring Batch job name, ambiguous TaskExecutor injection, and a MongoDB 4.2 health check incompatibility.

lucaslzAuthor
August 1, 2026 8 min read
#Spring Boot #Java #Spring Batch #MongoDB #Kubernetes #Postmortem
{ }

This post comes from a real upgrade. Service names, project coordinates, Pods, nodes, images, namespaces, and organization information have been anonymized or generalized. This post focuses on the upgrade troubleshooting process; do not copy the configuration or fixes into another service without verifying them first.

Recently, I upgraded two Spring Boot services from 3.1.7 to 3.5.13 and switched the runtime from Java 17 to Java 25. Maven compilation and packaging both passed, but after deployment to the test Kubernetes cluster, the two services successively failed to start or reported failing full health checks.

The most noteworthy part of this upgrade is that none of the problems were in business-code syntax; they all came from changed framework defaults. Below, they’re presented in the order we actually troubleshot them.

This post is the postmortem of the completed 3.1.7 → 3.5.13 upgrade. The next post, Upgrading from Spring Boot 3.5.13 to 4.1, only discusses the new compatibility boundaries introduced in the next phase and does not repeat the general startup, health check, and middleware acceptance process covered here.

Build an Upgrade Triage Chain First

flowchart LR
  A["Upgrade Spring Boot and JDK"] --> B["Compile and package with the target JDK"]
  B --> C["New Pod startup logs"]
  C --> D["Full /actuator/health"]
  D --> E["Middleware command and protocol verification"]
  E --> F["Rolling release and Endpoint switch"]

When an upgrade fails, don’t jump from “which component appeared in the error log” straight to root cause. First determine whether the failure happened during bean creation, framework initialization, health checks, or business requests, then gather independent evidence for each layer.

Upgrade Scope and Acceptance Boundary

The parent POM’s Spring Boot version went from 3.1.7 to 3.5.13, and the JDK from 17 to 25.

Confirm two things before upgrading:

  1. CI, the container base image, and local Maven all use the same JDK generation;
  2. “Compilation passed” alone is not an acceptance criterion — at minimum, verify application startup, the full Actuator health check, and connections to key middleware.

All three problems in this post fall into the second category: they don’t block compilation, but they surface when new replicas start or are actually probed.

Problem 1: Duplicate Spring Batch Job Names Prevent Startup

Symptom: The New Replica Fails While Registering Jobs

One service threw an exception like this at startup:

DuplicateJobException: A job configuration with this name [initPriceJob] was already registered

Two different @Bean methods each declare a job, but one of the JobBuilders still uses the internal name initPriceJob.

@Bean
public Job productionInitPriceJob(...) {
    return new JobBuilder("initPriceJob", jobRepository)
        // ...
        .build();
}

Evidence and Root Cause: The Bean Name Is Not the Batch Job Name

After the Spring Batch upgrade, the default configuration collects all Job beans and registers them into the JobRegistry during container initialization. As a result, the previously latent “duplicate internal job name” problem became a deterministic startup failure in the new version.

Two names need to be distinguished:

  • Spring bean name: for example, productionInitPriceJob;
  • Spring Batch job name: the name passed to new JobBuilder("...").

The latter is what participates in JobRegistry deduplication.

Fix: Make the JobBuilder Name Unique

Make the JobBuilder’s internal name unique to its business job:

return new JobBuilder("productionInitPriceJob", jobRepository)
    // ...
    .build();

Verification and Takeaways

When upgrading Spring Batch, do a global scan of all new JobBuilder(...) calls and check for duplicate string names, rather than only checking @Bean method names.

Problem 2: TaskExecutor Goes from “Injected by Name” to “Two Candidate Beans”

Symptom: Two Candidate Beans Break Injection

The other service failed to start:

Parameter 0 of ... required a single bean, but 2 were found:
 - applicationTaskExecutor
 - taskScheduler

The original code used field injection:

@Autowired
private TaskExecutor taskExecutor;

The service has both async and scheduled task features enabled. After the upgrade, the container contains both applicationTaskExecutor and taskScheduler; both match TaskExecutor, so Spring can no longer guess which one to inject.

Evidence and Root Cause: The Previous Implicit Name Matching No Longer Holds

In the old auto-configuration, the default async executor was still exposed as taskExecutor for compatibility. When the field name happened to match this alias, Spring could use name matching to complete the injection.

The new auto-configuration keeps applicationTaskExecutor but no longer provides the taskExecutor alias in the same way; with scheduling enabled, taskScheduler also becomes a TaskExecutor candidate. The implicit behavior that previously relied on the field name no longer applies.

Fix: Put the Thread Pool Choice in Code

Make it explicit that the application async thread pool is the dependency:

@Autowired
@Qualifier("applicationTaskExecutor")
private TaskExecutor taskExecutor;

If the project has multiple injection points of the same type, search them all, for example:

rg 'TaskExecutor taskExecutor' src/main/java

Verification and Takeaways

Don’t let business code depend on historical aliases of Spring Boot auto-configured beans. For types that commonly have multiple instances — thread pools, data sources, cache managers — use @Qualifier, or switch to constructor injection with the qualifier on the parameter.

Problem 3: MongoDB Looks “Unreachable,” but the Health Check Command Is Incompatible

Symptom: MongoDB Looks “Unreachable”

After the application started, logs kept showing:

MongoDB health check failed
Command failed with error 59 (CommandNotFound):
no such command: 'hello'

The first reaction is easily DNS, Service, credentials, or network policy. But verification inside the cluster showed:

db.adminCommand({ ping: 1 });
// { "ok" : 1 }

db.adminCommand({ isMaster: 1 });
// { "ismaster" : true, ..., "ok" : 1 }

db.adminCommand({ hello: 1 });
// no such command: 'hello'

The test environment runs MongoDB 4.2.8; the MongoDB Java driver itself connected successfully. The failure occurs when the full /actuator/health call invokes the default MongoHealthIndicator.

Evidence and Root Cause: The Failing Part Is the Actuator Command, Not the TCP Connection

Spring Boot 3.1’s Mongo health check executed:

mongoTemplate.executeCommand("{ isMaster: 1 }");

Spring Boot 3.5 changed it to:

mongoTemplate.executeCommand("{ hello: 1 }");

MongoDB 4.2 doesn’t recognize the hello command, so the health check reports DOWN. The key point: a failed health check doesn’t mean the application can’t establish a Mongo connection. First use ping, driver connection logs, and business reads/writes to determine whether the issue is protocol, authentication, or network.

Fix: Keep a Real Check and Override the Incompatible Default Command

It’s not recommended to disable the Mongo health check entirely just to make it green:

management.health.mongo.enabled=false

That would lose the real Mongo availability signal.

This upgrade kept the health check semantics and overrode the default contributor: provide a check implementation compatible with MongoDB 4.2 under the same bean name.

@Configuration(proxyBeanMethods = false)
public class MongoHealthConfiguration {

    @Bean(name = "mongoHealthContributor")
    public HealthIndicator mongoHealthContributor(MongoTemplate mongoTemplate) {
        return new AbstractHealthIndicator("MongoDB health check failed") {
            @Override
            protected void doHealthCheck(Health.Builder builder) throws Exception {
                Document result = mongoTemplate.executeCommand("{ isMaster: 1 }");
                builder.up().withDetail("maxWireVersion", result.getInteger("maxWireVersion"));
            }
        };
    }
}

Spring Boot’s auto-configuration backs off when it finds a bean named mongoHealthContributor. The final /actuator/health still genuinely checks Mongo and is compatible with the local 4.2 instance.

Verification and Takeaways

When upgrading frameworks, Actuator is part of the runtime compatibility surface. In particular, health check commands for databases, message queues, and registry centers can hit old server-side compatibility problems earlier than business code.

The long-term plan remains upgrading the MongoDB server; an application-side compatibility implementation suits test environments or a migration transition period.

Step 4: Turn Verification into an Upgrade Acceptance Checklist

Running mvn package alone isn’t enough to prove an upgrade succeeded. For a Spring Boot major upgrade, or one spanning multiple minor versions, verify in this order:

  1. Compile and package with the target JDK;
  2. Start a new replica locally or in the test environment and confirm there are no bean injection, auto-configuration, or job registration exceptions;
  3. Request the full /actuator/health — don’t just look at Kubernetes liveness/readiness;
  4. Confirm key components — DB, Redis, RabbitMQ, MongoDB, Nacos — are all UP;
  5. Run targeted regression on job names, thread pool injection, serialization config, and middleware protocol commands;
  6. After the rolling release, confirm the new Pod is Ready, the Endpoint has switched, and the old Pod has exited cleanly.

Summary: Make Previously Implicit Framework Contracts Explicit

This upgrade from Spring Boot 3.1.7 to 3.5.13 produced no traditional API compile errors, yet exposed three more subtle problems:

TypeRoot causeFix principle
Spring BatchThe new version strictly registers every job at startup, exposing duplicate internal namesKeep JobBuilder names globally unique
Async thread poolAuto-configuration bean aliases changed, producing multiple TaskExecutor candidatesExplicit @Qualifier; don’t rely on field-name matching
Mongo health checkThe default command changed from isMaster to hello, which old Mongo doesn’t supportOverride the health check and keep real connectivity checks

The core of a framework upgrade isn’t “bumping the version number” — it’s identifying and verifying the contracts that previously depended on default behavior but were never explicitly written into business code.

If problems after an upgrade appear in container directories, deprecated properties, commons-logging, Nacos Logback, or optional JDBC drivers, see the Spring Boot 3 container startup compatibility postmortem.
