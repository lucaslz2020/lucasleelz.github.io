Memory Drops from 3.5G to 900M After Upgrading Spring Boot to JDK 25: A Practical ZGC Analysis

Explains what Kubernetes actually sees in a Java container's memory, then walks through analyzing and tuning a Spring Boot service step by step with ZGC, SoftMaxHeapSize, ZUncommitDelay, and Native Memory Tracking.

lucaslzAuthor
July 26, 2026 8 min read
#Java #JDK 25 #ZGC #Kubernetes #Spring Boot
{ }

This article is based on a real optimization. Service names, images, nodes, capacities, and business data have all been generalized. The parameters are meant as an analytical approach, not something to copy verbatim into every Java service.

After a Spring Boot service upgraded to JDK 25, Kubernetes observed roughly 3.5 GiB at startup, which gradually dropped below 1 GiB once the service stabilized. This is not a case of the JVM “emptying business data,” nor can it be explained simply by “ZGC being more memory-efficient than G1.”

The key is to first understand what kubectl top actually sees, and why the JVM’s used heap, committed heap, process resident memory, and container working set are not equal.

What Makes Up Java Container Memory

flowchart TD
  A["Container Memory"] --> B["Java Heap"]
  A --> C["Metaspace / Compressed Class Space"]
  A --> D["Thread Stacks"]
  A --> E["Direct / Mapped Buffers"]
  A --> F["JIT Code Cache"]
  A --> G["GC Native Structures"]
  A --> H["Shared Libraries / Page Cache"]

-Xmx only caps the Java heap; it does not cover other regions. A process started with -Xmx2g can legitimately use more than 2 GiB of container memory.

Step 1: Confirm Which JDK Is Actually in the Pod

Don’t guess the vendor from the base image name:

kubectl -n <namespace> exec <pod> -- java -version

kubectl -n <namespace> exec <pod> -- \
  java -XshowSettings:properties -version 2>&1 \
  | grep -E 'java.vendor|java.version|java.home|java.vm.name'

OpenJDK is the implementation and ecosystem; Oracle JDK, Eclipse Temurin, Amazon Corretto, and Microsoft Build of OpenJDK are different distribution builds. When choosing, consider:

  • Security update cadence.
  • Container and CPU architecture support.
  • Vendor support and licensing.
  • Whether it passes the project’s full regression tests.

Switching to Oracle JDK will not automatically fix an application’s memory issues.

Step 2: Confirm Where All JVM Flags Come From

kubectl -n <namespace> exec <pod> -- sh -c '
  printf "JAVA_TOOL_OPTIONS=%s\n" "$JAVA_TOOL_OPTIONS"
  printf "JDK_JAVA_OPTIONS=%s\n" "$JDK_JAVA_OPTIONS"
  printf "JAVA_OPTS=%s\n" "$JAVA_OPTS"
'

Then inspect the process:

kubectl -n <namespace> exec <pod> -- jcmd 1 VM.command_line
kubectl -n <namespace> exec <pod> -- jcmd 1 VM.flags

Picked up JAVA_TOOL_OPTIONS and Picked up JDK_JAVA_OPTIONS indicate that flags were injected from the environment. If a Deployment defines both, make sure they don’t duplicate or conflict.

Global templates are especially risky: a flag supported only by the new JDK, once injected into a service still running an older JDK, will immediately produce:

Unrecognized option
Could not create the Java Virtual Machine

Step 3: Inspect Kubernetes and the JVM Separately

On the Kubernetes side:

kubectl top pod -n <namespace> <pod> --containers
kubectl -n <namespace> get pod <pod> \
  -o jsonpath='{.spec.containers[0].resources}{"\n"}'

Inside the container:

kubectl -n <namespace> exec <pod> -- sh -c '
  grep -E "VmRSS|VmSize|Threads" /proc/1/status
  test -f /sys/fs/cgroup/memory.current && cat /sys/fs/cgroup/memory.current
'

On the JVM side:

kubectl -n <namespace> exec <pod> -- jcmd 1 GC.heap_info
kubectl -n <namespace> exec <pod> -- jcmd 1 VM.native_memory summary

Native Memory Tracking requires a startup flag:

-XX:NativeMemoryTracking=summary

NMT has some overhead; it’s suitable for diagnostics and baseline observation. Whether to keep it enabled long-term should be decided under load testing.

Step 4: Understand SoftMaxHeapSize

Example:

-Xmx2g
-XX:SoftMaxHeapSize=1g

The Oracle JDK 25 ZGC documentation explains that Soft Max is a soft target for the GC, not a hard limit. ZGC will try to keep the heap near 1 GiB, but under pressure it may still temporarily grow up to -Xmx2g. The Z Garbage Collector

It is therefore a good fit for expressing:

平时尽量少占内存
高峰允许使用预留上限

It cannot replace the container memory limit, and it does not guarantee that RSS will stay below 1 GiB.

Step 5: Understand ZUncommitDelay

-XX:ZUncommitDelay=120

It means that after ZGC notices heap memory has been idle for a long time, the relevant memory pages must stay idle for about 120 seconds before they become eligible to be returned to the operating system. The default in JDK 25 is 300 seconds.

Setting it to 30 seconds may make the monitored numbers drop faster, but frequent load fluctuations can also cause repeated commit/uncommit cycles. It’s best to observe the interval between business peaks first:

Load patternInitial recommendation
Long periods of low load with occasional peaks120–300 seconds
Sustained steady high loadKeep the default; limited benefit
Rapid fluctuations every minuteAvoid too-short values; load-test first

“Returning memory faster” does not always mean “better throughput.”

Step 6: A Verifiable ZGC Starting Point

-XX:+UseZGC
-Xms512m
-Xmx2g
-XX:SoftMaxHeapSize=1g
-XX:ZUncommitDelay=120
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/data/java/dumps

Example container resources:

resources:
  requests:
    cpu: "1"
    memory: 1536Mi
  limits:
    cpu: "2"
    memory: 3Gi

Always leave headroom for non-heap memory. When the sum of the JVM heap cap, Direct Memory, thread stacks, Metaspace, and native libraries approaches the container limit, the kernel will OOMKill the process — and the JVM may never get a chance to produce a Heap Dump.

Step 7: Why It Starts High and Then Drops

During startup:

  • Loading a large number of classes and beans.
  • JIT compiling hot code.
  • Establishing client buffers for databases, Nacos, Kafka, and more.
  • Parsing configuration, scanning annotations, and creating threads.
  • The heap temporarily expands to sustain startup throughput.

After startup:

  • Short-lived objects are collected.
  • ZGC adjusts the heap target according to Soft Max.
  • Idle pages are gradually returned to the OS after exceeding ZUncommitDelay.

The drop from 3.5 GiB to 900 MiB may therefore include heap shrinkage as well as changes in file pages and the container working set. Only by looking at NMT, the heap, and cgroup together can you break down what actually happened.

Running locally often means there is no cgroup limit, so the JVM sees much larger host memory; the IDE may also override VM options. Start with:

jcmd <pid> VM.command_line
jcmd <pid> VM.flags
jcmd <pid> GC.heap_info

Don’t compare a “one minute after local startup” number with a “one hour stable in production” number.

Step 9: Handle JDK 25 Warnings

Unsafe terminally deprecated

This usually comes from dependencies such as Netty, gRPC, and the Nacos Client calling sun.misc.Unsafe. In order:

  1. Find the exact jar using the dependency tree.
  2. Check whether the upstream project already has a compatible version.
  3. Upgrade the dependency first and run regression tests.
  4. Don’t silence all warnings on your own.

restricted native access

--enable-native-access=ALL-UNNAMED

Only add it when you’ve confirmed the flag is supported at runtime, the dependency genuinely needs it, and the security review accepts it. It must not go into a global Deployment template that targets mixed JDK versions.

add-opens / add-exports

These flags are transitional measures for compatibility with legacy reflection or internal APIs. Each one should be documented with “which dependency needs it, and to what version it must be upgraded before it can be removed.”

Step 10: Load Testing and Acceptance

Compare at least two groups under identical traffic:

基线：原 JDK + 原 GC
候选：JDK 25 + ZGC 参数

Collect:

  • Startup time and time to Ready.
  • P50/P95/P99 latency.
  • Throughput and error rate.
  • Heap used/committed.
  • RSS, cgroup memory, and Direct Memory.
  • GC pause and allocation rate.
  • CPU and context switches.
  • One full batch run or business peak.

Observation should cover at least one full real load cycle — don’t just look at the first ten minutes after startup.

How to Tell Whether 900M Is Healthy

900 MiB is not inherently good news. Also confirm:

  • No frequent GC causing higher CPU usage.
  • P99 hasn’t gotten worse.
  • The heap has enough headroom at peaks.
  • Direct buffers, threads, and Metaspace aren’t growing steadily.
  • No OOMKilled events or container memory pressure.
  • Batch processing and message consumption throughput are normal.

Definition of Done

  • The runtime JDK, vendor, and JVM flags can be reproducibly confirmed.
  • The four layers of data — kubectl top, cgroup, heap, and NMT — line up with each other.
  • The relationship between Soft Max and Xmx has been validated at peak load.
  • ZUncommitDelay covers a real load cycle without causing obvious jitter.
  • The container limit reserves enough room for non-heap memory.
  • Every compatibility flag has a documented origin and removal condition.
  • Latency, throughput, and stability don’t regress after optimization.

ZGC’s value is not making the process “use less over time,” but more proactively adapting to load and returning long-idle heap memory to the OS, within what the latency target allows.
