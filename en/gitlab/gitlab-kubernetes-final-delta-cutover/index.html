GitLab 14 to 19 Migration, Part 3: Kubernetes Final Delta Cutover, Stable IP, and Rollback

A field report on final freeze, repository delta synchronization, stable-IP cutover, PV rebinding, six-layer acceptance, and rollback for GitLab in Kubernetes.

lucaslzAuthor
August 15, 2026 6 min read
#GitLab #Kubernetes #DevOps #Data Migration #Rollback
{ }

This is the last part of the GitLab CE 14.9.3 to 19.2.1 series. Part 1 covers same-version restore and upgrade cadence; Part 2 covers stops, background migrations, and PostgreSQL. This article answers one question: once the new GitLab starts, how can it safely replace the old one?

Initial restore is not a cutover

An initial backup is a snapshot. While the old GitLab remains open, it can still receive pushes, permission changes, CI variables, merge requests, and build records.

In our final audit, database object counts had not increased, but we found hundreds of push events across more than ten repositories. That matters: comparing project counts, restoring only the database, or even comparing only last-update time can miss real Git data deltas.

The goal before cutover is not simply that the new instance is reachable. It is to answer precisely what the old instance accepted last, which data must be synchronized, and how to prove both sides match afterwards.

Freeze the old instance before comparing it

At the start of the cutover window, stop the old web and background write paths while keeping a controlled root operations channel:

gitlab-ctl stop nginx
gitlab-ctl stop gitlab-workhorse
gitlab-ctl stop puma
gitlab-ctl stop sidekiq
gitlab-ctl stop gitlab-kas

Only then compare both sides. Audit core user/group/project/MR/CI counts, latest Project/Event times, default and active branch tips, LFS/Artifact/Upload/Package changes, and audit/event records. Events identify repositories likely to have changed; refs and object checks establish correctness.

Do not blindly rsync —delete every repository

We first located changed repositories through events and project times, then synchronized only their hashed repository directories. A blanket rsync --delete against an unknown difference can delete necessary target-side files and make the change too broad to roll back.

Ownership also matters. The git UID/GID can differ between GitLab images. rsync --numeric-ids carries old values to the target and can leave Gitaly unable to read or write. Repair ownership with the target container’s actual identity:

chown -R <target-git-uid>:<target-git-gid> <affected-repository>

Then verify refs and objects:

git -C <source-repository> for-each-ref \
  --format='%(refname) %(objectname)' | sort > source.refs
git -C <target-repository> for-each-ref \
  --format='%(refname) %(objectname)' | sort > target.refs
diff -u source.refs target.refs
git -C <target-repository> fsck --no-dangling

If an old commit-graph cache references missing objects, keep the old cache and rebuild from reachable refs; do not delete Git objects merely to silence an error. Clear Rails cache and refresh project activity time after synchronization.

Keeping the existing IP means handling node identity

To avoid changing developer laptops, Jenkins, and historical clone URLs, we retained the original GitLab service IP. That reduces client changes but binds the cutover window to the IP, hostname, Kubernetes Node name, and PV nodeAffinity.

The sequence was: scale GitLab to zero; make sure the old server is write-frozen, powered off, and no longer answers on the old IP; change the target node to its final hostname and static IP; run kubeadm reset and rejoin under the new node name; restore GitLab labels and taints; recreate PV/PVC metadata against the original data directory; scale StatefulSet to one; then validate every service layer.

PV nodeAffinity is immutable. After a node rename, do not patch it. Stop GitLab, verify that the PV reclaim policy is Retain, delete only PVC/PV objects while keeping the host data directory, rebuild them for the new node name, wait for Bound, and only then start GitLab. The old server must never come back online with the old IP; disconnect its NIC or assign another address first.

Six layers of acceptance

Pod Ready is only layer one. We accepted the migration only after all six passed:

  1. Kubernetes: node name, InternalIP, and hostname agree; the Pod is on the expected node without restarts; PVC is Bound; PV is Retain and targets the final node.
  2. GitLab services: gitlab-ctl status, gitlab-rake gitlab:check SANITIZE=true, GitLab Shell, Gitaly, Sidekiq, Redis, uploads, and hashed storage work.
  3. Database: counts match the frozen source, PostgreSQL is the target version, schema migrations are complete, unfinished background migrations are zero, and gitlab:doctor:secrets decrypts critical values.
  4. Repositories: refs match for all changed repositories and git fsck --no-dangling succeeds.
  5. Entry points: the HTTP sign-in page and SSH handshake work at the unchanged address.
  6. Real workflows: Jenkins checks out and reports status, webhooks deliver, runners take jobs, CI/CD variables decrypt, and login, 2FA, and personal access tokens work.
curl -fsS http://<gitlab-host>/users/sign_in >/dev/null
ssh -T git@<gitlab-host>

Rollback is a set of boundaries, not one file

After final cutover, do not immediately remove the old VM, old PostgreSQL directory, intermediate images, or critical backups. Keep the old VM powered off and isolated; the last verified full GitLab backup; critical dumps and configuration archives; old PostgreSQL data; the GitLab 18 full restore point; the GitLab 19 database-protection backup; actual image digests; and the final repository list plus ref checks.

Rollback is layered too: switch the old entry point back for an entry failure with intact data; restore the previous image and database state for a GitLab Pod failure; return to old PostgreSQL data for a database failure; or stop new writes, restore the last full backup, and recalculate deltas for an integrity failure. Never allow the old and new instances to accept writes at the same time.

Three criteria this migration left behind

  • The real unit of a GitLab upgrade is not an image: it is version, database, background migrations, and a recoverable backup.
  • A single-replica GitLab with local PV is not highly available. Kubernetes provides declarative deployment and centralized operations; it does not automatically replicate stateful data.
  • Initial restore is not completed migration. As long as the old instance stays open, final deltas must be checked separately for database objects, Git repositories, LFS/Artifact/Upload data, and configuration.

Treat each stage as an independent step with inputs, outputs, acceptance, and rollback, and a large migration becomes controlled work rather than luck.
