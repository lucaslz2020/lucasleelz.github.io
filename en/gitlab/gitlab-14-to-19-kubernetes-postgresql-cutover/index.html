GitLab 14 to 19 Migration, Part 1: Architecture, Upgrade Path, and Downtime Planning

A field report on restoring a long-running GitLab CE 14.9.3 into Kubernetes at the same version before moving safely to GitLab 19.2.1.

lucaslzAuthor
August 8, 2026 Updated August 10, 2026 6 min read
#GitLab #Kubernetes #PostgreSQL #DevOps #Migration
{ }

This article is based on a real production migration. IPs, domains, node names, project names, repository and user counts, registry names, backup names, and checksums have been sanitized or generalized. Secrets, passwords, and internal addresses are placeholders.

Required upgrade stops and the PostgreSQL support matrix change over time. Before executing any migration, recheck the official GitLab upgrade path and installation requirements. This is a reproducible case study, not a permanent version list.

This is not a “replace GitLab 14 with a GitLab 19 image” guide. We first restored an Omnibus GitLab CE 14.9.3 into Kubernetes at exactly the same version, then passed more than twenty upgrade stops, froze the old instance, synchronized final repository changes, and kept the existing HTTP and SSH endpoint.

This series has three parts:

  1. This article covers migration design, same-version restore, and upgrade cadence.
  2. Part 2: Required Upgrade Stops, Background Migrations, and PostgreSQL 17 covers the most failure-prone version and database work.
  3. Part 3: Kubernetes Final Delta Cutover, Stable IP, and Rollback covers the last mile that determines whether the new instance can go live.

The real constraints before migration

The starting point was a long-running GitLab CE 14.9.3 VM. Git repositories, bundled PostgreSQL, Redis, configuration, and logs all lived on that one machine. Developer laptops, Jenkins, and historical repository URLs already depended on its domain, service IP, and SSH entry point.

The goal was not containerization for its own sake. We needed to upgrade to GitLab CE 19.2.1, run a single-replica StatefulSet in Kubernetes, move to an independent in-cluster PostgreSQL database ending at PostgreSQL 17, preserve the existing Git endpoint, and keep usable rollback points.

Pod readiness cannot prove all of that. It says a process passed probes; it does not prove database migrations, batched background migrations, repository objects, encrypted values, or final deltas are safe.

Why we did not jump versions

Staying on 14.x means more than running an old release: security and defect fixes stop, client and integration compatibility keeps moving, and the operating system and database age out with the application.

GitLab upgrades are not just image tags, though. Major versions bring schema changes, encryption changes, and batched background migrations. Putting 14.9 data directly into 19.x commonly causes missing migration classes, incompatible tables or database versions, and undecryptable historic values.

We used this verified, conservative path. Each target minor was upgraded to its latest patch and accepted before the next stop:

14.9.3 → 14.9.5 → 14.10.5 → 15.0.5 → 15.4.6 → 15.11.13
→ 16.0.10 → 16.1.8 → 16.2.11 → 16.3.9 → 16.7.10 → 16.11.10
→ 17.3.7 → 17.5.5 → 17.8.7 → 17.11.7
→ 18.2.8 → 18.5.7 → 18.8.11 → 18.11.9 → 19.2.1

Some stops are conditional on instance scale, web node count, and table contents. We skipped stops that did not apply only after checking the relevant conditions. Treat that as a reminder to recalculate the path for every migration, not as a universal shortcut.

Establish a baseline before touching the platform

Before creating a Pod, we wrote down how we would later prove that data had not been lost. At minimum record the GitLab version, core object counts, refs for important repositories, attachment usage, PostgreSQL version and extensions, service health, and both kinds of migration state.

gitlab-rake gitlab:env:info
gitlab-rake gitlab:check SANITIZE=true

gitlab-rails runner '
puts({
  users: User.count,
  groups: Group.count,
  projects: Project.count,
  merge_requests: MergeRequest.count,
  builds: Ci::Build.count
}.inspect)
'

gitlab:check is valuable but not a data-consistency proof. It detects common configuration, permission, and service issues. Repository integrity still requires ref comparison, git fsck, and eventually real clone, push, and Jenkins checkout tests.

A backup is not a single tarball

Our first rehearsal exposed a familiar trap: an application backup is not the complete recovery capability. gitlab-secrets.json contains the ability to decrypt CI/CD variables and 2FA data; SSH host keys determine whether clients see an unexpected host fingerprint.

Before each important major version, we retained an application backup, an independent PostgreSQL dump, /etc/gitlab plus gitlab-secrets.json, SSH host keys, and manifests for StatefulSet, Service, PV, PVC, Secret, and ConfigMap. We also recorded sizes and SHA-256 checksums.

umask 077
gitlab-backup create
gitlab-ctl backup-etc
tar -C /etc -czf /backup/ssh-host-keys.tar.gz ssh
sha256sum /backup/* > /backup/SHA256SUMS

Restore a backup into the same GitLab version first. A 14.x backup goes back into 14.x; only after service and data validation should the upgrade start. When dumping external PostgreSQL, the pg_dump client major version must not be older than the server, so use the PostgreSQL Pod or a matching tool container if needed.

Separate platform migration from product upgrade

The key control point was restoring GitLab 14.9.3 into Kubernetes unchanged. Changing the runtime platform while crossing five major versions makes every failure ambiguous: PV, ownership, network, database connectivity, or GitLab itself.

We used a single-replica StatefulSet with a local PersistentVolume reclaimed as Retain. Its OnDelete strategy was intentional: an image change cannot roll a Pod automatically. Operators delete the Pod only after the current stop has completed its migrations, backup, and checks.

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: gitlab
spec:
  replicas: 1
  updateStrategy:
    type: OnDelete
  template:
    spec:
      nodeSelector:
        app-type: gitlab
      terminationGracePeriodSeconds: 300

Use the same gate at every stop

For every stop we checked the prior migrations, made a rollback backup, synchronized and pre-pulled the next image, updated the StatefulSet, explicitly recreated the Pod, inspected logs, then ran migration, service, and repository checks.

kubectl -n <namespace> set image statefulset/gitlab \
  gitlab=<registry>/gitlab-ce:<next-version>
kubectl -n <namespace> delete pod gitlab-0
kubectl -n <namespace> wait --for=condition=Ready pod/gitlab-0 --timeout=30m
kubectl -n <namespace> exec gitlab-0 -- gitlab-rake gitlab:check SANITIZE=true

Several minutes without readiness is not necessarily a hung process. We inspected events, reconfigure, database locks, Sidekiq, Gitaly, and disk I/O. Starting parallel Rails runners or a full checksum just because wait timed out can make storage contention worse.

The dangerous parts start after this cadence is in place: GitLab 17 changes background-migration status semantics, historic partitions can block jobs, and PostgreSQL must move in lockstep with GitLab.
