Upgrading GitLab CE 14.9.3 to 19.2.1 Safely: Kubernetes, PostgreSQL 17, and a Final Delta Cutover

A complete field guide to upgrading self-managed GitLab from 14.9.3 to 19.2.1, moving it to Kubernetes, adopting external PostgreSQL, synchronizing final repository changes, and preserving the original service address.

lucaslzAuthor
August 8, 2026 19 min read
#GitLab #Kubernetes #PostgreSQL #DevOps #Migration
{ }

This article is based on a real production migration. IP addresses, domains, node and project names, repository and user counts, container registries, backup filenames, and checksums have been sanitized or generalized. Secrets, passwords, and internal addresses are placeholders only.

GitLab’s required upgrade stops and PostgreSQL support matrix continue to change. Before you begin, check the official GitLab upgrade path and installation requirements again. Do not treat the version combination in this article as a permanent rule.

The source system was a GitLab CE 14.9.3 instance that had been running for years. It used an all-in-one Omnibus deployment, with Git repositories, PostgreSQL, Redis, configuration, and logs concentrated on one virtual machine.

The target state was:

  • GitLab CE 19.2.1.
  • A single-replica StatefulSet on Kubernetes.
  • Git repositories, uploads, and configuration on a retained local persistent volume.
  • A dedicated database and account on the cluster’s external PostgreSQL service.
  • PostgreSQL upgraded to version 17.
  • The external domain, service IP, and SSH endpoint unchanged.
  • The old server powered off after the final delta sync and retained temporarily as a rollback point.

This was not a matter of “change the image and wait for the Pod to turn green.” Four interdependent tracks had to advance together:

flowchart LR
  A["GitLab 14.9.3<br/>Old Omnibus"] --> B["GitLab 15<br/>Bundled PostgreSQL"]
  B --> C["GitLab 16<br/>External PostgreSQL 14"]
  C --> D["GitLab 17<br/>PostgreSQL 14 / 16"]
  D --> E["GitLab 18<br/>PostgreSQL 16 / 17"]

Every stage had to satisfy four conditions at once: the version path was valid, background migrations were complete, the database version was supported, and rollback data was usable.

Why Upgrade, and Why You Cannot Skip Straight to the Target

The problem with staying on 14.x is not merely that it is old:

  • Security and defect fixes eventually stop.
  • Compatibility ranges for new Runners, browsers, Git clients, and integrations keep moving forward.
  • Older PostgreSQL and operating-system releases also reach end of maintenance.
  • Legacy configuration, databases, and storage become obstacles when you later move to Kubernetes.

GitLab changes its database schema extensively, and major releases also rely on batched background migrations. Jumping directly from 14.9 to 19.x can leave you with missing migration classes, incompatible schemas, unsupported database versions, or encrypted values that can no longer be decrypted.

GitLab therefore requires specific upgrade stops. At each stop, install the latest patch of that minor release and wait for every background migration to finish before continuing.

The conservative path verified in this migration was:

Some older stops are conditional. In this case, we skipped stops that did not apply only after confirming there was a single web node and that the relevant business tables stayed below the documented thresholds.

Do not copy that conclusion blindly. Enter the source version, target version, instance scale, and relevant table sizes into GitLab’s Upgrade Path tool, then read the upgrade notes for every release in the resulting path.

Step 1: Freeze a Repeatable Migration Baseline

Before changing anything, record a baseline that can be queried repeatedly. Run the same checks after every upgrade stop.

At minimum, capture:

  • The GitLab version.
  • Counts for users, groups, projects, merge requests, pipelines, and jobs.
  • Total repository volume and the tips of important default branches.
  • LFS, upload, artifact, and package usage.
  • PostgreSQL version, database size, and extensions.
  • Sidekiq, Gitaly, Puma, Workhorse, and GitLab Shell status.
  • Regular schema migrations and batched background migration status.

For example:

gitlab-rake gitlab:env:info
gitlab-rake gitlab:check SANITIZE=true

gitlab-rails runner '
puts({
  users: User.count,
  groups: Group.count,
  projects: Project.count,
  merge_requests: MergeRequest.count,
  builds: Ci::Build.count
}.inspect)
'

gitlab:check alone is not enough. It finds many common configuration, permission, and service problems, but it does not replace business-object counts, repository ref comparisons, or real clone and push tests.

Step 2: A Backup Is More Than One Tarball

GitLab application backups and configuration backups are separate. The application backup includes the database and business files, while /etc/gitlab/gitlab-secrets.json contains the keys required to decrypt database values, CI/CD variables, 2FA data, and other secrets.

GitLab explicitly requires configuration and secrets to be stored separately in a secure location. See Backup and Restore GitLab.

At every critical stage, we retained at least:

  1. A GitLab application backup.
  2. An independent PostgreSQL dump.
  3. An archive of /etc/gitlab.
  4. gitlab-secrets.json.
  5. SSH host keys.
  6. Backup sizes and SHA-256 checksums.
  7. The current StatefulSet, Service, PV, PVC, Secret, and ConfigMap manifests.
umask 077

gitlab-backup create
gitlab-ctl backup-etc

tar -C /etc -czf /backup/ssh-host-keys.tar.gz ssh
sha256sum /backup/* > /backup/SHA256SUMS

A restore drill must use exactly the same GitLab version. A 14.x backup cannot be restored directly into a 19.x container.

One more common trap: when dumping an external PostgreSQL database, the pg_dump client major version cannot be older than the server major version. If the client bundled in the GitLab container is too old, create the dump from the PostgreSQL Pod or a temporary utility container with matching tools.

Step 3: Restore the Same Version on Kubernetes First

Do not change the runtime platform and cross several GitLab major versions at the same time. First restore 14.9.3 on Kubernetes. Begin the incremental upgrade only after that same-version deployment passes acceptance checks.

We used a single-replica StatefulSet. The core storage design looked like this:

apiVersion: v1
kind: PersistentVolume
metadata:
  name: gitlab-data
spec:
  capacity:
    storage: <capacity>
  accessModes: [ReadWriteOnce]
  persistentVolumeReclaimPolicy: Retain
  storageClassName: gitlab-local
  hostPath:
    path: /data/gitlab
  nodeAffinity:
    required:
      nodeSelectorTerms:
        - matchExpressions:
            - key: kubernetes.io/hostname
              operator: In
              values: [gitlab-node]

The StatefulSet used OnDelete:

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: gitlab
spec:
  replicas: 1
  updateStrategy:
    type: OnDelete
  template:
    spec:
      nodeSelector:
        app-type: gitlab
      tolerations:
        - key: app-type
          operator: Equal
          value: gitlab
          effect: NoSchedule
      terminationGracePeriodSeconds: 300

OnDelete is a safety control, not a shortcut. It prevents an image change from immediately rolling the StatefulSet. The operator must first verify that background migrations and backups for the current stop are complete, then explicitly delete the Pod to enter the next version.

Using Retain on the PV is equally important. Accidentally deleting the StatefulSet or PVC will not automatically reclaim the host’s /data/gitlab directory.

Step 4: Apply the Same Gate at Every GitLab Stop

The sequence at every stop was fixed:

  1. Confirm that all migrations from the previous version are complete.
  2. Create a rollback backup for the current version.
  3. Mirror the next image into the internal registry.
  4. Record the image digest and pre-pull it on the target node.
  5. Update the StatefulSet image.
  6. Explicitly delete the Pod.
  7. Watch reconfigure, database migration, Puma, Sidekiq, and Gitaly logs.
  8. Wait for the Pod to become Ready.
  9. Check schema and background migrations.
  10. Run HTTP, SSH, baseline-count, and gitlab:check validation.
kubectl -n <namespace> set image statefulset/gitlab \
  gitlab=<registry>/gitlab-ce:<next-version>

kubectl -n <namespace> delete pod gitlab-0
kubectl -n <namespace> wait --for=condition=Ready \
  pod/gitlab-0 --timeout=30m

kubectl -n <namespace> exec gitlab-0 -- \
  gitlab-rake gitlab:check SANITIZE=true

A Pod remaining unready for several minutes during its first start does not prove that the process is stuck. Inspect all of the following together:

kubectl -n <namespace> get pod gitlab-0 -o wide
kubectl -n <namespace> describe pod gitlab-0
kubectl -n <namespace> logs -f gitlab-0

Image pulls, Chef reconfigure, database locks, background migrations, repository checks, and disk I/O can all delay startup. Do not respond to one wait timeout by launching several Rails runners or full checksum jobs in parallel; that only increases disk contention.

Step 5: Identify Batched Background Migrations Correctly

This was the easiest part of the entire upgrade to misdiagnose.

An older script used:

WHERE status <> 3

In GitLab 17 and later, status 6 means finalized. The old condition therefore treats already completed migrations as unfinished and may even try to invoke migration classes that no longer exist in the current release.

A safer SQL query is:

SELECT id, job_class_name, table_name, status
FROM batched_background_migrations
WHERE status NOT IN (3, 6);

Alternatively, use the scope supplied by the model in that GitLab release:

gitlab-rails runner '
puts Gitlab::Database::BackgroundMigration::BatchedMigration.unfinished.count
'

Newer GitLab versions also provide more complete Rake tasks. The official documentation requires every background migration to finish before the next upgrade stop. See Check migrations before upgrade.

gitlab-rake gitlab:background_migrations:list
gitlab-rake gitlab:background_migrations:status

Do not simply mark a failed migration as finished. Inspect the parent migration, child jobs, business data, and the implementation in the current release first. Only consider the release-specific official finalize or execute tasks after proving that the migration does not apply to existing data and creating a recoverable backup.

Step 6: Keep PostgreSQL’s Upgrade Cadence Aligned with GitLab

GitLab and PostgreSQL cannot be upgraded independently. We used this cadence:

StageGitLabPostgreSQL strategy
Starting point14 / 15Keep the bundled Omnibus PostgreSQL
Middle16Move to external PostgreSQL 14
Before 1716.11Update PostgreSQL 14 to its latest compatible patch release
Before 1817.11Upgrade PostgreSQL 14 → 16
Before 1918.11Upgrade PostgreSQL 16 → 17
Target19.2Run on external PostgreSQL 17

GitLab 19 requires PostgreSQL 17. Consult the official GitLab installation requirements for the current support matrix.

The external service must use a dedicated database, role, and Secret:

postgresql['enable'] = false

gitlab_rails['db_adapter'] = 'postgresql'
gitlab_rails['db_host'] = 'postgresql.<namespace>.svc.cluster.local'
gitlab_rails['db_port'] = 5432
gitlab_rails['db_database'] = 'gitlabhq_production'
gitlab_rails['db_username'] = 'gitlab'
gitlab_rails['db_password'] = File.read('/run/secrets/gitlab-db/password').strip

Run pg_upgrade --check before every PostgreSQL major-version upgrade:

pg_upgrade \
  --old-datadir=<old-data> \
  --new-datadir=<new-data> \
  --old-bindir=<old-bin> \
  --new-bindir=<new-bin> \
  --check

The data volume in this migration used XFS with reflink support, so the actual upgrade used --clone instead of creating another full database copy:

pg_upgrade \
  --old-datadir=<old-data> \
  --new-datadir=<new-data> \
  --old-bindir=<old-bin> \
  --new-bindir=<new-bin> \
  --clone \
  --jobs=4

--clone is not a backup. Keep the old data directory until the final GitLab version, delta cutover, and business acceptance are all complete. Do not run the generated delete_old_cluster.sh prematurely.

Refresh optimizer statistics after the upgrade:

vacuumdb --all --analyze-in-stages --jobs=4

Finally, verify the real connection target and database version from GitLab Rails instead of relying only on PostgreSQL Pod logs.

Step 7: Resolve Real Upgrade Failures

1. status <> 3 Mistakes Finalized Migrations for Failures

GitLab 17 introduced another migration state. The fix is not to force completion; use the current release’s unfinished scope or NOT IN (3, 6).

2. Historical Partition Data Blocks a Background Migration

While processing historical notification data, one background task found records older than the available monthly partitions. Fabricating business records or skipping the task is unsafe.

The correct approach is:

  1. Identify the exact migration and source records.
  2. Confirm whether those records still have valid business relationships.
  3. Inspect the target table’s partition boundaries.
  4. During a write freeze and after taking a backup, add a fallback partition for legitimate historical data.
  5. Re-run or finalize the task using the official mechanism in that GitLab release.
  6. Recheck the unfinished migration count and data integrity.

3. GitLab 19 Exits on First Start Because of Legacy Component State

During the move from GitLab 18 to 19, the first reconfigure detected stale state from a historical component and exited. We did not immediately delete the whole Secret. We preserved a backup, confirmed that the new version would regenerate the obsolete block, and started it again. The schema migration then completed normally.

Distinguish carefully between:

  • Configuration that the new version genuinely removed.
  • A missing or damaged Secret.
  • Encrypted database values that can no longer be decrypted.

Each case requires a completely different response.

4. A Full Backup of the Final Version Can Exhaust the Disk

Near the end of the migration, there was not enough free space to stage another complete repository archive. We created a database-protection backup for the final version while retaining the verified full backup from the previous critical release, the repository volume, and the configuration archive.

This is a controlled trade-off only when the runbook states clearly which backup contains the database and which contains repositories. Never present a database-only archive as a complete restore point.

Step 8: Why a Successful Upgrade Still Is Not Ready for Cutover

The initial backup represents one instant in time. If the old GitLab remains open during the upgrade, developers continue to create pushes, permission changes, CI variables, merge requests, and build records.

A final delta audit is therefore mandatory before cutover.

Freeze the old instance first:

gitlab-ctl stop nginx
gitlab-ctl stop gitlab-workhorse
gitlab-ctl stop puma
gitlab-ctl stop sidekiq
gitlab-ctl stop gitlab-kas

Also prevent the git account from accepting SSH writes while keeping the operational root channel available. After the freeze, compare both sides:

  • Core counts for users, groups, projects, merge requests, and CI jobs.
  • Latest project and event timestamps.
  • Default-branch and active-branch tips.
  • Deltas in LFS, artifacts, uploads, and packages.
  • GitLab audit and event records.

In this migration, database object counts had not increased, yet several hundred push events affected more than ten repositories. Comparing only the database or project count would have missed those changes.

Step 9: Synchronize Only Repositories That Changed

Use event and project timestamps to locate changed repositories, then synchronize their hashed repository directories. Do not run rsync --delete across the entire repository tree until you fully understand the differences.

Perform at least three layers of validation after the sync.

File Ownership

The numeric UID and GID of the git account can differ between GitLab images. rsync --numeric-ids may preserve the old IDs and leave Gitaly unable to access the target.

Repair ownership using the actual UID/GID in the target container, not copied source numbers:

chown -R <target-git-uid>:<target-git-gid> <affected-repository>

Exact Ref Equality

git -C <source-repository> for-each-ref \
  --format='%(refname) %(objectname)' | sort > source.refs

git -C <target-repository> for-each-ref \
  --format='%(refname) %(objectname)' | sort > target.refs

diff -u source.refs target.refs

Object Integrity

git -C <target-repository> fsck --no-dangling

An old commit-graph cache may reference objects that no longer exist. Do not delete Git objects as a “repair.” Preserve the old cache directory first, then rebuild the commit graph from currently reachable refs.

Finally, update project activity timestamps and clear the Rails cache so that the home page does not continue to show the timestamp of the initial backup.

Step 10: Preserve the Original IP and Align Node Identity with It

To avoid changing every developer workstation, Jenkins job, and historical repository URL, the final service kept the original GitLab IP.

The cutover sequence was:

  1. Scale the GitLab StatefulSet to 0.
  2. Confirm that the old server is write-frozen, powered off, and no longer answers on the original IP.
  3. Change the target Kubernetes node’s hostname and management IP to their final values.
  4. Run kubeadm reset, then rejoin the cluster under the final node name.
  5. Restore the GitLab-specific labels and taints.
  6. Rebind the local PV.
  7. Scale the StatefulSet back to 1.
  8. Validate HTTP, SSH, Gitaly, the database, and repositories.
sequenceDiagram
  participant Old as Old GitLab
  participant API as Kubernetes API
  participant Node as New GitLab node
  participant GitLab as GitLab 19

  Old->>Old: Freeze HTTP and SSH Git writes
  Old->>Node: Synchronize final repository delta
  Old->>Old: Power off and release the service IP
  Node->>Node: Change hostname and static IP
  Node->>API: kubeadm join --node-name <final-node>
  API->>Node: Restore labels and taints
  API->>GitLab: Bind PV and start StatefulSet
  GitLab->>GitLab: Validate HTTP, SSH, database, and repositories

There is an important Kubernetes trap here: a PV’s nodeAffinity is immutable. You cannot patch it after renaming the node.

The correct procedure is:

  1. Keep the GitLab Pod stopped.
  2. Confirm that the PV reclaim policy is Retain.
  3. Delete the PVC and PV objects.
  4. Keep the actual /data/gitlab directory on the host.
  5. Recreate the PV and PVC with the new node name, pointing to the same directory.
  6. Start GitLab only after the PVC becomes Bound.

This deletes Kubernetes metadata, not repository data. Before proceeding, verify again that the Pod is stopped, the host path is correct, and the reclaim policy is correct.

Never power the old server back on while it still owns the original IP. Disconnect its virtual NIC at the hypervisor first, then reinstall it or assign a released address from the console before reconnecting the network. Otherwise, you create an IP conflict.

Step 11: Final Acceptance Must Go Beyond Pod Ready

We divided final acceptance into six layers.

Kubernetes Layer

kubectl get node <gitlab-node> -o wide
kubectl -n <namespace> get pod gitlab-0 -o wide
kubectl -n <namespace> get pvc
kubectl get pv

Confirm that:

  • Node name, InternalIP, and hostname agree.
  • The Pod runs on the intended node and has not restarted.
  • The PVC is Bound.
  • The PV uses Retain, and its nodeAffinity points to the final node.

GitLab Service Layer

gitlab-ctl status
gitlab-rake gitlab:check SANITIZE=true

Check GitLab Shell, Gitaly, Sidekiq, Redis, database migrations, upload permissions, and hashed storage.

Database Layer

  • Core object counts match the frozen source.
  • PostgreSQL runs the target version.
  • Every schema migration is complete.
  • The unfinished batched background migration count is zero.
  • gitlab:doctor:secrets can decrypt critical data.

Repository Layer

  • Refs match exactly for every repository with delta changes.
  • git fsck --no-dangling passes.
  • Sample clone, fetch, push, and merge operations succeed.

HTTP and SSH Layer

curl -fsS http://<gitlab-host>/users/sign_in >/dev/null
ssh -T git@<gitlab-host>

Real Workflow Layer

  • Jenkins can fetch source and publish statuses.
  • Webhooks are delivered successfully.
  • Runners can claim jobs.
  • CI/CD variables can be decrypted.
  • User login, 2FA, and personal access tokens work.

The migration is complete only after all six layers pass.

Rollback Strategy

Do not delete the old server, old PostgreSQL directories, or intermediate images immediately after cutover.

Retain at least:

  • The old GitLab VM, powered off and disconnected.
  • The last verified full GitLab backup.
  • Database dumps and configuration archives from every critical major release.
  • Old PostgreSQL data directories.
  • The final complete GitLab 18 restore point.
  • The GitLab 19 database-protection backup.
  • The exact GitLab and PostgreSQL images and digests used during the upgrade.
  • The final changed-repository list and ref comparison results.

Rollback is layered as well:

  1. Entry-point failure with healthy data: switch back to the old entry point.
  2. GitLab Pod failure: restore the previous image and matching database state.
  3. PostgreSQL failure: switch back to the retained old data directory.
  4. Data-integrity failure: stop writes to the new instance, restore the last complete backup, and recalculate the delta.

No rollback should ever leave the old and new systems accepting writes simultaneously.

The Most Important Lessons

1. The Smallest GitLab Upgrade Unit Is “Version + Database + Background Migrations”

Pod Ready only means the process passed its probe. A stop is truly complete when the version is correct, the database is supported, regular and background migrations are complete, backups are restorable, and real requests pass.

2. Moving to Kubernetes Does Not Create High Availability

A single-replica GitLab with a local PV remains a single-node stateful service. Kubernetes provides declarative deployment, probes, scheduling, resource controls, and a unified operational interface; it does not turn local storage into highly available storage.

3. A Successful Initial Restore Does Not Mean You Can Cut Over

As long as the old instance stays open, audit the final delta separately across database objects, Git repositories, LFS/artifacts/uploads, and configuration.

4. Preserving the Original IP Reduces Client Changes but Requires Correct Node Identity

Keep the IP, hostname, Kubernetes Node name, and PV nodeAffinity aligned whenever possible. Otherwise, incident response six months later begins with explaining why one address maps to a differently named node.

5. Do Not Clean Up Rollback Points Early

The most dangerous cleanup steps often look perfectly reasonable: delete old PostgreSQL directories, release the old VM, clear intermediate images, or remove full backups. Wait until business acceptance and the observation period have both ended.

Conclusion

The time-consuming part of upgrading GitLab 14.9.3 to 19.2.1 was not downloading twenty images. It was stopping at every version long enough to verify the system.

A reliable migration path can be summarized as:

Inventory
→ Same-version restore
→ Required upgrade stops
→ Finish background migrations at every stop
→ Upgrade PostgreSQL in stages
→ Create rollback points at every stop
→ Freeze the old instance
→ Synchronize the final delta
→ Validate refs and objects
→ Preserve the original entry point and cut over
→ Run six-layer acceptance
→ Clean up only after the observation period

The wider the infrastructure version gap, the less you can rely on the luck of a single successful start. Treat every phase as an independent step with defined inputs, outputs, acceptance criteria, and rollback, and the upgrade becomes controllable.
