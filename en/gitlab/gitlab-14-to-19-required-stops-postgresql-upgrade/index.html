GitLab 14 to 19 Migration, Part 2: Required Upgrade Stops, Background Migrations, and PostgreSQL 17

A field report on GitLab background-migration state mistakes, historic partition failures, and the staged move from PostgreSQL 14 to 17.

lucaslzAuthor
August 9, 2026 5 min read
#GitLab #PostgreSQL #DevOps #Database Migration
{ }

This is part two of the GitLab CE 14.9.3 to 19.2.1 series. Read Part 1 for the platform and upgrade cadence, and Part 3 for the final freeze, delta synchronization, and rollback.

The most misleading cross-version-upgrade signal is “the Pod is Ready.” What actually controls the next stop is whether ordinary schema migrations, batched background migrations, the database support matrix, and a recoverable backup are all in place.

A required upgrade stop is a gate, not a list of tags

GitLab requires specific required upgrade stops. At each one, use the latest patch in that minor, complete migrations, and read that version’s release guidance. We treated every stop as a small change window: inspect migrations, create a rollback backup, replace and explicitly recreate the Pod, observe reconfigure, Puma, Sidekiq, Gitaly, and the database, then run gitlab:check, object counts, and HTTP/SSH smoke tests.

This feels slower, but it confines failure to two neighbouring versions. Investigation can return to the previous image, database dump, and configuration instead of guessing across the difference between 14.x and 19.x.

The most dangerous false alarm: finalized reported as unfinished

An old script counted unfinished work with:

WHERE status <> 3

After GitLab 17, status 6 also means finalized. The old condition reports completed migrations as failures and may drive an operations script toward a migration class that no longer exists in the current version.

Use this safer SQL, or preferably the current GitLab version’s model and Rake tasks:

SELECT id, job_class_name, table_name, status
FROM batched_background_migrations
WHERE status NOT IN (3, 6);
gitlab-rails runner '
puts Gitlab::Database::BackgroundMigration::BatchedMigration.unfinished.count
'
gitlab-rake gitlab:background_migrations:list
gitlab-rake gitlab:background_migrations:status

Do not mark a job finished merely to make a number become zero. Inspect the parent migration, child jobs, source data, and current implementation first. Only with a complete backup and proof that the logic does not apply to the present data should you use an official finalize or execute task for that release.

How historic data blocked a migration

One background job processed historic notification data whose timestamp predated the available monthly partitions. Creating fake business data or skipping the job would both corrupt the upgraded state.

Our sequence was to locate the exact migration, child job, and record; verify whether it still had a valid business relation; check the target partition boundary and current migration logic; create a fallback partition for legitimate historic data while writes were stopped and backup was available; then rerun or finalize via the official task and recheck migration and data integrity.

The lesson is not “add a partition.” Background migrations are connected to business data. First establish that the record is legitimate and the action reversible, then use the current version’s supported tool.

A GitLab 19 reconfigure failure is not automatically a Secret failure

The first reconfigure from GitLab 18 to 19 exited because of residual historical component state. Deleting the entire Secret would have destroyed evidence and possibly encryption material. We preserved the backup and differentiated three situations: a configuration block removed by the new version, a damaged or missing Secret, and database values that cannot be decrypted by the current Secret.

Only after confirming the first case did we start again; schema migration then completed normally. Configuration, Secret, and decryption problems may all look like startup failure, but their remedies are entirely different.

PostgreSQL has to move with GitLab

GitLab and PostgreSQL cannot be upgraded independently. Our staged plan was bundled PostgreSQL at GitLab 14/15, external PostgreSQL 14 during GitLab 16, PostgreSQL 14 to 16 before GitLab 18, PostgreSQL 16 to 17 before GitLab 19, and external PostgreSQL 17 at the final GitLab 19.2 stop.

The application explicitly disables bundled PostgreSQL and uses a separate database, account, and Secret:

postgresql['enable'] = false
gitlab_rails['db_adapter'] = 'postgresql'
gitlab_rails['db_host'] = 'postgresql.<namespace>.svc.cluster.local'
gitlab_rails['db_port'] = 5432
gitlab_rails['db_database'] = 'gitlabhq_production'
gitlab_rails['db_username'] = 'gitlab'
gitlab_rails['db_password'] = File.read('/run/secrets/gitlab-db/password').strip

Run a check before a PostgreSQL major upgrade:

pg_upgrade \
  --old-datadir=<old-data> --new-datadir=<new-data> \
  --old-bindir=<old-bin> --new-bindir=<new-bin> --check

Our XFS volume supported reflinks, so the actual upgrade used --clone --jobs=4 to avoid another full database copy:

pg_upgrade \
  --old-datadir=<old-data> --new-datadir=<new-data> \
  --old-bindir=<old-bin> --new-bindir=<new-bin> \
  --clone --jobs=4

--clone saves space and time; it is not a backup. Keep old data directories, the full GitLab 18 restore point, and the GitLab 19 database-protection backup through final cutover and the observation period. Follow with vacuumdb --all --analyze-in-stages --jobs=4 and verify the real connection target and database version from GitLab Rails.

When disk space is tight, define the recovery boundary

At the final version, disk space could not hold another complete repository archive. We documented the boundary instead: a database-protection backup at the current point, plus an already-verified full backup, repository volume, and configuration archive from the preceding critical point. A database-only backup must never be mistaken for a complete restore point.

After migrations reach zero and the support matrix is satisfied, the old GitLab can still accept writes. The last step is a controlled final delta cutover: Part 3: Kubernetes Final Delta Cutover, Stable IP, and Rollback.
