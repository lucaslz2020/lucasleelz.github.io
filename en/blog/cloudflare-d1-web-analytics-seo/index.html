Analytics and SEO for a Static Blog: Cloudflare Web Analytics + D1

Add Cloudflare Web Analytics, Pages Functions, and D1 to an Astro static blog, with Canonical, Open Graph, JSON-LD, Sitemap, and automated SEO checks.

After moving the blog to Astro and Cloudflare Pages, the pages were light enough to deploy entirely as static files. But a site built for long-term writing still needs to answer two more questions: whether articles are actually being read, and whether search engines understand the content correctly.

At first I considered embedding an in-memory database in the project. That approach might work as a temporary cache for an ordinary server program, but it isn’t suited to static sites and serverless runtimes: static files have no long-running process, and Pages Functions instances can be created and recycled at any time. Counts kept in memory can’t be persisted, nor can they be shared across instances.

In the end I used Cloudflare Web Analytics + Pages Functions + D1: Web Analytics handles site-level traffic trends, D1 handles article read counts and custom click events, and I rounded out the setup with SEO metadata, structured data, and build-time checks. This article documents the complete design, implementation, launch, and troubleshooting process.

If you’d like to understand the blog’s stack choices, dual-repo publishing, and domain migration first, read the previous post: Rewriting a Personal Blog from Scratch: Astro + React + MDX + Cloudflare Pages.

Final Architecture

This analytics setup doesn’t turn the blog into a dynamic site. Articles, the homepage, archives, and tags are still built by Astro into static HTML; only /api/analytics is handled by Pages Functions.

flowchart LR
  A[Visit lucaslz.com] --> B[Cloudflare CDN]
  B --> C[Astro static pages]
  B --> D[Web Analytics]
  C --> E[Frontend analytics script]
  E --> F[/api/analytics<br/>Pages Functions]
  F --> G[(Cloudflare D1)]
  H[GitHub Actions] --> I[Build and SEO checks]
  I --> B

The two analytics systems answer different questions:

Web Analytics observes the whole site; D1 answers specific questions about content and interactions. They aren’t redundant — they complement each other.

Why Not Use an In-Memory Database

Cloudflare Pages is still mostly static files. Even with Pages Functions, requests run in Worker isolation environments created on demand; you can’t assume a JavaScript variable will stick around.

If you record page views like this:

let views = 0;

export function onRequest() {
  views += 1;
  return Response.json({ views });
}

This approach has three fundamental problems:

  1. The data resets to zero when the instance restarts.
  2. Multiple instances each maintain their own counter.
  3. A new deployment also loses the previous state.

Data in LocalStorage lives only in each visitor’s own browser and can’t be aggregated into a site-wide total. Real persistent storage is required. D1 is Cloudflare’s managed SQLite database that binds directly to Pages Functions, giving the simplest deployment structure.

Controlling Write Volume with Daily Aggregation

Analytics systems easily drift toward a “one row per visit” design, but a personal blog usually doesn’t need visitor-level logs. I care more about how many views an article got on a given day, or how many times an entry point was clicked.

So the schema uses daily aggregation:

CREATE TABLE IF NOT EXISTS event_daily (
  event TEXT NOT NULL,
  path TEXT NOT NULL,
  target TEXT NOT NULL DEFAULT '',
  stat_date TEXT NOT NULL,
  count INTEGER NOT NULL DEFAULT 0 CHECK (count >= 0),
  updated_at TEXT NOT NULL DEFAULT (datetime('now')),
  PRIMARY KEY (event, path, target, stat_date)
) WITHOUT ROWID;

CREATE INDEX IF NOT EXISTS idx_event_daily_date
  ON event_daily (stat_date, event);

The composite primary key is event + path + target + stat_date. On a given day, the same event for the same path and target updates only one row. No IP, User-Agent, full Referer, or user identity is stored.

This design pays off in several ways:

  • Data grows with “pages × events × days” instead of visit count.
  • Summing the daily counts gives cumulative article read counts.
  • No visitor profiles to maintain, and a clearer privacy boundary.
  • Storage and query costs stay manageable even as traffic grows.

The currently allowed events are:

page_view
article_click
article_impression
tag_click
search_click
nav_click
toc_click
cta_click
outbound_click

The Pages Functions Analytics API

After adding functions/api/analytics.js to the project root, Cloudflare Pages maps it to:

GET  /api/analytics?event=page_view&path=/article
POST /api/analytics

GET reads an article’s cumulative read count. POST accepts events and uses an Upsert to update that day’s count:

await env.BLOG_ANALYTICS.prepare(
  `INSERT INTO event_daily
     (event, path, target, stat_date, count, updated_at)
   VALUES (?1, ?2, ?3, ?4, 1, datetime('now'))
   ON CONFLICT (event, path, target, stat_date)
   DO UPDATE SET
     count = count + 1,
     updated_at = datetime('now')`,
)
  .bind(event, path, target, statDate)
  .run();

The API also enforces a few necessary constraints:

  • Only whitelisted events are accepted.
  • Trailing slashes and query parameters are stripped from paths.
  • Request bodies are capped at 2 KB.
  • POST only accepts same-origin requests.
  • External links only store the domain and path, not query parameters.
  • All responses set Cache-Control: no-store.

These restrictions can’t stop all malicious traffic, but they keep the API from becoming an arbitrary string collector and reduce the risk of sensitive query parameters being written to the database.

How the Frontend Records and Displays Data

When the page loads, the analytics component sends a single page_view event to /api/analytics. The API returns the cumulative value right after writing, and article pages then show the read count.

const response = await fetch("/api/analytics", {
  method: "POST",
  headers: { "content-type": "application/json" },
  body: JSON.stringify({
    event: "page_view",
    path: window.location.pathname,
  }),
  credentials: "same-origin",
});

const data = await response.json();
showPageViews(data.total);

To avoid inflating the count on every refresh within a session, the frontend uses sessionStorage to deduplicate page_view and impression events. This read count isn’t a strict unique-visitor metric; it’s a lightweight, explainable session-level reading count.

Click events are sent with navigator.sendBeacon(). When a visitor clicks a link and immediately leaves the page, a Beacon handles that final small payload better than a regular async request.

All tracking points are declared via HTML data-* attributes, so components don’t directly depend on the analytics implementation:

<a
  href={postHref}
  data-analytics-event="article_click"
  data-analytics-target={postHref}
>
  阅读文章
</a>

Creating and Binding D1 in Cloudflare

Once the code is ready, configure the actual database in the Cloudflare dashboard.

1. Create the Database

Navigate to:

Storage & databases
→ D1 SQL Database
→ Create database

Name the database:

lucaslz-blog-analytics

After creation, open the D1 Console and run migrations/0001_analytics.sql from the project; confirm the table and index were created.

2. Bind Pages Functions

Navigate to:

Workers & Pages
→ lucaslz-blog
→ Settings
→ Bindings
→ Add

Select D1 database and enter the variable name:

BLOG_ANALYTICS

Then select the lucaslz-blog-analytics database you just created and save. The variable name must match env.BLOG_ANALYTICS in the code exactly.

3. Redeploy

Here’s an easy-to-miss detail: new bindings only take effect on subsequent deployments. After saving a binding, existing deployments don’t automatically get the new environment.

If the binding is saved but you haven’t redeployed, the endpoint returns:

HTTP/2 503

{"enabled":false}

After triggering a GitHub Actions deployment, Pages Functions can read the D1 binding. Commit a normal change, or create an empty commit when there are no file changes:

git commit --allow-empty -m "chore: redeploy with D1 analytics"
git push origin main

Enabling Cloudflare Web Analytics

D1 isn’t the right place to reimplement a full set of visitor-source, geographic, device, and performance analytics. Cloudflare Web Analytics already provides these site-level metrics without creating a client identifier for every visitor.

In the Cloudflare Dashboard, navigate to:

Analytics
→ Web Analytics
→ Add a site

Enter lucaslz.com. Since the domain already belongs to your Cloudflare account, choose Automatic setup — there’s no need to manually add the Beacon code to the Astro layout.

After setup, the dashboard shows:

Web Analytics are now set up

Data won’t appear in the dashboard right away; after enabling it for the first time, wait for Cloudflare to collect and process visit data. See the official docs: Cloudflare Web Analytics.

Filling In SEO Systematically

Analytics only tells me whether content is visited; SEO determines how search engines and social platforms understand, index, and display pages. Rather than just adding a few <meta> tags, BaseLayout now generates the page semantics uniformly.

Base Metadata

Every page now includes:

  • A unique <title> and description.
  • An absolute Canonical pointing at https://lucaslz.com.
  • robots indexing directives.
  • zh-CN and x-default hreflang.
  • RSS and Web App Manifest links.
  • Open Graph and Twitter Card.
  • An absolute share image URL at 1200 × 630.

Canonical is generated from the current path and the fixed production domain, so pages.dev preview URLs aren’t treated as a second copy of the content:

const canonical = new URL(Astro.url.pathname, Astro.site ?? SITE.url);

JSON-LD Structured Data

Regular pages emit Person and WebSite. Article pages additionally emit:

  • BlogPosting
  • BreadcrumbList
  • Publish and update times
  • Author, tags, keywords, and word count
  • The main page and share image

JSON-LD is generated by serializing objects rather than hand-writing JSON strings; after serialization, < is escaped so article content can’t break the script boundary.

Sitemap, RSS, and robots.txt

Astro generates the sitemap at build time, and the article collection also generates RSS. robots.txt points to the production sitemap. That way, adding a new Markdown article doesn’t require maintaining a URL list by hand.

Making SEO a Build Gate

The thing SEO fears most is fixing an issue once and then overlooking it when the next page is added. So I added scripts/check-seo.mjs, which scans every HTML file in dist/ and checks:

  • Page title and description.
  • Whether Canonical uses the production domain.
  • robots directives.
  • Absolute Open Graph images.
  • Exactly one H1 per page.
  • Whether JSON-LD is valid JSON.
  • Whether article pages have BlogPosting and BreadcrumbList.

The analytics endpoint also has standalone tests covering normal writes, reads, invalid events, cross-origin requests, and OPTIONS responses.

The release order in GitHub Actions is now:

Astro check
→ Astro build
→ 站内链接检查
→ SEO 检查
→ Analytics 接口测试
→ 同步 GitHub Pages 镜像
→ 部署 Cloudflare Pages

If any step fails, the production deployment stops.

After deployment, first read a page that has no data yet:

curl \

When the endpoint works, it returns:

{
  "event": "page_view",
  "path": "/howtostudy",
  "total": 0
}

Then open the article or send a same-origin POST; the response status should be 201:

{
  "ok": true,
  "event": "page_view",
  "path": "/howtostudy",
  "total": 1
}

After refreshing the article page, the read count appears below the title:

7 分钟阅读 · 1 次阅读

Finally, check the aggregated results in the D1 Console:

SELECT
  event,
  path,
  target,
  SUM(count) AS total
FROM event_daily
GROUP BY event, path, target
ORDER BY total DESC;

Common Issues

The Endpoint Returns 503

{"enabled":false} means the Function is live, but the current deployment doesn’t have BLOG_ANALYTICS. Check the production binding and redeploy after saving.

The Endpoint Returns 500

Usually the database is bound but the migration hasn’t been run, so the event_daily table doesn’t exist. Run the migration in the D1 Console, then check the Function logs for SQL errors.

The Page Doesn’t Show the Read Count

Check in order:

  1. Whether the current domain is lucaslz.com, www.lucaslz.com, or pages.dev.
  2. Whether the GET endpoint returns 200 with a numeric total.
  3. Whether the article page has a data-page-views element.
  4. Whether the browser console shows CSP, network, or script errors.

Read Count and Web Analytics Don’t Match Exactly

This is expected. D1’s page_view is deduplicated within the same browser session, while Web Analytics has its own visitor, bot-filtering, and data-processing rules. The two metrics are defined differently, so don’t force the numbers to match.

Privacy and Cost Boundaries

This implementation deliberately does not store:

  • IP addresses
  • User-Agent
  • Cookie identifiers
  • User accounts
  • Full Referer
  • URL query parameters

D1 only holds the event, normalized path, target, date, and count. With Web Analytics and custom events handling separate concerns, there’s no need to load a heavy third-party analytics SDK into every page.

D1’s free tier and specific limits may change, so refer to the Cloudflare D1 pricing documentation. Compared with recording a row per visit, daily aggregation significantly reduces the number of rows and the amount of data read — a better fit for a personal blog.

The End Result

After this overhaul, the blog stays static-first:

Astro 静态内容
  ├─ Cloudflare Web Analytics：全站趋势与性能
  ├─ Pages Functions：轻量统计 API
  ├─ D1：文章阅读量与自定义事件
  └─ SEO：元数据、结构化数据与自动检查

The most important thing isn’t an extra visit number; it’s a feedback loop that’s maintainable over the long term: search engines understand the articles more accurately, I can see which content is actually read, and the build pipeline keeps future pages from easily losing the SEO baseline.

For a static personal blog, this covers most real-world needs without introducing a long-running server, an in-memory database, or a complex user-tracking system.
