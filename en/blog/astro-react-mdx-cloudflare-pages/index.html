Rewriting My Personal Blog from Scratch: Astro + React + MDX + Cloudflare Pages

My blog had worked fine for years, but it no longer felt like a place I wanted to keep writing: the pages leaned toward a documentation site, the mobile experience was mediocre, and the relationship between source code, build output, and deployment platform was unclear.

This time, instead of patching the old project again, I rewrote the blog from scratch. The final stack is Astro + React + MDX. The source lives in a private GitHub repository, and GitHub Actions builds it and publishes it to both a GitHub Pages mirror repository and Cloudflare Pages. Cloudflare manages DNS for lucaslz.com, which serves as the official entry point.

This article documents the complete process: tech stack selection, project structure, automated deployment, DNS switching, and troubleshooting.

The goals

Before rewriting, I set the constraints to avoid flip-flopping between frameworks:

  • The blog should look good first — not like an API reference.
  • It should work on phones, tablets, and desktops out of the box.
  • Posts are written in Markdown or MDX.
  • Keep using React, but don’t introduce a full server-side framework for purely static content.
  • Keep the source repository private; the built static files may be public.
  • Pushing to main automatically builds, checks, and deploys.
  • Maintain no servers; use free static hosting and a CDN where possible.
  • lucaslz.com is always the single official address.

The final publishing pipeline looks like this:

Why Astro + React + MDX

Astro handles static content

A blog is its posts. A post shouldn’t need React to re-run in the browser before it displays, so static generation fits better than full client-side rendering.

Astro generates HTML at build time and, by default, sends no unnecessary JavaScript to the browser. Its Content Collections validate post frontmatter, dynamic routes generate post pages consistently, and RSS, Sitemap, and SEO metadata are all produced at build time.

For this project, the build output is a dist/ directory with no Node.js server dependency, so it deploys to Cloudflare Pages and can also sync to GitHub Pages.

React only handles interaction

Keeping React doesn’t mean turning the whole blog into an SPA. The current project only uses React Islands where interaction is needed:

  • Site search
  • Dark mode toggle
  • Mobile navigation

Mermaid diagrams are handled by a separate on-demand script that downloads the renderer only when a diagram approaches the viewport. Astro outputs post bodies, homepage cards, archive, and tag pages directly as HTML. This keeps the React development experience while keeping client-side script size under control.

MDX handles expressiveness

Regular posts stay in Markdown; use MDX when you need components or complex interactions. Both are managed by the same content collection, so a few advanced posts don’t force the whole site to give up simplicity.

The key dependencies are:

{
  "dependencies": {
    "astro": "7.1.6",
    "@astrojs/mdx": "7.0.5",
    "@astrojs/react": "6.0.2",
    "react": "19.2.8",
    "react-dom": "19.2.8"
  }
}

For a purely static Astro project, deploying to Pages doesn’t require the @astrojs/cloudflare adapter; you only need it when using Cloudflare’s server runtime or SSR.

Content model and project structure

Blog content lives under src/content/blog/, and the file path directly determines the final URL. For example:

src/content/blog/
├── blog/
│   └── astro-react-mdx-cloudflare-pages.md
├── css/
├── foundation/
├── java/
└── react/

Post frontmatter is validated with Zod, so a wrong date, tag, or draft status doesn’t slip into production:

const blog = defineCollection({
  loader: glob({
    base: "./src/content/blog",
    pattern: "**/*.{md,mdx}",
  }),
  schema: z.object({
    title: z.string(),
    description: z.string(),
    date: z.coerce.date(),
    author: z.string().default("lucaslz"),
    tags: z.array(z.string()).default([]),
    featured: z.boolean().default(false),
    draft: z.boolean().default(false),
  }),
});

Publishing a post is just adding a Markdown file. The homepage, archive, tags, search index, RSS, and Sitemap all update automatically at build time.

Mobile isn’t an afterthought

This rewrite was designed around small screens from the start, instead of building desktop-first and squeezing it down later:

  • Every page sets the correct viewport.
  • Breakpoints follow content width, not specific phone models.
  • Post font sizes and spacing use clamp() for continuous scaling.
  • Touch targets are no smaller than common mobile touch sizes.
  • Desktop navigation becomes a drawer menu on small screens.
  • Code blocks scroll horizontally instead of breaking the post container.
  • Tables, images, Mermaid diagrams, and long URLs all have overflow protection.
  • Both light and dark system themes are supported.

A static page isn’t necessarily a simple page. Mobile experience depends more on layout, typography, touch areas, and asset size than on which JavaScript framework you use.

Why two GitHub repositories

The lucaslz-blog source repository is private and holds post sources, Astro configuration, and GitHub Actions workflows. The other repository, lucasleelz.github.io, only stores the built static files.

Splitting them has three benefits:

  1. Writing and engineering configuration stay private.
  2. The GitHub Pages repository still works as a public, rollback-capable static mirror.
  3. Cloudflare Pages and GitHub Pages use the same dist/, so there’s no duplicated build logic.

Build output isn’t source code, so don’t maintain dist/ manually in the source repository. CI should regenerate it on every run.

GitHub Actions automated publishing

The workflow only listens to main. Every push runs installation, type checking, a static build, internal link checks, and publishing in sequence.

Here’s a simplified version of the core structure:

name: Build and publish site

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  deployments: write

concurrency:
  group: publish-production
  cancel-in-progress: false

jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout source
        uses: actions/checkout@v6

      - name: Setup pnpm
        uses: pnpm/action-setup@v4

      - name: Setup Node
        uses: actions/setup-node@v6
        with:
          node-version: 24
          cache: pnpm

      - name: Install dependencies
        run: pnpm install --frozen-lockfile

      - name: Build site
        run: pnpm run build

      - name: Check internal links
        run: pnpm run check:links

Syncing the GitHub Pages mirror

The source repository gets write access to the static repository through a dedicated Deploy Key. The workflow checks out the target repository, then uses rsync --delete to make the target branch exactly match this dist/:

- name: Checkout Pages repository
  uses: actions/checkout@v6
  with:
    repository: lucaslz2020/lucasleelz.github.io
    ref: master
    ssh-key: ${{ secrets.PAGES_DEPLOY_KEY }}
    path: publish

- name: Copy static files
  run: rsync -a --delete --exclude=.git dist/ publish/

- name: Publish generated site
  working-directory: publish
  run: |
    git config user.name "github-actions[bot]"
    git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
    git add --all
    if git diff --cached --quiet; then
      exit 0
    fi
    git commit -m "deploy: ${GITHUB_SHA}"
    git push origin HEAD:master

Confirm whether the target repository actually uses main or master. If the branch name is wrong, the build succeeds but the publish step fails.

Publishing to Cloudflare Pages

The Cloudflare Pages project uses Direct Upload: GitHub Actions performs the custom build and uploads dist/. Cloudflare’s official docs also describe this approach for custom CI platforms.

- name: Deploy to Cloudflare Pages
  uses: cloudflare/wrangler-action@v3
  with:
    apiToken: ${{ secrets.CLOUDFLARE_API_TOKEN }}
    accountId: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
    command: >-
      pages deploy dist
      --project-name=lucaslz-blog
      --branch=main
    gitHubToken: ${{ secrets.GITHUB_TOKEN }}

In the production workflow, I also pin third-party Actions to full commit SHAs and keep the corresponding version in comments, reducing supply chain risk from upstream tags being changed unexpectedly.

Least-privilege credentials

Automated deployment needs write access in two directions, but that doesn’t mean reusing a personal SSH key or a global admin token.

GitHub Pages Deploy Key

  • Generate a dedicated SSH key pair.
  • Add only the public key to the static publishing repository with write access enabled.
  • Store the private key as the PAGES_DEPLOY_KEY secret in the source repository.
  • Delete the local temporary private key copy after confirming deployment works.

Cloudflare API Token

  • Create a custom API Token instead of using the Global API Key.
  • Grant Pages write access only for the target account.
  • Store the token in CLOUDFLARE_API_TOKEN.
  • Store the Account ID in CLOUDFLARE_ACCOUNT_ID.
  • Never expose the token itself in terminal output, build logs, screenshots, or articles.

If a token has ever appeared in logs or tool output, don’t just delete the logs: revoke the old token immediately, generate a new one, and overwrite the GitHub secret.

GitHub also recommends granting credentials only the minimum permissions needed for the task, preferring Deploy Keys, GitHub Apps, or dedicated service identities over long-lived personal credentials. See: GitHub Actions Secrets.

Switching from Vercel to Cloudflare Pages

The part most likely to break during migration isn’t the build — it’s the order of operations.

My domain initially still had a root A record pointing to Vercel. After I deleted the Vercel project, visiting the domain returned:

404: NOT_FOUND
Code: DEPLOYMENT_NOT_FOUND

This error doesn’t mean the Cloudflare Pages deployment failed. It means DNS was still routing requests to the deleted Vercel deployment.

A safer order is:

  1. First, create and verify the Cloudflare Pages pages.dev address.
  2. Add the domain in Cloudflare and review the auto-scanned DNS records.
  3. Confirm no mail records such as MX, SPF, DKIM, or DMARC are missing.
  4. Switch the authoritative nameservers to Cloudflare at the registrar.
  5. Wait for the Cloudflare zone to activate.
  6. Bind the root domain under Custom domains in the Pages project.
  7. After confirming HTTPS and the main pages work, clean up the old platform configuration.

This domain had no mail records, so the switch was relatively simple. If a domain also carries email, APIs, or other subdomains, you must migrate the full DNS first — don’t focus only on the blog’s A/CNAME records.

Changing nameservers at Alibaba Cloud

The registrar is Alibaba Cloud, and the original authoritative nameservers are HiChina. Once Cloudflare assigns two nameservers for the zone, go to the Alibaba Cloud domain console:

域名详情 → DNS 管理 → DNS 修改 → 修改 DNS 服务器

Enter the two nameservers Cloudflare assigned, complete SMS verification, and save.

Switching nameservers is a high-impact network change. Before submitting, at least confirm:

  • All existing records in the Cloudflare zone are complete.
  • DNSSEC is in a compatible state; if needed, disable the old provider’s DNSSEC first and let Cloudflare enable it after activation.
  • The domain doesn’t depend on unmigrated email, API, or verification records.
  • Old DNS TTLs won’t leave caches stale for too long.

The Cloudflare console may show Initializing or Verifying for a while. Don’t delete and recreate records just because the status hasn’t turned Active yet; verify the real result from both public DNS and HTTPS.

Binding the root domain

Once the zone is active, go to the Cloudflare dashboard:

Workers & Pages
→ lucaslz-blog
→ Custom domains
→ Set up a custom domain

Enter lucaslz.com. Cloudflare replaces the old root record with one pointing to lucaslz-blog.pages.dev and handles root-domain CNAME Flattening, proxying, and certificate issuance.

The final status should show:

lucaslz.com  Active
SSL enabled

The GitHub Pages mirror repository no longer keeps a CNAME file, so the two hosting platforms don’t both claim the same official domain.

Post-launch verification checklist

Don’t just trust the green status in the console. After publishing, check at least the following:

# 权威名称服务器
dig NS lucaslz.com

# HTTPS、跳转与响应头
curl -I -L https://lucaslz.com/

# 关键页面
curl -I -L https://lucaslz.com/archive/
curl -I -L https://lucaslz.com/tags/

# RSS 与 Sitemap
curl -I https://lucaslz.com/rss.xml
curl -I https://lucaslz.com/sitemap-index.xml

You should also verify in the browser:

  • Homepage, post pages, archive, and tags.
  • Navigation, search, and code blocks at phone width.
  • Light and dark themes.
  • The 404 page.
  • Canonical, Open Graph, RSS, and Sitemap URLs.
  • The footer shows the correct deployment platform.

After this launch, the homepage, archive, and post routes all returned 200, the server response header is cloudflare, and the Cloudflare Pages console shows Active · SSL enabled.

Lessons worth keeping

Validate the temporary domain before touching production DNS

pages.dev is the best isolated validation entry point. Don’t switch the official domain until the temporary domain passes build, link, and page checks.

Source deployment and artifact publishing are two different things

The private source repository handles writing and building; the public Pages repository only stores artifacts. Connecting them with GitHub Actions is more stable than copying dist/ manually and easier to audit.

Confirm DNS before deleting the old platform

If the old project is deleted before DNS is switched, you get an immediate platform 404. For production migration, prepare the new environment first, then switch traffic, and clean up the old environment last.

The right response to a leaked secret is rotation

“Not visible in the UI” doesn’t mean “the credential is safe.” Once a credential may have been read, revoke it, recreate it, update the secret, and remove local copies you no longer need.

CI must include checks beyond the build

A successful static build doesn’t mean the site works. Type checks, content schema validation, internal link checks, and an online smoke test should all be part of the release gate.

The result

The new blog has no running application server and no runtime database. Day-to-day publishing is just:

写 Markdown / MDX
→ 本地预览
→ git push main
→ GitHub Actions 构建与检查
→ 同步 GitHub Pages 镜像
→ 部署 Cloudflare Pages
→ lucaslz.com 自动更新

Astro turns content into the lightest possible static pages, React handles only the interactions that are genuinely needed, GitHub Actions makes publishing repeatable, and Cloudflare Pages provides the CDN, HTTPS, and official domain.

For a personal technical blog, this setup is simple enough and leaves room for long-term evolution. More importantly, it gives the time spent maintaining the deployment environment back to writing.
