Spring Boot 3 Container-Start-Postmortem: Verzeichnisse, veraltete Properties, Logging, Treiber

Von der UnsatisfiedDependencyException zu mkdir failed: Cache-Verzeichnis, server.use-forward-headers, commons-logging, nacos-logback.xml, leerer Class.forName.

lucaslzAutor
8. August 2026 10 Min. Lesezeit
#Spring Boot #Java #Nacos #Kubernetes #Postmortem
{ }

Dieser Artikel entstand im Rahmen eines Rolling Release eines Spring Boot 3-Dienstes. Klassennamen, Dienstnamen, Pfade und Geschäftskonfiguration wurden verallgemeinert. Navigation zur Serie: Kubernetes-Neuaufbau-Migrationsreihe.

Nach dem einheitlichen Deployment erschienen im Startlog gleichzeitig fünf Arten von Meldungen:

UnsatisfiedDependencyException ... Factory method threw: mkdir failed

failed to create cache dir: /root/nacos/naming/.../failover

server.use-forward-headers is no longer supported

please remove commons-logging.jar from classpath

Could not initialize Logback Nacos logging from classpath:nacos-logback.xml

java.lang.ClassNotFoundException:
  at java.lang.Class.forName(...)

Alles auf „das Deployment war kaputt“ zu schieben, wäre nicht korrekt; alles als harmlose Warnungen abzutun, ist ebenfalls riskant. Die Situation betrifft vier Ebenen:

EbeneTypisches ProblemKann den Start blockieren?
DateisystemSDK kann Cache- oder Checkpoint-Dateien nicht anlegenJa
KonfigurationsmigrationAlte Properties werden vom Migrator temporär gemapptMeistens nein
classpathDoppelte Logging-Bridge, inkompatible Logback-VersionJe nach Komponente
GeschäftscodeLeerer String wird an Class.forName übergebenJa oder latentes Risiko

Die richtige Reihenfolge der Fehlersuche

flowchart TD
  A["Spring Boot Start fehlgeschlagen"] --> B["Ab der untersten Exception nach oben lesen"]
  B --> C{"Was ist die tiefste Cause"}
  C --> D["IOException / mkdir"]
  C --> E["NoClassDefFound / ClassNotFound"]
  C --> F["Properties migration"]
  C --> G["Logging warning"]
  D --> H["UID, HOME, Mounts und Berechtigungen prüfen"]
  E --> I["Aktive Konfiguration und Dependency-Baum prüfen"]
  F --> J["Konfigurations-Key ersetzen"]
  G --> K["Logging-Bridge entfernen oder Adapter ergänzen"]

UnsatisfiedDependencyException ist oft nur der äußerste Wrapper: Der Controller hängt vom Service ab, der Service vom FileManager, und weil der FileManager beim Erzeugen kein Verzeichnis anlegen kann, lässt sich der Controller am Ende nicht injizieren.

Nur weil ein Bean im ersten Stacktrace-Abschnitt auftaucht, sollte man es nicht vorschnell ändern.

Vorfall 1: mkdir ist die Ursache der UnsatisfiedDependencyException

Äußere Logs:

Error creating bean with name 'voucherController'
Unsatisfied dependency expressed through constructor parameter 0

Weiter nach unten:

Error creating bean with name 'fileManager'
Factory method 'fileManager' threw exception with message: mkdir failed

Ganz unten:

Caused by: java.io.IOException: mkdir failed
  at ...FileRecorder.<init>(...)

Das zeigt:

  • Die Spring-DI selbst ist nicht defekt.
  • Controller- und Service-Konstruktoren sind nicht die eigentliche Ursache.
  • Das Datei-SDK eines Drittanbieters kann bei der Bean-Initialisierung das Verzeichnis für Checkpoint-Aufzeichnungen nicht anlegen.

Zum Prüfen mit demselben Image und Sicherheitskontext in den Container gehen:

id
printf 'HOME=%s\n' "$HOME"
java -XshowSettings:properties -version 2>&1 | grep 'user.home'
mount
ls -ld /root /tmp /data/java/logs
touch /tmp/write-test

Dass der Container mit root-UID läuft, bedeutet nicht, dass jeder Pfad beschreibbar ist: read-only root filesystem, Volume-Berechtigungen, Mount-Overlays und die vom SDK gewählten Standardpfade beeinflussen das Ergebnis.

Vorfall 2: Warum schreibt Nacos plötzlich nach /root/nacos

Der Nacos Client speichert naming failover, Snapshots oder Logs. Die Pfadberechnung kann von Folgendem abhängen:

  • HOME.
  • Java user.home.
  • Nacos’ JM.SNAPSHOT.PATH.
  • Nacos’ JM.LOG.PATH.

Das alte Deployment erlaubte das Schreiben nach /root, daher blieb das Problem lange verborgen. Nachdem die Sicherheitsbaseline verschärft oder der Image-Benutzer geändert wurde, meldet der Start-Thread:

failed to create cache dir: /root/nacos/naming/<namespace>/failover

Der Fix: Dem Client ein explizites, kontrolliertes, beschreibbares Verzeichnis geben:

volumeMounts:
  - name: tmp-volume
    mountPath: /tmp

env:
  - name: HOME
    value: /tmp
  - name: JDK_JAVA_OPTIONS
    value: >-
      -Duser.home=/tmp
      -DJM.SNAPSHOT.PATH=/tmp
      -DJM.LOG.PATH=/data/java/logs/nacos

volumes:
  - name: tmp-volume
    emptyDir:
      sizeLimit: 2Gi

Das Startskript legt die Verzeichnisse vorab an und bricht bei Fehlern ab:

mkdir -p /tmp/nacos /data/java/logs/nacos
test -w /tmp
test -w /data/java/logs/nacos

Ein Cache-Verzeichnisproblem sollte man nicht lösen, indem man alle Capabilities wiederherstellt oder das gesamte Root-Dateisystem beschreibbar macht.

Außerdem ist zwischen den Schweregraden zu unterscheiden:

  • Schlägt das Nacos-failover-Backup fehl, funktioniert der Hauptregistrierungsablauf manchmal noch, aber die Disaster-Recovery-Fähigkeit nimmt ab.
  • Schlägt das Datei-SDK während der Bean-Konstruktion mit mkdir failed fehl, startet der Spring Context nicht.

Dass alle Meldungen mit Stufe ERROR geloggt werden, bedeutet nicht, dass ihre Auswirkungen gleich sind; entscheidend ist die Lebenszyklus-Phase, in der die Exception auftritt.

Vorfall 3: server.use-forward-headers ist ein Migrationshinweis

Log:

The use of configuration keys that are no longer supported was found:
server.use-forward-headers
Reason: Replaced to support additional strategies.

Wird während des Upgrades spring-boot-properties-migrator eingebunden, kann die Anwendung weiterhin starten, weil der Migrator die alten Keys temporär mappt. Ersetzt werden sollten sie aber so bald wie möglich:

# 删除
server.use-forward-headers=true

# 根据代理链选择
server.forward-headers-strategy=framework

Die Unterschiede zwischen FRAMEWORK, NATIVE und NONE findest du im Spring-Boot-Leitfaden für Reverse-Proxy.

Der Spring-Boot-Upgrade-Leitfaden stellt klar, dass der Properties-Migrator nur zum Erkennen und vorübergehenden Migrieren umbenannter Properties dient; nach dem Upgrade sollte die Abhängigkeit entfernt werden.

Die Reihenfolge ist also:

  1. Alle Namespaces, Groups und DataIds mit dem alten Key in Nacos suchen.
  2. Durch den neuen Key ersetzen.
  3. Den Dienst per Rolling Release aktualisieren und bestätigen, dass keine Migrationsmeldungen mehr erscheinen.
  4. Den Properties-Migrator aus dem Parent oder der Anwendung entfernen.

Ein Konfigurationsproblem sollte man nicht „lösen“, indem man die Migrationslogs deaktiviert.

Vorfall 4: commons-logging und spring-jcl gleichzeitig im Classpath

Warnung:

Standard Commons Logging discovery in action with spring-jcl:
please remove commons-logging.jar from classpath

Spring Framework nutzt spring-jcl als Commons-Logging-Bridge. Taucht im Classpath zusätzlich das klassische

commons-logging:commons-logging

auf, kann es zu Konflikten bei der Erkennungsreihenfolge der Logging-Implementierung kommen.

Zuerst die Kette lokalisieren, über die sie ins Projekt gelangt:

mvn dependency:tree \
  -Dverbose \
  -Dincludes=commons-logging:commons-logging

Nicht in Dutzenden Business-Repositories einzeln ausschließen. Kommt die Abhängigkeit aus dem einheitlichen Nacos config/discovery starter, schließe sie an dessen direkter Abhängigkeitsgrenze aus:

<dependency>
  <groupId>com.alibaba.cloud</groupId>
  <artifactId>spring-cloud-starter-alibaba-nacos-config</artifactId>
  <exclusions>
    <exclusion>
      <groupId>commons-logging</groupId>
      <artifactId>commons-logging</artifactId>
    </exclusion>
  </exclusions>
</dependency>

Hat der Discovery-Starter eine eigene Abhängigkeit, muss auch dort an der entsprechenden Grenze ausgeschlossen werden. Eine Maven-Exclusion wirkt nur auf den angegebenen Abhängigkeitspfad; ein anderes SDK kann dasselbe JAR erneut einbringen.

Nach der Bereinigung erneut prüfen:

mvn dependency:tree \
  -Dincludes=commons-logging:commons-logging

jar tf application.jar \
  | grep 'BOOT-INF/lib/commons-logging'

Verlangt die Organisation, diese Abhängigkeit dauerhaft zu verbieten, kann im Parent eine bannedDependencies-Regel des Maven Enforcer ergänzt werden. Zuerst sollten aber die bekannten transitiven Ketten bereinigt werden, damit ein einzelnes Upgrade nicht alle Repositories gleichzeitig blockiert.

Vorfall 5: Nacos kann nacos-logback.xml nicht laden

Warnung:

Load Logback Configuration of Nacos fail,
message: Could not initialize Logback Nacos logging
from classpath:nacos-logback.xml

Das ist mehr als „eine XML-Datei fehlt“. Spring Boot 3 verwendet Logback 1.4, mit dem die Logging-Initialisierung einiger Nacos-Clients 2.2.x nicht kompatibel ist.

Die offizielle Nacos-FAQ nennt folgende Zuordnung:

Nacos Clientlogback-adapter
2.2.1–2.3.x1.0.x
2.4.0 und neuer1.1.x

Für Nacos Client 2.2.1 lässt sich die Version im einheitlichen Dependency-Management fixieren:

<properties>
  <nacos-logback-adapter.version>1.0.1</nacos-logback-adapter.version>
</properties>

<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>com.alibaba.nacos</groupId>
      <artifactId>logback-adapter</artifactId>
      <version>${nacos-logback-adapter.version}</version>
    </dependency>
  </dependencies>
</dependencyManagement>

dependencyManagement verwaltet aber nur Versionen und fügt das JAR nicht automatisch zur Anwendung hinzu. Der gemeinsame Starter, der Nacos tatsächlich nutzt, muss die Abhängigkeit zusätzlich deklarieren:

<dependency>
  <groupId>com.alibaba.nacos</groupId>
  <artifactId>logback-adapter</artifactId>
</dependency>

Am Ende mit dem ausführbaren JAR verifizieren statt nur auf das Parent zu schauen:

jar tf application.jar \
  | grep -E 'nacos-client|logback-adapter|logback-classic'

Man sollte keine alte nacos-logback.xml in jede Anwendung kopieren. Das verteilt die Verantwortung für die Versionskompatibilität auf alle Business-Repositories, und beim nächsten Nacos-Upgrade driftet sie erneut auseinander.

Vorfall 6: ClassNotFoundException ohne Message

Beim Start eines weiteren Dienstes erschien:

java.lang.ClassNotFoundException:
  at java.lang.Class.forName0(...)
  at java.lang.Class.forName(...)
  at ...JDBCUtil.initialize(...)

Hinter dem Doppelpunkt der Exception-Message steht kein Klassenname — ein wichtiger Hinweis. Der Code führte tatsächlich aus:

Class.forName(driver);

Die optionale Konfiguration war jedoch leer:

sales.driver=
sales.url=

Class.forName("") wirft eine ClassNotFoundException ohne nennenswerte fachliche Information.

Wenn diese synchrone Datenquelle eine optionale Funktion ist, sollte die Initialisierung zuerst prüfen, ob die Funktion aktiviert ist:

@PostConstruct
void initialize() {
    if (!StringUtils.hasText(url)) {
        log.info("未配置 sales.url，同步功能已禁用");
        return;
    }

    if (!StringUtils.hasText(driver)) {
        throw new IllegalStateException(
            "已配置 sales.url，但缺少 sales.driver"
        );
    }

    try {
        Class.forName(driver);
    } catch (ClassNotFoundException ex) {
        throw new IllegalStateException(
            "无法加载同步数据库驱动: " + driver,
            ex
        );
    }
}

Eleganter ist die bedingte Konfiguration:

@ConditionalOnProperty(
    prefix = "sales",
    name = "url"
)

So wird für die nicht konfigurierte optionale Funktion gar kein Bean erzeugt. Ein leerer String sollte nicht „aktiviert, Treiber aber noch unbekannt“ bedeuten.

Außerdem hieß die Methode mit Class.forName früher getServletPort, lädt aber eigentlich den JDBC-Treiber. Ein irreführender Name kann die Fehlersuche im Stacktrace in die falsche Richtung lenken und sollte gleich mit korrigiert werden.

So entscheidest du, ob Deployment, Nacos, Parent oder Business-Code geändert werden muss

BelegÄnderungsort
Gleiches Image: unter altem Sicherheitskontext beschreibbar, unter neuem nichtDeployment und Mounts
Key wird vom Properties-Migrator gemapptNacos-/Anwendungskonfiguration
Mehrere Anwendungen ziehen dasselbe alte JAR über denselben StarterParent oder gemeinsamer Starter
Nur ein optionales Modul übergibt leere Werte an eine Reflektion-APIBusiness-Code
Adapter und Client-Version passen nicht zueinanderdependency management + starter

Nur weil die Logs in Kubernetes auftauchen, heißt das nicht, dass sich jedes Problem per YAML beheben lässt.

Checkliste für die Rolling-Validierung

  1. Nach dem Build die Abhängigkeiten des finalen JAR prüfen, nicht nur die Dependency-View der IDE.
  2. Das Deployment rendern und HOME, user.home, Mounts und UID bestätigen.
  3. Zuerst eine Replik aktualisieren.
  4. Warten, bis das neue ReplicaSet Ready ist, und bestätigen, dass der alte Pod weiterhin als Fallback dient.
  5. Die fünf Arten von Schlüsselwörtern im Startlog prüfen.
  6. Reale Aufrufpfade für Nacos-Registrierung, Redis, Datei-Upload und optionales JDBC auslösen.
  7. Danach die restlichen Repliken aktualisieren.
kubectl -n <namespace> logs <new-pod> --since=20m \
  | grep -Ei \
  'mkdir failed|/root/nacos|use-forward-headers|commons-logging|nacos-logback|ClassNotFound'

Definition of Done

  • Die Spring-Exception ist bis zur untersten Cause zurückverfolgt, nicht beim Bean-Namen stehen geblieben.
  • Alle Client-Verzeichnisse mit Schreibbedarf haben kontrollierte Mounts und Größenlimits.
  • Nacos versucht nicht mehr, nach /root/nacos zu schreiben.
  • Nacos, Upload-SDK und Log-Verzeichnisse wurden mit echten Schreibzugriffen verifiziert.
  • server.use-forward-headers ist aus allen Nacos-DataIds entfernt.
  • Das finale JAR enthält kein klassisches commons-logging.jar.
  • Nacos Client und logback-adapter-Version passen zusammen.
  • Die optionale JDBC-Funktion lädt ohne Konfiguration keinen Treiber.
  • Der Wechsel zwischen altem und neuem ReplicaSet ist abgeschlossen; kein alter Pod dient langfristig als Fallback.

Fazit

Für diese Startfehler gab es keine einzige „Zauberkonfiguration“. Der eigentliche Gewinn ist ein stabiler Entscheidungspfad:

先读最深 Cause
→ 判断文件系统、配置、classpath 还是业务代码
→ 在最接近根因的公共边界修复
→ 检查最终 JAR 和最终 Pod，而不是源码与模板

Die verschärfte Sicherheitsbaseline hat die frühere implizite Annahme offengelegt, dass /root beschreibbar ist; Spring Boot 3 hat die Versionsgrenzen alter Properties und des Logging-Stacks aufgezeigt; das leere Class.forName hat gezeigt, dass der Business-Code „optionale Funktion“ nicht korrekt ausdrückt.

Behoben werden diese Probleme am jeweils richtigen Ort: Deployment, Nacos, gemeinsamer Starter und Business-Code. Nur so muss man nicht wegen einer Logzeile die Rechte des gesamten Clusters aufweichen oder neue Classpath-Konflikte einführen.
