Spring Boot auf JDK 25 umgestellt: Speicher sinkt von 3.5G auf 900M – eine Praxisanalyse mit ZGC

Erklärt, woraus sich der von Kubernetes beobachtete Speicher eines Java-Containers zusammensetzt, und zeigt Schritt für Schritt, wie sich ein Spring-Boot-Dienst mit ZGC, SoftMaxHeapSize, ZUncommitDelay und Native Memory Tracking analysieren und optimieren lässt.

Dieser Artikel basiert auf einer realen Optimierung. Dienstname, Images, Knoten, Kapazitäten und Geschäftsdaten wurden verallgemeinert. Die genannten Parameter dienen nur als Analyseansatz und lassen sich nicht ohne Weiteres auf jeden Java-Dienst übertragen.

Nach dem Upgrade auf JDK 25 meldete Kubernetes für einen Spring-Boot-Dienst direkt nach dem Start etwa 3.5 GiB; nach der Stabilisierung sank der Wert allmählich auf unter 1 GiB. Dieses Verhalten bedeutet weder, dass die JVM „Geschäftsdaten leert”, noch lässt es sich allein damit erklären, dass „ZGC sparsamer mit Speicher umgeht als G1”.

Entscheidend ist, zunächst zu klären, was kubectl top tatsächlich anzeigt und warum „verwendeter Heap”, „committeter Heap”, „residenter Prozessspeicher” und „Container-Arbeitssatz” nicht übereinstimmen.

Was den Speicher eines Java-Containers ausmacht

flowchart TD
  A["Container Memory"] --> B["Java Heap"]
  A --> C["Metaspace / Compressed Class Space"]
  A --> D["Thread Stacks"]
  A --> E["Direct / Mapped Buffers"]
  A --> F["JIT Code Cache"]
  A --> G["GC Native Structures"]
  A --> H["Shared Libraries / Page Cache"]

-Xmx begrenzt ausschließlich die Obergrenze des Java-Heaps; andere Bereiche sind nicht abgedeckt. Bei einem mit -Xmx2g gestarteten Prozess ist es völlig normal, dass der Containerspeicher 2 GiB übersteigt.

Schritt 1: Welches JDK steckt tatsächlich im Pod?

Der Anbieter sollte nicht anhand des Basis-Image-Namens erraten werden:

kubectl -n <namespace> exec <pod> -- java -version

kubectl -n <namespace> exec <pod> -- \
  java -XshowSettings:properties -version 2>&1 \
  | grep -E 'java.vendor|java.version|java.home|java.vm.name'

OpenJDK ist die Referenzimplementierung und das Ökosystem; Oracle JDK, Eclipse Temurin, Amazon Corretto und Microsoft Build of OpenJDK sind dagegen unterschiedliche Distributions-Builds. Bei der Auswahl ist Folgendes zu beachten:

  • Rhythmus der Sicherheitsupdates.
  • Unterstützung für Container und CPU-Architekturen.
  • Support und Lizenzierung durch den Anbieter.
  • Bestehen der vollständigen Regressionssuite des Projekts.

Ein Wechsel zu Oracle JDK behebt Speicherprobleme der Anwendung nicht automatisch.

Schritt 2: Alle Quellen der JVM-Parameter bestätigen

kubectl -n <namespace> exec <pod> -- sh -c '
  printf "JAVA_TOOL_OPTIONS=%s\n" "$JAVA_TOOL_OPTIONS"
  printf "JDK_JAVA_OPTIONS=%s\n" "$JDK_JAVA_OPTIONS"
  printf "JAVA_OPTS=%s\n" "$JAVA_OPTS"
'

Anschließend den Prozess prüfen:

kubectl -n <namespace> exec <pod> -- jcmd 1 VM.command_line
kubectl -n <namespace> exec <pod> -- jcmd 1 VM.flags

Picked up JAVA_TOOL_OPTIONS und Picked up JDK_JAVA_OPTIONS zeigen an, dass die Parameter über Umgebungsvariablen injiziert wurden. Werden in demselben Deployment beide definiert, ist sicherzustellen, dass sie sich weder doppeln noch widersprechen.

Globale Vorlagen sind besonders riskant: Wird ein Parameter, den ausschließlich das neue JDK unterstützt, in einen Dienst injiziert, der noch mit einem älteren JDK läuft, erscheint sofort:

Unrecognized option
Could not create the Java Virtual Machine

Schritt 3: Kubernetes und JVM getrennt prüfen

Auf Kubernetes-Seite:

kubectl top pod -n <namespace> <pod> --containers
kubectl -n <namespace> get pod <pod> \
  -o jsonpath='{.spec.containers[0].resources}{"\n"}'

Im Container:

kubectl -n <namespace> exec <pod> -- sh -c '
  grep -E "VmRSS|VmSize|Threads" /proc/1/status
  test -f /sys/fs/cgroup/memory.current && cat /sys/fs/cgroup/memory.current
'

Auf JVM-Seite:

kubectl -n <namespace> exec <pod> -- jcmd 1 GC.heap_info
kubectl -n <namespace> exec <pod> -- jcmd 1 VM.native_memory summary

Native Memory Tracking erfordert einen Startparameter:

-XX:NativeMemoryTracking=summary

NMT verursacht zusätzlichen Overhead und eignet sich für Diagnose und Basisbeobachtung. Ob es dauerhaft aktiviert bleibt, sollte anhand von Lasttests entschieden werden.

Schritt 4: SoftMaxHeapSize verstehen

Beispiel:

-Xmx2g
-XX:SoftMaxHeapSize=1g

In der ZGC-Dokumentation von Oracle JDK 25 wird erklärt, dass Soft Max ein weiches Ziel für den GC ist und keine harte Obergrenze darstellt. ZGC hält den Heap möglichst nahe bei 1 GiB, kann unter Druck jedoch vorübergehend bis auf -Xmx2g wachsen. The Z Garbage Collector

Damit lässt sich ausdrücken:

平时尽量少占内存
高峰允许使用预留上限

Es ersetzt weder das Memory-Limit des Containers noch garantiert es, dass die RSS unter 1 GiB bleibt.

Schritt 5: ZUncommitDelay verstehen

-XX:ZUncommitDelay=120

Das heißt: Sobald ZGC feststellt, dass Heap-Speicher längere Zeit ungenutzt bleibt, müssen die betroffenen Speicherseiten mindestens etwa 120 Sekunden ungenutzt bleiben, bevor sie an das Betriebssystem zurückgegeben werden können. Der Standardwert in JDK 25 beträgt 300 Sekunden.

Mit 30 Sekunden sinken die Messwerte möglicherweise schneller; bei häufig schwankender Last kann es jedoch zu wiederholtem Commit/Uncommit kommen. Empfohlen wird, zunächst den Abstand zwischen den Lastspitzen zu beobachten:

LastmusterErste Empfehlung
Längere Phasen niedriger Last mit gelegentlichen Spitzen120–300 Sekunden
Dauerhaft gleichmäßig hohe LastStandardwert beibehalten; begrenzter Nutzen
Schnelle Schwankungen im MinutentaktNicht zu kurz wählen; erst Lasttests durchführen

„Schneller zurückgeben” bedeutet nicht zwangsläufig „besserer Durchsatz”.

Schritt 6: Ein verifizierbarer ZGC-Ausgangspunkt

-XX:+UseZGC
-Xms512m
-Xmx2g
-XX:SoftMaxHeapSize=1g
-XX:ZUncommitDelay=120
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/data/java/dumps

Beispiel für Container-Ressourcen:

resources:
  requests:
    cpu: "1"
    memory: 1536Mi
  limits:
    cpu: "2"
    memory: 3Gi

Für den Nicht-Heap-Bereich muss Spielraum bleiben. Nähert sich die Summe aus Heap-Obergrenze, Direct Memory, Thread-Stacks, Metaspace und nativen Bibliotheken dem Container-Limit, beendet der Kernel den Prozess per OOMKill – die JVM hat dann unter Umständen keine Gelegenheit mehr, einen Heap-Dump zu erzeugen.

Schritt 7: Warum der Wert erst hoch ist und später sinkt

Während des Starts:

  • Es werden viele Klassen und Beans geladen.
  • Der JIT kompiliert heißen Code.
  • Puffer für Clients wie Datenbank, Nacos und Kafka werden angelegt.
  • Konfigurationen werden geparst, Annotationen gescannt und Threads erzeugt.
  • Der Heap dehnt sich vorübergehend aus, um den Startdurchsatz zu unterstützen.

Nach Abschluss des Starts:

  • Kurzlebige Objekte werden eingesammelt.
  • ZGC richtet das Heap-Ziel an Soft Max aus.
  • Seiten, die länger als ZUncommitDelay ungenutzt sind, werden nach und nach an das Betriebssystem zurückgegeben.

Der Rückgang von 3.5 GiB auf 900 MiB kann daher sowohl auf eine Verkleinerung des Heaps als auch auf Veränderungen bei Dateiseiten und im Arbeitssatz des Containers zurückgehen. Nur wer NMT, Heap und cgroup gemeinsam beobachtet, kann die Ursachen sauber zuordnen.

Beim lokalen Start gibt es häufig kein cgroup-Limit, sodass die JVM deutlich mehr Host-Speicher sieht; auch die IDE kann die VM-Optionen überschreiben. Zuerst ausführen:

jcmd <pid> VM.command_line
jcmd <pid> VM.flags
jcmd <pid> GC.heap_info

Der Wert „eine Minute nach dem lokalen Start” sollte nicht mit dem Wert „nach einer Stunde stabil im Produktionsbetrieb” verglichen werden.

Schritt 9: Umgang mit JDK-25-Warnungen

Unsafe terminally deprecated

Ursache sind in der Regel Aufrufe von sun.misc.Unsafe durch Abhängigkeiten wie Netty, gRPC oder den Nacos-Client. Empfohlene Reihenfolge:

  1. Das betreffende JAR über den Abhängigkeitsbaum lokalisieren.
  2. Prüfen, ob upstream bereits eine kompatible Version anbietet.
  3. Zuerst die Abhängigkeit aktualisieren und Regressionstests ausführen.
  4. Nicht eigenmächtig alle Warnungen unterdrücken.

restricted native access

--enable-native-access=ALL-UNNAMED

Nur hinzufügen, wenn der Parameter zur Laufzeit nachweislich unterstützt wird, die Abhängigkeit ihn tatsächlich benötigt und eine Sicherheitsprüfung ihn freigibt. Er gehört nicht in eine globale Deployment-Vorlage, die auf gemischte JDK-Versionen ausgelegt ist.

add-opens / add-exports

Solche Parameter sind Übergangsmaßnahmen für die Kompatibilität mit älterer Reflektion oder internen APIs. Für jeden Parameter sollte dokumentiert werden, welche Abhängigkeit ihn benötigt und ab welcher Upgrade-Version er entfernt werden kann.

Schritt 10: Lasttests und Abnahme

Mindestens zwei Konfigurationen unter identischer Last vergleichen:

基线：原 JDK + 原 GC
候选：JDK 25 + ZGC 参数

Erfassen:

  • Startzeit und Zeit bis Ready.
  • P50/P95/P99-Latenz.
  • Durchsatz und Fehlerrate.
  • Heap used/committed.
  • RSS, cgroup memory und Direct Memory.
  • GC pause und allocation rate.
  • CPU und Kontextwechsel.
  • Eine vollständige Batch-Verarbeitung oder Lastspitze.

Der Beobachtungszeitraum muss mindestens einen vollständigen realen Lastzyklus abdecken; die ersten zehn Minuten nach dem Start genügen nicht.

Woran erkennt man, ob 900M gesund ist?

900 MiB sind für sich genommen noch kein Zeichen von Gesundheit. Zusätzlich zu prüfen:

  • Kein häufiger GC, der die CPU-Auslastung erhöht.
  • P99 hat sich nicht verschlechtert.
  • Der Heap verfügt bei Spitzen über ausreichend Puffer.
  • Direct Buffer, Threads und Metaspace wachsen nicht dauerhaft.
  • Keine OOMKilled-Ereignisse oder Memory-Pressure im Container.
  • Durchsatz von Batch-Verarbeitung und Nachrichtenkonsum ist normal.

Abnahmekriterien

  • Laufzeit-JDK, Anbieter und JVM-Parameter lassen sich reproduzierbar bestätigen.
  • Die vier Datenschichten – kubectl top, cgroup, Heap und NMT – lassen sich einander zuordnen.
  • Das Verhältnis von Soft Max zu Xmx wurde unter Lastspitzen validiert.
  • ZUncommitDelay deckt einen realen Lastzyklus ab, ohne spürbare Schwankungen zu verursachen.
  • Das Container-Limit reserviert ausreichend Platz für den Nicht-Heap-Bereich.
  • Jeder Kompatibilitätsparameter hat eine dokumentierte Quelle und eine festgelegte Bedingung für seine Entfernung.
  • Latenz, Durchsatz und Stabilität verschlechtern sich nach der Optimierung nicht.

Der Wert von ZGC besteht nicht darin, dass der Prozess „immer weniger verbraucht”, sondern darin, dass er sich im Rahmen des Latenzziels proaktiver an die Last anpasst und länger ungenutzten Heap-Speicher an das Betriebssystem zurückgibt.
