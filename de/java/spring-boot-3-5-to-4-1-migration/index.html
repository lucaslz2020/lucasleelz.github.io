Von Spring Boot 3.5.13 auf 4.1: erst Erledigtes von echten Risiken trennen

Von Spring Boot 3.5.13 auf 4.1: Abhängigkeitsgrenzen, Umsetzungsreihenfolge und Abnahmeliste – JDK 25, Nacos 3.1.2 und Standard-Datenzugriff als Basis.

lucaslzAutor
2. August 2026 9 Min. Lesezeit
#Java #Spring Boot #Spring Cloud #Nacos #Kubernetes
{ }

Spring Boot 4.1 ist kein gewöhnliches Abhängigkeits-Upgrade. Es basiert auf Spring Framework 7, Jakarta EE 11 und Servlet 6.1 – und das gesamte Umfeld springt mit: Spring Cloud, Nacos Client, Web-Container, JSON, Datenzugriff und selbst entwickelte Starter überqueren dabei jeweils eine Major-Version.

Der häufigste Fehler bei einer Upgrade-Bewertung ist jedoch, bereits gelöste Probleme erneut als Risiko einzustufen. Dieser Artikel dokumentiert die Vorgehensweise vor einem realen Upgrade: Ausgangspunkt sind bereits Spring Boot 3.5.13, JDK 25 und Nacos Server 3.1.2; die alte Erweiterung für benutzerdefinierte Abfragen wurde ebenfalls entfernt. Im Fokus der Bewertung stehen daher nicht mehr die historischen Kompatibilitätsfragen von Boot 3.1 oder Nacos 2, sondern die tatsächlichen Bruchstellen zwischen 3.5 und 4.1.

Der vorherige Beitrag Spring Boot von 3.1.7 auf 3.5.13 upgraden beschreibt bereits die Vorgehensweise bei Kompilierung, Pod-Start, vollständigem Actuator-Health-Check und Middleware-Verifikation. Dieser Artikel konzentriert sich ausschließlich auf die mit Boot 4 neu hinzukommenden Kompatibilitätsrisiken, statt dieselbe allgemeine Checkliste erneut aufzuführen.

Dieser Artikel behandelt die Upgrade-Route und die Grenzen der Verifikation. Das heißt nicht, dass du nach einer bloßen Änderung der Versionsnummer auf 4.1 direkt live gehen kannst.

Hinweis zur Anonymisierung: Der Artikel enthält keine Projektnamen, Dienstnamen, Repository-Pfade, Domains, Cluster-Informationen, Namespaces, Data IDs, Konten oder echte Geschäftsdaten; alle Konfigurationsbeispiele sind Platzhalter.

Zuerst die Ausgangsbasis festlegen

Halte den aktuellen Stand zuerst klar im Change-Ticket fest, damit spätere Diskussionen nicht auf veralteten Informationen aufbauen:

ProjektAktueller StandIn diesem Upgrade zu behandeln
Spring Boot3.5.13Upgrade auf 4.1
JDK25Beibehalten, kein Downgrade
Nacos Server3.1.2Beibehalten, keine Datenbankmigration, kein Neuaufbau der Konfiguration
Alte Erweiterung für benutzerdefinierte AbfragenEntferntKeine Übernahme nötig
Komplexe AbfragenAls explizites SQL umgesetztRepository-Grenzen beibehalten und Ergebnisse regressiv prüfen

Dass Nacos Server bereits auf 3.1.2 läuft, heißt nur, dass Server, Datenbank und Konfigurationsdaten weiterverwendet werden können; es beweist nicht automatisch, dass ein Spring Cloud Alibaba Client mit Spring Boot 4.1 kompatibel ist. Server und Client sind zwei voneinander unabhängige Kompatibilitätsketten.

Die erste harte Grenze: Spring Cloud Alibaba und die Unterstützung für 4.1

Spring Cloud hat offiziell mitgeteilt, dass Spring Boot 4.1.x ab 2025.1.2 unterstützt wird. Die Zielversion von Spring Cloud für Boot 4.1 sollte daher sein:

<spring-cloud.version>2025.1.2</spring-cloud.version>

Die offizielle Kompatibilitätstabelle von Spring Cloud Alibaba nennt derzeit jedoch:

Spring Cloud Alibaba 2025.1.0.0
Spring Cloud 2025.1.0
Spring Boot 4.0.0

Zudem wird dieser Branch als Anpassung an Spring Boot 4.0.x beschrieben. 4.0.x ist kein Oberbegriff für 4.1.x; daraus kann nicht abgeleitet werden, dass 2025.1.0.0 offiziell Boot 4.1 unterstützt.

Das heißt nicht, dass diese Kombination gar nicht lauffähig wäre; vielmehr musst du zwei Aussagen unterscheiden:

  • Offizielle Unterstützung: Die Kompatibilitätsmatrix listet die entsprechende Version ausdrücklich auf.
  • Lokal verifiziert lauffähig: Projektergebnis aus Abhängigkeitskonsolidierung, Start, Registrierung, Konfigurationsabruf und fachlicher Regression.

Solange Alibaba keine Version veröffentlicht, die Boot 4.1 ausdrücklich unterstützt, solltest du bei einem direkten Wechsel auf Boot 4.1 die folgende Kombination als Verifikationsziel betrachten – nicht als stillschweigende Zusage für die Produktion:

Spring Boot 4.1.x
Spring Cloud 2025.1.2
Spring Cloud Alibaba 2025.1.x
Nacos Server 3.1.2

Offizielle Quellen: Kompatibilitätstabelle für Spring Cloud-Versionen, Versionshinweise zu Spring Cloud Alibaba 2025.x.

Nacos: keine Datenmigration – aber das Laden der Konfiguration muss umgestellt werden

Spring Cloud Alibaba 2025.x unterstützt Spring Cloud Bootstrap nicht mehr. Falls die Anwendung weiterhin auf Folgendem beruht:

bootstrap.yml
spring.cloud.bootstrap.enabled

muss sie auf Spring Boot Config Data umgestellt werden, zum Beispiel:

spring:
  config:
    import:
      - optional:nacos:<data-id>?group=<group>

Ob die Data ID aufgeteilt wird und wie Group, Namespace, Benutzername und Adresse im Detail definiert sind, richtet sich nach der Zielumgebung und sollte nicht in der öffentlichen Dokumentation auftauchen; geändert wird, wie die Anwendung die Konfiguration beim Start lädt – nicht das in Nacos gespeicherte Datenformat.

Nach Abschluss der Migration sind zwei Dinge zu verifizieren:

  1. Beim Start werden die erforderlichen Konfigurationen geladen, z. B. Feign-URL, Datenquelle, Redis und Message-Queue-Adressen.
  2. Zur Laufzeit funktionieren Konfigurations-Refresh, Dienstregistrierung und Instanz-Discovery weiterhin normal.

Die wichtigsten Änderungen durch Boot 4 selbst

1. Undertow ist nicht mehr als eingebetteter Container verfügbar

Die Servlet-6.1-Basislinie von Boot 4 ist nicht mit Undertow kompatibel; der Undertow-Starter und die Unterstützung für eingebettetes Undertow wurden offiziell entfernt. Falls der finale Abhängigkeitsbaum Undertow enthält, muss auf Tomcat 11 oder Jetty 12 gewechselt und die Konfiguration server.undertow.* entfernt werden.

Aus einer gemeinsamen Konfiguration allein sollte nicht geschlossen werden, dass alle Dienste den Container wechseln müssen; zunächst sind der finale Abhängigkeitsbaum und die tatsächlichen Startprotokolle jedes Dienstes zu prüfen.

2. Boot-Module und Starter wurden neu aufgeteilt

Boot 4 zerlegt viele große JARs in feinere Module. Besonders anfällig für Probleme zur Kompilierzeit sind selbst entwickelte Starter, Module, die direkt Boot-interne Klassen verwenden, sowie handgeschriebene Auto-Konfigurationen.

In der ersten Runde bekommst du mit spring-boot-starter-classic und spring-boot-starter-test-classic einen Classpath, der dem von Boot 3 nahekommt, und stellst Kompilierung, Start und Tests zunächst wieder her. Sobald alles stabil läuft, ersetzt du die Starter je nach tatsächlichem Bedarf durch präzisere. Ein selbst entwickelter Starter sollte nicht gleichzeitig Binärkompatibilität mit Boot 3 und Boot 4 versprechen; richte stattdessen eine eigene Versionslinie für Boot 4 ein.

3. Jackson 3 ist die Richtung – aber nicht mit dem Framework-Upgrade bündeln

Boot 4 tendiert standardmäßig zu Jackson 3; dabei ändern sich die Koordinaten und einige Paketnamen von Jackson 3. Für Systeme mit umfangreichem ObjectMapper-Einsatz, Nachrichtenserialisierung, Datumsformatierung sowie Import- und Exportlogik sollte in der ersten Runde das Jackson-2-kompatible Verhalten beibehalten werden:

spring:
  jackson:
    use-jackson2-defaults: true

Bei Bedarf können die von Boot bereitgestellten Übergangsmodule für Jackson 2 verwendet werden. Erst wenn HTTP-Antworten, Kafka-/Rabbit-Nachrichten und Exportdateien vollständig regressiv geprüft sind, sollte die Jackson-3-Migration separat geplant werden. Andernfalls lässt sich bei auftretenden Anomalien kaum beurteilen, ob Boot, Jackson oder die fachliche Serialisierung die Ursache ist.

4. Datenzugriffskomponenten müssen für Boot 4 neu verifiziert werden

Die alte Erweiterung für benutzerdefinierte Abfragen ist kein Risiko mehr; für die folgenden Komponenten müssen die Versionen jedoch neu bestätigt werden:

  • Hibernate 7: Entitäts-Mapping, Dialekt, JPA Criteria, natives SQL, JSON- und Datumsfelder.
  • Dynamische Datenquellen: dynamic-datasource-spring-boot3-starter darf nicht ohne Weiteres als kompatibel mit Boot 4 vorausgesetzt werden.
  • MyBatis-Plus: Paginierung, Interceptors, Transaktionen über mehrere Datenquellen und SQL-Logs.
  • Redis, Kafka, Rabbit: Clients, Serialisierung, Listener, Retry und Message-Header.

Jeder Punkt muss durch Tests nach dem Upgrade der jeweiligen Abhängigkeit bestätigt werden – nicht schon dadurch, dass Maven das JAR herunterladen kann.

5. Sicherheit, Tests und Betrieb folgen dem Upgrade ebenfalls

Boot 4 bringt zugleich Major-Upgrades wie Spring Security 7, Spring Kafka 4, Spring AMQP 4 und Spring Batch 6 mit sich. Besonders zu verifizieren sind:

  • Login, Token, Berechtigungs-Annotationen und Identität bei Feign-Aufrufen.
  • Nachrichtenkonsum, Deserialisierung, Retry und Idempotenz.
  • Web-Tests unter @SpringBootTest; bei Bedarf explizit @AutoConfigureMockMvc ergänzen.
  • Actuator-Health-Checks. Boot 4 aktiviert die Gruppen liveness/readiness standardmäßig; Kubernetes-Probes, Prometheus-Scraping und Graceful Shutdown sind erneut zu prüfen.

Umsetzungsreihenfolge auf Basis der 3.5-Abnahme

建立 4.1-SNAPSHOT 分支
        ↓
确认 Cloud / Alibaba Client 精确版本
        ↓
迁 Nacos Config Data，处理父工程自研 starter
        ↓
父工程全量编译与测试
        ↓
升级一个试点服务并在本地连接 Nacos 3.1.2
        ↓
test Kubernetes 发布与业务回归
        ↓
逐服务推广

Es wird empfohlen, zunächst einen Dienst mit klarer fachlicher Abgrenzung und guter Testabdeckung als Pilot zu wählen, statt alle Dienste auf einmal zu upgraden. Die neue Version des Parent-Projekts verwendet eine eigene Maven-Version, z. B. 4.1-SNAPSHOT, um das weiterhin laufende 3.5.13-SNAPSHOT nicht zu überschreiben.

Inkrementelle Abnahmeliste für den Boot-4-Pilot

Im Folgenden sind nur die gegenüber dem vorherigen Beitrag neu hinzugekommenen Prüfpunkte aufgeführt. Allgemeine Abnahmen wie Kompilierung mit der Ziel-JDK-Version, Pod-Start, vollständiger /actuator/health-Check sowie die Konnektivität von Datenbank und Message-Middleware bleiben Pflicht, werden hier aber nicht erneut aufgeführt.

Start und Infrastruktur

  • Spring Cloud verwendet bereits 2025.1.2+ mit Unterstützung für Boot 4.1; der Abhängigkeitsbaum enthält keinen alten Release Train.
  • Für die exakte Version des Spring Cloud Alibaba Clients liegen eine Kompatibilitätsmatrix oder Nachweise aus der Pilotverifikation vor; die Nacos-Server-Version allein genügt nicht.
  • Die Nacos-Konfiguration wurde auf Config Data umgestellt; die Startkette ist nicht mehr von Spring Cloud Bootstrap abhängig.
  • Der tatsächliche Web-Container ist Tomcat 11 oder Jetty 12; weder Abhängigkeitsbaum noch Konfiguration enthalten Reste von Undertow.
  • spring-boot-starter-classic dient nur als Übergang und wird entfernt, sobald die Aufteilung der Starter und die Migration der Eigenschaften abgeschlossen sind.

Fachlichkeit und Daten

  • Hibernate 7, MyBatis-Plus und die dynamische Datenquelle müssen jeweils Paginierung, Transaktionen, natives SQL und mehrere Datenquellen per Regression bestehen.
  • Job-Registrierung, Metadaten-Tabellen, Neustart und Partitionsausführung von Spring Batch 6 wurden verifiziert.
  • Message-Header, Serialisierung, Retry, Dead Letter und Idempotenzverhalten von Spring Kafka 4 und Spring AMQP 4 haben sich nicht verändert.
  • Von Jackson 3 und dem Übergangspfad für Jackson 2 darf nur eine Variante als Produktionsbasis gewählt werden; die Regressionen für HTTP, Nachrichten sowie Import und Export müssen abgeschlossen sein.

Schnittstellenvertrag

  • Anfragen und Fehlermeldungen der Kernseiten im Frontend.
  • Datum, Beträge, Enums, null-Felder und Paginierungsstruktur.
  • Deserialisierungskompatibilität von HTTP-APIs und Nachrichten-JSON.

Fazit

Beim Upgrade von Spring Boot 3.5.13 auf 4.1 sind Nacos 3.1.2 und die alte Erweiterung für benutzerdefinierte Abfragen keine Hindernisse mehr. Vorrangig ist zu klären, ob der Spring Cloud Alibaba Client Boot 4.1 ausdrücklich unterstützt; danach wird in folgender Reihenfolge vorgegangen: Laden der Nacos-Konfiguration, Modularisierung von Boot und Web-Container, Datenzugriff, Jackson und selbst entwickelte Starter.

Schaffe zuerst Belege, dass das Upgrade in der lokalen Umgebung und in der Testumgebung funktioniert, und mache es erst danach zum Produktionsstandard. So lässt sich ein Major-Versions-Upgrade wie dieses kontrolliert durchführen. Der offizielle Migrationsleitfaden von Boot kann als Checkliste für die schrittweise Prüfung dienen: Spring Boot 4.0 Migration Guide.
