JDK 17: Spring-Boot-Speicheroptimierung im Container – von 3–4G zu kontrolliertem Verbrauch

Spring-Boot-Speicher: vier Ebenen – Kubernetes, cgroup, JVM Heap, Native Memory – G1, Heap-Obergrenze, Metaspace, Threads, Prefetch, JProfiler, Probes justieren

lucaslzAutor
25. Juli 2026 Aktualisiert 6. August 2026 16 Min. Lesezeit
#Java #JDK 17 #G1 #Kubernetes #Spring Boot
{ }

Dieser Artikel entstand aus der Container-Speicheroptimierung einer Reihe von JDK-17-Services. Servicenamen, Cluster, Knoten und Geschäftsdaten wurden verallgemeinert; die Beispielparameter sind ein Ausgangspunkt für die Fehlersuche, keine Standardlösung, die sich eins zu eins auf jede Anwendung übertragen lässt.

Eine Zeitlang gingen wir beim Speicher von Java-Services recht grob vor: Sobald Container häufig neu starteten, erhöhten wir -Xmx und das Kubernetes-Memory-Limit gemeinsam. Das Ergebnis: Normale Spring-Boot-Services belegten dauerhaft 3–4 GiB, schwere Services kamen auf fast 5 GiB, und einzelne Instanzen wurden am Ende trotzdem beendet.

Bei der eigentlichen Fehlersuche zeigte sich, dass hinter diesen Symptomen mindestens zwei grundlegend verschiedene Probleme steckten:

  • Eine Instanz mit -Xmx4g hatte einen Heap-Verbrauch von etwa 3.5 GiB; nach einem Heap-Check fielen die lebenden Objekte auf etwa 1.9 GiB, die RSS sank jedoch nicht sofort.
  • Bei einer anderen Instanz nutzte der Heap nur etwa 280 MiB, während die RSS des Java-Prozesses bei über 1.2 GiB lag – bei mehr als 200 Threads und einem dauerhaft geladenen nativen Profiler.

Im ersten Fall dominieren Heap- und Allokationsdruck, im zweiten Non-Heap-, Thread- und nativer Speicher. Wer nur kubectl top betrachtet, stuft beides fälschlich als „Java-Heap zu groß“ ein.

Schritt 0: Vergleichsobjekte und Beweisfenster zuerst klären

Wenn die Frage lautet, warum sich zwei Pods desselben Services beim Speicher um ein Vielfaches unterscheiden, ist der erste Schritt nicht die JVM, sondern die Klärung, ob beide wirklich aus derselben Deployment-Vorlage stammen.

kubectl -n <namespace> get pod <pod-a> \
  -o jsonpath='{.metadata.ownerReferences[0].name}{"\n"}'

kubectl -n <namespace> get pod <pod-b> \
  -o jsonpath='{.metadata.ownerReferences[0].name}{"\n"}'

kubectl -n <namespace> get rs <replicaset> -o yaml

Ein identischer ReplicaSet-Hash im Pod-Namen bedeutet in der Regel, dass beide Pods dieselbe PodTemplateSpec teilen, einschließlich:

  • Image und Startkommando.
  • JVM-Parameter und Umgebungsvariablen.
  • ConfigMap, Secret und Mounts.
  • requests, limits, Probes und Scheduling-Regeln.

Gehören sie zum selben ReplicaSet, ist „unterschiedliche JVM-Parameter“ nicht mehr die erste Annahme. Zu prüfen sind stattdessen Traffic, Caches, Batch-Verarbeitung, Connection-Pools, Thread-Anzahl und native Allokationen.

Außerdem ist zu klären, ob historische Belege noch existieren. Alte Pods, alte ReplicaSets und previous logs können vom Rolling Release bereits bereinigt worden sein; auch das Retentionsfenster von Prometheus kann kürzer sein als die Offline-Zeit der Pods. Zuerst lässt sich das Zielzeitfenster abfragen:

max by (pod) (
  max_over_time(
    container_memory_working_set_bytes{
      namespace="<namespace>",
      pod=~"<application>-<revision>-.+",
      container!="",
      image!=""
    }[24h]
  )
)

Liegen für das Zielzeitfenster keine Metriken und Logs vor, sollte das ausdrücklich dokumentiert werden:

可以排除模板差异，但现有证据不足以证明旧 Pod 的具体根因。

Ziehe aus einem Snapshot des neuen Pods keine Schlüsse auf den alten. Die richtige Maßnahme ist dann, NMT, GC-Logs und Monitoring für die nächste Reproduktion bereitzustellen, statt sofort „Speicherleck“ zu verkünden.

Zuerst das richtige Speichermodell aufbauen

flowchart TD
  A["Pod memory working set"] --> B["Java Heap"]
  A --> C["Metaspace und Class Space"]
  A --> D["Thread-Stacks"]
  A --> E["Direct / Mapped Buffer"]
  A --> F["JIT Code Cache und GC-Strukturen"]
  A --> G["JNI, Profiler, glibc arena"]
  A --> H["Shared Libraries und einzelne Datei-Seiten"]

-Xmx begrenzt nur den Java Heap. Die folgende Gleichung stimmt in der Regel nicht:

容器内存 = Xmx

Näher an der Realität ist:

容器内存 ≈ Heap committed + JVM native + 线程栈 + 第三方 native + 工作集中的文件页

Deshalb muss zwischen Container-Limit und -Xmx eine klare Reserve bleiben.

Schritt 1: Prüfen, ob es wirklich ein OOM ist

Zuerst die Exit-Ursache ansehen; nicht bei jedem Restart sofort den Heap anheben:

kubectl -n <namespace> get pod <pod> \
  -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason}{"\n"}{.status.containerStatuses[0].lastState.terminated.exitCode}{"\n"}'

kubectl -n <namespace> describe pod <pod>
kubectl -n <namespace> logs <pod> --previous --tail=300

Häufige Fälle:

BelegWahrscheinlichere Richtung
OOMKilled, Exit Code 137Container hat das cgroup-Limit überschritten oder der Knoten steht unter Speicherdruck
Java-Log zeigt OutOfMemoryError: Java heap spaceJava Heap zu klein oder Objekte können nicht freigegeben werden
MetaspaceProblem bei Classloading, dynamischen Proxies oder der Metaspace-Obergrenze
Exit Code 143In der Regel SIGTERM erhalten, kein OOM
Restart nach wiederholten Probe-FehlernAnwendung blockiert, Dependency-Timeout oder GC-Pausen werden durch Probes verstärkt

Der Kernel-OOMKill kann zu schnell kommen, als dass die JVM noch einen Heap Dump erzeugen könnte. Ein fehlender Heap Dump ist deshalb kein Beleg dafür, dass kein Speicherproblem vorliegt.

Schritt 2: Pod, Prozess und JVM gleichzeitig messen

Kubernetes-Seite:

kubectl top pod -n <namespace> <pod> --containers

kubectl -n <namespace> get pod <pod> \
  -o jsonpath='{.spec.containers[0].resources}{"\n"}'

Container-Seite:

kubectl -n <namespace> exec <pod> -- sh -c '
  grep -E "VmRSS|VmSize|Threads" /proc/1/status
  test -f /sys/fs/cgroup/memory.current && cat /sys/fs/cgroup/memory.current
  test -f /sys/fs/cgroup/memory.stat && \
    grep -E "^(anon|file|kernel|sock) " /sys/fs/cgroup/memory.stat
'

JVM-Seite:

kubectl -n <namespace> exec <pod> -- jcmd 1 VM.version
kubectl -n <namespace> exec <pod> -- jcmd 1 VM.command_line
kubectl -n <namespace> exec <pod> -- jcmd 1 VM.flags
kubectl -n <namespace> exec <pod> -- jcmd 1 GC.heap_info

Der Zeitpunkt der Stichproben muss festgehalten werden. Daten aus der ersten Minute nach dem Start, aus einem Peak und nach einer Stunde Leerlauf lassen sich nicht direkt vergleichen.

Schritt 3: JVM Native Memory mit NMT aufschlüsseln

Beim Start ergänzen:

-XX:NativeMemoryTracking=summary

Wichtig: Der Parameter muss vor -jar stehen:

java \
  -XX:NativeMemoryTracking=summary \
  -jar /app/application.jar

Diese Schreibweise wirkt nicht, weil der Parameter bereits zu einem Anwendungsparameter geworden ist:

java -jar /app/application.jar -XX:NativeMemoryTracking=summary

Nach dem Start eine Baseline setzen und vergleichen:

jcmd 1 VM.native_memory summary scale=MB
jcmd 1 VM.native_memory baseline

# 运行一段代表性业务流量后
jcmd 1 VM.native_memory summary.diff scale=MB

Besonders prüfen:

  • Java Heap
  • Class
  • Thread
  • Code
  • GC
  • Compiler
  • Internal

NMT ist standardmäßig deaktiviert; sowohl summary als auch detail verursachen zusätzlichen Overhead. Die Oracle-Dokumentation nennt als Richtwert etwa 5%–10%. NMT deckt außerdem nicht alle nativen Allokationen aus Drittbibliotheken ab – dass die NMT-Summe kleiner als die RSS ist, ist daher nicht überraschend. Native Memory Tracking

Schritt 4: Die Konfiguration „Xmx gleich Container-Limit“ abschaffen

Die riskanteste Konfiguration sieht so aus:

容器 limit: 4Gi
-Xmx4g

Nähert sich der Heap 4 GiB, bleibt für Metaspace, Thread-Stacks, Direct Buffers, GC-Datenstrukturen und native Bibliotheken kein Platz. Am Ende steht dann eher ein cgroup-OOMKill als ein analysierbares Java-Heap-OOM.

In dieser Runde wurden normale JDK-17-Services so umgestellt, dass die Heap-Obergrenze aus dem Container-Speicher berechnet wird:

-Xms768m
-XX:MaxRAMPercentage=65.0
-XX:+UseG1GC

Bei einem Container-Limit von 3 GiB liegt das maximale Heap-Ziel beispielsweise bei etwa 1.95 GiB; die übrigen etwa 1.05 GiB stehen für Non-Heap und nativen Speicher zur Verfügung. 65% ist nur ein für den aktuellen Service verifizierter Startpunkt; Services mit vielen Threads, vielen Netty-Direct-Buffers oder schweren nativen Abhängigkeiten müssen den Wert weiter senken.

Zwei konkurrierende Obergrenzen sollten nicht gleichzeitig konfiguriert werden:

-Xmx2g
-XX:MaxRAMPercentage=65.0

Sobald ein explizites -Xmx existiert, ist der Prozentsatz nicht mehr das maßgebliche Steuerungsmittel. Die endgültigen Parameter sind mit jcmd 1 VM.flags zu verifizieren, nicht nur per Blick ins YAML.

JDK 17 bietet Container-Erkennung und prozentuale Heap-Parameter; die genaue Bedeutung lässt sich in der JDK-17-Dokumentation zum java-Kommando nachlesen.

Schritt 5: G1 behalten, aber Monitoring nicht mit Full GC beschönigen

JDK-17-Services nutzen weiterhin G1:

-XX:+UseG1GC

Bei einer Untersuchung vor Ort fiel der Heap used von etwa 3.5 GiB auf etwa 1.9 GiB, die RSS folgte jedoch nicht. Das zeigt:

  1. Die Zahl der lebenden Objekte ist tatsächlich gesunken.
  2. JVM oder Allokator können kommittierte Speicherseiten trotzdem behalten.
  3. „Heap used sinkt nach dem GC“ und „der Container gibt sofort dieselbe Menge RSS zurück“ sind nicht dasselbe.

Zwei Pods desselben ReplicaSets: Warum einer 1.8G und der andere 1.2G belegt

In einem weiteren Fall stammten zwei Replikate aus demselben ReplicaSet; Image, JVM-Parameter, Konfiguration und Limit waren vollständig identisch:

MetrikPod APod B
Pod working setca. 1.86 GiBca. 1.24 GiB
G1 committed Heapca. 1.5 GiBca. 768 MiB
Heap used zu diesem Zeitpunktca. 514 MiBca. 212 MiB
Restart / OOM00

Die GC-Logs zeigten, dass Pod A während eines Peaks eine Phase mit dichterer Allokation durchlief; G1 erweiterte dadurch den committed Heap. Nachfolgende mixed GCs senkten die lebenden Objekte schrittweise auf etwa 442 MiB; mit weiterem Leerlauf sank die Auslastung der Old-Generation, und der Heap schrumpfte wieder auf ein Niveau nahe Xms=768M; der Speicherverbrauch des Containers fiel schließlich auf etwa 1.27 GiB.

Vor Ort war Folgendes nicht zu beobachten:

  • OOMKilled.
  • Full-GC-Sturm.
  • kontinuierlich wachsende Humongous Regions.
  • zunehmende Restarts.
  • eine Old-Generation, die nur wächst und nie sinkt.

Diese Belege passen daher besser zu „kurzzeitige Allokation hebt den committed Heap an, G1 schrumpft verzögert“ als zu einem Speicherleck.

Die korrekte gleichzeitige Erfassung:

kubectl top pod <pod-a> <pod-b> -n <namespace>

kubectl exec -n <namespace> <pod-a> -- jcmd 1 GC.heap_info
kubectl exec -n <namespace> <pod-b> -- jcmd 1 GC.heap_info

kubectl exec -n <namespace> <pod-a> -- \
  jcmd 1 VM.native_memory summary scale=MB
kubectl exec -n <namespace> <pod-b> -- \
  jcmd 1 VM.native_memory summary scale=MB

Zusätzlich müssen die GC-Logs auf denselben Zeitpunkt ausgerichtet werden. Wer nur zwei kubectl top-Werte vergleicht, kann nicht erkennen, ob die Differenz von live objects, committed Heap oder native memory stammt.

Führe kein periodisches System.gc() aus, nur damit die Kurven fallen, und setze kein sehr kurzes G1PeriodicGCInterval global für alle Services. Periodische GCs kosten CPU und verschleiern echte Objektallokationsprobleme; nur wenn nachweislich lange Leerlauffenster existieren, lohnt eine separate Bewertung.

Wenn das aktuelle Deployment in Git den periodischen GC bereits entfernt hat, das laufende jcmd 1 VM.flags ihn aber weiterhin zeigt, stammen die Pods in Produktion noch aus einem alten spec. kubectl rollout restart baut nur nach dem aktuellen Cluster-spec neu und liest Git nicht automatisch; zuerst müssen Template-Rendering und Release ausgeführt werden.

Oracles wichtigste Empfehlung für G1 bleibt, möglichst die Standardstrategie zu verwenden, nur eine passende Heap-Obergrenze zu setzen und danach anhand der GC-Logs zu justieren. Garbage-First Garbage Collector Tuning

Schritt 6: Metaspace begrenzen, aber nicht willkürlich zu niedrig

Startpunkt der aktuellen Vorlage:

-XX:MetaspaceSize=256m
-XX:MaxMetaspaceSize=512m

Das verhindert, dass abnormales Classloading unbegrenzt Container-Speicher belegt; ein zu kleines MaxMetaspaceSize erzeugt jedoch direkt:

java.lang.OutOfMemoryError: Metaspace

Vor und nach der Änderung vergleichen:

jcmd 1 VM.native_memory summary scale=MB
jcmd 1 GC.class_histogram

Wächst die Zahl der Klassen kontinuierlich, sind zuerst dynamische Proxies, Script-Engines, Hot-Reload-ClassLoader und wiederholt erzeugte Klassen zu prüfen, statt die Obergrenze einfach weiter anzuheben.

Schritt 7: Den dauerhaft laufenden Profiler abschalten

Diagnosewerkzeuge beanspruchen selbst Speicher. Früher lud die Vorlage den nativen JProfiler-Agent standardmäßig; auch ohne verbundene Session blieben Agent, Sampling-Strukturen und zusätzliche Events dauerhaft im Prozess.

Standardmäßig deaktivieren:

env:
  - name: JPROFILER_ENABLED
    value: "false"

Das Startskript ergänzt den Agent nur bei der Fehlersuche:

set -- java

if [ "${JPROFILER_ENABLED:-false}" = "true" ]; then
  set -- "$@" \
    -agentpath:/opt/jprofiler/bin/linux-x64/libjprofilerti.so=port=8849,nowait
fi

Nach der Analyse den Schalter wieder auf false setzen und per Rolling Release ausrollen. Ein Profiler ist eine kurzfristige Diagnosefähigkeit und sollte kein fester Bestandteil jedes Produktions-Pods sein.

Schritt 8: Thread-Stacks und aufgestaute Nachrichten angehen

Die Vor-Ort-Daten eines leichten Service: Heap used etwa 280 MiB, RSS etwa 1.2 GiB, mehr als 200 Threads. Weiteres Verkleinern des Heaps bringt hier wenig; zuerst ist die Herkunft der Threads zu klären:

jcmd 1 Thread.print > /tmp/threads.txt
grep '^"' /tmp/threads.txt | wc -l

Bestandsaufnahme der Schwerpunkte:

  • Arbeitsthreads des Web-Containers.
  • Wartungsthreads der Datenbank-Connection-Pools.
  • Client-Threads von Kafka, RabbitMQ und Nacos.
  • XXL-JOB, Scheduled Tasks und eigene Thread-Pools.
  • ForkJoinPool und asynchrone Executors.

Ein global sehr kleines -Xss ist als erster Schritt nicht empfehlenswert. Tiefe Aufrufketten, komplexe Ausdrücke oder große Stack-Frames können sonst einen StackOverflowError auslösen. Robuster ist diese Reihenfolge:

  1. Doppelte Thread-Pools entfernen.
  2. Thread-Pool-Maxima an die Container-CPU koppeln.
  3. Concurrency und Prefetch der Message-Consumer reduzieren.
  4. -Xss erst zuletzt per Lasttest prüfen.

Message-Consumer können mit einer konservativen Konfiguration starten:

env:
  - name: SPRING_RABBITMQ_LISTENER_SIMPLE_CONCURRENCY
    value: "1"
  - name: SPRING_RABBITMQ_LISTENER_SIMPLE_MAX_CONCURRENCY
    value: "3"
  - name: SPRING_RABBITMQ_LISTENER_SIMPLE_PREFETCH
    value: "10"

Es geht nicht nur darum, Threads zu sparen. Bei zu großem prefetch bleiben viele noch nicht bestätigte Nachrichten samt Geschäftsobjekten gleichzeitig im Heap. Nach der Änderung müssen Konsum-Latenz und Backlog verifiziert werden, nicht nur der Speicherrückgang.

Schritt 9: glibc arena begrenzen

In Linux-glibc-Umgebungen können native Allokationen aus vielen Threads mehrere malloc-Arenas erzeugen. Nach der Freigabe von Geschäftsobjekten gibt der Allokator freie Arenas nicht unbedingt sofort ans Betriebssystem zurück – sichtbar ist dann: Der Heap ist bereits gesunken, die RSS bleibt erhöht.

Der aktuell verwendete konservative Startpunkt:

env:
  - name: MALLOC_ARENA_MAX
    value: "4"

Es ist kein JVM-Parameter; unter Alpine/musl oder mit anderen Allokatoren ist seine Wirkung nicht garantiert. Zu kleine Werte können die Lock-Konkurrenz bei nativen Allokationen aus vielen Threads erhöhen; daher sind parallel zu beobachten:

  • CPU-Auslastung.
  • P95/P99 der Requests.
  • Hot Spots nativer Allokation.
  • ob sich die RSS tatsächlich verbessert.

Schritt 10: Belege für das nächste OOM hinterlassen

Empfohlen bleibt:

-XX:+HeapDumpOnOutOfMemoryError
-XX:+ExitOnOutOfMemoryError
-XX:HeapDumpPath=/data/dumps/<app>/<pod>/heap.hprof
-Xlog:gc*,safepoint:file=/data/logs/gc-%t.log:time,uptime,level,tags:filecount=10,filesize=20M

Der Heap-Dump-Pfad muss:

  • beschreibbar sein,
  • ausreichend Platz bieten,
  • pro Pod eindeutig sein, damit sich Replikate nicht gegenseitig überschreiben,
  • über einen Cleanup- und Download-Prozess verfügen, damit das Shared Volume nicht vollgeschrieben wird.

GC-Logs beantworten „wann gesammelt wird, wie viel vor und nach der Sammlung, wie lange pausiert wird“; der Heap Dump beantwortet „welche Objekte den Heap belegen“. Beides kann einander nicht ersetzen.

Schritt 11: Kubernetes-Ressourcen und JVM-Parameter gemeinsam kalkulieren

Ein beispielhafter Startpunkt für einen normalen Service:

resources:
  requests:
    cpu: 250m
    memory: 1536Mi
  limits:
    memory: 3Gi

Dazu:

-Xms768m
-XX:MaxRAMPercentage=65.0

Drei Fragen sind zu beantworten:

  1. Wie hoch ist der P95-Speicherbedarf im Steady State, und deckt das request den normalen Betrieb ab?
  2. Wie hoch sind Start- und Batch-Peaks, und bleibt beim limit eine Sicherheitsreserve?
  3. Wie viel brauchen neben dem maximalen Heap noch Thread, Class, Code, GC, Direct und native zusammen?

Schwere Services dürfen die request/limits normaler Services nicht übernehmen. Für sie sind eigene Baselines zu erstellen; außerdem ist die Knotenkapazität zu berücksichtigen, wenn beim Rolling Release alte und neue Pods gleichzeitig laufen.

Schritt 12: Probes dürfen kurze Engpässe nicht in einen Restart-Sturm verwandeln

Unter Speicher- oder Abhängigkeitsdruck kann auch der Health-Endpoint langsamer werden. Erlaubt die liveness nur einige Dutzend Sekunden, startet Kubernetes die Anwendung genau dann wiederholt neu, wenn sie am stärksten ausgelastet ist:

启动分配高峰 → 探针超时 → 重启 → 再次启动分配高峰

Ein möglicher Ausgangspunkt ist die folgende Aufgabentrennung:

startupProbe:
  httpGet:
    path: /actuator/health/liveness
    port: http
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 30

readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: http
  periodSeconds: 5
  timeoutSeconds: 3
  failureThreshold: 2

livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: http
  periodSeconds: 10
  timeoutSeconds: 5
  failureThreshold: 12
  • startup gibt dem langsamen Start ein ausreichendes Fenster.
  • readiness zieht den Traffic zuerst schnell ab.
  • liveness behandelt nur echte, nicht mehr behebbare Prozesszustände.

Großzügigere Probes beheben kein Speicherleck, verhindern aber, dass ein kurzer GC, Datenbankschwankungen oder Dependency-Timeouts zu einem Cluster-weiten Restart-Sturm eskalieren.

Eine wiederverwendbare JDK-17-Startbaseline

#!/bin/sh
set -eu

DUMP_DIR="/data/dumps/${APP_NAME}/${HOSTNAME}"
mkdir -p "$DUMP_DIR" /data/logs

set -- java \
  -XX:+UseContainerSupport \
  -Xms768m \
  -XX:MaxRAMPercentage=65.0 \
  -XX:+UseG1GC \
  -XX:MetaspaceSize=256m \
  -XX:MaxMetaspaceSize=512m \
  -XX:+HeapDumpOnOutOfMemoryError \
  -XX:+ExitOnOutOfMemoryError \
  -XX:HeapDumpPath="$DUMP_DIR/heap.hprof" \
  -Xlog:gc*,safepoint:file=/data/logs/gc-%t.log:time,uptime,level,tags:filecount=10,filesize=20M

if [ "${NMT_ENABLED:-false}" = "true" ]; then
  set -- "$@" -XX:NativeMemoryTracking=summary
fi

if [ "${JPROFILER_ENABLED:-false}" = "true" ]; then
  set -- "$@" \
    -agentpath:/opt/jprofiler/bin/linux-x64/libjprofilerti.so=port=8849,nowait
fi

set -- "$@" -jar /app/application.jar
exec "$@"

Nach dem Rollout ist das tatsächlich verwendete Kommando zu verifizieren:

jcmd 1 VM.command_line
jcmd 1 VM.flags
jcmd 1 GC.heap_info

Empfohlene schrittweise Rollout-Reihenfolge

Nicht ein Dutzend Parameter auf einmal ändern – sonst lässt sich nach dem Speicherrückgang nicht mehr sagen, welcher Parameter gewirkt hat.

Phase A: Zuerst nur Beobachtung ergänzen

  • Pod working set, RSS, Heap und Thread-Anzahl aufzeichnen.
  • Rotierende GC-Logs ergänzen.
  • NMT auf einem Replikat kurzzeitig aktivieren.

Phase B: Dauerhafte Diagnose-Overheads entfernen

  • JProfiler standardmäßig deaktivieren.
  • MALLOC_ARENA_MAX=4 auf glibc-Images pilotieren.
  • CPU und Latenz vergleichen und sicherstellen, dass keine deutliche Regression auftritt.

Phase C: Heap und Container-Reserve neu berechnen

  • Von einem festen -Xmx4g auf einen berechneten Prozentsatz oder ein kleineres explizites -Xmx wechseln.
  • Mindestens 30%–35% für Non-Heap und native reservieren.
  • Getrennte Baselines für normale und schwere Services anlegen.

Phase D: Threads und In-flight-Nachrichten in den Griff bekommen

  • Thread-Pools reduzieren.
  • Nachrichten-Concurrency und prefetch senken.
  • Backlog, Durchsatz und Geschäftslatenz verifizieren.

Phase E: Ressourcen und Probes kalibrieren

  • request/limit an Steady State und Peaks anpassen.
  • Sicherstellen, dass der Knoten beim Rolling Release temporäre Replikate aufnehmen kann.
  • readiness zieht Traffic schnell ab, liveness vermeidet irrtümliche Beendigungen.

Erst nach mindestens einem echten Peak eine Schlussfolgerung ziehen. Speicher von 4 GiB auf 1.5 GiB zu senken ist kein Erfolg, wenn dafür häufige Full GCs oder Nachrichten-Backlogs in Kauf genommen werden.

Fazit

Was in dieser JDK-17-Runde wirklich geholfen hat, ist kein einzelner „Wunderparameter“, sondern das gleichzeitige Verschärfen der folgenden Grenzen:

  1. Der Heap frisst den Container nicht mehr auf; nativer Speicher erhält klar definierten Raum.
  2. G1 bleibt einfach: zuerst Objektallokation lösen, statt GC periodisch zu erzwingen.
  3. JProfiler wird nur noch bei Bedarf aktiviert.
  4. Mit NMT, RSS und cgroup-Daten Heap und Native unterscheiden.
  5. Threads, Nachrichten-Concurrency und prefetch reduzieren.
  6. glibc arena begrenzen und Nebenwirkungen über Latenz und CPU verifizieren.
  7. GC-Logs, Heap Dumps und Exit-Ursachen aufbewahren, damit sich der nächste Vorfall aufarbeiten lässt.
  8. Mit sinnvollen Probes verhindern, dass kurze Engpässe zu Restart-Stürmen werden.

Der wichtigste Effekt dieser Optimierung ist der Wechsel von „allen Services 4G geben“ zu „jede Serviceklasse hat ein erklärbares Speicherbudget“.
