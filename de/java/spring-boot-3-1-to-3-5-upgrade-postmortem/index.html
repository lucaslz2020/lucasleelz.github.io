Spring Boot von 3.1.7 auf 3.5.13: Drei Probleme, die sich erst nach erfolgreicher Kompilierung zeigten

Postmortem zur Aktualisierung von Spring Boot 3.1.7 auf 3.5.13 und Java 17 auf Java 25: analysiert werden doppelte Spring-Batch-Job-Namen, eine mehrdeutige TaskExecutor-Injektion und ein inkompatibler MongoDB-4.2-Health-Check.

Dieser Beitrag stammt aus einer realen Aktualisierung. Servicenamen, Projektkoordinaten, Pods, Knoten, Images, Namespaces und Organisationsinformationen wurden anonymisiert bzw. verallgemeinert. Im Mittelpunkt steht die Vorgehensweise bei der Fehlersuche; übernimm Konfigurationen oder Korrekturen nicht ungeprüft in andere Dienste.

Kürzlich habe ich zwei Spring-Boot-Dienste von 3.1.7 auf 3.5.13 aktualisiert und die Laufzeit von Java 17 auf Java 25 umgestellt. Maven-Kompilierung und -Paketierung liefen durch, doch nach der Bereitstellung im Test-Kubernetes-Cluster traten bei beiden Diensten nacheinander Startfehler bzw. Fehler in der vollständigen Health-Check-Prüfung auf.

Das Bemerkenswerteste an dieser Aktualisierung: Die Probleme lagen nicht auf der Syntaxebene des Geschäftscodes, sondern in verändertem Standardverhalten des Frameworks. Im Folgenden sind die Probleme in der Reihenfolge der tatsächlichen Fehlersuche dargestellt.

Dieser Beitrag ist das Postmortem zur abgeschlossenen Aktualisierung von 3.1.7 → 3.5.13. Der nächste Beitrag Von Spring Boot 3.5.13 auf 4.1: Abgeschlossenes von echten Risiken trennen behandelt nur die in der nächsten Phase neu hinzukommenden Kompatibilitätsgrenzen und wiederholt nicht die hier beschriebenen Abläufe für Start, Health-Check und Middleware-Abnahme.

Zuerst eine Upgrade-Diagnosekette aufbauen

flowchart LR
  A["Spring Boot und JDK aktualisieren"] --> B["Mit Ziel-JDK kompilieren und paketieren"]
  B --> C["Start-Logs des neuen Pods"]
  C --> D["Vollständiger /actuator/health"]
  D --> E["Middleware-Befehle und Protokollverifikation"]
  E --> F["Rolling Release und Endpoint-Wechsel"]

Bei einem fehlgeschlagenen Upgrade darf man nicht allein deshalb auf die Ursache schließen, weil eine Komponente in den Fehlerlogs auftaucht. Zunächst ist zu unterscheiden, ob der Fehler bei der Bean-Erstellung, der Framework-Initialisierung, dem Health-Check oder einer Geschäftsanfrage auftritt; für jede Ebene sind dann unabhängige Belege zu sammeln.

Upgrade-Umfang und Abnahmegrenzen

Die Spring-Boot-Version im Parent-POM wurde von 3.1.7 auf 3.5.13 angehoben, die JDK-Version von 17 auf 25.

Vor dem Upgrade sind zwei Dinge zu klären:

  1. CI, Basis-Container-Image und lokales Maven verwenden dieselbe JDK-Generation;
  2. „Kompiliert“ allein ist kein ausreichendes Abnahmekriterium – mindestens der Anwendungsstart, der vollständige Actuator-Health-Check und die Verbindung zu kritischen Middleware-Komponenten sind zu verifizieren.

Alle drei Probleme gehören zur zweiten Kategorie: Sie blockieren die Kompilierung nicht, treten aber beim Start neuer Replicas oder bei der tatsächlichen Probenprüfung zutage.

Problem 1: Doppelte Spring-Batch-Job-Namen verhindern den Start der Anwendung

Symptom: Neue Replicas scheitern bei der Job-Registrierung

Einer der Dienste warf beim Start eine ähnliche Exception:

DuplicateJobException: A job configuration with this name [initPriceJob] was already registered

Zwei verschiedene @Bean-Methoden deklarieren jeweils einen Job, aber der interne Name eines der JobBuilder lautet weiterhin initPriceJob.

@Bean
public Job productionInitPriceJob(...) {
    return new JobBuilder("initPriceJob", jobRepository)
        // ...
        .build();
}

Beweis und Ursache: Der Bean-Name ist nicht der Batch-Job-Name

Nach dem Spring-Batch-Upgrade sammelt die Standardkonfiguration während der Container-Initialisierung alle Job-Beans und registriert sie im JobRegistry. Dadurch wird das zuvor latente Problem doppelter interner Job-Namen beim Start der neuen Version zu einem deterministischen Fehler.

Hier sind zwei Namen zu unterscheiden:

  • Spring-Bean-Name: z. B. productionInitPriceJob;
  • Spring-Batch-Job-Name: der Name, der in new JobBuilder("...") übergeben wird.

Für die Deduplizierung in der JobRegistry ist ausschließlich der zweite Name maßgeblich.

Fix: JobBuilder-Namen eindeutig machen

Der interne Name des JobBuilder wird eindeutig gemacht und an den fachlichen Job angeglichen:

return new JobBuilder("productionInitPriceJob", jobRepository)
    // ...
    .build();

Verifikation und Erkenntnisse

Beim Spring-Batch-Upgrade sollte man alle new JobBuilder(...) global durchsuchen und prüfen, ob die String-Namen doppelt vergeben sind, statt nur die @Bean-Methodennamen zu betrachten.

Problem 2: TaskExecutor: von „Injektion per Name“ zu „zwei Kandidaten-Beans“

Symptom: Zwei Kandidaten-Beans führen zum Injektionsfehler

Der andere Dienst startete nicht:

Parameter 0 of ... required a single bean, but 2 were found:
 - applicationTaskExecutor
 - taskScheduler

Der ursprüngliche Code verwendete Feldinjektion:

@Autowired
private TaskExecutor taskExecutor;

Der Dienst nutzt gleichzeitig asynchrone und geplante Aufgaben. Nach dem Upgrade enthält der Container sowohl applicationTaskExecutor als auch taskScheduler; beide passen zu TaskExecutor, sodass Spring nicht mehr entscheiden kann, welche der beiden injiziert werden soll.

Beweis und Ursache: Die frühere implizite Namenszuordnung gilt nicht mehr

In der alten Auto-Konfiguration wurde der Standard-Async-Executor zusätzlich unter dem Namen taskExecutor bereitgestellt. Stimmte der Feldname exakt mit diesem Alias überein, konnte Spring die Injektion über die Namenszuordnung auflösen.

Die neue Auto-Konfiguration behält applicationTaskExecutor bei, stellt den Alias taskExecutor aber nicht mehr in gleicher Weise bereit. Zusätzlich wird taskScheduler bei aktivierter Scheduling-Funktion ebenfalls zum Kandidaten-Bean für TaskExecutor, wodurch das bisherige implizite Verhalten auf Basis des Feldnamens wegfällt.

Fix: Die Thread-Pool-Auswahl explizit im Code verankern

Klar benannt ist der anwendungsseitige asynchrone Thread-Pool:

@Autowired
@Qualifier("applicationTaskExecutor")
private TaskExecutor taskExecutor;

Gibt es im Projekt mehrere Injektionspunkte desselben Typs, sollten alle gesucht und einzeln korrigiert werden, z. B.:

rg 'TaskExecutor taskExecutor' src/main/java

Verifikation und Erkenntnisse

Geschäftscode sollte sich nicht auf historische Aliasnamen von Spring-Boot-Auto-Konfigurations-Beans verlassen. Bei Typen wie Thread-Pools, DataSources oder CacheManager, bei denen leicht mehrere Kandidaten-Beans entstehen, sollte @Qualifier verwendet oder auf Konstruktor-Injektion mit qualifizierendem Parameternamen umgestellt werden.

Problem 3: MongoDB wirkt „nicht erreichbar“ – in Wahrheit ist der Health-Check-Befehl inkompatibel

Symptom: MongoDB wirkt „nicht erreichbar“

Nach dem Start der Anwendung erscheinen in den Logs wiederholt:

MongoDB health check failed
Command failed with error 59 (CommandNotFound):
no such command: 'hello'

Die erste Reaktion richtet sich oft auf DNS, Service, Zugangsdaten oder Netzwerk-Policies. Eine Verifikation innerhalb des Clusters zeigte jedoch:

db.adminCommand({ ping: 1 });
// { "ok" : 1 }

db.adminCommand({ isMaster: 1 });
// { "ismaster" : true, ..., "ok" : 1 }

db.adminCommand({ hello: 1 });
// no such command: 'hello'

Das MongoDB der Testumgebung läuft auf 4.2.8; der Mongo Java Driver hat die Verbindung bereits erfolgreich aufgebaut. Der Fehler tritt auf, wenn der vollständige /actuator/health-Aufruf den Standard-MongoHealthIndicator verwendet.

Beweis und Ursache: Der Actuator-Befehl schlägt fehl, nicht die TCP-Verbindung

Der Mongo-Health-Check von Spring Boot 3.1 führt aus:

mongoTemplate.executeCommand("{ isMaster: 1 }");

Spring Boot 3.5 stattdessen:

mongoTemplate.executeCommand("{ hello: 1 }");

MongoDB 4.2 kennt den Befehl hello nicht, daher lautet das Health-Ergebnis DOWN. Entscheidend ist: Ein fehlgeschlagener Health-Check bedeutet nicht, dass die Anwendung keine Mongo-Verbindung aufbauen kann. Erst die Prüfung anhand von ping, Treiber-Verbindungslogs und fachlichen Lese-/Schreibzugriffen zeigt, ob ein Protokoll-, Authentifizierungs- oder Netzwerkproblem vorliegt.

Fix: Echte Prüfung beibehalten, inkompatiblen Standardbefehl überschreiben

Nicht zu empfehlen ist, den Mongo-Health-Check nur für ein grünes Ergebnis zu deaktivieren:

management.health.mongo.enabled=false

Dabei ginge das echte Signal zur Mongo-Verfügbarkeit verloren.

Gewählt wurde stattdessen der Weg, die Health-Check-Semantik beizubehalten und den Standard-Contributor zu überschreiben: eine mit MongoDB 4.2 kompatible Prüfimplementierung unter demselben Bean-Namen wie der Standard-Contributor.

@Configuration(proxyBeanMethods = false)
public class MongoHealthConfiguration {

    @Bean(name = "mongoHealthContributor")
    public HealthIndicator mongoHealthContributor(MongoTemplate mongoTemplate) {
        return new AbstractHealthIndicator("MongoDB health check failed") {
            @Override
            protected void doHealthCheck(Health.Builder builder) throws Exception {
                Document result = mongoTemplate.executeCommand("{ isMaster: 1 }");
                builder.up().withDetail("maxWireVersion", result.getInteger("maxWireVersion"));
            }
        };
    }
}

Sobald die Auto-Konfiguration eine Bean namens mongoHealthContributor findet, überspringt sie die Standardimplementierung. /actuator/health prüft Mongo damit weiterhin real und bleibt zugleich mit der lokalen 4.2-Instanz kompatibel.

Verifikation und Erkenntnisse

Bei Framework-Upgrades gehört auch der Actuator zur Laufzeit-Kompatibilität. Gerade Health-Check-Befehle für Datenbanken, Message Queues und Service-Registrys können früher als der Geschäftscode auf Kompatibilitätsprobleme mit alten Server-Versionen stoßen.

Die langfristige Lösung bleibt die geplante Aktualisierung der MongoDB-Server. Die kompatible Implementierung auf Anwendungsseite eignet sich für Testumgebungen und die Übergangsphase der Migration.

Schritt 4: Die Verifikation als Upgrade-Abnahme-Checkliste festhalten

Allein mvn package genügt nicht als Beleg für ein erfolgreiches Upgrade. Bei Major-Upgrades von Spring Boot oder Upgrades über mehrere Minor-Versionen empfiehlt sich die folgende Abnahmereihenfolge:

  1. Mit der Ziel-JDK kompilieren und paketieren;
  2. Neue Replicas lokal oder in der Testumgebung starten und bestätigen, dass keine Bean-Injektions-, Auto-Konfigurations- oder Job-Registrierungsfehler auftreten;
  3. Den vollständigen /actuator/health abfragen, nicht nur die liveness/readiness von Kubernetes;
  4. Prüfen, dass kritische Komponenten wie DB, Redis, RabbitMQ, MongoDB und Nacos alle UP sind;
  5. Gezielte Regressionstests für Job-Namen, Thread-Pool-Injektion, Serialisierungskonfiguration und Middleware-Protokollbefehle durchführen;
  6. Nach dem Rolling Release bestätigen, dass die neuen Pods Ready sind, der Endpoint gewechselt hat und die alten Pods ordentlich beendet wurden.

Zusammenfassung: Implizite Framework-Verträge explizit machen

Die Aktualisierung von Spring Boot 3.1.7 auf 3.5.13 brachte keine API-Kompilierungsfehler im klassischen Sinne, legte aber drei verstecktere Problemklassen offen:

TypUrsacheFix-Prinzip
Spring BatchBeim Start werden alle Jobs strikt registriert; doppelte interne Namen werden sichtbarJobBuilder-Namen global eindeutig halten
Async-Thread-PoolAlias-Änderung in der Auto-Konfiguration; mehrere TaskExecutor-KandidatenExplizites @Qualifier, keine Abhängigkeit vom Feldnamen
Mongo-Health-CheckStandardbefehl wechselt von isMaster zu hello; älteres Mongo unterstützt ihn nichtHealth-Check überschreiben und echte Erreichbarkeitsprüfung beibehalten

Der Kern eines Framework-Upgrades ist nicht, „die Versionsnummer hochzuziehen“, sondern die Verträge zu erkennen und zu verifizieren, die bisher implizit vom Standardverhalten abhingen, ohne je explizit im Geschäftscode zu stehen.

Treten nach dem Upgrade Probleme mit Container-Verzeichnissen, veralteten Properties, commons-logging, Nacos Logback oder optionalen JDBC-Treibern auf, siehe Spring Boot 3 Container-Start-Postmortem.
