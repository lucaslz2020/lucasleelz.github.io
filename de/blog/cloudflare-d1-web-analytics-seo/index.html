Statistik und SEO für einen statischen Blog: Cloudflare Web Analytics + D1 in der Praxis

Dokumentiert den vollständigen Weg eines Astro-Statikblogs zu Cloudflare Web Analytics, Pages Functions und D1 sowie die systematische Ergänzung von Canonical, Open Graph, JSON-LD, Sitemap und automatisierten SEO-Prüfungen.

Nachdem der Blog zu Astro und Cloudflare Pages migriert war, waren die Seiten leicht genug und ließen sich vollständig statisch bereitstellen. Eine Website, auf der man langfristig schreibt, muss aber zwei weitere Fragen beantworten: ob Artikel wirklich gelesen werden und ob Suchmaschinen den Inhalt richtig verstehen.

Zunächst habe ich erwogen, eine In-Memory-Datenbank in das Projekt einzubetten. Auf einem normalen Serverprogramm mag das als temporärer Cache funktionieren, für statische Websites und Serverless-Laufzeiten ist es aber ungeeignet: Statische Dateien haben keinen dauerhaft laufenden Prozess, und Instanzen von Pages Functions können jederzeit erstellt und wieder freigegeben werden. Zählerstände im Arbeitsspeicher lassen sich weder persistieren noch zwischen mehreren Instanzen teilen.

Am Ende habe ich Cloudflare Web Analytics + Pages Functions + D1 verwendet: Web Analytics übernimmt die Zugriffstrends auf Website-Ebene, D1 die Leseaufrufe pro Artikel und benutzerdefinierte Klickereignisse. Zusätzlich habe ich SEO-Metadaten, strukturierte Daten und Build-Prüfungen ergänzt. Dieser Artikel dokumentiert den vollständigen Prozess – vom Design über die Implementierung bis zum Go-live und zur Fehlersuche.

Wer sich zuerst über die Technologieauswahl des Blogs, die Veröffentlichung über zwei Repositories und die Domain-Migration informieren möchte, kann den vorherigen Beitrag lesen: Persönlichen Blog von Grund auf neu schreiben: Astro + React + MDX + Cloudflare Pages.

Gesamtarchitektur

Diese Statistiklösung macht aus dem Blog keine dynamische Website. Artikel, Startseite, Archiv und Tags werden weiterhin von Astro zu statischem HTML gebaut; nur /api/analytics wird von Pages Functions übernommen.

flowchart LR
  A[Besuch von lucaslz.com] --> B[Cloudflare CDN]
  B --> C[Astro statische Seiten]
  B --> D[Web Analytics]
  C --> E[Frontend-Statistikskript]
  E --> F[/api/analytics<br/>Pages Functions]
  F --> G[(Cloudflare D1)]
  H[GitHub Actions] --> I[Build und SEO-Prüfungen]
  I --> B

Die beiden Statistiksysteme lösen jeweils unterschiedliche Fragen:

Referrer, Länder und Performance-KennzahlenJaWird nicht erfasst

Web Analytics beobachtet die gesamte Website, D1 beantwortet konkrete Fragen zu Inhalt und Interaktionen. Sie duplizieren sich nicht, sondern ergänzen sich.

Warum keine In-Memory-Datenbank

Cloudflare Pages besteht weiterhin in erster Linie aus statischen Dateien. Selbst mit Pages Functions laufen Anfragen in isolierten Worker-Umgebungen, die bei Bedarf erstellt werden; man kann nicht davon ausgehen, dass eine JavaScript-Variable dauerhaft existiert.

Wenn Leseaufrufe so erfasst werden:

let views = 0;

export function onRequest() {
  views += 1;
  return Response.json({ views });
}

Das führt zu drei grundlegenden Problemen:

  1. Nach einem Neustart der Instanz fallen die Daten auf null zurück.
  2. Mehrere Instanzen führen jeweils einen eigenen Zähler.
  3. Auch eine neue Bereitstellung verliert den bisherigen Zustand.

Daten in LocalStorage bleiben nur im Browser des jeweiligen Besuchers und ergeben keinen Gesamtwert für die Website. Es braucht also einen echten dauerhaften Speicher. D1 ist die von Cloudflare verwaltete SQLite-Datenbank, die sich direkt an Pages Functions binden lässt und damit die einfachste Deployment-Struktur bietet.

Schreibvolumen mit Tagesaggregation begrenzen

Statistiksysteme verfallen leicht in das Design „pro Zugriff ein Detaildatensatz“. Ein persönlicher Blog braucht in der Regel aber keine Logs auf Besucherebene. Mir geht es vielmehr darum, wie oft ein Artikel an einem bestimmten Tag aufgerufen oder ein bestimmter Einstiegspunkt angeklickt wurde.

Deshalb verwendet das Tabellenschema eine tägliche Aggregation:

CREATE TABLE IF NOT EXISTS event_daily (
  event TEXT NOT NULL,
  path TEXT NOT NULL,
  target TEXT NOT NULL DEFAULT '',
  stat_date TEXT NOT NULL,
  count INTEGER NOT NULL DEFAULT 0 CHECK (count >= 0),
  updated_at TEXT NOT NULL DEFAULT (datetime('now')),
  PRIMARY KEY (event, path, target, stat_date)
) WITHOUT ROWID;

CREATE INDEX IF NOT EXISTS idx_event_daily_date
  ON event_daily (stat_date, event);

Der zusammengesetzte Primärschlüssel besteht aus event + path + target + stat_date. Am selben Tag wird für dasselbe Ereignis unter demselben Pfad und Ziel nur eine Zeile aktualisiert; es werden keine IP-Adressen, User-Agent-Strings, vollständigen Referer oder Nutzeridentitäten gespeichert.

Die Vorteile dieses Designs:

  • Die Datenmenge wächst mit „Seiten × Ereignisse × Tage“ statt mit der Anzahl der Zugriffe.
  • Für die kumulierte Leseanzahl eines Artikels genügt es, die Tageszähler zu summieren.
  • Es müssen keine Besucherprofile gepflegt werden, und die Datenschutzgrenze ist klarer.
  • Speicher- und Abfragekosten bleiben auch bei steigendem Traffic beherrschbar.

Aktuell sind folgende Ereignisse erlaubt:

page_view
article_click
article_impression
tag_click
search_click
nav_click
toc_click
cta_click
outbound_click

Die Statistik-API der Pages Functions

Sobald functions/api/analytics.js im Projektstammverzeichnis liegt, bildet Cloudflare Pages es wie folgt ab:

GET  /api/analytics?event=page_view&path=/article
POST /api/analytics

GET liest die kumulierte Leseanzahl eines Artikels. POST nimmt Ereignisse entgegen und aktualisiert den Tageszähler per Upsert:

await env.BLOG_ANALYTICS.prepare(
  `INSERT INTO event_daily
     (event, path, target, stat_date, count, updated_at)
   VALUES (?1, ?2, ?3, ?4, 1, datetime('now'))
   ON CONFLICT (event, path, target, stat_date)
   DO UPDATE SET
     count = count + 1,
     updated_at = datetime('now')`,
)
  .bind(event, path, target, statDate)
  .run();

Die API setzt außerdem einige notwendige Einschränkungen durch:

  • Es werden nur Ereignisse aus der Whitelist akzeptiert.
  • Abschließende Schrägstriche und Query-Parameter werden aus Pfaden entfernt.
  • Der Anforderungsbody ist auf 2 KB begrenzt.
  • POST akzeptiert nur Same-Origin-Anfragen.
  • Bei externen Links werden nur Domain und Pfad gespeichert, keine Query-Parameter.
  • Alle Antworten setzen Cache-Control: no-store.

Diese Einschränkungen können nicht jeden böswilligen Traffic verhindern, aber sie verhindern, dass die API zu einer Sammelstelle für beliebige Strings wird, und verringern das Risiko, dass sensible Query-Parameter in die Datenbank gelangen.

Wie das Frontend Daten erfasst und anzeigt

Nach dem Laden der Seite schreibt die Statistik-Komponente ein page_view an /api/analytics. Die API gibt direkt nach dem Schreiben den kumulierten Wert zurück, und die Artikelseite zeigt anschließend, wie oft der Artikel gelesen wurde.

const response = await fetch("/api/analytics", {
  method: "POST",
  headers: { "content-type": "application/json" },
  body: JSON.stringify({
    event: "page_view",
    path: window.location.pathname,
  }),
  credentials: "same-origin",
});

const data = await response.json();
showPageViews(data.total);

Damit der Zähler beim Aktualisieren innerhalb derselben Sitzung nicht immer weiter steigt, dedupliziert das Frontend page_view- und Impression-Ereignisse über sessionStorage. Der Lesezähler ist also keine exakte Zahl eindeutiger Besucher, sondern ein leichtgewichtiger, nachvollziehbarer Lesezähler auf Sitzungsebene.

Klickereignisse werden über navigator.sendBeacon() gesendet. Wenn ein Besucher auf einen Link klickt und die Seite sofort verlässt, eignet sich ein Beacon für diese letzte kleine Datenübertragung besser als eine normale asynchrone Anfrage.

Alle Tracking-Punkte werden über HTML-data-*-Attribute deklariert; die Komponenten müssen die Statistik-Implementierung nicht direkt kennen:

<a
  href={postHref}
  data-analytics-event="article_click"
  data-analytics-target={postHref}
>
  阅读文章
</a>

D1 in Cloudflare erstellen und binden

Nach der Implementierung muss in der Cloudflare-Konsole noch eine echte Datenbank eingerichtet werden.

1. Datenbank erstellen

Navigieren zu:

Storage & databases
→ D1 SQL Database
→ Create database

Die Datenbank heißt:

lucaslz-blog-analytics

Nach der Erstellung die D1 Console öffnen, migrations/0001_analytics.sql aus dem Projekt ausführen und prüfen, dass Tabelle und Index erfolgreich angelegt wurden.

2. Pages Functions binden

Navigieren zu:

Workers & Pages
→ lucaslz-blog
→ Settings
→ Bindings
→ Add

D1 database auswählen und den Variablennamen eintragen:

BLOG_ANALYTICS

Anschließend die soeben erstellte Datenbank lucaslz-blog-analytics auswählen und speichern. Der Variablenname muss exakt mit env.BLOG_ANALYTICS im Code übereinstimmen.

3. Neu bereitstellen

Hier gibt es ein leicht zu übersehendes Detail: Neue Bindings wirken sich erst auf spätere Deployments aus. Nach dem Speichern eines Bindings erhalten bestehende Deployments die neue Umgebung nicht automatisch.

Ist das Binding gespeichert, aber noch nicht neu bereitgestellt, antwortet die API:

HTTP/2 503

{"enabled":false}

Erst nach einem GitHub-Actions-Deployment kann Pages Functions das D1-Binding lesen. Dazu reicht ein normaler Commit; wenn sich keine Dateien geändert haben, kann auch ein leerer Commit erstellt werden:

git commit --allow-empty -m "chore: redeploy with D1 analytics"
git push origin main

Cloudflare Web Analytics aktivieren

D1 ist nicht der richtige Ort, um eine komplette Analyse von Besucherquellen, Geografie, Geräten und Performance neu zu implementieren. Cloudflare Web Analytics liefert diese Website-Kennzahlen bereits und braucht dafür keine Client-Kennung pro Besucher.

Im Cloudflare-Dashboard navigieren zu:

Analytics
→ Web Analytics
→ Add a site

lucaslz.com eingeben. Da die Domain bereits zum aktuellen Cloudflare-Konto gehört, kann Automatic setup gewählt werden; der Beacon-Code muss nicht manuell in das Astro-Layout eingefügt werden.

Danach zeigt das Dashboard:

Web Analytics are now set up

Die Daten erscheinen nicht sofort im Dashboard; nach der erstmaligen Aktivierung muss man warten, bis Cloudflare die Zugriffsdaten erfasst und verarbeitet. Siehe offizielle Dokumentation: Cloudflare Web Analytics.

SEO systematisch ergänzen

Statistiken sagen mir nur, ob Inhalte besucht werden; SEO bestimmt, wie Suchmaschinen und soziale Plattformen Seiten verstehen, indexieren und anzeigen. Diesmal wurden nicht nur ein paar <meta>-Tags ergänzt, sondern BaseLayout erzeugt die Seiten-Semantik einheitlich.

Basis-Metadaten

Jede Seite enthält jetzt:

  • Einen eindeutigen <title> und eine description.
  • Eine absolute Canonical, die auf https://lucaslz.com zeigt.
  • robots-Indexierungs-Anweisungen.
  • hreflang für zh-CN und x-default.
  • Links zu RSS und Web App Manifest.
  • Open Graph und Twitter Card.
  • Eine absolute Share-Bild-URL mit 1200 × 630.

Die Canonical wird aus dem aktuellen Pfad und der festen Produktionsdomain erzeugt, damit Vorschau-URLs unter pages.dev nicht als zweite Kopie des Inhalts gewertet werden:

const canonical = new URL(Astro.url.pathname, Astro.site ?? SITE.url);

Strukturierte Daten mit JSON-LD

Normale Seiten geben Person und WebSite aus. Artikelseiten zusätzlich:

  • BlogPosting
  • BreadcrumbList
  • Veröffentlichungs- und Aktualisierungszeitpunkt
  • Autor, Tags, Keywords und Wortanzahl
  • Hauptseite und Share-Bild

JSON-LD wird durch Serialisierung von Objekten erzeugt, nicht durch handgeschriebene JSON-Strings. Nach der Serialisierung wird < escaped, damit Artikelinhalte die Skriptgrenze nicht aufbrechen können.

Sitemap, RSS und robots.txt

Astro erzeugt die Sitemap während des Builds, die Artikelkollektion erzeugt zusätzlich den RSS-Feed. robots.txt verweist auf die Produktions-Sitemap. Neue Markdown-Artikel benötigen so keine manuell gepflegte URL-Liste mehr.

SEO als Build-Gate etablieren

Die größte Sorge bei SEO ist: „Diesmal behoben, bei der nächsten neuen Seite wieder ausgelassen.“ Deshalb habe ich scripts/check-seo.mjs ergänzt, das jede HTML-Datei in dist/ einzeln durchsucht und prüft:

  • Seitentitel und description.
  • Ob die Canonical die Produktionsdomain verwendet.
  • robots-Anweisungen.
  • Absolute Open-Graph-Bilder.
  • Ob die Seite genau ein H1 hat.
  • Ob JSON-LD gültiges JSON ist.
  • Ob Artikelseiten BlogPosting und BreadcrumbList enthalten.

Die Statistik-API hat außerdem eigene Tests, die normales Schreiben, Lesen, ungültige Ereignisse, Cross-Origin-Anfragen und OPTIONS-Antworten abdecken.

Die Release-Reihenfolge in GitHub Actions ist jetzt:

Astro check
→ Astro build
→ 站内链接检查
→ SEO 检查
→ Analytics 接口测试
→ 同步 GitHub Pages 镜像
→ 部署 Cloudflare Pages

Schlägt nur ein Schritt fehl, wird nicht in Produktion bereitgestellt.

Verifikation nach dem Launch

Nach der Bereitstellung zuerst eine Seite ohne Daten abrufen:

curl \
  "https://lucaslz.com/api/analytics?event=page_view&path=/howtostudy"

Bei funktionierender API lautet die Antwort:

{
  "event": "page_view",
  "path": "/howtostudy",
  "total": 0
}

Danach einen Artikel öffnen oder eine Same-Origin-POST-Anfrage senden; der Statuscode sollte 201 sein:

{
  "ok": true,
  "event": "page_view",
  "path": "/howtostudy",
  "total": 1
}

Nach dem Aktualisieren der Artikelseite erscheint unter dem Titel:

7 分钟阅读 · 1 次阅读

Abschließend in der D1 Console die aggregierten Ergebnisse prüfen:

SELECT
  event,
  path,
  target,
  SUM(count) AS total
FROM event_daily
GROUP BY event, path, target
ORDER BY total DESC;

Häufige Probleme

Die API antwortet mit 503

{"enabled":false} bedeutet, dass die Function läuft, das aktuelle Deployment aber kein BLOG_ANALYTICS erhalten hat. Das Binding in der Produktionsumgebung prüfen und nach dem Speichern neu bereitstellen.

Die API antwortet mit 500

Meist ist die Datenbank bereits gebunden, die Migration aber noch nicht ausgeführt, sodass die Tabelle event_daily fehlt. Die Migration in der D1 Console ausführen und anschließend die Function-Logs auf SQL-Fehler prüfen.

Die Leseanzahl wird auf der Seite nicht angezeigt

Der Reihe nach prüfen:

  1. Ob die aktuelle Domain lucaslz.com, www.lucaslz.com oder pages.dev ist.
  2. Ob die GET-API 200 und ein numerisches total zurückgibt.
  3. Ob die Artikelseite ein data-page-views-Element enthält.
  4. Ob die Browser-Konsole CSP-, Netzwerk- oder Skriptfehler anzeigt.

Leseanzahl und Web Analytics weichen voneinander ab

Das ist erwartetes Verhalten. page_view in D1 wird innerhalb derselben Browser-Sitzung dedupliziert, während Web Analytics eigene Regeln für Besucher, Bot-Filterung und Datenverarbeitung hat. Beide Kennzahlen sind unterschiedlich definiert; eine zahlenmäßige Übereinstimmung sollte man nicht erzwingen.

Datenschutz- und Kostengrenzen

Diese Implementierung speichert bewusst nicht:

  • IP-Adressen
  • User-Agent
  • Cookie-Kennungen
  • Benutzerkonten
  • Vollständige Referer
  • URL-Query-Parameter

In D1 stehen nur Ereignis, normalisierter Pfad, Ziel, Datum und Anzahl. Da Web Analytics und benutzerdefinierte Ereignisse getrennte Zuständigkeiten haben, muss auch kein schwergewichtiges Analyse-SDK eines Drittanbieters in jede Seite eingebunden werden.

Das kostenlose Kontingent und die konkreten Limits von D1 können sich ändern; maßgeblich ist die Preisdokumentation zu Cloudflare D1. Gegenüber Detaildatensätzen pro Zugriff reduziert die tägliche Aggregation die Zeilenzahl und den Leseumfang deutlich und passt besser zu einem persönlichen Blog.

Endergebnis

Nach diesem Umbau bleibt der Blog weiterhin statisch-first:

Astro 静态内容
  ├─ Cloudflare Web Analytics：全站趋势与性能
  ├─ Pages Functions：轻量统计 API
  ├─ D1：文章阅读量与自定义事件
  └─ SEO：元数据、结构化数据与自动检查

Das Wichtigste ist nicht eine zusätzliche Zugriffszahl, sondern ein langfristig wartbarer Feedback-Loop: Suchmaschinen verstehen die Artikel genauer, ich sehe, welche Inhalte tatsächlich gelesen werden, und der Build-Prozess stellt sicher, dass neue Seiten die SEO-Basislinie nicht versehentlich verlieren.

Für einen statischen persönlichen Blog deckt das die allermeisten praktischen Anforderungen ab, ohne einen dauerhaft laufenden Server, eine In-Memory-Datenbank oder ein komplexes Nutzer-Tracking-System einzuführen.
