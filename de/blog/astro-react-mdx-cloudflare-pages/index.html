Mein Blog von Grund auf neu aufgebaut: Astro + React + MDX + Cloudflare Pages

Der Blog hatte über Jahre hinweg zuverlässig funktioniert, aber er fühlte sich zunehmend weniger wie ein Ort an, an dem ich dauerhaft schreiben möchte: Die Seiten wirkten wie ein Dokumentationsportal, das Mobile-Erlebnis war mittelmäßig, und das Verhältnis zwischen Quellcode, Build-Artefakten und Deployment-Plattform blieb unklar.

Diesmal habe ich nicht versucht, das alte Projekt weiter zu flicken, sondern den Blog komplett neu aufgebaut. Die finale Lösung ist Astro + React + MDX. Der Quellcode liegt in einem privaten GitHub-Repository und wird von GitHub Actions gebaut und anschließend sowohl in das GitHub-Pages-Spiegelrepository als auch auf Cloudflare Pages veröffentlicht. lucaslz.com wird von Cloudflare per DNS verwaltet und ist der offizielle Einstiegspunkt.

Dieser Artikel dokumentiert den kompletten Prozess: Technologieauswahl, Projektstruktur, automatisiertes Deployment, DNS-Umstellung und Fehlerbehebung.

Die Ziele

Vor der Neuentwicklung habe ich die Randbedingungen festgelegt, um nicht ständig zwischen Frameworks hin und her zu wechseln:

  • Der Blog soll in erster Linie gut aussehen – nicht wie eine API-Dokumentation.
  • Er funktioniert standardmäßig auf Smartphones, Tablets und Desktops.
  • Beiträge werden in Markdown oder MDX verwaltet.
  • React bleibt im Einsatz, aber für rein statische Inhalte wird kein vollständiges Server-Framework eingeführt.
  • Das Quellcode-Repository bleibt privat; die gebauten statischen Dateien dürfen öffentlich sein.
  • Ein Push auf main baut, prüft und deployed automatisch.
  • Keine Serverwartung; nach Möglichkeit kostenloses statisches Hosting und CDN.
  • lucaslz.com ist und bleibt die einzige offizielle Adresse.

Die finale Publishing-Pipeline sieht so aus:

Warum Astro + React + MDX

Astro ist für statische Inhalte zuständig

Der Kern eines Blogs sind die Beiträge. Ein Beitrag muss nicht erst React im Browser erneut ausführen, um angezeigt zu werden – statisches Generieren passt daher besser als vollständiges Client-Rendering.

Astro erzeugt das HTML bereits zur Build-Zeit und liefert dem Browser standardmäßig kein unnötiges JavaScript aus. Seine Content Collections validieren das Frontmatter der Beiträge, dynamische Routen erzeugen die Beitragsseiten einheitlich, und RSS, Sitemap sowie SEO-Metadaten entstehen ebenfalls beim Build.

Für dieses Projekt ist das Build-Ergebnis ein dist/-Verzeichnis ohne Abhängigkeit von einem Node.js-Server. Es lässt sich daher sowohl auf Cloudflare Pages deployen als auch nach GitHub Pages synchronisieren.

React kümmert sich nur um die Interaktion

React zu behalten bedeutet nicht, den gesamten Blog in eine SPA zu verwandeln. Das aktuelle Projekt nutzt React Islands nur dort, wo Interaktion nötig ist:

  • Website-Suche
  • Dark-Mode-Umschaltung
  • Mobile Navigation

Diagramme werden in D2 geschrieben und beim Build von astro-d2 als Inline-SVG erzeugt, sodass der Browser kein zusätzliches Render-Skript braucht; ihre Farben folgen den Theme-Variablen der Website samt Hell-/Dunkel-Umschaltung, und per Klick lassen sie sich vergrößern. Beitragstexte, Homepage-Karten sowie Archiv- und Tag-Seiten gibt Astro direkt als HTML aus. So bleibt die React-Entwicklungserfahrung erhalten und der Umfang der Client-Skripte unter Kontrolle.

MDX sorgt für Ausdruckskraft

Normale Beiträge bleiben in Markdown; MDX kommt zum Einsatz, wenn Komponenten oder komplexe Interaktionen benötigt werden. Beides verwaltet dieselbe Content Collection, sodass wenige fortgeschrittene Beiträge nicht die Einfachheit der gesamten Website gefährden.

Zu den wichtigsten Abhängigkeiten des Projekts gehören:

{
  "dependencies": {
    "astro": "7.1.6",
    "@astrojs/mdx": "7.0.5",
    "@astrojs/react": "6.0.2",
    "react": "19.2.8",
    "react-dom": "19.2.8"
  }
}

Bei einem rein statischen Astro-Projekt ist für das Deployment auf Pages kein @astrojs/cloudflare-Adapter nötig; er wird nur benötigt, wenn die Cloudflare-Server-Runtime oder SSR zum Einsatz kommt.

Content-Modell und Projektstruktur

Die Blog-Inhalte liegen unter src/content/blog/; der Dateipfad bestimmt direkt die finale URL. Zum Beispiel:

src/content/blog/
├── blog/
│   └── astro-react-mdx-cloudflare-pages.md
├── css/
├── foundation/
├── java/
└── react/

Das Frontmatter der Beiträge wird per Zod validiert, damit falsche Datumsangaben, Tags oder Draft-Status nicht in die Produktion gelangen:

const blog = defineCollection({
  loader: glob({
    base: "./src/content/blog",
    pattern: "**/*.{md,mdx}",
  }),
  schema: z.object({
    title: z.string(),
    description: z.string(),
    date: z.coerce.date(),
    author: z.string().default("lucaslz"),
    tags: z.array(z.string()).default([]),
    featured: z.boolean().default(false),
    draft: z.boolean().default(false),
  }),
});

Einen Beitrag zu veröffentlichen bedeutet nur, eine neue Markdown-Datei anzulegen. Homepage, Archiv, Tags, Suchindex, RSS und Sitemap aktualisieren sich beim Build automatisch.

Mobile kommt nicht erst im Nachhinein

Diese Neuentwicklung wurde von Anfang an für kleine Bildschirme entworfen, statt zuerst eine Desktop-Version zu bauen und sie später zusammenzustauchen:

  • Alle Seiten verwenden den korrekten viewport.
  • Die Breakpoints orientieren sich an der Inhaltsbreite, nicht an bestimmten Smartphone-Modellen.
  • Schriftgrößen und Abstände in Beiträgen nutzen clamp() für kontinuierliche Skalierung.
  • Touch-Ziele sind nicht kleiner als die üblichen mobilen Touch-Größen.
  • Die Desktop-Navigation wechselt auf kleinen Bildschirmen zu einem Drawer-Menü.
  • Code-Blöcke scrollen horizontal, statt den Beitragscontainer zu sprengen.
  • Tabellen, Bilder, D2-Diagramme und lange URLs sind gegen Überlauf abgesichert.
  • Helle und dunkle Systemthemen werden unterstützt.

Eine statische Seite ist nicht automatisch eine einfache Seite. Das Mobile-Erlebnis hängt mehr von Layout, Typografie, Touch-Flächen und Ressourcengröße ab als vom verwendeten JavaScript-Framework.

Warum zwei GitHub-Repositories

Das Quellcode-Repository lucaslz-blog ist privat und enthält die Beitragsquellen, die Astro-Konfiguration und die GitHub-Actions-Workflows. Das zweite Repository, lucasleelz.github.io, speichert ausschließlich die gebauten statischen Dateien.

Diese Trennung hat drei Vorteile:

  1. Schreiben und technische Konfiguration bleiben privat.
  2. Das GitHub-Pages-Repository dient weiterhin als öffentlicher, rollbackfähiger statischer Spiegel.
  3. Cloudflare Pages und GitHub Pages verwenden dieselbe dist/ – so entstehen keine zwei getrennten Build-Logiken.

Build-Artefakte sind kein Quellcode; dist/ sollte daher nicht manuell im Quellcode-Repository gepflegt werden. CI erzeugt es bei jedem Build neu.

Automatisiertes Publishing mit GitHub Actions

Der Workflow hört ausschließlich auf main. Bei jedem Push laufen nacheinander Installation, Typprüfung, statischer Build, Prüfung interner Links und das Publishing.

Hier die vereinfachte Version der Kernstruktur:

name: Build and publish site

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  deployments: write

concurrency:
  group: publish-production
  cancel-in-progress: false

jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout source
        uses: actions/checkout@v6

      - name: Setup pnpm
        uses: pnpm/action-setup@v4

      - name: Setup Node
        uses: actions/setup-node@v6
        with:
          node-version: 24
          cache: pnpm

      - name: Install dependencies
        run: pnpm install --frozen-lockfile

      - name: Build site
        run: pnpm run build

      - name: Check internal links
        run: pnpm run check:links

GitHub-Pages-Spiegel synchronisieren

Das Quellcode-Repository erhält über einen dedizierten Deploy Key Schreibzugriff auf das statische Repository. Der Workflow checked das Zielrepository aus und bringt den Zielbranch mit rsync --delete exakt auf den Stand des aktuellen dist/:

- name: Checkout Pages repository
  uses: actions/checkout@v6
  with:
    repository: lucaslz2020/lucasleelz.github.io
    ref: master
    ssh-key: ${{ secrets.PAGES_DEPLOY_KEY }}
    path: publish

- name: Copy static files
  run: rsync -a --delete --exclude=.git dist/ publish/

- name: Publish generated site
  working-directory: publish
  run: |
    git config user.name "github-actions[bot]"
    git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
    git add --all
    if git diff --cached --quiet; then
      exit 0
    fi
    git commit -m "deploy: ${GITHUB_SHA}"
    git push origin HEAD:master

Prüfe vorher, ob das Zielrepository tatsächlich main oder master verwendet. Bei falschem Branchnamen gelingt der Build, aber der Publishing-Schritt schlägt fehl.

Auf Cloudflare Pages veröffentlichen

Das Cloudflare-Pages-Projekt nutzt Direct Upload: GitHub Actions führt den eigenen Build aus und lädt dist/ hoch. Auch die offizielle Cloudflare-Dokumentation beschreibt diesen Weg für die Anbindung eigener CI-Plattformen.

- name: Deploy to Cloudflare Pages
  uses: cloudflare/wrangler-action@v3
  with:
    apiToken: ${{ secrets.CLOUDFLARE_API_TOKEN }}
    accountId: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
    command: >-
      pages deploy dist
      --project-name=lucaslz-blog
      --branch=main
    gitHubToken: ${{ secrets.GITHUB_TOKEN }}

Im Produktionsworkflow pinne ich Third-Party-Actions zusätzlich auf vollständige Commit-SHAs und halte die passende Version im Kommentar fest, um das Supply-Chain-Risiko durch unerwartet geänderte Upstream-Tags zu senken.

Zugangsdaten nach dem Least-Privilege-Prinzip

Für das automatisierte Deployment werden zwei Schreibberechtigungen benötigt – das heißt aber nicht, dass du einen persönlichen SSH-Schlüssel oder ein globales Admin-Token wiederverwenden solltest.

GitHub Pages Deploy Key

  • Ein separates SSH-Schlüsselpaar erzeugen.
  • Nur den öffentlichen Schlüssel mit Schreibberechtigung zum statischen Publishing-Repository hinzufügen.
  • Den privaten Schlüssel als Secret PAGES_DEPLOY_KEY im Quellcode-Repository hinterlegen.
  • Nach erfolgreichem Deployment die lokale temporäre Kopie des privaten Schlüssels löschen.

Cloudflare API Token

  • Ein benutzerdefiniertes API-Token erstellen, statt den Global API Key zu verwenden.
  • Nur Schreibberechtigung für Cloudflare Pages des Zielkontos vergeben.
  • Das Token in CLOUDFLARE_API_TOKEN ablegen.
  • Die Account ID in CLOUDFLARE_ACCOUNT_ID ablegen.
  • Das Token selbst niemals in Terminalausgaben, Build-Logs, Screenshots oder Artikeln zeigen.

Wenn ein Token jemals in Logs oder Tool-Ausgaben aufgetaucht ist, reicht es nicht, die Logs zu löschen: Widerrufe das alte Token sofort, erzeuge ein neues und überschreibe das GitHub-Secret.

GitHub empfiehlt außerdem, Zugangsdaten nur die minimal nötigen Berechtigungen für die Aufgabe zu geben und bevorzugt Deploy Keys, GitHub Apps oder dedizierte Service-Identitäten zu verwenden, statt persönliche Zugangsdaten dauerhaft wiederzuverwenden. Siehe: GitHub Actions Secrets.

Wechsel von Vercel zu Cloudflare Pages

Der Punkt, der bei der Migration am ehesten schiefgeht, ist nicht der Build, sondern die Reihenfolge der Schritte.

Meine Domain hatte anfangs noch einen A-Record für die Root-Domain, der auf Vercel zeigte. Nachdem ich das Vercel-Projekt gelöscht hatte, lieferte der Aufruf der Domain:

404: NOT_FOUND
Code: DEPLOYMENT_NOT_FOUND

Dieser Fehler bedeutet nicht, dass das Cloudflare-Pages-Deployment fehlgeschlagen ist, sondern dass DNS die Anfragen weiterhin an das gelöschte Vercel-Deployment geleitet hat.

Sicherer ist diese Reihenfolge:

  1. Zuerst die pages.dev-Adresse von Cloudflare Pages erstellen und verifizieren.
  2. Die Domain in Cloudflare hinzufügen und die automatisch erkannten DNS-Einträge prüfen.
  3. Sicherstellen, dass keine Mail-Einträge wie MX, SPF, DKIM oder DMARC fehlen.
  4. Beim Domain-Registrar die autoritativen Nameserver auf Cloudflare umstellen.
  5. Auf die Aktivierung der Cloudflare-Zone warten.
  6. Die Root-Domain unter Custom domains im Pages-Projekt binden.
  7. Erst wenn HTTPS und die wichtigsten Seiten funktionieren, die Konfiguration der alten Plattform aufräumen.

Diese Domain hatte keine Mail-Einträge, daher war die Umstellung relativ einfach. Trägt eine Domain gleichzeitig Mail, APIs oder andere Subdomains, musst du zuerst das gesamte DNS migrieren – nicht nur die A/CNAME-Einträge des Blogs.

Nameserver bei Alibaba Cloud ändern

Der Registrar ist Alibaba Cloud; die ursprünglichen autoritativen Nameserver sind HiChina. Sobald Cloudflare der Zone zwei Nameserver zugewiesen hat, öffnest du in der Alibaba-Cloud-Domain-Konsole:

域名详情 → DNS 管理 → DNS 修改 → 修改 DNS 服务器

Die beiden von Cloudflare zugewiesenen Nameserver eintragen, die SMS-Verifizierung abschließen und speichern.

Die Nameserver-Umstellung ist ein Netzwerkvorgang mit großer Tragweite. Vor dem Absenden solltest du mindestens Folgendes prüfen:

  • Sind alle vorhandenen Einträge in der Cloudflare-Zone vollständig?
  • Ist DNSSEC in einem kompatiblen Zustand? Falls nötig, zuerst das DNSSEC des alten Anbieters deaktivieren und nach der Aktivierung von Cloudflare wieder aktivieren lassen.
  • Hängt die Domain von nicht migrierten Mail-, API- oder Verifizierungseinträgen ab?
  • Können alte DNS-TTLs dazu führen, dass Caches lange veraltet bleiben?

Die Cloudflare-Konsole zeigt unter Umständen eine Weile Initializing oder Verifying. Du solltest Einträge nicht nur deshalb wiederholt löschen und neu anlegen, weil der Status nicht sofort Active wird – verifiziere das tatsächliche Ergebnis über öffentliches DNS und HTTPS.

Die Root-Domain binden

Sobald die Zone aktiv ist, gehst du im Cloudflare-Dashboard zu:

Workers & Pages
→ lucaslz-blog
→ Custom domains
→ Set up a custom domain

lucaslz.com eintragen. Cloudflare ersetzt den alten Eintrag der Root-Domain durch einen Verweis auf lucaslz-blog.pages.dev und übernimmt CNAME Flattening, Proxy und Zertifikatsausstellung für die Root-Domain.

Der Endstatus sollte so aussehen:

lucaslz.com  Active
SSL enabled

Das GitHub-Pages-Spiegelrepository enthält keine CNAME-Datei mehr, damit nicht beide Hosting-Plattformen gleichzeitig dieselbe offizielle Domain beanspruchen.

Verifikations-Checkliste nach dem Launch

Verlass dich nicht nur auf den grünen Status in der Konsole. Nach der Veröffentlichung mindestens Folgendes prüfen:

# 权威名称服务器
dig NS lucaslz.com

# HTTPS、跳转与响应头
curl -I -L https://lucaslz.com/

# 关键页面
curl -I -L https://lucaslz.com/archive/
curl -I -L https://lucaslz.com/tags/

# RSS 与 Sitemap
curl -I https://lucaslz.com/rss.xml
curl -I https://lucaslz.com/sitemap-index.xml

Im Browser zusätzlich prüfen:

  • Homepage, Beitragsseiten, Archiv und Tag-Seiten.
  • Navigation, Suche und Code-Blöcke bei Smartphone-Breite.
  • Helle und dunkle Themen.
  • Die 404-Seite.
  • Canonical-, Open-Graph-, RSS- und Sitemap-URLs.
  • Ob der Footer die korrekte Deployment-Plattform anzeigt.

Nach diesem Launch lieferten Homepage, Archiv und Beitragsrouten 200 zurück, der server-Antwortheader ist cloudflare, und die Cloudflare-Pages-Konsole zeigt Active · SSL enabled.

Erfahrungen, die man behalten sollte

Erst die temporäre Domain verifizieren, dann das offizielle DNS umstellen

pages.dev ist der beste isolierte Verifizierungseinstieg. Solange die temporäre Domain Build-, Link- und Seitenprüfungen nicht bestanden hat, sollte die offizielle Domain nicht umgestellt werden.

Quellcode-Deployment und Artefakt-Publishing sind zwei verschiedene Dinge

Das private Quellcode-Repository übernimmt Schreiben und Build; das öffentliche Pages-Repository speichert nur die Artefakte. Die Verbindung über GitHub Actions ist stabiler als das manuelle Kopieren von dist/ und leichter zu auditieren.

Vor dem Löschen der alten Plattform DNS prüfen

Wenn das alte Projekt gelöscht ist, bevor DNS umgestellt wurde, erscheint sofort ein Plattform-404. Für Produktionsmigrationen gilt: erst die neue Umgebung vorbereiten, dann den Traffic umstellen und zuletzt die alte Umgebung aufräumen.

Die richtige Reaktion auf ein geleaktes Secret ist Rotation

„In der Oberfläche nicht mehr sichtbar” bedeutet nicht „die Zugangsdaten sind sicher”. Sobald ein Secret möglicherweise gelesen wurde, solltest du es widerrufen, neu erstellen, das Secret aktualisieren und nicht mehr benötigte lokale Kopien entfernen.

CI braucht Prüfungen über den Build hinaus

Ein erfolgreicher statischer Build bedeutet nicht, dass die Website funktioniert. Typprüfung, Content-Schema, Prüfung interner Links und ein Online-Smoke-Test sollten gemeinsam das Release-Gate bilden.

Das Ergebnis

Der neue Blog läuft ohne Anwendungsserver und ohne Laufzeit-Datenbank. Der tägliche Veröffentlichungsablauf reduziert sich auf:

写 Markdown / MDX
→ 本地预览
→ git push main
→ GitHub Actions 构建与检查
→ 同步 GitHub Pages 镜像
→ 部署 Cloudflare Pages
→ lucaslz.com 自动更新

Astro verwandelt Inhalte in möglichst leichte statische Seiten, React übernimmt nur die Interaktionen, die wirklich gebraucht werden, GitHub Actions macht das Publishing wiederholbar, und Cloudflare Pages liefert CDN, HTTPS und die offizielle Domain.

Für einen persönlichen Technik-Blog ist diese Struktur einfach genug und lässt zugleich Raum für langfristige Weiterentwicklung. Wichtiger noch: Sie gibt die Zeit, die bisher in die Pflege der Deployment-Umgebung geflossen ist, an das Schreiben selbst zurück.
