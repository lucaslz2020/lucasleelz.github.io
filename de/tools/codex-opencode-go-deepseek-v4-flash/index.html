DeepSeek V4 Flash in Codex über die Responses API von OpenCode Go

DeepSeek V4 Flash in Codex über die Responses API von OpenCode Go: ohne Klartext-Key, mit Modellkatalog, Profilwechsel und echten Dateiänderungen.

Das Ziel war klar: die bestehende OpenAI-Anmeldung von Codex behalten und gleichzeitig das von OpenCode Go bereitgestellte DeepSeek V4 Flash in Codex einbinden. DeepSeek soll standardmäßig verwendet werden; bei Bedarf lässt sich mit einem einzigen Befehl zurück zu OpenAI wechseln.

Am Ende gab es drei Einstiege:

# 默认：DeepSeek V4 Flash
codex

# 显式选择 DeepSeek
codex -p deepseek

# 切回 OpenAI
codex -p openai

Der tatsächliche Prozess war mehr als nur das Ändern eines Modellnamens. Im Spiel waren Responses-API-Kompatibilität, Provider-Authentifizierung, Modellmetadaten, benutzerdefinierte Codex-Tools und die Override-Reihenfolge der Profile. Erschwerend kam hinzu, dass manche Konfiguration die statische Prüfung besteht und erst bei der ersten echten Anfrage Protokollunterschiede offenbart.

Anforderungen, Randbedingungen und Abnahmekriterien

Vor Beginn der Änderungen habe ich das Ziel in eine Reihe überprüfbarer Bedingungen zerlegt:

  • deepseek-v4-flash verwenden, wie es in OpenCode Go bereits konfiguriert ist – ohne ein weiteres Credential anzufordern oder zu duplizieren.
  • Codex ruft die Responses API direkt auf, ohne einen dauerhaft laufenden lokalen Protokoll-Proxy.
  • DeepSeek bleibt die Standardoption; die OpenAI-Anmeldung und die OpenAI-Modelle bleiben weiterhin nutzbar.
  • Ein Wechsel zwischen Providern darf nicht nur den Modellnamen ändern, sondern muss zugleich Authentifizierung und Modellkatalog umschalten.
  • Die Konfiguration der aktuellen Session bleibt nachvollziehbar; vor Änderungen wird die ursprüngliche config.toml gesichert.
  • Der API-Key erscheint nicht in Terminal-Logs, Artikeln, Git oder Screenshots.
  • Verifikation nicht nur per curl, sondern auch über den nativen Codex-Chat und echte Dateiänderungen.
  • Bei Inkompatibilitäten bleibt der vollständige Fehler erhalten und wird der richtigen Protokollebene der Anfrage zugeordnet, statt ihn durch erneute Versuche zu übertünchen.

Die endgültigen Abnahmekriterien:

Die vollständige Timeline der Fehlersuche

Diese Integration durchlief mehrere Kurskorrekturen. Nachfolgend der Ablauf in chronologischer Reihenfolge:

Diese Timeline hat einen kontraintuitiven Punkt: Ohne Modellkatalog gelingt die Anfrage; mit dem vermeintlich vollständigeren Katalog schlägt sie fehl. Die Ursache lag nicht an der Modellqualität, sondern daran, dass der Modellkatalog die Tool-Deklarationen verändert, die Codex an den Upstream sendet.

Endgültige Architektur

  B -->|Standard oder -p deepseek| C[DeepSeek Profile]
  B -->|-p openai| D[OpenAI Profile]
  C --> E[OpenCode Go Provider]
  E --> F[deepseek-v4-flash]
  D --> G[OpenAI Provider]

Die Konfiguration verteilt sich auf vier Dateien:

~/.codex/
├── config.toml
├── deepseek.config.toml
├── openai.config.toml
└── model-catalogs/
    └── opencode-go.json

config.toml enthält die Standardwerte und die Provider-Definitionen; die beiden Profile überschreiben nur Modell, Provider, Kontextfenster und Modellkatalog. Der API-Key steht nicht in diesen Dateien, sondern wird zur Laufzeit aus der von OpenCode gespeicherten Authentifizierungsdatei gelesen.

Erst die Responses API verifizieren, nicht aus alten Unterlagen ableiten

Zunächst nahm ich anhand älterer Suchergebnisse fälschlich an, der DeepSeek-Endpunkt unterstütze nur Chat Completions, und plante einen zusätzlichen Protokoll-Proxy. In der DeepSeek-Dokumentation zum Erstellen einer Response fand ich dann die Bestätigung für die Responses API und verifizierte den tatsächlichen OpenCode-Go-Endpunkt mit einer minimalen Anfrage:

curl --request POST \
  --url https://opencode.ai/zen/go/v1/responses \
  --header "Authorization: Bearer ${OPENCODE_GO_API_KEY}" \
  --header "Content-Type: application/json" \
  --data '{
    "model": "deepseek-v4-flash",
    "input": "Reply exactly OK.",
    "max_output_tokens": 16
  }'

Die entscheidenden Ergebnisse in anonymisierter Form:

{
  "object": "response",
  "status": "completed",
  "model": "deepseek-v4-flash",
  "output_text": "OK",
  "error": null
}

Der Endpunkt lieferte HTTP 200, der Antwortstatus war completed, das Modell deepseek-v4-flash und der Text OK. Damit war kein zusätzlicher Protokoll-Proxy nötig; Codex kann direkt wire_api = "responses" verwenden.

Dokumentation, Modellservice und Gateway: drei Fähigkeitsebenen

Frag nicht nur, ob DeepSeek die Responses API unterstützt – die echte Anfrage durchläuft drei Ebenen:

  1. Ob DeepSeek-Modell und Interface-Definition das Response-Objekt unterstützen.
  2. Ob OpenCode Go eine kompatible /v1/responses-Route bereitstellt.
  3. Ob OpenCode Go die von Codex mitgelieferten Tool-Schemas und Streaming-Events vollständig akzeptiert.

Eine minimale Textanfrage belegt nur die ersten beiden Ebenen und die Grundzüge der dritten. Codex sendet zusätzlich Developer-Instructions, Tools, Reasoning-Parameter und Streaming-Konfiguration – daher ist weiterhin ein nativer End-to-End-Test nötig.

Dieser Schritt ist wichtig: Suchindizes, alte Dokumentation und Hinweise von Drittanbietern können veraltet sein. Maßgeblich sind letztlich die tatsächliche Spezifikation des Ziel-Endpunkts und das Ergebnis einer minimalen Anfrage. Der zuvor temporär installierte, aber noch nicht genutzte Proxy wurde anschließend entfernt, um keine doppelte Kette zurückzulassen.

Achte beim Testen darauf, dass der echte API-Key nicht in Artikel, Skripte oder die Shell-History gerät. Die Umgebungsvariable oben dient nur zur Veranschaulichung der Anfrage-Struktur.

Erster Umweg: Warum der Proxy installiert und wieder entfernt wurde

Die ursprüngliche Einschätzung beruhte auf dem Eindruck der älteren DeepSeek-API: Wenn der Upstream nur /chat/completions kennt und der aktuelle benutzerdefinierte Codex-Provider nur wire_api = "responses" akzeptiert, braucht es dazwischen eine Konvertierungsschicht.

Die damalige Alternativ-Kette war daher:

flowchart LR
  A[Codex Responses] --> B[Lokaler Kompatibilitäts-Proxy]
  B --> C[Chat Completions]
  C --> D[DeepSeek]

Das Proxy-Paket war zwar temporär installiert, aber es lief kein Dienst und es gab keinen Codex-Routing-Eintrag. Nach der neuen DeepSeek-Dokumentation habe ich die Proxy-Konfiguration nicht weiter ausgebaut, sondern zuerst die Direktverbindung verifiziert. Nach dem erfolgreichen Test wurde der Proxy sofort deinstalliert.

Es ging nicht nur darum, ein npm-Paket zu entfernen. Eine zusätzliche Proxy-Ebene hätte eingeführt:

  • eine zweite Stelle, an der API-Key oder Zugangsdaten gelesen werden
  • einen eigenen Prozess, Port, Health-Checks und Autostart
  • zwei Sätze aus Timeouts, Streaming-Weiterleitung, Retries und Fehlerformaten
  • Konvertierungsrisiken für Tool-Schemas, Reasoning-Felder und Response-Events
  • bei Fehlern ist schwer zu bestimmen, ob das Problem an Codex, am Proxy, an OpenCode Go oder am Modell liegt

Ein Proxy lohnt sich nur langfristig, wenn das direkte Protokoll wirklich fehlt oder wenn eine einheitliche Ebene für Audit, Rate-Limiting und Routing zwingend nötig ist.

Vor der Konfiguration: lokalen Zustand erfassen

Bevor ich config.toml überschrieb, prüfte ich die aktuelle Version, das Standardmodell, den Anmeldestatus und die gespeicherten OpenCode-Zugangsdaten. Zum Zeitpunkt dieses Artikels galt:

Codex CLI: 0.145.0
原默认模型: gpt-5.6-luna
原推理强度: high
OpenAI 登录: 已存在
OpenCode Go 凭证: 已存在

Versionsprüfung:

codex --version

Die Prüfung der Zugangsdaten liefert nur ein boolesches Ergebnis und gibt keinen Inhalt aus:

jq -e \
  '.["opencode-go"].key | type == "string" and length > 0' \
  ~/.local/share/opencode/auth.json >/dev/null

Danach die Dateiberechtigungen prüfen:

ls -l ~/.codex/config.toml ~/.local/share/opencode/auth.json

Erlauben die Berechtigungen anderen lokalen Benutzern Lesezugriff, schränke die Rechte zuerst ein, bevor du weitermachst. Führe zur Existenzprüfung des Keys nicht direkt jq -r aus, denn dieses Kommando würde den Key im Terminal ausgeben.

Den OpenCode-Go-Provider konfigurieren

Zuerst die aktuelle Konfiguration sichern:

cp ~/.codex/config.toml ~/.codex/config.toml.before-opencode-go

In ~/.codex/config.toml das Standardmodell festlegen:

model = "deepseek-v4-flash"
model_provider = "opencode-go"
model_context_window = 1000000
model_catalog_json = "/Users/you/.codex/model-catalogs/opencode-go.json"
model_reasoning_effort = "high"

[model_providers.opencode-go]
name = "OpenCode Go"
base_url = "https://opencode.ai/zen/go/v1"
wire_api = "responses"
request_max_retries = 4
stream_max_retries = 5
stream_idle_timeout_ms = 300000

base_url endet bei /v1; Codex fragt je nach wire_api /responses ab. Der vollständige /responses-Pfad darf nicht zusätzlich in base_url stehen.

Hier wird der Kontext explizit auf 1 Million gesetzt, aber das tatsächlich nutzbare Fenster hängt weiterhin von Modell, Provider und Gateway-Richtlinien ab. Für sehr lange Aufgaben brauchst du vor dem Produktivgang einen eigenen Grenzwerttest; lokale Metadaten allein reichen nicht.

Wofür jedes Feld steht

KonfigurationseintragZweck
modelModellkennung, die an den Upstream gesendet wird
model_providerWählt Base URL, Authentifizierung und Retry-Strategie aus
model_context_windowKontextbudget-Hinweis für Codex
model_catalog_jsonModellname, Reasoning-Stufen, Tool-Modus und weitere Fähigkeitsmetadaten
wire_apiLegt fest, dass der Provider das Responses-Protokoll verwendet
request_max_retriesMaximale Anzahl von Retries für normale HTTP-Anfragen
stream_max_retriesAnzahl der Wiederherstellungsversuche nach einer Streaming-Unterbrechung
stream_idle_timeout_msTimeout, wenn der Stream lange keine Events liefert

model und model_provider gehören zusammen. Wird das Modell auf DeepSeek geändert, aber model_provider = "openai" beibehalten, werden Anfragen nicht automatisch an OpenCode Go geroutet. Umgekehrt schlägt unter dem OpenCode-Go-Provider ein Modellname fehl, der nur von OpenAI angeboten wird.

Warum der Key nicht über eine Umgebungsvariable dupliziert wurde

Ein Codex-Provider kann auch eine benannte Umgebungsvariable lesen, aber dann müsste jedes Terminal, jede IDE und jeder Desktop-Prozess, der Codex startet, dieselbe Variable erben. Da die Zugangsdaten bereits von OpenCode verwaltet werden, entspricht ein Authentifizierungskommando, das die vorhandene Datei bei Bedarf liest, besser dem Prinzip einer einzigen Credential-Quelle.

Wenn das Team Umgebungsvariablen über einen zentralen Secret Manager injiziert, sollte die teamübliche Lösung Vorrang haben. Der jq-Ansatz dieses Artikels passt zu persönlichen Entwicklungsmaschinen, die bereits den lokalen OpenCode-Authentifizierungsspeicher nutzen.

Eine Antwort von /models heißt noch nicht, dass Codex sie verarbeiten kann

Nach der Provider-Konfiguration versucht Codex, die Modellliste zu aktualisieren. Das /models von OpenCode Go lieferte damals eine Struktur im OpenAI-Stil:

{
  "object": "list",
  "data": [{ "id": "deepseek-v4-flash", "object": "model" }]
}

Der Modellmanager von Codex erwartet in diesem benutzerdefinierten Aktualisierungspfad eine Katalogstruktur mit dem Feld models und protokollierte daher einen Fehler wie diesen:

failed to decode models response:
missing field `models`

Das bedeutet nicht, dass /responses unbrauchbar ist. Tatsächlich waren sowohl die minimale Response als auch die Codex-Anfrage mit Fallback-Metadaten erfolgreich. Gescheitert ist nur der Hilfspfad zur automatischen Aktualisierung des Modellkatalogs.

Die Lösung bestand weder darin, die Gateway-Antwort zu verändern, noch darin, alle Logs zu ignorieren, sondern darin, einen lokalen model_catalog_json bereitzustellen:

文本生成链路: Codex -> /responses -> 成功
模型发现链路: Codex -> /models -> schema 不匹配
替代方案:     Codex -> 本地 model_catalog_json

So bleiben Modellbetrieb und Modell-Discovery entkoppelt, und die Fähigkeitsdeklaration von DeepSeek liegt ausdrücklich in der lokalen Konfiguration.

Authentifizierung zur Laufzeit statt Klartext-Key-Kopie

OpenCode speichert die Zugangsdaten bereits in der lokalen Authentifizierungsdatei; es gibt keinen Grund, denselben Key zusätzlich in config.toml zu kopieren. Benutzerdefinierte Codex-Provider können Authentifizierungsinformationen über ein Kommando beziehen:

[model_providers.opencode-go.auth]
command = "/usr/bin/jq"
args = [
  "-r",
  ".[\"opencode-go\"].key",
  "/Users/you/.local/share/opencode/auth.json",
]
timeout_ms = 5000
refresh_interval_ms = 300000

Achtung: args wird von Codex direkt an das Kommando übergeben und durchläuft nicht unbedingt eine Shell. Nimm also nicht an, dass ~ automatisch expandiert wird. Gib unter macOS den tatsächlichen absoluten Pfad an, unter Linux in der Regel /home/用户名/....

Das hat mehrere Vorteile:

  • Es gibt keine zweite Klartext-Kopie des Keys in der Codex-Konfiguration.
  • Nach einem Credential-Update in OpenCode kann Codex die Datei innerhalb des Refresh-Intervalls erneut lesen.
  • Die Konfigurationsdatei eignet sich besser für Backups und Reviews.

Beschränke die Lesbarkeit von Authentifizierungsdatei und Codex-Konfiguration auf den aktuellen Benutzer, zum Beispiel mit Berechtigung 600. Auch Diagnoseausgaben dürfen den Key nicht ausgeben.

Warum ein benutzerdefinierter Modellkatalog nötig ist

Mit nur einem Modellnamen startet Codex zwar mit Fallback-Metadaten, meldet aber:

Model metadata for `deepseek-v4-flash` not found.
Defaulting to fallback metadata; this can degrade performance and cause issues.

Interessanterweise bestand dieser Fallback-Modus zunächst den nativen Codex-Test: Die Startausgabe zeigte deepseek-v4-flash + opencode-go und lieferte OK. Daraus ergeben sich zwei Schlussfolgerungen:

  • Provider, Authentifizierung und Responses-Routing funktionieren grundsätzlich.
  • Tritt ein späterer Fehler erst nach Aktivierung des benutzerdefinierten Katalogs auf, vergleiche zuerst die Modellmetadaten, statt den API-Key erneut infrage zu stellen.

Warum das minimale JSON scheiterte

Zunächst versuchte ich, einen Katalog von Hand zu schreiben, der nur Name, Kontext und Reasoning-Stufe enthält. Codex lehnte ihn beim Parsen direkt ab:

failed to parse model_catalog_json:
missing field `base_instructions`

Das zeigt: model_catalog_json ist keine einfache Liste für die Modellauswahl. Er enthält zusätzlich die Base Instructions, Nachrichtenvorlagen, Kürzungsstrategien und Tool-Fähigkeiten, die Codex zum Betrieb benötigt.

Von Hand Dutzende versionsabhängige Felder zu schreiben, erzeugt schnell neue Kompatibilitätsprobleme. Deshalb habe ich stattdessen einen vollständigen Eintrag aus der aktuellen models_cache.json geklont und die DeepSeek-Fähigkeiten anschließend bewusst eingeschränkt.

Damit Codex Modellname, Kontextfenster und Reasoning-Stufe kennt, lässt sich aus dem aktuellen Codex-Modellcache ein benutzerdefinierter Katalog erzeugen. Das folgende Kommando nutzt einen vorhandenen Modelleintrag als Strukturvorlage und ersetzt nur die DeepSeek-relevanten Fähigkeitsfelder:

mkdir -p ~/.codex/model-catalogs

jq '{
  models: [
    (.models[] | select(.slug == "gpt-5.6-luna")
      | .slug = "deepseek-v4-flash"
      | .display_name = "DeepSeek V4 Flash (OpenCode Go)"
      | .description = "通过 OpenCode Go 使用的 DeepSeek V4 Flash"
      | .context_window = 1000000
      | .max_context_window = 1000000
      | .effective_context_window_percent = 95
      | .default_reasoning_level = "high"
      | .supported_reasoning_levels = [
          {"effort": "high", "description": "适合日常编程与复杂任务"},
          {"effort": "max", "description": "为最困难任务提供最大推理强度"}
        ]
      | .tool_mode = null
      | .input_modalities = ["text"]
      | .supports_image_detail_original = false
      | .supports_search_tool = false
      | .use_responses_lite = false)
  ]
}' ~/.codex/models_cache.json > ~/.codex/model-catalogs/opencode-go.json

chmod 600 ~/.codex/model-catalogs/opencode-go.json

Das ist kein willkürlich zusammengebautes Minimal-JSON. Das Schema des Modellkatalogs entwickelt sich mit den Codex-Versionen weiter. Wer den vollständigen Eintrag aus dem Cache der installierten Version wiederverwendet, behält die von dieser Version verlangten Base Instructions und Pflichtfelder. Diese Konfiguration wurde mit Codex 0.145.0 verifiziert; nach einem Upgrade sollten Parsing- und End-to-End-Tests erneut laufen.

Nach der Erzeugung werden zuerst die Berechtigungen eingeschränkt und die wichtigsten Felder geprüft – die langen Base Instructions müssen nicht ausgegeben werden:

chmod 600 ~/.codex/model-catalogs/opencode-go.json

jq '.models[] | {
  slug,
  display_name,
  context_window,
  max_context_window,
  default_reasoning_level,
  tool_mode,
  input_modalities
}' ~/.codex/model-catalogs/opencode-go.json

Erwartete Schlüsselwerte:

{
  "slug": "deepseek-v4-flash",
  "display_name": "DeepSeek V4 Flash (OpenCode Go)",
  "context_window": 1000000,
  "max_context_window": 1000000,
  "default_reasoning_level": "high",
  "tool_mode": null,
  "input_modalities": ["text"]
}

Das unscheinbarste Problem: Der Modellkatalog verändert das Tool-Protokoll

Beim ersten Erzeugen des Katalogs habe ich die Fähigkeitsdeklaration des OpenAI-Modells vollständig übernommen, darunter:

{
  "tool_mode": "code_mode_only",
  "shell_type": "shell_command",
  "apply_patch_tool_type": "freeform"
}

Der Modellkatalog ließ sich fehlerfrei parsen, auch codex doctor meldete nichts, aber der echte Aufruf schlug fehl:

Unsupported custom tool: 'exec'. Only 'apply_patch' is supported.

Der Grund: tool_mode = "code_mode_only" ist nicht nur ein UI-Label. Es veranlasst Codex, im Responses-Request das Custom Tool exec zu deklarieren, während der OpenCode-Go-Upstream damals nur apply_patch als Custom Tool akzeptierte.

Der Tool-Modus des DeepSeek-Eintrags wird auf den Standardmodus geändert:

{
  "tool_mode": null
}

Dieselbe native Codex-Anfrage lieferte anschließend erfolgreich DEEPSEEK_OK.

Warum das Abschalten von features.unified_exec nicht half

Bei der Fehlersuche probierte ich zusätzlich eine Kommandozeilen-Override aus:

codex exec \
  -p deepseek \
  -c features.unified_exec=false \
  -s read-only \
  --ephemeral \
  "Reply exactly DEEPSEEK_OK. Do not use tools."

Die Anfrage meldete weiterhin denselben Unsupported custom tool: 'exec'. Das zeigt: Das Problem ist nicht nur ein globales Feature-Flag; der tool_mode = "code_mode_only" im Modelleintrag bestimmt weiterhin das Laufzeit-Tool-Protokoll.

Der wirklich aussagekräftige Kontrollversuch war: alle anderen Konfigurationen unverändert lassen und nur tool_mode im Modellkatalog auf null setzen. Vorher Fehler, nachher Erfolg – erst das ergibt einen klaren Kausalzusammenhang.

Echte Dateiänderung als Beleg für funktionierende Agent-Tools

Eine exakte Antwort belegt nur, dass das Modell Text erzeugen kann. Um sicherzugehen, dass Codex nicht bloß „chatten, aber keinen Code ändern“ kann, habe ich in einem separaten temporären Verzeichnis eine minimale Schreibaufgabe ausgeführt:

codex exec \
  -p deepseek \
  -C /private/tmp/codex-deepseek-agent-test \
  -s workspace-write \
  --ephemeral \
  --skip-git-repo-check \
  "Use apply_patch to create result.txt containing exactly DEEPSEEK_TOOL_OK followed by a newline. Then stop."

Die Laufzeitausgabe bestätigte:

model: deepseek-v4-flash
provider: opencode-go
sandbox: workspace-write
reasoning effort: high

Das Modell rief anschließend apply_patch auf, und Codex zeigte:

apply patch
patch: completed

--- /dev/null
+++ b/result.txt
@@ -0,0 +1 @@
+DEEPSEEK_TOOL_OK

Die byte-genaue Prüfung ergab 17 Bytes; das letzte Byte ist 0a:

44 45 45 50 53 45 45 4b 5f 54 4f 4f 4c 5f 4f 4b 0a
D  E  E  P  S  E  E  K  _  T  O  O  L  _  O  K  \n

Nach dem Test wurden Datei und temporäres Verzeichnis gelöscht; es blieb kein Testartefakt im Produktiv-Repository zurück.

Dieser Fall zeigt:

  • Responses-API-Unterstützung bedeutet nicht, dass alle erweiterten Codex-Tools unterstützt werden.
  • Der Modellkatalog ist keine reine Anzeigedatenquelle; er kann die Anfrage-Struktur verändern.
  • Ein erfolgreicher doctor und erfolgreiches JSON-Parsing belegen nur eine statisch gültige Konfiguration und ersetzen keine echten Anfragen.
  • Wer Metadaten von einem anderen Modell übernimmt, muss Tool-, Bild-, Such- und Reasoning-Fähigkeiten Punkt für Punkt abgleichen.

Sollte das Gateway künftig exec nativ unterstützen, kannst du den Tool-Modus neu bewerten. Deklariere Fähigkeiten erst nach einem Protokolltest, nicht im Voraus.

Schneller Provider-Wechsel über Profile

/model in einer interaktiven Codex-Session eignet sich, um Modell und Reasoning-Stufe innerhalb des aktuellen Providers zu wechseln. OpenAI und OpenCode Go sind aber zwei verschiedene Provider. Nur den Modellnamen zu ändern, kann Anfragen an den falschen Dienst schicken. Deshalb nutze Codex Profile, um Modell, Provider und Modellkatalog gemeinsam zu überschreiben.

Der aktuelle Codex verwendet separate Profildateien:

$CODEX_HOME/deepseek.config.toml
$CODEX_HOME/openai.config.toml

Nicht mehr die alte Schreibweise verwenden:

profile = "deepseek"

[profiles.deepseek]
model = "deepseek-v4-flash"

Seit Codex 0.134.0 liest --profile nicht mehr aus [profiles.<name>] in der Hauptkonfiguration, sondern lädt <name>.config.toml aus demselben Verzeichnis.

DeepSeek-Profil (Dateiname ~/.codex/deepseek.config.toml):

model = "deepseek-v4-flash"
model_provider = "opencode-go"
model_context_window = 1000000
model_catalog_json = "/Users/you/.codex/model-catalogs/opencode-go.json"
model_reasoning_effort = "high"
plan_mode_reasoning_effort = "max"

OpenAI-Profil (Dateiname ~/.codex/openai.config.toml):

model = "gpt-5.6-luna"
model_provider = "openai"
model_context_window = 272000
model_catalog_json = "/Users/you/.codex/models_cache.json"
model_reasoning_effort = "high"
plan_mode_reasoning_effort = "xhigh"

Passe /Users/you an dein System an. Kontextfenster und Reasoning-Stufen orientieren sich ebenfalls am aktuellen Modellkatalog; übernimm die Werte aus diesem Artikel nicht dauerhaft.

Umschalten beim Start:

codex -p deepseek
codex -p openai

Auch für nicht-interaktive Aufgaben gilt:

codex exec -p deepseek "检查当前代码"
codex exec -p openai "检查当前代码"

Profile werden beim Start einer neuen Session geladen. Eine bereits laufende Session lässt sich nicht verlustfrei über die Konfigurationsdateien auf einen anderen Provider umstellen; sicherer ist es, nach Abschluss der aktuellen Aufgabe eine neue Session zu starten.

Override-Reihenfolge der Konfiguration

Profile sind keine völlig eigenständige Konfiguration, sondern liegen über der Hauptkonfiguration des Benutzers. Die für diesen Artikel relevante Priorität lässt sich so vereinfachen:

用户 ~/.codex/config.toml
  < 启动时选择的 Profile
  < 项目 .codex/config.toml
  < CLI 专用参数或 -c/--config 覆盖

Das bedeutet:

  • deepseek.config.toml muss Base URL und Authentifizierung des Providers nicht wiederholen; es erbt sie aus der Hauptkonfiguration.
  • Ist model_provider projektseitig festgelegt, kann das das persönliche Profil überschreiben; zur Bestätigung dienen /status oder die Startausgabe.
  • Für kurzfristige Diagnosen eignet sich -c; erst nach erfolgreicher Prüfung entscheiden, ob die Änderung dauerhaft übernommen wird.

Abgrenzung von /model, --model und --profile

WegNeue SessionGeeignet für
/modelNeinModell oder Reasoning-Stufe innerhalb des aktuellen Providers wechseln
codex -m <model>JaEinmaliges Überschreiben des Modellnamens
codex -p <profile>JaModell, Provider, Katalog und Strategie gemeinsam wechseln
codex -c key=valueJaBeliebige Konfigurationseinträge temporär untersuchen

Beim Wechsel zwischen Providern sind Profile vorzuziehen, denn -m wählt nicht automatisch die andere Authentifizierung und Base URL.

Bei häufigem täglichem Wechsel lassen sich optionale Aliase in der persönlichen Shell-Konfiguration anlegen:

alias cdx-ds='codex -p deepseek'
alias cdx-openai='codex -p openai'

Aliase verkürzen nur den Startbefehl, sie ändern nichts an der Semantik der Codex-Konfiguration. Die Modellauswahl im Desktop-Client und die CLI-Profile sind ebenfalls nicht dasselbe; dieser Artikel verifiziert die lokale Codex CLI.

Die Verifikation braucht mehrere Ebenen

Abschließend wurde in fünf Ebenen verifiziert. Jede Ebene schließt andere Probleme aus; keine ersetzt die andere.

Ebene 1: Roh-Anfrage an die Responses API

Bestätigt, dass der OpenCode-Go-Endpunkt deepseek-v4-flash akzeptiert und completed zurückgibt. Diese Ebene schließt Probleme mit URL, Authentifizierung, Modellname und Basisprotokoll aus.

Ebene 2: Modellkatalog-Parsing

codex debug models

Die Ausgabe sollte enthalten:

deepseek-v4-flash
DeepSeek V4 Flash (OpenCode Go)
context_window: 1000000
default_reasoning_level: high
tool_mode: null

Die aktuelle Version von codex debug models akzeptiert kein --profile; Profile gelten nur für Laufzeitbefehle und einige Unterbefehle. Um zu prüfen, ob ein Profil tatsächlich greift, sieh in die Startausgabe von codex exec oder führe eine minimale Anfrage aus.

Bei der Fehlersuche lief einmal:

codex -p deepseek debug models | jq ...

Codex meldete eindeutig --profile only applies to runtime commands, aber da die Shell standardmäßig den Exit-Code des letzten Pipe-Segments (jq) zurückgibt, wirkte die gesamte Kommandozeile wie exit=0. Aktiviere in automatisierten Skripten pipefail, sonst wird der Fehler im ersten Teil leicht als Erfolg fehlinterpretiert:

set -o pipefail

Ebene 3: Codex-Health-Check

codex doctor --summary --no-color

Das Ergebnis diesmal:

17 ok · 1 idle · 1 notes · 0 warn · 0 fail

Er bestätigt, dass die Konfiguration lädt, der Provider keine OpenAI-Authentifizierung benötigt und der Ziel-HTTP-Endpunkt erreichbar ist – eine Tool-Protokoll-Diskrepanz deckt er aber nicht auf.

Ebene 4: Echte Anfragen mit beiden Profilen

Minimaler End-to-End-Test mit Read-only-Sandbox und temporärer Session:

codex exec -p deepseek \
  -s read-only \
  --ephemeral \
  "Reply exactly DEEPSEEK_OK. Do not use tools."

codex exec -p openai \
  -s read-only \
  --ephemeral \
  "Reply exactly OPENAI_OK. Do not use tools."

Am Ende lieferten sie:

DEEPSEEK_OK
OPENAI_OK

Die Startausgaben sollten außerdem zeigen:

model: deepseek-v4-flash
provider: opencode-go

sowie:

model: gpt-5.6-luna
provider: openai

Dieser Schritt verifiziert zugleich die Profil-Override-Reihenfolge, die Authentifizierung, den Modellkatalog, das Provider-Routing und die Responses-Anfragen.

Ebene 5: Datei-Tools des Agents

Mit der workspace-write-Sandbox wird in einem isolierten Verzeichnis ein echter apply_patch ausgeführt; anschließend werden Dateilänge und letztes Zeilenumbruch-Byte geprüft. Verifiziert wird nicht die Texterzeugung, sondern:

  • Das Modell kann die von Codex angebotenen Tools auswählen.
  • OpenCode Go akzeptiert die Tool-Deklaration.
  • Codex kann den Patch ausführen und das Ergebnis zurückgeben.
  • Der Inhalt der Zieldatei entspricht exakt der Vorgabe.

Erst wenn auch Ebene 5 besteht, kannst du der Kette eine minimale Coding-Agent-Fähigkeit zusprechen. Komplexere Shell-Aufgaben, parallele Tools, MCP, Bilder und Websuche müssen weiterhin separat verifiziert werden; ein einzelner apply_patch rechtfertigt keine Verallgemeinerung auf alle Fähigkeiten.

Häufige Irrtümer

Modellwechsel mit Providerwechsel gleichsetzen

/model oder --model überschreiben hauptsächlich den Modellnamen. Beim Wechsel zwischen Diensten müssen auch model_provider, Authentifizierungsmethode und Modellkatalog mitgewechselt werden. Ein Profil ist hier die verlässlichere atomare Konfigurationseinheit.

API-Key direkt in config.toml schreiben

Das erhöht das Leckrisiko bei Backups, Screenshots, Logs und versehentlichen Commits. Vorzuziehen sind bearer_token_env_var oder das Laufzeit-Authentifizierungskommando des Providers, ergänzt um restriktive Berechtigungen für die Datei mit den Zugangsdaten.

Nur doctor ausführen, keine echten Anfragen

Der Health-Check findet Probleme beim Konfigurations-Parsing und bei der Konnektivität; die vollständige Validierung der Tool-Schemas durch das Modell-Gateway löst er aber nicht zwingend aus. Führe zusätzlich mindestens eine echte Read-only-Session mit temporärem Charakter aus.

Offizielle Modellmetadaten blind kopieren

Kontextfenster, Tool-Modus, Bildeingabe, Websuche und Reasoning-Stufen können das Laufzeitverhalten beeinflussen. Kopieren ist nur ein Ausgangspunkt zum Erzeugen eines Schemas, keine Garantie für identische Fähigkeiten.

Einen überflüssigen Proxy für ein bereits unterstütztes Protokoll behalten

Wenn der Ziel-Endpunkt die Responses API bereits direkt unterstützt, bringt ein zusätzlicher Proxy nur weitere Ebenen bei Logs, Zugangsdaten, Retries und Fehlerlokalisierung. Erst die Direktverbindung verifizieren, dann entscheiden, ob wirklich eine Konvertierungsschicht nötig ist.

Checkliste: Reproduktion von Grund auf

Für die Konfiguration auf einer anderen Entwicklungsmaschine lässt sich die folgende Reihenfolge verwenden.

1. Version und Zugangsdaten prüfen

codex --version
jq -e \
  '.["opencode-go"].key | type == "string" and length > 0' \
  ~/.local/share/opencode/auth.json >/dev/null

2. Konfiguration sichern

cp ~/.codex/config.toml ~/.codex/config.toml.before-opencode-go

3. /responses mit einer Roh-Anfrage verifizieren

Nur einen kurzen Text senden, keine Tools anhängen. HTTP-Status, status, model und output_text prüfen.

4. Provider und Laufzeit-Authentifizierung hinzufügen

Zunächst nur model_provider, base_url, wire_api und die Authentifizierung konfigurieren und die Zahl der Variablen so klein wie möglich halten.

5. Erste Codex-Anfrage mit Fallback-Metadaten

Gelingt die Anfrage, erscheint aber eine Warnung zu den Modellmetadaten, ist die Laufzeitkette aufgebaut; der Katalog wird anschließend separat behandelt.

6. Lokalen Katalog aus dem aktuellen Modellcache erzeugen

Den vollständigen Eintrag klonen, Kontext, Eingabemodalitäten, Such- und Tool-Fähigkeiten einschränken und sicherstellen, dass tool_mode = null gesetzt ist.

7. Beide Profile getrennt anlegen

Das DeepSeek-Profil verweist auf OpenCode Go; das OpenAI-Profil auf OpenAI und den nativen Modellcache.

8. Statische und echte Verifikation nacheinander

codex debug models
codex doctor --summary --no-color
codex exec -p deepseek -s read-only --ephemeral "Reply exactly DEEPSEEK_OK."
codex exec -p openai -s read-only --ephemeral "Reply exactly OPENAI_OK."

9. apply_patch in einem isolierten Verzeichnis verifizieren

Der erste Tool-Test gehört nicht direkt in ein wichtiges Repository. Nach der Prüfung des Dateiinhalts das temporäre Verzeichnis aufräumen.

10. Versionen dokumentieren und Rollback-Punkt sichern

Codex, Gateway und Modellfähigkeiten ändern sich. Testdatum, Codex-Version, Modell-Slug und verifizierte Tools in die Dokumentation aufnehmen; nach einem Upgrade dieselben Prüfungen erneut ausführen.

Derzeit verifizierte und nicht verallgemeinerte Grenzen

Stand 2026-08-06 wurden mit dieser Konfiguration real verifiziert:

  • Nicht-streaming-minimale Anfragen gegen OpenCode Go /v1/responses.
  • Native Responses-Aufrufe von Codex.
  • Exakte Textantworten auf der Reasoning-Stufe high.
  • Die beiden CLI-Profile DeepSeek und OpenAI.
  • DeepSeek wählt apply_patch aus und führt ihn aus.
  • Codex-Health-Check, Modellkatalog-Parsing und Provider-Konnektivität.

Nicht als belegt gelten in diesem Artikel:

  • Grenzwerte für 1-Millionen-Kontext und die Grenzen der automatischen Komprimierung.
  • Bildeingabe, Original-Bilddetails und multimodale Ausgabe.
  • Erweiterte Tools wie Web Search, MCP, Browser und Computer Use.
  • Das Custom Tool exec und das vereinheitlichte PTY-Ausführungsprotokoll.
  • Wiederherstellung nach langen SSE-Unterbrechungen, parallele Tool-Aufrufe und Rate-Limit-Backoff.
  • Provider-Wechsel mit benutzerdefinierten Providern in Codex-Desktop- oder Cloud-Sessions.

Diese Grenzziehung ist keine vorsichtige Formulierung, sondern verhindert, aus „die API gibt einen Satz zurück“ fälschlich „alle Codex-Fähigkeiten entsprechen dem OpenAI-Provider“ zu machen.

Rollback

Zur vollständigen Wiederherstellung der vorherigen Codex-Standardkonfiguration:

cp ~/.codex/config.toml.before-opencode-go ~/.codex/config.toml

Profildateien sind eine separate Override-Ebene und berühren das Backup nicht. Wenn du sie nicht mehr brauchst, verschiebe sie zuerst aus ~/.codex und lösche sie erst nach einem erfolgreichen Codex-Start.

Fazit

Der wirklich schwierige Teil dieser Integration war nicht, model auf deepseek-v4-flash zu setzen, sondern die Fähigkeitsgrenzen der gesamten Kette zu ermitteln:

  1. Die Endpunkte von DeepSeek und OpenCode Go akzeptieren die Responses API.
  2. Der Codex-Provider nutzt Laufzeit-Authentifizierung, ohne Klartext-Zugangsdaten zu duplizieren.
  3. Der benutzerdefinierte Modellkatalog ergänzt Kontext und Reasoning-Stufen.
  4. tool_mode muss zum Custom-Tool-Protokoll des Gateways passen.
  5. Profile wechseln Modell, Provider und Katalog gemeinsam.
  6. Roh-API, statische Diagnose und native Codex-Anfragen müssen getrennt verifiziert werden.
  7. Erst nach einem echten apply_patch ist die minimale Coding-Agent-Kette belegt.

Die größte Lehre ist kein einzelnes TOML-Snippet, sondern die Reihenfolge der Fehlersuche: Erst das minimale Protokoll verifizieren, dann Codex anbinden; erst mit Fallback-Metadaten die Hauptkette belegen, dann den Modellkatalog ergänzen; nach der statischen Prüfung unbedingt eine echte Tool-Aufgabe ausführen. So hat jeder Schritt genau eine Hauptvariable, und bei einem Fehler kehrst du schnell zur richtigen Ebene zurück.
