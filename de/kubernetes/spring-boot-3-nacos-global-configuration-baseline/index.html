Nacos-Produktionsbaseline für Spring Boot 3: Redis, RabbitMQ, Hikari und Probes

Umsetzbare, mehrschichtige Nacos-Konfiguration für Spring Boot 3: Redis, RabbitMQ-Parallelität und Prefetch, Hikari, Tomcat, Graceful Shutdown und Actuator.

lucaslzAutor
9. August 2026 10 Min. Lesezeit
#Spring Boot #Nacos #Redis #RabbitMQ #Konfigurations-Governance
{ }

Dieser Beitrag entstand bei einer Governance-Runde zu Verbindungszahlen und Container-Speicher mehrerer Dienste. Adressen, Konten, Namespaces und Geschäftsnamen wurden generalisiert. Die Werte sind konservative Ausgangspunkte und müssen an die Kapazität von Datenbank, Redis und RabbitMQ sowie an die Lasttest-Ergebnisse angepasst werden.

Wenn Dutzende Spring Boot 3-Dienste gemeinsam eine global.properties lesen, wird jede beiläufige Optimierung durch die Replikazahl verstärkt:

每 Pod 多 8 个 Redis 空闲连接
× 60 个 Pod
= 480 个额外连接

Bei RabbitMQ verhält es sich genauso: Dutzende @RabbitListener, mehrere Consumer-Threads und ein großzügiger Prefetch verstärken sich gegenseitig – mehr Channels und Threads, und viele unbestätigte Nachrichten bleiben im JVM-Heap zurück.

Eine „vollständige Nacos-Konfiguration“ besteht daher nicht darin, alle verfügbaren Parameter zu setzen. Sie muss klar beantworten:

  • Welche Werte bilden eine sichere Baseline, die alle Spring Boot 3-Dienste teilen.
  • Welche Werte ausschließlich in die anwendungsspezifische dataId gehören.
  • Welche sensiblen Werte zwingend aus einem Kubernetes Secret stammen müssen.
  • Welche älteren Boot-Dienste eine temporäre Kompatibilitätsschicht brauchen.
  • Wie die Obergrenze jedes Verbindungspools zusammen mit der Pod-Anzahl berechnet wird.

Empfohlene Konfigurationsschichten

flowchart TD
  A["Kubernetes Secret / Umgebungsvariablen"] --> D["Finale Environment"]
  B["global.properties<br/>Konservative Boot-3-Baseline"] --> D
  C["application.properties<br/>Anwendungsausnahmen"] --> D

Empfohlene Abgrenzung:

SchichtInhaltBeispiel
SecretPasswörter, Tokens, ZertifikateRedis-, RabbitMQ- und Datenbank-Passwörter
global dataIdKonservative Parameter mit einheitlicher Version und SemantikTimeout, Probes, Standard-Parallelität

Derselbe Key sollte nicht in allen vier Schichten gepflegt werden. Spring-Property-Sources haben eine feste Priorität: Überschreibt eine Deployment-Umgebungsvariable Nacos, bedeutet eine erfolgreiche Veröffentlichung in der Konsole noch nicht, dass sich der Wert zur Laufzeit geändert hat.

Eine prüfbare Spring Boot 3-Globalvorlage

Die folgende Vorlage verwendet Platzhalter und enthält keine Produktionspasswörter. Betrachte sie zunächst als Kandidaten-Baseline, statt sie ungeprüft vollständig zu veröffentlichen.

# ------------------------------------------------------------
# Web 与反向代理
# ------------------------------------------------------------
server.forward-headers-strategy=framework
server.shutdown=graceful
spring.lifecycle.timeout-per-shutdown-phase=30s

# 仅适用于 Servlet / Tomcat 服务；WebFlux 服务会忽略这些项
server.tomcat.threads.max=100
server.tomcat.threads.min-spare=10
server.tomcat.accept-count=100
server.tomcat.max-connections=2000
server.tomcat.connection-timeout=10s

# ------------------------------------------------------------
# Actuator 与 Kubernetes 探针
# ------------------------------------------------------------
management.endpoint.health.probes.enabled=true
management.health.livenessstate.enabled=true
management.health.readinessstate.enabled=true
management.endpoint.health.show-details=never
management.endpoints.web.exposure.include=health,info,prometheus,serviceregistry

# ------------------------------------------------------------
# HikariCP：只对使用 Spring 默认 Hikari DataSource 的服务生效
# ------------------------------------------------------------
spring.datasource.hikari.maximum-pool-size=10
spring.datasource.hikari.minimum-idle=2
spring.datasource.hikari.connection-timeout=3000
spring.datasource.hikari.validation-timeout=1000
spring.datasource.hikari.idle-timeout=600000
spring.datasource.hikari.max-lifetime=1800000
spring.datasource.hikari.keepalive-time=120000

# ------------------------------------------------------------
# Spring Data Redis / Lettuce
# 地址不是 Secret，密码从环境变量读取
# ------------------------------------------------------------
spring.data.redis.host=redis-service.app.svc.cluster.local
spring.data.redis.port=6379
spring.data.redis.database=0
spring.data.redis.password=${REDIS_PASSWORD:}
spring.data.redis.connect-timeout=3s
spring.data.redis.timeout=3s
spring.data.redis.client-type=lettuce
spring.data.redis.lettuce.shutdown-timeout=100ms

# 默认不启用连接池，避免 commons-pool2 出现在 classpath 后
# 每个 Pod 自动建立一批空闲连接
spring.data.redis.lettuce.pool.enabled=false

# ------------------------------------------------------------
# RabbitMQ
# ------------------------------------------------------------
spring.rabbitmq.addresses=rabbitmq.app.svc.cluster.local:5672
spring.rabbitmq.username=${RABBITMQ_USERNAME}
spring.rabbitmq.password=${RABBITMQ_PASSWORD}
spring.rabbitmq.virtual-host=/
spring.rabbitmq.connection-timeout=5s
spring.rabbitmq.requested-heartbeat=30s

spring.rabbitmq.cache.connection.mode=channel
spring.rabbitmq.cache.channel.size=25
spring.rabbitmq.cache.channel.checkout-timeout=2s

spring.rabbitmq.listener.type=simple
spring.rabbitmq.listener.simple.concurrency=1
spring.rabbitmq.listener.simple.max-concurrency=3
spring.rabbitmq.listener.simple.prefetch=10
spring.rabbitmq.listener.simple.acknowledge-mode=auto
spring.rabbitmq.listener.simple.auto-startup=true

# ------------------------------------------------------------
# 文件上传：限制请求在内存和临时盘中的放大
# ------------------------------------------------------------
spring.servlet.multipart.max-file-size=100MB
spring.servlet.multipart.max-request-size=110MB
spring.servlet.multipart.file-size-threshold=2MB

Zuerst veraltete Properties korrigieren

Die Vorlage verwendet bereits server.forward-headers-strategy und verzichtet auf server.use-forward-headers. Die Wahl zwischen NATIVE, FRAMEWORK und NONE hängt von der konkreten Proxy-Kette ab; X-Forwarded-*-Header aus dem öffentlichen Netz darf man nicht bedingungslos vertrauen.

Migrationsberichte für alte Keys und die Exit-Kriterien von spring-boot-properties-migrator werden zentral im Spring Boot 3 Container-Start-Postmortem gepflegt; dieser Beitrag enthält nur die finale Produktionskonfiguration.

Redis: Weniger Verbindungen heißt nicht automatisch kleinerer Pool

Mit Spring Data Redis und Lettuce können normale Befehle die gemeinsame native Connection wiederverwenden. Nicht jeder Dienst benötigt standardmäßig einen Verbindungspool.

Die Property-Referenz von Spring Boot 3.1 erklärt: Befindet sich commons-pool2 im Classpath, kann der Lettuce-Pool automatisch aktiviert werden. Zieht also später ein Starter diese Abhängigkeit nach, kann sich das Verbindungsverhalten ändern.

Im Rahmen dieser Governance gilt global:

spring.data.redis.lettuce.pool.enabled=false

Nur Anwendungen, die alle folgenden Bedingungen erfüllen, aktivieren den Pool in ihrer eigenen dataId:

  • Sie verwenden blockierende Redis-Befehle.
  • Sie nutzen Transaktionen oder Aufrufe, die eine exklusive Connection benötigen.
  • Metriken belegen Konkurrenz auf der gemeinsamen Connection.
  • Im Classpath befindet sich explizit eine kompatible commons-pool2-Version.

Kandidaten für die Anwendungsebene:

spring.data.redis.lettuce.pool.enabled=true
spring.data.redis.lettuce.pool.max-active=8
spring.data.redis.lettuce.pool.max-idle=4
spring.data.redis.lettuce.pool.min-idle=0
spring.data.redis.lettuce.pool.max-wait=2s
spring.data.redis.lettuce.pool.time-between-eviction-runs=60s

min-idle=0 verhindert, dass jeder Pod ohne Geschäftslast eine Reihe ungenutzter Verbindungen vorhält. Ob der Wert erhöht werden sollte, hängt von den connected_clients, der Befehlslatenz von Redis und den Pool-Warte-Metriken ab.

Nicht vergessen: Redisson ist ein eigener Client

spring.data.redis.* begrenzt nicht RedissonClient-Instanzen, die im Code separat erzeugt werden. Nutzt ein Dienst Spring Data Redis und Redisson parallel, ergibt sich die Gesamtzahl der Verbindungen aus der Summe beider Clients.

Zusätzlich gilt es zu erfassen:

  • Ob Redisson im Single-Node-, Master-Slave-, Sentinel- oder Cluster-Modus läuft.
  • connectionPoolSize und connectionMinimumIdleSize.
  • Der Subscription-Verbindungspool.
  • threads und nettyThreads.
  • Wie viele RedissonClient-Instanzen ein Pod tatsächlich erzeugt.

Das Verbindungsbudget sollte pro Client getrennt berechnet werden:

总连接上界
≈ Pod 数
× 每 Pod 的 Lettuce 连接
+ Pod 数
× 每 Pod 的 Redisson 普通连接
+ subscription 连接
+ Redis 运维与监控连接

Mehrere Geschäftsmodule, die jeweils new RedissonClient aufrufen, sind gefährlicher als leicht überdimensionierte Pool-Parameter. Bevorzuge es, pro Anwendungskontext genau eine Gruppe verwalteter Clients zu erzeugen.

RabbitMQ: Global begrenzt wird jeder Listener-Container

In der Property-Dokumentation von Spring Boot RabbitMQ:

  • concurrency ist die minimale Anzahl der Listener-Invoker-Threads.
  • max-concurrency ist die Obergrenze der automatischen Skalierung.
  • prefetch ist die maximale Anzahl unbestätigter Nachrichten pro Consumer.

Also:

concurrency=1
max-concurrency=3
prefetch=10

Das heißt nicht „höchstens drei Nachrichten pro Dienst“, sondern: pro Listener-Container maximal drei Consumer und pro Consumer maximal zehn unbestätigte Nachrichten.

Bei 40 Listenern in einer Anwendung kann die theoretische Obergrenze erreicht werden:

40 × 3 × 10 = 1200 条未确认消息

Die tatsächliche Zahl hängt von Queue-Durchsatz und Container-Skalierung ab, aber diese Multiplikation erklärt, warum der Heap bei Diensten mit vielen Listenern plötzlich ansteigt.

In der globalen Baseline solltest du Folgendes nicht direkt ändern:

spring.rabbitmq.listener.simple.default-requeue-rejected
spring.rabbitmq.listener.simple.retry.enabled
spring.rabbitmq.publisher-confirm-type

Diese Werte verändern die Zuverlässigkeitssemantik von Nachrichten und müssen von den Fachteams zusammen mit DLQ, Idempotenz und Retry-Strategie entschieden werden – nicht als reine Performance-Optimierung.

Hikari: Zuerst rechnen, wie viele Verbindungen die Datenbank verträgt

maximum-pool-size=10 ist erst sinnvoll, wenn die Gesamtzahl der Verbindungen mit einkalkuliert wird:

数据库业务连接上界
= 所有服务的 Pod 数 × 各自 maximumPoolSize
+ 任务、管理、迁移和运维连接

Beispiel: 50 Dienste, jeweils 2 Pods und 20 Verbindungen pro Pool ergeben bereits 2000 Verbindungen. Nur weil jeder Pool „nur 20“ hat, heißt das nicht, dass die Datenbank das trägt.

Empfohlene Schritte:

  1. Alle Aufrufer und Replikazahlen je Datenbankinstanz zusammenfassen.
  2. Spitzenwerte für active, idle, pending und acquire time aufzeichnen.
  3. Normale Dienste zunächst mit kleineren Verbindungspools betreiben.
  4. Für Dienste mit hoher Parallelität oder langen Transaktionen Ausnahmen auf Anwendungsebene definieren.
  5. Puffer für Datenbankbetrieb und Failover einplanen.

Nutzt ein Projekt dynamic-datasource, Druid oder manuell erzeugte DataSources, wirkt spring.datasource.hikari.* möglicherweise nur auf die Standard-DataSource. Entscheidend ist der finale Bean, nicht nur der Nacos-Key.

Tomcat-Threads und Datenbankverbindungen sind nicht 1:1

server.tomcat.threads.max=100 bedeutet nicht, dass auch Hikari mit 100 Verbindungen konfiguriert werden sollte. Viele Requests werden vom Cache bedient, scheitern an der Validierung oder führen Nicht-Datenbanklogik aus; umgekehrt kann ein Request auch mehrere Datenquellen parallel ansprechen.

Die Kapazitätsbeziehung ist über Metriken zu verifizieren:

HTTP active threads
→ 数据库 active / pending
→ 下游 P95/P99
→ CPU 与 GC

WebFlux-/Netty-Dienste verwenden keine Tomcat-Thread-Konfiguration. Entferne diese wirkungslosen Werte aus der app-dataId und steuere Event Loop, Verbindungspools und Direct Buffer separat.

Die Actuator-Exposition muss zur Netzwerk-Grenze passen

health, prometheus und serviceregistry sind global freigegeben, damit Probes, Monitoring und das saubere Abziehen von Traffic funktionieren. serviceregistry kann jedoch den Registrierungsstatus verändern und darf nicht direkt aus dem öffentlichen Netz erreichbar sein.

Mindestens erforderlich:

  • Der Management-Port ist nur aus dem Cluster erreichbar.
  • Der Ingress leitet Management-Pfade nicht weiter, oder der Zugriff ist über Authentifizierung und NetworkPolicy begrenzt.
  • Health-Details geben keine Adressen, Konten oder Exception-Stacks preis.
  • Prometheus wird über einen definierten ServiceMonitor oder kontrolliertes Scraping abgerufen.

Lässt sich die Grenze nicht garantieren, sollte man Management-Endpoints nicht nur wegen des bequemen preStop global freigeben.

Boot-2-Dienste sollten diese globale Redis-Konfiguration nicht direkt erben

Spring Boot 2 nutzt spring.redis.*, Spring Boot 3 nutzt spring.data.redis.*. Noch nicht migrierte Dienste ergänzen nur in ihrer eigenen dataId Kompatibilitäts-Aliasse; alte Prefixe gehören nicht zurück in die Boot-3-Globalbaseline.

Die Kompatibilitätskonfiguration, die Beweiskette für localhost:6379 und die commons-pool2-Falle werden zentral in Boot 2/3 Redis-Konfiguration fällt auf localhost zurück gepflegt; dieser Beitrag wiederholt sie nicht.

Veröffentlichungsreihenfolge in Nacos

Änderungen an der globalen dataId betreffen viele Clients. Empfohlen:

  1. Originalkonfiguration, Namespace, Group, dataId und Prüfwerte exportieren und sichern.
  2. Für alle Keys eine Matrix aus Boot-Version und Komponenten-Eignung erstellen.
  3. Offensichtlich anwendungsspezifische Parameter aus global entfernen.
  4. Einen normalen Dienst auswählen und Kandidatenwerte über einen temporären Override auf Anwendungsebene testen.
  5. Ein Pod per Rollout ersetzen und die realen Redis-, RabbitMQ- und Datenbank-Pfade verifizieren.
  6. Verbindungen, Threads, Heap, Nachrichten-Stau und Latenz beobachten.
  7. Danach global veröffentlichen und die Dienste in mehreren Wellen rollen.
  8. Nacos zurücklesen und die effektive Konfiguration sowie die jüngsten Logs der neuen Pods prüfen.

Nicht gleichzeitig ändern:

  • Redis-Pool.
  • RabbitMQ-Parallelität.
  • Hikari-Obergrenze.
  • JVM-Heap.
  • Probe-Schwellenwerte.

Sonst lässt sich bei sinkendem Speicher oder schlechterem Durchsatz nicht mehr feststellen, welcher Parameter die Ursache ist.

Abnahme-Metriken

KomponentePflicht-MetrikenRisikosignale
Redisconnected_clients, Befehlslatenz, TimeoutsVerbindungen sinken, Pool-Wartezeit steigt
RedissonClients und Verbindungen je PodMehrfach erzeugte Instanzen
RabbitMQready, unacked, consumer, channelStau wächst kontinuierlich
Hikariactive, idle, pending, acquirepending ungleich null, Latenz steigt
Tomcatactive, queue, rejectThreads dauerhaft ausgelastet
JVMHeap used/committed, GC, RSSMehr Full GC oder OOM
KubernetesReady, Restart, rolloutAlte ReplicaSets lassen sich nicht beenden

Mindestens eine echte Geschäfts-Lastspitze abwarten, bevor weiter eingeschränkt wird.

Definition of Done

  • global.properties enthält nur Parameter, die für Boot 3 gelten und semantisch allgemeingültig sind.
  • Secrets liegen nicht im Klartext in Nacos.
  • Der Redis-Verbindungspool wächst standardmäßig nicht automatisch durch Classpath-Änderungen.
  • Redisson und Spring Data Redis werden getrennt im Verbindungsbudget geführt.
  • RabbitMQ-Parallelität und Prefetch sind anhand der Listener-Anzahl berechnet.
  • Die Gesamtzahl der Datenbankverbindungen liegt unter der Instanzkapazität und lässt Puffer für Failover.
  • Servlet- und WebFlux-Konfigurationen werden nicht mehr vermischt.
  • Zwischen Deployment-Umgebungsvariablen und Nacos gibt es keine doppelte Wahrheitsquelle, die sich gegenseitig überschreibt.
  • Boot-2-Kompatibilitätswerte existieren nur in der app-dataId und haben eine Löschfrist.

Fazit

Ziel der globalen Konfiguration ist nicht, dass alle Dienste identische Parameter haben, sondern ein minimales, sicheres und vorhersagbares Standardverhalten.

Redis-Verbindungen, unbestätigte RabbitMQ-Nachrichten und Datenbank-Verbindungspools wachsen mit der Pod-Anzahl und der Zahl der Geschäftskomponenten. Vor dem Einstellen in Nacos muss gerechnet werden; nach der Veröffentlichung ist zu prüfen, dass keine Deployment-Umgebungsvariable die Werte überschreibt.

Eine wirklich vollständige Konfiguration zeichnet sich nicht durch möglichst viele Keys aus, sondern dadurch, dass jeder Key eine passende Boot-Version, eine Kapazitätsbegründung, eine Override-Beziehung, eine Monitoring-Metrik und eine Rollback-Grenze hat.
