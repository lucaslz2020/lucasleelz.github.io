Kubernetes-Grundkomponenten einrichten: Calico, Metrics, NFS und Ingress

Calico, metrics-server, NFS-Dynamikspeicher und NGINX Ingress im kubeadm-Cluster nacheinander installieren und mit Smoke-Tests und Fehleranalyse verifizieren.

lucaslzAutor
6. Juni 2026 6 Min. Lesezeit
#Kubernetes #Calico #metrics-server #NFS #Ingress
{ }

Eine abgeschlossene kubeadm-Initialisierung bedeutet nur, dass die Control Plane bereitsteht. Ein Cluster, der produktive Workloads aufnehmen soll, braucht zusätzlich ein Pod-Netzwerk, Metriken, dynamischen Speicher und einen Ingress-Controller.

Seriennavigation: Kubernetes-Neuaufbau-Migrationsreihe. Schließe zuerst „Kubernetes von Grund auf aufbauen“ ab, bevor du mit diesem Beitrag weitermachst.

Dieser Beitrag geht von einem leeren Cluster aus: einer Control Plane mit drei Knoten und mehreren Worker-Knoten. Alle Images und Manifests müssen auf feste Versionen gepinnt und in Git eingecheckt werden; die <...>-Platzhalter in den Beispielen musst du ersetzen.

Installationsreihenfolge

Am besten hältst du dich strikt an die folgende Reihenfolge:

Calico → CoreDNS 验收 → metrics-server → StorageClass → Ingress → 综合冒烟

Bis Calico läuft, ist das gesamte Pod-Netzwerk nicht vertrauenswürdig. Bevor der Speicher bereitsteht, solltest du keine zustandsbehafteten Workloads deployen.

Schritt 1: Pod-CIDR prüfen

Bestätige die Pod-CIDR in der kubeadm-Konfiguration und in den Argumenten des Controllers:

grep -n 'podSubnet' manifests/kubeadm.yaml
kubectl -n kube-system get pod -l component=kube-controller-manager -o yaml \
  | grep -n -- '--cluster-cidr'

Prüfe danach den Adresspool im Calico-Manifest:

grep -nE 'CALICO_IPV4POOL_CIDR|cidr:' manifests/calico.yaml

Alle drei Angaben müssen übereinstimmen und dürfen sich weder mit dem Knotennetz, der Service-CIDR noch mit dem Büro- oder VPN-Netz überschneiden.

Schritt 2: Calico installieren

Führe zuerst einen serverseitigen Dry-Run aus:

kubectl apply --server-side --dry-run=server -f manifests/calico.yaml
kubectl apply -f manifests/calico.yaml

Beobachte die zentralen Pods:

kubectl -n kube-system get pods -l k8s-app=calico-node -o wide -w
kubectl -n kube-system rollout status daemonset/calico-node --timeout=10m
kubectl -n kube-system rollout status deployment/calico-kube-controllers --timeout=10m
kubectl get nodes

Alle Knoten sollten Ready sein, und auf jedem schedulbaren Knoten sollte ein calico-node laufen.

Falls ein Knoten fehlschlägt:

kubectl -n kube-system describe pod <calico-pod>
kubectl -n kube-system logs <calico-pod> -c calico-node --tail=200
sudo journalctl -u containerd -u kubelet -n 200 --no-pager

Behebe zuerst Probleme mit Modulen, sysctl, Routing, MTU und Firewall – verlass dich nicht auf Glück, indem du Pods wiederholt löschst.

Schritt 3: Netzwerk und DNS über Knoten hinweg verifizieren

Wenn du zwei Test-Deployments auf verschiedenen Knoten verteilen möchtest, ist der einfachste Weg: Lege zuerst zwei Pods an und pinne sie per nodeName auf zwei Testknoten:

apiVersion: v1
kind: Pod
metadata:
  name: net-a
  namespace: default
  labels: { app: net-smoke }
spec:
  nodeName: <worker-a>
  containers:
    - name: web
      image: <approved-nginx-image>
---
apiVersion: v1
kind: Pod
metadata:
  name: net-b
  namespace: default
spec:
  nodeName: <worker-b>
  containers:
    - name: client
      image: <approved-curl-image>
      command: ["sleep", "3600"]

Nach dem Anwenden holst du die Pod-IP von net-a und greifst von net-b aus darauf zu:

kubectl apply -f manifests/smoke/network.yaml
POD_IP="$(kubectl get pod net-a -o jsonpath='{.status.podIP}')"
kubectl exec net-b -- curl -fsS "http://${POD_IP}"

Lege außerdem einen ClusterIP-Service für net-a an:

kubectl expose pod net-a --name=net-smoke --port=80
kubectl exec net-b -- nslookup net-smoke.default.svc.cluster.local
kubectl exec net-b -- curl -fsS http://net-smoke

Diese drei Prüfungen belegen, dass das Pod-Routing über Knoten hinweg, CoreDNS und die Service-Weiterleitung funktionieren.

Schritt 4: metrics-server installieren

Speichere das offizielle Manifest in einer festen Version unter manifests/metrics-server.yaml, synce das Image in die interne Registry und wende es dann an:

kubectl apply --server-side --dry-run=server -f manifests/metrics-server.yaml
kubectl apply -f manifests/metrics-server.yaml
kubectl -n kube-system rollout status deployment/metrics-server --timeout=5m

Warte, bis die Aggregated API verfügbar ist:

kubectl get apiservice v1beta1.metrics.k8s.io
kubectl top nodes
kubectl top pods -A --sort-by=memory | head

Wenn Metrics API not available angezeigt wird:

kubectl describe apiservice v1beta1.metrics.k8s.io
kubectl -n kube-system logs deployment/metrics-server --tail=200

Häufige Ursachen sind ein nicht passendes SAN im kubelet-Zertifikat, ein nicht erreichbarer kubelet-Port und eine falsche Adressauswahl. Behandle --kubelet-insecure-tls nicht als Standardlösung für die Produktion.

Schritt 5: Dynamischen Speicher einrichten

Dieser Beitrag nutzt den NFS Dynamic Provisioner als Beispiel. Verifiziere auf jedem Knoten zuerst, dass der Storage-Server erreichbar ist, und stelle sicher, dass der NFS-Client installiert ist:

showmount -e <storage-server>

Wende das geprüfte RBAC, das Deployment und die StorageClass an:

kubectl apply -f manifests/storage/nfs-provisioner.yaml
kubectl -n storage-system rollout status deployment/nfs-provisioner --timeout=5m
kubectl get storageclass

Erstelle ein minimales PVC:

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-smoke
spec:
  storageClassName: <nfs-storage-class>
  accessModes: [ReadWriteMany]
  resources:
    requests:
      storage: 1Gi
---
apiVersion: v1
kind: Pod
metadata:
  name: pvc-smoke
spec:
  containers:
    - name: shell
      image: <approved-busybox-image>
      command: ["sh", "-c", "date > /data/created-at && sleep 3600"]
      volumeMounts:
        - { name: data, mountPath: /data }
  volumes:
    - name: data
      persistentVolumeClaim: { claimName: pvc-smoke }

Verifikation:

kubectl apply -f manifests/smoke/pvc.yaml
kubectl wait --for=condition=Ready pod/pvc-smoke --timeout=5m
kubectl exec pvc-smoke -- cat /data/created-at
kubectl get pvc,pv

Erst wenn die Datei nach dem Löschen und Neuaufbauen des Pods weiterhin existiert, ist die Persistenzkette nachgewiesen.

Schritt 6: NGINX Ingress installieren

Label zuerst die Ingress-Knoten und füge je nach Design die Taints hinzu:

kubectl label node <ingress-node-a> workload.yj/role=ingress
kubectl label node <ingress-node-b> workload.yj/role=ingress
kubectl label node <ingress-node-c> workload.yj/role=ingress

Konfiguriere im Ingress-Controller-Manifest die passenden nodeSelector, Tolerations und drei Replikas und wende es anschließend an:

kubectl apply -f manifests/ingress-nginx/
kubectl -n ingress-nginx rollout status deployment/ingress-nginx-controller --timeout=10m
kubectl -n ingress-nginx get pods -o wide
kubectl get ingressclass

Erstelle ein Ingress, das nur für Tests im internen Netz gedacht ist:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: net-smoke
spec:
  ingressClassName: nginx
  rules:
    - host: smoke.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: net-smoke
                port: { number: 80 }

Ohne die öffentliche DNS zu ändern, kannst du direkt über die Ingress-Adresse verifizieren:

curl --resolve smoke.example.com:80:<ingress-address> \
  http://smoke.example.com/

Schritt 7: Testressourcen aufräumen und Bericht speichern

kubectl delete -f manifests/smoke/network.yaml
kubectl delete service net-smoke
kubectl delete -f manifests/smoke/pvc.yaml

kubectl get nodes -o wide > reports/nodes.txt
kubectl get pods -A -o wide > reports/pods.txt
kubectl top nodes > reports/node-metrics.txt
kubectl get storageclass,pv,pvc -A > reports/storage.txt
kubectl get ingressclass > reports/ingressclass.txt

Definition of Done

  • Pod-IPs sind über Knoten hinweg erreichbar.
  • CoreDNS löst die Service-FQDN auf.
  • ClusterIP ist von verschiedenen Knoten aus erreichbar.
  • kubectl top nodes und kubectl top pods liefern Daten.
  • PVCs binden dynamisch, und die Daten überleben einen Pod-Neuaufbau.
  • Ingress routet über den Host-Header korrekt zum Test-Service.
  • Alle Manifests sind versioniert, Images sind auf Digests gepinnt, und Rollback-Versionen sind festgehalten.

Erst wenn alle diese Prüfungen bestanden sind, ist der richtige Zeitpunkt für die Planung der Node-Pools und die Migration der Workloads gekommen.
