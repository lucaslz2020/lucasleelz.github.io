Dreiknotiges Nacos-Cluster auf Kubernetes: vom Service zum StatefulSet

Einen dreiknotigen Nacos-Cluster aufsetzen: Datenbank, Secret, Headless Service, Service, StatefulSet, Authentifizierung, Anti-Affinity, Probes und Abnahme.

lucaslzAutor
14. Juni 2026 7 Min. Lesezeit
#Kubernetes #Nacos #StatefulSet #Service #MySQL
{ }

In diesem Beitrag geht es um genau eine Sache: einen Nacos-Cluster mit drei Knoten in einem Kubernetes-Cluster aufzusetzen, das bereits über CNI, DNS und dynamischen Storage verfügt.

Reihennavigation: Kubernetes-Neuaufbau-Migrationsreihe. Danach folgen Service-DNS-Governance und das Smooth Upgrade.

Alle im Beitrag genannten Image-Versionen, Domains, Passwörter und Adressen sind Platzhalter. Vor dem Produktivgang müssen die Umgebungsvariablen und das Datenbankschema gegen das Ziel-Nacos-Image geprüft werden; latest darf nicht direkt verwendet werden.

Zuerst die Zielstruktur verstehen

Nacos benötigt nur drei Pods, aber zwei Services:

flowchart LR
  A["App-Client"] --> B["nacos-client ClusterIP"]
  B --> C["nacos-0"]
  B --> D["nacos-1"]
  B --> E["nacos-2"]
  C <--> F["nacos-headless"]
  D <--> F
  E <--> F
  C --> G["Externe MySQL"]
  D --> G
  E --> G
  • nacos-headless hat clusterIP: None und liefert den StatefulSet-Pods eine stabile DNS, sodass sich die drei Nacos-Knoten gegenseitig finden können.
  • nacos-client ist ein normaler ClusterIP-Service. Anwendungen verbinden sich nur mit ihm und kümmern sich nicht um eine bestimmte Pod-IP.
  • Konfiguration und Service-Registrierungsdaten liegen in der externen MySQL; beim Neuerstellen von Pods geht nichts verloren.

Der Headless Service ist keine zusätzliche Nacos-Instanz, und Geschäftsanwendungen müssen ihn nicht direkt verwenden.

Voraussetzungen

Zunächst die grundlegenden Fähigkeiten des Clusters prüfen:

kubectl get nodes
kubectl get storageclass
kubectl -n kube-system get deployment coredns
kubectl run dns-smoke --image=<approved-busybox-image> --restart=Never \
  --command -- nslookup kubernetes.default.svc.cluster.local
kubectl logs dns-smoke
kubectl delete pod dns-smoke

Anforderungen:

  • Mindestens drei planbare Worker-Nodes.
  • Die Standard-StorageClass kann PVCs dynamisch erstellen, oder statische PVs sind bereits vorhanden.
  • Die externe MySQL ist hochverfügbar und verfügt über unabhängige Backups.
  • Das Nacos-Image ist in die interne Registry synchronisiert und auf einen festen Digest gepinnt.
  • Netzwerk und DNS zwischen den Knoten und MySQL sind verifiziert.

Schritt 1: Namespace und Datenbank vorbereiten

Einen dedizierten Namespace anlegen:

kubectl create namespace nacos-system

Das passende mysql-schema.sql der Ziel-Datenbank aus dem Nacos-Distributionspaket holen, zuerst in einer Testdatenbank ausführen und anschließend vom Datenbankadministrator auf die Produktionsdatenbank anwenden lassen. Kein SQL mit unbekannter Version aus dem alten Blog übernehmen.

Nach der Ausführung mindestens das Vorhandensein der Kerntabellen prüfen:

SHOW TABLES;
SELECT COUNT(*) FROM config_info;
SELECT COUNT(*) FROM tenant_info;

Das Datenbankkonto erhält nur die Rechte, die das Nacos-Schema benötigt; in Anwendungs-Pods sollte kein MySQL root verwendet werden.

Schritt 2: Authentifizierungsmaterial und Secret erzeugen

Der Nacos-Authentifizierungstoken wird aus einem Zufallswert von mindestens 32 Byte erzeugt und anschließend Base64-kodiert. Die folgenden Befehle speichern die Ergebnisse nur in Variablen der aktuellen Shell:

NACOS_RAW_TOKEN="$(openssl rand -hex 32)"
NACOS_AUTH_TOKEN="$(printf '%s' "$NACOS_RAW_TOKEN" | base64)"

kubectl -n nacos-system create secret generic nacos-secret \
  --from-literal=mysql-host='<mysql-host>' \
  --from-literal=mysql-port='<mysql-port>' \
  --from-literal=mysql-database='<mysql-database>' \
  --from-literal=mysql-username='<mysql-username>' \
  --from-literal=mysql-password='<mysql-password>' \
  --from-literal=auth-token="$NACOS_AUTH_TOKEN" \
  --from-literal=identity-key='serverIdentity' \
  --from-literal=identity-value='<random-identity-value>'

unset NACOS_RAW_TOKEN NACOS_AUTH_TOKEN

Das Secret darf nicht in Git eingecheckt werden. Ins Repository gehören eine ExternalSecret- oder SealedSecret-Vorlage oder eine Erstellungsanleitung ohne Werte.

Schritt 3: Die beiden Services erstellen

Als 00-services.yaml speichern:

apiVersion: v1
kind: Service
metadata:
  name: nacos-headless
  namespace: nacos-system
spec:
  clusterIP: None
  publishNotReadyAddresses: true
  selector:
    app.kubernetes.io/name: nacos
  ports:
    - name: http
      port: 8848
    - name: grpc-client
      port: 9848
    - name: grpc-server
      port: 9849
    - name: raft
      port: 7848
---
apiVersion: v1
kind: Service
metadata:
  name: nacos-client
  namespace: nacos-system
spec:
  selector:
    app.kubernetes.io/name: nacos
  ports:
    - name: http
      port: 8848
      targetPort: http
    - name: grpc-client
      port: 9848
      targetPort: grpc-client
    - name: console
      port: 8080
      targetPort: console

Die Anwendungsadresse lautet:

nacos-client.nacos-system.svc.cluster.local:8848

Erstellen und prüfen:

kubectl apply -f 00-services.yaml
kubectl -n nacos-system get service

nacos-headless sollte eine ClusterIP von None anzeigen, nacos-client eine normale ClusterIP erhalten.

Schritt 4: StatefulSet mit drei Knoten erstellen

Als 01-statefulset.yaml speichern. Im Folgenden ist die Kernstruktur dargestellt; die Namen der Umgebungsvariablen müssen erneut gegen das gepinnte Ziel-Image geprüft werden:

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: nacos
  namespace: nacos-system
spec:
  serviceName: nacos-headless
  replicas: 3
  podManagementPolicy: Parallel
  updateStrategy:
    type: RollingUpdate
  selector:
    matchLabels:
      app.kubernetes.io/name: nacos
  template:
    metadata:
      labels:
        app.kubernetes.io/name: nacos
    spec:
      terminationGracePeriodSeconds: 60
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchLabels:
                  app.kubernetes.io/name: nacos
              topologyKey: kubernetes.io/hostname
      containers:
        - name: nacos
          image: <image-registry>/nacos-server:<approved-version>@sha256:<digest>
          imagePullPolicy: IfNotPresent
          ports:
            - { name: http, containerPort: 8848 }
            - { name: grpc-client, containerPort: 9848 }
            - { name: grpc-server, containerPort: 9849 }
            - { name: raft, containerPort: 7848 }
            - { name: console, containerPort: 8080 }
          env:
            - { name: MODE, value: cluster }
            - { name: PREFER_HOST_MODE, value: hostname }
            - {
                name: NACOS_SERVERS,
                value: "nacos-0.nacos-headless.nacos-system.svc.cluster.local:8848 nacos-1.nacos-headless.nacos-system.svc.cluster.local:8848 nacos-2.nacos-headless.nacos-system.svc.cluster.local:8848",
              }
            - { name: SPRING_DATASOURCE_PLATFORM, value: mysql }
            - name: MYSQL_SERVICE_HOST
              valueFrom:
                { secretKeyRef: { name: nacos-secret, key: mysql-host } }
            - name: MYSQL_SERVICE_PORT
              valueFrom:
                { secretKeyRef: { name: nacos-secret, key: mysql-port } }
            - name: MYSQL_SERVICE_DB_NAME
              valueFrom:
                { secretKeyRef: { name: nacos-secret, key: mysql-database } }
            - name: MYSQL_SERVICE_USER
              valueFrom:
                { secretKeyRef: { name: nacos-secret, key: mysql-username } }
            - name: MYSQL_SERVICE_PASSWORD
              valueFrom:
                { secretKeyRef: { name: nacos-secret, key: mysql-password } }
            - { name: NACOS_AUTH_ENABLE, value: "true" }
            - name: NACOS_AUTH_TOKEN
              valueFrom:
                { secretKeyRef: { name: nacos-secret, key: auth-token } }
            - name: NACOS_AUTH_IDENTITY_KEY
              valueFrom:
                { secretKeyRef: { name: nacos-secret, key: identity-key } }
            - name: NACOS_AUTH_IDENTITY_VALUE
              valueFrom:
                { secretKeyRef: { name: nacos-secret, key: identity-value } }
          startupProbe:
            httpGet: { path: /nacos/v1/console/health/started, port: http }
            periodSeconds: 10
            timeoutSeconds: 5
            failureThreshold: 30
          readinessProbe:
            httpGet: { path: /nacos/v1/console/health/readiness, port: http }
            periodSeconds: 10
            timeoutSeconds: 5
            failureThreshold: 6
          livenessProbe:
            httpGet: { path: /nacos/v1/console/health/liveness, port: http }
            periodSeconds: 20
            timeoutSeconds: 5
            failureThreshold: 6
          resources:
            requests: { cpu: "1", memory: 2Gi }
            limits: { cpu: "2", memory: 4Gi }

Die Probe-Pfade können je nach Zielversion variieren. Zuerst mit dem Ziel-Image in der Testumgebung per curl verifizieren, bevor sie in das Produktionsmanifest übernommen werden.

Das StatefulSet erstellen:

kubectl apply --server-side --dry-run=server -f 01-statefulset.yaml
kubectl apply -f 01-statefulset.yaml
kubectl -n nacos-system rollout status statefulset/nacos --timeout=15m
kubectl -n nacos-system get pods -o wide

Die drei Pods sollten auf drei verschiedenen Knoten verteilt sein. Ist ein Pod Pending, zuerst die Events ansehen:

kubectl -n nacos-system describe pod nacos-2

Verfügt der Cluster nur über zwei geeignete Knoten, verhindert die required-Anti-Affinity die Planung des dritten Pods. Das ist ein Kapazitätsplanungsproblem und sollte nicht durch Entfernen der Anti-Affinity kaschiert werden.

Schritt 5: Node-Discovery, Datenbank und Service verifizieren

Die Logs einzeln ansehen:

for pod in nacos-0 nacos-1 nacos-2; do
  echo "===== ${pod} ====="
  kubectl -n nacos-system logs "$pod" --tail=100
done

DNS prüfen:

kubectl -n nacos-system exec nacos-0 -- \
  getent hosts nacos-1.nacos-headless.nacos-system.svc.cluster.local

Service-Endpoints prüfen:

kubectl -n nacos-system get endpointslice \
  -l kubernetes.io/service-name=nacos-client -o wide

Das EndpointSlice sollte drei Ready-Adressen enthalten. Abschließend den Client-Service von einem temporären Pod aus aufrufen:

kubectl -n nacos-system run nacos-smoke --rm -it --restart=Never \
  --image=<approved-curl-image> -- \
  curl -fsS http://nacos-client:8848/nacos/v1/console/health/readiness

Schritt 6: Die erste Anwendung anbinden

Zuerst eine nicht-kritische Anwendung auswählen; nicht alle Namespaces auf einmal umstellen:

spring.cloud.nacos.server-addr=nacos-client.nacos-system.svc.cluster.local:8848
spring.cloud.nacos.username=${NACOS_USERNAME}
spring.cloud.nacos.password=${NACOS_PASSWORD}

Nach dem Deployment beides prüfen:

kubectl -n <app-namespace> rollout status deployment/<app> --timeout=10m
kubectl -n <app-namespace> logs deployment/<app> --since=10m \
  | grep -Ei 'nacos|register|error|exception'

Anschließend die Instanzen über die Nacos-Konsole oder API prüfen – nicht nur, ob der Anwendungs-Pod Running ist.

Abnahmekriterien

Der Nacos-Cluster ist erst dann fertig aufgesetzt, wenn alle folgenden Bedingungen erfüllt sind:

  • Die drei Nacos-Pods liegen auf drei verschiedenen Knoten.
  • Jeder Pod kann die Headless-DNS der beiden anderen Pods auflösen.
  • nacos-client hat drei Ready-Endpoints.
  • Veröffentlichung, Lesen und historische Versionen von Konfigurationen funktionieren einwandfrei.
  • Eine Testanwendung kann sich registrieren, einen anderen Service entdecken und aufrufen.
  • Nach dem Löschen eines beliebigen Nacos-Pods können Anwendungen weiterhin Konfigurationen lesen und Services entdecken.
  • Für MySQL und die Nacos-Konfiguration existieren jeweils unabhängige Backup- und Wiederherstellungsschritte.

Das offizielle Quick-Start-Dokument weist ausdrücklich darauf hin, dass sein Standardmanifest nur für Tests geeignet ist. In der Produktion sollte man Authentifizierung aktivieren, eine zuverlässige Datenbank- und Persistenzlösung verwenden und den Betrieb in ein isoliertes internes Netzwerk verlegen. Siehe Nacos Kubernetes Quick Start und Nacos-Bereitstellung im Cluster-Modus.
