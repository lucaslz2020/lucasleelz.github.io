Kubernetes Node-Pools planen: Labels, Taints, Affinität und Anti-Affinität in der Praxis

Von einem Server-Inventar ausgehend werden nach und nach Ingress-, Plattform-, Business-, Daten-, Observability-, Shared- und Reserve-Node-Pools gebildet; Labels, Taints, Tolerations und Affinität setzen die Scheduling-Strategie um.

#Kubernetes #Scheduling #Node-Pools #Taint #Affinity

Node-Pools sind kein Konzept, das nur Cloud-Anbieter kennen. Selbst wenn alle Nodes von einer lokalen Virtualisierungsplattform stammen, sollten verschiedene Fehlerdomänen über Labels, Taints und Affinität getrennt werden.

Seriennavigation: Kubernetes-Neuaufbau-Migrationsreihe. Dieser Beitrag setzt voraus, dass die Basis-Komponenten die Abnahme bestanden haben.

Dieser Artikel geht von einem Node-Inventar aus und setzt die Planung in konkrete Kubernetes-Scheduling-Regeln um.

Schritt 1: Zuerst nach Verantwortlichkeit in Pools aufteilen

Ein sinnvoller Ausgangspunkt ist:

Node-PoolTypische WorkloadsExklusiv?
control-planeAPI Server, etcdJa
ingressIngress Controller, Layer-4-IngressJa
platformNacos, DevOps, KernplattformJe nach Kapazität
app-*Workloads der jeweiligen UmgebungFür Produktion empfohlen
dataMySQL, Redis, Kafka, RabbitMQ, ZooKeeperJa
observabilityPrometheus, Logging, TracingEmpfohlen
sharedKleine zustandslose ServicesNein
reserveReserviert für Ausfälle und Rolling-UpgradesKeine regulären Workloads

Weisen Sie zuerst jedem Node einen Hauptpool zu; dieselbe Maschine darf nicht gleichzeitig in zwei exklusiven Pools stehen.

Schritt 2: Den Plan als CSV festhalten und validieren

hostname,pool,cpu,memory_gib,disk_type,failure_domain
worker-a,app-test,8,32,ssd,host-a
worker-b,app-test,8,32,ssd,host-b
worker-c,app-test,8,32,ssd,host-c

Doppelte Einträge prüfen:

cut -d, -f1 inventory/node-pools.csv | tail -n +2 | sort | uniq -d

Node-Anzahl je Pool prüfen:

cut -d, -f2 inventory/node-pools.csv | tail -n +2 | sort | uniq -c

Bei der Planung von drei Replikaten für Hochverfügbarkeit müssen zwei Ebenen gleichzeitig berücksichtigt werden: die Kubernetes-Nodes und die virtuellen Hostmaschinen. Wenn die drei Pods zwar auf drei virtuellen Maschinen laufen, diese aber auf derselben physischen Hostmaschine liegen, bleibt es ein Single Point of Failure.

Schritt 3: Zuerst deskriptive Labels setzen

Labels beschreiben, was ein Node ist, und bewirken keine Ausschließung:

kubectl label node worker-a workload.yj/pool=app-test
kubectl label node worker-a topology.yj/failure-domain=host-a
kubectl label node worker-a hardware.yj/disk=ssd

Nach dem Batch-Vorgang prüfen:

kubectl get nodes -L workload.yj/pool,topology.yj/failure-domain,hardware.yj/disk

Eigene Labels sollten ein eigenes DNS-Präfix verwenden, um Konflikte mit von Kubernetes reservierten Labels zu vermeiden.

Schritt 4: Dann entscheiden, welche Pools Taints benötigen

Ein Taint bedeutet „wer hier nicht standardmäßig hereindarf“. Für den exklusiven Datenpool kann Folgendes hinzugefügt werden:

kubectl taint node data-a workload.yj/pool=data:NoSchedule
kubectl taint node data-b workload.yj/pool=data:NoSchedule
kubectl taint node data-c workload.yj/pool=data:NoSchedule

Prüfen:

kubectl describe node data-a | sed -n '/Taints:/,/Unschedulable:/p'

Fügen Sie nicht erst dutzenden Nodes Taints hinzu und ändern Sie danach das Deployment. Die richtige Reihenfolge ist:

准备应用 toleration 和 nodeAffinity
→ server-side dry-run
→ 给第一台节点加污点
→ 验证调度
→ 批量推广

Schritt 5: Die Anwendung deklariert Toleration und Ziel-Node gleichzeitig

Nur eine Toleration zu konfigurieren bedeutet „Eintritt erlaubt“, garantiert aber nicht, dass der Pod im Datenpool landet. nodeAffinity sollte daher gleich mitverwendet werden:

spec:
  template:
    spec:
      tolerations:
        - key: workload.yj/pool
          operator: Equal
          value: data
          effect: NoSchedule
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
              - matchExpressions:
                  - key: workload.yj/pool
                    operator: In
                    values: [data]

Zuerst einen Dry-Run durchführen:

kubectl apply --server-side --dry-run=server -f workload.yaml

Schritt 6: Stateful-Replikate verteilen

Kafka-, RabbitMQ-, ZooKeeper- und MySQL-Replikate dürfen nicht auf demselben Node landen. Pod-Anti-Affinität verwenden:

affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app.kubernetes.io/name: zookeeper
        topologyKey: kubernetes.io/hostname

Soll die Verteilung zusätzlich über virtuelle Hostmaschinen hinweg erfolgen, kann das eigene Fehlerdomänen-Label verwendet werden:

topologyKey: topology.yj/failure-domain

Wenn nicht genügend Nodes vorhanden sind, hält required den Pod im Zustand Pending. Das ist ehrlicher, als alle drei Replikate auf denselben Node zu pressen: Die Nodes sollten erweitert oder die Kapazitätsplanung angepasst werden, statt die Fehlerdomäne stillschweigend aufzuweichen.

Schritt 7: Kapazität für Rolling-Upgrades reservieren

Angenommen, ein Service hat zwei Pods, jeder mit einem Request von 2 Kernen und 6 GiB. Beim Rolling-Upgrade mit dem Standardwert maxSurge: 25% wird mindestens temporär Platz für einen dritten Pod benötigt.

Verfügbare Ressourcen müssen über die Requests berechnet werden, nicht über die tatsächliche momentane Auslastung:

kubectl describe node <node> | sed -n '/Allocated resources:/,$p'
kubectl top node <node>

Die beiden Befehle dienen unterschiedlichen Zwecken:

  • Die Allocated resources aus describe sind die Requests/Limits, die der Scheduler bereits zugesagt hat.
  • top zeigt die aktuelle tatsächliche Auslastung.

Niedrig priorisierte Workloads sollten den Reservepool nicht dauerhaft belegen, sonst bleiben sowohl die Fehlermigration als auch Rolling Releases stecken.

Schritt 8: Das Scheduling-Ergebnis verifizieren

Nach dem Deployment ausführen:

kubectl get pods -A -o custom-columns='NS:.metadata.namespace,POD:.metadata.name,NODE:.spec.nodeName' \
  | sort

kubectl get pods -n <namespace> -l app.kubernetes.io/name=<app> -o wide
kubectl get events -A --field-selector reason=FailedScheduling --sort-by=.lastTimestamp

Wichtige Prüfpunkte:

  • Ob in den exklusiven Pools fremde Pods gelandet sind.
  • Ob die drei Replikate auf verschiedenen Nodes und Fehlerdomänen liegen.
  • Ob DaemonSets wegen fehlender Tolerationen nicht auf getaintete Nodes geplant werden können.
  • Ob die Reserve-Nodes weiterhin frei sind.
  • Ob kleine Nodes schwere Services tragen, für die sie nicht geeignet sind.

Praxis-Rückblick: Wie 0/69 nodes are available zu lesen ist

Beim Release eines Dienstes mit zwei Replikaten meldeten die Events wiederholt:

0/69 nodes are available:
several nodes had untolerated taint,
some nodes didn't match Pod's node affinity/selector,
some nodes had insufficient memory

Das bedeutet nicht, dass auf allen 69 Maschinen der Speicher knapp ist. Der Scheduler filtert der Reihe nach:

flowchart LR
  A["69 Nodes"] --> B["Taint / Toleration"]
  B --> C["nodeSelector / nodeAffinity"]
  C --> D["CPU / Memory request"]
  D --> E["Topology spread / anti-affinity"]
  E --> F["Schedulable Nodes"]

Zuerst die Constraints des Pods vollständig ausgeben:

kubectl -n <namespace> get pod <pending-pod> -o jsonpath='
nodeSelector={.spec.nodeSelector}{"\n"}
affinity={.spec.affinity}{"\n"}
tolerations={.spec.tolerations}{"\n"}
requests={.spec.containers[*].resources.requests}{"\n"}
spread={.spec.topologySpreadConstraints}{"\n"}'

Dann die Kandidaten-Nodes Ebene für Ebene prüfen:

kubectl get node --show-labels
kubectl describe node <candidate-node>
kubectl get events -n <namespace> \
  --field-selector reason=FailedScheduling \
  --sort-by=.lastTimestamp

Warum der dritte Pod Speichermangel meldet, obwohl die beiden Pods tatsächlich nur 2G verbrauchen

Der Scheduler bewertet nicht, wie viel die beiden vorhandenen Pods aktuell zusammen verbrauchen, sondern vergleicht den memory request des neuen Pods mit der noch nicht zugesagten allocatable Kapazität des Nodes:

可调度
⇔ node allocatable
  - 已调度 Pod requests
  ≥ incoming Pod request

Wenn jeder Pod einen Request von 3.5 GiB hat, muss der Surge-Pod der neuen Revision die vollen 3.5 GiB anfordern, selbst wenn die beiden vorhandenen Instanzen aktuell jeweils nur etwa 1 GiB nutzen.

Genau deshalb wurden die Services im Ressourcen-Governance später in normale, datenspeichernde und schwere Stufen eingeteilt: Requests müssen die Auslastung im stabilen Zustand und erklärbare Spitzen abdecken, dürfen aber nicht mit einem einzigen zu großen generischen Wert alle dedizierten Nodes belegen.

Warum ein Pod einen scheinbar freien Node trotzdem nicht nutzen kann

„Auf dem Node laufen keine Workload-Pods“ bedeutet nicht, dass dieser Pod dort eingeplant werden kann. Mögliche Gründe:

  • Er trägt einen NoSchedule-Taint, den der aktuelle Pod nicht toleriert.
  • Ihm fehlen die Labels für einen erforderlichen nodeSelector.
  • Er gehört nicht zu einer eligible domain der Topology-Spread-Verteilung.
  • Seine Kapazität ist bereits durch Requests anderer Pods reserviert.
  • Er ist für Ausfälle oder Rolling-Upgrades reserviert.

Deshalb lässt sich aus der Node-Liste allein nicht ableiten, dass noch neun Server frei sind. Taints, Labels und allocated requests müssen gemeinsam ausgewertet werden.

Warum Volcano Engine manuell gelöschte Labels und Taints wiederherstellt

Die Konfiguration eines verwalteten Node-Pools ist der gewünschte Zustand der Control Plane. Wenn der Node-Pool weiterhin Folgendes deklariert:

app-type=<dedicated-service>
taint app-type=<dedicated-service>:NoSchedule

dann ändert das alleinige Ausführen von:

kubectl label node <node> app-type-
kubectl taint node <node> app-type-

möglicherweise nur vorübergehend das Kubernetes-Node-Objekt. Beim nächsten Sync stellt der Node-Pool-Controller diese Felder wieder her.

Dokumentation zu den VKE-Node-Pools von Volcano Engine hält ausdrücklich fest: Im Node-Pool neu hinzugefügte oder geänderte Labels und Taints werden automatisch auf neue und bestehende Nodes übertragen.

Um einen dedizierten Node dauerhaft in den gemeinsamen Pool zu überführen:

  1. Zuerst prüfen, dass der Node keine exklusiven Workloads und keine besondere Hardware-Rolle mehr übernimmt.
  2. Die Ziel-Labels und -Taints in der VKE-Node-Pool-Konfiguration löschen oder ändern.
  3. Warten, bis der Controller die Synchronisierung abgeschlossen hat.
  4. Danach das Kubernetes-Node-Objekt prüfen.
  5. Einen Pod mit geringem Risiko migrieren und das Scheduling im gemeinsamen Pool verifizieren.
  6. Sicherstellen, dass die Konfiguration nach Neustart, Skalierung oder Node-Ersatz nicht wiederhergestellt wird.

Wenn alle Mitglieder des ursprünglichen Node-Pools dieselbe Konfiguration teilen müssen, sollte eine einzelne Maschine nicht in diesem Pool bleiben; sie muss in einen gemeinsamen Node-Pool migriert werden oder es muss ein neuer Pool ohne dedizierte Taints angelegt werden.

Praxis-Rückblick: Warum zwei Replikate weiterhin auf demselben Node liegen

Bei nur preferred node affinity oder ScheduleAnyway kann der Scheduler zwei Replikate wegen einer besseren Ressourcenbewertung auf denselben Node legen. Das ist legitimes Verhalten, schützt aber nicht vor einem Ausfall des einzelnen Nodes.

In einem Deployment unter Kubernetes 1.30 lässt sich die Verteilung anhand der aktuellen ReplicaSet-Revision erzwingen:

topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: DoNotSchedule
    matchLabelKeys:
      - pod-template-hash
    labelSelector:
      matchLabels:
        app: <application>
        version: <version>

matchLabelKeys: [pod-template-hash] sorgt dafür, dass das alte und das neue ReplicaSet getrennt berechnet werden. So blockiert die alte Revision bei einem Rolling Release mit maxUnavailable: 0 und maxSurge: 1 die neue Revision nicht, weil sie in die Skew-Berechnung einbezogen wird.

Die Kubernetes-Dokumentation zu Topology Spread Constraints führt pod-template-hash ebenfalls als typisches Beispiel für die Verteilung nach Deployment-Revision an.

Vor dem Erzwingen der Verteilung muss sichergestellt sein:

  • Mindestens zwei Nodes erfüllen gleichzeitig nodeSelector/affinity.
  • Beide Nodes tolerieren die Taints des Pods.
  • Jeder Node kann den Request eines Replikats aufnehmen.
  • Während des Releases ist weiterhin Platz für den Surge-Pod vorhanden.

Wenn nur ein geeigneter Node existiert, hält DoNotSchedule den zweiten Pod im Zustand Pending. Das ist unter Fehlerdomänen-Constraints das normale Ergebnis; die Spread-Regel sollte nicht gelöscht werden, um die gemeinsame Platzierung heimlich wiederherzustellen.

Sicher zurückbauen

Taint entfernen:

kubectl taint node data-a workload.yj/pool=data:NoSchedule-

Label entfernen:

kubectl label node data-a workload.yj/pool-

Vor dem Zurückbauen zuerst den Workload anpassen, damit er nicht weiterhin ein Label verlangt, das es nicht mehr gibt.

Definition of Done

  • Jeder Node hat genau einen klar definierten Hauptpool.
  • Exklusive Pools sind sowohl mit Labels als auch mit Taints konfiguriert.
  • Die Workload-Manifeste konfigurieren sowohl Toleration als auch nodeAffinity.
  • Drei stateful Replikate sind über Nodes verteilt, kritische Services zusätzlich über physische Fehlerdomänen.
  • Beim Rolling-Upgrade kann mindestens ein Surge-Pod aufgenommen werden.
  • DaemonSets wie Monitoring, CNI und CSI sind verifiziert und tolerieren die erforderlichen Taints.
  • Reserve-Nodes werden nicht dauerhaft von regulären Workloads belegt.
  • Labels und Taints von verwalteten Node-Pools und Kubernetes-Nodes stimmen überein.
  • FailedScheduling wurde nach Taints, Affinität, Request und Spread schichtweise erklärt.
  • Zwei Replikate werden per revision-aware topology spread zwingend auf verschiedene Nodes verteilt.
