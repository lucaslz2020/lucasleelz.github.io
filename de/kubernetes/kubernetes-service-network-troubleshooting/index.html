Kubernetes-Service-Zugriffsfehler: Fehlersuche von DNS bis kube-proxy

Connection refused, No route to host, Timeout oder Nacos ohne verfügbare Instanzen? Ebene für Ebene: DNS, Service, Endpoint, Pod, CNI, kube-proxy, Firewall.

lucaslzAutor
28. Juni 2026 6 Min. Lesezeit
#Kubernetes #Service #kube-proxy #Calico #Fehlerbehebung
{ }

Ein typischer Fehler bei der Migration von Geschäftsanwendungen ist die Annahme: In den Anwendungsprotokollen steht Nacos, Redis oder Feign, also muss der Fehler bei Nacos, Redis oder im Code liegen. Tatsächlich liegt die Störung oft in der Service-Weiterleitung oder in der Netzwerkkommunikation zwischen den Knoten.

Seriennavigation: Kubernetes-Neuaufbau-Migrationsreihe. Dieser Beitrag eignet sich als eigenständiges Handbuch zur Fehlerbehebung für die Migrationsphase und den täglichen Bereitschaftsdienst.

Dieser Artikel beschreibt einen festen Weg zur Fehlersuche: Bei einer Störung arbeitest du ihn von oben nach unten ab, statt sofort alle Pods neu zu starten.

Zuerst nach Fehlerart eingrenzen

FehlerTypische Bedeutung
UnknownHostExceptionDNS-Name existiert nicht oder CoreDNS ist nicht verfügbar
Connection refusedDer Zielhost wurde erreicht, aber auf dem Port lauscht kein Dienst oder es wird an den falschen Port weitergeleitet
Connect timed outRouting, Firewall, NetworkPolicy oder das Ziel antworten nicht
No route to hostKnotenübergreifendes Routing, Firewall oder CNI-Adressbereich nicht erreichbar
Load balancer does not have available serverRegistry enthält keine gesunden Instanzen oder der Client hat nicht korrekt abonniert
HTTP 404Anfrage hat einen HTTP-Dienst erreicht, aber Host, Path oder Gateway-Route passen nicht

Fehler sind Hinweise, keine Schlussfolgerungen.

Ebene 1: Ermitteln, welche Adresse der Client tatsächlich verwendet

Wechsle in den fehlerhaften Pod und prüfe Umgebungsvariablen sowie die wirksame Konfiguration:

kubectl -n <namespace> exec <client-pod> -- env \
  | grep -Ei 'nacos|redis|gateway|service'

Stammt die Konfiguration aus Nacos, lies zusätzlich die zugehörige Data ID zurück. Verlass dich nicht nur auf die Konfiguration in Git: Zur Laufzeit kann sie durch Umgebungsvariablen, Startargumente oder eine Remote-Konfiguration überschrieben werden.

Ebene 2: DNS verifizieren

kubectl -n <namespace> exec <client-pod> -- \
  getent hosts <service>.<namespace>.svc.cluster.local

Enthält das Image keine Debug-Werkzeuge, starte einen temporären Diagnose-Pod:

kubectl -n <namespace> run net-debug --rm -it --restart=Never \
  --image=<approved-network-tool-image> -- sh

Prüfe bei DNS-Fehlern:

kubectl -n kube-system get deployment,pod -l k8s-app=kube-dns -o wide
kubectl -n kube-system logs deployment/coredns --tail=200
kubectl -n <namespace> get networkpolicy

Ebene 3: Die Service-Definition prüfen

kubectl -n <target-namespace> get service <service> -o yaml

Zu prüfen:

  • ob der selector mit den Labels der Ziel-Pods übereinstimmt.
  • port ist der Port, über den der Client zugreift.
  • ob targetPort auf den tatsächlich lauschenden Port des Containers oder auf den korrekten benannten Port zeigt.
  • ob versehentlich eine alte ClusterIP verwendet wird.

Vergleiche die Labels direkt:

kubectl -n <target-namespace> get pods --show-labels
kubectl -n <target-namespace> get pods -l '<service-selector>' -o wide

Ebene 4: EndpointSlice prüfen

kubectl -n <target-namespace> get endpointslice \
  -l kubernetes.io/service-name=<service> -o yaml

Sind keine Adressen vorhanden, liegt das Problem meist an einem nicht passenden selector oder an Pods, die nicht Ready sind. Sind Adressen vorhanden, aber conditions.ready: false gesetzt, prüfe die Readiness-Probe.

Notiere IP und Port eines Ready-Pods; anschließend testest du sowohl die direkte Verbindung zum Pod als auch den Weg über den Service.

Ebene 5: Pod-IP direkt verbinden

Führe den Befehl vom Client-Pod aus:

kubectl -n <namespace> exec <client-pod> -- \
  nc -vz <target-pod-ip> <target-port>

So interpretierst du das Ergebnis:

  • Pod-IP nicht erreichbar: zuerst CNI, Knoten-Routing, Firewall und NetworkPolicy prüfen.
  • Pod-IP erreichbar, ClusterIP nicht: zuerst kube-proxy oder die Service-Regeln prüfen.
  • Beides erreichbar: Anwendungsprotokoll, Authentifizierung, Gateway oder die Nacos-Registrierungsdaten weiter prüfen.

Ebene 6: Den Test auf verschiedenen Knoten wiederholen

Service-Fehler können nur auf einzelnen Knoten auftreten. Zeige an, auf welchem Knoten der Client läuft:

kubectl -n <namespace> get pod <client-pod> -o wide

Starte auf dem fehlerhaften und auf einem gesunden Knoten jeweils einen temporären Pod und greife von beiden auf dieselbe ClusterIP zu. Schlägt nur ein Knoten fehl, ist das Problem bereits auf dessen kube-proxy, CNI, iptables/nftables oder Firewall eingegrenzt.

Ebene 7: kube-proxy prüfen

kubectl -n kube-system get pods -l k8s-app=kube-proxy -o wide
kubectl -n kube-system logs <kube-proxy-pod-on-bad-node> --tail=200

Vergleiche die ConfigMap mit dem laufenden Modus:

kubectl -n kube-system get configmap kube-proxy -o yaml

Starte nur den kube-proxy des fehlerhaften Knotens neu:

kubectl -n kube-system delete pod <kube-proxy-pod-on-bad-node>
kubectl -n kube-system get pod -l k8s-app=kube-proxy -o wide -w

Das Löschen des DaemonSet-Pods veranlasst den Controller, ihn automatisch neu zu erstellen. Ohne Belege solltest du nicht den kube-proxy aller Knoten gleichzeitig löschen.

Ebene 8: Knoten-Routing und Firewall prüfen

Logge dich auf dem fehlerhaften Knoten ein:

ip route
sudo firewall-cmd --get-active-zones
sudo firewall-cmd --zone=trusted --list-sources
sudo sysctl net.ipv4.ip_forward

Das Pod-CIDR muss korrekt geroutet oder in die trusted Zone aufgenommen sein, net.ipv4.ip_forward muss 1 sein.

Prüfe in Calico-Umgebungen weiter:

kubectl -n kube-system get pod -l k8s-app=calico-node -o wide
kubectl -n kube-system logs <calico-pod-on-bad-node> -c calico-node --tail=200

Ebene 9: Zuletzt Nacos und die Anwendung prüfen

Sind alle Netzwerkebenen in Ordnung, meldet der Client aber weiterhin, dass kein Dienst verfügbar ist, prüfe in Nacos Folgendes:

  • ob namespace, group und cluster übereinstimmen.
  • ob Groß-/Kleinschreibung und Präfix des Servicenamens übereinstimmen.
  • ob die Instanz-IP weiterhin die Pod-IP des alten Clusters ist.
  • ob Health-Status und ephemeral-Status der Instanz stimmen.
  • ob der Client fälschlich den Dual-Write- oder den Kompatibilitätsmodus aktiviert hat.

Der Zugriff auf den Health-Check-Endpunkt der Abhängigkeit aus dem Ziel-Pod heraus ist aussagekräftiger als von einem Betriebsrechner.

Mit Kontrollexperimenten Fehleinschätzungen vermeiden

Die effektivste Tabelle für die Fehlersuche:

TestpositionPod-IPClusterIPService-DNSErgebnis
Pod auf fehlerhaftem Knoten<pod-ip><service-ip><service-fqdn>notieren
Pod auf gesundem Knoten<pod-ip><service-ip><service-fqdn>notieren
Ziel-Pod lokallocalhostnicht zutreffendnicht zutreffendnotieren

Diese Tabelle macht schnell deutlich, ob das Problem am Anwendungsport, am knotenübergreifenden CNI oder an der Service-Weiterleitung liegt.

Abnahme nach der Behebung

kubectl -n <namespace> exec <client-pod> -- \
  curl -fsS http://<service>.<target-namespace>.svc.cluster.local:<port>/<health-path>

kubectl -n <namespace> logs <client-pod> --since=10m \
  | grep -Ei 'refused|timed out|no route|available server'

Führe zusätzlich eine echte Geschäftsanfrage aus. Dass die Netzwerkbefehle wieder normal laufen, ist nur der erste Beleg; am Ende musst du die realen Pfade über Gateway, Login, Abfragen oder Message-Consumption verifizieren.

Abschließender Grundsatz

DNS → Service → EndpointSlice → Pod 端口 → 跨节点网络 → kube-proxy → 防火墙 → 注册中心 → 业务

Der Wert eines festen Vorgehens liegt darin, dass jeder Schritt eine ganze Ebene ausschließen kann. Alle Pods neu zu starten lässt die Symptome zwar vorübergehend verschwinden, findet die Ursache aber nicht und verhindert auch nicht, dass der Fehler bei der nächsten Verschiebung von Pods erneut auftritt.
