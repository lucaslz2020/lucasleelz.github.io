Nexus Repository 3 von Grund auf in Kubernetes deployen: PostgreSQL, PVC und Ingress

Nexus Repository 3 Schritt für Schritt in Kubernetes deployen: vom Namespace über PostgreSQL bis zum Ingress – persistent, backup- und upgradefähig.

lucaslzAutor
11. Juli 2026 7 Min. Lesezeit
#Nexus #Kubernetes #PostgreSQL #StatefulSet #Maven
{ }

Dieser Beitrag behandelt ausschließlich die Neuinstallation von Nexus Repository 3 – die Datenmigration von Nexus 2 ist nicht enthalten. Wenn du zuerst eine saubere Nexus-3-Installation stabil zum Laufen bringst, wird die Fehlersuche im anschließenden Migrationsartikel deutlich einfacher.

Seriennavigation: Kubernetes-Neuaufbau-Migrationsreihe. Dieser Beitrag ist die Voraussetzung für die Nexus-Migration.

Das Beispiel verwendet ein Single-Instance-StatefulSet, eine externe PostgreSQL-Datenbank und ein Persistent Volume. Ein hochverfügbares Multi-Instance-Setup betrifft Lizenzierung und die offizielle HA-Architektur – replicas einfach von 1 auf 3 zu erhöhen funktioniert nicht.

Zielstruktur

Das offizielle Nexus-Containerimage speichert Konfiguration, Logs und Artefakt-Daten unter /nexus-data; der Containerprozess läuft mit UID 200. Das Verzeichnis muss persistent und beschreibbar sein. Siehe die offizielle Containerimage-Dokumentation.

Schritt 1: Version, Kapazität und Kontextpfad festlegen

Friere zuerst die folgenden Werte ein:

NEXUS_VERSION=<approved-version>
NEXUS_IMAGE=<image-registry>/sonatype/nexus3:${NEXUS_VERSION}
NEXUS_HOST=repo.example.com
NEXUS_CONTEXT=/nexus

Verwende nicht latest. Synchronisiere das Image in die interne Registry und notiere den Digest:

crane digest "$NEXUS_IMAGE"

Bei der Kapazität solltest du mindestens berücksichtigen:

  • Das aktuelle Gesamtvolumen der gehosteten Artefakte.
  • Das Limit und die Cleanup-Policy des Proxy-Caches.
  • Temporärer Speicher für Datenbank, Logs und Tasks.
  • Die Aufbewahrungsdauer der Backups.
  • Das zu erwartende Wachstum der nächsten ein bis zwei Jahre.

Schritt 2: Namespace und PostgreSQL-Datenbank anlegen

kubectl create namespace repository-system

PostgreSQL sollte idealerweise von einer separaten Datenbankplattform bereitgestellt und gesichert werden. Lege einen dedizierten Account und eine Datenbank an:

CREATE ROLE nexus LOGIN PASSWORD '<generated-password>';
CREATE DATABASE nexus OWNER nexus ENCODING 'UTF8';

Verifiziere, dass der Nexus-Knoten die Datenbank erreichen kann:

kubectl -n repository-system run pg-check --rm -it --restart=Never \
  --image=<approved-postgres-client-image> -- \
  psql 'postgresql://nexus:<password>@<postgres-host>:5432/nexus' \
  -c 'select current_database(), current_user;'

Das Passwort darf nicht in der Shell-History auftauchen. In der Produktion nutzt du interaktive Eingabe, temporäre Umgebungsvariablen oder ein Secret-Management-System.

Schritt 3: Datenbank-Secret anlegen

kubectl -n repository-system create secret generic nexus-database \
  --from-literal=jdbc-url='jdbc:postgresql://<postgres-host>:5432/nexus' \
  --from-literal=username='nexus' \
  --from-literal=password='<generated-password>'

Offiziell lässt sich PostgreSQL über Umgebungsvariablen, JVM-Parameter oder eine Properties-Datei konfigurieren; eine Mischung wird jedoch nicht empfohlen. In Container-Umgebungen sind Umgebungsvariablen am klarsten. Siehe Nexus Repository mit PostgreSQL installieren.

Schritt 4: PVC anlegen

Speichere sie als 00-storage.yaml:

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: nexus-data
  namespace: repository-system
spec:
  storageClassName: <storage-class>
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: <planned-size>

Wende sie an und prüfe den Bindungsstatus:

kubectl apply -f 00-storage.yaml
kubectl -n repository-system get pvc nexus-data -w

Die PVC muss den Status Bound anzeigen. Bei statischen lokalen Volumes musst du dem Nexus-Pod zusätzlich eine nodeAffinity geben und die Wiederherstellung nach Knotenausfällen im Runbook dokumentieren.

Schritt 5: Service anlegen

Speichere ihn als 01-service.yaml:

apiVersion: v1
kind: Service
metadata:
  name: nexus
  namespace: repository-system
spec:
  selector:
    app.kubernetes.io/name: nexus
  ports:
    - name: http
      port: 8081
      targetPort: http
kubectl apply -f 01-service.yaml

Wenn du später Docker-hosted-/group-Repositories eigene Ports zuweist, ergänze sie explizit im Service und in den Container-Ports und verwechsle sie nicht mit dem Management-Port.

Schritt 6: StatefulSet anlegen

Speichere es als 02-statefulset.yaml:

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: nexus
  namespace: repository-system
spec:
  serviceName: nexus
  replicas: 1
  selector:
    matchLabels:
      app.kubernetes.io/name: nexus
  template:
    metadata:
      labels:
        app.kubernetes.io/name: nexus
    spec:
      terminationGracePeriodSeconds: 120
      securityContext:
        fsGroup: 200
        fsGroupChangePolicy: OnRootMismatch
      containers:
        - name: nexus
          image: <image-registry>/sonatype/nexus3:<approved-version>@sha256:<digest>
          ports:
            - { name: http, containerPort: 8081 }
          env:
            - { name: NEXUS_CONTEXT, value: /nexus }
            - name: NEXUS_DATASTORE_NEXUS_JDBCURL
              valueFrom:
                { secretKeyRef: { name: nexus-database, key: jdbc-url } }
            - name: NEXUS_DATASTORE_NEXUS_USERNAME
              valueFrom:
                { secretKeyRef: { name: nexus-database, key: username } }
            - name: NEXUS_DATASTORE_NEXUS_PASSWORD
              valueFrom:
                { secretKeyRef: { name: nexus-database, key: password } }
            - name: INSTALL4J_ADD_VM_PARAMS
              value: >-
                -Xms2g -Xmx2g -XX:MaxDirectMemorySize=2g
                -Djava.util.prefs.userRoot=/nexus-data/javaprefs
          resources:
            requests: { cpu: "2", memory: 4Gi }
            limits: { cpu: "4", memory: 6Gi }
          startupProbe:
            httpGet: { path: /nexus/service/rest/v1/status, port: http }
            periodSeconds: 10
            timeoutSeconds: 5
            failureThreshold: 60
          readinessProbe:
            httpGet: { path: /nexus/service/rest/v1/status, port: http }
            periodSeconds: 10
            timeoutSeconds: 5
            failureThreshold: 6
          livenessProbe:
            httpGet: { path: /nexus/service/rest/v1/status, port: http }
            periodSeconds: 30
            timeoutSeconds: 5
            failureThreshold: 6
          volumeMounts:
            - { name: data, mountPath: /nexus-data }
      volumes:
        - name: data
          persistentVolumeClaim: { claimName: nexus-data }

Die Ressourcen sind nur ein Ausgangspunkt: Passe sie erst nach Lasttests an, die Indexgröße, parallele Anfragen und die offiziellen Systemanforderungen berücksichtigen. Setze den JVM-Heap niemals direkt auf das Speicherlimit des Containers.

Vor dem Anwenden prüfen:

kubectl apply --server-side --dry-run=server -f 02-statefulset.yaml
kubectl apply -f 02-statefulset.yaml
kubectl -n repository-system rollout status statefulset/nexus --timeout=20m

Der erste Start kann einige Minuten dauern. Die startupProbe sollte die Datenbankinitialisierung und das Laden der Plugins abdecken; die readinessProbe darf den Traffic nicht zu früh freigeben.

Schritt 7: Startfehler beheben

kubectl -n repository-system get pod nexus-0 -o wide
kubectl -n repository-system describe pod nexus-0
kubectl -n repository-system logs nexus-0 --tail=300
kubectl -n repository-system get endpointslice \
  -l kubernetes.io/service-name=nexus -o wide

Häufige Ursachen:

  • Die PVC ist nicht gebunden, oder das Verzeichnis ist für UID 200 nicht beschreibbar.
  • PostgreSQL-Adresse, -Account oder TLS-Parameter sind falsch.
  • Der Probenpfad enthält den /nexus-Kontext nicht.
  • Der Container hat zu wenig Speicher und wird durch OOMKilled beendet.
  • Das Datenbankschema wurde von einer inkompatiblen Version initialisiert.

connection refused bedeutet, dass auf dem Port noch kein Prozess lauscht. Während des ersten Starts solltest du die Anwendungslogs prüfen, statt Pods wiederholt zu löschen.

Schritt 8: Initiales Admin-Passwort abrufen

kubectl -n repository-system exec nexus-0 -- \
  sh -c 'test -f /nexus-data/admin.password && cat /nexus-data/admin.password'

Nach dem ersten Login:

  1. Ändere das Admin-Passwort sofort und speichere es in einem Passwort-Manager.
  2. Lege ein persönliches Admin-Konto an, um das geteilte admin zu vermeiden.
  3. Entscheide anhand der Sicherheitsanforderungen, ob anonyme Downloads erlaubt sind.
  4. Konfiguriere E-Mail, Audit und Cleanup-Tasks.
  5. Bestätige, dass die Datei admin.password von Nexus gelöscht oder ungültig gemacht wurde.

Schreibe das Initialpasswort nicht in Wiki, Git oder Chatverlauf.

Schritt 9: Ingress anlegen

Speichere ihn als 03-ingress.yaml:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: nexus
  namespace: repository-system
  annotations:
    nginx.ingress.kubernetes.io/proxy-body-size: "0"
    nginx.ingress.kubernetes.io/proxy-read-timeout: "600"
    nginx.ingress.kubernetes.io/proxy-send-timeout: "600"
spec:
  ingressClassName: nginx
  tls:
    - hosts: [repo.example.com]
      secretName: repo-example-com-tls
  rules:
    - host: repo.example.com
      http:
        paths:
          - path: /nexus
            pathType: Prefix
            backend:
              service:
                name: nexus
                port: { number: 8081 }

Ändere die öffentlichen DNS-Einträge noch nicht und teste stattdessen mit --resolve:

curl -kfsS --resolve repo.example.com:443:<ingress-address> \
  https://repo.example.com/nexus/service/rest/v1/status

Erwartet wird ein Status, der die Verfügbarkeit bestätigt. Bevor du große Artefakte hochlädst, prüfe zusätzlich, dass weder Ingress, Load Balancer noch CDN die Request-Body-Größe begrenzen.

Schritt 10: Maven-Repository anlegen und verifizieren

Lege in der UI Folgendes an:

  • maven-releases: hosted, Version Policy Release.
  • maven-snapshots: hosted, Version Policy Snapshot.
  • maven-central: proxy, Remote-Repository ist Maven Central.
  • maven-public: group, enthält die oben genannten Repositories.

Adresse des Client-Repositories:

<repository>
  <id>nexus-public</id>
  <url>https://repo.example.com/nexus/repository/maven-public/</url>
</repository>

Adressen für das Publishing:

<distributionManagement>
  <repository>
    <id>nexus-releases</id>
    <url>https://repo.example.com/nexus/repository/maven-releases/</url>
  </repository>
  <snapshotRepository>
    <id>nexus-snapshots</id>
    <url>https://repo.example.com/nexus/repository/maven-snapshots/</url>
  </snapshotRepository>
</distributionManagement>

Die Zugangsdaten gehören in die settings.xml des Benutzers oder in CI-Secrets – nicht in das POM des Projekts.

Führe mit einem temporären Maven-Projekt aus:

mvn -U dependency:get -Dartifact=<group>:<artifact>:<version>
mvn deploy

Schritt 11: Backup- und Cleanup-Tasks konfigurieren

Das Backup muss alle drei Bereiche abdecken:

  • Ein konsistentes PostgreSQL-Backup.
  • Blobs, Konfiguration und Schlüsselmaterial unter /nexus-data.
  • Die Kubernetes-Manifeste und die Referenzen im Secret-Management-System.

Die Backup-Zeitpunkte von Datenbank und Blobs müssen aufeinander abgestimmt sein, sonst können Metadaten und Dateien inkonsistent werden. Für den Proxy-Cache kannst du Cleanup-Policies setzen; das Löschen gehosteter Artefakte braucht dagegen Aufbewahrungs- und Audit-Regeln.

Definition of Done

  • Das StatefulSet startet nach einem Neuaufbau mit derselben PVC wieder normal.
  • Für PostgreSQL und /nexus-data wurde jeweils eine Restore-Übung durchgeführt.
  • Service, Ingress, TLS und Kontextpfad stimmen überein.
  • Maven-Download sowie Release- und Snapshot-Publish sind erfolgreich.
  • Das Initialpasswort des Admins wurde rotiert; CI nutzt ein separates Konto mit minimalen Rechten.
  • Image-Version und Digest sind gepinnt; Upgrade- und Rollback-Schritte sind dokumentiert.

Erst nach der sauberen Neuinstallation geht es an die Datenmigration von Nexus 2 auf Nexus 3. Fasse „Plattform-Neuaufbau“ und „Import historischer Daten“ nicht zu einem einzigen Vorgang ohne Rollback-Möglichkeit zusammen.
