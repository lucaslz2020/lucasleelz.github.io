Nexus3 Kubernetes-Migrations-Runbook: H2, PostgreSQL, Probes und nahtloser Wechsel

Ein ausführbares Kubernetes-Runbook zur Nexus2→Nexus3-Migration: Ressourcen, Upgrade Wizard, H2-Upgrade, Database Migrator, Verifikation, VIP-Rollback.

lucaslzAutor
5. August 2026 7 Min. Lesezeit
#Nexus #Kubernetes #Runbook #PostgreSQL #StatefulSet
{ }

Dieser Artikel enthält nur die allgemeine Ausführungslogik. Adressen, Knoten, Domains, Kapazitäten und Secrets sind Platzhalter. Vor der Ausführung ist alles anhand der offiziellen Versionsmatrix und der eigenen Wiederherstellungsübungen erneut zu verifizieren.

Reihennavigation: Kubernetes-Neuaufbau-Migrationsreihe. Dieser Beitrag dient der schrittweisen Ausführung und Abnahme im offiziellen Migrationsfenster.

Der vorherige Beitrag hat das Gesamtdesign der Migration Nexus2 → Nexus3 → PostgreSQL beschrieben. Dieser Beitrag verdichtet die Migration zu einer ausführbaren Checkliste und beantwortet vor allem die Frage: Wann darf der nächste Schritt beginnen?

Eingefrorene Entscheidungen

Vor der Migration werden folgende Entscheidungen eingefroren:

  • Nexus2 ist auf die finale, offiziell unterstützte Version aktualisiert.
  • Nexus3 verwendet eine verifizierte Zwischenversion, um die Daten über den Upgrade Wizard zu übernehmen.
  • Nexus3 wird im H2-Modus auf die finale Zielversion aktualisiert.
  • Der Database Migrator entspricht exakt der Zielversion.
  • Die Java-Versionen von Nexus und Migrator erfüllen die Anforderungen der Zielversion.
  • Der Blob Store nutzt ein eigenes PersistentVolume mit der Reclaim Policy Retain.
  • PostgreSQL verwendet eine eigene Datenbank, eine eigene Rolle und ein eigenes Schema.
  • Der Kontextpfad /nexus bleibt unverändert.
  • Die alte Domain bzw. der alte VIP wird erst nach der finalen Verifikation umgeschaltet.

Nicht überspringbare Reihenfolge

Nexus2 最终版与完整备份
→ Nexus3 中转版 H2
→ Upgrade Wizard + Finalize
→ Nexus3 目标版 H2
→ H2 备份与 Blob Store 恢复点
→ 停止 Nexus
→ Database Migrator
→ PostgreSQL VACUUM
→ Nexus3 目标版 PostgreSQL
→ Browse/Search 完成
→ 真实构建与上传
→ VIP/域名切换

Auf der Zwischenversion darf PostgreSQL nicht vorzeitig migriert werden, und Nexus darf während der Datenbankmigration nicht laufen.

1. Kubernetes-Basisressourcen erstellen

Zuerst werden erstellt:

  1. StorageClass, PV und PVC.
  2. Nicht sensible ConfigMaps.
  3. Der Nexus-Service.
  4. Ein Initialisierungs-Job für Datenbank und Schema von PostgreSQL.
  5. Das Datenbank-Secret.

Das Secret wird per Befehl erstellt, nicht als YAML-Klartext:

kubectl -n repository create secret generic nexus-db \
  --from-literal=username=nexus \
  --from-literal=password="$(openssl rand -base64 36)"

Abnahme des Speichers:

  • PVC ist Bound.
  • PV hat die Reclaim Policy Retain.
  • Das Verzeichnis auf dem Zielknoten hat ausreichend Kapazität.
  • Die UID/GID des Nexus-Containers besitzt Schreibrechte.
  • Der Platzbedarf von Blob Store und Datenbank-Tempfiles ist getrennt zu bewerten.

2. Zwischenversion von Nexus3 mit H2 starten

kubectl -n repository apply -f nexus3-migration.yaml
kubectl -n repository rollout status statefulset/nexus --timeout=15m

curl -fsS \
  http://<migration-address>:8081/nexus/service/rest/v1/status

Nutze für den Startup-Probe das Status-Endpoint und plane für den ersten Upgrade ausreichend Zeit ein:

startupProbe:
  httpGet:
    path: /nexus/service/rest/v1/status
    port: http
  periodSeconds: 10
  timeoutSeconds: 5
  failureThreshold: 60

Meldet der Probe connection refused, prüfe zuerst nexus.log, statt die Wartezeit grenzenlos zu erhöhen.

3. Den Upgrade Wizard von Nexus2 ausführen

  1. Nexus2-Programm und Arbeitsverzeichnis sichern.
  2. Den Upgrade Agent auf Nexus2 erstellen.
  3. Die Upgrade Capability auf Nexus3 erstellen.
  4. Den Repository-Content migrieren.
  5. Die Server-Konfiguration migrieren.
  6. Warten, bis die Synchronisationswarteschlange auf null steht.
  7. Uploads einfrieren und Nexus2 stoppen.
  8. Finalize und Done ausführen.

Vor dem Finalize muss Folgendes bestätigt sein:

  • Die neuesten Hosted-Artefakte sind vorhanden.
  • Der Proxy kann Inhalte erneut abrufen.
  • Die Group-Mitglieder und ihre Reihenfolge stimmen.
  • Benutzer, Rollen und anonymer Zugriff stimmen.
  • Die modernen und die aus Kompatibilitätsgründen weiterhin benötigten alten URLs sind verfügbar.
  • Mindestens ein realer Maven-Build läuft durch.

4. Auf die Zielversion aktualisieren, weiterhin mit H2

Zuerst das offizielle H2-Backup erstellen und die SHA256-Summen notieren; parallel den Blob Store sichern:

sha256sum /backup/nexus-h2-* /backup/nexus-blob-* > /backup/SHA256SUMS

Danach das StatefulSet-Image aktualisieren. Nach dem Start warten, bis alle internen Schema- und Upgrade-Tasks abgeschlossen sind, und anschließend einen neuen H2-Wiederherstellungspunkt erzeugen.

Der Pod darf nicht neu gestartet werden, solange interne Tasks laufen.

5. PostgreSQL vorbereiten

CREATE ROLE nexus LOGIN PASSWORD '<random-password>';
CREATE DATABASE nexus OWNER nexus;

\connect nexus

CREATE SCHEMA nexus AUTHORIZATION nexus;
GRANT USAGE, CREATE ON SCHEMA nexus TO nexus;
ALTER ROLE nexus SET search_path TO nexus;

Verifizieren, dass die Anwendungsrolle Folgendes kann:

  • sich mit der Datenbank verbinden.
  • im Ziel-Schema temporäre Tabellen anlegen und löschen.
  • den erwarteten search_path verwenden.

Wird nur auf Datenbankebene autorisiert, ohne dem Schema USAGE und CREATE zu gewähren, schlägt der Migrator trotzdem fehl.

6. Den Database Migrator ausführen

Den Migrator passend zur Zielversion von Nexus herunterladen und verifizieren:

curl -fLO https://download.sonatype.com/nexus/nxrm3-migrator/nexus-db-migrator-<version>.jar
curl -fLO https://download.sonatype.com/nexus/nxrm3-migrator/nexus-db-migrator-<version>.jar.sha256

test "$(sha256sum nexus-db-migrator-<version>.jar | awk '{print $1}')" = \
  "$(cat nexus-db-migrator-<version>.jar.sha256)"

Nexus vollständig stoppen:

kubectl -n repository scale statefulset/nexus --replicas=0
kubectl -n repository wait --for=delete pod/nexus-0 --timeout=180s

Der Migrator liest die Verbindungsparameter aus einem kontrollierten Secret. Enthält das Passwort reservierte URL-Zeichen, kodiere es per URL-Encoding; die JDBC-URL darf nicht in Logs gelangen.

Fortsetzen nur, wenn:

  • Der Job den Status Complete hat.
  • In der Migrationszusammenfassung ist skipped gleich 0.
  • Keine Fehler bei failed, constraint, schema permission oder Authentifizierung auftreten.
  • Die Anzahl der PostgreSQL-Tabellen, Komponenten, Assets und Blob-Referenzen stimmt mit der Zusammenfassung überein.

Schlägt die Migration fehl, den Migrator nicht direkt gegen das bestehende Ziel-Schema erneut ausführen. Zuerst die Ursache eingrenzen, danach ein sauberes, leeres Schema wiederherstellen oder neu aufbauen.

7. PostgreSQL aufräumen und die finale Version starten

Solange Nexus noch gestoppt ist, ausführen:

VACUUM (FULL, ANALYZE);

Danach das finale StatefulSet mit PostgreSQL verbinden:

env:
  - name: NEXUS_DATASTORE_NEXUS_JDBCURL
    value: jdbc:postgresql://postgresql.repository.svc.cluster.local:5432/nexus?currentSchema=nexus
  - name: NEXUS_DATASTORE_NEXUS_USERNAME
    value: nexus
  - name: NEXUS_DATASTORE_NEXUS_PASSWORD
    valueFrom:
      secretKeyRef:
        name: nexus-db
        key: password

Nach dem Start warten auf:

  • Rebuild repository browse
  • Rebuild repository search

Bevor diese einmaligen Tasks abgeschlossen sind, die Instanz nicht neu starten und keinen Traffic umschalten.

8. Abnahmematrix

Laufzeit

  • Pod ist Ready, die Restart-Anzahl steigt nicht.
  • Das Status-Endpoint ist erreichbar.
  • Keine Datenbank-, Blob- oder Indexfehler in den Logs.
  • Nexus- und Java-Version entsprechen dem Plan.

Repositories

  • Hosted-Releases lassen sich herunterladen.
  • Hosted-Snapshots lassen sich herunterladen.
  • Third-party lässt sich herunterladen.
  • Proxy-Treffer und -Fehltreffer sind erfolgreich.
  • Group wird in der Mitgliederreihenfolge aufgelöst.
  • Search findet bekannte Komponenten.

Berechtigungen

  • Benutzer, Rollen und Realm funktionieren.
  • Anonymer Download verhält sich wie erwartet.
  • Die Upload-Berechtigungen für Hosted stimmen.

Clients

  • Maven baut mit den echten Settings vollständig.
  • Jenkins kann Abhängigkeiten herunterladen.
  • Eine temporäre Version hochladen und wieder aufräumen.
  • Zu erhaltende alte /content/-URLs sind verifiziert oder umgeschrieben.

9. Umschalten des Zugangs

Vor der Umschaltung:

  • Das alte Nexus2 ist gestoppt.
  • Der alte Knoten hält den VIP nicht mehr.
  • Das neue Nexus3 ist über die interne Adresse verifiziert.
  • Backup- und Rollback-Befehle funktionieren weiterhin.

Direkt nach der Umschaltung den Status, Downloads, Uploads und einen echten Build verifizieren. Zu keinem Zeitpunkt dürfen zwei Maschinen denselben VIP halten.

Rollback:

  1. Uploads auf dem neuen Nexus3 einfrieren.
  2. Den VIP vom neuen Knoten entfernen.
  3. Bestätigen, dass ARP und Routen konvergiert sind.
  4. Das alte Nexus2 starten.
  5. Den alten Zugang wiederherstellen.

10. Credentials und Backups abschließen

  • Secrets löschen, die nur während des Migrationsfensters verwendet wurden.
  • Falls Passwörter in Logs gelangt sein könnten, PostgreSQL-Rolle und Kubernetes-Secret rotieren.
  • Beide Passwörter müssen gleichzeitig aktualisiert werden.
  • Nexus2, beide H2-Wiederherstellungspunkte, das PostgreSQL-Backup und das Blob-Store-Backup aufbewahren.
  • Die alten Server erst nach stabiler Beobachtung und erfolgreichen Wiederherstellungsübungen freigeben.

Pflege der Komponentenzahlen der Community Edition

Für Proxy und Hosted getrennte Richtlinien festlegen:

  • Proxy: Lang nicht genutzte Cache-Komponenten löschen.
  • Hosted: Entsprechend den Release- und Compliance-Anforderungen aufbewahren.
  • Vor dem Cleanup ein PostgreSQL-Backup ausführen.
  • Zuerst Soft-Delete, erst nach Beobachtung Compact auf dem Blob Store ausführen.

Die Aktualisierung im Usage Center kann sich verzögern, und historische Spitzenwerte fallen nicht sofort. Cleanup nicht wiederholt ausführen, nur weil die Seite kurzzeitig noch die alten Zahlen anzeigt.

Definition of Done

迁移器无跳过
+ PostgreSQL 数据与 Blob 引用一致
+ Browse/Search 完成
+ 仓库和权限正确
+ Maven/Jenkins 下载上传通过
+ 入口切换成功
+ 回滚和备份仍可用

Ein gutes Runbook zielt nicht darauf ab, durch möglichst viele Befehle professionell zu wirken. Es sorgt dafür, dass jeder irreversible Schritt klare Eingaben, Fortsetzungsbedingungen und Rollback-Grenzen hat.
