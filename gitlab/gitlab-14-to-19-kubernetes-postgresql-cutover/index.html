ENGINEERING NOTE · 2026年8月8日

从 GitLab CE 14.9.3 平滑升级到 19.2.1：Kubernetes、PostgreSQL 17 与增量切流实战

记录一套自建 GitLab 从 14.9.3 逐级升级到 19.2.1，并迁入 Kubernetes、切换外部 PostgreSQL、同步最终增量、保留原入口地址的完整方法。

本文来自一次真实生产迁移。IP、域名、节点名、项目名、仓库数量、用户数量、镜像仓库、备份文件名和校验值均已脱敏或泛化；Secret、密码和内部地址只使用占位符。

GitLab 的升级停靠点和 PostgreSQL 支持矩阵会继续变化。执行前必须重新核对 GitLab 官方升级路径 与 安装要求，不能把本文的版本组合当作永久规则。

这次迁移的起点是一台运行多年的 GitLab CE 14.9.3。它使用 Omnibus 一体化部署，Git 仓库、PostgreSQL、Redis、配置和日志都集中在同一台虚拟机上。

终点是：

  • GitLab CE 19.2.1。
  • 以单副本 StatefulSet 运行在 Kubernetes。
  • Git 仓库、上传文件和配置保存在 Retain 本地持久卷。
  • PostgreSQL 使用集群内的独立数据库和账号。
  • PostgreSQL 最终升级到 17。
  • 对外域名、服务 IP 和 SSH 入口保持不变。
  • 旧服务器在最终增量同步后关机，并保留一段时间作为回滚点。

这不是一次“换镜像然后等待 Pod 变绿”的升级。真正需要处理的是四条相互约束的链路：

flowchart LR
  A["GitLab 14.9.3<br/>旧 Omnibus"] --> B["GitLab 15<br/>内置 PostgreSQL"]
  B --> C["GitLab 16<br/>外部 PostgreSQL 14"]
  C --> D["GitLab 17<br/>PostgreSQL 14 / 16"]
  D --> E["GitLab 18<br/>PostgreSQL 16 / 17"]
  E --> F["GitLab 19.2.1<br/>PostgreSQL 17"]
  G["required stops"] --> A
  G --> B
  G --> C
  G --> D
  G --> E
  H["备份与回滚点"] --> B
  H --> C
  H --> D
  H --> E
  H --> F

每个阶段都必须同时满足：版本路径正确、后台迁移完成、数据库版本受支持、回滚数据可用。

为什么必须升级，但不能直接跨版本

继续运行 14.x 的问题不只是“版本旧”：

  • 安全更新和缺陷修复无法持续获得。
  • 新版 Runner、浏览器、Git 客户端和集成组件的兼容范围不断前移。
  • 老版本 PostgreSQL 和操作系统也会进入维护末期。
  • 后续想迁入 Kubernetes 时，旧配置、旧数据库和旧存储会一起成为阻碍。

但 GitLab 的数据库结构变化很多，大版本之间还存在 Batched Background Migration。直接从 14.9 跳到 19.x，极易遇到缺失迁移类、表结构不匹配、数据库版本不支持或者加密配置无法解密。

GitLab 官方要求经过特定的 required upgrade stops。每到一个停靠点，都要使用该 minor 的最新 patch，等待后台迁移全部结束，再进入下一站。

其中某些旧版本停靠点是条件性的。例如，本次在确认只有一个 Web 节点、相关业务表数据量不触发条件后，才跳过了不适用的停靠点。

不要照抄结论。正确做法是把源版本、目标版本、实例规模和相关表数据输入 GitLab Upgrade Path 工具，再逐项阅读各版本 Upgrade Notes。

第 1 步：先固定迁移基线

开始前记录一组可重复查询的基线。后续每升级一站，都用相同脚本检查。

至少包括：

  • GitLab 版本。
  • 用户、组、项目、Merge Request、Pipeline 和 Job 数量。
  • 仓库总量和关键默认分支 tip。
  • LFS、Upload、Artifact、Package 占用。
  • PostgreSQL 版本、数据库大小和扩展。
  • Sidekiq、Gitaly、Puma、Workhorse、GitLab Shell 状态。
  • 普通数据库迁移和批量后台迁移状态。

示例：

gitlab-rake gitlab:env:info
gitlab-rake gitlab:check SANITIZE=true

gitlab-rails runner '
puts({
  users: User.count,
  groups: Group.count,
  projects: Project.count,
  merge_requests: MergeRequest.count,
  builds: Ci::Build.count
}.inspect)
'

只看 gitlab:check 不够。它能够发现常见的配置、权限和服务问题，却不能替代业务数据计数、仓库 refs 比对和真实 clone/push。

第 2 步：备份不只是一个 tar 包

GitLab 应用备份与配置备份是两套东西。应用备份包含数据库和业务文件，但 /etc/gitlab/gitlab-secrets.json 中保存着数据库加密密钥、CI/CD 变量、2FA 等敏感数据的解密能力。

GitLab 官方也明确要求把配置和 Secret 单独保存在安全位置，参见 Backup 和 Restore GitLab。

本次每个关键阶段至少保留：

  1. GitLab 应用备份。
  2. PostgreSQL 独立 dump。
  3. /etc/gitlab 配置归档。
  4. gitlab-secrets.json。
  5. SSH Host Key。
  6. 备份文件大小和 SHA-256。
  7. 当前 StatefulSet、Service、PV、PVC、Secret 和 ConfigMap 清单。
umask 077

gitlab-backup create
gitlab-ctl backup-etc

tar -C /etc -czf /backup/ssh-host-keys.tar.gz ssh
sha256sum /backup/* > /backup/SHA256SUMS

恢复演练必须使用相同 GitLab 版本。不能把 14.x 备份直接恢复进 19.x 容器。

还有一个容易踩的坑：执行外部 PostgreSQL dump 时，pg_dump 客户端主版本不能低于服务端主版本。如果 GitLab 容器里自带的客户端过旧，应在 PostgreSQL Pod 或匹配版本的临时工具容器中生成 dump。

第 3 步：先在 Kubernetes 恢复同版本

不要一边改变运行平台，一边跨多个 GitLab 大版本。第一步应先把 14.9.3 恢复进 Kubernetes，同版本通过验收后，再开始逐级升级。

这次采用单副本 StatefulSet，核心设计如下：

apiVersion: v1
kind: PersistentVolume
metadata:
  name: gitlab-data
spec:
  capacity:
    storage: <capacity>
  accessModes: [ReadWriteOnce]
  persistentVolumeReclaimPolicy: Retain
  storageClassName: gitlab-local
  hostPath:
    path: /data/gitlab
  nodeAffinity:
    required:
      nodeSelectorTerms:
        - matchExpressions:
            - key: kubernetes.io/hostname
              operator: In
              values: [gitlab-node]

StatefulSet 使用 OnDelete：

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: gitlab
spec:
  replicas: 1
  updateStrategy:
    type: OnDelete
  template:
    spec:
      nodeSelector:
        app-type: gitlab
      tolerations:
        - key: app-type
          operator: Equal
          value: gitlab
          effect: NoSchedule
      terminationGracePeriodSeconds: 300

使用 OnDelete 的目的不是偷懒，而是防止修改镜像后 StatefulSet 立刻滚动。运维人员必须先确认当前停靠点的后台迁移和备份完成，再显式删除 Pod 进入下一版本。

PV 使用 Retain 同样重要。误删 StatefulSet 或 PVC 时，宿主机 /data/gitlab 不会跟着被回收。

第 4 步：每个 GitLab 停靠点都执行同一套闸门

每一站的操作顺序固定为：

  1. 确认前一版本所有迁移完成。
  2. 创建当前版本回滚备份。
  3. 把下一版本镜像同步到内部镜像仓库。
  4. 记录镜像 digest，并在目标节点预拉取。
  5. 修改 StatefulSet 镜像。
  6. 显式删除 Pod。
  7. 观察 reconfigure、数据库迁移、Puma、Sidekiq 和 Gitaly 日志。
  8. 等待 Pod Ready。
  9. 检查数据库迁移与后台迁移。
  10. 执行 HTTP、SSH、核心计数和 gitlab:check。
kubectl -n <namespace> set image statefulset/gitlab \
  gitlab=<registry>/gitlab-ce:<next-version>

kubectl -n <namespace> delete pod gitlab-0
kubectl -n <namespace> wait --for=condition=Ready \
  pod/gitlab-0 --timeout=30m

kubectl -n <namespace> exec gitlab-0 -- \
  gitlab-rake gitlab:check SANITIZE=true

首次启动几分钟没有 Ready，不等于进程卡死。应同时检查：

kubectl -n <namespace> get pod gitlab-0 -o wide
kubectl -n <namespace> describe pod gitlab-0
kubectl -n <namespace> logs -f gitlab-0

镜像拉取、Chef reconfigure、数据库锁、后台迁移、仓库校验和磁盘 IO 都可能让启动变慢。不要因为一个等待超时就并发启动多个 Rails Runner 或完整 checksum，它们会进一步放大磁盘竞争。

第 5 步：正确识别 Batched Background Migration

这是整个升级过程中最容易误判的地方。

旧脚本曾使用：

WHERE status <> 3

GitLab 17 之后，6 表示 finalized。继续使用旧条件会把已经完成的迁移当成未完成，甚至调用当前版本已经不存在的迁移类。

更稳妥的 SQL 是：

SELECT id, job_class_name, table_name, status
FROM batched_background_migrations
WHERE status NOT IN (3, 6);

或者在对应版本 Rails 环境中使用模型提供的 scope：

gitlab-rails runner '
puts Gitlab::Database::BackgroundMigration::BatchedMigration.unfinished.count
'

GitLab 新版本还提供了更完整的 Rake Task。官方文档要求进入下一停靠点前所有后台迁移都必须结束，参见 Check migrations before upgrade。

gitlab-rake gitlab:background_migrations:list
gitlab-rake gitlab:background_migrations:status

不要直接把失败迁移改成 finished。先检查父迁移、子任务、业务数据和当前版本实现。只有确认迁移逻辑对现存数据确实不适用，并且已经创建可恢复备份后，才考虑使用当前版本官方提供的 finalize/execute 任务。

第 6 步：让 PostgreSQL 升级节奏跟上 GitLab

GitLab 与 PostgreSQL 不能各自独立升级。本次采用以下节奏：

阶段GitLabPostgreSQL 策略
起点14 / 15保留 Omnibus 内置 PostgreSQL
中段16迁移到外部 PostgreSQL 14
进入 17 前16.11PostgreSQL 14 升到最新兼容小版本
进入 18 前17.11PostgreSQL 14 → 16
进入 19 前18.11PostgreSQL 16 → 17
终点19.2外部 PostgreSQL 17

GitLab 19 要求 PostgreSQL 17。官方支持矩阵见 GitLab installation requirements。

外部数据库必须使用独立数据库、账号和 Secret：

postgresql['enable'] = false

gitlab_rails['db_adapter'] = 'postgresql'
gitlab_rails['db_host'] = 'postgresql.<namespace>.svc.cluster.local'
gitlab_rails['db_port'] = 5432
gitlab_rails['db_database'] = 'gitlabhq_production'
gitlab_rails['db_username'] = 'gitlab'
gitlab_rails['db_password'] = File.read('/run/secrets/gitlab-db/password').strip

PostgreSQL 大版本升级前先做 pg_upgrade --check：

pg_upgrade \
  --old-datadir=<old-data> \
  --new-datadir=<new-data> \
  --old-bindir=<old-bin> \
  --new-bindir=<new-bin> \
  --check

本次数据卷使用支持 reflink 的 XFS，因此实际升级采用 --clone，避免再复制一份完整数据库：

pg_upgrade \
  --old-datadir=<old-data> \
  --new-datadir=<new-data> \
  --old-bindir=<old-bin> \
  --new-bindir=<new-bin> \
  --clone \
  --jobs=4

--clone 不是备份。旧数据目录必须继续保留，直到 GitLab 最终版本、增量切流和业务验收全部完成。不要提前运行生成的 delete_old_cluster.sh。

升级完成后更新优化器统计信息：

vacuumdb --all --analyze-in-stages --jobs=4

然后从 GitLab Rails 内确认真实连接目标和数据库版本，而不是只看 PostgreSQL Pod 日志。

第 7 步：处理几个真实的升级故障

1. status <> 3 把 finalized 当成失败

原因是 GitLab 17 引入了新的迁移状态。修复不是“强制标记完成”，而是使用当前版本的 unfinished scope 或 NOT IN (3, 6)。

2. 历史分区数据阻塞后台迁移

某个后台任务处理历史通知数据时，发现记录时间早于现有月分区范围。此时不能伪造业务记录，也不能直接跳过。

正确处理思路是：

  1. 找到具体迁移和源记录。
  2. 确认记录是否仍有有效业务关联。
  3. 检查目标表分区边界。
  4. 在停写和备份条件下为合法历史数据准备兜底分区。
  5. 使用当前 GitLab 版本的官方任务重新执行或 finalize。
  6. 再次检查未完成迁移数和数据完整性。

3. GitLab 19 首次启动因旧组件状态退出

从 GitLab 18 进入 19 时，第一次 reconfigure 检测到历史组件遗留状态并退出。没有立即手工删除整个 Secret，而是先保留备份，确认新版本会重新生成不再需要的配置块，再启动一次。随后 schema migration 正常完成。

这类问题必须区分：

  • 配置确实已被新版本移除。
  • Secret 丢失或损坏。
  • 数据库中的加密值无法解密。

三种情况的处理方式完全不同。

4. 最终版本完整备份可能挤爆磁盘

迁移末期磁盘剩余空间不足以再暂存一份完整仓库归档。最终版本只创建数据库保护备份，同时继续保留上一关键版本已经校验过的完整备份、仓库数据卷和配置归档。

这是一种受控取舍，但前提是清楚记录“哪一个备份包含数据库，哪一个包含仓库”，不能把 database-only 备份误当成完整恢复点。

第 8 步：为什么升级完成后仍不能立刻切流

初始备份只是一个时间点。升级期间旧 GitLab 如果仍对开发者开放，就会继续产生 push、权限修改、CI 变量、Merge Request 和构建记录。

因此最终切流前必须做增量审计。

先冻结旧实例：

gitlab-ctl stop nginx
gitlab-ctl stop gitlab-workhorse
gitlab-ctl stop puma
gitlab-ctl stop sidekiq
gitlab-ctl stop gitlab-kas

同时禁止 git 用户继续通过 SSH 写入，但保留运维 root 通道。冻结后比较新旧两边：

  • 用户、组、项目、MR、CI Job 等核心计数。
  • 最新 Project/Event 时间。
  • 默认分支和活跃分支 tip。
  • LFS、Artifact、Upload、Package 是否有增量。
  • GitLab 审计/事件记录。

本次数据库对象计数没有新增，但发现数百条 push 事件，涉及十余个仓库。这说明只同步数据库或只比较项目数量都会漏数据。

第 9 步：只同步发生变化的仓库

先从事件和项目时间定位变更仓库，再同步对应的 hashed repository 目录。不要在不了解差异时对整个仓库目录执行 rsync --delete。

同步后至少完成三层校验。

文件所有权

不同 GitLab 镜像中的 git UID/GID 可能不同。使用 rsync --numeric-ids 会把旧 UID 原样带过来，导致目标 Gitaly 无权访问。

同步后以目标容器实际 UID/GID 修复，而不是复制旧数字：

chown -R <target-git-uid>:<target-git-gid> <affected-repository>

refs 完全一致

git -C <source-repository> for-each-ref \
  --format='%(refname) %(objectname)' | sort > source.refs

git -C <target-repository> for-each-ref \
  --format='%(refname) %(objectname)' | sort > target.refs

diff -u source.refs target.refs

对象完整性

git -C <target-repository> fsck --no-dangling

旧 commit-graph 缓存可能引用已经不存在的对象。不要删除 Git 对象来“修复”，而是先保留旧缓存目录，再从当前可达 refs 重建 commit-graph。

最后更新项目活动时间并清理 Rails Cache，避免首页仍显示初始备份时刻。

第 10 步：保留原 IP，同时让节点名与 IP 一致

为了不批量修改开发机、Jenkins 和历史仓库地址，最终继续使用原 GitLab 服务 IP。

切换过程是：

  1. GitLab StatefulSet 缩容到 0。
  2. 确认旧服务器已经停写并关机，原 IP 不再响应。
  3. 把目标 Kubernetes 节点主机名和管理 IP 改成最终值。
  4. 执行 kubeadm reset 后以新节点名重新加入集群。
  5. 恢复 GitLab 专用标签与污点。
  6. 重新绑定本地 PV。
  7. StatefulSet 扩容到 1。
  8. 验证 HTTP、SSH、Gitaly、数据库和仓库。
sequenceDiagram
  participant Old as 旧 GitLab
  participant API as Kubernetes API
  participant Node as 新 GitLab 节点
  participant GitLab as GitLab 19

  Old->>Old: 冻结 HTTP / SSH Git 写入
  Old->>Node: 同步最终仓库增量
  Old->>Old: 关机并释放服务 IP
  Node->>Node: 修改 hostname 与静态 IP
  Node->>API: kubeadm join --node-name <final-node>
  API->>Node: 恢复 label / taint
  API->>GitLab: 绑定 PV 并启动 StatefulSet
  GitLab->>GitLab: HTTP、SSH、数据库、仓库验收

这里有一个 Kubernetes 陷阱：PV 的 nodeAffinity 是不可变字段。节点改名后不能直接 patch。

正确做法是：

  1. GitLab Pod 保持停止。
  2. 确认 PV 回收策略为 Retain。
  3. 删除 PVC/PV 对象。
  4. 保留宿主机 /data/gitlab 实际目录。
  5. 使用新节点名重建 PV/PVC，并指向同一目录。
  6. 等 PVC Bound 后再启动 GitLab。

这一步删除的是 Kubernetes 元数据，不是仓库数据。操作前必须再次检查 Pod 已停止、路径正确、回收策略正确。

旧服务器不能带着原 IP 直接再次开机。应在虚拟化平台先断开虚拟网卡，从控制台重装或修改成已经释放的其他地址，再连接网络，否则会产生 IP 冲突。

第 11 步：最终验收不要只看 Pod Ready

最终验收分成六层。

Kubernetes 层

kubectl get node <gitlab-node> -o wide
kubectl -n <namespace> get pod gitlab-0 -o wide
kubectl -n <namespace> get pvc
kubectl get pv

确认：

  • 节点名、InternalIP 和主机名一致。
  • Pod 在预期节点运行且没有重启。
  • PVC 为 Bound。
  • PV 为 Retain，nodeAffinity 指向最终节点。

GitLab 服务层

gitlab-ctl status
gitlab-rake gitlab:check SANITIZE=true

检查 GitLab Shell、Gitaly、Sidekiq、Redis、数据库迁移、Uploads 权限和 hashed storage。

数据库层

  • 核心对象计数与冻结源一致。
  • PostgreSQL 为目标版本。
  • 所有 schema migration 已完成。
  • Batched Background Migration 未完成数为 0。
  • gitlab:doctor:secrets 能够解密关键数据。

仓库层

  • 所有发生增量的仓库 refs 完全一致。
  • git fsck --no-dangling 通过。
  • 抽样执行 clone、fetch、push、merge。

HTTP 与 SSH 层

curl -fsS http://<gitlab-host>/users/sign_in >/dev/null
ssh -T git@<gitlab-host>

真实业务层

  • Jenkins 能拉取源码并提交状态。
  • Webhook 能正常投递。
  • Runner 能领取任务。
  • CI/CD 变量可以解密。
  • 用户登录、2FA、Personal Access Token 正常。

只有六层全部通过，才算迁移完成。

回滚策略

最终切流后不要立刻删除旧服务器、旧 PostgreSQL 目录和中间版本镜像。

建议至少保留：

  • 旧 GitLab 虚拟机，保持关机和断网。
  • 最后一个已验证完整 GitLab 备份。
  • 每个关键大版本的数据库 dump 与配置归档。
  • PostgreSQL 旧数据目录。
  • GitLab 18 的最终完整恢复点。
  • GitLab 19 的数据库保护备份。
  • 实际使用过的 GitLab/PostgreSQL 镜像及 digest。
  • 最终增量仓库清单和 refs 校验结果。

回滚也分层：

  1. 入口异常但数据正常：切回旧入口。
  2. GitLab Pod 异常：恢复前一个镜像和对应数据库状态。
  3. PostgreSQL 异常：切回保留的旧数据目录。
  4. 数据完整性异常：关闭新实例写入，恢复最后完整备份，并重新计算增量。

任何回滚都要避免让新旧两边同时接受写入。

这次升级最重要的经验

1. GitLab 升级的最小单位不是镜像，而是“版本 + 数据库 + 后台迁移”

Pod Ready 只表示进程通过探针。真正的停靠点完成条件是：版本正确、数据库受支持、普通迁移完成、后台迁移完成、备份可恢复、真实请求通过。

2. 迁入 Kubernetes 不等于高可用

单副本 GitLab 加本地 PV 仍然是单节点有状态服务。Kubernetes 提供的是声明式部署、探针、调度、资源限制和统一运维入口，不会自动把本地存储变成高可用。

3. 初始恢复成功不代表可以切流

只要旧实例还开放，就必须把最终增量分成数据库对象、Git 仓库、LFS/Artifact/Upload 和配置四类分别核对。

4. 保留原 IP 能减少客户端改动，但必须处理节点身份

IP、主机名、Kubernetes Node 名和 PV nodeAffinity 最好保持一致。否则半年后排查问题时，很难解释为什么某个地址对应另一个节点名。

5. 不要提前清理回滚点

迁移最危险的清理动作往往看起来最合理：删除旧 PostgreSQL 目录、释放旧 VM、清空中间镜像、删除完整备份。等完整业务验收和观察期结束后再做。

结语

从 GitLab 14.9.3 升级到 19.2.1，真正耗时的不是下载二十个镜像，而是每一站都愿意停下来验证。

一条可靠的迁移路径可以归纳为：

盘点
→ 同版本恢复
→ required stops
→ 每站清空后台迁移
→ PostgreSQL 分阶段升级
→ 每站创建回滚点
→ 冻结旧实例
→ 同步最终增量
→ refs 与对象校验
→ 保留原入口切流
→ 六层验收
→ 观察期后再清理

越是跨度大的基础设施升级，越不能依赖“一次成功启动”的运气。把每个阶段变成有输入、有输出、有验收、有回滚的独立步骤，升级才真正可控。
