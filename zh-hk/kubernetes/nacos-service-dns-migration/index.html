將 Nacos 裡的固定 Service IP 改為 Kubernetes DNS：一次配置治理實戰

記錄如何盤點數百份 Nacos 配置，將 Kubernetes ClusterIP 安全遷移為 Service DNS，並區分 Redis、Kafka、外部依賴與已刪除的服務。

文中的 namespace、服務名稱、網域、地址和配置數量均已脫敏或泛化。真實配置備份可能包含密碼和 Token，絕不能放入網誌或 Git 儲存庫。

系列導覽：Kubernetes 重建遷移教學系列。本篇假設 Nacos 叢集已經搭建並通過驗收。

Kubernetes 叢集遷移之後，最隱蔽的一類故障不是 Pod 無法啟動，而是 Nacos 配置仍然保存着舊叢集的 Service ClusterIP。

典型現象包括：

Load balancer does not have available server
Unable to connect to Redis
No route to host
connect timed out

舊 IP 在新叢集可能不存在，亦可能剛好被另一個 Service 佔用。後者比直接逾時更危險，因為請求會被轉發到錯誤的服務。

因此，這次治理的目標不是「把 IP 換成新 IP」，而是盡可能改為穩定的 Kubernetes Service DNS。

下面先完整走一遍操作流程，再解釋為何有些地址不能自動替換。

第 1 步：建立隔離工作目錄

mkdir -p nacos-dns-migration/{backup,inventory,candidates,reports}
cd nacos-dns-migration

git init
printf 'backup/\n*.zip\n*.token\n.env\n' > .gitignore

原始 Nacos 匯出檔案可能包含密碼、Token 和資料庫地址，只可以放入 backup/，並應使用加密儲存。Git 只保留脫敏後的規則、指令碼和報告範本。

建立一份變更清單：

namespace,group,data_id,old_value,target_service,target_port,action,owner,status
app-test,DEFAULT_GROUP,global.properties,<old-address>,redis-service,6379,replace,team-a,pending

所有發布動作都要能夠追溯至這一行。

第 2 步：匯出 Nacos 配置

最穩妥的方式是使用 Nacos 控制台按 namespace 匯出配置壓縮包，並記錄匯出時間、操作人和檔案校驗值：

sha256sum backup/<namespace>-configs.zip \
  > backup/<namespace>-configs.zip.sha256

如果使用 OpenAPI 自動匯出，API 路徑、鑑權和相容性必須按目前 Nacos Server 版本核對。由 Nacos 3.2 起移除了部分舊 HTTP API，不能直接用舊指令碼操作新叢集。

解壓到臨時目錄後先做唯讀掃描：

mkdir -p backup/unpacked
unzip -q backup/<namespace>-configs.zip -d backup/unpacked

rg -n --glob '*.{properties,yaml,yml,json,xml}' \
  '([0-9]{1,3}\.){3}[0-9]{1,3}' backup/unpacked \
  > reports/ip-references.txt

不要在掃描結果列印整行 Secret。真實指令碼應將 password、secret、token 等鍵的值遮罩。

第 3 步：匯出新舊叢集 Service 清單

分別顯式指定 kubeconfig 匯出，不要依賴目前的 context：

kubectl --kubeconfig <old-kubeconfig> get service -A -o json \
  > inventory/old-services.json

kubectl --kubeconfig <new-kubeconfig> get service -A -o json \
  > inventory/new-services.json

轉換成方便審閱的 TSV：

jq -r '
  .items[]
  | select(.spec.clusterIP != "None")
  | [
      .metadata.namespace,
      .metadata.name,
      .spec.clusterIP,
      (.spec.ports | map((.port|tostring) + ":" + (.targetPort|tostring)) | join(","))
    ]
  | @tsv
' inventory/old-services.json > inventory/old-services.tsv

jq -r '
  .items[]
  | select(.spec.clusterIP != "None")
  | [
      .metadata.namespace,
      .metadata.name,
      .spec.clusterIP,
      (.spec.ports | map((.port|tostring) + ":" + (.targetPort|tostring)) | join(","))
    ]
  | @tsv
' inventory/new-services.json > inventory/new-services.tsv

現在可以按舊 IP 反查 Service：

rg -F '<old-service-ip>' inventory/old-services.tsv

預期得到：

app-test    rbac-api    <old-service-ip>    8082:8082

目標 DNS 便是：

rbac-api.app-test.svc.cluster.local

第 4 步：逐項確認目標 Service 和連接埠

先檢查新叢集是否存在同名 Service：

kubectl --kubeconfig <new-kubeconfig> -n app-test \
  get service rbac-api -o yaml

kubectl --kubeconfig <new-kubeconfig> -n app-test \
  get endpointslice \
  -l kubernetes.io/service-name=rbac-api -o wide

只有同時滿足以下條件，才可以進入自動候選清單：

  • 舊 IP 能唯一反查到一個 Service。
  • 新叢集存在語義相同的 Service。
  • 配置連接埠對應新 Service 的 port，而不是誤用 targetPort。
  • EndpointSlice 至少有一個 Ready 地址。
  • 負責人確認該依賴仍然存在。

其餘條目全部標為 manual-review，不能讓指令碼猜測。

第 5 步：產生候選檔案，不直接發布

複製一份原始配置：

cp backup/unpacked/global.properties \
  candidates/global.properties

將：

rbac.api.url=http://<old-service-ip>:8082

改為：

rbac.api.url=http://rbac-api.app-test.svc.cluster.local:8082

然後審閱差異：

diff -u backup/unpacked/global.properties \
  candidates/global.properties \
  | tee reports/global.properties.diff

審閱時逐行確認：

  • 只修改主機部分，協定、連接埠、路徑和參數沒有遺失。
  • 沒有把外部依賴改成叢集 DNS。
  • 沒有把 Kafka broker 地址合併成普通 Service。
  • 沒有新增不存在的 Service 名稱。

第 6 步：在業務 Pod 提前驗證 DNS

正式發布前，從真實呼叫方 Pod 測試目標地址：

kubectl -n <caller-namespace> exec <caller-pod> -- \
  getent hosts rbac-api.app-test.svc.cluster.local

kubectl -n <caller-namespace> exec <caller-pod> -- \
  nc -vz rbac-api.app-test.svc.cluster.local 8082

這一步失敗時，修改 Nacos 沒有意義。先修復 Service、Endpoint、NetworkPolicy、CNI 或 kube-proxy。

第 7 步：逐個 Data ID 發布

首次治理時，建議透過 Nacos 控制台操作：

  1. 進入正確的 namespace。
  2. 搜尋精確的 Data ID 和 Group。
  3. 開啟歷史版本，確認可以回滾。
  4. 貼上候選內容，檢視控制台 diff。
  5. 只發布一個 Data ID。
  6. 立即回讀並下載一次，比較校驗值。

如果使用自動化 API，指令碼必須實現：鑑權、逾時、發布前備份、發布後回讀、內容校驗和單個 Data ID 回滾。不要用一個迴圈無條件覆蓋整個 namespace。

第 8 步：只滾動受影響的用戶端

先確認配置是否支援動態重新整理。不能動態重新整理的應用才執行滾動重啟：

kubectl -n <caller-namespace> rollout restart deployment/<caller-app>
kubectl -n <caller-namespace> rollout status deployment/<caller-app> --timeout=10m

查看最近的日誌：

kubectl -n <caller-namespace> logs deployment/<caller-app> --since=10m \
  | grep -Ei 'nacos|refused|timed out|no route|available server'

不要因為修改了一份共享的 global.properties 就同時重啟所有命名空間。按依賴關係分批執行，前一批通過真實業務驗收後才繼續。

第 9 步：執行真實請求並搜尋舊地址

除了健康檢查，還應完成登入、查詢、快取讀寫或內部 RPC 等真實請求。然後在配置和執行日誌中搜尋舊地址：

rg -n -F '<old-service-ip>' candidates reports

kubectl -n <caller-namespace> logs deployment/<caller-app> --since=30m \
  | grep -F '<old-service-ip>'

候選配置和新日誌都不應再出現舊 Service IP。

第 10 步：按 Data ID 回滾

如果業務驗收失敗：

  1. 停止繼續發布其他 Data ID。
  2. 使用 Nacos 歷史版本還原剛才修改的內容。
  3. 回讀確認還原成功。
  4. 滾動剛才受影響的用戶端。
  5. 儲存故障日誌和失敗請求。

不要匯入整個舊 namespace 壓縮包，否則會覆蓋其他團隊在遷移期間已經發布的正常配置。

為什麼固定 ClusterIP 會成為遷移債項

ClusterIP 的生命週期屬於 Service 物件。刪除並重建 Service 後，如果沒有顯式指定 clusterIP，地址可能改變。

下面這種配置把應用與某一次叢集狀態綁定在一起：

rbac.api.url=http://10.x.y.z:8082
spring.data.redis.host=10.x.y.z

更穩定的寫法是：

rbac.api.url=http://rbac-api.app-test.svc.cluster.local:8082
spring.data.redis.host=redis-service.app-test.svc.cluster.local

只要 Service 名稱和 namespace 保持不變，Pod、Endpoint 和 ClusterIP 的變化都不會影響呼叫方。

先確立來源，而不是直接替換

針對每個 Nacos 配置引用，需要同時收集四類數據：

  1. 舊叢集的 Service 名稱、namespace、ClusterIP 和連接埠。
  2. 新叢集的 Service 名稱、namespace、ClusterIP 和連接埠。
  3. 線上或其他同構環境中的穩定配置。
  4. 目前 Deployment、StatefulSet 和 Endpoint 的實際存在狀態。

隨後為每個地址建立分類：

類型處理方式
目前存在的 Kubernetes Service改為完整 Service DNS，並核對連接埠
已刪除或未遷移的 Service不自動替換，先確認還原還是刪除路由
Pod IP禁止保留，找到對應 Service
Kafka broker 地址單獨設計 listener，不做普通 DNS 替換
節點上的 hostNetwork 服務評估能否改為 Service；不能時登記例外
外部資料庫、短訊、專網系統保持原有外部地址

這一步決定治理是否安全。正規表達式只能找到地址，無法判斷地址的所有權。

為什麼不能把所有 IP 都替換掉

已刪除服務

如果一個舊地址指向已經不存在的 Service，把它改成：

missing-service.app-test.svc.cluster.local

只會把連線逾時變成 DNS 解析失敗。正確選擇只有兩個：還原目標 Service，或者刪除不再使用的配置和路由。

Kafka advertised listener

Kafka 用戶端不是只連線到一個入口。Bootstrap Server 會返回 broker 的 advertised address，用戶端隨後直接連線到具體 broker。

因此，原本為每個 broker 暴露的 NodePort 或節點地址，不能簡單改成一個普通 ClusterIP。需要先設計：

  • 內部和外部 listener。
  • 每個 broker 獨立 Service。
  • Advertised listener。
  • DNS、NodePort 或負載平衡入口。

Kafka 地址治理應作為獨立項目執行。

外部依賴

短訊、雲端資料庫、合作夥伴介面和專網系統不屬於 Kubernetes。不能單單因為它們是 IP，就把它們改成 svc.cluster.local。

配置發布必須可以回滾

每次修改前儲存：

  • namespace。
  • Group。
  • Data ID。
  • 原始內容。
  • MD5 或其他校驗值。

發布流程：

flowchart LR
  A["匯出配置"] --> B["識別 IP 和 URL"]
  B --> C["關聯 Service 與連接埠"]
  C --> D["產生候選改動"]
  D --> E["人工審閱例外"]
  E --> F["逐個 Data ID 發布"]
  F --> G["回讀並比對校驗值"]
  G --> H["滾動用戶端並驗證"]

不要一次覆蓋整個 namespace，也不要把備份檔案提交到 Git。回滾應精確到單個 Data ID，而不是用舊匯出包覆蓋之後產生的其他正常變更。

連接埠必須與 Service 一併校驗

DNS 正確不代表配置正確。常見問題是服務名稱已改，但連接埠仍然來自舊環境。

可以把引用解析成：

namespace / service / configured-port

再與 Kubernetes Service 的 port、targetPort 和實際 Endpoint 對比。最終要求：

  • DNS 可以解析。
  • Service 存在。
  • 配置連接埠與 Service port 一致。
  • Endpoint 不為空。
  • 目標 Pod 確實監聽對應連接埠。

Redis 配置需要相容不同 Spring Boot 版本

不同服務可能分別讀取：

spring.data.redis.host
spring.redis.host
gateway.oauth2.redis.host
platform.redis.host

如果系統正在跨 Spring Boot 版本升級，可以先以新屬性為來源，並為舊服務保留臨時別名：

spring.data.redis.host=redis-service.app-test.svc.cluster.local
spring.data.redis.port=6379

spring.redis.host=${spring.data.redis.host}
spring.redis.port=${spring.data.redis.port}
spring.redis.password=${spring.data.redis.password}
spring.redis.database=${spring.data.redis.database}

相容別名需要註明移除條件，避免永久維護兩套配置。

如果舊應用已經回退到 localhost:6379，或者補充 Lettuce pool 參數後出現 commons-pool2 類別缺失，可以繼續閱讀 Boot 2/3 Redis 配置回退故障復盤。

驗證不能停留在 Nacos 頁面

配置發布後，按以下五層驗證：

1. 配置回讀

確認 namespace、Group、Data ID、內容和 MD5 與發布結果一致。

2. DNS 解析

從真實業務 Pod 中執行：

getent hosts redis-service.app-test.svc.cluster.local

3. Service 與 Endpoint

kubectl -n app-test get svc redis-service
kubectl -n app-test get endpointslice -l kubernetes.io/service-name=redis-service

4. 網絡連線

從呼叫方 Pod 存取 Service DNS 和連接埠。如果 Endpoint 可達但 Service 不可達，排查請求來源節點的 kube-proxy；如果 Pod IP 跨節點不可達，排查 CNI 和 firewalld。

5. 真實業務請求

重啟或重新整理對應用戶端後，執行登入、快取、訊息或內部 API 請求。日誌中不應繼續出現舊地址。

Nacos 服務發現與配置中心要分開看待

Nacos 同時承擔配置中心與服務發現，兩個問題經常被混為一談：

  • 配置中心決定 Redis、資料庫、內部 API 等 URL。
  • 服務發現決定某個服務是否有健康實例。

當閘道提示「沒有可用服務」時，應檢查 Nacos instance list；當應用連線到舊 ClusterIP 時，應檢查配置內容。只重啟 Pod 可能令故障現象暫時紓緩，但不會修復錯誤的來源配置。

自動化審計建議

持續治理可以包含這些檢查：

1. 扫描所有 IPv4、URL 和主机名
2. 判断是否属于 Pod CIDR、Service CIDR 或节点网段
3. 将 Service IP 反查到 namespace/service
4. 校验配置端口和 Service port
5. 标记不存在的 Service DNS
6. 生成例外清单，而不是自动覆盖

可以在 CI 為新增配置設定規則：

  • 禁止寫入 Pod CIDR。
  • 預設禁止寫入 Service CIDR。
  • 允許完整 Service DNS。
  • 固定 ClusterIP 必須引用白名單記錄。
  • Secret 和配置匯出不得進入儲存庫。

最終經驗

這次治理最重要的結果不是替換了多少地址，而是建立了明確邊界：

  1. Kubernetes 內部依賴優先使用 Service DNS。
  2. 已刪除服務不能靠虛構 DNS 修復。
  3. Kafka、hostNetwork 和外部系統必須單獨分類。
  4. 每次 Nacos 修改都要備份、逐項發布、回讀和真實請求驗證。

固定 IP 並不總是錯誤，但它必須是有負責人、有原因、有移除計劃的顯式相容項目，而不是來源不明的歷史字串。

地址遷移穩定後，可以繼續按 Spring Boot 3 Nacos 全域配置基線治理 Redis、Redisson、RabbitMQ、Hikari、Tomcat 與配置覆蓋關係。
