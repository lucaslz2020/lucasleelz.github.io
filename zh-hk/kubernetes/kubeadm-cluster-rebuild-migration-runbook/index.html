Kubernetes 重建式遷移 Runbook：把臨場救火變成階段驗收

一份可執行的 kubeadm 叢集重建遷移手冊，涵蓋凍結基線、備份還原、節點初始化、網絡、數據、Nacos、業務驗收、停止條件與回滾。

本文中的節點、地址、網域、環境名稱及容量數據均為脫敏示例。Secret、資料庫備份、Token 與內部倉庫資訊不屬於可發布內容。

系列導覽：Kubernetes 重建遷移教學系列。本篇涵蓋遷移日的執行、停止條件與回滾。

上一篇文章復盤了重建式遷移中遇到的問題。這篇不再按事故時間線敘述，而是把經驗整理成一份可以逐階段執行的 Runbook。

「一步到位」並不等於用一條指令啟動所有節點和業務，而是指：在遷移窗口內只執行經過驗證的版本化資產，不再臨時修改 YAML、Nacos、Service IP、節點污點或防火牆。

總原則：上一階段失敗就停止

flowchart LR
  A["凍結設計"] --> B["備份與還原演練"]
  B --> C["作業系統基線"]
  C --> D["高可用控制平面"]
  D --> E["CNI 與基礎設施"]
  E --> F["零副本預部署"]
  F --> G["數據還原"]
  G --> H["Nacos 與平台依賴"]
  H --> I["業務分批啟動"]
  I --> J["真實業務驗收"]
  J --> K["入口切換"]

每個箭頭都是硬性關卡。失敗時只能：

  1. 回滾當前批次。
  2. 在 Git 中修正源配置。
  3. 重新執行 dry-run 和評審。
  4. 由失敗階段重新執行。

不要用 kubectl edit、臨時 patch、固定 sleep 或重啟 Pod 來掩飾配置錯誤。

階段 0：凍結不可變基線

建立第一個控制平面之前，先凍結：

  • Kubernetes、kubeadm、kubelet、kubectl 版本。
  • 作業系統和 containerd 版本。
  • 控制平面節點和 API VIP。
  • Pod CIDR、Service CIDR、叢集 DNS 網域。
  • CNI、Ingress、StorageClass 和 metrics-server 方案。
  • Nacos 版本與叢集模式。
  • 映像來源和 digest。
  • 節點池、標籤、污點和 toleration。

三類網絡必須有清晰邊界：

網絡用途是否寫入應用配置
節點網段虛擬機器、節點及少量外部依賴僅在確有必要時
Pod CIDRCNI 分配的 Pod IP禁止
Service CIDRClusterIP僅限相容白名單

應用內部預設使用：

<service>.<namespace>.svc.cluster.local:<port>

階段 1：準備全部輸入

執行前必須具備：

  • 伺服器、虛擬機器、磁碟和節點池清單。
  • 舊主機名稱到新主機名稱的對應。
  • etcd snapshot 和 Kubernetes 資源歸檔。
  • 資料庫、訊息系統和檔案儲存備份。
  • Nacos namespace、group、dataId、內容和校驗值。
  • 映像及 digest 清單。
  • Service DNS 替換表和固定 ClusterIP 白名單。
  • 網域、證書、Ingress 和外層入口對應。
  • 回滾負責人、停止條件和還原指令。

只要任一輸入缺失，就不應重裝仍承載數據的舊節點。

階段 2：完成還原演練

備份矩陣可以按以下方式建立：

服務備份驗收
etcdsnapshot隔離還原，API 物件可讀
MySQL全量備份、用戶授權、binlog關鍵表、行數、應用帳號查詢
PostgreSQLdump/base backup、角色、WALschema、擴充功能、應用查詢
MongoDBdump/snapshot、認證庫collection、索引、業務查詢
RedisRDB/AOF、配置PING、關鍵 key、TTL 抽樣
Kafkatopic、partition、offsetbroker、ISR、consumer group
RabbitMQdefinitions、vhost、用戶exchange、queue、binding
NFS/hostPath檔案或儲存快照檔案數、容量、checksum 抽樣

備份檔案存在本身不算完成。還原演練才是門檻。

階段 3：所有配置先在 Git 改完

遷移前完成以下靜態治理：

  • 內部 URL 改為 Service DNS。
  • Pod IP 引用歸零。
  • 固定 ClusterIP 只保留白名單。
  • Kafka advertised listener 單獨評審，不做字串替換。
  • Deployment 的資源、探針、排程、DNS 和優雅停機統一。
  • 匯出物件移除唯讀欄位和舊管理平台元數據。
  • Deployment、StatefulSet 初始副本為 0。
  • CronJob 初始 suspend=true。

常用靜態掃描：

rg -n '<pod-cidr-pattern>' config/ manifests/
rg -n '<service-cidr-pattern>' config/ manifests/
rg -n 'node[0-9]+' manifests/

掃描結果不能直接批次替換，每個命中都需要歸類為 Service、節點、外部依賴或遺留垃圾配置。

階段 4：統一節點基線

重裝後每台節點執行同一指令碼：

swapoff -a
modprobe overlay
modprobe br_netfilter
sysctl --system
systemctl enable --now containerd
systemctl enable kubelet

逐節點驗收：

hostnamectl
ip address
ip route
timedatectl
swapon --show
systemctl is-active containerd
crictl info

firewalld 規則必須在執行 kubeadm 之前完成。所有節點需要允許 Pod CIDR 轉發；hostNetwork 服務則按實際連接埠增加最小範圍的放行規則。

階段 5：建立控制平面

順序固定為：

  1. 初始化第一個 control-plane。
  2. 部署 kube-vip 並驗證 API VIP。
  3. 加入其餘 control-plane。
  4. 檢查 etcd 成員。
  5. 測試 VIP Leader 漂移。
  6. 產生並妥善保存 worker join 指令。

控制平面驗收項：

  • API VIP 連續可達。
  • 三個控制平面節點 Ready。
  • etcd 三成員健康。
  • kubeconfig 指向 VIP，而非單台主機。
  • 證書 SAN 包含實際存取地址。

階段 6：安裝網絡和基礎設施

安裝 CNI 後，先驗證跨節點 Pod IP、CoreDNS、Service ClusterIP 和外部 DNS。

再依次安裝：

  1. 預設儲存類。
  2. metrics-server。
  3. Ingress Controller。
  4. 日誌與監控。

每個節點池至少執行一次 PVC smoke test；kubectl top nodes 和 kubectl top pods -A 都返回數據後，指標系統才算可用。

階段 7：標籤、污點和零副本預部署

節點加入後立即設定目標標籤和污點，避免未標記節點參與排程。

多副本狀態服務使用 required Pod Anti-Affinity：

podAntiAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
    - topologyKey: kubernetes.io/hostname
      labelSelector:
        matchLabels:
          app: zookeeper

資源預部署後的硬性檢查：

  • PVC 已 Bound 或有明確還原計劃。
  • Service selector 與 Pod label 完全匹配。
  • 固定 ClusterIP 未衝突。
  • 所有映像可拉取。
  • 不存在舊主機名稱。
  • 停用環境的副本保持為 0。

階段 8：數據還原

固定順序：

存储
→ 基础数据库与消息组件
→ Kafka
→ PostgreSQL 与辅助服务
→ Nacos 数据库
→ Nacos

每個服務必須從同節點 Pod、跨節點 Pod、Service DNS 三個入口驗證。只看 Pod 是否 Ready，無法發現 kube-proxy、firewalld 或 DNS 問題。

階段 9：Nacos 叢集驗收

Nacos 三個 Pod 需要兩類 Service：

Service類型用途
nacos-hsHeadless成員穩定 DNS 和叢集互聯
nacos-csClusterIP用戶端統一入口

三層驗收：

  1. 三個成員均為健康狀態。
  2. 三個節點的執行模式開關一致。
  3. 測試用戶端註冊後，三個節點都能查詢到同一執行個體。

完成後再匯入 Nacos 配置，逐個回讀 namespace、group、dataId 和校驗值。

階段 10：平台依賴和業務分批啟動

先啟動鑑權、字典、檔案、工作流程等平台依賴，再啟動 OAuth、Gateway 和 DevOps。首個鑑權服務應成為硬性門檻：

  • Deployment Ready。
  • Service 有 Endpoint。
  • 三個 Nacos 節點執行個體一致。
  • OAuth 能透過 Service DNS 呼叫。
  • 無效登入應返回明確的業務錯誤，而不是「無可用執行個體」。

業務一次只啟動一個命名空間。該批次全部通過後再繼續下一批。

階段 11：Ingress 與真實業務驗收

先繞過外部入口，直接請求 Ingress：

curl --resolve app.example.com:443:<ingress-address> \
  https://app.example.com/

叢集內成功後，再配置路由器、NLB 或代理層的 Host/SNI 轉發。當叢集內返回 200 而公網存取失敗時，不要修改 Kubernetes 業務資源。

真實驗收至少覆蓋：

  • 正常登入、失敗登入和 Token 刷新。
  • 權限、檔案、Session。
  • 資料庫讀寫。
  • Kafka/RabbitMQ 生產消費。
  • WebSocket。
  • CI/CD 上傳發布。

自動停止條件

遇到以下情況立即停止：

  • etcd 或資料庫備份無法還原。
  • 網絡 CIDR 衝突。
  • API VIP 漂移失敗。
  • CNI 或 kube-proxy 未全量就緒。
  • 數據校驗不一致。
  • Nacos 三節點執行個體不一致。
  • 核心鑑權鏈路不可用。
  • 出現不可接受的數據寫入錯誤。
  • 公網故障需要修改業務 Pod 才能繞過。

Go / No-Go 清單

  • 伺服器與節點池清單無重複、無遺漏。
  • 版本、網絡和映像已凍結。
  • etcd 與資料庫已還原演練。
  • 檔案儲存已備份。
  • Nacos 配置已匯出、DNS 化並回讀。
  • 固定 ClusterIP 白名單已評審。
  • 標籤、污點和 toleration 已成對校驗。
  • 防火牆初始化指令碼已驗證。
  • Nacos 兩類 Service 清單完整。
  • 網域、證書和入口對應已準備。
  • 所有資源可零副本預部署。
  • 真實驗收請求及預期結果已準備。
  • 回滾入口、負責人和停止條件已確認。

完成定義

遷移完成必須同時滿足：

全部节点 Ready
+ 基础组件健康
+ 数据恢复并通过应用查询
+ Nacos 三节点一致
+ Service DNS 与 Endpoint 正常
+ 活跃业务全部 Ready
+ 登录与核心业务成功
+ 公网入口成功
+ 配置和脚本已进入 Git
+ 旧集群经过观察窗口后下线

Runbook 的真正價值不是讓操作更「機械」，而是把依賴個人記憶的臨場決策，轉化為可以審查、暫停、回滾和重現的工程流程。
