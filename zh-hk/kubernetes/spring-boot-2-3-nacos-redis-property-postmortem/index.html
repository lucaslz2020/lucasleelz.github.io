Spring Boot 2 與 3 混合部署：Nacos Redis 配置為何會回退到 localhost

復盤一次 Spring Boot 2 服務在 Kubernetes 中讀取不到 Boot 3 Redis 配置的問題，涵蓋屬性前綴、Nacos dataId、延遲建連、滾動發布與 commons-pool2 依賴陷阱。

2026年8月8日 12 分鐘閱讀
#Spring Boot #Nacos #Redis #Kubernetes #故障復盤
{ }

本文源自一次 Spring Boot 2 與 3 混合部署叢集的真實排障。服務名稱、叢集、地址及業務數據均已作匿名化處理。系列導覽：Kubernetes 重建遷移教學系列。

在一次全域 Redis 連接池優化發布之後，大部分 Spring Boot 3 服務運作正常，但少量閘道與 WebSocket 服務開始反覆報告：

Unable to connect to localhost:6379

Redis 明明部署在 Kubernetes Service 後面，Nacos 中亦存有正確地址。更具誤導性的是：部分舊服務啟動成功，過了一段時間才出現異常；另一些服務在補上連接池參數後，直接因為缺少 commons-pool2 而無法啟動。

最終確認，這不是 Redis、Service DNS 或網絡故障，而是三件事疊加：

  1. Spring Boot 2 與 3 使用不同的 Redis 屬性前綴。
  2. Redis 用戶端可能延遲到第一次業務存取時才真正建立連線。
  3. 配置連接池參數會改變自動配置分支，缺少依賴時反而令應用程式無法啟動。

先看事故鏈路

flowchart LR
  A["全局配置改為 spring.data.redis"] --> B["Boot 3 正常綁定"]
  A --> C["Boot 2 忽略新前綴"]
  C --> D["保留預設 localhost:6379"]
  D --> E["首次存取 Redis 時才建立連線"]
  E --> F["業務運行後才暴露異常"]
  C --> G["盲目補充 Lettuce pool 參數"]
  G --> H["缺少 commons-pool2"]
  H --> I["新 Pod 啟動失敗"]

這條鏈路解釋了為何「配置已經在 Nacos」「Pod 已經 Ready」與「Redis 實際可達」可以同時成立，但業務仍然訪問 localhost:6379。

根因一：Boot 2 與 Boot 3 的前綴並非同一個

Spring Boot 2 的常見寫法：

spring.redis.host=redis-service.app.svc.cluster.local
spring.redis.port=6379
spring.redis.database=0
spring.redis.timeout=3s

Spring Boot 3 則使用：

spring.data.redis.host=redis-service.app.svc.cluster.local
spring.data.redis.port=6379
spring.data.redis.database=0
spring.data.redis.timeout=3s

Spring Boot 的官方屬性清單亦可以直接驗證這個版本界線：Boot 2.7 使用 spring.redis.*、Boot 3.5 使用 spring.data.redis.*；兩者的預設 host 均為 localhost，預設連接埠均為 6379。

spring.redis.host 與 spring.data.redis.host 並非 relaxed binding 可以自動互換的同一個屬性。舊應用程式讀到後者時，不一定會報「未知配置」，而是可能繼續使用用戶端預設值：

host = localhost
port = 6379

因此，日誌中的 localhost:6379 是很有價值的證據：它通常說明應用程式沒有綁定到預期地址，而非叢集把 Redis 網域解析到本機。

根因二：啟動成功不代表 Redis 配置正確

不少服務不會在 Spring Context 初始化階段立即訪問 Redis。例如：

  • 只有用戶登入後才會讀取 Session。
  • 只有 WebSocket 建立連線後才會寫入在線狀態。
  • 定時任務到點後才會獲取分散式鎖。
  • 某個低頻介面才會訪問快取。

這類服務可能先通過 startup、readiness 甚至 liveness 探針，直到真實請求觸發連線時才出現異常：

RedisConnectionFailureException
Unable to connect to localhost:6379

所以「新 Pod 已經 Ready」只能說明目前探針檢查通過，不能證明所有延遲初始化的外部依賴都可用。

第 1 步：先建立版本與配置矩陣

不要單憑倉庫名稱猜測 Spring Boot 版本。可以從構建檔案、啟動日誌或可執行 JAR 中確認：

unzip -l app.jar | grep 'BOOT-INF/lib/spring-boot-[0-9]'

然後建立最小矩陣：

服務Boot 版本Redis 前綴啟動時是否建立連線是否有 commons-pool2
service-a3.xspring.data.redis否是
service-b2.3.xspring.redis否否
service-c2.7.xspring.redis是是

這張表比「一次性修改全局配置，然後觀察誰報錯」可靠得多。尤其要把暫未訪問 Redis 的服務列為潛在風險，而不是標記為正常。

第 2 步：排除 DNS、Service 與 Redis 本身

從出問題的真實業務 Pod 內驗證：

getent hosts redis-service.app.svc.cluster.local
nc -vz redis-service.app.svc.cluster.local 6379

再從叢集側確認 Service 與 Endpoint：

kubectl -n app get svc redis-service
kubectl -n app get endpointslice \
  -l kubernetes.io/service-name=redis-service

如果網域可以解析、連接埠可以連接、Endpoint 非空，而異常地址明確是 localhost:6379，排查重點就應該轉向屬性綁定與配置優先級。

第 3 步：確認 Nacos 的實際屬性來源

在 Nacos 中「能搜尋到某個 key」不等於應用程式最終使用了它。至少要確認：

  • namespace 是否正確。
  • group 是否正確。
  • dataId 是否被當前應用程式載入。
  • shared、extension 與 application dataId 的優先級。
  • 環境變數、命令列參數是否覆蓋 Nacos。
  • 發布後用戶端是否真正重新整理配置。

建議在變更單中記錄：

application -> namespace -> group -> dataId -> key -> expected value

同時應回讀剛發布的配置並比對內容或校驗值，不能只依賴控制台上的「發布成功」提示。

最小風險修復：在舊應用程式 dataId 中加入相容別名

如果全局配置已經按 Spring Boot 3 統一，可以只在仍使用 Boot 2 的應用級 dataId 中加入：

spring.redis.host=${spring.data.redis.host}
spring.redis.port=${spring.data.redis.port}
spring.redis.database=${spring.data.redis.database}
spring.redis.timeout=${spring.data.redis.timeout}

這樣做有三個好處：

  1. Redis 地址仍由一組 Boot 3 全局屬性維護。
  2. 相容範圍只覆蓋舊應用程式，不會令所有 Boot 3 服務長期攜帶棄用 key。
  3. 應用程式升級後，可以按 dataId 精確刪除臨時別名。

不要為了「相容所有版本」而把兩套前綴永久放進全局配置。這樣會擴大配置面，亦會令 Boot 3 應用程式持續觸發屬性遷移或棄用警告。

如果密碼來自 Secret 或獨立 dataId，也應引用已有值，不要在相容配置中複製明文。

一個容易踩中的二次事故：連接池參數會啟動新程式碼路徑

排查時很容易順手補上：

spring.redis.lettuce.pool.max-active=16
spring.redis.lettuce.pool.max-idle=8
spring.redis.lettuce.pool.min-idle=2
spring.redis.lettuce.pool.max-wait=2s

但連接池配置並非「無依賴的效能參數」。對於缺少 Apache Commons Pool 2 的舊應用程式，它可能令自動配置進入池化分支，並在啟動時失敗：

NoClassDefFoundError:
org/apache/commons/pool2/impl/GenericObjectPoolConfig

Spring Boot 的屬性說明亦明確將連接池的可用性與 commons-pool2 關聯在一起；因此不能只把 pool key 當成 Nacos 側的數值優化。

如果業務確實需要 Lettuce 連接池，應先在程式碼中明確加入依賴並完成構建驗證：

<dependency>
  <groupId>org.apache.commons</groupId>
  <artifactId>commons-pool2</artifactId>
</dependency>

事故止血階段更穩妥的做法是：

  1. 只補齊 host、port、database 與 timeout。
  2. 不啟用尚未驗證依賴的 pool 參數。
  3. 把連接池優化作為獨立的程式碼變更與容量測試。

配置變更不僅會改變數值，也可能改變 Spring Boot 的條件裝配結果。這點必須納入評審清單。

為何滾動發布沒有把舊服務一併拖垮

在 Deployment 預設的滾動更新策略下，新 Pod 啟動失敗時，舊 Pod 通常會保留下來並繼續提供服務。這是好事，但也容易造成假象：

Deployment 有可用副本 ≠ 新版本发布成功

發布後必須同時檢查：

kubectl -n app rollout status deployment/<deployment> --timeout=10m
kubectl -n app get pod -l app=<application> -o wide
kubectl -n app get rs -l app=<application>
kubectl -n app logs <new-pod> --since=20m

如果舊 ReplicaSet 仍有副本、新 ReplicaSet 的 Pod 正在重啟，業務可能暫時可用，但發布已經失敗。

建議的滾動修復順序

  1. 備份目標 dataId 的原始內容與校驗值。
  2. 先選擇一個低風險的 Boot 2 服務，加入四個相容 key。
  3. 回讀 Nacos，確認 namespace、group、dataId 與內容。
  4. 滾動該 Deployment，並等待新 ReplicaSet 全部 Ready。
  5. 觸發一條真實的 Redis 讀寫路徑，而不是只檢查健康介面。
  6. 搜尋新 Pod 日誌中的 localhost:6379、連線異常與類別缺失。
  7. 驗證通過後，再按版本矩陣逐個處理其餘舊服務。

建議的日誌檢查：

kubectl -n app logs deployment/<deployment> --since=30m \
  | grep -Ei 'localhost:6379|RedisConnection|commons.pool2|GenericObjectPool'

同時需要檢查之前看似正常的 Boot 2 服務，因為它們可能只是尚未真正訪問 Redis。

完成定義

這次修復不能只以「Pod 不重啟」作為完成標誌。完成標準至少包括：

  • 所有使用 Redis 的服務都已確認 Spring Boot 版本。
  • Boot 2 服務均存在可解釋的應用級相容配置。
  • 新 Pod 全部來自目標 ReplicaSet，且 Ready。
  • 真實 Redis 業務路徑讀寫成功。
  • 目前與近期日誌不再出現 localhost:6379。
  • 未配置連接池的服務不會意外載入 pool 分支。
  • 每個相容別名都有升級與刪除條件。

最終結論

這次事故最關鍵的教訓不是「記住兩個 Redis 前綴」，而是配置中心治理必須連同用戶端版本一併考慮。

全局配置可以統一連線地址，但不能假設不同 Spring Boot 大版本擁有完全相同的綁定規則；Pod Ready 可以證明程式暫時可提供服務，但不能涵蓋延遲建連；一個看似普通的連接池參數，也可能改變自動配置路徑並引入新的執行期依賴。

更穩妥的治理方法是：先建立版本矩陣，以新屬性作為單一事實來源，在舊應用程式 dataId 中做最小相容，透過真實業務路徑驗證，最後隨着升級逐項刪除相容層。
