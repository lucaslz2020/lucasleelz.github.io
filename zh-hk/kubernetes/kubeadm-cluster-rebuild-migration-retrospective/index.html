由零開始搭建 Kubernetes v1.36.3：Rocky Linux 與 kubeadm 完整教學

由網絡規劃和 Rocky Linux 初始化開始，一步步建立 kubeadm 高可用叢集，安裝 kube-vip、Calico、指標、儲存與 Ingress，並完成叢集驗收。

本文來自一次真實遷移的復盤。節點、地址、網域、命名空間、業務數量和內部儲存庫資訊均已脫敏或泛化，範例不能直接用於生產環境。

系列導覽：Kubernetes 重建遷移教學系列。本篇的目標是由零建立一個健康的空叢集。

今次升級沒有在舊控制平面上連續執行多次 kubeadm upgrade，而是建立一套全新的 Kubernetes v1.36.3 叢集，再分階段遷移節點、數據、中介軟體、配置和業務。

以下不單止講結論，而是按照實際執行順序，由建立工作目錄開始，一直寫到業務切換完成。你可以把指令複製到自己的營運儲存庫，再替換所有 <...> 佔位符。

選擇重建而非原地升級，主要因為舊環境同時存在作業系統老化、節點用途混亂、固定 Service IP、歷史命名空間、網絡規則不一致和有狀態服務分散等問題。單單升級控制平面，只會把這些問題原封不動帶到新版本。

最終證明，遷移最難的部分不是令 Pod 顯示 Running，而是把以下整條鏈路全部打通：

节点
→ CNI / kube-proxy
→ PVC 与真实数据
→ Pod Ready
→ Service Endpoint
→ Service DNS / 服务注册
→ Gateway / Ingress
→ 登录与真实业务请求
→ 外部入口

遷移目標與最終形態

最終叢集採用：

  • Rocky Linux 10.2。
  • Kubernetes v1.36.3。
  • containerd，使用 systemd cgroup。
  • 三節點控制平面和 etcd。
  • kube-vip 提供 API 虛擬地址。
  • Calico 提供 Pod 網絡。
  • NGINX Ingress 三個副本。
  • NFS 動態儲存與少量本地 PersistentVolume。
  • metrics-server 提供節點和 Pod 指標。
  • Nacos 三節點叢集。
  • 按業務、數據、入口、監控、共享和預留用途劃分節點池。

網絡規劃在建立控制平面之前凍結。Pod CIDR、Service CIDR、節點網段三者不能重疊，應用也不能混淆這三類地址。

開始前：建立版本化工作目錄

不要把下載檔案、備份、臨時修補和最終清單散落在營運機的下載目錄。先建立一個獨立目錄：

mkdir -p cluster-migration/{inventory,backup,images,manifests,scripts,reports}
cd cluster-migration

git init
printf 'backup/\n*.key\n*.kubeconfig\n.env\n' > .gitignore

建議目錄結構如下：

cluster-migration/
├── inventory/       # 节点、服务、存储和域名清单
├── backup/          # 不进入 Git 的备份及校验值
├── images/          # 镜像和 digest 清单
├── manifests/       # kubeadm、CNI、存储和业务清单
├── scripts/         # 可重复执行的初始化与验证脚本
└── reports/         # 每个阶段的验收结果

再建立一個不提交到 Git 的 .env：

cat > .env <<'EOF'
K8S_VERSION=v1.36.3
API_VIP=<api-vip>
POD_CIDR=<pod-cidr>
SERVICE_CIDR=<service-cidr>
CONTROL_PLANE_1=<control-plane-1>
CONTROL_PLANE_2=<control-plane-2>
CONTROL_PLANE_3=<control-plane-3>
EOF

chmod 600 .env

本文不會給出真實地址。對於公開文件，可以使用 192.0.2.0/24、198.51.100.0/24 等專用文件網段；真實執行必須替換成自己的規劃。

第 1 步：把伺服器清單變成可驗證數據

不要只維護一張自由格式 Excel。至少額外導出一份 CSV：

hostname,ip,role,pool,cpu,memory_gib,disk_gib,local_data
cp-a,<node-ip>,control-plane,control-plane,8,32,100,false
worker-a,<node-ip>,worker,app-dev,8,32,100,false
data-a,<node-ip>,worker,data,16,64,500,true

先檢查 IP、主機名稱是否重複：

cut -d, -f1 inventory/nodes.csv | tail -n +2 | sort | uniq -d
cut -d, -f2 inventory/nodes.csv | tail -n +2 | sort | uniq -d

兩個指令都不應輸出任何內容。再核對節點池數量：

cut -d, -f4 inventory/nodes.csv | tail -n +2 | sort | uniq -c

這一步雖然簡單，卻能提早發現一台節點被寫入兩個業務池、預留節點被誤當數據節點等問題。

第 2 步：匯出舊叢集資源

先確認自己操作的是舊叢集：

kubectl config current-context
kubectl cluster-info
kubectl get nodes -o wide

然後分別匯出 namespaced 和 cluster-scoped 資源。生產環境建議用經過審核的腳本逐類匯出；下面只展示結構：

kubectl get deploy,statefulset,daemonset,job,cronjob -A -o yaml \
  > backup/workloads.yaml

kubectl get svc,ingress,configmap,pvc -A -o yaml \
  > backup/application-resources.yaml

kubectl get pv,storageclass,clusterrole,clusterrolebinding,crd -o yaml \
  > backup/cluster-resources.yaml

Secret 必須單獨處理：

umask 077
kubectl get secret -A -o yaml > backup/secrets.yaml

backup/secrets.yaml 不得提交到 Git，也不得透過聊天工具或一般檔案分享散佈。完成後對備份計算校驗值：

sha256sum backup/*.yaml > backup/SHA256SUMS

還要儲存副本數量，因為之後會把新叢集中的工作負載統一改成零副本：

kubectl get deployment,statefulset -A \
  -o custom-columns='KIND:.kind,NAMESPACE:.metadata.namespace,NAME:.metadata.name,REPLICAS:.spec.replicas' \
  > inventory/workload-replicas.txt

第 3 步：建立並驗證 etcd 快照

在控制平面節點上找到 etcd 憑證和 endpoint，再執行：

ETCDCTL_API=3 etcdctl snapshot save /backup/etcd-snapshot.db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=<etcd-ca> \
  --cert=<etcd-client-cert> \
  --key=<etcd-client-key>

ETCDCTL_API=3 etcdctl snapshot status /backup/etcd-snapshot.db \
  --write-out=table

把快照複製到獨立儲存，並在隔離主機上做一次 restore：

etcdutl snapshot restore /backup/etcd-snapshot.db \
  --data-dir /var/lib/etcd-restore-test

還原目錄能成功建立、member 資訊可讀取，才表示快照至少具備基本可還原性。正式演練還應啟動隔離的 etcd 和 API Server 來驗證物件。

第 4 步：製作統一節點初始化腳本

不要在每台節點上手動輸入指令。建立 scripts/prepare-node.sh，腳本至少完成：

#!/usr/bin/env bash
set -euo pipefail

swapoff -a
sed -ri '/\sswap\s/s/^#?/#/' /etc/fstab

cat >/etc/modules-load.d/kubernetes.conf <<'EOF'
overlay
br_netfilter
EOF

modprobe overlay
modprobe br_netfilter

cat >/etc/sysctl.d/99-kubernetes.conf <<'EOF'
net.bridge.bridge-nf-call-iptables=1
net.bridge.bridge-nf-call-ip6tables=1
net.ipv4.ip_forward=1
EOF

sysctl --system
systemctl enable --now containerd
systemctl enable kubelet

containerd 配置產生後，確認：

containerd config dump | grep -E 'SystemdCgroup|sandbox_image'
crictl info

預期 SystemdCgroup=true，pause 映像應來自你已經驗證過可拉取的儲存庫。

第 5 步：在加入叢集前完成防火牆

在所有節點放行規劃好的 Pod CIDR：

firewall-cmd --permanent --zone=trusted --add-source=<pod-cidr>
firewall-cmd --reload
firewall-cmd --zone=trusted --query-source=<pod-cidr>

最後一個指令必須輸出 yes。再把結果寫入報告：

hostname
firewall-cmd --zone=trusted --list-sources

不要貪方便長期關閉 firewalld。關閉防火牆看似能讓網絡快速恢復，卻會失去可稽核的安全邊界。

第 6 步：產生 kubeadm 配置並預先拉取映像

建立 manifests/kubeadm.yaml：

apiVersion: kubeadm.k8s.io/v1beta4
kind: ClusterConfiguration
kubernetesVersion: v1.36.3
controlPlaneEndpoint: <api-vip>:6443
imageRepository: <kubernetes-image-mirror>
networking:
  dnsDomain: cluster.local
  podSubnet: <pod-cidr>
  serviceSubnet: <service-cidr>
apiServer:
  certSANs:
    - <api-vip>
    - <api-dns-name>
    - <control-plane-1-ip>
    - <control-plane-2-ip>
    - <control-plane-3-ip>

在三台控制平面節點上預先拉取映像：

kubeadm config images list --config manifests/kubeadm.yaml
kubeadm config images pull --config manifests/kubeadm.yaml

如果這裡失敗，先解決映像儲存庫、DNS 和憑證問題，不要繼續執行 kubeadm init。

第 7 步：初始化第一台控制平面

在第一台控制平面執行：

sudo kubeadm init --config manifests/kubeadm.yaml --upload-certs \
  | tee reports/kubeadm-init.log

初始化成功後，儲存輸出中的兩條 kubeadm join 指令。它們分別用於控制平面和工作節點，包含短期有效的 token，不能提交到 Git。

為目前管理員配置 kubeconfig：

mkdir -p "$HOME/.kube"
sudo install -m 600 /etc/kubernetes/admin.conf "$HOME/.kube/config"
sudo chown "$(id -u):$(id -g)" "$HOME/.kube/config"

kubectl get nodes
kubectl get pods -A

此時第一台節點通常處於 NotReady，CoreDNS 也可能處於 Pending。這是因為 CNI 尚未安裝，不要把它誤判為 kubeadm 失敗。

第 8 步：部署 API 高可用虛擬地址

三節點控制平面不能讓用戶端固定連線某一台節點。本文使用 kube-vip 的 Static Pod 模式提供 <api-vip>。

先在第一台控制平面節點上產生 manifest。映像版本必須在遷移前固定，並完成映像掃描：

export VIP=<api-vip>
export INTERFACE=<node-interface>
export KVVERSION=<approved-kube-vip-version>

sudo ctr image pull <kube-vip-image>:${KVVERSION}
sudo ctr run --rm --net-host <kube-vip-image>:${KVVERSION} vip /kube-vip manifest pod \
  --interface "$INTERFACE" \
  --address "$VIP" \
  --controlplane \
  --services \
  --arp \
  --leaderElection \
  | sudo tee /etc/kubernetes/manifests/kube-vip.yaml >/dev/null

檢查虛擬地址和 API：

ip address show dev <node-interface>
curl --cacert /etc/kubernetes/pki/ca.crt https://<api-vip>:6443/readyz

預期 /readyz 返回 ok。如果沒有 VIP，先查 kubelet 日誌和 Static Pod：

sudo crictl ps -a --name kube-vip
sudo journalctl -u kubelet -n 100 --no-pager

第 9 步：安裝 Calico，讓節點真正 Ready

把經過審核、版本固定的 Calico 清單儲存到 manifests/calico.yaml。安裝前確認其中的地址池與 kubeadm 的 <pod-cidr> 完全一致：

grep -n '<pod-cidr>' manifests/calico.yaml
kubectl apply -f manifests/calico.yaml
kubectl -n kube-system rollout status daemonset/calico-node --timeout=10m
kubectl get nodes

所有節點應逐步進入 Ready，CoreDNS 也應進入 Running。繼續做一次 DNS 測試：

kubectl run dns-check --image=<approved-busybox-image> --restart=Never \
  --command -- nslookup kubernetes.default.svc.cluster.local
kubectl logs dns-check
kubectl delete pod dns-check

只看見 Calico Pod 在執行還不夠。至少再建立兩個位於不同節點的測試 Pod，互相存取 Pod IP，並存取一個 ClusterIP Service，證明跨節點路由和 Service 轉發都正常。

第 10 步：加入其餘控制平面和工作節點

先加入另外兩台控制平面節點，再加入工作節點。控制平面指令形如：

sudo kubeadm join <api-vip>:6443 \
  --token <bootstrap-token> \
  --discovery-token-ca-cert-hash sha256:<ca-hash> \
  --control-plane \
  --certificate-key <certificate-key>

工作節點不帶最後兩項：

sudo kubeadm join <api-vip>:6443 \
  --token <bootstrap-token> \
  --discovery-token-ca-cert-hash sha256:<ca-hash>

token 失效後，在現有控制平面節點上重新產生：

kubeadm token create --print-join-command
sudo kubeadm init phase upload-certs --upload-certs

全部加入後檢查控制平面和 etcd Static Pod 是否平均分佈：

kubectl get nodes -o wide
kubectl -n kube-system get pods -o wide | grep -E 'kube-apiserver|etcd'
kubectl get --raw='/readyz?verbose'

第 11 步：安裝指標、儲存和 Ingress

基礎元件的安裝順序建議固定為：

metrics-server → StorageClass → 动态制备器 → Ingress Controller

每安裝一個元件就完成一次小驗收，不要一次過執行 kubectl apply -f manifests/：

kubectl apply -f manifests/metrics-server.yaml
kubectl -n kube-system rollout status deployment/metrics-server --timeout=5m
kubectl top nodes

kubectl apply -f manifests/storage/
kubectl get storageclass

kubectl apply -f manifests/ingress-nginx/
kubectl -n ingress-nginx rollout status deployment/ingress-nginx-controller --timeout=10m

儲存必須用臨時 PVC 做讀寫測試，Ingress 必須用臨時網域做 Host 路由測試。詳細清單放在本系列的「基礎元件篇」，不要單憑 Pod 處於 Running 就進入業務遷移。

第 12 步：完成叢集級驗收

建立 reports/cluster-baseline.txt，記錄以下指令輸出：

kubectl get nodes -o wide
kubectl get pods -A -o wide
kubectl get storageclass
kubectl top nodes
kubectl get ingressclass
kubectl get --raw='/readyz?verbose'

到這裡，新的空叢集才算搭建完成。接下來按專題繼續：

  • 基礎元件：Calico、metrics-server、Ingress 和 NFS 的逐項部署與驗收。
  • 節點排程：標籤、污點、親和性和數據服務反親和性。
  • 業務遷移：零副本預先部署、數據還原、分批放量、入口切換和回滾。
  • Nacos：三節點叢集搭建、Service DNS 治理和平滑升級。

復盤：為何第一步不是安裝，而是盤點

遷移前先建立伺服器與工作負載清單。每台節點至少記錄：

  • 虛擬化宿主機和虛擬機器識別碼。
  • IP、主機名稱、CPU、記憶體和磁碟。
  • 是否承載本機磁碟、資料庫、Ingress、代理或控制平面。
  • 舊主機名稱到新主機名稱的對應。
  • 目標節點池、標籤、污點和容忍關係。

舊叢集則要單獨匯出：

  • Deployment、StatefulSet、DaemonSet、CronJob。
  • Service、Ingress、Endpoint、ConfigMap、Secret。
  • PVC、PV、StorageClass 和本機目錄。
  • RBAC、CRD 和叢集級資源。
  • 各工作負載目前的副本數量和 CronJob suspend 狀態。

只儲存 YAML 還不夠。還原時最容易失去的是「執行狀態」和「數據實際在哪裡」。因此副本數量、節點親和性、儲存位置和數據校驗必須另行記錄。

備份必須證明能還原

重裝節點前完成三類備份：

  1. etcd snapshot。
  2. Kubernetes 全量資源封存。
  3. 資料庫、訊息系統、NFS 和 hostPath 數據備份。

最低限度的校驗包括：

etcdctl snapshot status /backup/etcd-snapshot.db --write-out=table
tar -tzf /backup/kubernetes-resources.tgz | head
sha256sum /backup/* > /backup/SHA256SUMS

真正可靠的做法是在隔離環境執行一次 etcd restore，並對資料庫做抽樣還原。snapshot status 正常只能證明檔案可讀，不能證明還原流程完整。

作業系統基線要先於 kubeadm

所有節點統一使用同一份版本化初始化腳本：

swapoff -a
modprobe overlay
modprobe br_netfilter
sysctl --system

systemctl enable --now containerd
systemctl enable kubelet

containerd 統一使用：

SystemdCgroup = true

同時啟用橋接流量和 IPv4 轉發：

net.bridge.bridge-nf-call-iptables=1
net.bridge.bridge-nf-call-ip6tables=1
net.ipv4.ip_forward=1

今次最典型的網絡故障來自 firewalld：Nacos 返回的 Pod IP 健康，但跨節點用戶端存取時出現 No route to host。原因不是 Nacos，而是節點沒有信任 Calico Pod CIDR。

正確做法是在 kubeadm 之前把 <pod-cidr> 永久加入信任區域，並在 Calico 安裝後用一次性 DaemonSet 對所有節點再校準。不能等業務啟動後逐台補規則。

對於仍使用 hostNetwork 的數據服務，還要單獨驗證目標節點連接埠是否允許來自 Pod SNAT 後的流量。長期方案應是減少 hostNetwork，透過一般 Pod 網絡和 Service 暴露服務。

控制平面與基礎元件

高可用控制平面使用三個節點。kubeadm 配置中的版本、API VIP、Pod CIDR、Service CIDR 和 DNS 網域一旦凍結，就不應在業務遷移過程中修改。

apiVersion: kubeadm.k8s.io/v1beta4
kind: ClusterConfiguration
kubernetesVersion: v1.36.3
controlPlaneEndpoint: <api-vip>:6443
networking:
  dnsDomain: cluster.local
  podSubnet: <pod-cidr>
  serviceSubnet: <service-cidr>

控制平面完成後按順序安裝：

  1. Calico。
  2. NFS provisioner。
  3. metrics-server。
  4. NGINX Ingress。
  5. 日誌、監控和必要系統元件。

營運機的 kubectl 應與 API Server 保持官方支援的版本偏差。Kubernetes 文件規定，kubectl 與 kube-apiserver 的版本差只能在一個 minor 版本以內。參見 Version Skew Policy。

節點池解決的不是整齊，而是故障邊界

節點劃分為控制平面、入口、平台基礎服務、業務、數據、監控、共享和預留池。排程策略同時使用：

  • nodeSelector 指定目標池。
  • 污點阻止未獲授權的工作負載進入專用池。
  • toleration 允許對應工作負載排程。
  • required Pod Anti-Affinity 分散 Kafka、Zookeeper、Nacos 等副本。

一個常見錯誤是只加標籤，不加污點。這樣「指定了節點池」的業務看起來正常，但沒有 nodeSelector 的其他 Pod 仍會落到專用節點。另一個錯誤是先加污點、後補 toleration，結果造成大量 Pod Pending。

標籤、污點和 toleration 必須在 Git 中成對產生並提前 dry-run。

資源先落地，副本保持為零

舊物件不能原樣匯入。需要移除：

  • uid
  • resourceVersion
  • managedFields
  • creationTimestamp
  • status
  • 自動產生的 ServiceAccount Token
  • Helm release Secret
  • 舊叢集管理平台的標籤和資源

Service、Ingress、ConfigMap、Secret、PVC 等先建立；Deployment 和 StatefulSet 初始副本設為 0；CronJob 先 suspend。

這一步可以提早發現：

  • YAML 與新 API 不相容。
  • 固定 ClusterIP 衝突。
  • PVC 無法綁定。
  • 映像不存在或拉取憑證缺失。
  • Service selector 與 Pod label 不相配。
  • 節點標籤和容忍配置不完整。

有狀態服務必須逐層還原

啟動順序固定為：

存储与 PVC
→ MySQL / MongoDB / Redis / RabbitMQ / Zookeeper
→ Kafka
→ PostgreSQL 与辅助服务
→ Nacos
→ 平台依赖
→ 业务服务

不能因為建立了同名空庫，就當作遷移完成。至少要驗證資料表、權限、關鍵列數、索引和真實應用帳號查詢。

Redis 的排查則分成四層：

redis-cli PING
→ Pod Endpoint
→ ClusterIP
→ Service DNS
→ 真实应用接口

如果 Endpoint 正常而 ClusterIP 失敗，優先檢查請求來源節點的 kube-proxy；重啟業務 Pod 或修改 Nacos 都不會修復 Service 轉發表。

Nacos：程序啟動不等於註冊中心可用

Nacos 使用三個 StatefulSet Pod。Headless Service 為每個成員提供穩定 DNS，一般 ClusterIP Service 為用戶端提供統一入口。

nacos-0.nacos-hs.platform.svc.cluster.local
nacos-1.nacos-hs.platform.svc.cluster.local
nacos-2.nacos-hs.platform.svc.cluster.local

nacos-cs.platform.svc.cluster.local:8848

遷移時曾出現這樣的問題：Nacos 日誌顯示啟動成功，但用戶端仍無法註冊。最終發現執行模式開關與 gRPC 註冊不相容。修復後按三層驗收：

  1. 三個 Pod Ready，三個成員全部健康。
  2. 三個節點執行模式一致。
  3. 同一個測試用戶端在三個節點的執行個體清單中都可見。

只有這三層通過，才能繼續啟動 OAuth、閘道和業務服務。

從固定 IP 遷移到 Service DNS

舊配置中大量內部服務使用 ClusterIP：

rbac.api.url=http://<cluster-ip>:8082
spring.data.redis.host=<cluster-ip>

遷移後改為：

rbac.api.url=http://rbac-api.app-test.svc.cluster.local:8082
spring.data.redis.host=redis-service.app-test.svc.cluster.local

但不能用正則表達式把所有 IP 都替換為 DNS：

  • 已刪除的 Service 沒有可替換目標。
  • Kafka advertised listener 需要單獨設計。
  • 外部資料庫、短訊和專網地址不是 Kubernetes Service。
  • 少量 Jenkins 或入口依賴可暫時保留固定 ClusterIP，但必須進入白名單並寫入 Git。

Pod Running 只是驗收起點

業務按命名空間逐批啟動。每批至少檢查：

kubectl -n <namespace> get deployment,statefulset,pod
kubectl -n <namespace> get svc,endpointslice
kubectl -n <namespace> get event --sort-by=.lastTimestamp

然後執行真實請求：

  • 登入與 token 重新整理。
  • 用戶、角色和權限。
  • Redis Session。
  • 檔案上傳下載。
  • RabbitMQ 與 Kafka 生產消費。
  • 資料庫讀寫。
  • WebSocket 建立連線。
  • CI/CD 發布介面。

未登入介面返回「未登入」，只能證明入口到業務服務的鏈路可達，不能替代登入後的業務驗證。

今次最有價值的故障模式

現象根因正確處理
服務註冊為空Nacos 執行模式或用戶端註冊失敗查三個節點的執行個體清單，不要只看啟動日誌
Pod IP 跨節點不可達firewalld 未信任 Pod CIDR全節點固化規則並做跨節點測試
Endpoint 正常、ClusterIP 逾時單節點 kube-proxy 規則異常只處理故障來源節點的 kube-proxy
Redis 正常但應用逾時Service 地址過期或 hostNetwork 連接埠被拒絕分層驗證 Endpoint、Service 和防火牆
指標為空metrics-server 無法存取 kubelet驗證網絡路徑，必要時使用 hostNetwork
叢集內 200、公網失敗外層路由或 SNI 未配置修改入口層，不要反覆重啟業務 Pod
Job Pending仍綁定舊主機名稱或缺少 toleration同步修改 selector、PV affinity 和 toleration

回滾必須在遷移前設計

回滾分為四層：

  1. 入口回滾：還原舊路由、VIP 或 DNS。
  2. 物件回滾：從資源封存還原 Service、Ingress、RBAC、PVC/PV。
  3. 配置回滾：按 Nacos 的 namespace、group、dataId 精確回滾。
  4. 數據回滾：使用資料庫備份、binlog/WAL 和儲存快照還原。

一旦新環境開始接受寫入，回滾就不再只是切換入口。必須明確增量數據如何處理，避免新舊環境雙寫或數據倒退。

最終結論

重建式升級的價值，不只是獲得一個新版本叢集，而是順便清理舊系統累積的隱性依賴：固定 IP、未登記節點用途、無法還原的備份、混亂污點、失效路由和無法追蹤的手動配置。

真正可複用的原則只有四條：

  1. 所有設計在切換前凍結。
  2. 所有有狀態數據在重裝前證明能還原。
  3. 每個階段都有不可跳過的驗收門檻。
  4. 最終用真實業務請求定義完成，而不是用 Pod 狀態定義完成。
