Kubernetes Service 存取失敗如何排查：由 DNS 到 kube-proxy 的完整鏈路

面對 Connection refused、No route to host、逾時與 Nacos 無可用實例，按 DNS、Service、Endpoint、Pod、CNI、kube-proxy 與防火牆逐層定位。

業務遷移中最容易誤判的一類問題，就是「應用程式日誌寫著 Nacos、Redis 或 Feign，所以故障一定出在 Nacos、Redis 或程式碼」。實際上，故障往往發生在 Service 轉發或跨節點網絡的環節。

系列導覽：Kubernetes 重建遷移教學系列。本篇可以作為遷移期間與日常值班的獨立排障手冊。

這篇文章提供一套固定的排障流程。遇到故障時，由上至下依序執行，不要一開始就重啟所有 Pod。

先按錯誤類型縮小範圍

錯誤常見含義
UnknownHostExceptionDNS 名稱不存在，或 CoreDNS 不可用
Connection refused已到達目標主機，但連接埠上沒有服務監聽，或流量被轉發到錯誤的連接埠
Connect timed out路由、防火牆、NetworkPolicy 或目標無回應
No route to host跨節點路由、防火牆或 CNI 網段不通
Load balancer does not have available server註冊中心沒有健康實例，或用戶端未正確訂閱
HTTP 404請求已到達某個 HTTP 服務，但 Host、Path 或 Gateway 路由不匹配

錯誤只是線索，不是結論。

第 1 層：確認用戶端實際使用的地址

進入出錯的 Pod，查看環境變數與實際生效的設定：

kubectl -n <namespace> exec <client-pod> -- env \
  | grep -Ei 'nacos|redis|gateway|service'

若設定來自 Nacos，還要回讀對應的 Data ID。不要只看 Git 裡的設定，因為執行階段可能被環境變數、啟動參數或遠端設定覆蓋。

第 2 層：驗證 DNS

kubectl -n <namespace> exec <client-pod> -- \
  getent hosts <service>.<namespace>.svc.cluster.local

若映像沒有除錯工具，啟動臨時診斷 Pod：

kubectl -n <namespace> run net-debug --rm -it --restart=Never \
  --image=<approved-network-tool-image> -- sh

DNS 失敗時檢查：

kubectl -n kube-system get deployment,pod -l k8s-app=kube-dns -o wide
kubectl -n kube-system logs deployment/coredns --tail=200
kubectl -n <namespace> get networkpolicy

第 3 層：檢查 Service 定義

kubectl -n <target-namespace> get service <service> -o yaml

核對：

  • selector 是否與目標 Pod 的 label 一致。
  • port 是否是用戶端存取的連接埠。
  • targetPort 是否指向容器實際監聽的連接埠，或正確的命名連接埠。
  • 是否誤用了舊叢集的 ClusterIP。

立即比對標籤：

kubectl -n <target-namespace> get pods --show-labels
kubectl -n <target-namespace> get pods -l '<service-selector>' -o wide

第 4 層：檢查 EndpointSlice

kubectl -n <target-namespace> get endpointslice \
  -l kubernetes.io/service-name=<service> -o yaml

如果沒有地址，問題通常是 selector 不匹配或 Pod 未 Ready。如果有地址但 conditions.ready: false，檢查 readiness probe。

記下一個 Ready Pod 的 IP 與連接埠，稍後再分別測試「直連 Pod」與「經由 Service」兩條路徑。

第 5 層：直連 Pod IP

從用戶端 Pod 執行：

kubectl -n <namespace> exec <client-pod> -- \
  nc -vz <target-pod-ip> <target-port>

結果判斷：

  • Pod IP 不通：優先查 CNI、節點路由、防火牆與 NetworkPolicy。
  • Pod IP 通、ClusterIP 不通：優先查 kube-proxy 或 Service 規則。
  • 兩者都通：繼續查應用程式協定、驗證、Gateway 或 Nacos 註冊數據。

第 6 層：在不同節點重複測試

Service 故障可能只發生在某個節點。查看用戶端所在的節點：

kubectl -n <namespace> get pod <client-pod> -o wide

分別在故障節點與健康節點啟動臨時 Pod，存取同一個 ClusterIP。如果只有一個節點失敗，問題範圍就縮小到該節點的 kube-proxy、CNI、iptables/nftables 或防火牆。

第 7 層：檢查 kube-proxy

kubectl -n kube-system get pods -l k8s-app=kube-proxy -o wide
kubectl -n kube-system logs <kube-proxy-pod-on-bad-node> --tail=200

比對 ConfigMap 與 kube-proxy 的執行模式：

kubectl -n kube-system get configmap kube-proxy -o yaml

只重啟故障節點上的 kube-proxy：

kubectl -n kube-system delete pod <kube-proxy-pod-on-bad-node>
kubectl -n kube-system get pod -l k8s-app=kube-proxy -o wide -w

刪除 DaemonSet 的 Pod 後，控制器會自動將其重建。不要在沒有證據時同時刪除所有節點的 kube-proxy。

第 8 層：檢查節點路由與防火牆

登入故障節點：

ip route
sudo firewall-cmd --get-active-zones
sudo firewall-cmd --zone=trusted --list-sources
sudo sysctl net.ipv4.ip_forward

Pod CIDR 應正確路由或納入信任區域，net.ipv4.ip_forward 應為 1。

在 Calico 環境中繼續檢查：

kubectl -n kube-system get pod -l k8s-app=calico-node -o wide
kubectl -n kube-system logs <calico-pod-on-bad-node> -c calico-node --tail=200

第 9 層：最後再看 Nacos 與應用程式

如果網絡層全部正常，但用戶端仍提示沒有可用服務，檢查 Nacos 中的以下項目：

  • namespace、group 與 cluster 是否一致。
  • 服務名稱的大小寫與前綴是否一致。
  • 實例 IP 是否仍是舊叢集的 Pod IP。
  • 實例的健康狀態與 ephemeral 狀態是否正常。
  • 用戶端是否誤啟用了雙寫或相容模式。

從目標應用程式 Pod 內部直接存取相依服務的健康檢查地址，會比在營運主機上存取更具參考價值。

用對照實驗避免誤判

最有效的排障表是：

測試位置Pod IPClusterIPService DNS結果
故障節點 Pod<pod-ip><service-ip><service-fqdn>記錄
健康節點 Pod<pod-ip><service-ip><service-fqdn>記錄
目標 Pod 本機localhost不適用不適用記錄

這張表能快速判斷問題是出在應用程式連接埠、跨節點 CNI，還是 Service 轉發。

修復後的驗收

kubectl -n <namespace> exec <client-pod> -- \
  curl -fsS http://<service>.<target-namespace>.svc.cluster.local:<port>/<health-path>

kubectl -n <namespace> logs <client-pod> --since=10m \
  | grep -Ei 'refused|timed out|no route|available server'

再執行一筆真實的業務請求。網絡指令恢復正常只是第一層證據，最終必須驗證 Gateway、登入、查詢或訊息消費等真實鏈路。

最終原則

DNS → Service → EndpointSlice → Pod 端口 → 跨节点网络 → kube-proxy → 防火墙 → 注册中心 → 业务

照固定順序排障的價值，在於每一步都能排除一整層。重啟所有 Pod 或許能讓症狀暫時消失，卻無法定位故障原因，也無法防止下次節點漂移後問題再次發生。
