ZooKeeper 每個 Pod 接近 2G：從固定 Heap 到 Kubernetes 資源縮減

透過 JVM 參數、mntr、快照與 Kubernetes requests 拆解 ZooKeeper Pod 記憶體偏高的原因，並提供分階段縮容、監控、滾動驗證與持久化遷移方案。

本文來自一個三節點 ZooKeeper 叢集的資源治理。命名空間、節點、業務名稱與容量已泛化；參數只能作為同量級負載的起點，不能直接搬到生產環境。系列導覽：Kubernetes 重建遷移教學系列。

一個三節點 ZooKeeper 叢集長期呈現以下資源狀態：

指標節點 A節點 B節點 C
Pod 記憶體約 1.8 GiB約 1.8 GiB約 1.4 GiB
CPU約 10m約 9m約 11m
memory request2 GiB2 GiB2 GiB
memory limit3 GiB3 GiB3 GiB
重啟次數000

乍看之下很像記憶體洩漏：CPU 很低，三個 Pod 卻佔用了接近 5 GiB。但繼續檢查發現，業務數據只有約 1.2 MiB，連線數與 watch 數也很低。

真正的問題不是 ZooKeeper 保存了幾 GiB 數據，而是 JVM 被配置成固定 2 GiB 的 Heap，Chart 又透過資源預設為每個 Pod 申請了 2 GiB 記憶體。

先建立判斷鏈路

重點是先分清「Heap 上限大」、「Heap 已提交」與「業務存活物件多」三種情況；單憑 kubectl top 無法分辨。

第 1 步：讀取運行中的真實 JVM 參數

不要只看 Helm values。先檢查容器內的 Java 程式：

kubectl -n infra exec zookeeper-0 -- \
  sh -c 'tr "\0" " " < /proc/1/cmdline'

今次看到的關鍵片段是：

-Xmx1000m -Xmx2048m -Xms2048m

重複的 -Xmx 不會相加，HotSpot 通常採用最後出現的值。因此有效配置是：

Xms = 2048 MiB
Xmx = 2048 MiB

前一個 -Xmx1000m 來自映像指令碼的預設值，後一個 -Xmx2048m 與 -Xms2048m 來自 Chart 的 heapSize。這說明：

  • 預設值沒有真正限制住 Heap。
  • Heap 從啟動開始便以 2 GiB 的固定大小提交。
  • 三個節點的理論固定 Heap 預算已達 6 GiB。

重複參數本身不會形成 3 GiB Heap，也不是洩漏的證據，但會令只檢查環境變數的人得出錯誤結論。

第 2 步：區分 RSS、Committed Heap 與 Live Data

ZooKeeper Pod 的記憶體可以粗略理解為：

Pod working set
≈ JVM committed heap
+ Metaspace / Code Cache / GC structures
+ thread stacks / direct buffers / native libraries
+ process working-set file pages

Xms=2g 不代表程式在啟動瞬間一定佔滿 2 GiB RSS，但 JVM 在運行與 GC 過程中會逐步觸碰已提交的記憶體頁。即使存活物件很少，作業系統看到的 working set 也可能長期接近固定 Heap 大小。

因此，以下兩個判斷都不成立：

Pod RSS 接近 2 GiB，所以 ZooKeeper 一定存了 2 GiB 数据
数据只有 1 MiB，所以 Pod RSS 应该只有几十 MiB

業務數據規模是決定 Heap 需求的重要輸入，但不能直接等同於 Pod 總記憶體。

第 3 步：用 mntr 判斷真實負載

ZooKeeper 的四字命令必須在伺服器端白名單放行。啟用前應評估安全邊界，避免把管理介面暴露到不可信網絡。ZooKeeper 管理指南已經建議新系統優先使用 AdminServer；這裡保留 mntr，是為了與現有叢集的收集方式保持一致。

在容許 mntr 的環境中，可以執行：

kubectl -n infra exec zookeeper-0 -- \
  sh -c 'printf "mntr\n" | nc 127.0.0.1 2181'

重點收集：

zk_server_state
zk_znode_count
zk_approximate_data_size
zk_num_alive_connections
zk_outstanding_requests
zk_avg_latency
zk_max_latency
zk_watch_count
zk_ephemerals_count
zk_open_file_descriptor_count
zk_max_file_descriptor_count

今次去識別化後的數據量級是：

指標觀測值解釋
znode 數約 22,000規模較小
approximate data size約 1.2 MiB業務數據遠小於固定 Heap
全局 Session約 40用戶端壓力低
單節點存活連線10–20連線壓力低
watch 數10–20不存在 watch 風暴
outstanding requests0沒有請求排隊
平均延遲低於 1 ms當前效能餘量充足
單個快照約 3 MiB與數據量級一致

這些證據更支援「Heap 配置過大」這個判斷，而不是「業務物件正在無限增長」。

第 4 步：檢查交易日誌與快照

繼續檢查 ZooKeeper 數據目錄：

kubectl -n infra exec zookeeper-0 -- \
  sh -c 'du -sh /bitnami/zookeeper/data /bitnami/zookeeper/logs 2>/dev/null'

交易日誌可能使用預先分配的檔案。看到幾十 MiB 的日誌檔，並不代表其中每個位元組都是有效業務數據，也不能直接作為 Heap 大小的依據。

同時確認：

  • snapCount。
  • autopurge.snapRetainCount。
  • autopurge.purgeInterval。
  • 數據目錄是否位於 PVC。
  • 三個節點的快照與交易日誌是否持續增長。

今次自動清理已經啟用，快照亦很小，因此沒有證據支援立即調整 snapCount 或清理頻率。效能調優只應調整有證據支援的參數。

第 5 步：把 Chart 資源預設改為明確預算

當前配置類似：

heapSize: 2048

resourcesPreset: large
resources: {}

resourcesPreset 適合快速部署，但不適合長期容量治理。它隱藏了實際的 request 與 limit，亦難以表達「CPU 很低、記憶體需要保留 JVM 餘量」這個真實模型。Bitnami ZooKeeper Chart同樣建議生產工作負載按實際場景調整 resources。

不要在沒有監控的情況下直接由 2 GiB Heap 降到 512 MiB。更穩妥的是兩階段收縮。

第一階段：先降到 1536 MiB

heapSize: 1536

resourcesPreset: none
resources:
  requests:
    cpu: 250m
    memory: 1792Mi
    ephemeral-storage: 256Mi
  limits:
    cpu: 1500m
    memory: 2560Mi
    ephemeral-storage: 1Gi

這個階段保留約 1 GiB 的容器級餘量，用來容納 JVM 非堆記憶體、執行緒、直接記憶體、共用程式庫與 working set 波動。

第二階段：穩定後再評估 1024 MiB

如果至少跨過一個完整業務高峰，且 GC、延遲、連線與選舉都穩定，可以繼續評估：

heapSize: 1024

resourcesPreset: none
resources:
  requests:
    cpu: 250m
    memory: 1280Mi
    ephemeral-storage: 256Mi
  limits:
    cpu: 1500m
    memory: 2Gi
    ephemeral-storage: 1Gi

三個副本在第一階段的 memory request 合計 5.25 GiB；進入第二階段後合計 3.75 GiB。CPU request 則由原本的 3 核降到 750m。實際節省應以排程器看到的 request 為準，而不是只看即時 kubectl top。

為什麼 Heap 不能頂到容器 limit

即使 ZooKeeper 的主要數據在 Java Heap 中，也必須為以下區域留出空間：

  • Metaspace 與 Compressed Class Space。
  • JIT Code Cache。
  • GC remembered set 與其他本地結構。
  • NIO Direct Buffer。
  • 執行緒堆疊。
  • JNI 與壓縮程式庫。
  • 檔案頁與程式運行時。

如果設置：

Xmx = container memory limit

JVM Heap 尚未 OOM，容器就可能先被 cgroup 殺掉。為 1 GiB Heap 設定 2 GiB limit 不是浪費，而是先建立可驗證的安全邊界；觀察穩定後再決定是否繼續壓縮。

第 6 步：縮容前先補可觀測性

如果原配置關閉了 metrics，資源縮小後只能靠 kubectl top 猜測，風險很高。建議先開啟 ZooKeeper metrics exporter，並至少監控：

  • Pod working set 與 RSS。
  • JVM heap used、committed、max。
  • GC pause、次數與分配速率。
  • zk_outstanding_requests。
  • avg/max latency。
  • alive connections、watch、znode、ephemeral 數。
  • leader 變化與選舉時間。
  • 容器重啟、OOMKilled 與探針失敗。

警示不應只用「記憶體超過 80%」。更有意義的是組合判斷：

heap 持续高位
+ GC 频率升高
+ 请求延迟或 outstanding requests 增长

固定 Heap 的情況下，RSS 長期處於高位本來就可能是預期行為。

第 7 步：按 ZooKeeper 法定人數滾動

三節點叢集需要始終保持至少兩個健康成員。推薦流程：

  1. 備份 values、ZooKeeper 配置與關鍵數據。
  2. 確認三個成員的角色、連線與法定人數正常。
  3. 一次只更新一個 follower。
  4. 等待該 Pod Ready，並透過 ruok、stat、mntr 驗證。
  5. 觀察同步、延遲、GC 與連線恢復。
  6. 更新另一個 follower。
  7. 最後才處理 leader，或先確認 leader 已安全遷移。
  8. 跨過真實高峰後才進入第二階段。

每一步都應等待 StatefulSet 就緒：

kubectl -n infra rollout status statefulset/zookeeper --timeout=15m
kubectl -n infra get pod -l app.kubernetes.io/name=zookeeper -o wide

發生以下任何一種情況，應立即停止繼續滾動：

  • 成員無法加入 quorum。
  • 選舉頻繁發生。
  • GC 暫停明顯上升。
  • outstanding requests 持續非零並增長。
  • 業務端 Session 大量重建或逾時。

比記憶體更大的風險：數據目錄使用 emptyDir

今次檢查還發現，StatefulSet 沒有 volumeClaimTemplates，持久化開關已關閉，數據目錄實際使用 emptyDir。Bitnami Chart 的參數說明亦明確指出：persistence.enabled=false 時使用 emptyDir。

這代表：

  • 容器重啟但 Pod 未重建時，目錄可能仍然存在。
  • Pod 被重新排程、刪除或節點故障時，本地快照與交易日誌會遺失。
  • 單一節點可從其他成員重新同步，但不代表三個節點同時遺失後仍能還原。

三個副本不能取代持久化。副本解決運行時可用性，PVC 與備份解決可還原性。

ZooKeeper 更適合使用低延遲區塊儲存，例如 SSD StorageClass，而不是把高頻交易日誌放到一般 NFS 上。一個保守起點是每個 Pod 10 GiB PVC，再按交易量與保留策略調整：

persistence:
  enabled: true
  storageClass: ssd
  size: 10Gi

但這裡不能直接做一般滾動更新。StatefulSet 的 volumeClaimTemplates 涉及不可變欄位，通常需要另行設計遷移：

  1. 建立並驗證備份。
  2. 確認現有 ensemble 健康。
  3. 準備帶 PVC 的新 StatefulSet，或按 Chart 的升級要求重建。
  4. 一次遷移一個成員並等待重新同步。
  5. 驗證快照、交易日誌與故障還原。
  6. 保留明確的回滾窗口。

記憶體收縮與儲存遷移應該拆成兩次變更，否則出現問題時無法快速判斷是 JVM 容量還是數據目錄所導致。

不應順手修改的參數

當前證據沒有指向以下參數，因此不應為了「優化」而一併修改：

  • maxClientCnxns：當前連線數遠未達到限制。
  • snapCount：當前快照與交易壓力不高。
  • 自動清理週期：現有磁碟增長正常。
  • Tick、Session timeout：沒有 Session 抖動的證據。
  • 副本數：三節點是生產環境常用的最小 quorum。

一次只改變一個容量變數，才能在指標變化後判斷因果關係。

完成定義

ZooKeeper 記憶體優化完成，至少要滿足：

  • JVM 指令行中不存在無法解釋的重複 Heap 參數。
  • Heap、request 與 limit 形成明確的三層預算。
  • 三個成員在滾動期間始終保持 quorum。
  • 至少經過一個業務高峰，沒有明顯 GC 或延遲退化。
  • znode、Session、watch、連線與請求積壓均有監控。
  • OOMKilled、頻繁選舉與 Session 重建須有警示。
  • emptyDir 風險已有獨立的 SSD PVC 遷移計劃與還原演練。

最終結論

ZooKeeper Pod 接近 2 GiB 並不等於記憶體洩漏。固定 Xms=Xmx=2g、Chart 的大規格資源預設，以及 JVM 已提交頁被逐步觸碰，足以在很小的數據量下形成穩定的高 working set。

正確做法不是看到 CPU 低就一次過把記憶體砍半，而是先讀取真實指令行，用 mntr 與快照證明負載規模，明確定義 requests/limits，再透過 1536 MiB 到 1024 MiB 的兩階段滾動驗證，逐步釋放資源。

而檢查中暴露的 emptyDir 才是更值得優先列入風險清單的問題：資源過配浪費容量，沒有持久化則可能在故障時失去還原基礎。
