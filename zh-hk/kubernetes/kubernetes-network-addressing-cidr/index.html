Kubernetes 中的 Pod CIDR、Service CIDR 與節點網段到底是甚麼

從數據封包的實際流向出發，解釋 Node IP、Pod IP、Service ClusterIP 和 DNS 的關係，並提供地址規劃、衝突檢查、遷移與驗證方法。

系列導覽：Kubernetes 重建遷移教學系列。本文中的地址均使用 <...> 佔位符，不含真實網絡資訊。

同一個 Kubernetes 叢集同時出現多段 IP，並不代表網絡混亂。節點、Pod 和 Service 本來就承擔不同職責，真正要問的是：地址段是否互不重疊、元件配置是否一致、應用程式是否誤用了某個臨時 IP。

先看一次請求經過哪裏

flowchart LR
  A["用戶端 Pod"] --> B["Service DNS"]
  B --> C["ClusterIP"]
  C --> D["kube-proxy 或 eBPF Service 轉發"]
  D --> E["EndpointSlice"]
  E --> F["目標 Pod IP"]
  F --> G["目標節點"]

這裡至少有四類地址：

地址由誰分配是否直接綁定程式主要用途
Node IP實體網絡、虛擬化平台或雲端平台是節點管理、跨節點承載
Pod IPCNI，例如 Calico是Pod 到 Pod 通訊
Service ClusterIPkube-apiserver否穩定虛擬入口與負載轉發
外部入口 IPLB、VIP、Ingress 或路由器視乎實作而定叢集外存取

Kubernetes 官方網絡模型要求 Node、Pod 和 Service 使用互不重疊的地址範圍。Service 只是邏輯入口，後端由 EndpointSlice 持續更新。Cluster Networking 和 Service 對此有完整定義。

Node IP：數據封包最終要到達的機器

kubectl get nodes -o wide
kubectl get node <node> -o jsonpath='{.status.addresses}'

Node IP 來自現有的基礎網絡。Calico、kubelet、API Server、儲存掛載和日常運維 SSH 都可能用到它。

規劃時記錄：

  • 節點管理地址段。
  • 預設閘道和 MTU。
  • 實體機或虛擬化主機的故障域。
  • 防火牆允許的 Pod 地址段。
  • VPN、辦公室網絡或專線是否有重疊。

不要為了「統一」把 Node IP 併入 Pod CIDR。它們位於不同網絡層。

Pod CIDR：CNI 分配給工作負載的地址

Pod CIDR 在 kubeadm 中常寫為：

networking:
  podSubnet: <pod-cidr>

Calico 也必須使用相同的地址池：

kubectl get ippools.crd.projectcalico.org -o wide
kubectl get pod -A -o wide

每個普通 Pod 都會獲得一個 Pod IP。Pod 重建後 IP 可能改變，因此：

  • 不能把 Pod IP 寫入 Nacos 配置。
  • 不能讓用戶端儲存任何 Pod IP。
  • 應透過 Service 或 Headless Service 發現後端。

跨節點 Pod IP 不通時，應優先檢查 CNI 路由、封裝模式、MTU 和 firewalld，而不是修改 Service DNS。

Service CIDR：沒有網絡卡的虛擬地址池

Service CIDR 在 kubeadm 中常寫為：

networking:
  serviceSubnet: <service-cidr>

ClusterIP 不會像 Node IP 一樣出現在某張網絡卡上。kube-proxy 的 iptables、IPVS，或 CNI 的 eBPF 資料面負責將它轉發到 Endpoint。

kubectl get service -A -o wide
kubectl get endpointslice -A

Service CIDR 只應在叢集內部使用。應用程式應配置 DNS：

<service>.<namespace>.svc.cluster.local

而不是：

<cluster-ip>

Service 刪除重建後 ClusterIP 可能變化，只要 Service 名稱和 namespace 不變，DNS 名稱仍然有效。

CoreDNS 沒有建立第四套業務網絡

CoreDNS 監聽 Kubernetes API，為 Service 和 Pod 產生 DNS 記錄。普通 ClusterIP Service 的 DNS 最終解析為 ClusterIP；Headless Service 則返回後端 Pod IP。

kubectl run dns-check --rm -it --restart=Never \
  --image=<approved-dns-image> -- \
  nslookup <service>.<namespace>.svc.cluster.local

DNS 正常只證明名稱可以解析，不代表：

  • Service selector 正確。
  • Endpoint 非空。
  • 目標連接埠正在監聽。
  • kube-proxy 轉發表正確。

因此還要繼續檢查：

kubectl -n <namespace> get service <service> -o yaml
kubectl -n <namespace> get endpointslice \
  -l kubernetes.io/service-name=<service> -o wide

為甚麼不能把三類 IP 統一成一段

假設 Node、Pod 和 Service 使用重疊範圍，一個目標地址可能同時被理解為：

  • 本地二層網絡中的某台伺服器。
  • 需要交給 Calico 的遠端 Pod。
  • 需要交給 kube-proxy 的虛擬 Service。

最終路由優先次序可能把流量送到錯誤介面，常見現象包括：

No route to host
connect timed out
某些节点能访问，某些节点不能访问
访问一个 Service 却命中另一台真实主机

「統一」應該指統一規劃和統一配置，而不是把所有用途塞進同一個 CIDR。

第 1 步：遷移前收集所有網絡

建立 network-plan.csv：

type,cidr,owner,purpose,changeable
node,<node-cidr>,network-team,node-management,false
pod,<pod-cidr>,kubernetes-team,calico,true
service,<service-cidr>,kubernetes-team,clusterip,true
vpn,<vpn-cidr>,network-team,remote-access,false

還要收集：

kubectl -n kube-system get configmap kubeadm-config -o yaml
kubectl get service -A -o json
kubectl get pod -A -o wide
ip route

第 2 步：檢查重疊

使用團隊認可的 IPAM 或 CIDR 工具檢查：

Pod CIDR ∩ Service CIDR = 空集
Pod CIDR ∩ Node CIDR = 空集
Service CIDR ∩ Node CIDR = 空集
三者 ∩ VPN/办公网/专线 = 空集

還要為未來擴容預留餘量。不能只按目前的 Pod 數量計算；滾動發布、Job、DaemonSet 和故障漂移都會暫時增加地址消耗。

第 3 步：凍結到版本化配置

至少固定：

manifests/kubeadm.yaml
manifests/calico.yaml
inventory/network-plan.csv
scripts/network-smoke.sh

在建立控制平面後臨時修改 Pod CIDR 或 Service CIDR，通常不是普通的配置變更，而是一次網絡遷移。不要在業務啟動期間嘗試「順手統一」。

第 4 步：執行四層冒煙測試

Pod 到 Pod

kubectl exec <source-pod> -- ping -c 3 <target-pod-ip>

Pod 到 ClusterIP

kubectl exec <source-pod> -- nc -vz <service-ip> <service-port>

Pod 到 Service DNS

kubectl exec <source-pod> -- \
  nc -vz <service>.<namespace>.svc.cluster.local <service-port>

叢集外到 Ingress

curl --resolve app.example.com:443:<ingress-address> \
  https://app.example.com/<health-path>

測試 Pod 要覆蓋不同節點，否則無法發現單一節點的 kube-proxy 或防火牆故障。

第 5 步：清理配置中的地址依賴

按以下規則處理：

發現的地址處理方式
Pod IP必須改為 Service
ClusterIP優先改為 Service DNS
Node IP + NodePort確認是否為必要的外部入口
Kafka broker 地址單獨處理 advertised listener
外部資料庫或專線保留並登記擁有者

不要盲目把所有 IPv4 字串替換成 .svc.cluster.local。

完成定義

  • Node、Pod、Service、VPN 和辦公室網絡地址段互不重疊。
  • kubeadm 與 CNI 使用相同的 Pod CIDR。
  • 所有節點都有正確的 Pod 路由和防火牆規則。
  • 跨節點 Pod、ClusterIP、Service DNS 和 Ingress 冒煙測試通過。
  • Kubernetes 內部的應用程式不再依賴 Pod IP。
  • 固定 ClusterIP 僅限於經過評審的相容白名單。

一個叢集存在多段 IP 是正常設計；真正應該統一的是網絡規劃、配置來源和驗證方法。
