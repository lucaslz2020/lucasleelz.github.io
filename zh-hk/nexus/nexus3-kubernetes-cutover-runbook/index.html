Nexus3 Kubernetes 遷移 Runbook：H2、PostgreSQL、探針與無感切換

將 Nexus2 遷移至 Nexus3 的流程拆解成可執行的 Kubernetes Runbook，涵蓋資源建立、Upgrade Wizard、H2 升級、Database Migrator、驗證與 VIP 回滾。

本文只保留通用執行邏輯。位址、節點、網域、容量與 Secret 均為佔位符，執行時必須按官方版本矩陣和自己的還原演練結果重新確認。

系列導覽：Kubernetes 重建遷移教學系列。本篇用於正式遷移窗口內的逐項執行與驗收。

上一篇文章說明了 Nexus2 → Nexus3 → PostgreSQL 的整體設計。這篇把遷移收斂成一份執行清單，重點是回答「每一步何時可以繼續」。

固定設計

遷移前先凍結以下決策：

  • Nexus2 已升級到官方支援的最終版本。
  • Nexus3 使用經驗證的中繼版本接收 Upgrade Wizard 數據。
  • Nexus3 在 H2 模式下升級到最終目標版本。
  • Database Migrator 與目標版本嚴格相符。
  • Nexus 與遷移器的 Java 版本符合目標版本要求。
  • Blob Store 使用獨立的持久卷，回收策略為 Retain。
  • PostgreSQL 使用獨立的資料庫、角色與 schema。
  • /nexus context path 保持不變。
  • 舊網域或 VIP 只在最終驗證後才切換。

不可跳過的順序

Nexus2 最终版与完整备份
→ Nexus3 中转版 H2
→ Upgrade Wizard + Finalize
→ Nexus3 目标版 H2
→ H2 备份与 Blob Store 恢复点
→ 停止 Nexus
→ Database Migrator
→ PostgreSQL VACUUM
→ Nexus3 目标版 PostgreSQL
→ Browse/Search 完成
→ 真实构建与上传
→ VIP/域名切换

不要在中繼版上提早遷移 PostgreSQL，也不要讓 Nexus 在資料庫遷移期間運行。

一、建立 Kubernetes 基礎資源

先建立：

  1. StorageClass、PV、PVC。
  2. 非敏感的 ConfigMap。
  3. Nexus Service。
  4. PostgreSQL 資料庫與 schema 初始化 Job。
  5. 資料庫 Secret。

Secret 用指令建立，不寫成 YAML 明文：

kubectl -n repository create secret generic nexus-db \
  --from-literal=username=nexus \
  --from-literal=password="$(openssl rand -base64 36)"

儲存驗收：

  • PVC 已 Bound。
  • PV 為 Retain。
  • 目標節點目錄容量充足。
  • Nexus 容器 UID/GID 有寫入權限。
  • Blob Store 與資料庫暫存檔的空間須分別評估。

二、以 H2 啟動中繼版 Nexus3

kubectl -n repository apply -f nexus3-migration.yaml
kubectl -n repository rollout status statefulset/nexus --timeout=15m

curl -fsS \
  http://<migration-address>:8081/nexus/service/rest/v1/status

啟動探針建議使用狀態介面，並為首次升級預留足夠時間：

startupProbe:
  httpGet:
    path: /nexus/service/rest/v1/status
    port: http
  periodSeconds: 10
  timeoutSeconds: 5
  failureThreshold: 60

如果探針回報 connection refused，先檢查 nexus.log，不要無止境地拉長等待時間。

三、執行 Nexus2 Upgrade Wizard

  1. 備份 Nexus2 程式與工作目錄。
  2. 在 Nexus2 建立 Upgrade Agent。
  3. 在 Nexus3 建立 Upgrade Capability。
  4. 遷移 repository content。
  5. 遷移 server configuration。
  6. 等待同步佇列歸零。
  7. 凍結上傳並停止 Nexus2。
  8. 執行 Finalize 與 Done。

Finalize 前必須確認：

  • Hosted 的最新製品存在。
  • Proxy 能重新拉取。
  • Group 成員與順序正確。
  • 用戶、角色與匿名存取正確。
  • 現代 URL 與需要相容的舊 URL 均可用。
  • 至少一次真實的 Maven 構建通過。

四、升級目標版本，繼續使用 H2

先建立 H2 官方備份並記錄 SHA256，同時備份 Blob Store：

sha256sum /backup/nexus-h2-* /backup/nexus-blob-* > /backup/SHA256SUMS

再升級 StatefulSet 映像。啟動後等待內部 schema 與 upgrade 任務全部完成，再重新產生 H2 還原點。

禁止在內部任務運行時重啟 Pod。

五、準備 PostgreSQL

CREATE ROLE nexus LOGIN PASSWORD '<random-password>';
CREATE DATABASE nexus OWNER nexus;

\connect nexus

CREATE SCHEMA nexus AUTHORIZATION nexus;
GRANT USAGE, CREATE ON SCHEMA nexus TO nexus;
ALTER ROLE nexus SET search_path TO nexus;

驗證應用角色可以：

  • 連線到資料庫。
  • 在目標 schema 中建立與刪除暫存資料表。
  • 使用預期的 search_path。

如果只做資料庫層級的授權、不授予 schema 的 USAGE 與 CREATE，遷移器仍然會失敗。

六、執行 Database Migrator

下載與 Nexus 目標版本相符的遷移器並驗證：

curl -fLO https://download.sonatype.com/nexus/nxrm3-migrator/nexus-db-migrator-<version>.jar
curl -fLO https://download.sonatype.com/nexus/nxrm3-migrator/nexus-db-migrator-<version>.jar.sha256

test "$(sha256sum nexus-db-migrator-<version>.jar | awk '{print $1}')" = \
  "$(cat nexus-db-migrator-<version>.jar.sha256)"

完全停止 Nexus：

kubectl -n repository scale statefulset/nexus --replicas=0
kubectl -n repository wait --for=delete pod/nexus-0 --timeout=180s

遷移器從受控的 Secret 讀取連線參數。若密碼包含 URL 保留字元，先進行 URL 編碼，也不要讓 JDBC URL 出現在日誌中。

繼續條件：

  • Job 狀態為 Complete。
  • 遷移摘要中的 skipped 為 0。
  • 沒有 failed、constraint、schema permission 或認證錯誤。
  • PostgreSQL 資料表、元件、資產與 Blob 引用數量與摘要一致。

遷移失敗時，不要直接對既有的目標 schema 重跑遷移器。先找出原因，再還原或重建一個已確認乾淨的空 schema。

七、整理 PostgreSQL 並啟動最終版本

Nexus 仍在停止狀態時執行：

VACUUM (FULL, ANALYZE);

然後讓最終的 StatefulSet 連線到 PostgreSQL：

env:
  - name: NEXUS_DATASTORE_NEXUS_JDBCURL
    value: jdbc:postgresql://postgresql.repository.svc.cluster.local:5432/nexus?currentSchema=nexus
  - name: NEXUS_DATASTORE_NEXUS_USERNAME
    value: nexus
  - name: NEXUS_DATASTORE_NEXUS_PASSWORD
    valueFrom:
      secretKeyRef:
        name: nexus-db
        key: password

啟動後等待：

  • Rebuild repository browse
  • Rebuild repository search

這些一次性任務完成前，不要重啟實例或切換流量。

八、驗證矩陣

運行時

  • Pod Ready，Restart 次數沒有增加。
  • 狀態介面正常。
  • 日誌沒有資料庫、Blob、索引錯誤。
  • Nexus 與 Java 版本符合計劃。

倉庫

  • Hosted releases 可下載。
  • Hosted snapshots 可下載。
  • Third-party 可下載。
  • Proxy 命中與未命中都成功。
  • Group 依成員順序解析。
  • Search 找得到已知元件。

權限

  • 用戶、角色與 Realm 正常。
  • 匿名下載符合預期。
  • Hosted 上傳權限正確。

用戶端

  • Maven 使用真實 settings 完整構建。
  • Jenkins 可下載依賴。
  • 使用臨時版本上傳並清理。
  • 需要保留的舊 /content/ URL 已驗證或重寫。

九、入口切換

切換前：

  • 舊 Nexus2 已停止。
  • 舊節點不再持有 VIP。
  • 新 Nexus3 已透過內部位址驗證。
  • 備份與回滾指令仍可使用。

切換後立即驗證狀態、下載、上傳與真實構建。任何時刻都不能讓兩台機器同時持有同一個 VIP。

回滾：

  1. 凍結新 Nexus3 的上傳。
  2. 從新節點移除 VIP。
  3. 確認 ARP 與路由已經收斂。
  4. 啟動舊 Nexus2。
  5. 還原舊入口。

十、憑證與備份收尾

  • 刪除只在遷移期間使用的 Secret。
  • 如果密碼可能進入日誌，輪換 PostgreSQL 角色與 Kubernetes Secret。
  • 兩邊的密碼必須同時更新。
  • 保留 Nexus2、兩個 H2 還原點、PostgreSQL 備份與 Blob Store 備份。
  • 經過穩定觀察與還原演練後，才能釋放舊伺服器。

社群版元件數量維護

對 Proxy 與 Hosted 分別設定策略：

  • Proxy：刪除長期未使用的快取元件。
  • Hosted：依發布與合規要求保留。
  • 清理前執行 PostgreSQL 備份。
  • 先軟刪除，觀察後再對 Blob Store 執行 Compact。

Usage Center 可能延遲更新，歷史峰值也不會立即下降。不要因為頁面短時間仍顯示舊數量而重複執行清理。

完成定義

迁移器无跳过
+ PostgreSQL 数据与 Blob 引用一致
+ Browse/Search 完成
+ 仓库和权限正确
+ Maven/Jenkins 下载上传通过
+ 入口切换成功
+ 回滚和备份仍可用

一份好的 Runbook 不追求「指令越多越專業」，而是讓每個不可逆步驟都有清晰的輸入、繼續條件與回滾邊界。
