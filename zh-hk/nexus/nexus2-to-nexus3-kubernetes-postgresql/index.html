ENGINEERING NOTE · 2026年7月12日

從 Nexus Repository 2 平滑遷移到 Nexus 3：Kubernetes、PostgreSQL 與 VIP 切換

完整記錄 Nexus2 到 Nexus3 的遷移路徑：官方 Upgrade Wizard、H2 版本升級、PostgreSQL 數據庫遷移、Kubernetes StatefulSet、舊路徑相容與 VIP 回滾。

2026年7月12日 12 分鐘閱讀
#Nexus #Kubernetes #PostgreSQL #Maven #DevOps
{ }

本文來自一次真實遷移。伺服器、地址、網域、倉庫數量、元件數量及企業配置均已脫敏。範例 Secret 與密碼均為佔位符。

系列導覽：Kubernetes 重建遷移教學系列。建議先完成「在 Kubernetes 從零開始部署 Nexus Repository 3」教學。

運行多年的 Nexus Repository 2，通常早已是 Maven、Jenkins、開發機與發布指令碼高度依賴的關鍵服務。真正的困難不是啟動 Nexus3，而是在不遺失製品、不破壞權限、不過度要求用戶端改動的前提下完成遷移。

這次遷移的最終目標：

  • 將 Nexus2 的倉庫、用戶、角色與配置遷入 Nexus3。
  • Nexus3 以單副本 StatefulSet 運行在 Kubernetes。
  • Blob Store 使用獨立持久卷。
  • 元數據從 H2 遷移到 PostgreSQL。
  • 保留原有網域、VIP、連接埠及 /nexus 上下文路徑。
  • 舊 Maven URL 在過渡期內繼續相容。
  • 遷移失敗時可以快速切回 Nexus2。

Sonatype 已於 2025 年 6 月 30 日停止維護 Nexus Repository 2，不再提供新功能與缺陷修復，並建議盡快遷移到 Nexus3。參見 Nexus Repository 2 Version Status。

最終遷移鏈路

最關鍵的設計是將遷移拆成兩個階段：

  1. Nexus2 → Nexus3，並繼續使用 H2。
  2. Nexus3 升級至目標版本後，再做 H2 → PostgreSQL。

不要將倉庫轉換、版本升級、數據庫遷移與流量切換混成一個步驟。

為什麼 Nexus2 數據目錄不能直接掛載給 Nexus3

Nexus3 重新設計了元件元數據與 Blob Store。Nexus2 的工作目錄並非 Nexus3 可直接讀取的數據卷。

正確路徑是：

  • 將 Nexus2 升級到官方支援的最終版本。
  • 使用 Nexus2 Upgrade Agent 與 Nexus3 Upgrade Capability。
  • 遷移倉庫內容與伺服器配置。
  • 待同步完成後執行 Finalize。

官方流程見 Upgrade from Nexus Repository 2。中轉版本與目標版本必須按執行時的官方升級矩陣確認，不能把某次成功的組合當作永久規則。

遷移前盤點

類別需要記錄
運行時Nexus、Java、作業系統、安裝目錄與工作目錄
倉庫Hosted、Proxy、Group、格式、遠端地址與成員順序
數據元件、資產、Blob 容量與 checksum 抽樣
權限用戶、角色、Realm、匿名存取
用戶端Maven settings、Jenkins Credential、上傳 URL
網絡網域、VIP、連接埠、上下文路徑、代理規則
任務清理、索引、備份任務
擴充外掛程式、指令碼、自訂 Realm

尤其要掃描 Nexus2 舊路徑：

/nexus/content/repositories/releases/
/nexus/content/groups/public/

Nexus3 的現代路徑通常是：

/nexus/repository/releases/
/nexus/repository/public/

若用戶端無法一次過全部修改，應在外層代理配置明確的重寫規則，並為舊路徑設定移除日期。

完整備份 Nexus2

至少保留：

  1. Nexus2 程式目錄。
  2. Nexus2 工作目錄。
  3. 倉庫儲存與校驗記錄。

凍結寫入後，執行檔案系統備份：

systemctl stop nexus

tar -C /opt -czf /backup/nexus2-program.tar.gz nexus-2
tar -C /data -czf /backup/nexus2-work.tar.gz sonatype-work
sha256sum /backup/nexus2-*.tar.gz > /backup/SHA256SUMS

若在運行中直接複製目錄，可能產生元數據與製品不一致的備份。

Kubernetes 中的儲存設計

Nexus 的 Blob Store 讀寫頻繁。今次使用獨立本地 PV，並設定：

apiVersion: v1
kind: PersistentVolume
metadata:
  name: nexus-data
spec:
  capacity:
    storage: <capacity>
  accessModes: [ReadWriteOnce]
  persistentVolumeReclaimPolicy: Retain
  storageClassName: nexus-local
  local:
    path: /data/nexus
  nodeAffinity:
    required:
      nodeSelectorTerms:
        - matchExpressions:
            - key: kubernetes.io/hostname
              operator: In
              values: [repo-node]

Retain 很重要：誤刪 StatefulSet 或 PVC 時，歷史製品不會隨之被自動銷毀。

本地 PV 會把 Pod 固定在特定節點，因此它不是高可用方案。對單副本社群版而言，這個取捨是以更清晰的故障邊界換取更低的儲存複雜度。

保持上下文路徑與健康檢查

為減少用戶端變更，繼續使用 /nexus：

application-port=8081
application-host=0.0.0.0
nexus-context-path=/nexus
nexus.datastore.enabled=true

探針使用狀態介面，而不是主頁 HTML：

startupProbe:
  httpGet:
    path: /nexus/service/rest/v1/status
    port: http
  failureThreshold: 60
  periodSeconds: 10
  timeoutSeconds: 5

首次升級與索引重建可能持續數分鐘。connection refused 只表示程式尚未監聽連接埠，真正原因要看 nexus.log。

Nexus2 → Nexus3 的正確順序

先讓 Nexus3 使用 H2：

  1. 建立 Upgrade Agent / Upgrade Capability。
  2. 建立連線並執行預檢查。
  3. 遷移 repository content。
  4. 遷移 server configuration。
  5. 等待同步佇列歸零。
  6. 凍結 Nexus2 上傳。
  7. 執行 Finalize 和 Done。

Finalize 前至少驗證 Hosted 最新版本、Proxy 拉取、Group 順序、匿名存取與真實 Maven 構建。

Upgrade Wizard 不是雙向同步系統。遷移開始後，不要繼續修改 Nexus2 的用戶、角色與倉庫結構。

先升級 H2，再遷 PostgreSQL

完成 Nexus2 遷移後，仍使用 H2 將 Nexus3 升級至目標版本。升級前同時備份 H2 與 Blob Store，確保兩者來自同一個還原點。

啟動新版本後，等待內部 schema、upgrade、browse 與 search 任務結束。Pod Ready 不等於升級任務完成，任務執行期間不要反覆重啟實例。

準備 PostgreSQL

CREATE ROLE nexus LOGIN PASSWORD '<random-password>';
CREATE DATABASE nexus OWNER nexus;

\connect nexus

CREATE SCHEMA nexus AUTHORIZATION nexus;
GRANT USAGE, CREATE ON SCHEMA nexus TO nexus;
ALTER ROLE nexus SET search_path TO nexus;

密碼只保存在 Kubernetes Secret 中：

kubectl -n repository create secret generic nexus-db \
  --from-literal=username=nexus \
  --from-literal=password="$(openssl rand -base64 36)"

Base64 只是編碼，並非加密。Secret 的明文與輸出都不應出現在 Git 或 CI 日誌中。

使用 Database Migrator

遷移器版本必須與 Nexus 目標版本匹配，並校驗 SHA256。官方說明見 Migrating to a New Database。

sha256sum nexus-db-migrator-<version>.jar

由 Nexus Repository 3.93.0 起，自建部署至少需要 Java 25，執行遷移器前也要確認運行時要求。參見 2026 Release Notes。

遷移前完全停止 Nexus：

kubectl -n repository scale statefulset/nexus --replicas=0
kubectl -n repository wait --for=delete pod/nexus-0 --timeout=180s

若密碼包含 +、&、%、?、# 等字元，寫入 JDBC URL 前必須先編碼，且不得列印完整 URL。

遷移 Job 顯示 Complete 不代表完成，還要檢查最終彙總中是否有 skipped 或 failed 記錄。失敗後不能直接對已有數據的 schema 重跑，應先找出原因，再還原到乾淨的目標資料庫。

遷移完成後，在 Nexus 仍停止時執行：

VACUUM (FULL, ANALYZE);

連接 PostgreSQL 並啟動最終版本

env:
  - name: NEXUS_DATASTORE_NEXUS_JDBCURL
    value: jdbc:postgresql://postgresql.repository.svc.cluster.local:5432/nexus?currentSchema=nexus
  - name: NEXUS_DATASTORE_NEXUS_USERNAME
    value: nexus
  - name: NEXUS_DATASTORE_NEXUS_PASSWORD
    valueFrom:
      secretKeyRef:
        name: nexus-db
        key: password

啟動後等待 Browse/Search 重建任務完成，再驗證搜尋、下載與上傳。

五層驗收

  1. Pod 與日誌：Ready、重啟穩定、無數據庫與 Blob 錯誤。
  2. 狀態介面：/nexus/service/rest/v1/status 正常。
  3. 倉庫：Hosted、Proxy、Group 各自驗證。
  4. 真實構建：執行 Maven 構建，覆蓋 POM、metadata、checksum 與認證。
  5. 上傳：用臨時版本驗證 Hosted 上傳並清理。

只用瀏覽器打開管理頁面，無法證明 Maven 構建鏈路正常。

VIP 無感切換與回滾

大量歷史用戶端依賴固定地址時，可以把舊地址作為 VIP 切到新節點。

切換前必須滿足：

  • 舊 Nexus2 已停止。
  • 舊節點不再持有 VIP。
  • 新 Nexus3 已通過內部地址驗證。
  • 加入 VIP 後重新執行下載、上傳與構建。

任何時刻都不能讓兩台機器同時持有同一個 IP，否則會出現 ARP 抖動與隨機落點。

回滾順序：凍結新上傳、移除新節點 VIP、確認網絡收斂、啟動舊 Nexus2、還原舊入口。新環境一旦接受寫入，回滾還必須處理兩端數據差異。

社群版用量治理

截至本文發布時，Nexus Repository Community Edition 的使用限制為 40,000 個元件或每天 100,000 個請求；超限時不能新增元件，指標更新可能延遲約一小時。參見 Usage Center。

治理原則：

  • 優先清理長期未使用的 Proxy 快取。
  • Hosted releases、snapshots 與內部 third-party 使用獨立保留策略。
  • 清理前備份 PostgreSQL。
  • 先軟刪除，觀察期過後再 Compact Blob Store。
  • 不要單憑頁面短時間未刷新就判斷清理失敗。

Proxy 可從上游重新拉取，Hosted 則很可能是企業的唯一來源，兩者不能共用同一套清理策略。

最容易踩的坑

  • 在錯誤版本上遷移資料庫。
  • Nexus 未停止就執行 Migrator。
  • 只授權資料庫，沒有授權 schema。
  • JDBC 密碼未編碼。
  • Job Complete 後立即重啟，忽略索引任務。
  • 只備份資料庫，不備份 Blob Store。
  • 只驗證管理頁面。
  • 提早銷毀舊伺服器與還原點。

總結

Nexus2 升級 Nexus3 的核心不是「換映像」，而是控制四個邊界：

  1. 內容與元數據通過受支援的路徑轉換。
  2. 版本升級與數據庫遷移分階段完成。
  3. 數據庫、Blob Store 與用戶端存取路徑共同驗證。
  4. 每個不可逆步驟之前都有獨立還原點。

堅持先備份、分階段、逐層驗證、最後切流量，才能把停機時間集中在最終凍結、數據庫遷移與入口切換這幾個階段，而不是讓整個項目長期處於不可用狀態。
