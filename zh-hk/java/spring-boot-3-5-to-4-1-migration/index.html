ENGINEERING NOTE · 2026年8月2日

由 Spring Boot 3.5.13 升級到 4.1：先分清已完成事項與真正風險

以 JDK 25、Nacos 3.1.2 和標準數據存取為基線，梳理 Spring Boot 3.5.13 升級到 4.1 的依賴邊界、實施順序與驗收清單。

2026年8月2日 12 分鐘閱讀
#Java #Spring Boot #Spring Cloud #Nacos #Kubernetes
{ }

Spring Boot 4.1 並非一次普通的依賴升級。它建基於 Spring Framework 7、Jakarta EE 11 和 Servlet 6.1，周邊的 Spring Cloud、Nacos Client、Web 容器、JSON、數據存取和自家開發的 starter 亦會一併跨越大版本。

不過，升級評估最容易犯的錯誤，就是將已經解決的問題重新列為風險。本文記錄一次實際升級前的梳理方法：起點已經是 Spring Boot 3.5.13、JDK 25、Nacos Server 3.1.2，歷史的自訂查詢擴充功能亦已移除。因此評估重點不再是 Boot 3.1 或 Nacos 2 的歷史相容問題，而是 3.5 到 4.1 的真正斷點。

上一篇Spring Boot 由 3.1.7 升級到 3.5.13已經講述了編譯、Pod 啟動、完整 Actuator 健康檢查和中介軟體驗證方法。本文只聚焦 Boot 4 新增的相容風險，避免把同一份通用清單再寫一次。

本文討論的是升級路線和驗證邊界，並不代表把版本號改為 4.1 後就可以直接上線。

脫敏說明：文中不含項目名稱、服務名稱、儲存庫路徑、網域、叢集資訊、命名空間、Data ID、帳號或真實業務數據；配置片段均為佔位範例。

先鎖定基線

先在變更單中寫清楚當前狀態，避免往後的討論混入過時資訊：

項目當前狀態今次是否需要處理
Spring Boot3.5.13升級到 4.1
JDK25維持，無需回退
Nacos Server3.1.2維持，不遷移資料庫、不重建配置
歷史自訂查詢擴充功能已移除毋須移植
複雜查詢已下沉為顯式 SQL保持 Repository 邊界並回歸結果

Nacos Server 已升級到 3.1.2，只能說明伺服器端、資料庫和配置數據可以繼續使用；它不能自動證明某個 Spring Cloud Alibaba Client 已相容 Spring Boot 4.1。Server 與 Client 是兩條獨立的相容鏈。

第一個硬邊界：Spring Cloud Alibaba 對 4.1 的支援

Spring Cloud 官方已說明，由 2025.1.2 開始支援 Spring Boot 4.1.x。因此 Boot 4.1 的 Spring Cloud 目標版本應是：

<spring-cloud.version>2025.1.2</spring-cloud.version>

但 Spring Cloud Alibaba 的官方相容表目前列出的是：

Spring Cloud Alibaba 2025.1.0.0
Spring Cloud 2025.1.0
Spring Boot 4.0.0

並將該分支描述為適配 Spring Boot 4.0.x。4.0.x 並非 4.1.x 的泛稱，不能據此宣稱 2025.1.0.0 已獲得 Boot 4.1 的官方支援。

這並不代表該組合一定無法運行，而是要區分兩種結論：

  • 官方支援：相容矩陣明確列出對應版本。
  • 本地驗證可用：透過依賴收斂、啟動、註冊、配置讀取和業務回歸所得的項目結論。

在 Alibaba 發布明確的 Boot 4.1 適配版本之前，若要直接推進 Boot 4.1，應把以下組合視為驗證對象，而不是視為預設的生產承諾：

Spring Boot 4.1.x
Spring Cloud 2025.1.2
Spring Cloud Alibaba 2025.1.x
Nacos Server 3.1.2

官方依據：Spring Cloud 版本相容表、Spring Cloud Alibaba 2025.x 版本說明。

Nacos 毋須遷移數據，但應用配置載入方式要遷移

Spring Cloud Alibaba 2025.x 不再支援 Spring Cloud Bootstrap。應用若仍依賴：

bootstrap.yml
spring.cloud.bootstrap.enabled

就要改為 Spring Boot Config Data 方式，例如：

spring:
  config:
    import:
      - optional:nacos:<data-id>?group=<group>

Data ID 是否拆分，以及 Group、Namespace、用戶名稱和地址等細節，沿用目標環境的定義即可，且不應寫入公開文件；改變的是「應用在啟動階段如何讀取配置」，而不是 Nacos 中儲存的數據格式。

遷移完成後，必須驗證兩個方向：

  1. 啟動時能載入必填配置，例如 Feign URL、數據源、Redis、訊息佇列地址。
  2. 運行中的配置刷新、服務註冊、實例發現仍然正常。

Boot 4 本身帶來的主要變化

1. Undertow 不能再作為嵌入式容器

Boot 4 的 Servlet 6.1 基線與 Undertow 不相容，官方已移除 Undertow starter 和嵌入式 Undertow 支援。若最終依賴樹使用 Undertow，需要切換到 Tomcat 11 或 Jetty 12，並刪除 server.undertow.* 配置。

不要單憑一份公共配置就認定所有服務都需要更換容器；應先確認每個服務的最終依賴樹和實際啟動日誌。

2. Boot 模組和 starter 重新拆分

Boot 4 將許多大型 jar 拆成更細的模組。自家開發的 starter、直接依賴 Boot 內部類別、手寫自動配置的模組，尤其容易在編譯期暴露問題。

首輪可使用 spring-boot-starter-classic 和 spring-boot-starter-test-classic 取得接近 Boot 3 的完整 classpath，先恢復編譯、啟動和測試；穩定後再按實際功能替換為更精確的 starter。不要讓同一個自家開發的 starter 同時承諾 Boot 3 與 Boot 4 二進制相容，應建立獨立的 Boot 4 版本線。

3. Jackson 3 是大方向，不應與框架升級捆綁冒險

Boot 4 預設偏向 Jackson 3，而 Jackson 3 的坐標和部分套件名稱有變。對已有大量 ObjectMapper、訊息序列化、日期格式化、匯入匯出邏輯的系統，首輪應優先保持 Jackson 2 的相容行為：

spring:
  jackson:
    use-jackson2-defaults: true

必要時使用 Boot 提供的臨時 Jackson 2 模組。待 HTTP 回應、Kafka/Rabbit 訊息和匯出檔案全部通過回歸後，再單獨規劃 Jackson 3 遷移。否則一旦出現異常，很難判斷是 Boot、Jackson 還是業務序列化造成。

4. 數據存取元件必須按 Boot 4 重新確認

已移除的歷史自訂查詢擴充功能不再是風險，但以下元件仍需確認版本：

  • Hibernate 7：實體映射、方言、JPA Criteria、原生 SQL、JSON 與日期欄位。
  • 動態數據源：dynamic-datasource-spring-boot3-starter 不能直接假定相容 Boot 4。
  • MyBatis-Plus：分頁、攔截器、多數據源交易與 SQL 日誌。
  • Redis、Kafka、Rabbit：用戶端、序列化、監聽器、重試和訊息頭。

每一項都應以「升級依賴後執行測試」的方式確認，而不是只看 Maven 能否下載 jar。

5. 安全、測試和營運也會隨之升級

Boot 4 同時帶來 Spring Security 7、Spring Kafka 4、Spring AMQP 4、Spring Batch 6 等大版本升級。需要重點驗證：

  • 登入、Token、權限註解、Feign 呼叫身份。
  • 訊息消費、反序列化、重試和冪等。
  • @SpringBootTest 下的 Web 測試；需要時顯式加上 @AutoConfigureMockMvc。
  • Actuator 健康檢查。Boot 4 預設啟用 liveness/readiness 分組，Kubernetes 探針、Prometheus 抓取和優雅停機都要複核。

在 3.5 驗收基線上的實施順序

建立 4.1-SNAPSHOT 分支
        ↓
确认 Cloud / Alibaba Client 精确版本
        ↓
迁 Nacos Config Data，处理父工程自研 starter
        ↓
父工程全量编译与测试
        ↓
升级一个试点服务并在本地连接 Nacos 3.1.2
        ↓
test Kubernetes 发布与业务回归
        ↓
逐服务推广

建議先選一個業務邊界清晰、測試較完整的服務作為試點，而不是一次過升級所有服務。父工程新版本使用獨立的 Maven 版本，例如 4.1-SNAPSHOT，避免覆蓋仍在運行的 3.5.13-SNAPSHOT。

Boot 4 試點的增量驗收清單

下面只列出相對於上一篇新增的檢查項目。目標 JDK 編譯、Pod 啟動、完整 /actuator/health、資料庫和訊息中介軟體連通性等通用驗收仍然必須執行，但不會在此重複展開。

啟動與基礎設施

  • Spring Cloud 已使用支援 Boot 4.1 的 2025.1.2+，依賴樹中沒有舊 Release Train。
  • Spring Cloud Alibaba Client 的精確版本有相容矩陣或試點驗證證據，不能只用 Nacos Server 版本代替。
  • Nacos 配置已改為 Config Data，啟動鏈路不再依賴 Spring Cloud Bootstrap。
  • 實際 Web 容器是 Tomcat 11 或 Jetty 12，依賴樹與配置中沒有殘留 Undertow。
  • spring-boot-starter-classic 只作為過渡；拆分 starter 和屬性遷移完成後應移除。

業務與數據

  • Hibernate 7、MyBatis-Plus 和動態數據源分別完成分頁、交易、原生 SQL 與多數據源回歸。
  • Spring Batch 6 的 Job 註冊、元數據表、重啟和分區執行語義通過驗證。
  • Spring Kafka 4、Spring AMQP 4 的訊息頭、序列化、重試、死信和冪等行為沒有變化。
  • Jackson 3 與臨時 Jackson 2 相容路徑只能選擇一條作為生產基線，並完成 HTTP、訊息和匯入匯出回歸。

介面契約

  • 前端核心頁面請求與錯誤提示。
  • 日期、金額、枚舉、null 欄位、分頁結構。
  • HTTP API 與訊息 JSON 的反序列化相容。

總結

由 Spring Boot 3.5.13 升到 4.1，Nacos 3.1.2 與已移除的歷史自訂查詢擴充功能不再是阻礙。真正需要優先確認的是 Spring Cloud Alibaba Client 對 Boot 4.1 是否有明確支援；隨後按 Nacos 配置載入、Boot 模組化與 Web 容器、數據存取、Jackson 和自家開發 starter 的順序推進。

先建立「本地和 test 環境驗證可用」的證據，再將其確立為生產標準，才是這類跨大版本升級可控的做法。Boot 官方遷移指南可作為逐項排查清單：Spring Boot 4.0 Migration Guide。
