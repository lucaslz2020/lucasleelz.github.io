ENGINEERING NOTE · 2026年8月8日

從 GitLab CE 14.9.3 平滑升級到 19.2.1：Kubernetes、PostgreSQL 17 與最終增量切換實戰

記錄一套自建 GitLab 從 14.9.3 逐級升級到 19.2.1，並遷入 Kubernetes、切換外部 PostgreSQL、同步最終增量及保留原入口地址的完整方法。

本文來自一次真實生產遷移。IP、網域、節點名、項目名、倉庫數量、用戶數量、鏡像倉庫、備份文件名和驗證值均已脫敏或泛化；Secret、密碼和內部地址只使用佔位符。

GitLab 的升級停靠點和 PostgreSQL 支援矩陣會繼續變化。執行前必須重新核對 GitLab 官方升級路徑 與 安裝要求，不能把本文的版本組合當作永久規則。

這次遷移的起點是一台運行多年的 GitLab CE 14.9.3。它使用 Omnibus 一體化部署，Git 倉庫、PostgreSQL、Redis、配置和日誌都集中在同一台虛擬機上。

終點是：

  • GitLab CE 19.2.1。
  • 以單副本 StatefulSet 運行在 Kubernetes。
  • Git 倉庫、上傳文件和配置保存在 Retain 本地持久卷。
  • PostgreSQL 使用叢集內的獨立數據庫和帳號。
  • PostgreSQL 最終升級到 17。
  • 對外網域、服務 IP 和 SSH 入口保持不變。
  • 舊伺服器在最終增量同步後關機，並保留一段時間作為回滾點。

這不是一次“換鏡像然後等待 Pod 變綠”的升級。真正需要處理的是四條相互約束的鏈路：

  B --> C["GitLab 16<br/>外部 PostgreSQL 14"]
  C --> D["GitLab 17<br/>PostgreSQL 14 / 16"]
  D --> E["GitLab 18<br/>PostgreSQL 16 / 17"]

每個階段都必須同時滿足：版本路徑正確、後台遷移完成、數據庫版本受支援、回滾數據可用。

為什麼必須升級，但不能直接跨版本

繼續運行 14.x 的問題不只是“版本舊”：

  • 安全更新和缺陷修復無法持續獲得。
  • 新版 Runner、瀏覽器、Git 客戶端和整合元件的兼容範圍不斷前移。
  • 老版本 PostgreSQL 和操作系統也會進入維護末期。
  • 後續想遷入 Kubernetes 時，舊配置、舊數據庫和舊儲存會一起成為阻礙。

但 GitLab 的數據庫結構變化很多，大版本之間還存在 Batched Background Migration。直接從 14.9 跳到 19.x，極易遇到缺失遷移類、表結構不匹配、數據庫版本不支援或者加密配置無法解密。

GitLab 官方要求經過特定的 required upgrade stops。每到一個停靠點，都要使用該 minor 的最新 patch，等待後台遷移全部結束，再進入下一站。

其中某些舊版本停靠點是條件性的。例如，本次在確認只有一個 Web 節點、相關業務表數據量不觸發條件後，才跳過了不適用的停靠點。

不要照抄結論。正確做法是把源版本、目標版本、實例規模和相關表數據輸入 GitLab Upgrade Path 工具，再逐項閱讀各版本 Upgrade Notes。

第 1 步：先固定遷移基線

開始前記錄一組可重複查詢的基線。後續每升級一站，都用相同指令碼檢查。

至少包括：

  • GitLab 版本。
  • 用戶、組、項目、Merge Request、Pipeline 和 Job 數量。
  • 倉庫總量和關鍵預設分支 tip。
  • LFS、Upload、Artifact、Package 佔用。
  • PostgreSQL 版本、數據庫大小和擴展。
  • Sidekiq、Gitaly、Puma、Workhorse、GitLab Shell 狀態。
  • 普通數據庫遷移和批次後台遷移狀態。

示例：

gitlab-rake gitlab:env:info
gitlab-rake gitlab:check SANITIZE=true

gitlab-rails runner '
puts({
  users: User.count,
  groups: Group.count,
  projects: Project.count,
  merge_requests: MergeRequest.count,
  builds: Ci::Build.count
}.inspect)
'

只看 gitlab:check 不夠。它能夠發現常見的配置、權限和服務問題，卻不能替代業務數據計數、倉庫 refs 比對和真實 clone/push。

第 2 步：備份不只是一個 tar 包

GitLab 應用備份與配置備份是兩套東西。應用備份包含數據庫和業務文件，但 /etc/gitlab/gitlab-secrets.json 中保存著數據庫加密金鑰、CI/CD 變數、2FA 等敏感數據的解密能力。

GitLab 官方也明確要求把配置和 Secret 單獨保存在安全位置，參見 Backup 和 Restore GitLab。

本次每個關鍵階段至少保留：

  1. GitLab 應用備份。
  2. PostgreSQL 獨立 dump。
  3. /etc/gitlab 配置歸檔。
  4. gitlab-secrets.json。
  5. SSH Host Key。
  6. 備份文件大小和 SHA-256。
  7. 當前 StatefulSet、Service、PV、PVC、Secret 和 ConfigMap 清單。
umask 077

gitlab-backup create
gitlab-ctl backup-etc

tar -C /etc -czf /backup/ssh-host-keys.tar.gz ssh
sha256sum /backup/* > /backup/SHA256SUMS

恢復演練必須使用相同 GitLab 版本。不能把 14.x 備份直接恢復進 19.x 容器。

還有一個容易踩的坑：執行外部 PostgreSQL dump 時，pg_dump 客戶端主版本不能低於服務端主版本。如果 GitLab 容器裏自帶的客戶端過舊，應在 PostgreSQL Pod 或匹配版本的臨時工具容器中生成 dump。

第 3 步：先在 Kubernetes 恢復同版本

不要一邊改變運行平台，一邊跨多個 GitLab 大版本。第一步應先把 14.9.3 恢復進 Kubernetes，同版本通過驗收後，再開始逐級升級。

這次採用單副本 StatefulSet，核心設計如下：

apiVersion: v1
kind: PersistentVolume
metadata:
  name: gitlab-data
spec:
  capacity:
    storage: <capacity>
  accessModes: [ReadWriteOnce]
  persistentVolumeReclaimPolicy: Retain
  storageClassName: gitlab-local
  hostPath:
    path: /data/gitlab
  nodeAffinity:
    required:
      nodeSelectorTerms:
        - matchExpressions:
            - key: kubernetes.io/hostname
              operator: In
              values: [gitlab-node]

StatefulSet 使用 OnDelete：

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: gitlab
spec:
  replicas: 1
  updateStrategy:
    type: OnDelete
  template:
    spec:
      nodeSelector:
        app-type: gitlab
      tolerations:
        - key: app-type
          operator: Equal
          value: gitlab
          effect: NoSchedule
      terminationGracePeriodSeconds: 300

使用 OnDelete 的目的不是偷懶，而是防止修改鏡像後 StatefulSet 立刻滾動。運維人員必須先確認當前停靠點的後台遷移和備份完成，再顯式刪除 Pod 進入下一版本。

PV 使用 Retain 同樣重要。誤刪 StatefulSet 或 PVC 時，宿主機 /data/gitlab 不會跟著被回收。

第 4 步：每個 GitLab 停靠點都執行同一套閘門

每一站的操作順序固定為：

  1. 確認前一版本所有遷移完成。
  2. 建立當前版本回滾備份。
  3. 把下一版本鏡像同步到內部鏡像倉庫。
  4. 記錄鏡像 digest，並在目標節點預拉取。
  5. 修改 StatefulSet 鏡像。
  6. 顯式刪除 Pod。
  7. 觀察 reconfigure、數據庫遷移、Puma、Sidekiq 和 Gitaly 日誌。
  8. 等待 Pod Ready。
  9. 檢查數據庫遷移與後台遷移。
  10. 執行 HTTP、SSH、核心計數和 gitlab:check。
kubectl -n <namespace> set image statefulset/gitlab \
  gitlab=<registry>/gitlab-ce:<next-version>

kubectl -n <namespace> delete pod gitlab-0
kubectl -n <namespace> wait --for=condition=Ready \
  pod/gitlab-0 --timeout=30m

kubectl -n <namespace> exec gitlab-0 -- \
  gitlab-rake gitlab:check SANITIZE=true

首次啟動幾分鐘沒有 Ready，不等於進程卡死。應同時檢查：

kubectl -n <namespace> get pod gitlab-0 -o wide
kubectl -n <namespace> describe pod gitlab-0
kubectl -n <namespace> logs -f gitlab-0

鏡像拉取、Chef reconfigure、數據庫鎖、後台遷移、倉庫驗證和磁碟 IO 都可能讓啟動變慢。不要因為一個等待超時就併發啟動多個 Rails Runner 或完整 checksum 檢查，它們會進一步放大磁碟競爭。

第 5 步：正確識別 Batched Background Migration

這是整個升級過程中最容易誤判的地方。

舊指令碼曾使用：

WHERE status <> 3

GitLab 17 之後，6 表示 finalized。繼續使用舊條件會把已經完成的遷移當成未完成，甚至調用當前版本已經不存在的遷移類。

更穩妥的 SQL 是：

SELECT id, job_class_name, table_name, status
FROM batched_background_migrations
WHERE status NOT IN (3, 6);

或者在對應版本 Rails 環境中使用模型提供的 scope：

gitlab-rails runner '
puts Gitlab::Database::BackgroundMigration::BatchedMigration.unfinished.count
'

GitLab 新版本還提供了更完整的 Rake Task。官方文檔要求進入下一停靠點前所有後台遷移都必須結束，參見 Check migrations before upgrade。

gitlab-rake gitlab:background_migrations:list
gitlab-rake gitlab:background_migrations:status

不要直接把失敗遷移改成 finished。先檢查父遷移、子任務、業務數據和當前版本實現。只有確認遷移邏輯對現存數據確實不適用，並且已經建立可恢復備份後，才考慮使用當前版本官方提供的 finalize/execute 任務。

第 6 步：讓 PostgreSQL 升級節奏跟上 GitLab

GitLab 與 PostgreSQL 不能各自獨立升級。本次採用以下節奏：

階段GitLabPostgreSQL 策略
起點14 / 15保留 Omnibus 內置 PostgreSQL
中段16遷移到外部 PostgreSQL 14
進入 17 前16.11PostgreSQL 14 升到最新兼容小版本
進入 18 前17.11PostgreSQL 14 → 16
進入 19 前18.11PostgreSQL 16 → 17
終點19.2外部 PostgreSQL 17

GitLab 19 要求 PostgreSQL 17。官方支援矩陣見 GitLab installation requirements。

外部數據庫必須使用獨立數據庫、帳號和 Secret：

postgresql['enable'] = false

gitlab_rails['db_adapter'] = 'postgresql'
gitlab_rails['db_host'] = 'postgresql.<namespace>.svc.cluster.local'
gitlab_rails['db_port'] = 5432
gitlab_rails['db_database'] = 'gitlabhq_production'
gitlab_rails['db_username'] = 'gitlab'
gitlab_rails['db_password'] = File.read('/run/secrets/gitlab-db/password').strip

PostgreSQL 大版本升級前先做 pg_upgrade --check：

pg_upgrade \
  --old-datadir=<old-data> \
  --new-datadir=<new-data> \
  --old-bindir=<old-bin> \
  --new-bindir=<new-bin> \
  --check

本次數據卷使用支援 reflink 的 XFS，因此實際升級採用 --clone，避免再複製一份完整數據庫：

pg_upgrade \
  --old-datadir=<old-data> \
  --new-datadir=<new-data> \
  --old-bindir=<old-bin> \
  --new-bindir=<new-bin> \
  --clone \
  --jobs=4

--clone 不是備份。舊數據目錄必須繼續保留，直到 GitLab 最終版本、最終增量切換和業務驗收全部完成。不要提前運行生成的 delete_old_cluster.sh。

升級完成後更新優化器統計信息：

vacuumdb --all --analyze-in-stages --jobs=4

然後從 GitLab Rails 內確認真實連接目標和數據庫版本，而不是隻看 PostgreSQL Pod 日誌。

第 7 步：處理幾個真實的升級故障

1. status <> 3 把 finalized 當成失敗

原因是 GitLab 17 引入了新的遷移狀態。修復不是“強制標記完成”，而是使用當前版本的 unfinished scope 或 NOT IN (3, 6)。

2. 歷史分區數據阻塞後台遷移

某個後台任務處理歷史通知數據時，發現記錄時間早於現有月分區範圍。此時不能偽造業務記錄，也不能直接跳過。

正確處理思路是：

  1. 找到具體遷移和源記錄。
  2. 確認記錄是否仍有有效業務關聯。
  3. 檢查目標表分區邊界。
  4. 在停寫和備份條件下為合法歷史數據準備兜底分區。
  5. 使用當前 GitLab 版本的官方任務重新執行或 finalize。
  6. 再次檢查未完成遷移數和數據完整性。

3. GitLab 19 首次啟動因舊組件狀態退出

從 GitLab 18 進入 19 時，第一次 reconfigure 檢測到歷史組件遺留狀態並退出。沒有立即手工刪除整個 Secret，而是先保留備份，確認新版本會重新生成不再需要的配置塊，再啟動一次。隨後 schema migration 正常完成。

這類問題必須區分：

  • 配置確實已被新版本移除。
  • Secret 丟失或損壞。
  • 數據庫中的加密值無法解密。

三種情況的處理方式完全不同。

4. 最終版本完整備份可能擠爆磁碟

遷移末期磁碟剩餘空間不足以再暫存一份完整倉庫歸檔。最終版本只建立數據庫保護備份，同時繼續保留上一關鍵版本已經驗證過的完整備份、倉庫數據卷和配置歸檔。

這是一種受控取捨，但前提是清楚記錄“哪一個備份包含數據庫，哪一個包含倉庫”，不能把 database-only 備份誤當成完整恢復點。

第 8 步：為什麼升級完成後仍不能立刻切換

初始備份只是一個時間點。升級期間舊 GitLab 如果仍對開發者開放，就會繼續產生 push、權限修改、CI 變數、Merge Request 和構建記錄。

因此最終切換前必須做增量審計。

先凍結舊實例：

gitlab-ctl stop nginx
gitlab-ctl stop gitlab-workhorse
gitlab-ctl stop puma
gitlab-ctl stop sidekiq
gitlab-ctl stop gitlab-kas

同時禁止 git 用戶繼續通過 SSH 寫入，但保留運維 root 通道。凍結後比較新舊兩邊：

  • 用戶、組、項目、MR、CI Job 等核心計數。
  • 最新 Project/Event 時間。
  • 預設分支和活躍分支 tip。
  • LFS、Artifact、Upload、Package 是否有增量。
  • GitLab 審計/事件記錄。

本次數據庫對象計數沒有新增，但發現數百條 push 事件，涉及十餘個倉庫。這說明只同步數據庫或只比較項目數量都會漏數據。

第 9 步：只同步發生變化的倉庫

先從事件和項目時間定位變更倉庫，再同步對應的 hashed repository 目錄。不要在不瞭解差異時對整個倉庫目錄執行 rsync --delete。

同步後至少完成三層驗證。

文件所有權

不同 GitLab 鏡像中的 git UID/GID 可能不同。使用 rsync --numeric-ids 會把舊 UID 原樣帶過來，導致目標 Gitaly 無權訪問。

同步後以目標容器實際 UID/GID 修復，而不是複製舊數字：

chown -R <target-git-uid>:<target-git-gid> <affected-repository>

refs 完全一致

git -C <source-repository> for-each-ref \
  --format='%(refname) %(objectname)' | sort > source.refs

git -C <target-repository> for-each-ref \
  --format='%(refname) %(objectname)' | sort > target.refs

diff -u source.refs target.refs

對象完整性

git -C <target-repository> fsck --no-dangling

舊 commit-graph 緩存可能引用已經不存在的對象。不要刪除 Git 對象來“修復”，而是先保留舊緩存目錄，再從當前可達 refs 重建 commit-graph。

最後更新項目活動時間並清理 Rails Cache，避免首頁仍顯示初始備份時刻。

第 10 步：保留原 IP，同時讓節點名與 IP 一致

為了不批量修改開發機、Jenkins 和歷史倉庫地址，最終繼續使用原 GitLab 服務 IP。

切換過程是：

  1. GitLab StatefulSet 縮容到 0。
  2. 確認舊伺服器已經停寫並關機，原 IP 不再響應。
  3. 把目標 Kubernetes 節點主機名和管理 IP 改成最終值。
  4. 執行 kubeadm reset 後以新節點名重新加入叢集。
  5. 恢復 GitLab 專用標籤與污點。
  6. 重新綁定本地 PV。
  7. StatefulSet 擴容到 1。
  8. 驗證 HTTP、SSH、Gitaly、數據庫和倉庫。
sequenceDiagram
  participant Old as 舊 GitLab
  participant API as Kubernetes API
  participant Node as 新 GitLab 節點
  participant GitLab as GitLab 19

  Old->>Old: 凍結 HTTP / SSH Git 寫入
  Old->>Node: 同步最終倉庫增量
  Old->>Old: 關機並釋放服務 IP
  Node->>Node: 修改 hostname 與靜態 IP
  Node->>API: kubeadm join --node-name <final-node>
  API->>Node: 恢復 label / taint
  API->>GitLab: 綁定 PV 並啟動 StatefulSet
  GitLab->>GitLab: HTTP、SSH、數據庫、倉庫驗收

這裏有一個 Kubernetes 陷阱：PV 的 nodeAffinity 是不可變字段。節點改名後不能直接 patch。

正確做法是：

  1. GitLab Pod 保持停止。
  2. 確認 PV 回收策略為 Retain。
  3. 刪除 PVC/PV 對象。
  4. 保留宿主機 /data/gitlab 實際目錄。
  5. 使用新節點名重建 PV/PVC，並指向同一目錄。
  6. 等 PVC Bound 後再啟動 GitLab。

這一步刪除的是 Kubernetes 元數據，不是倉庫數據。操作前必須再次檢查 Pod 已停止、路徑正確、回收策略正確。

舊伺服器不能帶著原 IP 直接再次開機。應在虛擬化平台先斷開虛擬網卡，從控制台重裝或修改成已經釋放的其他地址，再連接網絡，否則會產生 IP 衝突。

第 11 步：最終驗收不要只看 Pod Ready

最終驗收分成六層。

Kubernetes 層

kubectl get node <gitlab-node> -o wide
kubectl -n <namespace> get pod gitlab-0 -o wide
kubectl -n <namespace> get pvc
kubectl get pv

確認：

  • 節點名、InternalIP 和主機名一致。
  • Pod 在預期節點運行且沒有重啓。
  • PVC 為 Bound。
  • PV 為 Retain，nodeAffinity 指向最終節點。

GitLab 服務層

gitlab-ctl status
gitlab-rake gitlab:check SANITIZE=true

檢查 GitLab Shell、Gitaly、Sidekiq、Redis、數據庫遷移、Uploads 權限和 hashed storage。

數據庫層

  • 核心對象計數與凍結源一致。
  • PostgreSQL 為目標版本。
  • 所有 schema migration 已完成。
  • Batched Background Migration 未完成數為 0。
  • gitlab:doctor:secrets 能夠解密關鍵數據。

倉庫層

  • 所有發生增量的倉庫 refs 完全一致。
  • git fsck --no-dangling 通過。
  • 抽樣執行 clone、fetch、push、merge。

HTTP 與 SSH 層

curl -fsS http://<gitlab-host>/users/sign_in >/dev/null
ssh -T git@<gitlab-host>

真實業務層

  • Jenkins 能拉取源碼並提交狀態。
  • Webhook 能正常投遞。
  • Runner 能領取任務。
  • CI/CD 變數可以解密。
  • 用戶登錄、2FA、Personal Access Token 正常。

只有六層全部通過，才算遷移完成。

回滾策略

最終切換後不要立刻刪除舊伺服器、舊 PostgreSQL 目錄和中間版本鏡像。

建議至少保留：

  • 舊 GitLab 虛擬機，保持關機和斷網。
  • 最後一個已驗證完整 GitLab 備份。
  • 每個關鍵大版本的數據庫 dump 與配置歸檔。
  • PostgreSQL 舊數據目錄。
  • GitLab 18 的最終完整恢復點。
  • GitLab 19 的數據庫保護備份。
  • 實際使用過的 GitLab/PostgreSQL 鏡像及 digest。
  • 最終增量倉庫清單和 refs 驗證結果。

回滾也分層：

  1. 入口異常但數據正常：切回舊入口。
  2. GitLab Pod 異常：恢復前一個鏡像和對應數據庫狀態。
  3. PostgreSQL 異常：切回保留的舊數據目錄。
  4. 數據完整性異常：關閉新實例寫入，恢復最後完整備份，並重新計算增量。

任何回滾都要避免讓新舊兩邊同時接受寫入。

這次升級最重要的經驗

1. GitLab 升級的最小單位不是鏡像，而是“版本 + 數據庫 + 後台遷移”

Pod Ready 只表示進程通過探針。真正的停靠點完成條件是：版本正確、數據庫受支援、普通遷移完成、後台遷移完成、備份可恢復、真實請求通過。

2. 遷入 Kubernetes 不等於高可用

單副本 GitLab 加本地 PV 仍然是單節點有狀態服務。Kubernetes 提供的是聲明式部署、探針、調度、資源限制和統一運維入口，不會自動把本地儲存變成高可用。

3. 初始恢復成功不代表可以切換

只要舊實例還開放，就必須把最終增量分成數據庫對象、Git 倉庫、LFS/Artifact/Upload 和配置四類分別核對。

4. 保留原 IP 能減少客戶端改動，但必須處理節點身份

IP、主機名、Kubernetes Node 名和 PV nodeAffinity 最好保持一致。否則半年後排查問題時，很難解釋為什麼某個地址對應另一個節點名。

5. 不要提前清理回滾點

遷移最危險的清理動作往往看起來最合理：刪除舊 PostgreSQL 目錄、釋放舊 VM、清空中間鏡像、刪除完整備份。等完整業務驗收和觀察期結束後再做。

結語

從 GitLab 14.9.3 升級到 19.2.1，真正耗時的不是下載二十個鏡像，而是每一站都願意停下來驗證。

一條可靠的遷移路徑可以歸納為：

盤點
→ 同版本恢復
→ required stops
→ 每站清空後台遷移
→ PostgreSQL 分階段升級
→ 每站建立回滾點
→ 凍結舊實例
→ 同步最終增量
→ refs 與對象驗證
→ 保留原入口切換
→ 六層驗收
→ 觀察期後再清理

越是跨度大的基礎設施升級，越不能依賴“一次成功啟動”的運氣。把每個階段變成有輸入、有輸出、有驗收、有回滾的獨立步驟，升級才真正可控。
