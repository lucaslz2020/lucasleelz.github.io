GitLab 14 升級到 19 實戰復盤（三）：Kubernetes 增量切流、保留 IP 與回滾

復盤 GitLab 升級完成後的最終凍結、倉庫增量同步、原 IP 切換、PV 重綁、六層驗收和可執行回滾策略。

這是 GitLab 14.9.3 升級到 19.2.1 系列的最後一篇。第一篇介紹同版本恢復與升級節奏，第二篇介紹停靠點、後台遷移和 PostgreSQL。本文只討論一個問題：新 GitLab 已能啓動，怎樣才能安全替換舊 GitLab。

初始恢復成功，不等於可以切流

最初的應用備份只是某個時刻的快照。升級期間舊 GitLab 仍然對開發者開放，就可能繼續產生 push、權限修改、CI 變量、Merge Request 和構建記錄。

這次最終審計中，數據庫對象計數沒有新增，但發現了數百條 push 事件，涉及十餘個倉庫。這個結果很關鍵：只比項目數量、只恢復數據庫，甚至只對比最新更新時間，都會漏掉真實的 Git 數據增量。

因此切流前的目標不是“新實例已經可訪問”，而是明確回答三個問題：舊實例最後接收了什麼寫入？哪些數據需要補同步？補完後怎麼證明新舊一致？

凍結舊實例，先把寫入窗口關住

切流窗口開始後，我們先停止舊 GitLab 的 Web 和後台寫入入口，保留受控的 root 運維通道：

gitlab-ctl stop nginx
gitlab-ctl stop gitlab-workhorse
gitlab-ctl stop puma
gitlab-ctl stop sidekiq
gitlab-ctl stop gitlab-kas

凍結後再比較兩端，而不是邊寫邊同步。審計範圍至少包括：用户、組、項目、MR、CI Job 等核心對象計數；最新 Project/Event 時間；默認分支和活躍分支 tip；LFS、Artifact、Upload、Package 的變化；以及審計和事件記錄。

對 Git 倉庫而言，事件記錄幫助定位“哪些倉庫可能變了”，最終正確性仍由 refs 和對象校驗決定。

不要對整個倉庫目錄盲目 rsync —delete

我們先從事件和項目更新時間鎖定發生寫入的倉庫，再同步對應的 hashed repository 目錄。對未知差異直接全量 rsync --delete，可能把目標側已經生成的必要文件誤刪，也會把校驗範圍擴大到難以回滾。

同步後必須處理所有權。不同 GitLab 鏡像裏的 git UID/GID 可能不同；rsync --numeric-ids 會把舊數字原樣帶到目標，導致 Gitaly 沒有讀寫權限。應以目標容器的實際 UID/GID 修復：

chown -R <target-git-uid>:<target-git-gid> <affected-repository>

然後做兩層倉庫驗證。第一層比對所有 refs：

git -C <source-repository> for-each-ref \
  --format='%(refname) %(objectname)' | sort > source.refs
git -C <target-repository> for-each-ref \
  --format='%(refname) %(objectname)' | sort > target.refs
diff -u source.refs target.refs

第二層檢查對象完整性：

git -C <target-repository> fsck --no-dangling

舊 commit-graph 緩存可能引用已不存在的對象。遇到這種情況，不要刪除 Git 對象“修復報錯”；保留舊緩存目錄，再從當前可達 refs 重建 commit-graph。最後清理 Rails Cache 並更新項目活動時間，避免首頁仍顯示初始恢復時刻。

保留原 IP，先處理節點身份

為了不批量修改開發機、Jenkins 和歷史 clone 地址，最終繼續使用原 GitLab 服務 IP。這個決定減少了客户端改動，但把 IP、主機名、Kubernetes Node 名和 PV nodeAffinity 綁定在同一個切換窗口中。

實際順序是：

  1. GitLab StatefulSet 縮容到 0。
  2. 確認舊服務器已停止寫入、關機且原 IP 不再響應。
  3. 將目標節點改為最終主機名和靜態 IP。
  4. kubeadm reset 後以新節點名重新加入集羣。
  5. 恢復 GitLab 專用標籤和污點。
  6. 以新節點身份重建 PV/PVC 元數據並綁定原數據目錄。
  7. StatefulSet 擴容到 1。
  8. 執行 HTTP、SSH、Gitaly、數據庫和倉庫驗收。

這裏的 Kubernetes 陷阱是：PV 的 nodeAffinity 不可變。節點改名後不能直接 patch。正確方式是先讓 GitLab Pod 停止，確認 PV 為 Retain，刪除 PVC/PV 對象、保留宿主機數據目錄，再按新節點名重建 PV/PVC，等 PVC 為 Bound 後才啓動 GitLab。

刪除的是 Kubernetes 元數據，不是倉庫數據；但這個區別只有在 Pod 已停止、路徑核對正確且回收策略為 Retain 時才成立。舊服務器也不能帶着原 IP 再次開機，必須先斷開虛擬網卡或改成其他地址，避免 IP 衝突。

六層驗收：Pod Ready 只是第一層

最終驗收按下面六層執行：

  1. Kubernetes：節點名、InternalIP、主機名一致；Pod 在預期節點且不重啓；PVC 為 Bound；PV 是 Retain 並指向最終節點。
  2. GitLab 服務：gitlab-ctl status、gitlab-rake gitlab:check SANITIZE=true、GitLab Shell、Gitaly、Sidekiq、Redis、Uploads 和 hashed storage 正常。
  3. 數據庫：核心計數與凍結源一致，目標 PostgreSQL 版本正確，schema migration 完成，未完成批量後台遷移為 0，gitlab:doctor:secrets 能解密關鍵數據。
  4. 倉庫：所有發生增量的倉庫 refs 完全一致，git fsck --no-dangling 通過。
  5. 入口：HTTP 登錄頁可訪問，SSH 握手成功，原地址沒有變化。
  6. 真實業務：Jenkins 能拉取並回傳狀態，Webhook 能投遞，Runner 能領取任務，CI/CD 變量可解密，用户登錄、2FA 和 Personal Access Token 正常。
curl -fsS http://<gitlab-host>/users/sign_in >/dev/null
ssh -T git@<gitlab-host>

六層全部通過，才把這次遷移標記為完成。尤其不要把“頁面能打開”當作驗收結束：倉庫讀寫、CI、Webhook、Secret 解密才是開發者真正依賴的能力。

回滾點不是一個文件，而是一組邊界

最終切流後，舊 GitLab 虛擬機、舊 PostgreSQL 數據目錄、中間版本鏡像和關鍵備份都不能立即清理。我們至少保留：舊虛擬機（關機、斷網）、最後一個已驗證完整 GitLab 備份、關鍵大版本 dump 與配置歸檔、PostgreSQL 舊數據目錄、GitLab 18 完整恢復點、GitLab 19 數據庫保護備份、實際鏡像 digest、最終增量倉庫清單和 refs 校驗結果。

回滾也分層：

  • 入口異常但數據正常：切回舊入口。
  • GitLab Pod 異常：恢復前一鏡像和對應數據庫狀態。
  • PostgreSQL 異常：切回保留的舊數據目錄。
  • 數據完整性異常：關閉新實例寫入，恢復最後完整備份，再重新計算增量。

任何回滾都必須避免新舊兩邊同時接受寫入。觀察期結束後再清理回滾點，升級才算真正收尾。

這次遷移留下的三個判斷標準

  • GitLab 升級的最小單位不是鏡像，而是“版本 + 數據庫 + 後台遷移 + 可恢復備份”。
  • 單副本 GitLab 加本地 PV 不是高可用；Kubernetes 提供的是聲明式部署和統一運維入口，不會自動複製有狀態數據。
  • 初始恢復成功並不等於數據完成遷移。只要舊實例持續開放，最終增量就必須按數據庫對象、Git 倉庫、LFS/Artifact/Upload 和配置分別核對。

回頭看，真正耗時的從來不是下載二十個鏡像，而是每到一個關鍵點都願意停下來驗證。把遷移拆成有輸入、有輸出、有驗收和有回滾的小步驟，複雜升級才不會依賴運氣。
