GitLab 14 升級到 19 實戰復盤（二）：升級停靠點、後台遷移與 PostgreSQL 17

復盤 GitLab 跨版本升級中最容易誤判的後台遷移狀態、歷史分區故障和 PostgreSQL 14 到 17 的分階段升級。

這是 GitLab 14.9.3 升級到 19.2.1 系列的第二篇。遷移架構和逐站節奏見第一篇；最終凍結、增量同步和回滾見第三篇。

跨版本升級最容易把人帶偏的信號是“Pod 已經 Ready”。在這次遷移裏，真正決定能否進入下一站的不是探針，而是普通 schema migration、批量後台遷移、數據庫支持矩陣和可恢復備份是否同時滿足。

required upgrade stop 不是版本清單，而是閘門

GitLab 要求經過特定的 required upgrade stops（必要升級停靠點）。每到一站必須使用該 minor 的最新 patch，完成遷移並讀取該版本的升級説明；不能只把二十多個標籤排成隊然後逐個替換。

我們把每一站視為一個小型變更窗口：

  1. 用當前版本檢查 schema migration 與後台遷移。
  2. 創建此站回滾備份。
  3. 修改鏡像並顯式重建 Pod。
  4. 觀察 reconfigure、Puma、Sidekiq、Gitaly、數據庫和事件。
  5. 執行 gitlab:check、核心對象計數及 HTTP/SSH 冒煙。
  6. 只有全部通過才記錄該站完成。

這樣做看似慢，卻把失敗範圍限制在兩個相鄰版本之間。遇到問題時，能夠回到上一站的鏡像、數據庫 dump 和配置，而不是從 14.x 與 19.x 的巨大差異中猜根因。

最危險的誤判：把 finalized 當成未完成

遷移過程中曾有腳本用下面的條件統計“未完成”任務：

WHERE status <> 3

這在舊版本中看起來可用，但 GitLab 17 後狀態 6 也表示 finalized。舊條件會把已經完成的遷移誤報為失敗，甚至可能讓運維腳本去調用當前版本已不存在的遷移類。

更穩妥的 SQL 是：

SELECT id, job_class_name, table_name, status
FROM batched_background_migrations
WHERE status NOT IN (3, 6);

更推薦在當前 GitLab 版本的 Rails 環境中使用官方模型和 Rake Task，而不是依賴跨版本固定的狀態數字：

gitlab-rails runner '
puts Gitlab::Database::BackgroundMigration::BatchedMigration.unfinished.count
'

gitlab-rake gitlab:background_migrations:list
gitlab-rake gitlab:background_migrations:status

這裏的原則很簡單：不要為了讓計數歸零而把任務手工改成 finished。先確認父遷移、子任務、源業務數據和當前版本實現。只有在完整備份存在、並確認遷移邏輯對現存數據不適用時，才考慮執行該版本官方提供的 finalize 或 execute 任務。

歷史數據為什麼會阻塞後台遷移

實際遇到的另一類問題是，某個任務處理歷史通知數據時，發現記錄時間早於現有月分區範圍。此時“造一條新業務數據讓它通過”或“直接跳過任務”都會污染升級後的數據。

我們的處理順序是：

  1. 定位具體遷移、子任務和源記錄。
  2. 確認這條歷史記錄是否仍有有效業務關聯。
  3. 核對目標表分區邊界與 GitLab 當前版本的遷移邏輯。
  4. 在停寫、備份和可回滾條件下，為合法歷史數據準備兜底分區。
  5. 使用當前版本官方任務重新執行或 finalize。
  6. 重新檢查未完成遷移數和相關數據完整性。

這個案例的價值不在於“加了一個分區”，而在於先判斷數據是否合法、處理是否可逆，再運行當前版本提供的工具。GitLab 的後台遷移與業務數據相連，不能當成普通隊列任務隨意清狀態。

GitLab 19 首次 reconfigure 退出時，不要先刪 Secret

從 GitLab 18 進入 19 時，首次 reconfigure 因歷史組件遺留狀態退出。最危險的反應是直接刪除整份 Secret 或配置，試圖讓 GitLab “自己重新生成”。

我們先保留備份，再區分三種情況：

  • 新版本已經移除了舊組件配置，可以由新版本重新生成不再需要的配置塊。
  • Secret 確實損壞或缺失，需要從受控備份恢復。
  • 數據庫中加密值已經無法被當前 Secret 解密，需要先停下調查，不能覆蓋證據。

確認是第一種情況後再進行下一次啓動，schema migration 隨後正常完成。這裏的經驗是：配置問題、Secret 問題和數據解密問題的外在現象可能都是啓動失敗，但處理方式完全不同。

PostgreSQL 必須跟着 GitLab 分階段走

GitLab 與 PostgreSQL 不能各自獨立升級。本次採取的節奏如下：

階段GitLabPostgreSQL 策略
起點14 / 15保留 Omnibus 內置 PostgreSQL
中段16遷移至外部 PostgreSQL 14
進入 17 前16.11PostgreSQL 14 升至兼容小版本
進入 18 前17.11PostgreSQL 14 → 16
進入 19 前18.11PostgreSQL 16 → 17
終點19.2外部 PostgreSQL 17

GitLab 19 的支持要求應以執行當日的官方安裝要求為準。應用配置明確關閉內置 PostgreSQL，並使用獨立數據庫、賬號和 Secret：

postgresql['enable'] = false
gitlab_rails['db_adapter'] = 'postgresql'
gitlab_rails['db_host'] = 'postgresql.<namespace>.svc.cluster.local'
gitlab_rails['db_port'] = 5432
gitlab_rails['db_database'] = 'gitlabhq_production'
gitlab_rails['db_username'] = 'gitlab'
gitlab_rails['db_password'] = File.read('/run/secrets/gitlab-db/password').strip

大版本升級前先執行檢查：

pg_upgrade \
  --old-datadir=<old-data> \
  --new-datadir=<new-data> \
  --old-bindir=<old-bin> \
  --new-bindir=<new-bin> \
  --check

本次數據卷是支持 reflink 的 XFS，因此實際升級使用 --clone，避免再複製一份完整數據庫：

pg_upgrade \
  --old-datadir=<old-data> \
  --new-datadir=<new-data> \
  --old-bindir=<old-bin> \
  --new-bindir=<new-bin> \
  --clone --jobs=4

--clone 節省的是空間和時間，不是額外備份。舊數據目錄、GitLab 18 的完整恢復點和 GitLab 19 的數據庫保護備份，都必須保留到最終切流和觀察期結束。升級後還要運行 vacuumdb --all --analyze-in-stages --jobs=4，並從 GitLab Rails 內核對實際連接目標和數據庫版本。

磁盤不足時，先定義恢復邊界

在最終版本階段，磁盤剩餘空間不足以再暫存一份完整倉庫歸檔。我們沒有假裝“一切都有完整備份”，而是明確記錄：當前只創建數據庫保護備份，同時保留上一關鍵版本已經校驗過的完整備份、倉庫數據卷和配置歸檔。

這是一項受控取捨。關鍵是知道哪一個備份包含數據庫，哪一個包含倉庫，並在切流前驗證每一個恢復點，而不是把 database-only 備份誤當作完整恢復點。

後台遷移歸零、數據庫版本符合支持矩陣、最終版本啓動穩定後，仍然不能立刻宣佈成功。舊 GitLab 在升級期間繼續接收寫入，最終需要凍結舊實例、識別真實變化的倉庫，再完成精確同步。
